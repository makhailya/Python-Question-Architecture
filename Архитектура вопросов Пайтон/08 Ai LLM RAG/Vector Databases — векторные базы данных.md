# 🗄️ Vector Databases — векторные базы данных

## 🎤 Короткий ответ для собеседования

**Vector Database (векторная база данных)** — это система хранения и поиска данных, представленных в виде числовых векторов — [[embeddings]].

Главная задача векторной базы — **быстро находить наиболее близкие векторы** по заданной метрике расстояния или сходства.

Например, пользователь спрашивает:

> Как исправить ошибку при обработке поставки?

Векторная база позволяет найти документы, близкие по смыслу к этому вопросу, даже если в них используются другие формулировки.

Для поиска применяются:

- **Cosine Similarity** — косинусное сходство.
- **Euclidean Distance (L2)** — евклидово расстояние.
- **Dot Product** — скалярное произведение.

Для ускорения поиска используются индексы, например **HNSW** и **IVFFlat**.

Популярные решения: PostgreSQL + pgvector, Qdrant, Milvus. FAISS — библиотека векторного поиска, а не полноценная СУБД.

## 🗣️ Ответ на собеседовании

Векторная база данных — это хранилище, оптимизированное для поиска похожих объектов по их embeddings.

В отличие от обычного поиска по точному совпадению значений, векторный поиск позволяет находить документы по семантической близости.

Например, в RAG-системе мы разбиваем документацию на фрагменты, вычисляем embeddings и сохраняем их вместе с текстом и метаданными.

Когда пользователь задаёт вопрос, Backend вычисляет embedding запроса, обращается к векторной базе и получает Top-K наиболее близких фрагментов.

Для ускорения поиска на больших объёмах применяются ANN-индексы, например HNSW. Они позволяют находить ближайших соседей быстрее полного перебора, но могут пропускать некоторые результаты.

В PostgreSQL для этого можно использовать расширение pgvector. Оно поддерживает тип `vector`, операции поиска расстояния и индексы HNSW и IVFFlat.

Если приложение уже использует PostgreSQL, я бы сначала рассмотрел pgvector. При больших объёмах векторов, специфических требованиях к масштабированию и высокой поисковой нагрузке можно рассмотреть специализированные решения, например Qdrant.

Важно, что векторная база не генерирует ответы. Она отвечает за retrieval — поиск релевантных данных. Итоговый ответ формирует LLM.

## 📚 Разбор поглубже

### 1. Зачем нужна векторная база данных

Представим, что у нас есть документация Backend-сервиса:

```text
Документ 1:
Как повторно обработать поставку после таймаута.

Документ 2:
Как исправить ошибки валидации товара.

Документ 3:
Как восстановить пароль сотрудника.
```

Пользователь спрашивает:

```text
Поставка не прошла проверку. Что делать?
```

Обычный поиск по словам может не найти второй документ, поскольку в запросе нет слова «валидация».

Но embedding-модель способна преобразовать вопрос и документы в векторы, отражающие их семантические свойства.

```text
Вопрос пользователя
       |
       v
Embedding Model
       |
       v
[0.12, -0.45, 0.78, ...]
       |
       v
Vector Database
       |
       v
Поиск похожих векторов
       |
       v
Документ 2: Ошибки валидации товара
```

**Главная идея:** мы ищем не только одинаковые слова, но и близкие по смыслу представления.

Однако близость по смыслу не гарантирует фактическую правильность найденного документа.

### 2. Что хранится в Vector Database

Векторная база обычно хранит не только embedding, но и идентификатор, метаданные и иногда сам исходный текст.

Пример:

| id | content | embedding | metadata |
|---|---|---|---|
| 1 | Ошибка валидации | [0.12, 0.35, ...] | type=error |
| 2 | Повторная обработка | [0.73, -0.21, ...] | type=retry |
| 3 | Восстановление пароля | [-0.41, 0.62, ...] | type=auth |

Разберём поля.

**id** — уникальный идентификатор записи.

**content** — текст документа или фрагмента.

**embedding** — числовой вектор.

**metadata** — дополнительные свойства, например:

```json
{
  "document_id": 125,
  "service": "supply-validation",
  "version": "2.1",
  "language": "ru"
}
```

Метаданные позволяют ограничивать поиск.

Например, искать только в документации определённого сервиса.

### 3. Как работает векторный поиск

Допустим, в базе хранятся три embeddings:

```text
Документ A → [0.8, 0.7, 0.1]

Документ B → [0.75, 0.72, 0.12]

Документ C → [-0.4, 0.1, 0.9]
```

Поступает запрос:

```text
Query → [0.78, 0.71, 0.11]
```

Векторная база вычисляет расстояние между запросом и документами.

Условно:

```text
Query
  |
  ├── Document A → близко
  |
  ├── Document B → очень близко
  |
  └── Document C → далеко
```

После этого возвращает наиболее подходящие результаты.

Такой процесс называется **Nearest Neighbor Search** — поиск ближайших соседей.

Если нужно вернуть пять результатов, используется `Top-K = 5`.

### 4. Метрики расстояния

Чтобы определить близость векторов, используются математические метрики.

| Метрика | Что измеряет | Что считается лучшим |
|---|---|---|
| Cosine Similarity | Сходство направлений | Больше значение |
| Cosine Distance | Косинусное расстояние | Меньше значение |
| Euclidean Distance | Геометрическое расстояние | Меньше значение |
| Dot Product | Скалярное произведение | Больше значение при поиске по сходству |

**Cosine Similarity**

\[
\cos(A,B)=\frac{A\cdot B}{\|A\|\|B\|}
\]

Для ненулевых векторов значение находится в диапазоне от −1 до 1.

Если векторы нормализованы до единичной длины, cosine similarity совпадает со скалярным произведением.

**Euclidean Distance**

\[
d(A,B)=\sqrt{\sum_{i=1}^{n}(A_i-B_i)^2}
\]

Чем меньше расстояние, тем ближе векторы.

**Важно:** метрику желательно выбирать в соответствии с рекомендациями embedding-модели. Не существует одной универсально лучшей метрики для всех задач.

## 5. Exact Search vs Approximate Search

Это важный вопрос на техническом собеседовании.

Есть два основных подхода к поиску ближайших векторов.

### Exact Nearest Neighbor Search

Точный поиск сравнивает запрос с кандидатами и находит действительно ближайшие векторы.

Упрощённая логика:

```python
for document in documents:
    distance = calculate_distance(query, document.embedding)
```

Если документов миллион, полный перебор требует обработки большого количества векторов.

Для N векторов размерности d стоимость прямого перебора составляет примерно O(N × d), без учёта сортировки или отбора результатов.

Преимущества:

- Точный результат.
- Простая логика.
- Подходит для небольших наборов данных.

Недостаток — высокая стоимость поиска при большом количестве векторов.

### Approximate Nearest Neighbor (ANN)

ANN — приближённый поиск ближайших соседей.

Он использует специальные структуры данных, чтобы не сравнивать запрос со всеми векторами.

Преимущества:

- Высокая скорость поиска на больших объёмах.
- Возможность настройки баланса между скоростью и качеством.

Недостатки:

- Результат может быть приближённым.
- Индексы потребляют дополнительную память и место.
- Требуется настройка параметров.

**Главный компромисс:**

```text
Exact Search
    ↓
Максимальная точность
Но потенциально высокая стоимость

ANN Search
    ↓
Быстрее на больших данных
Но возможен пропуск ближайших соседей
```

## 6. HNSW — индекс для векторного поиска

**HNSW (Hierarchical Navigable Small World)** — графовый алгоритм приближённого поиска ближайших соседей.

Представим, что каждый вектор — это точка, соединённая с другими точками.

Вместо проверки всех точек алгоритм перемещается по графу, постепенно приближаясь к запросу.

Упрощённая схема:

```text
Вектор запроса
      |
      v
Верхний уровень графа
      |
      v
Поиск подходящей области
      |
      v
Нижние уровни графа
      |
      v
Уточнение ближайших соседей
      |
      v
Top-K результатов
```

Основные параметры HNSW в pgvector:

**m** — максимальное количество связей для каждого элемента на уровне графа, с особенностями для нижнего уровня.

**ef_construction** — размер динамического списка кандидатов при построении индекса.

**hnsw.ef_search** — размер списка кандидатов во время поиска.

Чем выше параметры, тем потенциально лучше полнота поиска, но больше расходы памяти, времени построения или выполнения.

Пример PostgreSQL:

```sql
CREATE INDEX documents_embedding_hnsw_idx
ON documents
USING hnsw (embedding vector_cosine_ops);
```

## 7. IVFFlat — альтернативный индекс

**IVFFlat (Inverted File with Flat Compressionless Storage)** — индекс, который группирует векторы в списки по близости.

Упрощённо:

```text
Все векторы
     |
     v
Разделение на группы
     |
     ├── Group A
     ├── Group B
     ├── Group C
     └── Group D
             |
             v
      Поиск по выбранным группам
```

Вместо проверки всех векторов алгоритм исследует наиболее перспективные списки.

В pgvector важные параметры:

- `lists` — количество списков при построении индекса.
- `ivfflat.probes` — количество просматриваемых списков при поиске.

Пример:

```sql
CREATE INDEX documents_embedding_ivfflat_idx
ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

Для качественного построения IVFFlat индекс обычно создают после загрузки достаточного количества данных.

### HNSW vs IVFFlat

| Критерий | HNSW | IVFFlat |
|---|---|---|
| Структура | Многоуровневый граф | Списки векторов |
| Качество поиска | Часто выше при сопоставимой скорости | Зависит от настройки |
| Построение | Обычно дороже | Обычно дешевле |
| Память | Может требовать больше | Часто экономнее |
| Данные до построения | Необязательны | Желательны для обучения групп |
| Подходит для | Быстрого ANN-поиска | Сценариев с подходящим компромиссом ресурсов |

Конкретные результаты нужно проверять бенчмарками на своих данных.

## 8. PostgreSQL + pgvector

Для Backend-разработчика, который уже использует PostgreSQL, pgvector — один из самых доступных способов начать работу с векторным поиском.

**pgvector** — расширение PostgreSQL, добавляющее векторные типы, операции расстояния и индексы.

### Шаг 1. Подключаем расширение

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Расширение должно быть установлено на сервере PostgreSQL.

### Шаг 2. Создаём таблицу

```sql
CREATE TABLE documents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(384) NOT NULL
);
```

Здесь:

`id` — идентификатор документа.

`content` — исходный текст.

`embedding VECTOR(384)` — вектор из 384 чисел.

**Важно:** размерность должна соответствовать embedding-модели.

### Шаг 3. Добавляем данные

Для простоты используем трёхмерные векторы в отдельной демонстрационной таблице.

```sql
CREATE TABLE demo_documents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(3) NOT NULL
);
```

```sql
INSERT INTO demo_documents (content, embedding)
VALUES
    ('Возврат товара', '[0.8, 0.7, 0.1]'),
    ('Обработка поставки', '[0.75, 0.72, 0.12]'),
    ('Восстановление пароля', '[-0.4, 0.1, 0.9]');
```

### Шаг 4. Выполняем поиск

```sql
SELECT
    id,
    content,
    embedding <=> '[0.78, 0.71, 0.11]' AS distance
FROM demo_documents
ORDER BY embedding <=> '[0.78, 0.71, 0.11]'
LIMIT 2;
```

Оператор `<=>` вычисляет косинусное расстояние.

Чем меньше расстояние, тем ближе векторы.

`LIMIT 2` возвращает два ближайших результата.

**Это демонстрационные векторы**, а не результат реальной embedding-модели.

### 9. Основные операторы pgvector

| Оператор | Значение |
|---|---|
| `<->` | L2 distance |
| `<#>` | Отрицательное скалярное произведение |
| `<=>` | Cosine distance |
| `<+>` | Manhattan (L1) distance |

Почему `<#>` возвращает отрицательное скалярное произведение?

Потому что PostgreSQL использует сортировку по возрастанию для индексного поиска, а для обычного dot product наиболее похожие векторы имеют большее значение.

Поэтому отрицательное значение позволяет использовать подходящий порядок сортировки.

Пример cosine similarity:

```sql
SELECT
    content,
    1 - (embedding <=> '[0.78, 0.71, 0.11]') AS similarity
FROM demo_documents
ORDER BY embedding <=> '[0.78, 0.71, 0.11]'
LIMIT 3;
```

## 10. Векторная база и обычная реляционная БД

| Характеристика | Реляционная БД | Векторная БД |
|---|---|---|
| Основные данные | Таблицы и отношения | Векторы и связанные данные |
| Типичные запросы | SQL, JOIN, фильтры | Similarity Search |
| Индексы | B-tree, GIN и другие | HNSW, IVFFlat и другие |
| Основная задача | Транзакции и структурированные данные | Поиск близких объектов |
| Пример | PostgreSQL | Qdrant |

При этом это не строго взаимоисключающие категории.

PostgreSQL с pgvector умеет выполнять и SQL-запросы, и векторный поиск.

А специализированные векторные базы также могут поддерживать фильтрацию по метаданным и другие операции с данными.

## 11. PostgreSQL + pgvector vs Qdrant vs FAISS

### PostgreSQL + pgvector

Преимущества:

- Можно использовать существующую инфраструктуру PostgreSQL.
- SQL, JOIN и транзакции.
- Возможность объединять бизнес-данные и embeddings.
- Удобен для небольших и средних RAG-систем, а также многих крупных систем при грамотной настройке.

Недостатки:

- Векторная нагрузка конкурирует за ресурсы с обычными SQL-запросами.
- Масштабирование и настройка больших ANN-индексов требуют внимания.

### Qdrant

Специализированная векторная база данных.

Преимущества:

- API для векторного поиска.
- Фильтрация по метаданным.
- Поддержка HNSW.
- Возможности распределённого развёртывания.

Недостатки:

- Дополнительный сервис в инфраструктуре.
- Отдельная система хранения, резервного копирования и мониторинга.
- При наличии PostgreSQL может потребоваться синхронизация данных между двумя хранилищами.

### FAISS

Библиотека для эффективного поиска ближайших соседей.

Преимущества:

- Разные алгоритмы и структуры векторного поиска.
- Подходит для локальных экспериментов и поисковых компонентов.
- Может работать без отдельного сервера БД.

Ограничения:

- Не является полноценной СУБД с готовой моделью многопользовательского доступа и привычными возможностями транзакционной базы.
- Хранение метаданных, API и жизненный цикл индексов часто нужно организовывать самостоятельно.

### Что выбрать?

| Сценарий | Разумный старт |
|---|---|
| Backend уже работает на PostgreSQL | pgvector |
| Нужен отдельный специализированный векторный сервис | Qdrant |
| Локальный прототип поиска | FAISS |
| Крупная распределённая векторная инфраструктура | Qdrant или Milvus, после оценки требований |

**Для большинства первых RAG-проектов на FastAPI и PostgreSQL я бы начал с pgvector**, если нет специальных требований к отдельному векторному хранилищу.

## 12. Metadata Filtering — фильтрация по метаданным

В реальных RAG-системах недостаточно искать только по близости векторов.

Представим корпоративную документацию.

Есть документы:

```text
supply-service
warehouse-service
payment-service
```

Пользователь задаёт вопрос об ошибке поставки.

Нужно искать только в документации `supply-service`.

В PostgreSQL можно добавить поле:

```sql
ALTER TABLE documents
ADD COLUMN service_name TEXT;
```

И выполнять поиск:

```sql
SELECT
    content,
    embedding <=> $1 AS distance
FROM documents
WHERE service_name = 'supply-service'
ORDER BY embedding <=> $1
LIMIT 5;
```

Здесь `$1` — параметр запроса с вектором нужной размерности.

Важный нюанс: при ANN-поиске фильтрация может влиять на полноту результатов и план выполнения. В pgvector иногда требуется настройка параметров поиска или использование дополнительных механизмов для фильтруемых запросов.

### Фильтрация по правам доступа

Если пользователь не имеет права читать документ, этот документ не должен попадать в результаты retrieval.

Векторная близость не отменяет авторизацию.

Например:

```text
User A → документы отдела A

User B → документы отдела B
```

Поиск должен учитывать права доступа до передачи фрагментов в LLM.

## 13. Как Vector Database используется в RAG

Полный процесс состоит из двух частей.

### Indexing Pipeline

```text
PDF / Markdown / HTML
          |
          v
    Document Loader
          |
          v
       Chunking
          |
          v
    Embedding Model
          |
          v
    Vector Database
```

На этом этапе документы подготавливаются и индексируются.

### Retrieval Pipeline

```text
Вопрос пользователя
         |
         v
   Embedding Model
         |
         v
   Vector Database
         |
         v
   Similarity Search
         |
         v
   Top-K Documents
         |
         v
      Reranker
         |
         v
   Контекст для LLM
         |
         v
        LLM
         |
         v
   Ответ пользователю
```

**Reranker** — дополнительная модель или алгоритм, который повторно оценивает найденные документы и уточняет их порядок.

Он не обязателен, но часто помогает улучшить качество retrieval.

## 14. Hybrid Search — гибридный поиск

Векторный поиск не всегда хорошо работает с точными значениями.

Например:

```text
SUPPLY_VALIDATION_1042
```

Это код ошибки.

Векторный поиск может найти семантически похожие документы, но не обязательно документ с точным кодом.

Поэтому используется **Hybrid Search**.

```text
Вопрос пользователя
        |
        ├── Semantic Search
        |       |
        |       v
        |   Vector Database
        |
        └── Keyword Search
                |
                v
            Full-Text Search
                |
                v
        Объединение результатов
                |
                v
             Reranking
                |
                v
              Top-K
```

В PostgreSQL можно сочетать pgvector с полнотекстовым поиском через `tsvector` и `tsquery`.

Для объединения результатов иногда применяют **Reciprocal Rank Fusion (RRF)**.

RRF учитывает позиции документов в разных ранжированных списках, а не требует напрямую сравнивать несовместимые оценки сходства.

## 15. Практический Backend-пример на Python

Представим, что у нас есть FastAPI-сервис и PostgreSQL с pgvector.

Логика обработки запроса:

1. Получить вопрос пользователя.
2. Вычислить embedding.
3. Выполнить векторный поиск.
4. Получить релевантные документы.
5. Передать документы в LLM.
6. Вернуть ответ.

Упрощённый пример поиска с Ollama и psycopg:

```python
import ollama
import psycopg
from pgvector.psycopg import register_vector


MODEL = "nomic-embed-text"


def get_embedding(text: str) -> list[float]:
    response = ollama.embed(
        model=MODEL,
        input=text,
    )

    return response["embeddings"][0]


def search_documents(
    question: str,
    connection: psycopg.Connection,
    limit: int = 5,
) -> list[tuple]:
    embedding = get_embedding(question)

    with connection.cursor() as cursor:
        cursor.execute(
            """
            SELECT
                id,
                content,
                embedding <=> %s AS distance
            FROM documents
            ORDER BY embedding <=> %s
            LIMIT %s
            """,
            (embedding, embedding, limit),
        )

        return cursor.fetchall()


with psycopg.connect(
    "postgresql://postgres:postgres@localhost:5432/rag_db"
) as connection:
    register_vector(connection)

    results = search_documents(
        question="Как исправить ошибку поставки?",
        connection=connection,
    )

    for document_id, content, distance in results:
        print(document_id, distance, content)
```

Для примера нужны пакеты:

```bash
pip install ollama "psycopg[binary]" pgvector
```

Также требуется запущенный Ollama, загруженная модель `nomic-embed-text`, PostgreSQL с расширением pgvector и таблица `documents` с векторами соответствующей размерности.

### Разбор

`get_embedding()` — преобразует вопрос в вектор.

`psycopg.connect()` — подключается к PostgreSQL.

`register_vector(connection)` — регистрирует адаптацию векторного типа для psycopg.

`cursor.execute()` — выполняет SQL-запрос.

`embedding <=> %s` — вычисляет косинусное расстояние между сохранённым embedding и вектором вопроса.

`ORDER BY` — сортирует результаты от наиболее близких к наиболее далёким.

`LIMIT` — ограничивает количество результатов.

`fetchall()` — возвращает найденные строки.

**Обрати внимание:** этот пример реализует только retrieval. Генерация ответа через LLM — следующий этап RAG.

## 16. Как оценивать качество векторного поиска

Векторный поиск нужно оценивать не только по скорости.

Основные метрики:

**Recall@K** — сколько релевантных результатов удалось найти среди первых K.

**Precision@K** — какая доля первых K результатов действительно релевантна.

**MRR (Mean Reciprocal Rank)** — насколько высоко находится первый релевантный результат.

**Latency** — время выполнения поиска.

**QPS (Queries Per Second)** — количество запросов в секунду.

Для ANN-индексов особенно важен баланс:

```text
Скорость поиска
      ↕
Полнота результатов
```

Слишком агрессивная оптимизация может ускорить поиск, но ухудшить качество retrieval.

## 17. Типичные ошибки

**Ошибка 1. Считать Vector Database генеративной моделью.**

Векторная база ищет данные. Она не обязана генерировать ответы.

**Ошибка 2. Считать, что Vector Database сама создаёт embeddings.**

Обычно embeddings вычисляет отдельная модель. Некоторые платформы предлагают встроенные механизмы векторизации, но это дополнительная возможность.

**Ошибка 3. Смешивать embeddings разных моделей.**

Несовместимые модели формируют разные векторные пространства. Их результаты нельзя произвольно сравнивать.

**Ошибка 4. Считать ANN точным поиском.**

ANN ускоряет поиск ценой возможного снижения полноты.

**Ошибка 5. Игнорировать метаданные.**

Без фильтрации поиск может возвращать документы не того сервиса, версии или пользователя.

**Ошибка 6. Использовать только векторный поиск для кодов ошибок.**

Для точных идентификаторов часто лучше подходит гибридный поиск.

**Ошибка 7. Не обновлять embeddings после изменения документа.**

Если текст изменился, старый вектор может перестать соответствовать актуальному содержимому.

**Ошибка 8. Денормализовать или переносить всё в отдельную Vector Database без необходимости.**

Если PostgreSQL с pgvector удовлетворяет требованиям, отдельный сервис может только усложнить архитектуру.

**Ошибка 9. Не учитывать права доступа.**

Релевантный документ не обязательно разрешён конкретному пользователю.

## 🎤 Вопросы на собеседовании

**1. Что такое Vector Database?**

Система хранения и поиска данных по векторным представлениям.

**2. Зачем нужна векторная база?**

Для быстрого поиска похожих объектов, например документов по смыслу.

**3. Что такое embedding?**

Числовой вектор, представляющий семантические или другие свойства данных.

**4. Что такое Similarity Search?**

Поиск наиболее близких векторов по выбранной метрике.

**5. Что такое Top-K?**

Количество ближайших результатов, возвращаемых поиском.

**6. Что такое HNSW?**

Графовый индекс для приближённого поиска ближайших соседей.

**7. Что такое IVFFlat?**

Индекс, который группирует векторы в списки и ищет по выбранным группам.

**8. Чем ANN отличается от Exact Search?**

ANN выполняет приближённый поиск быстрее на больших данных, но может пропустить некоторые ближайшие результаты.

**9. Что такое pgvector?**

Расширение PostgreSQL для хранения векторов и векторного поиска.

**10. Чем pgvector отличается от Qdrant?**

pgvector расширяет PostgreSQL, а Qdrant — отдельная специализированная векторная база.

**11. Что такое Metadata Filtering?**

Ограничение результатов поиска по дополнительным атрибутам документов.

**12. Что такое Hybrid Search?**

Объединение семантического и лексического поиска.

**13. Что такое Reranking?**

Повторная оценка найденных документов для улучшения их порядка.

**14. Как Vector Database используется в RAG?**

Хранит embeddings документов и возвращает релевантные фрагменты для передачи в LLM.

**15. Почему нельзя использовать разные embedding-модели для документов и запросов?**

Потому что их векторные пространства могут быть несовместимы, если модели специально не обучены для совместной работы.

**16. Что такое Recall@K?**

Метрика полноты поиска среди первых K результатов.

**17. Что выбрать для Backend на PostgreSQL?**

Часто разумно начать с pgvector, а специализированную базу выбирать при подтверждённых требованиях.
