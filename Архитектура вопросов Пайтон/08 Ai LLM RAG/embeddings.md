# 🧠 Embeddings — векторные представления данных

## 🎤 Короткий ответ для собеседования

**Embeddings (эмбеддинги)** — это числовые векторные представления текста, изображений или других данных, которые позволяют сравнивать объекты по их смысловой близости.

Embedding-модель преобразует входные данные в вектор фиксированной размерности.

Например:

```text
"Как оформить возврат товара?"
             ↓
      Embedding Model
             ↓
[0.12, -0.35, 0.78, 0.21, ...]
```

Тексты с близким смыслом обычно получают близкие векторы.

Embeddings применяются для:

- Семантического поиска (Semantic Search).
- RAG — Retrieval-Augmented Generation.
- Поиска похожих документов.
- Рекомендательных систем.
- Кластеризации и классификации данных.

Для сравнения векторов часто используют **Cosine Similarity** — косинусное сходство.

## 🗣️ Ответ на собеседовании

Embeddings — это способ представить текст или другие данные в виде числовых векторов, которые отражают семантические свойства исходного содержимого.

Например, фразы «Как вернуть товар?» и «Как оформить возврат покупки?» имеют разную формулировку, но близкий смысл. Хорошая embedding-модель должна размещать их в близких областях векторного пространства.

В Backend embeddings часто применяются в RAG-системах. Документы разбиваются на фрагменты, для каждого вычисляется embedding, после чего векторы сохраняются в векторном хранилище, например PostgreSQL с расширением pgvector.

Когда пользователь задаёт вопрос, мы вычисляем embedding запроса, ищем наиболее близкие фрагменты и передаём найденный контекст в LLM для генерации ответа.

Для поиска используются метрики близости, например cosine similarity, а при больших объёмах данных — приближённые индексы, такие как HNSW.

Важно, что embedding-модель сама по себе не генерирует ответ. Она преобразует данные в векторы для дальнейшего поиска или анализа.

## 1. Что такое embedding простыми словами

Представим, что у нас есть три предложения:

```text
1. Кошка спит на диване.

2. Кот отдыхает на кровати.

3. PostgreSQL использует индексы.
```

Для человека очевидно:

- Первое и второе предложения близки по смыслу.
- Третье относится к совершенно другой теме.

Но компьютер не понимает смысл предложений так, как человек.

Embedding-модель преобразует предложения в числовые векторы.

Условный пример:

```text
Кошка спит на диване
    ↓
[0.8, 0.7, 0.1]

Кот отдыхает на кровати
    ↓
[0.75, 0.72, 0.12]

PostgreSQL использует индексы
    ↓
[-0.4, 0.1, 0.9]
```

Первые два вектора похожи друг на друга.

Третий отличается.

**Важно:** числа приведены исключительно для иллюстрации. Реальные модели обычно возвращают сотни или тысячи чисел, а отдельные координаты не имеют очевидного человеку значения.

## 2. Что такое вектор

Вектор — это упорядоченный набор чисел.

Например:

```python
vector = [0.2, -0.5, 0.8]
```

Здесь три числа, значит, вектор трёхмерный.

В embedding-моделях размерность может составлять, например:

- 384.
- 768.
- 1024.
- 1536.
- 3072.

Конкретная размерность зависит от модели и её конфигурации.

Например:

```python
embedding = [0.12, -0.35, 0.78, ...]
```

Если модель возвращает 768 чисел, говорят, что размерность embedding равна 768.

**Размерность не равна количеству слов в тексте.**

И короткая фраза, и длинный документ могут преобразовываться в векторы одинаковой размерности, если модель поддерживает соответствующую длину входа.

## 3. Как создаётся embedding

Упрощённый процесс:

```text
Входной текст
     |
     v
Токенизация
     |
     v
Embedding-модель
     |
     v
Вектор фиксированной размерности
```

### Шаг 1. Токенизация

Текст преобразуется в токены — элементы, с которыми работает модель.

Например:

```text
"Как вернуть товар?"
```

Модель разбивает текст на токены согласно своему токенизатору.

Токены не обязательно совпадают с целыми словами.

### Шаг 2. Обработка моделью

Нейронная сеть анализирует входную последовательность и формирует внутренние представления.

### Шаг 3. Получение вектора

Модель возвращает числовой вектор, представляющий весь текст или другой выбранный объект.

Способ формирования итогового вектора зависит от архитектуры модели: это может быть специальный токен, pooling по токенам или другой механизм.

## 4. Как сравнивать embeddings

Допустим, у нас есть два вектора:

```python
a = [1, 0]
b = [0.9, 0.1]
```

Они направлены примерно в одну сторону.

А теперь:

```python
c = [0, 1]
```

Этот вектор направлен перпендикулярно первому.

Чтобы оценить близость, можно использовать косинусное сходство.

### Cosine Similarity

Формула:

\[
\operatorname{cosine}(A,B)=\frac{A\cdot B}{\|A\|\|B\|}
\]

Где:

- \(A \cdot B\) — скалярное произведение.
- \(\|A\|\) — длина первого вектора.
- \(\|B\|\) — длина второго вектора.

Для ненулевых векторов результат находится от −1 до 1.

| Значение | Интерпретация |
|---|---|
| Близко к 1 | Векторы направлены почти одинаково |
| Близко к 0 | Векторы почти ортогональны |
| Близко к −1 | Векторы направлены противоположно |

Это математическая интерпретация. Семантический смысл конкретного значения зависит от модели, данных и задачи.

### Пример на Python

```python
import math


def cosine_similarity(a: list[float], b: list[float]) -> float:
    if len(a) != len(b):
        raise ValueError("Размерности векторов должны совпадать")

    dot_product = sum(x * y for x, y in zip(a, b))

    norm_a = math.sqrt(sum(x ** 2 for x in a))
    norm_b = math.sqrt(sum(y ** 2 for y in b))

    if norm_a == 0 or norm_b == 0:
        raise ValueError("Нельзя вычислить cosine для нулевого вектора")

    return dot_product / (norm_a * norm_b)


vector_a = [1.0, 0.0]
vector_b = [0.9, 0.1]

print(cosine_similarity(vector_a, vector_b))
```

Результат приблизительно:

```text
0.9939
```

### Разбор логики

`zip(a, b)` — объединяет соответствующие элементы двух векторов в пары.

`x * y` — перемножает соответствующие координаты.

`sum(...)` — вычисляет скалярное произведение.

`math.sqrt(...)` — вычисляет квадратный корень, необходимый для определения длины вектора.

В конце мы делим скалярное произведение на произведение длин векторов.

**Сложность алгоритма:** O(d), где d — размерность вектора.

## 5. Cosine Similarity vs Euclidean Distance vs Dot Product

Для поиска похожих векторов существуют разные метрики.

| Метрика | Что измеряет | Особенность |
|---|---|---|
| Cosine Similarity | Сходство направлений | Не зависит от масштаба ненулевых векторов |
| Euclidean Distance | Геометрическое расстояние | Учитывает расстояние между координатами |
| Dot Product | Скалярное произведение | Учитывает направление и длину векторов |

**Cosine Similarity** часто используют в семантическом поиске.

**Euclidean Distance (L2)** измеряет прямое расстояние между точками.

**Dot Product** особенно удобен для нормализованных векторов: при единичной длине обоих векторов он совпадает с cosine similarity.

Выбор метрики зависит от того, как обучалась embedding-модель и какую метрику рекомендует её разработчик.

## 6. Embeddings и обычный текстовый поиск

Представим, что пользователь ищет:

```text
Как оформить возврат товара?
```

В базе есть документ:

```text
Покупатель может вернуть приобретённую продукцию
в течение установленного срока.
```

### Обычный поиск

Например, поиск по совпадению слов может не найти документ, если слова запроса и документа различаются.

### Семантический поиск

Embedding-модель может определить смысловую близость между вопросом и документом.

```text
Вопрос пользователя
        |
        v
    Embedding
        |
        v
Сравнение с векторами документов
        |
        v
Наиболее близкие документы
```

**Важно:** семантический поиск не всегда лучше полнотекстового.

Для точных идентификаторов, артикулов, кодов ошибок и названий часто полезнее поиск по ключевым словам.

Поэтому на практике нередко используют **Hybrid Search** — комбинацию полнотекстового и векторного поиска.

## 7. Как embeddings используются в RAG

RAG расшифровывается как **Retrieval-Augmented Generation** — генерация с дополнением найденным контекстом.

Это одна из главных областей применения embeddings в Backend.

RAG обычно состоит из двух процессов:

1. Подготовка документов (Indexing).
2. Поиск и генерация ответа (Retrieval + Generation).

### Этап 1. Подготовка документов

```text
Документы
    |
    v
Разбиение на фрагменты (Chunking)
    |
    v
Embedding-модель
    |
    v
Векторы фрагментов
    |
    v
Vector Database
```

Например, у нас есть документация по обработке поставок.

```text
Документ: Ошибки при приёмке поставок
```

Разбиваем его на небольшие фрагменты:

```text
Chunk 1: Ошибки валидации товара

Chunk 2: Повторная обработка поставки

Chunk 3: Ошибки складской интеграции
```

Для каждого фрагмента вычисляем embedding.

Затем сохраняем:

```text
chunk_id
document_id
text
embedding
metadata
```

### Этап 2. Обработка вопроса

Пользователь спрашивает:

```text
Почему поставка не прошла валидацию?
```

Процесс:

```text
Вопрос пользователя
        |
        v
Embedding вопроса
        |
        v
Vector Search
        |
        v
Top-K подходящих фрагментов
        |
        v
Формирование контекста
        |
        v
LLM
        |
        v
Ответ пользователю
```

**Top-K** означает, что мы выбираем K наиболее близких результатов.

Например, `top_k = 5` — пять фрагментов.

После этого LLM получает вопрос и найденный контекст.

Embedding-модель не формирует окончательный ответ — это делает генеративная модель.

## 8. Chunking — зачем разбивать документы

Почему нельзя просто создать один embedding для огромного документа?

Потому что большой документ может содержать несколько разных тем.

Например:

```text
Документация
├── Авторизация
├── Работа с API
├── Ошибки
├── Логирование
└── Мониторинг
```

Если создать один вектор для всего документа, конкретные детали могут потеряться в общем представлении.

Поэтому документ делят на фрагменты — chunks.

Например:

```text
Chunk 1 → Авторизация

Chunk 2 → Работа с API

Chunk 3 → Ошибки

Chunk 4 → Логирование
```

### Основные параметры

**Chunk Size** — размер фрагмента.

**Chunk Overlap** — перекрытие между соседними фрагментами.

Пример:

```text
Chunk 1: [токены 1–500]

Chunk 2: [токены 401–900]

Chunk 3: [токены 801–1300]
```

Перекрытие помогает сохранить контекст на границах фрагментов.

Но слишком большое перекрытие увеличивает количество векторов и может приводить к избыточным результатам поиска.

Размер фрагментов нужно подбирать экспериментально под документы и типы вопросов.

## 9. Vector Database — где хранить embeddings

Embeddings можно хранить в специализированных векторных базах или в обычных БД с поддержкой векторного поиска.

Популярные варианты:

| Инструмент | Назначение |
|---|---|
| PostgreSQL + pgvector | Векторный поиск внутри PostgreSQL |
| Qdrant | Специализированная векторная БД |
| FAISS | Библиотека поиска по векторам |
| Milvus | Система векторного поиска |

Для Python Backend с PostgreSQL часто удобно начать с **pgvector**.

Это позволяет хранить обычные бизнес-данные и embeddings в одной базе.

### Пример PostgreSQL + pgvector

Подключим расширение:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Создадим таблицу:

```sql
CREATE TABLE documents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(384)
);
```

Здесь `VECTOR(384)` означает, что каждый вектор содержит 384 координаты.

Размерность должна соответствовать используемой модели.

Поиск похожих документов:

```sql
SELECT
    id,
    content,
    embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;
```

Здесь показан шаблон запроса: многоточие нужно заменить полным вектором правильной размерности.

Оператор `<=>` в pgvector вычисляет **косинусное расстояние**.

Чем меньше расстояние, тем ближе векторы по этой метрике.

Для косинусного сходства можно использовать:

```sql
1 - (embedding <=> query_vector)
```

где `query_vector` — вектор запроса.

## 10. Индексы HNSW и IVFFlat

Если документов немного, можно искать ближайшие векторы точным перебором.

Но при миллионах embeddings полный перебор может оказаться дорогим.

Для ускорения применяются ANN-индексы.

**ANN (Approximate Nearest Neighbor)** — приближённый поиск ближайших соседей.

Он ускоряет поиск, допуская вероятность того, что некоторые истинно ближайшие результаты не попадут в выдачу.

### HNSW

Hierarchical Navigable Small World — графовая структура для приближённого поиска.

Пример индекса pgvector:

```sql
CREATE INDEX documents_embedding_hnsw_idx
ON documents
USING hnsw (embedding vector_cosine_ops);
```

Преимущества:

- Быстрый приближённый поиск.
- Хорошее соотношение скорости и качества поиска во многих сценариях.

Недостатки:

- Дополнительное потребление памяти.
- Стоимость построения и обслуживания индекса.
- Не гарантирует нахождение всех точных ближайших соседей.

### IVFFlat

Другой подход — группировка векторов в списки и поиск по выбранным группам.

В pgvector также поддерживается индекс IVFFlat.

Выбор между HNSW, IVFFlat и точным поиском зависит от объёма данных, частоты обновлений, ограничений по памяти и требуемого recall.

**Recall** здесь — доля действительно релевантных ближайших результатов, найденных алгоритмом.

## 11. Практический пример на Python с Ollama

Рассмотрим локальное получение embeddings.

Для этого потребуется запущенный Ollama и установленная embedding-модель, например `nomic-embed-text`.

Сначала в терминале:

```bash
ollama pull nomic-embed-text
```

Установим Python-клиент:

```bash
pip install ollama
```

Код:

```python
import ollama


text = "Как оформить возврат товара?"

response = ollama.embed(
    model="nomic-embed-text",
    input=text,
)

embedding = response["embeddings"][0]

print("Размерность:", len(embedding))
print("Первые координаты:", embedding[:5])
```

### Пошаговый разбор

`import ollama` — подключаем Python-клиент Ollama.

`text` — исходный текст, который нужно преобразовать в вектор.

`ollama.embed()` — отправляет запрос локальному серверу Ollama для вычисления embedding.

`model` — название embedding-модели.

`input` — текст для обработки.

`response["embeddings"][0]` — извлекает первый вектор из результата.

`len(embedding)` — показывает размерность.

`embedding[:5]` — выводит первые пять координат.

**Важно:** для качественного поиска запросы и документы обычно нужно кодировать одной и той же совместимой моделью и с соблюдением её рекомендаций. Некоторые модели используют разные префиксы или режимы для запросов и документов.

### 12. Мини-проект: семантический поиск без векторной БД

Сначала разберём логику.

У нас есть три документа:

```text
1. Как оформить возврат товара
2. Как восстановить пароль
3. Как оплатить заказ
```

Пользователь задаёт вопрос.

Нужно:

1. Получить embedding каждого документа.
2. Получить embedding вопроса.
3. Вычислить cosine similarity.
4. Выбрать документ с максимальным сходством.

```python
import math
import ollama


MODEL = "nomic-embed-text"

documents = [
    "Инструкция по возврату товара и оформлению возврата денег",
    "Инструкция по восстановлению пароля пользователя",
    "Способы оплаты заказа банковской картой",
]


def get_embedding(text: str) -> list[float]:
    response = ollama.embed(
        model=MODEL,
        input=text,
    )

    return response["embeddings"][0]


def cosine_similarity(a: list[float], b: list[float]) -> float:
    if len(a) != len(b):
        raise ValueError("Размерности векторов не совпадают")

    dot_product = sum(x * y for x, y in zip(a, b))

    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))

    if norm_a == 0 or norm_b == 0:
        raise ValueError("Нулевой вектор")

    return dot_product / (norm_a * norm_b)


document_embeddings = [
    get_embedding(document)
    for document in documents
]

question = "Как мне вернуть покупку?"

question_embedding = get_embedding(question)

results = []

for document, embedding in zip(documents, document_embeddings):
    score = cosine_similarity(question_embedding, embedding)

    results.append((score, document))

results.sort(reverse=True)

for score, document in results:
    print(f"{score:.4f} | {document}")
```

Ожидаемая логика результата:

```text
Наиболее близкий документ → инструкция по возврату
```

Конкретные оценки сходства зависят от модели.

### Почему этот пример полезен

Он показывает базовый принцип векторного поиска без дополнительной инфраструктуры.

Но в реальном Backend-приложении не стоит пересчитывать embeddings всех документов при каждом запросе.

Обычно embeddings документов вычисляют заранее и сохраняют.

При поступлении вопроса рассчитывают только embedding запроса, а поиск выполняют по сохранённым векторам.

## 13. Embeddings vs LLM

Это частый вопрос на собеседовании.

| Embedding-модель | Генеративная LLM |
|---|---|
| Преобразует данные в вектор | Генерирует текст |
| Используется для поиска и сравнения | Используется для ответа и рассуждения |
| Результат — набор чисел | Результат — токены текста |
| Например, поиск похожих документов | Например, объяснение ошибки |
| Обычно не отвечает на вопрос напрямую | Может сформировать ответ |

Пример RAG:

```text
Embedding Model → нашла релевантные документы

LLM → сформировала ответ на основе документов
```

Это разные компоненты системы.

## 14. Embeddings vs Fine-tuning

Эти понятия тоже часто путают.

**Embeddings** — способ представить данные в виде векторов.

**Fine-tuning** — дополнительное обучение модели на подготовленных данных.

Например, если мы добавили в RAG новую документацию и рассчитали её embeddings, мы **не обучили LLM заново**.

Мы лишь сделали новые документы доступными для поиска.

Это одно из преимуществ RAG: знания можно обновлять без повторного обучения генеративной модели.

## 15. Основные проблемы embeddings

### Семантическая близость не равна фактической правильности

Два текста могут быть похожими по смыслу, но содержать противоположные утверждения.

Например:

```text
Возврат разрешён.

Возврат запрещён.
```

Embedding-модель может расположить их близко, поскольку оба текста относятся к возвратам.

Поэтому найденные документы не следует автоматически считать правильным ответом.

### Ошибки в точных идентификаторах

Векторный поиск может плохо различать похожие коды:

```text
ERR-1001

ERR-1002
```

Для таких случаев полезен гибридный поиск с точным сопоставлением.

### Неправильный Chunking

Если фрагменты слишком маленькие, может теряться контекст.

Если слишком большие — ухудшаться точность поиска и увеличиваться стоимость обработки.

### Смена embedding-модели

Нельзя без проверки смешивать в одном поисковом пространстве embeddings разных несовместимых моделей.

Даже если размерности совпадают, координаты могут иметь совершенно другую семантику.

При смене модели обычно требуется повторно вычислить embeddings документов и перестроить соответствующие индексы.

### Устаревшие документы

Embedding отражает содержимое текста на момент его обработки.

Если документ изменился, вектор нужно обновить.

### Ограничения доступа

В корпоративном RAG нельзя выдавать пользователю фрагменты документов, на которые у него нет прав.

Поэтому векторный поиск необходимо сочетать с фильтрацией по правам доступа.

## 16. Как оценивать качество поиска

Высокая cosine similarity сама по себе не доказывает, что RAG работает хорошо.

Для оценки retrieval используют:

- **Recall@K** — сколько релевантных документов найдено среди первых K результатов.
- **Precision@K** — какая доля первых K результатов релевантна.
- **MRR** — насколько высоко расположен первый релевантный результат.
- **Latency** — время поиска.
- **Recall–Latency trade-off** — компромисс между полнотой и скоростью.

Для оценки итоговой RAG-системы дополнительно проверяют:

- Насколько ответ соответствует найденным источникам.
- Не добавляет ли LLM неподтверждённые факты.
- Правильно ли система обрабатывает отсутствие ответа.
- Соблюдаются ли ограничения доступа.

## 17. Типичные ошибки на собеседовании

**Ошибка 1. «Embedding — это просто список случайных чисел».**

Нет. Вектор вычисляется обученной моделью и представляет свойства входных данных.

**Ошибка 2. «Embedding-модель отвечает на вопросы».**

Обычно нет. Она преобразует входные данные в векторы.

**Ошибка 3. «Чем выше cosine similarity, тем ответ точно правильнее».**

Нет. Сходство векторов — это сигнал для поиска, а не гарантия достоверности.

**Ошибка 4. «В RAG мы обучаем LLM на документах».**

В стандартном RAG документы индексируются и используются как внешний контекст, без обязательного изменения весов LLM.

**Ошибка 5. «Все embeddings можно сравнивать между собой».**

Нет. Нужны совместимые векторные пространства.

**Ошибка 6. «Векторная БД обязательна для любого RAG».**

Нет. Для небольших наборов документов можно использовать обычный перебор или библиотеку поиска.

**Ошибка 7. «Векторный поиск всегда лучше полнотекстового».**

Нет. Для точных терминов, идентификаторов и кодов ошибок полнотекстовый или гибридный поиск может работать лучше.

## 🎤 Вопросы на собеседовании

**1. Что такое embeddings?**

Числовые векторные представления данных, позволяющие сравнивать их семантические свойства.

**2. Что такое размерность embedding?**

Количество координат вектора, определяемое моделью.

**3. Как сравнивать embeddings?**

Например, через cosine similarity, Euclidean distance или dot product.

**4. Что такое cosine similarity?**

Метрика, измеряющая сходство направлений двух ненулевых векторов.

**5. Как embeddings используются в RAG?**

Для преобразования документов и запроса в векторы, поиска релевантных фрагментов и передачи их в LLM.

**6. Что такое Chunking?**

Разбиение документов на фрагменты перед индексированием.

**7. Что такое Vector Database?**

Хранилище или система, поддерживающая эффективный поиск по векторам.

**8. Что такое pgvector?**

Расширение PostgreSQL для хранения векторов и выполнения векторного поиска.

**9. Что такое HNSW?**

Графовый индекс для приближённого поиска ближайших векторов.

**10. Чем embeddings отличаются от LLM?**

Embedding-модель создаёт числовые представления, а генеративная LLM формирует текст.

**11. Нужно ли обучать LLM при добавлении документов в RAG?**

Нет, в стандартном RAG достаточно обработать и проиндексировать документы.

**12. Можно ли сравнивать embeddings разных моделей?**

Как правило, нет, если модели не обеспечивают совместимость представлений.

**13. Что такое Hybrid Search?**

Комбинация семантического векторного и лексического поиска.

**14. Что такое Top-K?**

Количество наиболее близких результатов, возвращаемых поиском.

**15. Как оценить качество embedding-поиска?**

С помощью тестового набора запросов и метрик, например Recall@K, Precision@K и MRR.

```text
Текст
  ↓
Embedding Model

Вектор
  ↓

  ↓
Релевантные документы
  ↓
```
