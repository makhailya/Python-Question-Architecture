# 🔐 JWT (JSON Web Token)

## 🎤 Короткий ответ

**JWT (JSON Web Token)** — это компактный токен, который используется для передачи **утверждений ([[claims]])** между сторонами и часто применяется для аутентификации и авторизации в API.

JWT состоит из трёх частей:[[Header]], [[Payload]], [[Signature]]

```text
Header.Payload.Signature
```

Они кодируются в **[[Base64URL]]** и разделяются точками.

Главная особенность JWT — сервер может проверить **подлинность и целостность** токена по подписи, не обращаясь к хранилищу сессий на каждый запрос.

При этом JWT **по умолчанию не шифрует данные**: содержимое payload можно декодировать.

## 🗣️ Ответ на собеседовании

JWT — это JSON Web Token, стандарт RFC 7519 для передачи claims между сторонами в виде компактного токена.

На практике JWT часто используют для аутентификации API. После успешного логина сервер выдаёт токен клиенту. Клиент затем передаёт его, например, в заголовке `Authorization: Bearer <token>`.

JWT состоит из трёх частей: **[[Header]], [[Payload]] и [[Signature]]**. Header содержит информацию о типе токена и алгоритме подписи, payload — claims, а signature позволяет проверить целостность и подлинность токена.

Важно, что JWT обычно **не шифруется**. [[Base64URL]] — это кодирование, а не шифрование, поэтому секретные данные в payload помещать нельзя.

JWT удобен тем, что сервер может валидировать токен без хранения серверной сессии, но это не означает, что JWT автоматически делает систему stateless во всех смыслах. Также важно правильно управлять сроком жизни токенов, отзывом и refresh-механизмом.

# 📚 Разбор поглубже

## 1. Что такое JWT

JWT расшифровывается как:

**JSON Web Token**

Это стандартный формат токена для передачи claims между сторонами.

Пример использования:

```text
Клиент
   │
   │ username + password
   ▼
POST /login
   │
   ▼
Сервер
   │
   │ JWT
   ▼
Клиент
   │
   │ Authorization: Bearer <JWT>
   ▼
API
```

Сервер проверяет JWT и определяет, можно ли выполнить запрос.

---

# 2. Из чего состоит JWT

JWT имеет три части:

```text
Header.Payload.Signature
```

Например, условно:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiIxMjMiLCJleHAiOjE3MDAwMDAwMDB9
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

Разделитель:

```text
.
```

То есть:

```text
JWT
├── Header
├── Payload
└── Signature
```

---

# 3. Header

Header содержит метаданные о токене.

Например:

```python
{
    "alg": "HS256",
    "typ": "JWT"
}
```

Здесь:

* `alg` — алгоритм подписи;
* `typ` — тип токена.

Header кодируется в Base64URL.

---

# 4. Payload

Payload содержит **claims** — утверждения о субъекте или токене.

Например:

```python
{
    "sub": "123",
    "name": "Ilya",
    "role": "admin",
    "exp": 1790000000
}
```

Здесь:

* `sub` — subject, например идентификатор пользователя;
* `name` — имя;
* `role` — роль;
* `exp` — время истечения токена.

Payload тоже кодируется в Base64URL.

### Важный момент

Payload **не зашифрован**.

Например, если JWT содержит:

```python
{
    "password": "123456"
}
```

пароль не становится секретным.

Поэтому:

> **JWT ≠ шифрование.**

В payload нельзя помещать секреты и чувствительные данные только в расчёте на то, что JWT их скроет.

---

# 5. Signature

Signature используется для проверки **целостности и подлинности** токена.

Упрощённо для HMAC:

```text
HMAC(
    base64url(header) + "." + base64url(payload),
    secret
)
```

Получается:

```text
Header.Payload.Signature
```

Если кто-то изменит payload:

```text
"role": "user"
```

на:

```text
"role": "admin"
```

подпись перестанет соответствовать содержимому.

Сервер обнаружит это при проверке.

---

# 6. Кодирование ≠ шифрование

Это один из самых важных вопросов на собеседовании.

JWT использует **Base64URL encoding**.

Base64URL:

```text
кодирует данные
```

но не:

```text
шифрует данные
```

Поэтому payload можно декодировать без знания секретного ключа.

Подпись нужна для другого:

```text
Payload
   ↓
Signature
   ↓
Проверка целостности
```

То есть:

```text
JWT
├── Base64URL → представление данных
└── Signature → защита целостности/подлинности
```

# 7. Как происходит аутентификация

Типичный сценарий:

### Шаг 1. Login

Клиент отправляет credentials:

```text
POST /login
```

Сервер проверяет пользователя.

### Шаг 2. Создание JWT

Сервер создаёт access token.

Например, в payload помещает:

```python
{
    "sub": "123",
    "exp": 1790000000
}
```

### Шаг 3. Клиент сохраняет токен

Например:

```text
access_token
```

### Шаг 4. Следующий запрос

Клиент отправляет:

```text
Authorization: Bearer <JWT>
```

### Шаг 5. Сервер проверяет JWT

Сервер проверяет:

* структуру;
* подпись;
* алгоритм;
* срок действия;
* claims;
* дополнительные ограничения.

После этого запрос может быть передан дальше.

---

# 8. Access Token

**Access token** используется для доступа к защищённым ресурсам.

Например:

```text
GET /profile
Authorization: Bearer <access_token>
```

Обычно access token делают относительно короткоживущим.

Причина проста:

> Если токен украден, злоумышленник сможет использовать его до окончания срока действия или до того момента, когда система сможет его отозвать.

---

# 9. Refresh Token

Чтобы пользователю не приходилось постоянно вводить логин и пароль, используют **refresh token**.

Упрощённая схема:

```text
Access Token
↓
короткий срок жизни

Refresh Token
↓
более длительный срок жизни
```

Когда access token истёк:

```text
Client
   │
   │ refresh token
   ▼
/refresh
   │
   ▼
New Access Token
```

Важно:

> Refresh token и access token — разные сущности, даже если оба реализованы в виде JWT.

Refresh token также **не обязан быть JWT**.

---

# 10. Claims

Claims — это утверждения, которые находятся внутри payload.

Есть стандартные зарегистрированные claims.

Например:

### `sub`

Subject — кому относится токен.

```python
{
    "sub": "123"
}
```

### `exp`

Expiration Time — время истечения.

```python
{
    "exp": 1790000000
}
```

### `iat`

Issued At — время выпуска.

```python
{
    "iat": 1789990000
}
```

### `iss`

Issuer — кто выпустил токен.

```python
{
    "iss": "auth-service"
}
```

### `aud`

Audience — для кого предназначен токен.

```python
{
    "aud": "my-api"
}
```

Кроме стандартных claims можно использовать собственные.

Например:

```python
{
    "sub": "123",
    "role": "admin"
}
```

# 11. Симметричная и асимметричная подпись

JWT может использовать разные алгоритмы.

## HMAC

Например:

```text
HS256
```

Используется **один секретный ключ**:

```text
Server
   │
   └── secret
```

Им подписывают и проверяют токен.

Плюс — простота.

Минус — тот же секрет должен быть известен всем компонентам, которым нужно проверять подпись.

---

## RSA / ECDSA

Например:

```text
RS256
ES256
```

Используется пара ключей:

```text
Private Key → подписывает

Public Key → проверяет
```

Это удобно, например, когда один auth-сервис выпускает токены, а несколько API-сервисов должны их проверять.

Схема:

```text
Auth Service
     │
     │ private key
     ▼
   JWT
     │
     ▼
API Service
     │
     │ public key
     ▼
  verify
```

# 12. JWT и Session

Это частый вопрос.

### Session

Сервер хранит состояние сессии:

```text
Client
  │
  │ session_id
  ▼
Server
  │
  ▼
Session Store
```

Например:

```text
session_id → user_id
```

### JWT

Основная информация о токене находится в самом токене, а сервер проверяет его подпись:

```text
Client
  │
  │ JWT
  ▼
Server
  │
  └── verify signature
```

Упрощённо:

| Session                        | JWT                                       |
| ------------------------------ | ----------------------------------------- |
| Состояние хранится на сервере  | Claims находятся в токене                 |
| Нужен session store            | Может не требоваться хранилище сессий     |
| Легче централизованно отозвать | Отзыв требует дополнительного механизма   |
| Маленький session ID           | Токен обычно больше                       |
| Server-side state              | Часто используется как stateless-механизм |

Но это **не означает, что JWT всегда лучше Session**. Выбор зависит от архитектуры.

---

# 13. JWT и Stateless

JWT часто используют для построения stateless-аутентификации.

Например:

```text
Client
  │
  │ JWT
  ├──────────→ API 1
  │
  ├──────────→ API 2
  │
  └──────────→ API 3
```

Каждый API-сервис может самостоятельно проверить токен.

Но есть важный нюанс:

> **Использование JWT само по себе не гарантирует полностью stateless архитектуру.**

Например, система может хранить blacklist отозванных токенов в Redis.

Тогда появляется серверное состояние, связанное с токенами.

---

# 14. Главная проблема JWT — отзыв

Представим:

```text
Access Token
TTL = 1 час
```

Пользователь нажал «Выйти».

Если сервер просто перестал выдавать новые токены, уже выданный JWT может оставаться валидным до истечения `exp`.

Поэтому для немедленного отзыва применяют дополнительные механизмы:

* blacklist;
* token revocation;
* короткий TTL access token;
* rotation refresh token;
* хранение состояния refresh-сессий.

Это одна из причин, почему JWT нельзя воспринимать как магическое решение для аутентификации.

---

# 15. JWT ≠ OAuth 2.0

Это тоже популярный вопрос.

**JWT** — формат токена.

**OAuth 2.0** — framework протоколов авторизации.

Они могут использоваться вместе:

```text
OAuth 2.0
   │
   └── Access Token
          │
          └── может быть JWT
```

Но OAuth 2.0 не требует, чтобы access token обязательно был JWT.

---

# 16. JWT ≠ аутентификация сама по себе

JWT — это формат токена.

Он может использоваться в процессе аутентификации и авторизации, но сам по себе не определяет:

* как пользователь логинится;
* где хранится пароль;
* как выдаётся токен;
* как токен отзывается;
* какие permissions получает пользователь.

Поэтому правильнее говорить:

> JWT — механизм представления и передачи claims, который часто используется как access token в системах аутентификации и авторизации.

## 🎤 Вопросы на собеседовании

**Что такое JWT?**

> JSON Web Token — компактный формат передачи claims, который часто используется для аутентификации и авторизации API.

**Из каких частей состоит JWT?**

> Header, Payload и Signature.

**Payload зашифрован?**

> Нет. Обычно он только кодируется Base64URL, поэтому его содержимое можно декодировать.

**Зачем нужна Signature?**

> Для проверки целостности токена и подтверждения того, что он подписан доверенной стороной.

**Можно ли изменить payload?**

> Технически можно изменить строку payload, но после этого подпись перестанет соответствовать токену, и корректно настроенный сервер отклонит его.

**Что такое `exp`?**

> Claim, содержащий время истечения токена.

**Что такое `sub`?**

> Subject — идентификатор субъекта, например пользователя, которому принадлежит токен.

**Что такое access token?**

> Токен, который клиент предъявляет для доступа к защищённым ресурсам.

**Что такое refresh token?**

> Токен, используемый для получения нового access token после его истечения. Он может иметь другой формат и не обязан быть JWT.

**Чем JWT отличается от Session?**

> Session хранит состояние на сервере и обычно передаёт клиенту идентификатор сессии. JWT содержит claims внутри токена и позволяет серверу проверять его без обязательного хранения серверной сессии.

**JWT всегда stateless?**

> Нет. JWT часто используется для stateless-аутентификации, но приложение может дополнительно хранить blacklist, refresh-сессии и другое состояние.

**JWT — это шифрование?**

> Нет. Base64URL — кодирование, а подпись обеспечивает целостность и подлинность.

**JWT и OAuth 2.0 — это одно и то же?**

> Нет. JWT — формат токена, а OAuth 2.0 — framework авторизации. OAuth может использовать JWT в качестве access token, но не обязан.

**Что произойдёт, если украдут JWT?**

> Злоумышленник сможет предъявлять его как валидный токен до истечения срока или отзыва, поэтому важны HTTPS, короткий TTL, безопасное хранение токенов и корректная стратегия refresh/revocation.
