# 🔤 Base64URL

## 🎤 Короткий ответ

**Base64URL** — это вариант кодирования Base64, адаптированный для безопасного использования в URL и HTTP-заголовках.

Он преобразует бинарные данные в текстовую строку.

В отличие от обычного Base64, в Base64URL:

* `+` заменяется на `-`;
* `/` заменяется на `_`;
* `=` padding обычно убирается.

Важно:

> **Base64URL — это кодирование, а не шифрование.**

Любой человек может декодировать Base64URL без секретного ключа.

В JWT Base64URL используется для кодирования:

```text
Header
Payload
Signature
```

---

## 🗣️ Ответ на собеседовании

Base64URL — это URL-safe вариант Base64-кодирования.

Base64 позволяет представить бинарные данные в виде ASCII-строки, но стандартный Base64 использует символы `+` и `/`, которые неудобны в некоторых URL и других контекстах.

Поэтому Base64URL заменяет `+` на `-`, `/` на `_`, а padding `=` обычно убирается.

JWT использует Base64URL для представления Header, Payload и Signature.

При этом Base64URL не обеспечивает конфиденциальность: строку можно легко декодировать обратно. Защиту целостности JWT обеспечивает не Base64URL, а **криптографическая подпись**.

# 📚 Разбор поглубже

## 1. Зачем вообще нужен Base64

Компьютер работает с бинарными данными:

```text
01001000 01100101 01101100 01101100 01101111
```

Но во многих протоколах и форматах удобнее передавать текст.

Base64 позволяет представить бинарные данные в виде текста:

```text
Hello
```

превращается в:

```text
SGVsbG8=
```

То есть Base64 — это способ **представления данных**, а не защиты.

---

# 2. Почему именно Base64

Base64 использует алфавит из 64 символов:

```text
A-Z
a-z
0-9
+
/
```

Плюс используется символ:

```text
=
```

для padding.

Название Base64 связано с тем, что используется **64 основных символа**:

```text
2⁶ = 64
```

Каждый символ Base64 представляет 6 бит информации.

---

# 3. Почему появился Base64URL

Обычный Base64 содержит:

```text
+
/
=
```

Некоторые из этих символов имеют специальное значение в URL.

Поэтому существует URL-safe вариант.

### Обычный Base64

```text
SGVsbG8+Lw==
```

### Base64URL

```text
SGVsbG8-Lw
```

Основные изменения:

```text
Base64      Base64URL
---------------------
+      →    -
/      →    _
=      →    обычно удаляется
```

---

# 4. Base64URL — это не шифрование

Это принципиально важно.

Например:

```text
SGVsbG8
```

можно декодировать обратно:

```text
Hello
```

Никакого ключа не требуется.

Поэтому:

```text
Base64URL
    ↓
кодирование
```

а не:

```text
Base64URL
    ↓
шифрование
```

Если нужно скрыть содержимое, используются криптографические алгоритмы шифрования.

---

# 5. Base64URL в JWT

JWT выглядит так:

```text
Header.Payload.Signature
```

Например:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiIxMjMifQ
.
abc123...
```

Каждая часть представлена в Base64URL:

```text
JWT
├── Header
│   └── Base64URL
│
├── Payload
│   └── Base64URL
│
└── Signature
    └── Base64URL
```

Поэтому можно взять JWT и декодировать первые две части без знания секретного ключа.

Например:

```text
eyJzdWIiOiIxMjMifQ
```

декодируется в:

```python
{
    "sub": "123"
}
```

Это не означает, что токен подделан или небезопасен сам по себе.

Подлинность проверяется отдельно — через **Signature**.

---

# 6. Что защищает JWT

Здесь важно разделять три понятия:

```text
Base64URL
    ↓
представляет данные

Signature
    ↓
защищает целостность и подлинность

Encryption
    ↓
защищает конфиденциальность
```

Например:

```text
Header.Payload.Signature
```

Base64URL позволяет прочитать:

```text
Header
Payload
```

Но изменение Payload:

```text
"role": "user"
```

на:

```text
"role": "admin"
```

изменит данные, а существующая Signature больше не будет им соответствовать.

Сервер проверит подпись и отклонит такой токен.

---

# 7. Почему в JWT убирают `=`

В обычном Base64 используется padding:

```text
SGVsbG8=
```

В Base64URL padding `=` обычно убирается:

```text
SGVsbG8
```

Это делает строку компактнее и удобнее для использования в URL.

При декодировании padding при необходимости может быть восстановлен.

---

# 8. Base64URL и URL Encoding — не одно и то же

Это важное различие.

### URL Encoding

Например:

```text
hello world
```

может превратиться в:

```text
hello%20world
```

Это **percent-encoding**.

### Base64URL

Данные преобразуются в Base64-представление с URL-safe алфавитом:

```text
Hello
↓
SGVsbG8
```

Поэтому:

```text
URL Encoding ≠ Base64URL
```

---

# 9. Пример в Python

Python предоставляет стандартный модуль `base64`.

```python
import base64

data = b"Hello"

encoded = base64.urlsafe_b64encode(data)
print(encoded)
```

Получим:

```text
b'SGVsbG8='
```

Если нужен JWT-подобный вариант без padding:

```python
import base64

data = b"Hello"

encoded = base64.urlsafe_b64encode(data).rstrip(b"=")
print(encoded)
```

Результат:

```text
b'SGVsbG8'
```

Обратное преобразование:

```python
import base64

encoded = b"SGVsbG8"

padding = b"=" * (-len(encoded) % 4)

decoded = base64.urlsafe_b64decode(encoded + padding)

print(decoded)
```

Результат:

```text
b"Hello"
```

---

# 10. Почему Base64 увеличивает размер

Base64 кодирует каждые:

```text
3 байта
```

в:

```text
4 символа
```

Поэтому размер данных увеличивается примерно на **33%**.

У Base64URL принцип тот же.

Это одна из причин, почему Base64 не используют как способ сжатия.

---

# 11. Что важно помнить про JWT

Представь JWT:

```text
Header.Payload.Signature
```

Не нужно думать:

```text
JWT
└── зашифрованные данные
```

Правильнее:

```text
JWT
├── Header
│   └── Base64URL
│
├── Payload
│   └── Base64URL
│
└── Signature
    └── криптографическая подпись
```

Именно поэтому:

> **JWT можно прочитать, но нельзя незаметно изменить, если подпись проверяется корректно.**

## 🎤 Вопросы на собеседовании

**Что такое Base64URL?**

> URL-safe вариант Base64-кодирования, в котором `+` заменяется на `-`, `/` на `_`, а padding `=` обычно удаляется.

**Base64URL — это шифрование?**

> Нет. Это кодирование. Данные можно декодировать без ключа.

**Зачем Base64URL нужен в JWT?**

> JWT должен быть удобен для передачи в URL и HTTP-заголовках, поэтому Header, Payload и Signature представляются в URL-safe формате.

**Чем Base64URL отличается от Base64?**

> Основные отличия — замена `+` на `-`, `/` на `_` и обычно отсутствие padding `=`.

**Можно ли прочитать Payload JWT без секретного ключа?**

> Да. Payload закодирован Base64URL, а не зашифрован.

**Что защищает Payload от изменения?**

> Криптографическая подпись JWT, а не Base64URL.

**Base64URL сжимает данные?**

> Нет. Наоборот, Base64-представление обычно увеличивает размер примерно на треть.

**Base64URL и URL Encoding — одно и то же?**

> Нет. Base64URL кодирует бинарные данные в URL-safe Base64, а URL Encoding использует percent-encoding, например `%20` для пробела.
