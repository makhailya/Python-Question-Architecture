# 🔐 Session

## 🎤 Короткий ответ

**Session (сессия)** — это механизм хранения состояния пользователя между HTTP-запросами.

HTTP сам по себе **stateless**: каждый запрос независим. Session позволяет серверу связать несколько запросов с одним пользователем.

Обычно сервер хранит данные сессии у себя, а клиент получает **session ID**, который отправляет с каждым следующим запросом, чаще всего через cookie.

```text
Клиент → POST /login
          ↓
       Сервер
          ↓
Создаёт session_id
          ↓
Set-Cookie: session_id=abc123

Клиент → GET /profile
Cookie: session_id=abc123
          ↓
       Сервер
          ↓
Находит сессию abc123
          ↓
Определяет пользователя
```

---

## 🗣️ Ответ на собеседовании

> Session — это способ сохранить состояние пользователя между HTTP-запросами. Поскольку HTTP является stateless, сервер сам по себе не помнит предыдущий запрос.
>
> При логине сервер создаёт сессию и генерирует идентификатор сессии — `session_id`. Этот идентификатор обычно передаётся клиенту через cookie.
>
> При следующих запросах браузер автоматически отправляет cookie обратно. Сервер использует `session_id`, чтобы найти данные сессии и определить пользователя.
>
> Важный момент: обычно клиент хранит только идентификатор, а сами данные сессии находятся на сервере — например, в памяти, Redis или базе данных.
>
> Session-подход отличается от JWT тем, что состояние аутентификации в основном хранится на сервере. Поэтому сервер может проще инвалидировать сессию, например при logout.

# 📚 Разбор поглубже

## 1. Какую проблему решает Session

HTTP не хранит контекст между запросами.

Например:

```text
GET /profile
GET /orders
GET /settings
```

С точки зрения HTTP это три независимых запроса.

Серверу нужно понять:

> «Все эти запросы принадлежат одному пользователю?»

Session добавляет такой механизм идентификации.

---

## 2. Как работает Session

Упрощённая схема:

```text
                 ┌──────────────────┐
                 │      Сервер      │
                 │                  │
                 │ session_id       │
                 │       ↓          │
                 │ user_id = 42     │
                 │ role = "user"    │
                 └────────┬─────────┘
                          │
                          │
                    session_id
                          │
                          ↓
                 ┌──────────────────┐
                 │     Клиент       │
                 │                  │
                 │ Cookie:          │
                 │ session_id=abc   │
                 └──────────────────┘
```

### Шаг 1. Пользователь логинится

```text
POST /login
```

Сервер проверяет:

```text
login + password
```

Если всё правильно, создаёт сессию.

Например:

```text
session_id = abc123
```

---

### Шаг 2. Сервер отправляет cookie

Например:

```text
Set-Cookie: session_id=abc123
```

Браузер сохраняет cookie.

---

### Шаг 3. Следующий запрос

```text
GET /profile
Cookie: session_id=abc123
```

---

### Шаг 4. Сервер ищет сессию

Например, в Redis:

```text
abc123 → {
    user_id: 42,
    role: "user"
}
```

Сервер понимает:

```text
session_id abc123
        ↓
user_id 42
        ↓
пользователь авторизован
```

---

# 3. Где хранятся данные Session

Есть несколько вариантов.

### Память процесса

```text
Application
└── RAM
    └── sessions
```

Просто, но плохо масштабируется.

Если приложение перезапустилось — сессии могут исчезнуть.

---

### Redis

Очень распространённый вариант:

```text
Client
   ↓
Backend
   ↓
Redis
   ↓
session_id → session data
```

Redis удобен, потому что быстрый и поддерживает TTL.

Например:

```text
session:abc123
    user_id = 42
    expires = 2026-09-21
```

---

### База данных

Сессии также можно хранить в PostgreSQL или другой БД.

Например:

```text
sessions

id          user_id       expires_at
--------------------------------------
abc123      42            ...
xyz456      17            ...
```

Но для большого количества короткоживущих сессий часто используют Redis.

---

# 4. Cookie и Session — это не одно и то же

Это важное различие.

**Cookie** — механизм хранения и передачи небольших данных на стороне клиента.

**Session** — механизм хранения состояния пользователя.

Они часто используются вместе:

```text
Cookie
└── session_id
        ↓
Session
└── user_id
└── role
└── expires_at
```

То есть cookie может содержать только идентификатор:

```text
session_id=abc123
```

а сами данные находятся на сервере.

---

# 5. Session ID

`session_id` должен быть:

* случайным;
* непредсказуемым;
* достаточно длинным;
* уникальным;
* защищённым от кражи.

Нельзя делать:

```text
session_id=123
```

или:

```text
session_id=user42
```

Иначе злоумышленник может подобрать идентификатор.

Лучше использовать криптографически безопасный случайный идентификатор.

---

# 6. Безопасность Cookie

Для session-cookie обычно используются важные атрибуты.

### HttpOnly

```text
HttpOnly
```

Запрещает JavaScript напрямую читать cookie.

Это снижает риск кражи session ID через XSS.

---

### Secure

```text
Secure
```

Cookie отправляется только по HTTPS.

---

### SameSite

Например:

```text
SameSite=Lax
```

Помогает ограничить отправку cookie в cross-site запросах и снижает риск CSRF.

---

Пример концептуально:

```text
Set-Cookie:
session_id=abc123;
HttpOnly;
Secure;
SameSite=Lax
```

---

# 7. Logout

При session-based authentication logout обычно означает **инвалидацию серверной сессии**.

Например:

```text
session_id = abc123
```

удаляется из Redis:

```text
DELETE session:abc123
```

После этого:

```text
Cookie: session_id=abc123
```

уже не даёт доступа.

Это одно из важных отличий от самостоятельно содержащего состояние токена: серверная сессия позволяет централизованно удалить состояние.

---

# 8. Session vs JWT

| Session                                   | JWT                                                  |
| ----------------------------------------- | ---------------------------------------------------- |
| Состояние хранится на сервере             | Claims находятся внутри токена                       |
| Клиент обычно хранит `session_id`         | Клиент хранит JWT                                    |
| Сервер ищет session по ID                 | Сервер обычно проверяет подпись JWT                  |
| Logout через инвалидирование сессии       | Часто сложнее немедленно отозвать access token       |
| Нужен session storage                     | Может работать без server-side session storage       |
| Удобно централизованно управлять сессиями | Удобен для распределённых систем и stateless-подхода |

Но важно:

**Session и JWT — не взаимоисключающие технологии.**

Например, приложение может использовать JWT для API и обычные sessions для web-интерфейса.

---

# 9. Session не делает HTTP stateful

Это важный нюанс на собеседовании.

HTTP остаётся **stateless-протоколом**.

Session — это механизм, который позволяет приложению **восстановить состояние между stateless HTTP-запросами**.

То есть:

```text
HTTP
└── stateless

Application
└── Session
    └── сохраняет состояние пользователя
```

Поэтому корректнее говорить:

> HTTP stateless, а session добавляет механизм хранения состояния на уровне приложения.

# 10. Session в распределённой системе

Представим два backend-сервера:

```text
             Load Balancer
                 ↓
          ┌──────┴──────┐
          ↓             ↓
      Backend 1      Backend 2
```

Если session хранится только в RAM Backend 1:

```text
session abc
    ↓
Backend 1
```

пользователь может отправить следующий запрос на Backend 2:

```text
Backend 2
    ↓
"Я не знаю session abc"
```

### Решение

Использовать общее хранилище:

```text
             Load Balancer
                 ↓
          ┌──────┴──────┐
          ↓             ↓
      Backend 1      Backend 2
          │             │
          └──────┬──────┘
                 ↓
               Redis
                 ↓
             Sessions
```

Теперь любой экземпляр приложения может получить сессию.

---

# 11. Sticky Sessions

Другой вариант — **sticky sessions**.

Load Balancer старается отправлять одного пользователя на один и тот же backend:

```text
User A → Backend 1
User B → Backend 2
```

Но это создаёт зависимость от конкретного сервера и усложняет масштабирование.

Поэтому при распределённых приложениях часто предпочитают централизованное или общее session storage.

---

# 12. Session Fixation

Одна из атак, связанная с сессиями, — **Session Fixation**.

Идея:

```text
Атакующий
    ↓
получает/навязывает session ID
    ↓
жертва авторизуется
    ↓
session ID становится авторизованным
    ↓
атакующий использует тот же ID
```

Защита — после успешной аутентификации **регенерировать session ID**.

```text
До login:

session_id = abc

После login:

session_id = xyz
```

---

# 13. Жизненный цикл Session

Можно представить так:

```text
Создание
   ↓
session_id
   ↓
Cookie
   ↓
Запросы
   ↓
Session lookup
   ↓
Продление TTL
   ↓
Logout / Expiration
   ↓
Удаление Session
```

Session может закончиться двумя основными способами:

```text
Logout
   ↓
удаление сессии
```

или:

```text
TTL истёк
   ↓
сессия недействительна
```

# 🎤 Вопросы на собеседовании

### Что такое Session?

Механизм хранения состояния пользователя между HTTP-запросами. Обычно клиент хранит `session_id` в cookie, а сервер хранит соответствующие данные сессии.

### Где обычно хранится Session?

В памяти приложения, Redis или базе данных. Для распределённых приложений часто используют Redis.

### Session и Cookie — одно и то же?

Нет. Cookie — механизм хранения и передачи данных на клиенте, а Session — механизм хранения состояния пользователя. Cookie часто содержит `session_id`, который ссылается на серверную сессию.

### Почему HTTP не помнит пользователя?

Потому что HTTP является stateless. Каждый запрос сам по себе не содержит состояния предыдущих запросов.

### Как работает Session?

```text
Login
 ↓
создание session
 ↓
session_id
 ↓
cookie
 ↓
следующий request
 ↓
session_id
 ↓
поиск session
 ↓
user_id
```

### Зачем нужен Redis для Session?

Чтобы несколько экземпляров backend-приложения могли использовать общее хранилище сессий и быстро получать их по `session_id`.

### Что такое Session Fixation?

Атака, при которой злоумышленник пытается заставить жертву использовать известный ему session ID. Один из способов защиты — регенерировать session ID после успешной аутентификации.

### Что такое `HttpOnly`?

Атрибут cookie, запрещающий доступ к ней через JavaScript API браузера. Это снижает риск кражи session cookie через XSS.

### Session или JWT?

Это разные модели управления состоянием аутентификации. В Session состояние в основном хранится на сервере, а JWT обычно содержит claims внутри самого токена. Выбор зависит от архитектуры и требований приложения.
