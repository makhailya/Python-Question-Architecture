# 🛡️ Авторизация

## 🎤 Суперкоротко

**Авторизация** — это проверка того, **какие действия разрешены уже идентифицированному и аутентифицированному пользователю.**

**Авторизация отвечает на вопрос: «Что тебе можно?»**

Пример:

```text
Пользователь → обычный user

Можно:
✅ читать свои данные
✅ редактировать свой профиль

Нельзя:
❌ удалить другого пользователя
❌ открыть admin-панель
```

---

## 🎯 Ответ на собеседовании

**Авторизация** — это процесс определения и проверки прав доступа субъекта к определённым ресурсам или операциям.

После того как система установила личность пользователя через аутентификацию, она проверяет, имеет ли этот пользователь необходимые разрешения для выполнения конкретного действия.

---

# 🔄 Полная последовательность

```text
Идентификация
      ↓
«Кто ты?»
      ↓
Аутентификация
      ↓
«Докажи»
      ↓
Авторизация
      ↓
«Что тебе можно?»
```

Это одна из самых важных схем для собеседования.

---

# 👤 Пример с ролями

Есть пользователи:

```text
Ilya → user
Anna → manager
Admin → admin
```

И операция:

```text
DELETE /users/10
```

Система сначала устанавливает:

```text
Кто пользователь?
      ↓
Ilya
```

Затем проверяет:

```text
Есть ли у Ilya право DELETE /users/10?
```

Если нет:

```text
403 Forbidden
```

---

# 🔑 RBAC

Один из распространённых подходов — **RBAC (Role-Based Access Control)**.

Права назначаются ролям.

Например:

```text
admin
 ├── create
 ├── read
 ├── update
 └── delete

manager
 ├── read
 └── update

user
 └── read
```

Пользователь получает роль:

```text
Ilya
 ↓
user
 ↓
read
```

---

# 🧩 Permissions

Можно назначать конкретные разрешения.

Например:

```python
permissions = {
    "users.read": True,
    "users.update": True,
    "users.delete": False
}
```

При запросе:

```text
DELETE /users/10
```

проверяется:

```text
users.delete?
     ↓
False
     ↓
403 Forbidden
```

---

# 🌐 Авторизация в API

Например:

```text
GET /users/me
```

Пользователь авторизован:

```text
Authorization: Bearer TOKEN
```

Сервер определяет пользователя и проверяет доступ.

Но запрос:

```text
DELETE /users/10
```

может требовать дополнительных прав.

Например:

```text
role = admin
```

# 🆚 401 и 403

Это очень любят спрашивать на собеседованиях.

### 401 Unauthorized

Проблема с **аутентификацией**.

Например:

```text
Нет токена
Токен недействителен
Токен истёк
```

Смысл:

> «Я не могу подтвердить, кто ты».

---

### 403 Forbidden

Пользователь известен, но у него **нет необходимых прав**.

```text
Пользователь → authenticated
Права → недостаточны
```

Смысл:

> «Я знаю, кто ты, но тебе это запрещено».

Упрощённая схема:

```text
401 → проблема с authentication
403 → проблема с authorization
```

---

# 🧠 Авторизация не обязательно означает роли

Авторизация может основываться на:

* ролях;
* permissions;
* группах;
* владельце ресурса;
* атрибутах пользователя;
* контексте запроса;
* политике доступа.

Например:

```text
Пользователь может редактировать
только свои документы.
```

Здесь недостаточно просто иметь роль `user`.

Система дополнительно проверяет:

```text
document.owner_id == current_user.id
```

# 🔐 Authentication + Authorization в API

Типичный запрос:

```python
headers = {
    "Authorization": "Bearer TOKEN"
}
```

Сервер:

```text
                Request
                   ↓
          Есть credentials?
                   ↓
              Authentication
                   ↓
             Кто пользователь?
                   ↓
              Authorization
                   ↓
             Есть права?
              ↙       ↘
            Да         Нет
            ↓           ↓
          200          403
```

Если пользователь не прошёл аутентификацию:

```text
401
```

---

# 🧩 Где это встречается в Django / DRF

В Django REST Framework эти понятия разделены.

Упрощённо:

```text
Authentication
      ↓
Определяет пользователя
      ↓
Permissions
      ↓
Проверяют права
```

Например:

```python
from rest_framework.permissions import IsAuthenticated
```

`IsAuthenticated` проверяет, что пользователь аутентифицирован.

Но это ещё не означает, что пользователь имеет любые возможные права.

Можно реализовать собственные permission-классы для более точной авторизации.

---

# 🆚 Три понятия

| Этап           | Вопрос     | Пример                    |
| -------------- | ---------- | ------------------------- |
| Идентификация  | Кто ты?    | `ilya`                    |
| Аутентификация | Докажи     | пароль / токен            |
| Авторизация    | Что можно? | `read`, `write`, `delete` |

Полная схема:

```text
🪪 Идентификация
       ↓
«Я — Илья»

🔐 Аутентификация
       ↓
«Вот мой пароль / токен»

🛡️ Авторизация
       ↓
«Илье разрешено читать этот ресурс»
```

---

# 🧠 Главное

**Идентификация** — определяем, кто пользователь.

**Аутентификация** — проверяем, действительно ли это он.

**Авторизация** — проверяем его права.

Запоминать лучше именно в таком порядке:

```text
КТО?
 ↓
ДОКАЖИ
 ↓
ЧТО МОЖНО?
```

Или:

```text
Идентификация
     ↓
Аутентификация
     ↓
Авторизация
```
