# 🅛 Liskov Substitution Principle — принцип подстановки Лисков

## 🎯 Ответ на собеседовании

**Liskov Substitution Principle (LSP)** — принцип подстановки Лисков.

Он говорит, что **объекты дочернего класса должны быть взаимозаменяемы с объектами базового класса без нарушения корректности программы**.

То есть если `B` является наследником `A`, то объект `B` должен корректно работать везде, где программа ожидает `A`.

Проще:

> **Наследник должен сохранять контракт родительского класса.**

---

## 🎤 Суперкоротко

```text
LSP
 ↓
Наследник заменяет родителя
 ↓
и не ломает программу
```

Главный вопрос:

> **«Могу ли я подставить наследника вместо родителя и сохранить корректное поведение?»**

---

# 🧩 Что такое контракт класса

Контракт — это то, что класс обещает своим пользователям.

Например:

```python
class Bird:

    def fly(self):
        pass
```

Контракт говорит:

```text
Bird
 ↓
fly()
 ↓
можно вызвать
```

Если наследник нарушает это обещание, возникает проблема.

---

# ❌ Нарушение LSP

Классический пример:

```python
class Bird:

    def fly(self):
        print("Flying")


class Sparrow(Bird):

    def fly(self):
        print("Sparrow flies")


class Penguin(Bird):

    def fly(self):
        raise NotImplementedError
```

Есть функция:

```python
def make_bird_fly(bird: Bird):
    bird.fly()
```

Для воробья:

```python
make_bird_fly(Sparrow())
```

работает.

Для пингвина:

```python
make_bird_fly(Penguin())
```

получаем исключение.

Проблема:

```text
Bird
 ↓
обещает fly()
 ↓
Penguin
 ↓
не может выполнить fly()
```

Значит, `Penguin` не соответствует контракту `Bird`.

---

# 🧠 Почему это проблема наследования

Само наследование:

```python
class Penguin(Bird):
    ...
```

говорит:

> `Penguin` является разновидностью `Bird`.

Но базовый класс одновременно утверждает:

```python
class Bird:

    def fly(self):
        pass
```

Получается противоречие:

```text
Bird
 ↓
все умеют fly()

Penguin
 ↓
не умеет fly()
```

Поэтому проблема не в пингвине, а в неправильной абстракции.

---

# ✅ Как исправить

Нужно разделить абстракции.

Например:

```python
class Bird:
    def eat(self):
        pass


class FlyingBird(Bird):
    def fly(self):
        pass


class Sparrow(FlyingBird):

    def fly(self):
        print("Flying")


class Penguin(Bird):
    pass
```

Теперь:

```text
Bird
 ├── Sparrow
 │     └── FlyingBird
 │           └── fly()
 │
 └── Penguin
```

`Penguin` больше не обязан реализовывать `fly()`.

---

# 🔄 Правильная подстановка

Есть функция:

```python
def make_flying_bird_fly(bird: FlyingBird):
    bird.fly()
```

Теперь можно передать:

```python
make_flying_bird_fly(Sparrow())
```

Потому что `Sparrow` соответствует контракту `FlyingBird`.

```text
FlyingBird
     ↓
  fly()
     ↓
Sparrow
     ↓
  fly()
```

---

# 🧩 LSP — это не только про методы

Нарушить LSP можно не только отсутствием метода.

Наследник не должен неожиданно менять ожидаемое поведение родителя.

Например, базовый класс обещает:

```python
class Repository:

    def save(self, user):
        pass
```

Код ожидает:

```text
save()
 ↓
пользователь сохраняется
```

Если наследник:

```python
class ReadOnlyRepository(Repository):

    def save(self, user):
        raise PermissionError
```

то подстановка такого объекта может нарушить ожидания кода, который работает с `Repository`.

---

# ⚠️ LSP и исключения

Само наличие исключения **не означает автоматически нарушение LSP**.

Важно, соответствует ли поведение наследника контракту базового класса.

Например, если базовый класс явно допускает определённое исключение, наследник может его использовать.

Проблема возникает, когда наследник:

```text
изменяет ожидаемое поведение
или
усиливает ограничения
или
нарушает обещания базового класса
```

---

# 🧠 Что значит «сохранять контракт»

Упрощённо наследник должен соблюдать ожидания базового класса относительно:

```text
входных данных
      ↓
поведения
      ↓
результата
```

Например:

```text
Родитель:
принимает положительное число
возвращает результат

Наследник:
принимает положительное число
возвращает результат
```

Наследник не должен неожиданно требовать:

```text
«Теперь мне нужен только int > 100»
```

если родитель обещал принимать любое положительное число.

# 🔗 LSP и полиморфизм

LSP особенно важен при использовании полиморфизма.

Например:

```python
def process_payment(payment: Payment):
    payment.pay()
```

Если есть:

```text
Payment
 ├── CardPayment
 ├── CashPayment
 └── CryptoPayment
```

то функция должна корректно работать с каждым допустимым наследником:

```python
process_payment(CardPayment())
process_payment(CashPayment())
process_payment(CryptoPayment())
```

Если один из наследников неожиданно ломает контракт `Payment`, нарушается LSP.

# 🆚 OCP и LSP

Эти принципы связаны, но отвечают на разные вопросы.

### OCP

> **Как добавлять новое поведение?**

```text
OCP
 ↓
Расширяй систему
не изменяя стабильный код
```

### LSP

> **Как должны вести себя наследники?**

```text
LSP
 ↓
Наследник должен
корректно заменять родителя
```

Можно запомнить:

```text
OCP → добавляем новую реализацию

LSP → новая реализация должна
      соблюдать контракт
```

# 🧩 LSP и Duck Typing в Python

В Python не обязательно использовать формальное наследование.

Благодаря **duck typing** важнее поведение объекта:

> «Если объект ведёт себя как нужный тип, его можно использовать».

Например:

```python
def save_data(repository):
    repository.save()
```

Любой объект, у которого есть корректный `save()`, потенциально подходит.

Но требования к поведению всё равно существуют.

Поэтому LSP можно рассматривать шире классического наследования:

```text
Ожидаемый контракт
       ↓
Объект должен ему соответствовать
```

---

# 🎯 Как ответить, если попросят пример

> **Например, если базовый класс `Bird` имеет метод `fly()`, а `Penguin` наследуется от `Bird`, но не может реализовать `fly()`, то при подстановке `Penguin` вместо `Bird` программа может сломаться. Это нарушение LSP. Правильнее изменить абстракцию и вынести способность летать в отдельный класс или интерфейс `FlyingBird`.**

---

# 🎯 Как определить нарушение LSP

Задай вопрос:

> **«Если я заменю объект родительского класса объектом дочернего класса, продолжит ли программа работать корректно?»**

Если:

```text
Parent → работает
Child  → ломает ожидаемое поведение
```

то, вероятно, нарушен LSP.

---

# 🧠 Главное

```text
LSP
 │
 ├── Наследник совместим с родителем
 │
 ├── Соблюдает контракт родителя
 │
 └── Не ломает код при подстановке
```

Наследник может иметь дополнительные возможности:

```text
Parent
  ↑
Child
  ├── поведение Parent
  └── дополнительные возможности
```

Но он не должен нарушать ожидаемое поведение `Parent`.

---

# 🧠 Формула для запоминания

**LSP = наследник должен быть полноценной заменой родителя.**

```text
Если код ожидает Parent,
ему должно быть всё равно:

Parent
или
Child

→ поведение остаётся корректным.
```

**Главная идея LSP — не наследование само по себе, а соблюдение контракта при подстановке.**
