# 🔑 IP Hash

## 🎯 Ответ на собеседовании

**IP Hash** — это алгоритм балансировки нагрузки, при котором сервер для клиента выбирается на основе **хеширования его IP-адреса**.

Идея в том, что один и тот же IP-адрес обычно будет направляться на **один и тот же сервер**.

Например:

```python
client_ip = "192.168.1.10"

hash(client_ip) → Server 2
```

Следующие запросы от этого клиента снова будут направляться на `Server 2`.

Это позволяет обеспечить **стабильную привязку клиента к серверу** — так называемую *session affinity* или *sticky sessions*.

---

## 🎤 Суперкоротко

**IP Hash = сервер выбирается по IP-адресу клиента.**

Один IP → обычно один и тот же сервер.

---

## 🔄 Как работает

Допустим, есть три сервера:

```text
Server 1
Server 2
Server 3
```

Приходит клиент:

```text
IP = 192.168.1.10
```

Балансировщик вычисляет хеш:

```text
hash("192.168.1.10")
        ↓
    Server 2
```

Все следующие запросы этого клиента:

```text
192.168.1.10 → Server 2
192.168.1.10 → Server 2
192.168.1.10 → Server 2
```

Другой клиент:

```text
192.168.1.20 → Server 1
```

---

## 🍪 Зачем нужен IP Hash

Основное применение — когда приложение хранит **состояние сессии на конкретном сервере**.

Например:

```text
Client
   ↓
Load Balancer
   ↓
Server 1
   ↓
Session пользователя
```

Если следующий запрос уйдёт на `Server 2`, приложение может не найти сессию пользователя.

IP Hash старается отправлять этого клиента обратно на `Server 1`.

---

## 🆚 Round Robin

**Round Robin:**

```text
Client → Server 1
Client → Server 2
Client → Server 3
Client → Server 1
```

Запросы распределяются по очереди.

**IP Hash:**

```text
Client A → Server 1
Client A → Server 1
Client A → Server 1

Client B → Server 3
Client B → Server 3
Client B → Server 3
```

Здесь важна **привязка клиента к серверу**.

---

## 🆚 Least Connections

**Least Connections** выбирает сервер с наименьшим количеством активных соединений.

```text
Server 1 → 10
Server 2 →  3 ← выбран
Server 3 →  7
```

**IP Hash** не выбирает сервер по текущей загрузке.

Он ориентируется на:

```text
IP клиента → hash → сервер
```

---

## ⚙️ Пример в Nginx

```python
upstream backend {
    ip_hash;

    server 192.168.1.10;
    server 192.168.1.11;
    server 192.168.1.12;
}
```

`ip_hash` заставляет Nginx использовать IP-адрес клиента для распределения запросов.

---

## ⚠️ Недостатки

### 1. Не учитывает реальную нагрузку

Один сервер может получить много клиентов и оказаться перегруженным.

```text
Server 1 → 100 клиентов
Server 2 → 10 клиентов
Server 3 → 5 клиентов
```

IP Hash сам по себе не перераспределяет нагрузку по принципу Least Connections.

### 2. NAT

Многие пользователи могут выходить в интернет через один публичный IP:

```text
100 пользователей
       ↓
   NAT / Proxy
       ↓
203.0.113.10
       ↓
   Server 1
```

В таком случае большое количество пользователей может оказаться привязанным к одному серверу.

### 3. Изменение количества серверов

При изменении набора серверов распределение хешей может измениться, и часть клиентов будет направлена на другие серверы.

Это может привести к потере локальных сессий, если они хранятся непосредственно на сервере.

---

## 💡 Как решить проблему с сессиями

Вместо хранения сессий только на конкретном сервере можно использовать **общее хранилище**:

```text
             ┌── Server 1 ──┐
Client → LB ├── Server 2 ──┼── Redis
             └── Server 3 ──┘
```

Например:

```text
FastAPI / Django
       ↓
     Redis
       ↓
Session data
```

Тогда запрос пользователя может попасть на любой сервер.

---

## 🆚 Сравнение алгоритмов

| Алгоритм                   | Основной принцип                |
| -------------------------- | ------------------------------- |
| Round Robin                | По очереди                      |
| Weighted Round Robin       | По очереди + вес                |
| Least Connections          | Меньше активных соединений      |
| Weighted Least Connections | Соединения + вес                |
| IP Hash                    | Сервер выбирается по IP клиента |

## 🧠 Главное

```text
IP Hash

IP клиента
    ↓
  Hash
    ↓
  Сервер
```

Основная идея:

**один клиент → один и тот же сервер**

Плюс:

**можно сохранять серверную сессию без отдельного общего хранилища.**

Минусы:

**не учитывает текущую нагрузку и может плохо распределять клиентов при NAT.**

**IP Hash = алгоритм балансировки, который привязывает клиента к серверу на основе его IP-адреса.**
