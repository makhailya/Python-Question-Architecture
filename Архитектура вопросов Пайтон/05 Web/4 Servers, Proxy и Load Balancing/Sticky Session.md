# 🍪 Sticky Session

## 🎯 Ответ на собеседовании

**Sticky Session** — это механизм, при котором клиент после первого попадания на сервер **закрепляется за этим сервером на время сессии**.

Все последующие запросы этого клиента направляются на тот же сервер.

Это используется, когда приложение хранит состояние пользовательской сессии **локально на конкретном сервере**.

Например:

```python
Client
   ↓
Load Balancer
   ↓
Server 1
```

После этого:

```python
Client → Server 1
Client → Server 1
Client → Server 1
```

Даже если существуют другие серверы.

---

## 🎤 Суперкоротко

**Sticky Session = один клиент → один backend-сервер на время сессии.**

---

## 🔄 Как работает

Допустим, есть:

```text
Server 1
Server 2
Server 3
```

Первый запрос клиента попадает на:

```text
Client
   ↓
Load Balancer
   ↓
Server 2
```

Балансировщик запоминает привязку:

```text
Client → Server 2
```

Следующие запросы:

```text
Client → Server 2
Client → Server 2
Client → Server 2
```

---

## 🍪 Cookie-based Sticky Session

Один из распространённых способов — специальная **cookie**.

Например:

```text
Set-Cookie: SERVER_ID=server2
```

Клиент сохраняет cookie и отправляет её со следующими запросами.

Балансировщик видит:

```text
SERVER_ID=server2
```

и отправляет запрос на:

```text
Server 2
```

---

## 🔑 IP Hash vs Sticky Session

Они похожи, но это **не одно и то же**.

### IP Hash

Сервер определяется на основе IP:

```text
Client IP
    ↓
  Hash
    ↓
Server 2
```

### Sticky Session

Балансировщик сохраняет **сам факт привязки клиента к серверу**, например через cookie:

```text
Client
   ↓
Cookie
   ↓
Server 2
```

Поэтому Sticky Session обычно более гибкий механизм.

---

## 💡 Зачем нужен Sticky Session

Главная причина — **stateful-приложения**.

Например, сервер хранит данные сессии пользователя в своей памяти:

```text
Server 1
└── Session A

Server 2
└── Session B

Server 3
└── Session C
```

Если клиент сначала попал на Server 1:

```text
Client → Server 1
```

а следующий запрос попал на Server 2:

```text
Client → Server 2
```

Server 2 может не найти его сессию.

Sticky Session решает эту проблему:

```text
Client → Server 1
Client → Server 1
Client → Server 1
```

---

## ⚠️ Недостатки

### 1. Неравномерная нагрузка

Один сервер может получить много "тяжёлых" клиентов:

```text
Server 1 → 100 клиентов
Server 2 → 20 клиентов
Server 3 → 15 клиентов
```

При этом клиенты остаются привязанными к своим серверам.

### 2. Отказ сервера

Если Server 1 вышел из строя:

```text
Client
   ↓
Server 1 ❌
```

его сессия может потеряться, если она хранилась только на Server 1.

### 3. Масштабирование становится сложнее

При добавлении или удалении серверов нужно учитывать существующие привязки клиентов.

---

## 🏗️ Более современный подход

Вместо хранения сессии непосредственно на backend-сервере часто используют **общее хранилище**:

```text
              ┌── Server 1 ──┐
Client → LB ──┼── Server 2 ──┼── Redis
              └── Server 3 ──┘
```

Например:

```text
Client
   ↓
Load Balancer
   ↓
Любой сервер
   ↓
Redis
   ↓
Session
```

Теперь запрос пользователя может попасть на любой сервер, потому что состояние сессии общее.

---

## 🆚 Sticky Session vs IP Hash

|               | Sticky Session      | IP Hash                |
| ------------- | ------------------- | ---------------------- |
| Привязка      | Клиент → сервер     | IP → сервер            |
| Механизм      | Например, cookie    | Hash IP                |
| Sticky-сессия | Да                  | Да, косвенно           |
| Зависит от IP | Нет                 | Да                     |
| NAT-проблемы  | Меньше              | Есть                   |
| Использование | Stateful-приложения | Простая привязка по IP |

---

## 🆚 Stateful vs Stateless

### Stateful

Состояние хранится на конкретном сервере:

```text
Client → Server 1
           ↓
        Session
```

Здесь Sticky Session может быть полезен.

### Stateless

Сервер не хранит состояние клиента локально:

```text
Client
   ↓
Load Balancer
   ↓
Server 1 / Server 2 / Server 3
```

Состояние хранится, например, в:

```text
Redis
PostgreSQL
JWT
```

В таком случае Sticky Session обычно **не требуется**.

---

## 🧠 Главное

```text
Sticky Session

Первый запрос
     ↓
 Server 2
     ↓
запоминаем привязку
     ↓
последующие запросы
     ↓
 Server 2
```

**Sticky Session — это механизм закрепления клиента за конкретным backend-сервером на время сессии.**

Главная причина использования:

**серверная сессия хранится локально на конкретном сервере.**

Но для современных распределённых приложений часто предпочтительнее сделать приложение **stateless** и вынести общее состояние в Redis или другую внешнюю систему.
