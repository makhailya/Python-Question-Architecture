# ⚖️ Алгоритмы балансировки нагрузки

## 🎯 Ответ на собеседовании

**Алгоритм балансировки нагрузки (Load Balancing Algorithm)** — это способ, по которому балансировщик решает, **на какой backend-сервер направить очередной запрос**.

Основные алгоритмы:

* **[[Round Robin]]** — по очереди;
* **[[Weighted Round Robin]]** — по очереди с учётом веса сервера;
* **[[Least Connections]]** — на сервер с наименьшим количеством активных соединений;
* **[[Weighted Least Connections]]** — Least Connections с учётом веса;
* **[[IP Hash]]** — выбор сервера на основе IP клиента;
* **[[Random]]** — случайный выбор.

Цель балансировки — **распределить нагрузку между несколькими backend-серверами**, чтобы избежать перегрузки одного сервера и повысить отказоустойчивость.

---

## 🎤 Суперкоротко

```text
Load Balancer
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
App1 App2 App3
```

Балансировщик выбирает backend по алгоритму:

```text
Round Robin       → по очереди
Least Connections → меньше всего соединений
IP Hash           → по IP клиента
Weighted          → с учётом мощности сервера
Random            → случайно
```

---

# 🔄 Round Robin

Самый простой алгоритм.

Запросы распределяются по очереди:

```text
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
Request 5 → Server 2
Request 6 → Server 3
```

Схема:

```text
        Load Balancer
              ↓
      ┌───────┼───────┐
      ↓       ↓       ↓
     App1    App2    App3
      ↑               │
      └───────────────┘
          по кругу
```

### Плюс

Простой и предсказуемый.

### Минус

Не учитывает:

* текущую нагрузку;
* количество соединений;
* производительность серверов.

Если один сервер мощнее другого, обычный Round Robin этого не учитывает.

---

# ⚖️ Weighted Round Robin

**Weighted Round Robin** — Round Robin с весами.

Каждому серверу назначается вес:

```text
Server 1 → weight 3
Server 2 → weight 2
Server 3 → weight 1
```

В результате более мощный сервер получает больше запросов:

```text
Server 1 → 3 части нагрузки
Server 2 → 2 части нагрузки
Server 3 → 1 часть нагрузки
```

Условно:

```text
App1 → ██████
App2 → ████
App3 → ██
```

Используется, когда серверы имеют разную производительность.

---

# 🔌 Least Connections

**Least Connections** отправляет новый запрос на сервер, у которого сейчас **меньше всего активных соединений**.

Например:

```text
App1 → 10 connections
App2 → 3 connections
App3 → 7 connections
```

Новый запрос:

```text
Request
   ↓
App2
```

Потому что:

```text
3 < 7 < 10
```

### Плюс

Учитывает текущую загрузку серверов.

### Минус

Количество соединений не всегда отражает реальную нагрузку CPU или сложность запросов.

---

# ⚖️ Weighted Least Connections

Комбинация:

```text
Least Connections
        +
      Weight
```

Например:

```text
App1 → мощный → weight 3
App2 → средний → weight 2
App3 → слабый  → weight 1
```

Балансировщик учитывает одновременно:

* количество соединений;
* производительность сервера.

Это полезно, если backend-серверы имеют разные характеристики.

---

# 🔑 IP Hash

**IP Hash** выбирает сервер на основе IP-адреса клиента.

Упрощённо:

```text
hash(client_ip) → Server
```

Например:

```text
192.168.1.10 → App1
192.168.1.20 → App2
192.168.1.30 → App3
```

При повторных запросах одного клиента он обычно попадает на тот же backend, пока структура backend-пула не меняется.

Это может использоваться для **session persistence / sticky sessions**.

---

# 🎲 Random

Балансировщик выбирает backend случайным образом:

```text
Request 1 → App2
Request 2 → App1
Request 3 → App3
Request 4 → App2
```

Простой вариант, но без учёта текущей нагрузки.

---

# 🍪 Sticky Sessions

Иногда важно, чтобы пользователь попадал на один и тот же backend.

Например:

```text
User
 ↓
App1
 ↓
Session
```

Следующие запросы:

```text
User
 ↓
App1
```

Это называется **sticky session**.

IP Hash — один из способов добиться подобного поведения.

Но в современных распределённых системах часто стараются сделать backend **stateless**:

```text
Client
  ↓
Load Balancer
  ↓
App1 / App2 / App3
```

А состояние хранят отдельно:

```text
App1 ─┐
App2 ─┼→ Redis / Database
App3 ─┘
```

---

# 🏥 Health Check

Балансировщик должен понимать, работает ли backend.

Например:

```text
App1 → healthy
App2 → healthy
App3 → unhealthy
```

Тогда:

```text
             Load Balancer
                  ↓
          ┌───────┴───────┐
          ↓               ↓
        App1             App2

        App3
          ✕
```

Запросы на неисправный сервер временно не направляются.

Health check может выглядеть как:

```text
GET /health
```

Ответ:

```text
200 OK
```

# 🌐 Пример с Nginx

Nginx может использовать upstream:

```python
upstream backend {
    server app1:8000;
    server app2:8000;
    server app3:8000;
}


server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

По умолчанию запросы распределяются между upstream-серверами по алгоритму **Round Robin**.

Можно использовать веса:

```python
upstream backend {
    server app1:8000 weight=3;
    server app2:8000 weight=2;
    server app3:8000 weight=1;
}
```

Теперь `app1` получает больше запросов.

---

# 🆚 Сравнение алгоритмов

| Алгоритм                       | Принцип                    | Когда полезен                |
| ------------------------------ | -------------------------- | ---------------------------- |
| **Round Robin**                | По очереди                 | Серверы примерно одинаковые  |
| **Weighted Round Robin**       | По очереди + вес           | Серверы разной мощности      |
| **Least Connections**          | Меньше активных соединений | Разная длительность запросов |
| **Weighted Least Connections** | Соединения + вес           | Разная мощность серверов     |
| **IP Hash**                    | По IP клиента              | Sticky sessions              |
| **Random**                     | Случайно                   | Простые сценарии             |

---

# 🧠 Как выбрать алгоритм

```text
Серверы одинаковые?
        ↓
      Да
        ↓
 Round Robin
```

Если серверы разной мощности:

```text
Разная мощность
      ↓
Weighted Round Robin
```

Если запросы имеют сильно разную продолжительность:

```text
Разная длительность запросов
      ↓
Least Connections
```

Если нужно привязать клиента к серверу:

```text
Sticky Sessions
      ↓
IP Hash
```

# ⚠️ Важный момент

Балансировка по количеству запросов **не означает**, что нагрузка распределена равномерно.

Например:

```text
Request 1 → тяжёлый SQL-запрос
Request 2 → простой SELECT
```

Оба считаются одним запросом, но нагрузка на сервер может сильно отличаться.

Поэтому в реальных системах могут использоваться более сложные стратегии и метрики:

```text
CPU
RAM
connections
latency
response time
queue length
```

# 🧩 L4 и L7 Load Balancing

Балансировка может происходить на разных уровнях.

### L4 — Transport Layer

Балансировщик работает с:

```text
TCP
UDP
IP
Port
```

Он не обязательно понимает содержимое HTTP-запроса.

```text
Client
  ↓
L4 Load Balancer
  ↓
Server
```

### L7 — Application Layer

Балансировщик понимает HTTP:

```text
URL
Host
Headers
Cookies
HTTP Method
```

Например:

```text
/api/users → User Service

/api/orders → Order Service
```

Nginx может работать на уровне L7 как HTTP reverse proxy.

### Формула для собеседования

> **Алгоритм балансировки нагрузки определяет, на какой backend направить очередной запрос. Наиболее распространённые варианты — Round Robin, Weighted Round Robin, Least Connections и IP Hash. Выбор алгоритма зависит от характеристик серверов, типа нагрузки и необходимости сохранять состояние сессии.**

```text
Load Balancing
      ↓
Выбрать backend
      ↓
по определённому алгоритму
      ↓
App1 / App2 / App3
```
