# 🏗️ Layered System

## 🎯 Ответ на собеседовании

**Layered System** — это принцип REST, согласно которому система может состоять из **нескольких независимых слоёв**, каждый из которых выполняет свою задачу.

Клиент не обязан знать, **с каким именно сервером или слоем он взаимодействует**.

Например:

```text id="m7k4qz"
Client
   ↓
Nginx
   ↓
Load Balancer
   ↓
FastAPI
   ↓
PostgreSQL
```

Клиент видит API и не обязан знать, что между ним и приложением находятся Nginx, балансировщик или другие промежуточные компоненты.

---

## 🎤 Суперкоротко

**Layered System = система состоит из независимых слоёв, каждый отвечает за свою задачу.**

```text id="z3s1py"
Client
  ↓
Proxy
  ↓
Load Balancer
  ↓
API
  ↓
Database
```

Клиент не знает внутреннюю структуру системы.

---

## 🔄 Как работает

Допустим, клиент отправляет:

```python id="q7m2vs"
GET /api/users
```

Запрос может пройти через несколько слоёв:

```text id="2s7q8k"
Client
   ↓
Nginx
   ↓
Load Balancer
   ↓
FastAPI
   ↓
PostgreSQL
```

Каждый компонент выполняет свою функцию.

Например:

```text id="n1l9xy"
Nginx          → reverse proxy, TLS, статика
Load Balancer  → распределение запросов
FastAPI        → API и бизнес-логика
PostgreSQL     → хранение данных
```

---

## 🧱 Почему клиент не должен знать о слоях

Клиент взаимодействует только с доступным ему интерфейсом:

```text id="a8x6hr"
Client
   ↓
API
```

Он не обязан знать:

```text id="7a3wqk"
есть ли Nginx
сколько backend-серверов
какая база данных
есть ли Redis
какой балансировщик используется
```

Внутреннюю архитектуру можно изменять, сохраняя внешний API.

---

## 🔀 Пример с балансировкой

```text id="zj7p6d"
                 ┌→ FastAPI 1
Client → Nginx ──┼→ FastAPI 2
                 └→ FastAPI 3
```

Клиент отправляет запрос только на Nginx.

Nginx или другой балансировщик решает, на какой backend его направить.

Клиенту не нужно знать о существовании трёх серверов.

---

## 💾 Пример с кэшем

Промежуточный слой может выполнять кэширование:

```text id="h2s7ca"
Client
   ↓
Cache
   ↓
API Server
```

Если данные есть в кэше:

```text id="y9p3kd"
Client → Cache → Response
```

До backend запрос может вообще не дойти.

---

## 🔐 Пример с авторизацией

Можно добавить отдельный слой, который проверяет запрос:

```text id="d4j6tm"
Client
   ↓
API Gateway
   ↓
Authentication
   ↓
Backend
```

Backend получает уже проверенный запрос.

---

## 🚀 Преимущества

### 1. Независимость компонентов

Каждый слой отвечает за свою задачу.

### 2. Масштабирование

Можно независимо масштабировать отдельные части:

```text id="u4m8fe"
Load Balancer
      ↓
┌─────┼─────┐
↓     ↓     ↓
API   API   API
```

### 3. Безопасность

Внутренние компоненты можно скрыть от клиента.

### 4. Гибкость

Можно заменить внутреннюю реализацию, не изменяя клиентский интерфейс.

---

## ⚠️ Важный нюанс

**Layered System не означает, что каждый запрос обязательно должен проходить через большое количество слоёв.**

Это архитектурное ограничение REST, которое **разрешает** использовать промежуточные компоненты.

Например:

```text id="d8j4qk"
Client → API Server
```

тоже допустимо.

А более сложная система:

```text id="k3v9ps"
Client
  ↓
CDN
  ↓
Nginx
  ↓
Load Balancer
  ↓
API
  ↓
Database
```

использует несколько слоёв.

---

## 🆚 Layered System vs Client-Server

**Client-Server**:

```text id="g1g5zk"
Client ↔ Server
```

Разделяет систему на клиентскую и серверную части.

**Layered System**:

```text id="8m6w2q"
Client
  ↓
Layer 1
  ↓
Layer 2
  ↓
Layer 3
```

Позволяет организовать систему в виде нескольких независимых слоёв.

То есть **Layered System расширяет идею разделения ответственности внутри распределённой системы**.

---

## 🧠 Главное

```text id="s8p5v2"
Layered System

Client
   ↓
[ Layer 1 ]
   ↓
[ Layer 2 ]
   ↓
[ Layer 3 ]
   ↓
Server
```

Каждый слой выполняет свою функцию, а клиент не обязан знать о внутренней структуре системы.

**Layered System = REST-принцип, позволяющий строить систему из независимых промежуточных слоёв, скрывающих внутреннюю архитектуру от клиента.**
