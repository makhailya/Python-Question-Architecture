# 💾 Cacheable

## 🎯 Ответ на собеседовании

**Cacheable** — это принцип REST, согласно которому **ответ сервера должен явно определять, можно ли его кэшировать и на какой срок**.

Если ответ разрешено кэшировать, клиент или промежуточный кэш может сохранить его и использовать повторно, не обращаясь каждый раз к серверу.

Например:

```python
GET /api/products
```

Сервер может вернуть:

```python
Cache-Control: max-age=3600
```

Это означает, что ответ можно использовать из кэша в течение **3600 секунд**.

---

## 🎤 Суперкоротко

**Cacheable = ответы можно кэшировать, если сервер разрешает это.**

```text
Client
  ↓
Cache
  ↓
Server
```

Повторный запрос может быть обслужен из кэша.

---

## 🔄 Как это работает

Первый запрос:

```text
Client
   ↓
GET /api/products
   ↓
Server
   ↓
Response
   ↓
Cache
```

Ответ сохраняется в кэше.

Следующий запрос:

```text
Client
   ↓
GET /api/products
   ↓
Cache
   ↓
Response
```

Сервер может вообще не получать этот запрос.

---

## ⚙️ Cache-Control

Один из основных HTTP-заголовков для управления кэшированием:

```python
Cache-Control: max-age=3600
```

Основные варианты:

```python
Cache-Control: no-cache
```

Ответ можно хранить, но перед повторным использованием нужно проверить его актуальность.

```python
Cache-Control: no-store
```

Ответ вообще нельзя сохранять в кэше.

```python
Cache-Control: max-age=3600
```

Ответ считается свежим в течение 3600 секунд.

---

## 💡 Пример

Допустим, API возвращает список категорий:

```python
GET /api/categories
```

Категории меняются редко, поэтому сервер может разрешить кэширование:

```python
Cache-Control: max-age=86400
```

Теперь клиент может использовать сохранённый ответ в течение суток.

---

## 🚀 Зачем нужно кэширование

Кэширование позволяет:

* уменьшить количество запросов к серверу;
* снизить нагрузку на backend;
* уменьшить количество обращений к базе данных;
* ускорить получение данных;
* снизить задержку ответа.

Например:

```text
Без кэша:

1000 клиентов
      ↓
1000 запросов
      ↓
Backend
      ↓
PostgreSQL
```

С кэшем:

```text
1000 клиентов
      ↓
    Cache
      ↓
Backend
      ↓
PostgreSQL
```

Большая часть запросов может обслуживаться непосредственно из кэша.

---

## 🧱 Где может находиться кэш

Кэширование может происходить на разных уровнях:

```text
Client
  ↓
Browser Cache
  ↓
CDN / Proxy Cache
  ↓
Nginx
  ↓
Backend
  ↓
Redis
  ↓
Database
```

Не обязательно использовать все уровни одновременно.

---

## 🔗 Cacheable и Stateless

Эти принципы хорошо сочетаются.

**Stateless**:

```text
Каждый запрос самодостаточен
```

**Cacheable**:

```text
Ответ можно повторно использовать
```

Благодаря этому промежуточный сервер может кэшировать ответы, не зная внутреннего состояния приложения.

---

## ⚠️ Важный нюанс

**Cacheable не означает, что абсолютно все ответы нужно кэшировать.**

Например, персональные данные пользователя:

```python
GET /api/profile
```

могут зависеть от конкретного пользователя и требуют осторожности при кэшировании.

Особенно важно не допустить ситуацию, когда:

```text
User A
  ↓
Cache
  ↓
данные User B
```

Поэтому сервер должен правильно задавать правила кэширования.

---

## 🆚 Cacheable vs No-Cache

| Директива      | Смысл                                                         |
| -------------- | ------------------------------------------------------------- |
| `max-age=3600` | можно использовать кэш 1 час                                  |
| `no-cache`     | можно хранить, но перед использованием проверить актуальность |
| `no-store`     | вообще не сохранять ответ                                     |

Важно:

**`no-cache` ≠ "не кэшировать".**

`no-cache` разрешает хранение, но требует проверки актуальности перед повторным использованием.

---

## 🧠 Главное

```text
Cacheable

Request
   ↓
Server
   ↓
Response
   ↓
Cache
   ↓
повторное использование
```

**Cacheable — REST-принцип, согласно которому ответы должны определять, могут ли они кэшироваться.**

Главные преимущества:

**меньше запросов → меньше нагрузка → быстрее ответы.**

Для собеседования достаточно запомнить:

> **Cacheable означает, что ответ API может быть сохранён и повторно использован клиентом или промежуточным кэшем в соответствии с правилами кэширования.**
