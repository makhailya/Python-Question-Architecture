# 🌐 REST — ключевые принципы

## 🎯 Ответ на собеседовании

**REST (REpresentational State Transfer)** — это **архитектурный стиль**, а не протокол и не стандарт, предназначенный для построения распределённых клиент-серверных систем.

REST определяет набор **архитектурных ограничений (constraints)**, которым должна соответствовать система.

Ключевые принципы REST:

1. **[[Client-Server ]]** - разделение клиента и сервера по ответственности
2. **[[Stateless]]** - каждый запрос самодостаточен
3. **[[Cacheable]]** - ответы можно кэшировать, если сервер разрешает это
4. **[[Uniform Interface]]** - единый и предсказуемый способ взаимодействия с ресурсами
5. **[[Layered System]]** - нескольких независимых слоёв
6. **[[Code on Demand]]** — сервер может отправить клиенту исполняемый код для выполнения

---

## 🎤 Суперкоротко

```text
REST =
Client-Server
+ Stateless
+ Cacheable
+ Uniform Interface
+ Layered System
+ Code on Demand (опционально)
```

Главная идея:

**клиент и сервер разделены, каждый запрос самодостаточен, ресурсы имеют единый интерфейс взаимодействия.**

---

## 1. 🖥️ Client-Server

Клиент и сервер должны быть **разделены по ответственности**.

```text
Client
  ↓ HTTP
Server
  ↓
Database
```

### Клиент отвечает за:

* пользовательский интерфейс;
* взаимодействие с пользователем;
* отправку запросов.

### Сервер отвечает за:

* бизнес-логику;
* хранение и обработку данных;
* предоставление API.

Разделение позволяет независимо развивать клиент и сервер.

Например:

```text
Web      ──┐
Mobile   ──┼──→ REST API
Telegram ──┘
```

---

## 2. 🧠 Stateless

**Сервер не должен хранить состояние клиента между запросами.**

Каждый запрос должен содержать **всю информацию, необходимую серверу для его обработки**.

Например:

```python id="l8c1sm"
GET /api/profile
Authorization: Bearer <token>
```

Сервер не должен рассчитывать на то, что предыдущий запрос уже установил какое-то состояние.

```text
Request 1 → Server
Request 2 → Server
Request 3 → Server
```

Каждый запрос обрабатывается независимо.

### Почему это важно?

Любой сервер может обработать запрос:

```text
             ┌→ Server 1
Client → LB ─┼→ Server 2
             └→ Server 3
```

Это упрощает:

* горизонтальное масштабирование;
* балансировку нагрузки;
* отказоустойчивость.

---

## 3. 💾 Cacheable

Ответ сервера должен явно определять, **можно ли его кэшировать**.

Например:

```python id="g9n0gy"
Cache-Control: max-age=3600
```

Если ответ можно кэшировать, клиент или промежуточный сервер может использовать сохранённый ответ вместо повторного запроса.

```text
Client
  ↓
Cache
  ↓
Server
```

Это уменьшает:

* количество запросов;
* нагрузку на сервер;
* задержку получения данных.

---

## 4. 🔗 Uniform Interface

**Единый интерфейс взаимодействия с ресурсами** — один из самых важных принципов REST.

Клиент должен взаимодействовать с ресурсами стандартным и предсказуемым способом.

Например:

```python id="v6ozk9"
GET    /users
GET    /users/10
POST   /users
PATCH  /users/10
DELETE /users/10
```

Здесь:

```text
/users       → коллекция пользователей
/users/10    → конкретный пользователь
```

REST API должен использовать единообразные правила работы с ресурсами.

### Основные идеи Uniform Interface

**1. Ресурсы идентифицируются URI**

```text
/users/10
/orders/25
/products/100
```

**2. Используются стандартные HTTP-методы**

```text
GET
POST
PUT
PATCH
DELETE
```

**3. Представление ресурса отделено от самого ресурса**

Например, один и тот же пользователь может быть представлен в JSON:

```python id="v7j1ml"
{
    "id": 10,
    "name": "Ilya"
}
```

Сам ресурс при этом не является JSON-документом — JSON является его **представлением**.

**4. Сообщения должны быть понятными и самодостаточными**

По запросу и ответу должно быть понятно, что происходит и как их обработать.

---

## 5. 🏗️ Layered System

REST допускает построение системы из **слоёв**.

Клиент не обязан знать, напрямую ли он взаимодействует с конечным сервером.

```text
Client
   ↓
Nginx
   ↓
Load Balancer
   ↓
API Server
   ↓
Database
```

Каждый слой выполняет свою задачу.

Например:

```text
Client
   ↓
Nginx → TLS termination
   ↓
Load Balancer → распределение нагрузки
   ↓
FastAPI → бизнес-логика
   ↓
PostgreSQL → данные
```

Клиенту не обязательно знать обо всех этих компонентах.

---

## 6. ⚙️ Code on Demand

**Необязательный принцип REST.**

Сервер может передавать клиенту код, который клиент выполняет.

Например:

```text
Server
   ↓
JavaScript
   ↓
Browser
```

Это единственное **опциональное** ограничение REST.

В типичных REST API этот принцип часто вообще не используется.

---

# 🧩 REST и HTTP

REST **не является HTTP**.

REST — это архитектурный стиль:

```text
REST
 ↓
архитектурные ограничения
```

HTTP — это протокол:

```text
HTTP
 ↓
протокол передачи данных
```

REST часто реализуется поверх HTTP, используя его возможности:

```text
GET
POST
PUT
PATCH
DELETE

HTTP status codes
Headers
URI
Cache-Control
```

Поэтому правильно говорить:

> **REST API часто реализуют поверх HTTP.**

Но REST и HTTP — не одно и то же.

# 🧠 Пример REST API

Допустим, есть ресурс `users`.

```python id="h4z4e2"
GET    /users
GET    /users/10
POST   /users
PATCH  /users/10
DELETE /users/10
```

Здесь:

```text
/users
   ↓
коллекция ресурсов

/users/10
   ↓
конкретный ресурс
```

А HTTP-метод определяет операцию:

```text
GET    → получить
POST   → создать
PATCH  → частично изменить
DELETE → удалить
```

---

# ⚠️ Частая ошибка на собеседовании

Неправильно:

> REST — это протокол.

Правильно:

> **REST — архитектурный стиль.**

Неправильно:

> REST — это стандарт API.

Правильно:

> **REST определяет набор архитектурных ограничений для построения распределённых систем.**

Также REST не требует конкретно JSON:

```text
REST ≠ JSON
REST ≠ HTTP
```

JSON — всего лишь распространённый формат представления данных.

# 🧠 Главное

```text
REST
│
├── Client-Server
│   └── разделение клиента и сервера
│
├── Stateless
│   └── каждый запрос самодостаточен
│
├── Cacheable
│   └── ответы могут кэшироваться
│
├── Uniform Interface
│   └── единый интерфейс работы с ресурсами
│
├── Layered System
│   └── система состоит из независимых слоёв
│
└── Code on Demand
    └── сервер может передавать исполняемый код
       (опционально)
```

**REST = архитектурный стиль + набор ограничений.**

Самые важные для собеседования:

**Client-Server → Stateless → Cacheable → Uniform Interface → Layered System.**

**Code on Demand — опциональный принцип.**
