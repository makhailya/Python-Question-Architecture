# 🌐 REST API

## 🎤 Короткий ответ

**REST API** — это API, построенный на принципах [[REST]] для взаимодействия между клиентом и сервером через [[HTTP]].

В [[REST]] ресурсы представлены [[URI]], а операции над ними выполняются через HTTP-методы:

* `GET` — получить;
* `POST` — создать;
* `PUT` — полностью заменить;
* `PATCH` — частично изменить;
* `DELETE` — удалить.

Ключевой принцип REST — **stateless**: сервер не должен хранить состояние конкретной клиентской сессии между запросами. Каждый запрос должен содержать всё необходимое для его обработки.

---

## 🗣️ Ответ на собеседовании

REST API — это архитектурный подход к построению API, основанный на принципах REST и обычно реализуемый поверх HTTP.

В REST мы работаем не просто с набором функций, а с **ресурсами**. Например, есть ресурс `users`, и клиент взаимодействует с ним через HTTP:

```text
GET    /users
GET    /users/42
POST   /users
PATCH  /users/42
DELETE /users/42
```

HTTP-метод определяет смысл операции, а URI идентифицирует ресурс.

Одно из основных свойств REST — **stateless**. Сервер не должен зависеть от состояния предыдущего запроса клиента: каждый запрос содержит необходимую для обработки информацию.

REST также использует стандартные возможности HTTP — методы, статус-коды, заголовки, представление данных и кеширование.

При этом важно понимать, что REST — это не просто «JSON через HTTP». REST — это набор архитектурных ограничений, а конкретный API может соблюдать их в разной степени.

# 📚 Разбор поглубже

## 1. Что такое API

**API — Application Programming Interface**.

Это интерфейс, через который одна программа взаимодействует с другой.

Например:

```text id="7v3m91"
Frontend
   │
   │ HTTP
   ↓
Backend API
   │
   ↓
PostgreSQL
```

Frontend не должен знать, как именно backend хранит данные.

Он взаимодействует с API через определённый контракт.

---

# 2. Что такое REST

**REST — Representational State Transfer.**

Это архитектурный стиль, предложенный Роем Филдингом.

REST задаёт набор архитектурных ограничений, которые помогают строить распределённые системы.

Основные ограничения:

```text id="j8c4p2"
REST
├── Client-Server
├── Stateless
├── Cacheable
├── Uniform Interface
├── Layered System
└── Code-on-Demand
    └── optional
```

На практике при разработке backend API особенно часто обсуждают:

* ресурсы;
* URI;
* HTTP-методы;
* stateless;
* статус-коды;
* кеширование;
* единый интерфейс.

---

# 3. Ресурс

Центральное понятие REST — **resource**.

Например:

```text id="k3s7n5"
User
Order
Product
Article
Comment
```

Ресурс получает URI.

Например:

```text id="x9f2q6"
GET /users
GET /users/42

GET /orders
GET /orders/100

GET /products
GET /products/15
```

Здесь:

```text id="e8m1r4"
/users       → коллекция пользователей
/users/42    → конкретный пользователь
```

---

# 4. URI — идентификатор ресурса

URI должен описывать **ресурс**, а HTTP-метод — операцию над ним.

Хороший вариант:

```text id="q7w3p8"
GET /users/42
```

Вместо:

```text id="v5n2k1"
GET /getUser?id=42
```

И:

```text id="h4r8s6"
POST /users
```

вместо:

```text id="m2c7x9"
POST /createUser
```

Идея:

> **Не помещать действие в URI, если его смысл уже выражается HTTP-методом.**

---

# 5. HTTP-методы в REST

## GET

Получение ресурса.

```text id="n8x3q5"
GET /users/42
```

Ответ:

```python id="p6d1k4"
{
    "id": 42,
    "name": "Ivan"
}
```

`GET` не должен изменять состояние ресурса.

---

## POST

Создание нового ресурса или выполнение операции, для которой семантика других методов не подходит.

```text id="r7m2v9"
POST /users
```

Тело:

```python id="c5q8w1"
{
    "name": "Ivan",
    "email": "ivan@example.com"
}
```

Сервер может создать:

```text id="a3f6k2"
User #42
```

Частый успешный статус:

```text
201 Created
```

---

## PUT

Обычно используется для **полной замены** ресурса.

```text id="u4s9j7"
PUT /users/42
```

Например:

```python id="b8m3p6"
{
    "name": "Ivan",
    "email": "new@example.com"
}
```

Концептуально:

```text
старое представление
        ↓
     заменить
        ↓
новое представление
```

---

## PATCH

Частичное изменение ресурса.

```text id="z6q2n8"
PATCH /users/42
```

Например:

```python id="d4r7k3"
{
    "email": "new@example.com"
}
```

Меняется только указанный атрибут.

---

## DELETE

Удаление ресурса.

```text id="w9h5s2"
DELETE /users/42
```

---

# 6. Основная таблица

| Метод    | Типичная семантика              | Пример             |
| -------- | ------------------------------- | ------------------ |
| `GET`    | Получить                        | `GET /users/42`    |
| `POST`   | Создать / инициировать операцию | `POST /users`      |
| `PUT`    | Полностью заменить              | `PUT /users/42`    |
| `PATCH`  | Частично изменить               | `PATCH /users/42`  |
| `DELETE` | Удалить                         | `DELETE /users/42` |

Важно: это **семантика HTTP**, а не жёсткое правило, что сервер обязан использовать каждый метод только одним способом.

---

# 7. Stateless

Один из самых важных принципов REST.

**Stateless** означает, что сервер не должен хранить состояние клиентской сессии между запросами таким образом, чтобы следующий запрос зависел от внутреннего состояния предыдущего запроса.

Например:

```text id="r2v8m5"
Request 1
GET /users/42
Authorization: Bearer ...

Request 2
GET /orders
Authorization: Bearer ...
```

Каждый запрос содержит необходимую информацию для его обработки.

Сервер не должен рассуждать:

> «Это тот клиент, который пять минут назад делал запрос №1, поэтому я знаю, что ему нужно».

---

# 8. Stateless ≠ сервер вообще ничего не хранит

Это распространённая ошибка.

Stateless **не означает**, что сервер не хранит данные.

Сервер спокойно может хранить:

```text id="c8k4n2"
Users
Orders
Products
Payments
```

в PostgreSQL.

Речь идёт именно о **состоянии взаимодействия клиента и сервера**.

```text
Данные приложения
→ могут храниться

Session state конкретного клиента
→ не должен быть необходим для обработки следующего запроса
```

---

# 9. REST и JWT

Например:

```text id="g7p3w9"
GET /profile
Authorization: Bearer <token>
```

Сервер получает токен и может определить пользователя без необходимости хранить состояние каждой HTTP-сессии на сервере.

Это хорошо сочетается с stateless-подходом.

Но важно:

> **JWT не является обязательным для REST.**

REST API может использовать:

* JWT;
* session cookies;
* API keys;
* OAuth;
* другие механизмы аутентификации.

REST API использует HTTP status codes для передачи результата операции.


# 11. `401` vs `403`

Частый вопрос на собеседовании.

### 401 Unauthorized

У клиента нет корректной аутентификации.

Например:

```text
Authorization отсутствует
```

или токен недействителен.

### 403 Forbidden

Сервер понял, кто пользователь, но запрещает ему выполнять операцию.

```text
Пользователь авторизован
        ↓
прав недостаточно
        ↓
403
```

# 12. Идемпотентность

**Идемпотентный запрос** — запрос, многократное выполнение которого имеет тот же эффект на состояние сервера, что и однократное выполнение.

Например:

```text id="f2k7m4"
PUT /users/42
```

с одним и тем же представлением ресурса можно повторить несколько раз.

Результирующее состояние должно быть тем же.

```text id="s5n8q1"
PUT
PUT
PUT
PUT
 ↓
одно и то же состояние
```

По спецификации HTTP `GET`, `PUT` и `DELETE` являются идемпотентными; `POST` обычно нет.

Важно:

> Идемпотентность относится к **эффекту операции**, а не к тому, будет ли каждый ответ абсолютно одинаковым.

---

# 13. REST ≠ JSON

Очень распространённая ошибка:

> «REST API — это JSON через HTTP».

Нет.

JSON — это **формат представления данных**.

REST — архитектурный стиль.

Можно использовать:

```text
JSON
XML
HTML
другие представления
```

REST API часто использует JSON, потому что он удобен для современных веб-приложений, но JSON сам по себе не делает API RESTful.

---

# 14. REST ≠ HTTP

REST часто реализуют поверх HTTP, но понятия разные.

```text id="y3r6p8"
REST
└── архитектурный стиль

HTTP
└── протокол прикладного уровня
```

HTTP предоставляет:

* методы;
* статус-коды;
* заголовки;
* URI;
* кеширование;
* семантику запросов.

REST использует эти механизмы в рамках определённых архитектурных ограничений.

# 16. Query Parameters

Для фильтрации, сортировки и пагинации часто используют query parameters.

Например:

```text id="r6v3k9"
GET /products?category=phone&page=2&limit=20
```

Здесь:

```text
category=phone
page=2
limit=20
```

не являются отдельными ресурсами.

Они задают параметры получения коллекции.

---

# 17. Path Parameters

Если идентифицируем конкретный ресурс:

```text id="m7q2x5"
GET /users/42
```

`42` — path parameter.

В FastAPI:

```python id="c9f4k1"
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"id": user_id}
```

# 18. REST и CRUD

Очень часто REST API сопоставляют с CRUD:

```text id="w5n8p3"
CRUD
├── Create → POST
├── Read   → GET
├── Update → PUT / PATCH
└── Delete → DELETE
```

Это полезная модель для начала.

Но:

> **REST не равен CRUD.**

REST описывает архитектурные ограничения, а CRUD — базовые операции над данными.

---

# 19. Что значит RESTful

Можно встретить термин:

**RESTful API**

Обычно так называют API, которое достаточно хорошо следует принципам REST.

Но важно понимать:

```text
REST
```

не является бинарным переключателем:

```text
REST / НЕ REST
```

Можно соблюдать одни ограничения и нарушать другие.

Поэтому на собеседовании лучше говорить:

> «API следует REST-принципам в такой-то степени»

а не автоматически называть любой HTTP API RESTful.

Самая полезная модель:

```text id="x8m3q6"
Client

  │ HTTP request
```
