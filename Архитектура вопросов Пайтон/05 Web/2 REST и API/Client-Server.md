# 🖥️ Client-Server

## 🎯 Ответ на собеседовании

**Client-Server** — это архитектурный принцип REST, согласно которому **клиент и сервер разделены по ответственности** и могут развиваться независимо друг от друга.

Клиент отвечает за **интерфейс и взаимодействие с пользователем**, а сервер — за **данные, бизнес-логику и их обработку**.

Например:

```text
Client
  ↓ HTTP-запрос
Server
  ↓
Database
```

Клиент не должен знать, как сервер внутри реализует бизнес-логику или работает с базой данных. Он взаимодействует с сервером через определённый интерфейс — например, REST API.

---

## 🎤 Суперкоротко

**Client-Server = разделение клиента и сервера по ответственности.**

```text
Client → API → Server → Database
```

Клиент отвечает за интерфейс, сервер — за данные и бизнес-логику.

---

## 👤 Client

Клиент — сторона, которая **отправляет запросы серверу** и отображает полученный результат.

Например:

* Web-приложение;
* мобильное приложение;
* desktop-приложение;
* другой backend-сервис.

Пример:

```python
GET /api/users/10
```

Клиент отправляет запрос и получает ответ:

```python
{
    "id": 10,
    "name": "Ilya"
}
```

---

## 🖥️ Server

Сервер принимает запрос, выполняет необходимую обработку и возвращает результат.

Например:

```text
Client
   ↓
GET /api/users/10
   ↓
FastAPI
   ↓
PostgreSQL
   ↓
User
   ↓
JSON response
   ↓
Client
```

Сервер может выполнять:

* бизнес-логику;
* аутентификацию и авторизацию;
* работу с базой данных;
* валидацию;
* обработку запросов;
* формирование ответа.

---

## 🔗 Разделение ответственности

Главная идея:

```text
┌──────────────┐          ┌──────────────┐
│    Client    │          │    Server    │
│              │          │              │
│ UI           │  HTTP    │ API          │
│ UX           │ ───────→ │ Logic        │
│ отображение  │ ←─────── │ Data         │
└──────────────┘          └──────────────┘
```

Клиенту не нужно знать:

```text
как устроена БД
как реализована бизнес-логика
какие внутренние сервисы используются
```

Серверу, в свою очередь, не нужно знать, **как именно клиент отображает полученные данные**.

---

## 🔄 Независимое развитие

Одна из главных выгод Client-Server — клиент и сервер можно изменять независимо, пока сохраняется совместимый API.

Например:

```text
Web Client ──────┐
                 │
Mobile Client ───┼──→ REST API → Backend → DB
                 │
Desktop Client ──┘
```

Можно изменить frontend, не переписывая backend.

И наоборот — изменить внутреннюю реализацию backend, сохранив API для клиентов.

---

## 💡 Пример из Python Backend

Допустим, backend написан на **FastAPI**:

```text
React
  ↓
FastAPI
  ↓
PostgreSQL
```

Frontend отправляет:

```python
GET /api/products
```

FastAPI:

1. принимает запрос;
2. обращается к PostgreSQL;
3. получает товары;
4. формирует ответ;
5. возвращает данные клиенту.

Frontend при этом не работает напрямую с PostgreSQL.

---

## ✅ Преимущества

* разделение ответственности;
* независимое развитие клиента и сервера;
* возможность иметь несколько клиентов для одного API;
* упрощение масштабирования;
* возможность независимо изменять внутреннюю реализацию сервера.

---

## 🧠 Главное

```text
Client
  ↓ запрос
Server
  ↓ обработка
Database
  ↓ данные
Server
  ↓ ответ
Client
```

**Client-Server — это разделение системы на клиентскую и серверную части с чётким разделением ответственности.**

Для REST важно запомнить:

> **Клиент отвечает за представление и взаимодействие с пользователем, сервер — за хранение и обработку данных и бизнес-логику.**

При этом клиент и сервер **не должны быть жёстко связаны внутренней реализацией друг друга**.
