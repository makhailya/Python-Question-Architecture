# 🌐 HTTP/1.1

## 🎤 Суперкоротко

> **HTTP/1.1 — текстовый протокол прикладного уровня, в котором запросы и ответы передаются последовательно по TCP-соединению. Он поддерживает постоянные соединения через Keep-Alive, но при последовательной обработке запросов возникает проблема Head-of-Line Blocking.**

---

# 🎯 Ответ на собеседовании

**HTTP/1.1** — версия протокола HTTP, стандартизированная в 1997 году.

Она работает поверх **TCP** и использует текстовое представление HTTP-запросов и ответов.

Типичный запрос выглядит так:

```python
request = """GET /users/42 HTTP/1.1
Host: example.com
Connection: keep-alive
"""
```

Сервер возвращает HTTP-ответ:

```python
response = """HTTP/1.1 200 OK
Content-Type: application/json

{"id": 42, "name": "Ilya"}
"""
```

---

# 🔗 HTTP/1.1 работает поверх TCP

HTTP/1.1 относится к **прикладному уровню**.

Для передачи данных он обычно использует **TCP**:

```text
Application
    ↓
HTTP/1.1
    ↓
TCP
    ↓
IP
    ↓
Network
```

TCP отвечает за:

* установление соединения;
* доставку данных;
* порядок байтов;
* повторную передачу потерянных данных;
* контроль перегрузки.

HTTP отвечает уже за структуру и смысл запросов и ответов.

---

# 📝 Текстовый формат

HTTP/1.1 использует **текстовый формат** сообщений.

Например:

```python
request = """GET /users HTTP/1.1
Host: example.com
Accept: application/json

"""
```

Можно визуально увидеть:

```text
Метод + путь + версия
        ↓
GET /users HTTP/1.1

Заголовки
        ↓
Host: example.com
Accept: application/json

Пустая строка
        ↓
разделяет headers и body
```

Это делает протокол относительно простым для понимания и диагностики.

---

# 🔄 Keep-Alive

В HTTP/1.0 для каждого запроса часто создавалось отдельное TCP-соединение.

HTTP/1.1 по умолчанию поддерживает **persistent connection** — постоянное TCP-соединение.

Идея:

```text
TCP connection
      ↓
Request 1
Response 1
      ↓
Request 2
Response 2
      ↓
Request 3
Response 3
      ↓
закрытие соединения
```

Это позволяет не устанавливать новое TCP-соединение для каждого запроса.

Преимущество:

```text
меньше TCP handshake
        ↓
меньше накладных расходов
        ↓
лучше производительность
```

---

# 📦 Host Header

В HTTP/1.1 заголовок `Host` является обязательным.

Например:

```python
headers = {
    "Host": "example.com",
}
```

Он нужен потому, что один IP-адрес может обслуживать несколько доменных имён.

Например:

```text
example.com
api.example.com
shop.example.com
```

могут находиться на одном сервере.

`Host` позволяет серверу понять, для какого домена предназначен запрос.

---

# 🧵 Последовательная обработка запросов

Одна из важных особенностей HTTP/1.1 — запросы в рамках одного соединения исторически обрабатывались последовательно.

Упрощённо:

```text
Request 1
    ↓
Response 1
    ↓
Request 2
    ↓
Response 2
```

Если первый запрос выполняется долго:

```text
Request 1
    ↓
долго выполняется
    ↓
Response 1
    ↓
Request 2
```

второй запрос вынужден ждать.

---

# 🚧 Head-of-Line Blocking

Это приводит к проблеме **Head-of-Line Blocking (HOL Blocking)**.

Например:

```text
Request 1 → ███████████████████
Request 2 → ░░░░░░░░░░░░░░░░░░░
Request 3 → ░░░░░░░░░░░░░░░░░░░
```

Если первый запрос задержался, последующие запросы на этом соединении могут ждать его завершения.

Именно эту проблему HTTP/2 значительно уменьшает с помощью **мультиплексирования**.

---

# 🚀 Pipeline

HTTP/1.1 формально поддерживает **HTTP pipelining**.

Идея:

```text
Request 1 ─┐
Request 2 ─┼──→ TCP connection
Request 3 ─┘
```

То есть клиент может отправить несколько запросов, не дожидаясь каждого ответа.

Но ответы должны возвращаться в определённом порядке:

```text
Request 1 → Response 1
Request 2 → Response 2
Request 3 → Response 3
```

Из-за проблем с блокировками и совместимостью HTTP pipelining практически не получил широкого применения.

---

# 🌍 Несколько TCP-соединений

Из-за ограничений последовательной обработки браузеры часто открывали **несколько TCP-соединений** к одному серверу.

Упрощённо:

```text
Browser
   │
   ├── TCP connection 1 → Request
   │
   ├── TCP connection 2 → Request
   │
   ├── TCP connection 3 → Request
   │
   └── TCP connection 4 → Request
```

Это позволяло выполнять больше операций одновременно.

Но дополнительные соединения означают дополнительные:

* TCP handshake;
* ресурсы;
* нагрузку;
* служебный трафик.

HTTP/2 решает эту проблему другим способом — через мультиплексирование потоков внутри одного соединения.

---

# 📦 Chunked Transfer Encoding

HTTP/1.1 позволяет передавать тело ответа частями с помощью **chunked transfer encoding**.

Это удобно, когда сервер заранее не знает полный размер ответа.

Например, концептуально:

```text
chunk 1
   ↓
chunk 2
   ↓
chunk 3
   ↓
конец
```

Сервер может отправлять данные постепенно, не ожидая формирования всего ответа целиком.

# 🗃️ Кэширование

HTTP/1.1 поддерживает механизмы кэширования.

Например:

```python
headers = {
    "Cache-Control": "max-age=3600",
}
```

Это означает, что ответ может считаться актуальным в течение определённого времени.

Также используются:

```text
ETag
Last-Modified
If-None-Match
If-Modified-Since
```

Например, клиент может отправить:

```python
headers = {
    "If-None-Match": '"abc123"',
}
```

Если ресурс не изменился, сервер может вернуть:

```python
status_code = 304  # Not Modified
```

Тогда клиент использует сохранённую копию.

---

# 🗜️ Сжатие

HTTP/1.1 позволяет согласовать сжатие содержимого.

Например:

```python
headers = {
    "Accept-Encoding": "gzip, deflate",
}
```

Сервер может ответить:

```python
headers = {
    "Content-Encoding": "gzip",
}
```

Это уменьшает размер передаваемых данных.

---

# 🆚 HTTP/1.1 и HTTP/1.0

Главные отличия:

```text
HTTP/1.0
    ↓
новое соединение для запросов
    ↓
HTTP/1.1
    ↓
persistent connections
```

HTTP/1.1 также стандартизировал и расширил механизмы:

```text
Host
Caching
Chunked Transfer Encoding
Persistent Connections
Content Negotiation
```

---

# ⚠️ Основные недостатки HTTP/1.1

Главные проблемы:

```text
1. Последовательная обработка
        ↓
   Head-of-Line Blocking

2. Для параллельности
        ↓
   несколько TCP-соединений

3. Текстовый формат
        ↓
   больше служебных данных

4. Заголовки повторяются
        ↓
   лишний трафик
```

Эти ограничения стали одной из причин появления HTTP/2.

---

# 🔄 Как HTTP/2 решает проблемы HTTP/1.1

Упрощённо:

```text
HTTP/1.1
    ↓
несколько TCP-соединений
    ↓
параллельные запросы


HTTP/2
    ↓
одно TCP-соединение
    ↓
множество потоков
    ↓
мультиплексирование
```

HTTP/2 также переходит от текстового представления сообщений к **бинарным фреймам** и использует **HPACK** для сжатия заголовков.
