# 🔐 TLS — Transport Layer Security

## 🎤 Суперкоротко

**TLS** — криптографический протокол, который защищает данные при передаче по сети.

Он обеспечивает три основные вещи:

* 🔒 **Конфиденциальность** — данные нельзя прочитать при перехвате.
* 🛡️ **Целостность** — данные нельзя незаметно изменить.
* 🪪 **Аутентификацию** — клиент может проверить, что подключился именно к нужному серверу.

**HTTPS = HTTP + TLS.**

---

## 🎯 Ответ на собеседовании

**TLS (Transport Layer Security)** — криптографический протокол, который обеспечивает безопасную передачу данных между клиентом и сервером.

TLS защищает соединение от прослушивания, подмены и изменения данных.

При установлении соединения TLS выполняет handshake, во время которого стороны договариваются о параметрах шифрования, сервер предоставляет сертификат, а затем стороны устанавливают общие секретные ключи.

После handshake данные передаются в зашифрованном виде с использованием симметричного шифрования.

---

# 📚 От чего защищает TLS

Без TLS злоумышленник, находящийся между клиентом и сервером, потенциально может:

```text
Клиент ──────── Интернет ──────── Сервер
                 ↑
              Атакующий
```

### 1. Перехват данных

Атакующий может увидеть:

```text
login=ilya
password=123456
```

TLS превращает передаваемые данные в зашифрованный набор байтов:

```text
8f 3a 91 7c ... 
```

---

### 2. Изменение данных

Атакующий может попытаться изменить:

```text
amount=100
```

на:

```text
amount=10000
```

TLS позволяет обнаружить изменение данных.

---

### 3. Подмену сервера

Атакующий может создать сервер, который притворяется настоящим.

TLS использует **сертификаты**, чтобы клиент мог проверить подлинность сервера.

---

# 🔐 Симметричное и асимметричное шифрование

TLS использует оба подхода.

## Симметричное шифрование

Для шифрования данных используется **один общий секретный ключ**.

```text
Клиент ── [секретный ключ] ── Сервер

Данные → 🔐 → Зашифрованные данные
```

Преимущество:

**очень быстро.**

Поэтому именно симметричное шифрование используется для основной передачи данных.

Примеры:

* AES-GCM
* ChaCha20-Poly1305

---

## Асимметричное шифрование

Используется пара ключей:

```text
🔓 Public Key
🔐 Private Key
```

Публичный ключ можно распространять.

Приватный ключ должен оставаться только у владельца.

Асимметрическая криптография используется в TLS прежде всего для **аутентификации и установления общего секрета**, а не для шифрования всего большого потока данных.

---

# 🪪 Сертификат

TLS-сертификат связывает:

```text
Домен
   ↓
Публичный ключ
   ↓
Информация о владельце
   ↓
Цифровая подпись CA
```

Например:

```text
example.com
     ↓
Public Key
     ↓
Certificate
     ↓
CA Signature
```

Сертификат позволяет клиенту проверить, что публичный ключ действительно относится к нужному домену.

---

# 🏛️ Что такое CA

**CA (Certificate Authority)** — центр сертификации.

Он выпускает и подписывает сертификаты.

Пример цепочки доверия:

```text
Root CA
   ↓
Intermediate CA
   ↓
Certificate
   ↓
example.com
```

Операционная система или браузер содержит список доверенных корневых сертификатов.

Если цепочка сертификата ведёт к доверенному Root CA, сертификат может считаться доверенным.

---

# 🤝 TLS Handshake

**TLS handshake** — процесс установления защищённого соединения.

Упрощённо:

```text
Клиент                         Сервер
  │                              │
  │──── ClientHello ────────────>│
  │                              │
  │<──── ServerHello ────────────│
  │<──── Certificate ────────────│
  │<──── CertificateVerify ──────│
  │<──── Finished ───────────────│
  │                              │
  │════ Зашифрованные данные ════│
```

---

# 1️⃣ ClientHello

Клиент сообщает серверу:

* поддерживаемые версии TLS;
* доступные алгоритмы;
* `key share`;
* SNI;
* ALPN и другие параметры.

Условно:

```python
client_hello = {
    "tls_versions": ["TLS 1.3"],
    "cipher_suites": [
        "AES_128_GCM",
        "CHACHA20_POLY1305"
    ],
    "server_name": "example.com"
}
```

---

# 2️⃣ ServerHello

Сервер выбирает параметры соединения:

```text
Client:
TLS 1.3
AES-128-GCM
      ↓
Server:
TLS 1.3
AES-128-GCM
```

Также сервер отправляет свой `key share`.

---

# 3️⃣ Certificate

Сервер отправляет клиенту сертификат.

Клиент проверяет:

* кому выдан сертификат;
* соответствует ли домен;
* не истёк ли срок действия;
* кем подписан сертификат;
* можно ли построить цепочку доверия до доверенного CA.

---

# 4️⃣ CertificateVerify

Сервер доказывает, что действительно владеет **приватным ключом**, соответствующим публичному ключу из сертификата.

Это важно.

Просто украсть сертификат недостаточно.

Нужно иметь соответствующий приватный ключ.

---

# 5️⃣ Finished

Стороны подтверждают, что handshake завершён успешно и параметры соединения совпадают.

После этого начинается защищённая передача данных.

```text
Handshake
    ↓
Общие секретные ключи
    ↓
Зашифрованное соединение
    ↓
Application Data
```

---

# 🔄 Откуда берётся общий секретный ключ

В современных TLS-соединениях используется механизм обмена ключами на основе **Diffie–Hellman**, обычно его эпhemeral-вариант:

* ECDHE;
* реже DHE.

Идея:

```text
Клиент ───────────── Сервер
   │                    │
   │  обмен публичными  │
   │      данными       │
   │                    │
   └───────┬────────────┘
           ↓
    общий секрет
```

При этом сам секрет не передаётся по сети в открытом виде.

---

# 🛡️ Forward Secrecy

**Forward Secrecy** означает, что компрометация долгосрочного приватного ключа сервера в будущем не должна позволить расшифровать ранее записанный трафик.

Для этого используются временные ключи обмена.

Упрощённо:

```text
Соединение №1 → временный ключ №1
Соединение №2 → временный ключ №2
Соединение №3 → временный ключ №3
```

Компрометация долгосрочного ключа сервера не раскрывает автоматически прошлые сессии.

---

# ⚡ TLS 1.2 vs TLS 1.3

| TLS 1.2                                 | TLS 1.3                                 |
| --------------------------------------- | --------------------------------------- |
| Старее                                  | Современнее                             |
| Больше вариантов алгоритмов             | Набор алгоритмов сильно сокращён        |
| Больше этапов handshake                 | Быстрее handshake                       |
| Forward Secrecy зависит от конфигурации | Эфемерный обмен ключами является нормой |
| Более сложный протокол                  | Более простой дизайн                    |
| Широко используется                     | Предпочтительный современный вариант    |

Главное для собеседования:

**TLS 1.3 уменьшил количество этапов handshake, убрал устаревшие криптографические механизмы и сделал современную безопасную конфигурацию стандартной.**

---

# 🚀 0-RTT

TLS 1.3 может использовать **0-RTT** при возобновлении ранее установленной сессии.

Это позволяет клиенту отправить часть application data практически сразу.

```text
Обычное соединение:
Handshake → Data

0-RTT:
Data ──→
Handshake ──→
```

Но есть важный нюанс:

**0-RTT имеет риск replay-атак.**

Поэтому его нельзя бездумно использовать для операций, которые нельзя безопасно повторить.

---

# 🔒 Что происходит после handshake

После установления общего секрета используется симметричная криптография.

Например:

```text
HTTP Request
     ↓
TLS
     ↓
🔐 AES-GCM / ChaCha20-Poly1305
     ↓
TCP
```

Это значительно быстрее, чем использовать асимметричную криптографию для каждого сообщения.

---

# 🧠 Почему нельзя использовать только асимметричное шифрование?

Потому что асимметричная криптография значительно медленнее симметричной.

Поэтому TLS использует комбинацию:

```text
Асимметрическая криптография
        ↓
Аутентификация + установление секрета
        ↓
Симметричная криптография
        ↓
Основной трафик
```

Это один из важных принципов TLS.

---

# 🌐 TLS и HTTPS

TLS сам по себе не является HTTP.

TLS можно использовать для защиты разных протоколов.

```text
HTTPS = HTTP + TLS
```

Например:

```text
HTTP
 ↓
TLS
 ↓
TCP
```

становится:

```text
HTTPS
```

Стандартный HTTPS использует порт:

```text
443
```

---

# ⚠️ Что TLS НЕ скрывает

TLS защищает содержимое соединения, но не делает пользователя полностью невидимым.

Например, обычно остаются видимыми:

* IP-адреса;
* факт соединения;
* объём трафика;
* время и продолжительность соединения;
* метаданные сети.

То есть:

```text
TLS
 ↓
Защищает содержимое
```

но:

```text
TLS ≠ полная анонимность
```

# 🆚 TLS и SSL

**SSL (Secure Sockets Layer)** — предшественник TLS.

SSL 2.0 и SSL 3.0 устарели и небезопасны.

Современный термин:

**TLS.**

Поэтому фраза:

> «SSL-сертификат»

часто используется в разговорной речи, но технически современные сертификаты используются для TLS.

---

# 🔐 mTLS

**mTLS (Mutual TLS)** — взаимная аутентификация.

В обычном TLS:

```text
Клиент ── проверяет ──> Сервер
```

В mTLS:

```text
Клиент ── проверяет ──> Сервер
Клиент <─ проверяет ─── Сервер
```

То есть сертификаты используются для аутентификации **обеих сторон**.

mTLS часто применяется:

* между микросервисами;
* во внутренних API;
* в корпоративных системах;
* для service-to-service authentication.

# 🧠 Формула для запоминания

**TLS = аутентификация + обмен ключами + симметричное шифрование + защита целостности.**
