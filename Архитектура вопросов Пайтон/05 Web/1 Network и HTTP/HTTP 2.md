# 🚀 HTTP/2

## 🎤 Суперкоротко

> **HTTP/2 — версия HTTP, которая работает поверх TCP и решает многие проблемы HTTP/1.1 за счёт бинарного формата, мультиплексирования потоков, сжатия заголовков HPACK и одного TCP-соединения для множества параллельных запросов.**

---

# 🎯 Ответ на собеседовании

**HTTP/2** — это версия протокола HTTP, разработанная для повышения производительности веб-взаимодействия.

В отличие от HTTP/1.1, HTTP/2 использует **бинарное представление данных** и позволяет передавать несколько независимых потоков данных внутри одного TCP-соединения.

Главная идея:

```text
HTTP/1.1
    ↓
несколько запросов
    ↓
несколько TCP-соединений


HTTP/2
    ↓
одно TCP-соединение
    ↓
много потоков
    ↓
параллельная передача
```

---

# 🔗 HTTP/2 работает поверх TCP

HTTP/2 всё ещё использует TCP:

```text
Application
    ↓
HTTP/2
    ↓
TCP
    ↓
IP
```

Это важно помнить.

**HTTP/2 не использует UDP.**

UDP появляется уже в **HTTP/3**, где используется протокол QUIC.

---

# 🔢 Бинарный формат

Одно из главных отличий HTTP/2 — переход от текстового формата HTTP/1.1 к **бинарному framing layer**.

HTTP/1.1:

```text
GET /users HTTP/1.1
Host: example.com
Accept: application/json
```

HTTP/2 передаёт данные в виде **бинарных фреймов**.

Упрощённо:

```text
HTTP/2
   ↓
Frames
   ↓
Streams
```

Клиент и сервер работают с бинарными структурами, а не с текстовыми строками HTTP/1.1.

Преимущество:

* эффективнее обработка;
* проще разбирать сообщения на части;
* появляется возможность мультиплексирования.

---

# 🧵 Streams

**Stream** — логический независимый поток внутри HTTP/2-соединения.

Одно TCP-соединение может содержать множество потоков:

```text
TCP connection
│
├── Stream 1 → Request A
├── Stream 3 → Request B
├── Stream 5 → Request C
└── Stream 7 → Request D
```

Каждый поток имеет собственный идентификатор.

---

# 🔀 Multiplexing

Главное преимущество HTTP/2 — **мультиплексирование**.

Несколько запросов и ответов могут одновременно передаваться через **одно TCP-соединение**.

Например:

```text
TCP connection
│
├── Stream 1 ── Request 1
├── Stream 3 ── Request 2
├── Stream 5 ── Request 3
└── Stream 7 ── Request 4
```

Данные разных потоков могут чередоваться:

```text
Stream 1 → часть данных
Stream 3 → часть данных
Stream 1 → ещё данные
Stream 5 → часть данных
Stream 3 → ещё данные
```

Это называется **multiplexing**.

---

# 🆚 Multiplexing vs HTTP/1.1

В HTTP/1.1 для большого количества параллельных запросов часто использовались несколько TCP-соединений:

```text
HTTP/1.1

TCP 1 → Request 1
TCP 2 → Request 2
TCP 3 → Request 3
TCP 4 → Request 4
```

HTTP/2 позволяет:

```text
HTTP/2

TCP 1
 ├── Stream 1 → Request 1
 ├── Stream 3 → Request 2
 ├── Stream 5 → Request 3
 └── Stream 7 → Request 4
```

То есть вместо большого количества TCP-соединений можно использовать **одно соединение с множеством потоков**.

---

# 🚧 Head-of-Line Blocking

Здесь есть важный нюанс.

HTTP/2 решает **проблему блокировки запросов на уровне HTTP**, которая характерна для последовательной модели HTTP/1.1.

Но TCP гарантирует порядок доставки байтов.

Если TCP-пакет потерян:

```text
Packet 1 ✓
Packet 2 ✗
Packet 3 ✓
Packet 4 ✓
```

TCP должен дождаться повторной передачи потерянного пакета.

Поэтому данные других HTTP/2-потоков тоже могут ждать:

```text
Stream 1 ──┐
Stream 3 ──┤
            ↓
         TCP loss
            ↓
       ожидание пакета
```

Получается:

> **HTTP/2 устраняет HTTP-level HOL Blocking, но TCP-level HOL Blocking остаётся.**

Это одна из ключевых причин появления HTTP/3 и QUIC.

---

# 🗜️ HPACK

HTTP/2 использует **HPACK** для сжатия HTTP-заголовков.

В HTTP/1.1 одни и те же заголовки могут передаваться снова и снова:

```text
Host: example.com
User-Agent: ...
Accept: application/json
Authorization: ...
```

При большом количестве запросов это создаёт лишний трафик.

HTTP/2 использует HPACK:

```text
Headers
   ↓
HPACK
   ↓
compressed representation
```

HPACK использует:

* статическую таблицу;
* динамическую таблицу;
* кодирование заголовков.

В результате повторяющиеся заголовки можно передавать значительно эффективнее.

---

# 📦 Frames

HTTP/2 разбивает сообщения на **frames**.

Основные типы фреймов:

```text
DATA
HEADERS
PRIORITY
RST_STREAM
SETTINGS
PUSH_PROMISE
PING
GOAWAY
WINDOW_UPDATE
CONTINUATION
```

Например:

```text
HEADERS
   ↓
метаданные запроса

DATA
   ↓
тело запроса или ответа
```

Это позволяет HTTP/2 управлять несколькими потоками внутри одного соединения.

---

# 🎚️ Stream и Frame

Эти понятия часто путают.

**Stream** — логический поток.

**Frame** — небольшая единица передачи данных внутри потока.

Упрощённо:

```text
HTTP/2 Connection
       ↓
    Streams
       ↓
     Frames
```

Например:

```text
Stream 1
 ├── HEADERS
 ├── DATA
 └── DATA

Stream 3
 ├── HEADERS
 └── DATA
```

---

# 🎯 Stream ID

Каждый поток HTTP/2 имеет идентификатор.

Например:

```text
Stream 1
Stream 3
Stream 5
Stream 7
```

Это позволяет различать данные разных запросов внутри одного TCP-соединения.

---

# 🚀 Server Push

HTTP/2 первоначально поддерживал **Server Push**.

Идея:

> Сервер может отправить клиенту ресурс, который клиент ещё не запросил.

Например, клиент запрашивает:

```text
index.html
```

Сервер знает, что странице нужен:

```text
style.css
```

и может отправить его заранее.

```text
Client
  │
  │ GET /index.html
  ↓
Server
  │
  ├── index.html
  └── style.css
```

Однако механизм оказался сложным и малоэффективным на практике. В современных реализациях HTTP/2 Server Push обычно не используется; поддержка была удалена из современных браузеров.

---

# 🎛️ Приоритизация

HTTP/2 предусматривает механизмы приоритизации потоков.

Идея:

```text
HTML
 ↓
высокий приоритет

CSS
 ↓
высокий приоритет

Изображения
 ↓
более низкий приоритет
```

Сервер может учитывать приоритеты при передаче данных.

Это позволяет эффективнее распределять ресурсы соединения.

---

# 🌊 Flow Control

HTTP/2 имеет механизм **flow control**.

Он позволяет контролировать количество данных, которое может быть отправлено, чтобы быстрый отправитель не перегружал получателя.

Упрощённо:

```text
Sender
   ↓
данные
   ↓
Receiver
   ↓
WINDOW_UPDATE
   ↓
можно отправить ещё
```

Flow control существует на уровне потоков и всего соединения.

---

# 🔄 Connection Preface

При установлении HTTP/2-соединения стороны обмениваются специальными данными, которые помогают определить использование HTTP/2.

Для клиентского HTTP/2-соединения используется специальная последовательность:

```text
PRI * HTTP/2.0
```

После неё начинается бинарный обмен HTTP/2-фреймами.

---

# 🔐 HTTP/2 и HTTPS

HTTP/2 **может технически работать без TLS**, но в браузерах HTTP/2 практически используется через HTTPS.

Обычно:

```text
HTTPS
  ↓
TLS
  ↓
HTTP/2
  ↓
TCP
```

Поэтому в реальном вебе чаще всего встречается:

```text
https://example.com
```

с HTTP/2.

---

# 🆚 HTTP/1.1 vs HTTP/2

```text
HTTP/1.1
    ↓
текстовый формат
    ↓
последовательная модель
    ↓
несколько TCP-соединений
    ↓
повторяющиеся заголовки


HTTP/2
    ↓
бинарный формат
    ↓
мультиплексирование
    ↓
одно TCP-соединение
    ↓
HPACK
```

Главные изменения:

| HTTP/1.1                       | HTTP/2                  |
| ------------------------------ | ----------------------- |
| Текстовый формат               | Бинарные фреймы         |
| Последовательная модель        | Мультиплексирование     |
| Часто несколько TCP-соединений | Одно TCP-соединение     |
| Заголовки передаются повторно  | HPACK                   |
| HOL на HTTP-уровне             | HTTP-level HOL устранён |
| Нет streams                    | Есть streams            |

---

# 🧩 Что важно не перепутать

### HTTP/2 ≠ UDP

```text
HTTP/2 → TCP
HTTP/3 → QUIC → UDP
```

### Multiplexing ≠ несколько TCP-соединений

HTTP/2 использует:

```text
1 TCP connection
       ↓
много streams
```

### HTTP/2 не полностью устраняет HOL Blocking

Он устраняет проблему на уровне HTTP, но **TCP-level Head-of-Line Blocking остаётся**.

Именно поэтому HTTP/3 использует QUIC.

---

# 🐍 HTTP/2 в Python

На уровне приложения Python-код обычно не работает с HTTP/2-фреймами напрямую.

Например, HTTP-клиент может использовать HTTP/2:

```python
import httpx


with httpx.Client(http2=True) as client:
    response = client.get("https://example.com")

print(response.http_version)
print(response.status_code)
```

Здесь библиотека сама занимается:

```text
Python
   ↓
HTTP client
   ↓
HTTP/2
   ↓
TLS
   ↓
TCP
```

Поэтому разработчику Backend обычно важно понимать **принципы HTTP/2**, а не вручную формировать бинарные фреймы.

```text
HTTP/2
   ↓
TCP
   ↓
бинарные frames
   ↓
streams
   ↓
multiplexing
   ↓
одно TCP-соединение
```

Ключевые технологии:

```text
Multiplexing
      ↓
много потоков в одном соединении

HPACK
      ↓
сжатие заголовков

Binary Framing
      ↓
бинарные фреймы

Flow Control
      ↓
контроль передачи данных
```
