# Builder — конспект для Python Backend

## Формула для собеседования

**Builder (Строитель)** — порождающий паттерн проектирования, который позволяет пошагово создавать сложные объекты, отделяя процесс их построения от конечного представления.

**Формула:**

`Клиент → Builder → Пошаговая настройка → Готовый объект`

Главная идея: вместо одного конструктора с большим количеством аргументов объект собирается последовательно, по мере необходимости.

## Короткий ответ

Builder нужен, когда объект имеет много параметров, часть из которых необязательна, а процесс его создания включает несколько этапов.

Например, при формировании HTTP-запроса можно отдельно задать URL, заголовки, параметры, тело и тайм-аут, а затем получить готовый запрос.

Паттерн делает создание объекта более читаемым и помогает скрыть сложную логику его сборки.

## Ответ на собеседовании

Builder — это порождающий паттерн, который отделяет процесс создания сложного объекта от его представления. Он позволяет собирать объект пошагово, настраивая только необходимые параметры и скрывая детали конструирования.

В Python это может быть полезно для создания сложных конфигураций, HTTP-запросов, отчётов или объектов с большим количеством необязательных параметров. Вместо конструктора с множеством аргументов используется отдельный объект Builder с методами настройки и финальным методом `build()`.

Преимущества — читаемость, контроль процесса создания и возможность проверять объект перед завершением сборки. Недостаток — дополнительные классы и методы. Для простых объектов обычно достаточно конструктора с аргументами по умолчанию или `dataclass`.

## 1. Какую проблему решает Builder

Представим, что в Backend-приложении нужно создать сложный объект отчёта.

У него могут быть параметры:

- название;
- период;
- список колонок;
- фильтры;
- сортировка;
- формат экспорта;
- настройки пагинации.

Один из вариантов — конструктор с множеством параметров:

```python
report = Report(
    "Продажи",
    "2026-01-01",
    "2026-01-31",
    ["product", "amount"],
    {"status": "paid"},
    "amount",
    "desc",
    "xlsx",
)
```

Такой код трудно читать: не всегда понятно, что означает каждый аргумент и в каком порядке их передавать.

Можно использовать именованные аргументы, но если создание объекта включает сложную последовательность действий, проверки и зависимые настройки, одного конструктора может быть недостаточно.

Builder позволяет выразить создание объекта в виде последовательных операций.

## 2. Структура паттерна

| Элемент | Назначение |
|---|---|
| Builder | Определяет операции настройки и сборки объекта |
| Concrete Builder | Реализует конкретный процесс построения |
| Product | Объект, который создаётся |
| Director | При необходимости задаёт последовательность сборки |
| Client | Запускает создание и получает готовый объект |

**Важно:** Director — необязательный компонент. В простых реализациях клиент напрямую вызывает методы Builder и `build()`.

## 3. Реализация на Python

Рассмотрим создание HTTP-запроса.

### Шаг 1. Определяем готовый объект

```python
from dataclasses import dataclass, field


@dataclass
class HttpRequest:
    url: str
    method: str = "GET"
    headers: dict[str, str] = field(default_factory=dict)
    params: dict[str, str] = field(default_factory=dict)
    body: dict | None = None
    timeout: float = 10.0
```

`HttpRequest` — это продукт, который мы хотим получить.

### Шаг 2. Реализуем Builder

```python
class HttpRequestBuilder:
    def __init__(self, url: str):
        self._url = url
        self._method = "GET"
        self._headers = {}
        self._params = {}
        self._body = None
        self._timeout = 10.0

    def method(self, method: str):
        self._method = method
        return self

    def header(self, key: str, value: str):
        self._headers[key] = value
        return self

    def param(self, key: str, value: str):
        self._params[key] = value
        return self

    def body(self, body: dict):
        self._body = body
        return self

    def timeout(self, seconds: float):
        self._timeout = seconds
        return self

    def build(self) -> HttpRequest:
        if not self._url.startswith(("http://", "https://")):
            raise ValueError("Некорректный URL")

        if self._timeout <= 0:
            raise ValueError("Тайм-аут должен быть положительным")

        return HttpRequest(
            url=self._url,
            method=self._method,
            headers=self._headers.copy(),
            params=self._params.copy(),
            body=self._body,
            timeout=self._timeout,
        )
```

Каждый метод настраивает один аспект будущего объекта и возвращает `self`. Благодаря этому можно вызывать методы цепочкой.

Метод `build()` проверяет параметры и создаёт итоговый `HttpRequest`.

### Шаг 3. Используем Builder

```python
request = (
    HttpRequestBuilder("https://api.example.com/orders")
    .method("POST")
    .header("Authorization", "Bearer token")
    .header("Content-Type", "application/json")
    .param("source", "web")
    .body({"product_id": 42, "quantity": 2})
    .timeout(5.0)
    .build()
)

print(request.method)  # POST
print(request.timeout)  # 5.0
```

Создание читается как описание намерения: какой запрос нужен и какие настройки ему требуются.

> Это учебная реализация. В production-коде необходимо также продумать допустимые HTTP-методы, типы значений, глубокое копирование изменяемых данных и безопасную обработку секретов.

## 4. Зачем методы возвращают `self`

В примере методы Builder возвращают текущий экземпляр:

```python
def timeout(self, seconds: float):
    self._timeout = seconds
    return self
```

Это позволяет использовать цепочку вызовов:

```python
builder.method("POST").timeout(5.0).header(
    "Accept", "application/json"
)
```

Такой приём называется **method chaining** — цепочка вызовов методов.

Сам по себе method chaining не является Builder. Это лишь удобный способ организовать его интерфейс.

## 5. Нужен ли Director

Director — дополнительный объект, который определяет стандартную последовательность построения.

Например, в приложении есть типовой запрос к внутреннему API:

```python
class InternalApiRequestDirector:
    def __init__(self, builder: HttpRequestBuilder):
        self._builder = builder

    def build_health_check(self) -> HttpRequest:
        return (
            self._builder
            .method("GET")
            .header("Accept", "application/json")
            .timeout(2.0)
            .build()
        )
```

Использование:

```python
director = InternalApiRequestDirector(
    HttpRequestBuilder("https://api.example.com/health")
)

request = director.build_health_check()
```

Director полезен, когда существуют повторяющиеся сценарии сборки. Если объект всегда создаётся одним простым вызовом, отдельный Director чаще всего избыточен.

## 6. Когда Builder действительно нужен

Используй Builder, если:

- у объекта много необязательных параметров;
- создание включает несколько последовательных этапов;
- некоторые параметры зависят друг от друга;
- перед завершением сборки нужна сложная валидация;
- существуют повторяемые сценарии сборки;
- необходимо скрыть детали создания от клиентского кода.

Не используй его автоматически для каждого объекта с несколькими полями.

### Пример: когда Builder избыточен

```python
from dataclasses import dataclass


@dataclass
class User:
    username: str
    email: str
    is_active: bool = True
```

Для такого объекта достаточно `dataclass`. Создание Builder только увеличит количество кода:

```python
user = User(
    username="ilya",
    email="ilya@example.com",
)
```

## 7. Builder vs Factory Method vs Abstract Factory

Все три паттерна связаны с созданием объектов, но решают разные задачи.

| Критерий | Builder | Factory Method | Abstract Factory |
|---|---|---|---|
| Основная задача | Пошаговая сборка сложного объекта | Создание конкретного продукта через переопределяемый метод | Создание семейства связанных продуктов |
| Главный акцент | Как объект собирается | Какой конкретный продукт создаётся | Какие совместимые продукты создаются |
| Типичный интерфейс | `set_*()` и `build()` | `create_product()` | Несколько методов создания |
| Пример | Настройка сложного HTTP-запроса | Создание парсера JSON или XML | Создание набора совместимых компонентов |
| Director | Возможен, но необязателен | Не является обязательным элементом | Не является обязательным элементом |

**Коротко для собеседования:**

- Builder — собирает один сложный объект по шагам.
- Factory Method — делегирует создание продукта подклассам.
- Abstract Factory — создаёт семейства взаимосвязанных объектов.

## 8. Builder и возможности Python

В Python не всегда требуется реализовывать классический Builder.

### Именованные аргументы

```python
request = HttpRequest(
    url="https://api.example.com/orders",
    method="POST",
    timeout=5.0,
)
```

Подход подходит для объектов с понятным набором параметров и простой логикой создания.

### Dataclass

`dataclass` автоматически создаёт ряд стандартных методов класса, включая `__init__`. Это уменьшает объём шаблонного кода, но не заменяет сложный процесс сборки.

### Функция-фабрика

Если требуется вычислить параметры или выбрать реализацию, иногда достаточно функции:

```python
def create_request(url: str) -> HttpRequest:
    return HttpRequest(
        url=url,
        headers={"Accept": "application/json"},
        timeout=5.0,
    )
```

### Pydantic

В FastAPI и других Backend-приложениях Pydantic-модели удобно использовать для валидации и представления данных. Если объект можно надёжно создать из набора данных, отдельный Builder может не понадобиться.

## 9. Преимущества и недостатки

### Преимущества

- **Читаемость:** процесс сборки виден в коде.
- **Гибкость:** необязательные параметры можно задавать только при необходимости.
- **Инкапсуляция:** детали создания скрыты внутри Builder.
- **Валидация:** можно проверять состояние объекта перед завершением сборки.
- **Повторное использование:** можно описывать типовые последовательности сборки.

### Недостатки

- **Дополнительный код:** нужны отдельные методы и иногда отдельный класс.
- **Сложность поддержки:** при простых объектах Builder может усложнить архитектуру.
- **Изменяемое состояние:** ошибочное повторное использование одного Builder может привести к неожиданным результатам.
- **Не гарантирует корректность автоматически:** правила валидации необходимо реализовать самостоятельно.

## 10. Типичные ошибки

1. **Путать Builder с обычным конструктором.** Builder полезен прежде всего при нетривиальном процессе сборки.
2. **Считать цепочку методов обязательной частью паттерна.** Можно реализовать Builder и без fluent-интерфейса.
3. **Забывать о валидации.** Метод `build()` должен проверять необходимые условия, если они не обеспечиваются раньше.
4. **Повторно использовать Builder без сброса состояния.** Настройки предыдущего объекта могут случайно попасть в следующий.
5. **Создавать Director без необходимости.** Он нужен только для повторяемых сценариев сборки.
6. **Игнорировать изменяемые значения.** Списки и словари могут разделяться между объектами, если не контролировать копирование.

## 11. Вопросы для собеседования

### Какую проблему решает Builder?

Позволяет создавать сложные объекты пошагово и отделять процесс их построения от использования готового объекта.

### Обязательно ли использовать Director?

Нет. В простых сценариях клиент вызывает методы Builder напрямую.

### Что обычно делает метод `build()`?

Проверяет состояние сборки и возвращает готовый объект.

### Чем Builder отличается от Factory Method?

Builder отвечает за последовательность и процесс сборки сложного объекта, а Factory Method — за выбор конкретной реализации создаваемого продукта.

### Можно ли использовать Builder в Python без классов?

Да. Некоторые задачи можно решить функциями, конфигурационными словарями или другими средствами. Но классический паттерн Builder обычно представлен отдельным объектом со стадиями настройки.

### Какие альтернативы есть в Python?

`dataclass`, именованные аргументы, функции-фабрики, Pydantic-модели и DI-контейнеры — в зависимости от задачи.
