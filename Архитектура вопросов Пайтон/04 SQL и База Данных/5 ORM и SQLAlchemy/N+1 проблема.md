# ⚡ Проблема N+1 запросов

## 🎯 Ответ на собеседовании

**N+1 проблема** — это ситуация, когда приложение сначала выполняет **один запрос для получения списка объектов**, а затем выполняет ещё **N отдельных запросов** для получения связанных данных каждого объекта.

В результате вместо одного или нескольких эффективных запросов получается:

```python id="n7x4qp"
1 + N запросов
```

Например:

```python id="c3m8za"
SELECT * FROM users;                         # 1 запрос

SELECT * FROM orders WHERE user_id = 1;     # N
SELECT * FROM orders WHERE user_id = 2;     # N
SELECT * FROM orders WHERE user_id = 3;     # N
...
```

При 100 пользователях:

```python id="q5v9kc"
1 + 100 = 101 запрос
```

---

## 🎤 Суперкоротко

> **N+1 — это проблема избыточного количества SQL-запросов, обычно возникающая при ленивой загрузке связанных объектов в ORM. Сначала получаем N объектов одним запросом, а затем отдельным запросом загружаем связь для каждого объекта. Решение — eager loading, JOIN, `select_related`, `prefetch_related` или batch-загрузка.**

---

# 🧠 Как возникает N+1

Представим:

```python id="r4k8mx"
User
 │
 └── Orders
```

Нам нужно вывести пользователей и их заказы.

Наивная реализация:

```python id="p6c2wn"
users = get_users()

for user in users:
    orders = get_orders(user.id)
```

Сначала:

```python id="x8m3qa"
SELECT *
FROM users;
```

Потом для каждого пользователя:

```python id="v7n2kc"
SELECT *
FROM orders
WHERE user_id = 1;

SELECT *
FROM orders
WHERE user_id = 2;

SELECT *
FROM orders
WHERE user_id = 3;
```

Получаем:

```python id="z5q9mw"
1 запрос users
+
N запросов orders
=
N + 1
```

---

# 📊 Почему это плохо

Главная проблема — не обязательно объём данных.

Проблема в **количестве обращений к БД**.

Например:

```python id="m4x8vp"
100 пользователей
        ↓
101 SQL-запрос
```

А если:

```python id="k7c3na"
10 000 пользователей
        ↓
10 001 SQL-запрос
```

Количество round trips между приложением и БД резко увеличивается.

```python id="w2q6zr"
Application
    │
    ├──► DB
    ├──► DB
    ├──► DB
    ├──► DB
    ├──► ...
    └──► DB
```

Это может значительно увеличить latency и нагрузку на БД.

---

# 🔗 Решение №1 — JOIN

Вместо множества запросов можно получить данные одним SQL-запросом:

```python id="c9v4mx"
SELECT
    u.id,
    u.name,
    o.id,
    o.amount
FROM users u
LEFT JOIN orders o
    ON o.user_id = u.id;
```

Теперь вместо:

```python id="t5n8qa"
1 + N запросов
```

может быть:

```python id="j3m7kp"
1 запрос
```

Но нужно учитывать, что `JOIN` может **размножить строки** при связи `1:N`.

Например:

```python id="b8q2wc"
User 1
 ├── Order 1
 ├── Order 2
 └── Order 3
```

Результат JOIN содержит три строки для этого пользователя.

---

# 🐍 N+1 в Django ORM

Классический пример:

```python id="f6x3qm"
users = User.objects.all()

for user in users:
    print(user.orders.all())
```

Если связь загружается лениво, ORM может выполнить:

```python id="s8m4vp"
SELECT * FROM users;

SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
...
```

Получается N+1.

---

# 🚀 `select_related()`

Для связей типа:

* `ForeignKey`;
* `OneToOneField`

можно использовать:

```python id="n4q7xc"
users = User.objects.select_related("company")
```

ORM может сформировать JOIN.

Условно:

```python id="z6m2ka"
User
  │
  └── Company
```

вместо:

```python id="w8p3mr"
SELECT users;

SELECT company WHERE id = 1;
SELECT company WHERE id = 2;
SELECT company WHERE id = 3;
```

получаем один запрос с JOIN.

---

# 📦 `prefetch_related()`

Для `ManyToMany` и обратных связей `ForeignKey` обычно используется:

```python id="q7c5mx"
users = User.objects.prefetch_related("orders")
```

Django может выполнить два запроса:

```python id="a4n8vz"
SELECT *
FROM users;

SELECT *
FROM orders
WHERE user_id IN (1, 2, 3, 4, ...);
```

То есть:

```python id="r5k9cw"
1 + N
```

превращается примерно в:

```python id="m3x7qa"
2 запроса
```

---

# 🆚 `select_related()` vs `prefetch_related()`

|                     | `select_related()`         | `prefetch_related()`                    |
| ------------------- | -------------------------- | --------------------------------------- |
| Основной механизм   | JOIN                       | Отдельный запрос + объединение в Python |
| ForeignKey          | ✅                          | ✅                                       |
| OneToOne            | ✅                          | ✅                                       |
| ManyToMany          | ❌                          | ✅                                       |
| Reverse ForeignKey  | ❌                          | ✅                                       |
| Количество запросов | Обычно 1                   | Обычно 2                                |
| Когда удобно        | Одиночная связанная запись | Коллекция связанных объектов            |

Главная идея:

```python id="u6m2wp"
select_related
→ JOIN

prefetch_related
→ отдельная batch-загрузка
```

# 📦 Batch-загрузка

N+1 можно решить не только JOIN.

Вместо:

```python id="x5q8nc"
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
```

можно сделать:

```python id="v3m7ka"
SELECT *
FROM orders
WHERE user_id IN (1, 2, 3);
```

Это **batch loading**.

Схема:

```python id="q9x4mp"
100 пользователей
      ↓
получили IDs
      ↓
один batch-запрос
      ↓
все orders
```

---

# 🧩 N+1 не только про ORM

Проблема существует и без базы данных.

Например:

```python id="k4m8qa"
users = get_users()

for user in users:
    profile = api.get_profile(user.id)
```

Получаем:

```python id="z7c3xn"
1 API request
+
N API requests
```

То есть:

**N+1 — общий паттерн избыточных последовательных обращений к внешнему ресурсу.**

Это может быть:

* SQL;
* REST API;
* микросервис;
* файловая система;
* Redis;
* другой внешний сервис.

---

# 🌐 N+1 между микросервисами

Например:

```python id="p8q3mw"
Order Service
      │
      ├──► User Service → user 1
      ├──► User Service → user 2
      ├──► User Service → user 3
      └──► ...
```

Получается:

```python id="j6v9kc"
1 + N network requests
```

Это особенно плохо из-за сетевой latency.

Можно использовать:

```python id="c5x8na"
Batch API
```

Например:

```python id="r2m7qp"
GET /users?ids=1,2,3,4
```

Вместо:

```python id="w4k8cz"
GET /users/1
GET /users/2
GET /users/3
GET /users/4
```

# 🔍 Как обнаружить N+1

### 1. Посмотреть количество SQL-запросов

Например, в Django Debug Toolbar.

Условно:

```python id="n3q7mx"
Request
 ↓
101 SQL queries
```

при ожидании:

```python id="x8c4vp"
1–2 queries
```

---

### 2. Посмотреть логи

```python id="m6k2qa"
SELECT users ...
SELECT orders WHERE user_id=1
SELECT orders WHERE user_id=2
SELECT orders WHERE user_id=3
...
```

Если видим один и тот же SQL, который повторяется с разными параметрами, это подозрительно.

---

### 3. Профилирование

Измеряем:

```python id="q4m9wc"
Количество запросов
Latency
DB CPU
DB connections
Network
```

# ⚠️ Не всегда нужно превращать всё в один JOIN

Иногда решение:

```python id="v8x3mk"
N+1
 ↓
1 огромный JOIN
```

тоже может быть плохим.

Например, несколько `1:N` связей могут создать большое количество комбинаций:

```python id="z5q7pn"
User
 ├── Orders × 100
 └── Messages × 100

JOIN
 ↓
100 × 100 = 10 000 строк
```

Поэтому иногда лучше:

```python id="a9m4xc"
Query 1 → users
Query 2 → orders
Query 3 → messages
```

чем один огромный JOIN.

То есть цель:

> **Не минимальное количество SQL-запросов любой ценой, а эффективное получение необходимых данных.**

---

# 🧠 N+1 и индексы

Важно:

> **Индекс не устраняет N+1.**

Можно иметь отличный индекс:

```python id="h7q2mw"
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

но всё равно выполнять:

```python id="c8x4vp"
SELECT orders WHERE user_id = 1;
SELECT orders WHERE user_id = 2;
SELECT orders WHERE user_id = 3;
...
```

Индекс ускорит каждый запрос, но проблема **количества запросов** останется.

Нужно уменьшать количество обращений или использовать batch loading.

---

# 🆚 N+1 vs медленный SQL

Это разные проблемы.

### Медленный запрос

```python id="m2v8qa"
1 SQL query
    ↓
Seq Scan
    ↓
10 секунд
```

Проблема — стоимость одного запроса.

### N+1

```python id="x7k4mc"
1001 SQL queries
    ↓
каждый быстрый
    ↓
общий latency высокий
```

Проблема — количество запросов.

Обе проблемы могут существовать одновременно.

# 🎯 Типичный пример

### ❌ Плохо

```python id="p4m8xq"
users = User.objects.all()

for user in users:
    print(user.company.name)
```

Если `company` загружается лениво:

```python id="c7n3mv"
1 query users
+
N queries company
```

---

### ✅ Хорошо

```python id="w5q9ka"
users = User.objects.select_related("company")

for user in users:
    print(user.company.name)
```

Условно:

```python id="r8m2xc"
1 query
```

---

# 🎯 Ещё один пример

### ❌ N+1

```python id="j6x4vp"
users = User.objects.all()

for user in users:
    orders = Order.objects.filter(user_id=user.id)
```

### ✅ Batch

```python id="q3m8za"
user_ids = [user.id for user in users]

orders = Order.objects.filter(
    user_id__in=user_ids
)
```

Получаем:

```python id="v7k2cw"
1 query users
+
1 query orders
=
2 queries
```

# 🎤 Формулировка для собеседования

> **N+1 проблема возникает, когда приложение сначала получает N объектов одним запросом, а затем для каждого объекта отдельно запрашивает связанные данные. В результате вместо одного или нескольких эффективных запросов выполняется N+1 запросов. Классический пример — ленивые связи в ORM. В Django для решения используют `select_related()` для ForeignKey и OneToOne, `prefetch_related()` для коллекций и обратных связей, а также batch-запросы или JOIN. При этом не нужно стремиться к одному SQL-запросу любой ценой — важно минимизировать общую стоимость получения данных.**
