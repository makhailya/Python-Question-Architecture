# ⏱️ TTL — Time To Live

## 🎯 Ответ на собеседовании

**TTL (Time To Live)** — это время жизни объекта, данных или записи, после которого они считаются устаревшими и должны быть удалены или перестать использоваться.

В backend-разработке TTL часто применяется к:

* кэшу;
* сессиям;
* токенам;
* временным данным;
* DNS-записям;
* ключам в Redis.

Например, если установить TTL ключа Redis в 60 секунд:

```python
redis.set("session:123", "user_data", ex=60)
```

то через 60 секунд ключ автоматически истечёт.

---

## 🎤 Суперкоротко

**TTL = сколько времени объект должен жить.**

```text
Создали объект
     ↓
TTL = 60 секунд
     ↓
60 секунд
     ↓
Объект истёк
```

---

# 🧠 Зачем нужен TTL

TTL позволяет автоматически удалять временные данные.

Без TTL пришлось бы самостоятельно следить за их удалением:

```text
Создали данные
     ↓
Храним
     ↓
Проверяем срок
     ↓
Удаляем
```

С TTL:

```text
Создали данные
     ↓
Установили TTL
     ↓
Время истекло
     ↓
Данные автоматически становятся недействительными
```

---

# ⚡ TTL в Redis

Redis часто используется как in-memory хранилище и кэш.

Можно установить TTL:

```python
redis.set(
    "user:123",
    "Ilya",
    ex=60
)
```

Здесь:

```text
ex=60
```

означает:

**ключ будет жить 60 секунд.**

Проверить оставшееся время можно через `TTL`:

```python
seconds = redis.ttl("user:123")
```

Например:

```text
60
```

означает, что осталось около 60 секунд.

---

# 🗑️ Что происходит после истечения TTL

Упрощённо:

```text
Key
 ↓
TTL = 60
 ↓
59
58
57
...
1
0
 ↓
Expired
```

После истечения срока ключ считается **expired**.

Redis удаляет истёкшие ключи с использованием механизмов expiration, поэтому не стоит воспринимать это как буквальное действие ровно в ту же миллисекунду, когда счётчик достиг нуля.

---

# 🗄️ TTL и кэш

Очень распространённый сценарий:

```text
Запрос
  ↓
Проверяем Cache
  ↓
Есть данные?
 ↙       ↘
Да       Нет
 ↓         ↓
Вернуть   База данных
           ↓
         Cache
           ↓
         TTL
```

Например:

```python
redis.set(
    "product:123",
    product_data,
    ex=300
)
```

Данные кэшируются на:

```text
300 секунд = 5 минут
```

После этого кэш устаревает, и приложение может снова получить данные из базы.

---

# 🎟️ TTL и JWT

TTL напрямую не является частью JWT как отдельного механизма.

Но JWT обычно содержит claim:

```python
payload = {
    "sub": "123",
    "exp": 1790000000
}
```

`exp` задаёт **момент истечения токена**.

Логика похожа на TTL:

```text
JWT создан
    ↓
exp = время окончания
    ↓
Время наступило
    ↓
JWT считается недействительным
```

Например:

```text
Access Token
TTL ≈ 15 минут
```

После истечения токен нельзя использовать для доступа к API.

---

# 🍪 TTL и Session

Сессии тоже могут иметь время жизни.

Например:

```text
Session
   ↓
TTL = 30 минут
   ↓
Нет активности / срок истёк
   ↓
Session expired
```

Это позволяет автоматически инвалидировать старые сессии.

---

# 🌐 TTL и DNS

В DNS TTL означает, **сколько времени DNS-запись может храниться в кэше**.

Например:

```text
example.com
    ↓
IP: 1.2.3.4
TTL: 3600
```

DNS-клиент или DNS-сервер может кэшировать результат примерно на:

```text
3600 секунд = 1 час
```

После истечения TTL запись нужно получать заново.

---

# ⚠️ TTL ≠ срок хранения в базе

TTL не является универсальным механизмом удаления данных из любой базы.

Он означает:

> «После определённого времени данные больше не должны считаться действительными».

Конкретное поведение зависит от системы.

Например:

```text
Redis → expiration ключей
DNS   → время кэширования
JWT   → exp
Cache → время актуальности
```

---

# 🆚 TTL и Expiration Date

Они связаны, но формулировка разная.

### TTL

Относительный срок:

```text
Жить 300 секунд
```

### Expiration timestamp

Абсолютный момент:

```text
Истечь в 12:30:00
```

Например:

```text
Создано: 12:25:00
TTL: 300 секунд
        ↓
Истекает: 12:30:00
```

# 🧩 TTL в архитектуре приложения

TTL часто используется для управления временными данными:

```text
┌──────────────────────┐
│      Application     │
└──────────┬───────────┘
           ↓
      Redis / Cache
           ↓
       TTL = 300
           ↓
      Data expires
```

Типичные случаи:

```text
Cache
Session
OTP
Temporary tokens
Rate limiting
DNS cache
Temporary locks
```

# 🎯 Что важно запомнить

**TTL — это время жизни данных или объекта до его истечения.**

Примеры:

```text
Redis key → TTL
Cache     → TTL
DNS record → TTL
Session   → TTL
JWT       → exp / срок действия
```

Главная идея:

```text
Создание
   ↓
TTL
   ↓
Время проходит
   ↓
Expiration
   ↓
Данные больше не используются
```

---

# 🧠 Формула для запоминания

**TTL = «Сколько ещё это должно жить?»**

```text
TTL = 60 секунд

60 → 59 → 58 → ... → 0
                    ↓
                 expired
```
