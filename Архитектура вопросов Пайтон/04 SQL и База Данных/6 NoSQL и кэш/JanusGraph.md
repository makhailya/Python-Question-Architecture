# JanusGraph — конспект для Python Backend

## Формула для собеседования

**JanusGraph** — распределённая графовая база данных, предназначенная для хранения и обхода больших графов. Она использует отдельные системы хранения данных и индексации, например Apache Cassandra, HBase, Berkeley DB и Elasticsearch или Solr, в зависимости от конфигурации.

**Ключевая формула:**

`JanusGraph = Graph Model + Storage Backend + Index Backend + Gremlin`

## Краткий ответ

- **Тип:** распределённая графовая база данных с открытым исходным кодом.
- **Модель данных:** Property Graph.
- **Язык обхода графа:** Gremlin — язык семейства Apache TinkerPop.
- **Хранение данных:** подключаемый backend, например Cassandra или HBase.
- **Индексация:** подключаемый индексный backend, например Elasticsearch или Solr.
- **Масштабирование:** зависит от выбранных хранилищ, индексации и архитектуры развёртывания.
- **Python:** доступ через Gremlin-Python и Gremlin Server.
- **Основные сценарии:** графы знаний, социальные сети, анализ зависимостей, рекомендации, fraud detection.

## Ответ на собеседовании

JanusGraph — это графовая база данных, которая предназначена для работы с большими графами и распределённым хранением. В отличие от Neo4j, JanusGraph обычно не предоставляет собственное единое хранилище всех данных: она использует внешнюю систему хранения и, при необходимости, отдельный поисковый backend для индексации.

Для обхода графа применяется Gremlin — язык Apache TinkerPop. Python-приложение может отправлять запросы через Gremlin-Python на Gremlin Server, который выполняет обход графа с использованием JanusGraph.

Главное преимущество JanusGraph — возможность строить распределённые графовые системы на базе подходящих инфраструктурных компонентов. Обратная сторона — более сложная эксплуатация: необходимо отдельно настраивать хранение, индексы, серверы обхода графа, отказоустойчивость и согласованность данных.

## 1. Архитектура JanusGraph

JanusGraph отделяет графовую модель и операции обхода от физического хранения данных.

### Основные компоненты

| Компонент | Назначение |
|---|---|
| **JanusGraph** | Графовая модель, управление схемой и выполнение операций над графом |
| **Storage Backend** | Постоянное хранение вершин, рёбер и свойств |
| **Index Backend** | Поиск по свойствам и выполнение индексируемых запросов |
| **Apache TinkerPop** | Экосистема графовых API и языка Gremlin |
| **Gremlin Server** | Принимает удалённые запросы Gremlin и выполняет их |
| **Gremlin-Python** | Python-клиент для подключения к Gremlin Server |

Пример архитектуры:

```text
Python Backend
      |
      v
Gremlin-Python
      |
      v
Gremlin Server
      |
      v
JanusGraph
   /       \
  v         v
Storage    Index Backend
Backend    (Elasticsearch /
(Cassandra, Solr)
 HBase, ...)
```

Gremlin Server и JanusGraph могут развёртываться совместно или в соответствии с выбранной архитектурой. Конкретная схема зависит от версии и конфигурации.

### Почему хранение отделено от графовой модели

Это позволяет выбирать инфраструктуру под нагрузку:

- распределённое хранилище для большого объёма графовых данных;
- индексный backend для поиска по свойствам;
- отдельные вычислительные ресурсы для выполнения обходов графа.

Однако подключение внешних backend не делает любой запрос автоматически распределённым или быстрым. Эффективность зависит от структуры графа, индексов, числа переходов и сетевых затрат.

## 2. Модель данных Property Graph

Как и Neo4j, JanusGraph использует графовую модель, состоящую из вершин, рёбер и свойств.

| Элемент | Описание | Пример |
|---|---|---|
| **Vertex** | Вершина, представляющая сущность | Пользователь |
| **Edge** | Ребро между вершинами | Подписка |
| **Property** | Свойство вершины или ребра | `name`, `created_at` |
| **Label** | Тип вершины или ребра | `User`, `FOLLOWS` |
| **Schema** | Правила типов и свойств графа | Тип `email` |

Пример:

```text
(User: Илья)
    |
    | FOLLOWS
    v
(User: Анна)
    |
    | PURCHASED
    v
(Product: Клавиатура)
```

### Важная особенность схемы

JanusGraph поддерживает схему, которая определяет типы вершин и рёбер, ключи свойств и их характеристики.

Схема может быть гибкой, но для production-систем важно осознанно проектировать:
- типы вершин и рёбер;
- типы свойств;
- кардинальность свойств;
- индексы;
- правила уникальности.

Это помогает избежать неоднозначной модели данных и улучшает предсказуемость запросов.

## 3. Gremlin — язык обхода графа

**Gremlin** — язык обхода графа, входящий в Apache TinkerPop. Он позволяет находить вершины и рёбра, переходить между связанными элементами, фильтровать результаты и выполнять изменения.

### Основные операции

| Операция | Назначение |
|---|---|
| `V()` | Начать обход с вершин |
| `E()` | Начать обход с рёбер |
| `addV()` | Создать вершину |
| `addE()` | Создать ребро |
| `has()` | Отфильтровать элементы по свойству |
| `out()` | Перейти по исходящим рёбрам |
| `in()` | Перейти по входящим рёбрам |
| `both()` | Перейти по рёбрам в обоих направлениях |
| `values()` | Получить значения свойств |
| `hasLabel()` | Фильтрация по метке |
| `limit()` | Ограничить количество результатов |
| `count()` | Подсчитать результаты |

### Поиск вершины

```groovy
g.V().has('User', 'user_id', 'u-101')
```

Находит вершину с меткой `User` и свойством `user_id = 'u-101'`.

### Создание вершины

```groovy
g.addV('User').
  property('user_id', 'u-101').
  property('name', 'Илья')
```

### Создание связи

```groovy
g.V().has('User', 'user_id', 'u-101').
  addE('FOLLOWS').
  to(g.V().has('User', 'user_id', 'u-102'))
```

Этот пример показывает создание ребра `FOLLOWS` от одного пользователя к другому. Для production следует учитывать, что при отсутствии целевой вершины операция может не создать ожидаемое ребро.

### Поиск подписок пользователя

```groovy
g.V().has('User', 'user_id', 'u-101').
  out('FOLLOWS').
  values('name')
```

### Поиск друзей друзей

```groovy
g.V().has('User', 'user_id', 'u-101').
  out('FOLLOWS').
  out('FOLLOWS').
  dedup().
  values('name')
```

`dedup()` удаляет повторяющиеся значения на текущем этапе обхода.

## 4. Storage Backend

JanusGraph делегирует постоянное хранение графовых данных выбранной системе хранения.

Возможные варианты зависят от версии и конфигурации JanusGraph.

| Backend | Назначение |
|---|---|
| **Apache Cassandra** | Распределённое хранение с горизонтальным масштабированием |
| **Apache HBase** | Распределённое хранение поверх HDFS |
| **Berkeley DB** | Встраиваемое хранилище для определённых сценариев |
| **ScyllaDB** | Совместимость и поддержка зависят от версии и конфигурации; необходимо проверять конкретный стек |

### Почему нельзя выбрать backend только по названию

Производительность графового приложения зависит не только от скорости записи. Необходимо учитывать:
- шаблоны обхода графа;
- количество рёбер у одной вершины;
- объём данных;
- конкурентную нагрузку;
- требования к доступности;
- согласованность операций;
- поддержку конкретного backend выбранной версией JanusGraph.

**Важно:** не следует считать, что все системы хранения одинаково поддерживаются любой версией JanusGraph. Совместимость необходимо проверять по документации конкретного релиза.

## 5. Index Backend

Индексный backend используется для эффективного поиска по свойствам графа.

Например, приложению нужно найти пользователя по email, а затем пройти по его связям.

Без подходящего индекса поиск начальной вершины может потребовать просмотра большого количества данных.

### Пример логики

```text
Найти User по email
        |
        v
Получить вершину
        |
        v
Обойти FOLLOWS
        |
        v
Вернуть связанных пользователей
```

### Типы индексов

**Composite Index**

Подходит для поиска по определённым комбинациям ключей свойств и меток. Может поддерживать эффективный поиск по точным значениям, а при соответствующей конфигурации — ограничения уникальности.

**Mixed Index**

Использует внешний индексный backend, например Elasticsearch или Solr, и может поддерживать более разнообразные поисковые операции в пределах возможностей backend.

### Что важно помнить

- Индекс нужно правильно создать и настроить.
- Поддержка операций зависит от типа индекса и backend.
- Индексы требуют ресурсов и дополнительного обслуживания.
- При изменениях данных могут возникать вопросы согласованности между графовым хранилищем и внешним индексом.
- Индекс не гарантирует ускорения любого обхода графа.

## 6. Транзакции и согласованность

JanusGraph предоставляет транзакционную модель работы с графом, но реальные гарантии зависят от используемого storage backend и настроек.

Важные аспекты:
- операции чтения и записи выполняются в контексте транзакций;
- изменения необходимо корректно фиксировать;
- конкурентные изменения требуют продуманной обработки конфликтов;
- уникальность свойств следует обеспечивать поддерживаемыми ограничениями и индексами;
- согласованность внешнего поискового индекса может отличаться от согласованности основного хранилища.

Нельзя автоматически переносить гарантии одной базы данных на всю систему JanusGraph: поведение определяется совокупностью графового движка и подключённых компонентов.

## 7. Использование JanusGraph из Python

Один из распространённых способов — библиотека `gremlinpython`, которая подключается к Gremlin Server.

Документация:
- JanusGraph: https://docs.janusgraph.org/
- Apache TinkerPop: https://tinkerpop.apache.org/docs/current/reference/
- Gremlin-Python: https://tinkerpop.apache.org/docs/current/reference/#gremlin-python

### Установка

```bash
pip install gremlinpython
```

Версию `gremlinpython` следует подбирать с учётом версии Apache TinkerPop, используемой сервером.

### Подключение и запрос

```python
from gremlin_python.driver import client
from gremlin_python.driver.serializer import (
    GraphSONSerializersV3d0,
)

gremlin_client = client.Client(
    "ws://localhost:8182/gremlin",
    "g",
    message_serializer=GraphSONSerializersV3d0(),
)

try:
    result = gremlin_client.submit(
        "g.V().has('User', 'user_id', user_id)."
        "values('name')",
        bindings={"user_id": "u-101"},
    )

    print(result.all().result())
finally:
    gremlin_client.close()
```

Пример использует WebSocket-подключение к Gremlin Server на локальном адресе. Сервер должен быть запущен и настроен на работу с JanusGraph.

### Что здесь важно

- `client.Client()` создаёт клиент для удалённых запросов.
- `submit()` отправляет Gremlin-обход.
- `bindings` передаёт значения отдельно от текста запроса.
- `result.all().result()` получает результаты асинхронно предоставляемого драйвером механизма.
- `close()` освобождает ресурсы клиента.

### Практические рекомендации

1. Не собирайте запросы конкатенацией пользовательского ввода.
2. Используйте bindings для значений.
3. Настраивайте таймауты, аутентификацию и TLS для production.
4. Проверяйте поведение при сетевых сбоях и повторных запросах.
5. Не создавайте новый клиент для каждого запроса без необходимости.
6. Проверяйте совместимость версий Python-клиента, TinkerPop и серверной конфигурации.

## 8. JanusGraph vs Neo4j vs PostgreSQL

| Критерий | JanusGraph | Neo4j | PostgreSQL |
|---|---|---|---|
| Модель | Графовая | Графовая | Реляционная |
| Язык запросов | Gremlin | Cypher | SQL |
| Основное хранение | Подключаемый backend | Собственная графовая платформа | Собственное реляционное хранилище |
| Индексация | Подключаемый backend | Встроенные механизмы и поддерживаемые интеграции | Встроенные индексы |
| Распределённая архитектура | Строится вокруг выбранных компонентов | Зависит от редакции и конфигурации | Обычно отдельные решения для масштабирования |
| Эксплуатация | Относительно сложная, несколько компонентов | Обычно проще как единая платформа | Хорошо подходит для большинства бизнес-сервисов |
| Графовые обходы | Основной сценарий | Основной сценарий | Возможны, но не являются основной специализацией |
| Python | Gremlin-Python | Официальный драйвер `neo4j` | `psycopg` и другие драйверы |

### Когда выбирать JanusGraph

- Требуется большой распределённый граф.
- Нужно использовать поддерживаемые внешние хранилища.
- Архитектура требует гибкости в выборе инфраструктурных компонентов.
- Команда готова обслуживать несколько взаимосвязанных систем.

### Когда выбирать Neo4j

- Нужна графовая база с интегрированной платформой.
- Предпочтительнее единый продукт вместо самостоятельной сборки нескольких backend.
- Требуется использовать Cypher и экосистему Neo4j.

### Когда выбирать PostgreSQL

- Преобладают CRUD-операции, SQL-запросы и бизнес-транзакции.
- Основные связи хорошо выражаются внешними ключами и JOIN.
- Графовые обходы не являются центральным требованием приложения.

## 9. Производительность и типичные проблемы

### Высокая степень связности

Вершины с огромным количеством рёбер могут становиться дорогими для обхода.

**Что делать:** ограничивать глубину обхода, фильтровать данные как можно раньше и не возвращать лишние вершины.

### Отсутствие подходящих индексов

Поиск начальной вершины может стать узким местом.

**Что делать:** анализировать типичные запросы и создавать соответствующие индексы.

### Слишком глубокие обходы

Обход большого количества уровней может приводить к взрывному росту числа посещаемых вершин и рёбер.

**Что делать:** задавать ограничения глубины и объёма результатов, проверять план выполнения и измерять нагрузку.

### Проблемы внешнего backend

Задержки storage или index backend напрямую влияют на приложение.

**Что делать:** мониторить каждый компонент отдельно, настраивать таймауты и планировать восстановление после сбоев.

### Сложность эксплуатации

В дополнение к JanusGraph могут требоваться отдельные кластеры хранения, поиска и Gremlin Server.

**Что делать:** автоматизировать развёртывание, мониторинг, резервное копирование и обновления, а также документировать совместимость версий.

## 10. Частые вопросы на собеседовании

### Что такое JanusGraph?

Распределённая графовая база данных, предназначенная для хранения и обхода больших графов с использованием подключаемых систем хранения и индексации.

### Чем JanusGraph отличается от Neo4j?

JanusGraph отделяет графовую модель от storage backend и index backend. Neo4j предоставляет интегрированную графовую платформу с собственными механизмами хранения и языком Cypher.

### Что такое Apache TinkerPop?

Это экосистема для работы с графами, включающая Gremlin — язык обхода графа, а также API и серверные компоненты.

### Что такое Gremlin?

Язык обхода графа, позволяющий искать вершины, переходить по рёбрам, фильтровать результаты и изменять граф.

### Зачем JanusGraph нужен Storage Backend?

Для постоянного хранения графовых данных. В зависимости от конфигурации используются внешние системы, например Cassandra или HBase.

### Зачем нужен Index Backend?

Для поиска по свойствам и выполнения операций, которые требуют индексирования и неэффективны при полном просмотре графа.

### Чем Composite Index отличается от Mixed Index?

Composite Index предназначен для определённых комбинаций свойств и меток, часто для точного поиска и уникальности. Mixed Index делегирует более широкий набор поисковых операций внешнему индексному движку. Конкретные возможности зависят от backend и конфигурации.

### Можно ли использовать JanusGraph из Python?

Да. Один из распространённых вариантов — Gremlin-Python, который отправляет запросы на Gremlin Server.

### Подходит ли JanusGraph для микросервисов?

Да, если микросервис работает с крупным графом и сложными связями. Но необходимо учитывать операционную сложность внешних хранилищ, индексов и серверов обхода.

### Всегда ли JanusGraph лучше Neo4j для больших графов?

Нет. JanusGraph предоставляет гибкость выбора backend, но это не гарантирует лучшую производительность. Выбор следует делать по нагрузочным тестам, требованиям к согласованности, доступности и стоимости эксплуатации.
