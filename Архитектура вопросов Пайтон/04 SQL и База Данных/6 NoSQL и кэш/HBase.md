# HBase — конспект для Python Backend

## Формула для собеседования

**HBase** — распределённая NoSQL-база данных с широкими столбцами (wide-column database), построенная поверх HDFS и предназначенная для хранения огромных объёмов разреженных данных с доступом по ключу. HBase обеспечивает горизонтальное масштабирование и случайное чтение и запись на больших наборах данных.

**Ключевая формула:**

`HBase = HDFS + распределённое хранение + случайный доступ по Row Key`

## Краткий ответ

- **Тип:** распределённая wide-column NoSQL DB.
- **Основа хранения:** HDFS.
- **Модель данных:** таблицы, строки, семейства столбцов и версии ячеек.
- **Основной ключ доступа:** `Row Key`.
- **Масштабирование:** горизонтальное, за счёт распределения регионов между RegionServer.
- **Язык запросов:** собственного полноценного SQL-интерфейса по умолчанию нет; используются Java API, shell и клиентские библиотеки.
- **Python:** доступ через клиентские библиотеки и совместимые API, например HappyBase через Thrift.
- **Основные сценарии:** большие разреженные таблицы, временные ряды, логи, телеметрия и хранение событий.

## Ответ на собеседовании

HBase — распределённая NoSQL-база данных, основанная на модели Google Bigtable. Она работает поверх HDFS и предназначена для хранения очень больших таблиц, в которых данные распределены между множеством серверов.

В отличие от PostgreSQL, HBase не ориентирована на сложные SQL-запросы и JOIN. Основной способ доступа к данным — чтение и запись по `Row Key`, а также сканирование диапазонов ключей.

Таблица разделяется на регионы (`Regions`), которые обслуживаются процессами `RegionServer`. При росте объёма данных регионы могут разделяться и распределяться между серверами, обеспечивая горизонтальное масштабирование.

HBase подходит, когда нужно хранить огромные объёмы данных и быстро получать записи по ключу. Для транзакционной бизнес-логики с большим количеством связей, JOIN и сложных аналитических запросов обычно выбирают другие инструменты.

## 1. Архитектура HBase

### Основные компоненты

| Компонент | Назначение |
|---|---|
| **HMaster** | Координирует управление таблицами, назначение регионов и балансировку |
| **RegionServer** | Обслуживает чтение и запись данных в назначенных ему регионах |
| **Region** | Горизонтальный диапазон строк таблицы, определяемый диапазоном Row Key |
| **ZooKeeper** | В традиционных развёртываниях участвует в координации и обнаружении сервисов |
| **HDFS** | Распределённая файловая система для хранения файлов данных и журналов |
| **WAL** | Write-Ahead Log — журнал изменений для восстановления данных после сбоев |
| **MemStore** | Буфер изменений в памяти перед записью в постоянные файлы |
| **HFile** | Формат файлов, в которых хранятся данные на HDFS |
| **BlockCache** | Кэш блоков для ускорения чтения |

Конкретные детали взаимодействия компонентов зависят от версии HBase и конфигурации кластера.

### Как организовано хранение

```text
HBase Cluster
├── HMaster
├── RegionServer 1
│   ├── Region A
│   └── Region B
├── RegionServer 2
│   ├── Region C
│   └── Region D
└── HDFS
    ├── HFiles
    └── WAL files
```

Одна таблица может состоять из множества регионов. Каждый регион отвечает за определённый диапазон `Row Key`.

Когда регион становится слишком большим, HBase может разделить его на два региона. Это называется **Region Split**.

### Как проходит запись

Упрощённая последовательность:

1. Клиент определяет регион, обслуживающий нужный `Row Key`.
2. Запрос направляется на соответствующий `RegionServer`.
3. Изменение записывается в WAL.
4. Данные добавляются в MemStore.
5. Позже накопленные данные сбрасываются на HDFS в виде HFiles.
6. Compaction объединяет файлы для повышения эффективности хранения и чтения.

WAL помогает восстановить изменения после сбоя до их сброса в постоянные файлы.

### Как проходит чтение

1. Клиент определяет нужный регион.
2. RegionServer ищет данные в BlockCache и MemStore.
3. Если данных там нет, выполняется чтение соответствующих HFiles.
4. Результат возвращается клиенту.

На практике поиск может затрагивать несколько источников данных одновременно.

## 2. Модель данных

HBase использует модель, в которой каждая строка имеет уникальный ключ, а данные организованы по семействам столбцов.

Основные понятия:

| Понятие | Значение |
|---|---|
| **Table** | Таблица |
| **Row Key** | Уникальный ключ строки |
| **Column Family** | Семейство столбцов, заданное на уровне схемы таблицы |
| **Column Qualifier** | Имя конкретного столбца внутри семейства |
| **Cell** | Ячейка, определяемая строкой, семейством, qualifier и версией |
| **Timestamp / Version** | Временная метка или версия значения |

Пример:

```text
Table: users

Row Key: user:1001
├── profile:name       = "Илья"
├── profile:city       = "Екатеринбург"
└── activity:last_seen = "2026-10-21"
```

Здесь `profile` и `activity` — Column Families, а `name`, `city` и `last_seen` — Column Qualifiers.

### Чем HBase отличается от реляционной таблицы

В PostgreSQL обычно задают структуру таблицы с конкретными колонками и типами данных.

В HBase семейства столбцов определяются схемой таблицы, но отдельные qualifiers могут различаться от строки к строке. Поэтому модель хорошо подходит для разреженных и неоднородных данных.

Например, одна строка может содержать `profile:email`, а другая — нет. Отсутствующие ячейки не требуют хранения `NULL` для каждого возможного столбца.

### Версии ячеек

HBase может хранить несколько версий значения ячейки, различающихся временными метками.

Это полезно для:
- истории изменений;
- временных данных;
- аудита;
- восстановления предыдущих значений в пределах сохранённой истории.

Количество хранимых версий и правила удаления старых версий зависят от настроек семейства столбцов.

## 3. Row Key и проектирование ключей

**Row Key — один из важнейших элементов проектирования HBase.** От него зависит, где окажутся данные и насколько равномерно нагрузка распределится между регионами.

### Хороший Row Key

Ключ должен учитывать:
- основные сценарии чтения;
- необходимость получать диапазоны записей;
- равномерное распределение нагрузки;
- вероятность возникновения горячих регионов.

Пример ключа для событий пользователя:

```text
user_id#timestamp
```

Такой ключ позволяет группировать данные пользователя и получать его события по диапазону ключей при подходящем формате timestamp.

Однако если ключи растут последовательно, например только по времени, новые записи могут концентрироваться в одном диапазоне ключей. Это создаёт риск **hotspotting**.

### Что такое hotspotting

Hotspotting — ситуация, когда непропорционально большая часть запросов или записей направляется в небольшой набор регионов.

Возможные последствия:
- перегрузка отдельных RegionServer;
- неравномерное использование ресурсов;
- увеличение задержек;
- снижение общей пропускной способности кластера.

### Как уменьшить hotspotting

- Добавлять распределяющий префикс или salt к Row Key.
- Проектировать ключи под реальные запросы.
- Предварительно создавать регионы при известном распределении ключей.
- Избегать монотонно возрастающих ключей без дополнительного распределения нагрузки.

**Компромисс:** случайное распределение может улучшить баланс записи, но усложнить чтение диапазона данных конкретного пользователя или временного интервала.

## 4. Основные операции

Для демонстрации используется HBase Shell.

### Создание таблицы

```ruby
create 'users', 'profile', 'activity'
```

Создаётся таблица `users` с двумя семействами столбцов.

### Запись значения

```ruby
put 'users', 'user:1001', 'profile:name', 'Илья'
put 'users', 'user:1001', 'profile:city', 'Екатеринбург'
```

Общий формат:

```text
put <table>, <row_key>, <family:qualifier>, <value>
```

### Чтение строки

```ruby
get 'users', 'user:1001'
```

Получение конкретной ячейки:

```ruby
get 'users', 'user:1001', 'profile:name'
```

### Сканирование таблицы

```ruby
scan 'users'
```

Сканирование диапазона строк:

```ruby
scan 'users', {
  STARTROW => 'user:1000',
  STOPROW => 'user:2000'
}
```

Границы и параметры сканирования нужно выбирать с учётом порядка сортировки ключей.

### Удаление значения

```ruby
delete 'users', 'user:1001', 'profile:name'
```

В HBase удаление обычно реализуется через tombstone — маркер удаления. Физическое удаление данных происходит позднее в процессе compaction.

## 5. Консистентность и транзакции

HBase обеспечивает сильную согласованность чтения и записи для отдельной строки в рамках стандартной модели доступа. Но это **не означает наличие полноценных ACID-транзакций между произвольными строками**.

### Что важно понимать

- Операции над отдельной строкой имеют атомарные свойства в рамках поддерживаемых API.
- Нельзя автоматически считать последовательность изменений нескольких строк одной атомарной транзакцией.
- Репликация и восстановление после сбоев зависят от конфигурации кластера.
- Для бизнес-операций, затрагивающих несколько записей, может потребоваться дополнительная логика согласованности.

### HBase и CAP

В распределённой системе нельзя рассматривать CAP как простую универсальную метку «CP» или «AP» без уточнения конкретной операции и поведения при сетевом разделении.

На собеседовании лучше объяснить, какие гарантии HBase предоставляет на уровне строки, и отдельно обозначить ограничения межстрочных транзакций.

## 6. HBase vs PostgreSQL vs Cassandra

| Критерий | HBase | PostgreSQL | Apache Cassandra |
|---|---|---|---|
| Тип | Wide-column NoSQL | Реляционная СУБД | Wide-column NoSQL |
| Основной доступ | Row Key | SQL, индексы | Partition Key |
| Хранение | HDFS / HFiles | Страницы данных и индексы | SSTables и commit log |
| Масштабирование | Горизонтальное | Обычно вертикальное, возможно горизонтальное с дополнительными решениями | Горизонтальное |
| SQL | Нет полноценного SQL по умолчанию | Да | CQL, ограниченная SQL-подобная модель |
| JOIN | Не является основным сценарием | Да | Не является основным сценарием |
| Транзакции | Ограничены относительно реляционных БД | Полноценные ACID-транзакции | Гарантии зависят от операции и конфигурации |
| Типичный сценарий | Очень большие таблицы и доступ по ключу | Транзакционные приложения и связи | Распределённые приложения с высокой доступностью и записью |

### Когда выбирать HBase

Подходит, если:
- данные измеряются терабайтами или петабайтами;
- нужна распределённая таблица с доступом по ключу;
- важна интеграция с экосистемой Hadoop;
- требуются сканирования диапазонов ключей;
- данные естественно укладываются в wide-column модель.

Не лучший выбор, если приложению нужны сложные JOIN, гибкая аналитика через SQL и транзакции над множеством связанных сущностей.

## 7. Использование HBase из Python

В Python нет одного универсального официального клиента, который был бы стандартом для всех вариантов развёртывания HBase. Выбор зависит от версии HBase и доступных интерфейсов.

### HappyBase

[HappyBase](https://happybase.readthedocs.io/) — Python-библиотека для работы с HBase через Thrift API. Для неё сервер HBase должен быть настроен на предоставление совместимого Thrift-интерфейса.

Установка:

```bash
pip install happybase
```

Пример подключения:

```python
import happybase

connection = happybase.Connection(
    host="localhost",
    port=9090,
)

table = connection.table("users")

table.put(
    b"user:1001",
    {
        b"profile:name": b"Ilya",
        b"profile:city": b"Yekaterinburg",
    },
)

row = table.row(b"user:1001")
print(row)

connection.close()
```

В этом примере используются байты (`bytes`) для ключей, имён столбцов и значений.

### Что учитывать в реальном проекте

- Настроить таймауты и обработку ошибок подключения.
- Закрывать соединения корректно.
- Не создавать новое соединение без необходимости для каждой операции.
- Учитывать ограничения Thrift API и совместимость версии клиента с сервером.
- Для production проверять аутентификацию, TLS и настройки доступа.
- Не хранить секреты подключения в исходном коде.

## 8. Производительность и эксплуатация

### Основные механизмы

**MemStore**  
Накапливает изменения в памяти до сброса в HFiles.

**WAL**  
Позволяет восстановить незасброшенные изменения после сбоя.

**HFile**  
Формат постоянного хранения данных.

**Compaction**  
Объединяет HFiles, уменьшает количество файлов и обрабатывает tombstones в соответствии с правилами хранения.

**BlockCache**  
Ускоряет чтение часто используемых блоков.

### Что может ухудшить производительность

- Неудачно спроектированный Row Key.
- Hotspotting.
- Чрезмерное количество Column Families.
- Большое количество мелких файлов.
- Частые или дорогие compaction.
- Неоптимальные сканирования больших диапазонов.
- Недостаточная память для MemStore и BlockCache.
- Высокая задержка или нехватка ресурсов HDFS.

### Практические рекомендации

1. Начинать проектирование с access patterns — типичных запросов приложения.
2. Выбирать Row Key исходя из распределения данных и нагрузки.
3. Использовать Scan только с необходимыми диапазонами и ограничениями.
4. Следить за задержками, размером регионов и равномерностью нагрузки.
5. Настраивать число версий и TTL под требования к хранению данных.
6. Проверять влияние compaction на задержки и пропускную способность.

## 9. Частые вопросы на собеседовании

### Что такое HBase?

Распределённая wide-column NoSQL-база данных, построенная поверх HDFS и предназначенная для хранения больших объёмов данных с доступом по Row Key.

### Чем HBase отличается от Hadoop HDFS?

HDFS — распределённая файловая система, которая хранит файлы и обеспечивает доступ к ним.

HBase — база данных, использующая HDFS для постоянного хранения и предоставляющая структурированный доступ к строкам и ячейкам.

### Что такое RegionServer?

Серверный процесс, который обслуживает операции чтения и записи в назначенных ему регионах HBase.

### Что такое Region?

Часть таблицы, содержащая диапазон Row Key. По мере роста данных регионы могут разделяться и распределяться между серверами.

### Что такое Column Family?

Семейство столбцов, которое задаётся в схеме таблицы и используется для организации и настройки хранения группы столбцов.

### Почему Row Key так важен?

Он определяет порядок строк и влияет на распределение данных по регионам, маршрутизацию запросов и возможность эффективного чтения диапазонов.

### Что такое hotspotting?

Неравномерное распределение запросов или записей, когда отдельные регионы получают значительно большую нагрузку, чем остальные.

### Для чего нужен WAL?

WAL фиксирует изменения до их окончательного сброса в постоянные файлы и используется для восстановления после сбоев.

### Что такое HFile?

Формат файлов постоянного хранения данных HBase на HDFS.

### Что такое tombstone?

Маркер удаления, который позволяет логически удалить значение. Физическая очистка обычно происходит позднее в ходе compaction.

### Есть ли в HBase SQL?

В стандартной модели HBase нет полноценного SQL-интерфейса, аналогичного PostgreSQL. Доступ осуществляется через API, shell и дополнительные интеграционные инструменты.

### Подходит ли HBase для обычного CRUD-приложения?

Технически да, но это не всегда оправдано. Для большинства CRUD-сервисов со связями, ограничениями и транзакциями PostgreSQL проще. HBase оправдана при больших объёмах распределённых данных и соответствующем профиле нагрузки.
