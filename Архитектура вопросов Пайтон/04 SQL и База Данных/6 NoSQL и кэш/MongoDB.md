# MongoDB — конспект для Python Backend

## Формула для собеседования

**MongoDB — документоориентированная NoSQL-база данных**, которая хранит данные в документах BSON внутри коллекций. В отличие от PostgreSQL, MongoDB не требует заранее заданной реляционной схемы и удобна для данных с изменяющейся структурой. Поддерживает индексы, агрегации и транзакции.

**Ключевые слова:** Document, Collection, BSON, `_id`, Index, Aggregation Pipeline, Replica Set, Sharding.

## Короткий ответ

- **Database** — база данных.
- **Collection** — аналог таблицы в реляционной БД.
- **Document** — аналог строки, хранится в формате BSON.
- **Field** — поле документа.
- **`_id`** — уникальный идентификатор документа.
- **Index** — ускоряет поиск, но требует места и замедляет запись.
- **Aggregation Pipeline** — обработка и группировка документов.
- **Replica Set** — несколько узлов с репликацией данных.
- **Sharding** — распределение данных между несколькими узлами.

## Ответ на собеседовании

MongoDB — документоориентированная NoSQL-база данных. Она хранит данные в BSON-документах внутри коллекций. Документы одной коллекции могут иметь разную структуру, хотя при необходимости схему можно валидировать.

MongoDB подходит для каталогов товаров, событий, профилей пользователей и других данных, которые удобно представлять вложенными документами. Для сложных связей и запросов с большим количеством реляционных JOIN часто удобнее PostgreSQL.

При проектировании MongoDB важно выбирать структуру документов исходя из сценариев чтения и записи, правильно использовать индексы и учитывать ограничения атомарности операций.

## 1. Как устроена MongoDB

```text
MongoDB Server
└── Database
    └── Collection: users
        ├── Document
        │   ├── _id: ObjectId(...)
        │   ├── name: "Иван"
        │   └── age: 30
        └── Document
            ├── _id: ObjectId(...)
            ├── name: "Анна"
            └── email: "anna@example.com"
```

Пример документа:

```json
{
  "_id": "user-123",
  "name": "Иван",
  "age": 30,
  "skills": ["Python", "SQL"],
  "address": {
    "city": "Екатеринбург",
    "street": "Ленина"
  }
}
```

В реальной базе `_id` часто имеет тип `ObjectId`, а не строку. BSON — бинарное представление документов, которое поддерживает дополнительные типы данных, например даты и идентификаторы.

## 2. Основные операции CRUD

CRUD — Create, Read, Update, Delete.

### Создание

```javascript
db.users.insertOne({
    name: "Иван",
    age: 30
})
```

Несколько документов:

```javascript
db.users.insertMany([
    { name: "Анна", age: 25 },
    { name: "Пётр", age: 35 }
])
```

### Чтение

```javascript
// Все документы
db.users.find()

// Пользователи старше 25 лет
db.users.find({ age: { $gt: 25 } })

// Один документ
db.users.findOne({ name: "Иван" })
```

Основные операторы сравнения:

| Оператор | Значение |
|---|---|
| `$eq` | Равно |
| `$ne` | Не равно |
| `$gt` | Больше |
| `$gte` | Больше или равно |
| `$lt` | Меньше |
| `$lte` | Меньше или равно |
| `$in` | Значение входит в список |

### Обновление

```javascript
db.users.updateOne(
    { name: "Иван" },
    { $set: { age: 31 } }
)
```

`$set` изменяет указанное поле, не заменяя весь документ.

Увеличение значения:

```javascript
db.users.updateOne(
    { name: "Иван" },
    { $inc: { age: 1 } }
)
```

### Удаление

```javascript
db.users.deleteOne({ name: "Иван" })
```

Важно: `deleteMany({})` удаляет все документы коллекции. На рабочей базе такие операции требуют особой осторожности.

## 3. Вложенные документы и массивы

MongoDB позволяет хранить связанные данные внутри одного документа.

```json
{
  "name": "Иван",
  "address": {
    "city": "Екатеринбург"
  },
  "skills": ["Python", "FastAPI"]
}
```

Поиск по вложенному полю:

```javascript
db.users.find({
    "address.city": "Екатеринбург"
})
```

Поиск по элементу массива:

```javascript
db.users.find({
    skills: "Python"
})
```

Обновление массива:

```javascript
db.users.updateOne(
    { name: "Иван" },
    { $addToSet: { skills: "Docker" } }
)
```

`$addToSet` добавляет элемент, только если такого значения ещё нет. В отличие от `$push`, он не добавляет дубликаты.

## 4. Индексы

Индекс позволяет находить документы без полного перебора коллекции.

```javascript
db.users.createIndex({ email: 1 })
```

`1` означает сортировку индекса по возрастанию, `-1` — по убыванию.

Уникальный индекс:

```javascript
db.users.createIndex(
    { email: 1 },
    { unique: true }
)
```

Проверка плана запроса:

```javascript
db.users.find({
    email: "ivan@example.com"
}).explain("executionStats")
```

**Плюсы индексов:**
- Ускоряют подходящие запросы.
- Могут помогать сортировке.
- Уникальные индексы обеспечивают уникальность значений.

**Минусы:**
- Занимают место.
- Требуют обновления при изменении данных.
- Могут замедлять запись.

Составной индекс:

```javascript
db.orders.createIndex({
    user_id: 1,
    created_at: -1
})
```

Порядок полей важен: такой индекс особенно полезен для запросов по `user_id` и сортировки по `created_at`. Эффективность зависит от фильтров, сортировки и распределения данных.

## 5. Aggregation Pipeline

Aggregation Pipeline — последовательность стадий обработки документов.

Пример: подсчитать количество заказов каждого пользователя.

```javascript
db.orders.aggregate([
    {
        $group: {
            _id: "$user_id",
            total_orders: { $sum: 1 }
        }
    }
])
```

Часто используемые стадии:

| Стадия | Назначение |
|---|---|
| `$match` | Фильтрация документов |
| `$group` | Группировка и агрегаты |
| `$project` | Выбор и преобразование полей |
| `$sort` | Сортировка |
| `$limit` | Ограничение количества результатов |
| `$unwind` | Разворачивание массива в отдельные документы |
| `$lookup` | Соединение с другой коллекцией |

Пример с фильтрацией, группировкой и сортировкой:

```javascript
db.orders.aggregate([
    { $match: { status: "paid" } },
    {
        $group: {
            _id: "$user_id",
            total: { $sum: "$amount" }
        }
    },
    { $sort: { total: -1 } },
    { $limit: 10 }
])
```

Здесь выбираются оплаченные заказы, рассчитывается сумма по каждому пользователю и возвращаются десять пользователей с наибольшей суммой.

## 6. MongoDB vs PostgreSQL

| Критерий | MongoDB | PostgreSQL |
|---|---|---|
| Тип | Документоориентированная NoSQL | Реляционная SQL |
| Основная структура | Документы BSON | Таблицы и строки |
| Схема | Гибкая, с возможностью валидации | Задаётся структурой таблиц |
| Связи | Вложенные документы, ссылки, `$lookup` | Внешние ключи и JOIN |
| Запросы | MQL, Aggregation Pipeline | SQL |
| Транзакции | Поддерживаются, в том числе много-документные | Поддерживаются |
| Типичные сценарии | Гибкие документы, события, каталоги | Связанные данные, отчётность, транзакционные системы |

**Важно:** MongoDB — не просто база «без схемы» и не база «без транзакций». В ней можно валидировать структуру документов и выполнять транзакции. Выбор зависит от модели данных и требований приложения.

## 7. Встраивание или ссылка?

Один из главных вопросов проектирования MongoDB — хранить связанные данные внутри документа или отдельно.

### Встраивание (Embedding)

```json
{
  "_id": "order-1",
  "user_id": "user-1",
  "items": [
    {"product_id": "p1", "quantity": 2},
    {"product_id": "p2", "quantity": 1}
  ]
}
```

Подходит, когда данные обычно читаются вместе и размер документа остаётся контролируемым.

### Ссылки (Referencing)

```json
{
  "_id": "order-1",
  "user_id": "user-1"
}
```

Данные пользователя хранятся отдельно.

Подходит, когда сущности независимы, переиспользуются многими документами или часто изменяются отдельно.

**Правило:** проектируй модель под реальные запросы, а не пытайся механически перенести реляционную схему в MongoDB.

## 8. Replica Set и Sharding

### Replica Set

Группа узлов, хранящих реплики данных. Обычно есть primary, который принимает записи, и secondary, которые реплицируют изменения.

Зачем нужен:
- Повышение доступности.
- Автоматические выборы нового primary при определённых отказах.
- Возможность читать с secondary, если это допустимо политикой чтения.

Репликация сама по себе не является резервной копией: случайное удаление данных может распространиться на реплики.

### Sharding

Распределение данных между несколькими узлами — шардами.

Используется для горизонтального масштабирования хранения и нагрузки. Ключ шардирования существенно влияет на равномерность распределения данных и эффективность запросов.

## 9. MongoDB в Python

Для синхронного кода часто используют `pymongo`, для асинхронного — совместимый с выбранным стеком асинхронный драйвер. При выборе учитывай актуальный статус поддержки и рекомендации проекта MongoDB.

Пример с PyMongo:

```python
from pymongo import MongoClient

client = MongoClient(
    "mongodb://localhost:27017",
    serverSelectionTimeoutMS=5000,
)

db = client["shop"]
users = db["users"]

users.insert_one({
    "name": "Иван",
    "age": 30,
})

user = users.find_one({"name": "Иван"})
print(user)

client.close()
```

Здесь:
1. Создаётся клиент подключения.
2. Выбирается база `shop`.
3. Выбирается коллекция `users`.
4. Создаётся документ и выполняется поиск.

В реальном приложении клиент обычно создают один раз на процесс и переиспользуют, а не открывают заново для каждого запроса. Строку подключения и секреты хранят в переменных окружения.

### Асинхронный вариант

Для нового проекта можно рассмотреть поддерживаемый асинхронный драйвер MongoDB, например `AsyncMongoClient` в актуальных версиях PyMongo. Важно использовать его API в соответствии с установленной версией драйвера и не смешивать синхронные операции с асинхронным кодом без необходимости.

## 10. Ошибки, которых стоит избегать

- Создавать индексы наугад, не изучая реальные запросы.
- Хранить неограниченно растущие массивы внутри одного документа.
- Дублировать данные без стратегии их синхронизации.
- Считать, что гибкая схема означает отсутствие требований к структуре данных.
- Использовать `$lookup` повсюду вместо продуманной модели документов.
- Полагаться на репликацию как на полноценную резервную копию.
- Формировать запросы конкатенацией строк вместо передачи параметров и безопасного API драйвера.
- Не проверять планы запросов через `explain()`.

## 11. Частые вопросы на собеседовании

**1. Что такое MongoDB?**

Документоориентированная NoSQL-база данных, которая хранит документы в формате BSON внутри коллекций.

**2. Чем документ отличается от строки PostgreSQL?**

Документ может содержать вложенные объекты и массивы, а его структура может отличаться от структуры других документов в коллекции. В PostgreSQL данные обычно организованы в таблицах с определённой схемой.

**3. Зачем нужен индекс?**

Чтобы ускорять подходящие запросы и сортировки за счёт дополнительной структуры данных. Цена — место на диске и дополнительные затраты при записи.

**4. Что такое Aggregation Pipeline?**

Последовательность стадий обработки документов: фильтрация, группировка, преобразование, сортировка и другие операции.

**5. Что выбрать: embedding или referencing?**

Embedding — когда связанные данные читаются вместе и их размер ограничен. Referencing — когда данные независимы, часто переиспользуются или изменяются отдельно.

**6. Поддерживает ли MongoDB транзакции?**

Да. MongoDB поддерживает атомарность на уровне отдельного документа, а также много-документные транзакции. Последние требуют дополнительных ресурсов и не должны заменять хорошее проектирование данных.

**7. Что такое Replica Set?**

Группа узлов с репликацией данных, обеспечивающая отказоустойчивость и возможность автоматического выбора нового primary.

**8. Что такое Sharding?**

Распределение данных между несколькими шардами для масштабирования. Важнейший фактор — правильно выбранный ключ шардирования.

**9. Что такое `_id`?**

Уникальный идентификатор документа в коллекции. Если не передать его при вставке, MongoDB обычно создаст `ObjectId` автоматически.

**10. Как ускорить медленный запрос?**

Проверить `explain("executionStats")`, посмотреть используемый индекс и число просмотренных документов, затем оценить фильтры, сортировку и селективность индекса.
