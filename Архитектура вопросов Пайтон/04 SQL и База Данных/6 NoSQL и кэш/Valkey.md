# Valkey — конспект для Python Backend

## Формула для собеседования

**Valkey — это open-source in-memory хранилище данных типа key-value**, совместимое с Redis OSS. Оно поддерживает структуры данных, такие как строки, хеши, списки, множества и отсортированные множества. В Backend-разработке его используют для кэширования, хранения временных данных, счётчиков, блокировок и обмена сообщениями.

**Ключевые слова:** In-memory, Key-Value, TTL, Cache, Eviction, Pub/Sub, Persistence, Replication, Redis Protocol.

## Короткий ответ

- **Key-Value** — данные хранятся по ключу.
- **In-memory** — основные операции выполняются с данными в оперативной памяти.
- **TTL** — время жизни ключа.
- **Cache** — временное хранение результатов для ускорения приложения.
- **Eviction** — удаление ключей при достижении лимита памяти по выбранной политике.
- **Persistence** — сохранение данных на диск.
- **Pub/Sub** — публикация сообщений и подписка на каналы.
- **Replication** — копирование данных на другие узлы.
- **Valkey** — отдельный open-source проект, созданный после перехода Redis на другую лицензионную модель.

## Ответ на собеседовании

Valkey — высокопроизводительное хранилище данных в памяти с интерфейсом key-value. Оно поддерживает множество структур данных и протокол, совместимый с Redis OSS, поэтому во многих случаях позволяет использовать привычные инструменты и клиенты Redis.

В Python Backend Valkey часто применяют как кэш между приложением и PostgreSQL: приложение сначала проверяет наличие данных в кэше и обращается к основной базе только при cache miss. Также Valkey может хранить сессии, временные токены и счётчики запросов.

При этом Valkey не заменяет реляционную базу данных: данные в кэше могут истекать или вытесняться, а сохранность зависит от конфигурации persistence и отказоустойчивости.

## 1. Как устроен Valkey

```text
Python Backend
      |
      v
    Valkey
      |
      | cache miss
      v
  PostgreSQL
```

Типичный сценарий:

1. Приложение запрашивает пользователя.
2. Проверяет кэш Valkey.
3. Если ключ найден — возвращает данные из кэша.
4. Если ключа нет — читает PostgreSQL.
5. Сохраняет результат в Valkey с TTL.
6. Возвращает данные клиенту.

## 2. Основные команды

### Строки

```text
SET user:1 "Иван"
GET user:1
DEL user:1
```

Установка времени жизни:

```text
SET user:1 "Иван" EX 300
TTL user:1
```

`EX 300` задаёт TTL в секундах. После истечения времени ключ становится недоступным.

### Счётчики

```text
INCR page:views
INCR page:views
GET page:views
```

`INCR` атомарно увеличивает числовое значение ключа. Это удобно для счётчиков и некоторых сценариев rate limiting.

### Хеши

```text
HSET user:1 name "Иван" age 30
HGET user:1 name
HGETALL user:1
```

Хеш позволяет хранить несколько полей под одним ключом.

### Списки

```text
LPUSH tasks "task-1"
RPUSH tasks "task-2"
LRANGE tasks 0 -1
```

Списки поддерживают добавление и извлечение элементов с разных концов. Их можно применять для простых очередей, но для надёжной обработки задач необходимо отдельно продумать подтверждение, повторные попытки и восстановление после сбоев.

### Множества

```text
SADD tags python backend database
SMEMBERS tags
SISMEMBER tags python
```

Множества хранят уникальные значения.

### Sorted Sets

```text
ZADD leaderboard 100 user:1
ZADD leaderboard 250 user:2
ZREVRANGE leaderboard 0 9 WITHSCORES
```

Sorted Set хранит уникальные элементы с числовыми оценками. Подходит для рейтингов, ранжирования и временных индексов.

## 3. Кэширование: Cache-Aside

Один из наиболее распространённых паттернов.

```python
import json

from valkey import Valkey

cache = Valkey(
    host="localhost",
    port=6379,
    decode_responses=True,
)


def get_user(user_id: int) -> dict:
    key = f"user:{user_id}"

    cached = cache.get(key)
    if cached is not None:
        return json.loads(cached)

    # Здесь получаем пользователя из PostgreSQL.
    user = {
        "id": user_id,
        "name": "Иван",
    }

    cache.set(key, json.dumps(user), ex=300)
    return user
```

В этом примере чтение из PostgreSQL показано условно — реальный код должен использовать репозиторий или ORM.

**Преимущества:**
- Снижается нагрузка на PostgreSQL.
- Уменьшается задержка при повторных запросах.
- Можно обслуживать часть запросов без обращения к основной БД.

**Проблемы:**
- Cache miss — нужного значения нет в кэше.
- Cache stampede — множество запросов одновременно пытаются загрузить один и тот же отсутствующий объект.
- Устаревшие данные — кэш не соответствует основной БД.
- Cache penetration — повторные запросы к данным, которых не существует.

Для снижения риска одновременного истечения множества ключей используют случайный разброс TTL, а для дорогих запросов — координацию загрузки и другие стратегии защиты.

## 4. Инвалидация кэша

Если пользователь изменился в PostgreSQL, кэш нужно обновить или удалить.

```python
def update_user(user_id: int, new_name: str) -> None:
    # 1. Обновляем пользователя в PostgreSQL.
    # 2. После успешного коммита удаляем кэш.
    cache.delete(f"user:{user_id}")
```

Главная идея: PostgreSQL остаётся источником истины, а кэш можно восстановить.

Однако простое удаление ключа не решает все гонки между параллельными чтениями и записями. В критичных системах стратегию согласованности нужно проектировать отдельно.

## 5. TTL и eviction

### TTL

TTL (Time To Live) задаёт срок жизни ключа.

```text
SET session:abc "user-1" EX 1800
```

Ключ действует 30 минут.

TTL полезен для:
- Сессий.
- Временных токенов.
- Кэшированных результатов.
- Временных блокировок.

### Eviction

Eviction — политика освобождения памяти, когда хранилище достигает заданного лимита.

В зависимости от конфигурации могут применяться политики вроде:

- `noeviction` — не вытеснять ключи, а возвращать ошибки при невозможности выделить память для записи.
- `allkeys-lru` — вытеснять наименее недавно использованные ключи среди всех ключей.
- `allkeys-lfu` — вытеснять наименее часто используемые ключи среди всех ключей.
- `volatile-lru` — выбирать кандидатов среди ключей с TTL.

Конкретные доступные политики и их поведение нужно проверять для используемой версии Valkey.

**Важно:** TTL и eviction — разные механизмы. TTL задаёт срок жизни ключа, а eviction освобождает память по политике вытеснения.

## 6. Valkey и PostgreSQL

| Критерий | Valkey | PostgreSQL |
|---|---|---|
| Основное назначение | Кэш и быстрый доступ к данным | Основная реляционная БД |
| Хранение | В основном оперативная память | Долговременное хранение на диске |
| Модель | Key-value и структуры данных | Таблицы, связи и SQL |
| Запросы | По ключам и структурам данных | SQL, JOIN, агрегаты |
| Транзакции | Команды и механизмы атомарности в рамках поддерживаемого API | ACID-транзакции |
| Типичное применение | Кэш, счётчики, временные данные | Пользователи, заказы, платежи |

Valkey может использовать persistence, но это не делает его прямой заменой PostgreSQL для всех задач.

## 7. Valkey и Redis

Valkey возник как open-source форк Redis после изменения лицензирования Redis в 2024 году.

В большинстве типовых сценариев Valkey совместим с Redis OSS на уровне протокола и многих команд. Поэтому часто можно использовать существующие Redis-клиенты для Python, если поддерживаются нужные команды и версия сервера.

Однако перед миграцией нужно проверить:
- Совместимость конкретных команд и структур данных.
- Версии сервера и клиентской библиотеки.
- Настройки persistence и репликации.
- Поддержку используемых модулей и дополнительных функций.

**На собеседовании:** Valkey и Redis тесно связаны исторически, но это отдельные проекты с разным развитием и лицензированием.

## 8. Подключение из Python

Установка клиента:

```bash
pip install valkey
```

Пример:

```python
from valkey import Valkey

client = Valkey(
    host="localhost",
    port=6379,
    decode_responses=True,
)

client.set("language", "Python", ex=60)

value = client.get("language")
print(value)

client.close()
```

`decode_responses=True` позволяет получать строки Python вместо байтов для строковых ответов.

В реальном приложении клиент создают на уровне приложения и переиспользуют. Пароли и адреса подключения следует хранить в переменных окружения.

### Применение с FastAPI

Обычно клиент инициализируют при запуске приложения и закрывают при завершении. В асинхронном FastAPI следует выбирать соответствующий асинхронный клиент и не блокировать event loop синхронными сетевыми вызовами.

## 9. Pub/Sub

Pub/Sub позволяет публиковать сообщения в канал, на который подписаны другие клиенты.

```text
PUBLISH notifications "Новый заказ"
SUBSCRIBE notifications
```

Это полезно для простых событий и уведомлений, но важно помнить: обычный Pub/Sub не гарантирует доставку сообщения подписчику, который был отключён в момент публикации.

Если требуется хранение сообщений, подтверждение обработки и повторное чтение, следует рассмотреть Valkey Streams или специализированный брокер сообщений.

## 10. Persistence и отказоустойчивость

Valkey поддерживает механизмы сохранения состояния, включая RDB-снимки и AOF-журналирование, если они включены и настроены.

- **RDB** — сохранение снимка данных.
- **AOF** — журнал команд записи, позволяющий восстановить состояние с учётом настроек синхронизации.
- **Replication** — передача данных на реплики.
- **Sentinel** — механизм мониторинга и переключения primary в поддерживаемых конфигурациях.
- **Cluster** — распределение данных по узлам и масштабирование в поддерживаемой кластерной конфигурации.

Репликация повышает доступность, но не заменяет резервное копирование. При выборе конфигурации важно учитывать допустимую потерю данных и время восстановления.

## 11. Частые вопросы на собеседовании

**1. Что такое Valkey?**

Open-source in-memory хранилище key-value с поддержкой различных структур данных и совместимостью с Redis OSS.

**2. Зачем Valkey в Backend?**

Для кэширования, временных данных, сессий, счётчиков и других сценариев, где нужен быстрый доступ по ключу.

**3. Что такое TTL?**

Время жизни ключа, после которого он перестаёт быть доступным.

**4. Чем TTL отличается от eviction?**

TTL ограничивает время жизни ключа. Eviction выбирает ключи для удаления при нехватке памяти согласно политике вытеснения.

**5. Что такое Cache-Aside?**

Приложение сначала читает кэш, а при отсутствии значения загружает данные из основной БД и помещает их в кэш.

**6. Что такое cache stampede?**

Ситуация, когда множество запросов одновременно пытаются пересчитать или загрузить одно и то же значение после истечения кэша.

**7. Можно ли использовать Valkey вместо PostgreSQL?**

Для отдельных сценариев — да, но не как универсальную замену. У Valkey другая модель данных и другие гарантии; сложные реляционные запросы и долговременное хранение обычно остаются задачей PostgreSQL.

**8. Гарантирует ли Pub/Sub доставку сообщений?**

Нет. Обычный Pub/Sub не хранит сообщения для отключённых подписчиков.

**9. Что такое RDB и AOF?**

Два механизма persistence: снимки состояния и журналирование операций записи.

**10. Чем Valkey отличается от Redis?**

Это отдельный open-source проект, возникший как форк Redis. Во многих типовых сценариях совместим с Redis OSS, но совместимость конкретных функций необходимо проверять.

```text

DEL             → удаление ключа
EX              → TTL в секундах
INCR            → атомарное увеличение счётчика
HSET / HGET     → работа с хешами
LPUSH / RPOP    → операции со списками
SADD / SMEMBERS → множества
ZADD / ZRANGE   → отсортированные множества
Pub/Sub         → публикация сообщений без гарантии хранения

RDB             → снимок состояния

Eviction        → освобождение памяти по политике вытеснения
Cache-Aside     → кэширование на стороне приложения
```
