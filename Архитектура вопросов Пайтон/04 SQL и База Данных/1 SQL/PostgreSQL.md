# PostgreSQL — конспект для Python Backend

## Формула для собеседования

**PostgreSQL** — объектно-реляционная СУБД с поддержкой SQL, транзакций ACID, индексов, внешних ключей, JSONB, конкурентного доступа и расширений.

Ключевые понятия:

- **Таблица** — хранит данные в строках и столбцах.
- **PRIMARY KEY** — уникально идентифицирует строку.
- **FOREIGN KEY** — обеспечивает ссылочную целостность.
- **Индекс** — ускоряет поиск и сортировку, но увеличивает стоимость записи и хранения.
- **JOIN** — объединяет данные из нескольких таблиц.
- **Транзакция** — объединяет операции в одну логическую единицу.
- **ACID** — свойства надёжных транзакций.
- **MVCC** — позволяет транзакциям работать с согласованными версиями строк.
- **EXPLAIN ANALYZE** — помогает анализировать фактическое выполнение запроса.
- **Connection Pool** — переиспользует соединения с базой данных.

**Главная мысль:** хороший Backend-разработчик должен не только писать SQL, но и понимать целостность данных, конкурентный доступ, производительность запросов и поведение системы при ошибках.

---

## Короткий ответ

PostgreSQL — реляционная СУБД, которую используют для хранения структурированных данных и выполнения транзакционных операций.

В Python Backend я работаю с PostgreSQL через SQL-запросы или ORM, например SQLAlchemy. Использую ограничения целостности, транзакции, индексы и внешние ключи, чтобы сохранять корректность данных.

Для оптимизации анализирую запросы через `EXPLAIN ANALYZE`, проверяю индексы и избегаю лишних обращений к базе. При разработке API учитываю пулы соединений, конкурентные операции и обработку ошибок транзакций.

## 1. Реляционная модель данных

Реляционная база хранит данные в таблицах, связанных между собой отношениями.

Например, интернет-магазин может содержать таблицы:

```text
users
  |
  | 1:N
  v
orders
  |
  | 1:N
  v
order_items
  |
  | N:1
  v
products
```

Один пользователь может иметь несколько заказов. Каждый заказ содержит несколько позиций, а каждая позиция ссылается на товар.

### Создание таблиц

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    status TEXT NOT NULL DEFAULT 'new',
    total NUMERIC(12, 2) NOT NULL CHECK (total >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Что важно:

- `PRIMARY KEY` — уникальный идентификатор строки.
- `NOT NULL` — запрещает отсутствие значения.
- `UNIQUE` — запрещает дубликаты.
- `REFERENCES` — задаёт внешний ключ.
- `CHECK` — проверяет условие для значения.
- `DEFAULT` — задаёт значение по умолчанию.
- `TIMESTAMPTZ` — хранит момент времени с нормализацией к UTC.

Ограничения лучше определять в самой базе данных, а не полагаться исключительно на проверки в Python.

## 2. Основные SQL-команды

### SELECT — чтение

```sql
SELECT id, email
FROM users
WHERE email LIKE '%@gmail.com'
ORDER BY id DESC
LIMIT 10;
```

Запрос выбирает пользователей с адресами Gmail, сортирует их по идентификатору и возвращает максимум десять строк.

### INSERT — добавление

```sql
INSERT INTO users (email)
VALUES ('user@example.com')
RETURNING id, email;
```

`RETURNING` позволяет получить данные созданной строки без отдельного `SELECT`.

### UPDATE — изменение

```sql
UPDATE orders
SET status = 'paid'
WHERE id = 10;
```

Без `WHERE` будут изменены все строки таблицы. Поэтому перед выполнением изменения важно проверять условие.

### DELETE — удаление

```sql
DELETE FROM orders
WHERE id = 10;
```

Внешние ключи могут запрещать удаление или определять поведение связанных строк.

### UPSERT — вставка или обновление

```sql
INSERT INTO users (email)
VALUES ('user@example.com')
ON CONFLICT (email)
DO NOTHING;
```

`ON CONFLICT` позволяет обработать конфликт уникальности на уровне базы данных.

## 3. JOIN — объединение таблиц

`JOIN` позволяет получить связанные данные из нескольких таблиц.

### INNER JOIN

Возвращает только строки, для которых найдено совпадение в обеих таблицах.

```sql
SELECT
    users.email,
    orders.id AS order_id,
    orders.total
FROM users
INNER JOIN orders
    ON users.id = orders.user_id;
```

### LEFT JOIN

Возвращает все строки левой таблицы, даже если совпадения справа нет.

```sql
SELECT
    users.email,
    orders.id AS order_id
FROM users
LEFT JOIN orders
    ON users.id = orders.user_id;
```

Пользователи без заказов тоже попадут в результат. Для них `order_id` будет `NULL`.

### Когда использовать

- `INNER JOIN` — нужны только связанные записи.
- `LEFT JOIN` — нужны все записи основной таблицы, включая те, для которых нет связи.

## 4. Индексы

**Индекс** — дополнительная структура данных, позволяющая быстрее находить строки по определённым условиям.

Без подходящего индекса PostgreSQL может читать всю таблицу. Такой план называется `Seq Scan`.

### Создание индекса

```sql
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

Теперь индекс может помочь запросу:

```sql
SELECT *
FROM orders
WHERE user_id = 42;
```

### Составной индекс

```sql
CREATE INDEX idx_orders_user_status
ON orders(user_id, status);
```

Порядок столбцов имеет значение. Такой индекс особенно полезен для фильтрации по `user_id` и для условий по обоим столбцам.

Он обычно не столь полезен для запросов, фильтрующих только по `status`, потому что `status` находится не в начале индекса.

### UNIQUE INDEX

```sql
CREATE UNIQUE INDEX idx_users_email
ON users(email);
```

Обеспечивает уникальность значений индекса. Для обычного ограничения уникальности чаще используют `UNIQUE` непосредственно в определении таблицы.

### Когда индекс может навредить

- Увеличивает расход дискового пространства.
- Замедляет `INSERT`, `UPDATE` и `DELETE`, поскольку индексы нужно поддерживать.
- Может быть бесполезным для небольших таблиц или неудачно подобранных условий.

**Правило:** индекс нужно обосновывать реальными запросами и проверять планом выполнения.

## 5. EXPLAIN ANALYZE — анализ запросов

`EXPLAIN` показывает план, который PostgreSQL собирается использовать.

`EXPLAIN ANALYZE` дополнительно выполняет запрос и показывает фактические показатели выполнения.

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE user_id = 42;
```

Обращай внимание на:

- `Seq Scan` — последовательное чтение таблицы.
- `Index Scan` — чтение через индекс.
- `Bitmap Index Scan` — использование индекса для формирования набора строк.
- `Nested Loop`, `Hash Join`, `Merge Join` — алгоритмы соединения таблиц.
- `actual time` — фактическое время узла плана.
- `rows` — оценка или фактическое число строк в зависимости от секции вывода.
- `Buffers` — информация об использовании буферов при соответствующих настройках.

`Seq Scan` не всегда означает проблему: для маленькой таблицы или запроса, который возвращает большую часть строк, он может быть эффективнее индекса.

**Важно:** `EXPLAIN ANALYZE` действительно выполняет запрос. Для изменяющих запросов, например `UPDATE`, используй осторожность: анализ может реально изменить данные. При необходимости тестируй в транзакции с последующим `ROLLBACK`, учитывая побочные эффекты внешних функций.

## 6. Транзакции

**Транзакция** объединяет несколько операций так, чтобы они выполнялись как одна логическая единица.

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Если перевод должен выполняться целиком, нельзя допускать, чтобы деньги списались с одного счёта, но не зачислились на другой.

При ошибке транзакцию можно откатить:

```sql
ROLLBACK;
```

В реальном банковском сценарии дополнительно необходимы проверки баланса, корректная обработка конкуренции и ограничения на допустимые значения.

---

## 7. ACID

ACID описывает четыре свойства транзакций.

| Свойство | Значение |
|---|---|
| Atomicity | Все операции транзакции фиксируются вместе либо откатываются |
| Consistency | Транзакция сохраняет заданные правила целостности |
| Isolation | Конкурентные транзакции взаимодействуют согласно выбранному уровню изоляции |
| Durability | После успешного `COMMIT` изменения сохраняются согласно гарантиям настроенной системы |

### Пример

При переводе денег:
- Atomicity — списание и зачисление выполняются совместно.
- Consistency — баланс не нарушает бизнес-правила.
- Isolation — параллельные переводы не приводят к некорректным результатам.
- Durability — подтверждённый перевод не теряется при обычном перезапуске в пределах гарантий конфигурации хранения.

## 8. MVCC и конкурентный доступ

**MVCC (Multi-Version Concurrency Control)** — механизм управления конкурентным доступом, при котором PostgreSQL хранит версии строк.

Это позволяет читателям и писателям во многих ситуациях работать параллельно без взаимной блокировки на уровне каждой операции чтения и записи.

### Зачем это нужно

Предположим, один запрос читает данные, а другой обновляет строку. Благодаря MVCC первый запрос в соответствии со своим снимком данных может прочитать согласованную версию, не дожидаясь завершения изменения.

Однако MVCC не отменяет все блокировки. Конкурентные изменения одних и тех же строк могут конфликтовать.

### Блокировка строки

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

`FOR UPDATE` блокирует выбранные строки от несовместимых конкурентных изменений до завершения транзакции.

Этот механизм полезен, когда бизнес-операция требует прочитать строку и затем безопасно изменить её.

**Важно:** удерживай транзакции короткими. Долгие транзакции могут мешать очистке старых версий строк и ухудшать производительность.

## 9. Уровни изоляции

PostgreSQL поддерживает следующие основные уровни изоляции:

| Уровень | Особенность |
|---|---|
| Read Uncommitted | В PostgreSQL ведёт себя как Read Committed |
| Read Committed | Каждый SQL-оператор получает собственный снимок данных |
| Repeatable Read | Транзакция работает с устойчивым снимком |
| Serializable | Обеспечивает результат, эквивалентный последовательному выполнению транзакций, но возможны ошибки сериализации |

### Read Committed

Это уровень изоляции по умолчанию в PostgreSQL.

Каждый оператор видит данные, зафиксированные к моменту начала этого оператора.

### Serializable

Самый строгий из перечисленных уровней. PostgreSQL может прервать транзакцию, если обнаружит конфликт сериализации.

Приложение должно быть готово повторить всю транзакцию при соответствующей ошибке.

**На собеседовании:** более строгая изоляция не означает, что приложение освобождается от обработки ошибок и повторов.

## 10. Нормализация

Нормализация помогает уменьшать дублирование данных и избегать аномалий при изменении информации.

Например, вместо хранения имени и адреса пользователя в каждой строке заказа создают отдельную таблицу пользователей и ссылаются на неё через `user_id`.

### Первая нормальная форма (1NF)

Значения в столбцах должны соответствовать выбранной модели атомарных значений; не следует хранить повторяющиеся группы элементов в одном поле вместо подходящей структуры данных.

### Вторая нормальная форма (2NF)

Таблица должна соответствовать 1NF, а каждый неключевой атрибут должен зависеть от полного кандидатного ключа, а не от его части.

### Третья нормальная форма (3NF)

Таблица должна соответствовать 2NF и не содержать определённых транзитивных зависимостей неключевых атрибутов от ключа.

### Когда нужна денормализация

Иногда данные намеренно дублируют ради производительности чтения. Но тогда необходимо продумать, как поддерживать согласованность дублированных значений.

## 11. Типы данных PostgreSQL

| Тип | Применение |
|---|---|
| `INTEGER` / `BIGINT` | Целые числа |
| `NUMERIC(p, s)` | Точные десятичные значения, например денежные суммы |
| `TEXT` | Строки |
| `BOOLEAN` | Логические значения |
| `DATE` | Календарная дата |
| `TIMESTAMPTZ` | Момент времени |
| `UUID` | Идентификаторы UUID |
| `JSONB` | Структурированные JSON-данные с эффективной обработкой |
| `BYTEA` | Бинарные данные |

### Почему для денег часто используют NUMERIC?

Тип `NUMERIC` обеспечивает точную десятичную арифметику в пределах возможностей типа.

Типы с плавающей точкой, например `REAL` и `DOUBLE PRECISION`, не гарантируют точного представления многих десятичных дробей.

### JSONB

`JSONB` полезен для полуструктурированных данных, например настроек или дополнительных атрибутов.

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'
);
```

Поиск по полю JSONB:

```sql
SELECT *
FROM products
WHERE attributes ->> 'color' = 'black';
```

Оператор `->>` извлекает JSON-значение как текст.

Для подходящих сценариев можно создавать индексы по JSONB. Но структурированные данные, по которым часто выполняются связи и ограничения, обычно удобнее хранить в отдельных столбцах.

## 12. Connection Pool

Создание нового соединения с PostgreSQL для каждого запроса может быть дорогим и неэффективным.

**Connection Pool** хранит набор открытых соединений и выдаёт их приложению по мере необходимости.

### Зачем нужен

- Снижает накладные расходы на установку соединений.
- Ограничивает число одновременных подключений.
- Позволяет эффективнее использовать ресурсы PostgreSQL.

### Важный нюанс

Если запустить несколько экземпляров приложения, каждый со своим пулом, суммарное число соединений может превысить возможности базы.

Например, четыре процесса с пулом максимум 20 соединений могут создать до 80 соединений только для этой группы процессов.

При проектировании учитывают все приложения, фоновые workers, административные подключения и резерв ресурсов для обслуживания.

## 13. PostgreSQL в Python Backend

Обычно используются несколько вариантов доступа к базе.

| Инструмент | Назначение |
|---|---|
| psycopg | Драйвер PostgreSQL для Python |
| asyncpg | Асинхронный драйвер PostgreSQL |
| SQLAlchemy | SQL toolkit и ORM |
| Alembic | Миграции схемы БД |
| SQLModel | Модели на основе Pydantic и SQLAlchemy |

### Прямой SQL

Плюсы:
- Явный контроль над запросами.
- Удобно использовать возможности PostgreSQL.
- Хорошо подходит для сложных запросов и аналитики.

Минусы:
- Больше ручной работы с преобразованием данных.
- Нужно внимательно организовывать доступ к соединениям и транзакциям.

### ORM

Плюсы:
- Работа с объектами Python.
- Удобное описание моделей и связей.
- Интеграция с транзакциями и миграциями.

Минусы:
- Можно случайно создавать много лишних запросов.
- Для сложных операций иногда требуется знание SQL.
- ORM не заменяет понимание транзакций и индексов.

## 14. SQL Injection

SQL Injection возникает, когда пользовательский ввод включается в SQL как часть исполняемого текста.

### Небезопасно

```python
query = (
    f"SELECT * FROM users "
    f"WHERE email = '{email}'"
)
```

Если `email` содержит специально сформированную строку, запрос может изменить смысл.

### Безопаснее

```python
cursor.execute(
    "SELECT * FROM users WHERE email = %s",
    (email,),
)
```

Здесь используется параметризованный запрос. Значение передаётся отдельно от SQL-кода.

Синтаксис плейсхолдеров зависит от драйвера. Например, SQLAlchemy использует собственные механизмы связывания параметров.

**Правило:** не формируй SQL через конкатенацию пользовательских значений. Для динамических имён столбцов и таблиц нужны отдельные механизмы безопасного построения SQL, поскольку обычные параметры не заменяют идентификаторы.

## 15. N+1 Query Problem

Проблема N+1 возникает, когда приложение сначала получает список объектов одним запросом, а затем выполняет дополнительный запрос для каждого объекта.

Например:

```python
users = await get_users()

for user in users:
    orders = await get_orders(user.id)
```

Если пользователей 100, может получиться 101 запрос вместо одного или нескольких оптимизированных запросов.

### Решения

- `JOIN`, когда подходит объединение на стороне БД.
- Пакетная загрузка связанных данных.
- `selectinload` или другие стратегии загрузки SQLAlchemy.
- Группировка запросов по идентификаторам.

**Важно:** не каждый дополнительный запрос — ошибка. Цель состоит в том, чтобы избегать ненужного числа обращений и измерять производительность.

## 16. Миграции базы данных

Миграции позволяют управлять изменениями схемы БД между версиями приложения.

Например, требуется добавить столбец `phone` в таблицу пользователей.

Обычно используют Alembic в проектах с SQLAlchemy.

### Безопасный подход к изменению схемы

Для крупной работающей системы часто применяют поэтапное изменение:

1. Добавить новое поле или таблицу так, чтобы старая версия приложения продолжала работать.
2. Обновить приложение для записи и чтения новых данных.
3. При необходимости перенести старые данные.
4. Переключить использование на новую схему.
5. Удалять старые поля только после того, как они больше не нужны.

Это помогает избежать ситуации, когда новая схема несовместима с ещё работающими экземплярами старой версии приложения.

## 17. Типичные ошибки

- Создание индексов без анализа запросов.
- Отсутствие внешних ключей и ограничений там, где они нужны.
- Долгие транзакции.
- Игнорирование блокировок и ошибок сериализации.
- SQL Injection из-за конкатенации строк.
- N+1 Query Problem.
- Неограниченный рост числа соединений.
- Выполнение тяжёлых запросов без анализа плана.
- Использование `float` для точных денежных вычислений.
- Изменение схемы без учёта совместимости версий приложения.
- Предположение, что репликация заменяет резервное копирование.

## 18. Вопросы для собеседования

### Чем PostgreSQL отличается от обычной SQL-базы?

SQL — язык запросов. PostgreSQL — конкретная система управления базами данных, которая реализует SQL и предоставляет собственные возможности.

### Что такое индекс?

Дополнительная структура данных, которая ускоряет определённые операции чтения, но требует места и обслуживания при изменениях.

### Что такое ACID?

Atomicity, Consistency, Isolation, Durability — свойства транзакций, обеспечивающие атомарность, целостность, изоляцию и долговечность в рамках настроенной системы.

### Что такое MVCC?

Механизм хранения и использования версий строк, который помогает организовать конкурентный доступ к данным.

### Что такое Connection Pool?

Набор переиспользуемых соединений, уменьшающий расходы на подключение и позволяющий контролировать параллельный доступ к БД.

### Когда использовать JOIN?

Когда требуется получить связанные данные из нескольких таблиц на стороне базы данных.

### Чем `DELETE` отличается от `TRUNCATE`?

`DELETE` удаляет строки с возможностью использовать условие `WHERE`. `TRUNCATE` быстро очищает таблицу целиком, имеет другие особенности блокировок и поведения, а также поддерживает собственные правила работы с внешними ключами.

### Чем `WHERE` отличается от `HAVING`?

`WHERE` фильтрует строки до группировки, а `HAVING` фильтрует группы после `GROUP BY`.

### Что такое уровень изоляции?

Набор правил, определяющих, какие эффекты конкурентных транзакций могут быть видны друг другу.

### Зачем нужен `EXPLAIN ANALYZE`?

Чтобы сравнить предполагаемый план с фактическим выполнением и найти узкие места запроса.

## Итог

Для Python Backend-разработчика PostgreSQL — это не только хранение данных. Нужно понимать SQL, связи таблиц, индексы, транзакции, блокировки, уровни изоляции, пулы соединений и безопасную работу с запросами.

**Главная формула:**

`SQL + ограничения целостности + транзакции + индексы + анализ запросов`

Эта база знаний поможет писать корректный код, устранять проблемы производительности и уверенно отвечать на вопросы технических интервью.
