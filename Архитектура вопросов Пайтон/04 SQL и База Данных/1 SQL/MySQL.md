# MySQL — конспект для Python Backend

## Формула для собеседования

**MySQL** — реляционная система управления базами данных (RDBMS), которая хранит данные в таблицах и использует SQL для запросов и управления данными. В типичных веб-приложениях MySQL работает с движком хранения InnoDB, поддерживающим транзакции, внешние ключи и блокировки строк.

**Ключевая формула:**

`MySQL = Tables + SQL + Indexes + Transactions + InnoDB`

## Краткий ответ

- **Тип:** реляционная СУБД (RDBMS).
- **Язык запросов:** SQL.
- **Основной движок хранения:** InnoDB.
- **Транзакции:** поддерживаются InnoDB.
- **Связи:** первичные и внешние ключи.
- **Индексы:** B-Tree и другие поддерживаемые типы.
- **Масштабирование:** репликация, шардинг и другие архитектурные решения.
- **Python:** `mysql-connector-python`, `PyMySQL`, SQLAlchemy.
- **Основные сценарии:** веб-приложения, интернет-магазины, CRM, CMS, транзакционные системы.

## Ответ на собеседовании

MySQL — реляционная СУБД, которая хранит данные в таблицах с определённой структурой. Таблицы связываются через первичные и внешние ключи, а для работы с данными используется SQL.

В большинстве современных приложений основным движком хранения выступает InnoDB. Он поддерживает ACID-транзакции, внешние ключи, блокировки на уровне строк и механизм восстановления после сбоев.

Производительность MySQL зависит от правильного проектирования схемы, индексов, запросов и транзакций. В Python Backend её часто используют вместе с SQLAlchemy и драйвером MySQL для реализации CRUD-операций, бизнес-логики и транзакционных процессов.

## 1. Основные понятия

| Термин | Описание |
|---|---|
| **Database** | База данных, содержащая таблицы и другие объекты |
| **Table** | Таблица с данными |
| **Row** | Строка таблицы |
| **Column** | Столбец с определённым типом данных |
| **Primary Key (PK)** | Уникальный идентификатор строки |
| **Foreign Key (FK)** | Ссылка на ключ другой или той же таблицы |
| **Index** | Структура для ускорения поиска |
| **Constraint** | Ограничение целостности данных |
| **Transaction** | Группа операций, выполняемых как единое целое |
| **Storage Engine** | Движок, определяющий способ хранения и обработки данных |

Пример структуры:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Здесь:
- `id` — первичный ключ;
- `AUTO_INCREMENT` — автоматическая генерация числового идентификатора;
- `NOT NULL` — обязательное значение;
- `UNIQUE` — запрет дубликатов;
- `DEFAULT` — значение по умолчанию.

## 2. Типы данных

### Числовые

| Тип | Назначение |
|---|---|
| `TINYINT` | Малые целые числа |
| `INT` | Целые числа |
| `BIGINT` | Большие целые числа |
| `DECIMAL(p, s)` | Точные десятичные числа, например денежные суммы |
| `FLOAT` | Числа с плавающей точкой |
| `DOUBLE` | Числа с плавающей точкой повышенной точности |

Для денежных значений обычно выбирают `DECIMAL`, а не `FLOAT` или `DOUBLE`, поскольку двоичная арифметика с плавающей точкой может давать погрешности.

### Строковые

| Тип | Назначение |
|---|---|
| `CHAR(n)` | Строки фиксированной длины |
| `VARCHAR(n)` | Строки переменной длины |
| `TEXT` | Текстовые данные |
| `BLOB` | Двоичные данные |

### Дата и время

- `DATE` — дата.
- `TIME` — время суток или интервал времени в поддерживаемом формате.
- `DATETIME` — дата и время без автоматического преобразования часового пояса.
- `TIMESTAMP` — дата и время с преобразованием относительно часового пояса сессии в пределах поддерживаемого диапазона.

Для backend-приложений важно договориться о едином подходе к часовым поясам. Часто время в приложении хранится в UTC, а преобразование в локальное время выполняется на уровне представления.

### Другие типы

- `BOOLEAN` — псевдоним `TINYINT(1)` в MySQL; это не отдельный строгий булевый тип.
- `JSON` — хранение JSON-документов с поддерживаемыми операциями над ними.
- `ENUM` — значение из заданного списка вариантов.

Не следует выбирать `ENUM` автоматически: при часто изменяемых наборах статусов иногда удобнее справочная таблица или строковое поле с ограничениями на уровне приложения.

## 3. Основные SQL-операции

### INSERT — добавление

```sql
INSERT INTO users (name, email)
VALUES ('Илья', 'ilya@example.com');
```

### SELECT — чтение

```sql
SELECT id, name, email
FROM users
WHERE id = 1;
```

### UPDATE — изменение

```sql
UPDATE users
SET name = 'Илья Маханек'
WHERE id = 1;
```

Без `WHERE` команда может изменить все строки таблицы.

### DELETE — удаление

```sql
DELETE FROM users
WHERE id = 1;
```

Без `WHERE` будут удалены все строки, подходящие под отсутствие фильтра, то есть вся таблица будет очищена от записей.

### ORDER BY и LIMIT

```sql
SELECT id, name
FROM users
ORDER BY created_at DESC
LIMIT 10;
```

Запрос возвращает последние десять записей по времени создания. Для стабильного порядка при совпадающих временных метках полезно добавить уникальный критерий сортировки, например `id`.

## 4. JOIN — объединение таблиц

JOIN позволяет получать связанные данные из нескольких таблиц.

Пусть есть таблицы `users` и `orders`.

```sql
SELECT
    users.name,
    orders.id AS order_id,
    orders.total
FROM users
JOIN orders
    ON orders.user_id = users.id;
```

### Основные виды JOIN

| Вид | Результат |
|---|---|
| `INNER JOIN` | Только строки с совпадениями в обеих таблицах |
| `LEFT JOIN` | Все строки левой таблицы и совпадения справа |
| `RIGHT JOIN` | Все строки правой таблицы и совпадения слева |
| `CROSS JOIN` | Декартово произведение таблиц |

Пример `LEFT JOIN`:

```sql
SELECT users.name, orders.id AS order_id
FROM users
LEFT JOIN orders
    ON orders.user_id = users.id;
```

Пользователи без заказов тоже попадут в результат. Поля заказа для них будут `NULL`.

### Когда использовать JOIN

- получение заказа вместе с данными пользователя;
- построение отчётов;
- выборка связанных сущностей;
- фильтрация по данным другой таблицы.

Не нужно загружать связанные данные отдельным запросом для каждой строки без необходимости: в ORM это может приводить к проблеме N+1.

## 5. Индексы

**Индекс ускоряет поиск и сортировку, но требует места и увеличивает стоимость операций записи.**

### Создание индекса

```sql
CREATE INDEX idx_users_name
ON users (name);
```

Уникальный индекс:

```sql
CREATE UNIQUE INDEX idx_users_email
ON users (email);
```

Если для `email` уже создано ограничение `UNIQUE`, отдельный дублирующий индекс обычно не нужен.

### Составной индекс

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at);
```

Такой индекс может быть полезен для запроса:

```sql
SELECT id, total, created_at
FROM orders
WHERE user_id = 10
ORDER BY created_at DESC;
```

### Правило левого префикса

Индекс `(user_id, created_at)` обычно хорошо подходит для поиска:
- по `user_id`;
- по `user_id` и `created_at`.

Но он обычно не обеспечивает такой же эффективности для поиска только по `created_at`, поскольку это не первый столбец индекса.

### Типы индексов и нюансы

- InnoDB использует кластеризованное хранение данных по первичному ключу.
- Вторичные индексы InnoDB содержат значения индексируемых столбцов и первичного ключа.
- Для некоторых сценариев доступны полнотекстовые и пространственные индексы.
- Hash-индексы не являются обычным универсальным типом пользовательского индекса InnoDB.

### EXPLAIN

```sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 10;
```

`EXPLAIN` показывает план выполнения запроса, включая предполагаемый способ доступа к данным, выбранные индексы и оценки количества строк.

Для анализа реального выполнения в поддерживаемых версиях MySQL можно использовать `EXPLAIN ANALYZE`.

## 6. InnoDB и другие движки хранения

### InnoDB

Основной выбор для транзакционных приложений.

Поддерживает:
- ACID-транзакции;
- внешние ключи;
- блокировки строк и диапазонов в соответствующих операциях;
- MVCC;
- восстановление после сбоев;
- кластеризованный первичный ключ.

### MyISAM

Исторический движок, который не поддерживает полноценные транзакции и внешние ключи так, как это делает InnoDB. Для новых транзакционных приложений обычно выбирают InnoDB.

### Почему InnoDB важен для собеседования

Когда говорят, что MySQL поддерживает транзакции, блокировки строк и внешние ключи, важно уточнять, что эти свойства относятся прежде всего к InnoDB, а не автоматически ко всем возможным движкам хранения.

## 7. ACID и транзакции

ACID — четыре свойства транзакций.

| Свойство | Значение |
|---|---|
| **Atomicity** | Все изменения транзакции фиксируются вместе или откатываются |
| **Consistency** | Транзакция сохраняет заданные правила целостности |
| **Isolation** | Параллельные транзакции взаимодействуют согласно уровню изоляции |
| **Durability** | Зафиксированные изменения сохраняются при предусмотренных моделью сбоях |

### Пример транзакции

Перевод денег между счетами:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Если возникает ошибка, приложение должно выполнить `ROLLBACK`, а не фиксировать частично выполненную бизнес-операцию.

В реальном приложении также необходимо проверять существование счетов, достаточность средств и количество затронутых строк.

### Уровни изоляции

| Уровень | Особенности |
|---|---|
| `READ UNCOMMITTED` | Возможны грязные чтения |
| `READ COMMITTED` | Чтение только зафиксированных данных; повторное чтение может вернуть другой результат |
| `REPEATABLE READ` | Повторное чтение строки в транзакции сохраняет согласованное представление; детали диапазонных блокировок зависят от запроса и плана |
| `SERIALIZABLE` | Более строгая изоляция, возможны дополнительные блокировки и снижение параллелизма |

Для InnoDB уровень по умолчанию в типичных конфигурациях MySQL — `REPEATABLE READ`.

### COMMIT и ROLLBACK

- `COMMIT` — фиксирует изменения.
- `ROLLBACK` — отменяет незакоммиченные изменения транзакции.

## 8. Блокировки и MVCC

### MVCC

**Multi-Version Concurrency Control** позволяет читать согласованные версии данных без необходимости блокировать каждую читаемую строку на всё время чтения.

В InnoDB MVCC помогает уменьшить конфликты между обычными чтениями и изменениями данных.

### Блокировки

- **Shared lock** — блокировка для чтения в поддерживаемых сценариях.
- **Exclusive lock** — блокировка для изменения.
- **Gap lock** — блокировка промежутка ключей в определённых условиях.
- **Next-key lock** — сочетание блокировки записи и диапазона, используемое InnoDB для некоторых операций при соответствующих уровнях изоляции.

Пример блокирующего чтения:

```sql
START TRANSACTION;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

`FOR UPDATE` запрашивает блокировку выбранных записей для последующего изменения в рамках транзакции.

### Deadlock

Deadlock — взаимная блокировка, когда транзакции ждут ресурсы друг друга.

Что делать:
1. Делать транзакции короткими.
2. Блокировать сущности в согласованном порядке.
3. Создавать индексы, уменьшающие число затрагиваемых записей.
4. Обрабатывать ошибку deadlock и при необходимости повторять всю транзакцию.

## 9. Нормализация и связи

Нормализация помогает уменьшить дублирование и аномалии при изменении данных.

### Первая нормальная форма (1NF)

Значения столбцов должны соответствовать выбранной модели атомарных значений, а повторяющиеся группы не следует хранить как отдельные позиции в одной ячейке.

### Вторая нормальная форма (2NF)

Таблица находится в 1NF, и каждый неключевой атрибут зависит от полного кандидатного ключа, а не от его части.

### Третья нормальная форма (3NF)

Таблица находится во 2NF и не содержит определённых транзитивных зависимостей неключевых атрибутов от ключа.

### Пример связи один-ко-многим

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    total DECIMAL(12, 2) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Один пользователь может иметь много заказов.

Для связи многие-ко-многим обычно создают промежуточную таблицу, например `order_items` для заказов и товаров.

Нормализация не означает, что денормализация всегда запрещена: её используют осознанно для конкретных требований к производительности и чтению.

## 10. SQL-агрегации и группировка

### COUNT, SUM, AVG, MIN, MAX

```sql
SELECT
    user_id,
    COUNT(*) AS orders_count,
    SUM(total) AS total_spent,
    AVG(total) AS average_order
FROM orders
GROUP BY user_id;
```

Запрос считает количество заказов, общую сумму и средний чек каждого пользователя.

### WHERE и HAVING

- `WHERE` фильтрует строки до группировки.
- `HAVING` фильтрует группы после `GROUP BY`.

```sql
SELECT user_id, SUM(total) AS total_spent
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY user_id
HAVING SUM(total) > 10000;
```

### NULL

`NULL` означает отсутствие или неизвестность значения.

Неправильно:

```sql
WHERE deleted_at = NULL
```

Правильно:

```sql
WHERE deleted_at IS NULL
```

Для обработки `NULL` могут применяться `COALESCE()` и другие функции, но важно понимать, что `NULL` не равен нулю или пустой строке.

## 11. Подзапросы и оконные функции

### Подзапрос

```sql
SELECT name
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
);
```

Выбирает пользователей, у которых есть заказы.

### Оконная функция

```sql
SELECT
    user_id,
    id AS order_id,
    total,
    ROW_NUMBER() OVER (
        PARTITION BY user_id
        ORDER BY total DESC
    ) AS order_rank
FROM orders;
```

`ROW_NUMBER()` нумерует заказы внутри каждого пользователя по убыванию суммы.

Оконные функции позволяют выполнять вычисления над группами строк без сведения каждой группы к одной строке, как при обычной агрегации.

Поддержка конкретных функций зависит от версии MySQL; оконные функции доступны в современных версиях, начиная с MySQL 8.0.

## 12. Репликация и масштабирование

### Репликация

Репликация позволяет передавать изменения с исходного сервера на один или несколько реплик.

Типичный сценарий:
- запись направляется на primary;
- часть чтений выполняется с replicas;
- реплики используются для масштабирования чтения и повышения доступности.

Однако репликация может быть асинхронной. Поэтому сразу после записи реплика не всегда содержит последние изменения.

### Шардинг

Шардинг — разделение данных между несколькими независимыми узлами.

Он позволяет распределять объём хранения и нагрузку, но усложняет:
- распределение запросов;
- транзакции между шардами;
- уникальность ключей;
- изменение схемы;
- балансировку данных.

Шардинг не следует путать с репликацией: репликация копирует данные, а шардинг распределяет разные части данных.

### Резервное копирование

Репликация не заменяет резервные копии. Ошибочное удаление или повреждение данных может распространиться на реплики.

Для production нужны проверенные процедуры backup и restore, мониторинг репликации и план восстановления.

## 13. Оптимизация запросов

Основные практики:

1. **Использовать индексы** для часто применяемых фильтров, JOIN и сортировки.
2. **Проверять планы** через `EXPLAIN` и, где доступно, `EXPLAIN ANALYZE`.
3. **Не запрашивать лишние поля** — вместо `SELECT *` указывать необходимые столбцы.
4. **Избегать N+1** — получать связанные данные пакетно или использовать подходящие возможности ORM.
5. **Сокращать транзакции** — не держать блокировки во время сетевых запросов.
6. **Пагинировать результаты** — для больших наборов рассматривать keyset pagination вместо больших `OFFSET`.
7. **Следить за индексами** — лишние индексы увеличивают объём хранения и стоимость записи.
8. **Измерять реальную нагрузку** — план запроса и тестовые данные должны соответствовать production-сценарию.

### OFFSET и keyset pagination

Пример с OFFSET:

```sql
SELECT id, name
FROM users
ORDER BY id
LIMIT 20 OFFSET 10000;
```

При больших смещениях серверу может потребоваться обработать много строк до выдачи результата.

Keyset pagination:

```sql
SELECT id, name
FROM users
WHERE id > 10000
ORDER BY id
LIMIT 20;
```

Этот вариант эффективен при подходящем индексе и стабильном порядке по ключу. Для сложной сортировки курсор должен включать все необходимые поля сортировки.

## 14. Python Backend: MySQL и SQLAlchemy

В Python Backend часто используют SQLAlchemy, которая предоставляет ORM и Core API для работы с базами данных.

### Установка

```bash
pip install sqlalchemy pymysql
```

### Подключение

```python
import os

from sqlalchemy import create_engine, text

DATABASE_URL = os.environ["DATABASE_URL"]

engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,
)

with engine.connect() as connection:
    result = connection.execute(
        text("SELECT id, name FROM users WHERE id = :user_id"),
        {"user_id": 1},
    )

    for row in result:
        print(row.id, row.name)
```

Пример URL для PyMySQL:

```text
mysql+pymysql://user:password@localhost:3306/app_db
```

В production строку подключения нужно хранить в переменных окружения или менеджере секретов, а не в репозитории.

### Что важно знать

- `create_engine()` создаёт engine и управляет пулом соединений.
- `pool_pre_ping=True` помогает обнаруживать некоторые неработающие соединения до использования.
- `text()` позволяет выполнять параметризованный SQL.
- `:user_id` — параметр SQLAlchemy, не конкатенация пользовательского ввода.
- `engine.connect()` открывает соединение.
- Для транзакций можно использовать `engine.begin()` или ORM-сессию с корректным `commit`/`rollback`.

### Пример транзакции

```python
from sqlalchemy import text

with engine.begin() as connection:
    connection.execute(
        text("""
            UPDATE accounts
            SET balance = balance - :amount
            WHERE id = :account_id
        """),
        {"amount": 100, "account_id": 1},
    )
```

Контекст `engine.begin()` фиксирует транзакцию при успешном завершении блока и откатывает её при исключении.

В реальном финансовом сценарии необходимо дополнительно проверять баланс, количество изменённых строк и конкурентные изменения.

## 15. MySQL vs PostgreSQL

| Критерий | MySQL | PostgreSQL |
|---|---|---|
| Тип | Реляционная СУБД | Реляционная СУБД |
| SQL | Да | Да |
| Основной движок | Часто InnoDB | Единая система хранения с расширяемой архитектурой |
| Транзакции | InnoDB поддерживает ACID | Поддерживает ACID |
| Внешние ключи | InnoDB | Да |
| JSON | Тип JSON и соответствующие функции | JSON и JSONB с широкими возможностями индексации |
| Расширяемость | Зависит от доступных механизмов | Сильная поддержка расширений и пользовательских типов |
| Типичные сценарии | Веб-приложения, CMS, коммерческие сервисы | Веб-приложения, сложные запросы, аналитические и транзакционные системы |

Нельзя утверждать, что одна СУБД всегда быстрее другой. Выбор зависит от запросов, схемы, индексов, нагрузки, доступных инструментов и компетенций команды.

## 16. Частые вопросы на собеседовании

### Что такое MySQL?

Реляционная СУБД, которая хранит данные в таблицах и использует SQL для чтения и изменения данных.

### Что такое InnoDB?

Движок хранения MySQL, поддерживающий транзакции, внешние ключи, MVCC и механизмы восстановления после сбоев.

### Чем PRIMARY KEY отличается от UNIQUE?

`PRIMARY KEY` идентифицирует строку и не допускает `NULL`. В таблице может быть только один первичный ключ, который при этом может состоять из нескольких столбцов.

`UNIQUE` ограничивает дублирование значений. В MySQL уникальные индексы могут допускать несколько `NULL`, в зависимости от структуры ограничения.

### Чем DELETE отличается от TRUNCATE?

`DELETE` удаляет строки и может использовать `WHERE`.

`TRUNCATE TABLE` очищает таблицу целиком и имеет особенности DDL-операции: в частности, обычно вызывает неявную фиксацию транзакции и не используется как обычная операция построчного удаления.

### Чем WHERE отличается от HAVING?

`WHERE` фильтрует строки до группировки, а `HAVING` фильтрует результаты группировки.

### Что такое индекс?

Дополнительная структура данных, которая ускоряет поиск и некоторые операции сортировки, но требует места и увеличивает стоимость записи.

### Что такое нормализация?

Организация структуры таблиц для уменьшения дублирования и предотвращения аномалий вставки, обновления и удаления.

### Что такое MVCC?

Механизм управления параллельным доступом, при котором транзакции могут читать подходящие версии данных без блокировки каждой читаемой строки на всё время чтения.

### Что такое deadlock?

Ситуация, когда транзакции ожидают ресурсы, удерживаемые друг другом. СУБД может прервать одну транзакцию; приложение должно корректно обработать ошибку.

### Что такое N+1?

Проблема, при которой приложение выполняет один запрос для получения списка объектов и затем отдельный запрос для каждого объекта. Решается пакетной загрузкой, JOIN или подходящими стратегиями ORM.

### Чем репликация отличается от шардинга?

Репликация создаёт копии данных на других узлах. Шардинг разделяет разные части данных между узлами.

### Как защититься от SQL injection?

Использовать параметризованные запросы, не собирать SQL конкатенацией пользовательского ввода, валидировать динамические имена столбцов и таблиц и ограничивать права пользователя БД.
