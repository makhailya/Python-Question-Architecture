# 🧹 Autovacuum в PostgreSQL

## 🎯 Ответ на собеседовании

**Autovacuum** — встроенный механизм PostgreSQL, который автоматически запускает [[VACUUM]] и [[ANALYZE]] для таблиц.

Он нужен для удаления/обработки **dead tuples**, обновления статистики планировщика и предотвращения проблем с **transaction ID wraparound**.

---

## 🎤 Суперкоротко

```text
INSERT / UPDATE / DELETE
          ↓
   появляются dead tuples
          ↓
      Autovacuum
       ↙       ↘
   VACUUM     ANALYZE
      ↓           ↓
очистка       обновление
dead tuples    статистики
```

**Главная идея:**

> Autovacuum автоматически обслуживает таблицы PostgreSQL: очищает последствия MVCC и обновляет статистику для планировщика.

---

# 1. 🧬 Почему вообще нужен Autovacuum

PostgreSQL использует **MVCC**.

При `UPDATE` старая версия строки не просто заменяется новой.

Упрощённо:

```text
UPDATE users
SET name = 'Petr'
WHERE id = 1;
```

происходит примерно так:

```text
старая версия строки
       ↓
становится невидимой
       ↓
появляется новая версия строки
```

Старая версия называется **dead tuple**, когда она больше не нужна никакой транзакции.

Если их не обслуживать:

```text
dead tuples
     ↓
занимают место
     ↓
table bloat
     ↓
хуже эффективность работы
```

---

# 2. 🧹 VACUUM

Autovacuum может автоматически запускать `VACUUM`.

`VACUUM`:

* обрабатывает dead tuples;
* освобождает место для повторного использования внутри таблицы;
* обновляет visibility map;
* участвует в предотвращении transaction ID wraparound.

Важно:

> Обычный `VACUUM` обычно **не уменьшает физический размер файла таблицы** и не возвращает освободившееся место ОС.

Например:

```text
Таблица
100 GB
  ↓
удалили много данных
  ↓
VACUUM
  ↓
внутри таблицы появилось
свободное место для повторного использования
```

Но файл может по-прежнему занимать около:

```text
100 GB
```

---

# 3. 📊 ANALYZE

Autovacuum также может запускать `ANALYZE`.

`ANALYZE` собирает статистику о данных, которая нужна **query planner**.

Например, PostgreSQL должен решить:

```text
Seq Scan
    или
Index Scan?
```

Для этого ему нужны оценки:

* количества строк;
* количества различных значений;
* распределения значений;
* NULL;
* наиболее частых значений;
* корреляции и других статистических характеристик.

Устаревшая статистика может привести к плохому плану выполнения.

---

# 4. 🔄 VACUUM vs ANALYZE

|                                                | VACUUM               | ANALYZE               |
| ---------------------------------------------- | -------------------- | --------------------- |
| Основная задача                                | Работа с dead tuples | Обновление статистики |
| Связан с MVCC                                  | ✅                    | Косвенно              |
| Помогает planner                               | Косвенно             | ✅                     |
| Освобождает место для повторного использования | ✅                    | ❌                     |
| Уменьшает файл таблицы                         | Обычно нет           | ❌                     |
| Запускается autovacuum                         | ✅                    | ✅                     |

Поэтому:

```text
Autovacuum
├── VACUUM
└── ANALYZE
```

---

# 5. ⚙️ Когда Autovacuum запускается

Autovacuum не ждёт, пока таблица полностью заполнится dead tuples.

PostgreSQL использует пороги, зависящие от:

* размера таблицы;
* количества изменённых/удалённых строк;
* настроек autovacuum;
* индивидуальных настроек таблицы.

Упрощённо:

```text
изменения таблицы
       ↓
достигнут порог
       ↓
autovacuum запускает VACUUM
```

Для `ANALYZE` используется отдельный порог изменения данных.

---

# 6. 🧮 Упрощённая формула

Для `VACUUM` концептуально:

```text
порог ≈
autovacuum_vacuum_threshold
+
autovacuum_vacuum_scale_factor × размер таблицы
```

Например:

```text
threshold = 50
scale_factor = 0.2
```

Для таблицы на 10 000 строк:

```text
50 + 0.2 × 10 000
= 2050
```

После достаточного количества изменений autovacuum получает основание запустить `VACUUM`.

Это **упрощённая модель**; фактическое поведение зависит от версии PostgreSQL и дополнительных настроек.

---

# 7. 🏭 Почему для больших таблиц важны настройки

Представим таблицу:

```text
100 000 000 строк
```

Если используется большой `scale_factor`, порог может получиться очень большим.

Например, условные:

```text
0.2 × 100 000 000
=
20 000 000
```

То есть ждать до очистки такого количества изменений может быть невыгодно.

Для больших и активно изменяемых таблиц часто настраивают autovacuum отдельно.

Например:

```python
ALTER TABLE orders
SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_analyze_scale_factor = 0.005
);
```

Конкретные значения подбираются по нагрузке и наблюдаемым метрикам, а не копируются вслепую.

---

# 8. 🚨 Autovacuum и Transaction ID Wraparound

Это одна из важных причин, почему autovacuum нельзя просто отключать.

PostgreSQL использует **transaction IDs**.

Они имеют ограниченный диапазон и со временем могут приблизиться к wraparound.

Поэтому PostgreSQL должен периодически выполнять **freezing** старых tuple.

Autovacuum участвует в этом процессе.

Если PostgreSQL видит опасность transaction ID wraparound, обслуживание таблиц становится критически важным.

---

# 9. 🧊 Freeze

При работе PostgreSQL старые версии строк могут получить состояние, при котором их старый transaction ID больше не нужно хранить обычным способом.

Это называется **freezing**.

Упрощённо:

```text
старые tuple
     ↓
freeze
     ↓
их старые transaction ID
не создают риск wraparound
```

Поэтому autovacuum выполняет не только обычную очистку dead tuples, но и важную работу по предотвращению wraparound.

---

# 10. 👀 Autovacuum и Index Only Scan

Autovacuum выполняет `VACUUM`, который обновляет **visibility map**.

Это важно для:

```text
Index Only Scan
```

Если PostgreSQL знает, что страницы таблицы содержат только tuple, видимые всем нужным транзакциям, ему в некоторых случаях не требуется обращаться к heap.

Поэтому:

```text
VACUUM
 ↓
visibility map
 ↓
Index Only Scan может работать эффективнее
```

---

# 11. 📈 Autovacuum и Bloat

Если dead tuples накапливаются:

```text
UPDATE / DELETE
       ↓
dead tuples
       ↓
bloat
```

Autovacuum помогает контролировать этот рост.

Проверить состояние таблиц можно, например:

```python
SELECT
    relname,
    n_live_tup,
    n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Если у таблицы постоянно растёт `n_dead_tup`, стоит разбираться:

* хватает ли autovacuum;
* не слишком ли высокий порог;
* нет ли долгих транзакций;
* насколько интенсивно изменяется таблица;
* хватает ли ресурсов autovacuum.

---

# 12. ⏳ Долгие транзакции

Особенно важный момент:

```text
долгая транзакция
       ↓
старый snapshot
       ↓
некоторые старые версии строк
ещё могут быть нужны
       ↓
VACUUM не может удалить их полностью
```

Поэтому даже хорошо настроенный autovacuum не всегда может эффективно убрать dead tuples.

Долгие транзакции могут приводить к:

```text
bloat
+
росту таблиц
+
росту нагрузки
```

---

# 13. ❌ Autovacuum ≠ VACUUM FULL

Это важно различать.

### Autovacuum

```text
автоматическое обслуживание
        ↓
обычный VACUUM
+
ANALYZE
```

### VACUUM FULL

```text
переписывает таблицу
        ↓
сильно компактизирует
        ↓
может вернуть место ОС
```

`VACUUM FULL` требует сильной блокировки таблицы и является тяжёлой операцией.

Поэтому его **не используют как обычную ежедневную замену autovacuum**.

---

# 14. ⚠️ Можно ли отключить Autovacuum?

Технически настройки позволяют это сделать.

Но обычно это плохая идея для обычных таблиц.

Без регулярного обслуживания могут возникнуть:

```text
dead tuples
      ↓
bloat
      ↓
рост таблиц
      ↓
ухудшение производительности
```

А в долгосрочной перспективе существует риск проблем с:

```text
transaction ID wraparound
```

Если autovacuum отключают для конкретной таблицы, нужно понимать, чем и как будет выполняться необходимое обслуживание.

---

# 15. 🧩 Autovacuum — это отдельный процесс

Autovacuum — автоматический механизм PostgreSQL, который запускает **autovacuum workers** для обслуживания таблиц.

Упрощённо:

```text
PostgreSQL
    │
    ▼
Autovacuum Launcher
    │
    ├── Worker → table A
    ├── Worker → table B
    └── Worker → table C
```

Количество одновременно работающих workers также регулируется настройками.

---

# 16. 🔬 Как посмотреть настройки

Например:

```python
SHOW autovacuum;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_analyze_threshold;
SHOW autovacuum_analyze_scale_factor;
SHOW autovacuum_max_workers;
```

# 17. 🧠 Autovacuum в общей картине PostgreSQL

```text
                 PostgreSQL
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
        MVCC                    Planner
          │                       │
          ▼                       ▼
    dead tuples               statistics
          │                       │
          ▼                       ▼
       VACUUM                  ANALYZE
          │                       │
          └───────────┬───────────┘
                      ▼
                 AUTOVACUUM
```

То есть Autovacuum связывает две важные задачи:

```text
VACUUM
→ обслуживание MVCC

ANALYZE
→ актуальная статистика для planner
```

# 🎯 Главное

```text
AUTOVACUUM
│
├── автоматически запускает VACUUM
│     ├── обрабатывает dead tuples
│     ├── помогает контролировать bloat
│     ├── обновляет visibility map
│     └── участвует в freeze
│
├── автоматически запускает ANALYZE
│     └── обновляет статистику planner
│
└── помогает предотвращать
    transaction ID wraparound
```

### Формула для собеседования

> **Autovacuum — встроенный механизм PostgreSQL для автоматического обслуживания таблиц. Он запускает VACUUM для обработки dead tuples, обновления visibility map и freeze, а также ANALYZE для обновления статистики планировщика. Это необходимо для контроля bloat, корректной работы MVCC и предотвращения transaction ID wraparound.**

### Самая короткая версия:

```text
Autovacuum
→ автоматически обслуживает БД
→ VACUUM + ANALYZE
→ dead tuples + статистика + freeze
→ меньше bloat и риск wraparound
```
