# 📝 WAL (журнал предзаписи) в PostgreSQL

## 🎯 Ответ на собеседовании

**WAL (Write-Ahead Log, журнал предзаписи)** — это журнал изменений PostgreSQL, в который информация о изменениях записывается **до того, как изменённые страницы данных будут гарантированно записаны на диск**.

WAL обеспечивает прежде всего **Durability** в [[ACID]] и позволяет PostgreSQL **восстановить состояние БД после сбоя**.

---

## 🎤 Суперкоротко

```text
Изменение данных
      ↓
WAL
      ↓
COMMIT
      ↓
данные могут быть записаны
в основные файлы таблиц позже
```

Если сервер упал:

```text
Основные данные
      +
WAL
      ↓
Recovery
      ↓
восстановление состояния БД
```

**Главная идея:**

> Сначала надёжно фиксируем информацию об изменении в WAL, а уже потом записываем изменённые страницы таблиц на диск.

---

# 1. 💡 Зачем нужен WAL

Представим:

```text
UPDATE users
SET balance = 1000
WHERE id = 1;
```

PostgreSQL изменяет данные в памяти (`shared buffers`).

Но записывать каждую изменённую страницу таблицы сразу на диск было бы дорого.

Вместо этого PostgreSQL использует WAL.

Упрощённо:

```text
Изменение
   ↓
страница в памяти
   +
WAL-запись
   ↓
COMMIT
```

WAL позволяет сначала надёжно сохранить информацию о произведённом изменении.

---

# 2. ⏱️ Почему называется Write-Ahead Log

**Write-Ahead** означает:

> «Запиши журнал сначала».

Перед тем как изменённая страница данных будет записана на диск, соответствующая WAL-информация должна быть записана в WAL.

Упрощённо:

```text
❌ Неправильно:

Изменённые данные
       ↓
диск

WAL
       ↓
потом
```

Правильная последовательность:

```text
Изменение
   ↓
WAL
   ↓
основные данные
```

Это и есть принцип **Write-Ahead Logging**.

---

# 3. 💾 WAL и COMMIT

Рассмотрим транзакцию:

```python
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Упрощённо PostgreSQL:

```text
1. Изменяет страницы в памяти
2. Формирует WAL-записи
3. При COMMIT обеспечивает запись необходимого WAL
4. После успешного COMMIT транзакция считается зафиксированной
5. Изменённые страницы таблиц могут быть записаны на диск позже
```

Поэтому **COMMIT не означает, что все изменённые страницы таблиц уже физически записаны в свои файлы**.

---

# 4. 🚨 Что происходит при сбое

Представим:

```text
UPDATE
   ↓
изменение в памяти
   ↓
WAL записан
   ↓
сервер упал
```

Часть изменённых страниц таблиц могла ещё не попасть на диск.

При запуске PostgreSQL выполняется **crash recovery**.

Упрощённо:

```text
Файлы данных
     +
WAL
     ↓
Recovery
     ↓
воспроизведение необходимых изменений
```

PostgreSQL использует WAL, чтобы привести состояние данных к корректному состоянию.

---

# 5. 🛡️ WAL и Durability

WAL напрямую связан с буквой **D** в ACID:

```text
ACID

A — Atomicity
C — Consistency
I — Isolation
D — Durability
```

**Durability** означает:

> После успешного COMMIT изменения не должны исчезнуть из-за обычного сбоя процесса или питания.

WAL является одним из ключевых механизмов, обеспечивающих эту гарантию в PostgreSQL.

---

# 6. 🧩 WAL не является копией таблицы

Важно не путать WAL с резервной копией.

WAL:

```text
журнал изменений
```

а не:

```text
полная копия всех таблиц
```

Концептуально:

```text
Таблица:
id=1 balance=1000

WAL:
"изменение, необходимое для перехода
из предыдущего состояния в новое"
```

Конкретное содержимое WAL состоит из низкоуровневых записей, необходимых для восстановления.

---

# 7. 🔄 WAL и VACUUM

WAL связан не только с обычными `INSERT`, `UPDATE`, `DELETE`.

Некоторые действия PostgreSQL, изменяющие состояние данных/структур на диске, также порождают WAL-записи.

Поэтому:

```text
VACUUM
   ↓
изменения страниц / метаданных
   ↓
WAL
```

При этом важно не смешивать задачи:

```text
WAL
→ журналирование изменений
→ recovery

VACUUM
→ обслуживание MVCC
→ dead tuples
```

---

# 8. 📈 WAL и репликация

WAL используется PostgreSQL и для **физической репликации**.

Упрощённо:

```text
                 Primary
                    │
                    │ WAL
                    ▼
                 Replica
                    │
                    ▼
                replay WAL
```

Primary генерирует WAL.

Replica получает WAL и воспроизводит изменения.

Таким образом, replica может поддерживать состояние, близкое к состоянию Primary.

---

# 9. 🔁 WAL и Point-in-Time Recovery

WAL также является основой **Point-in-Time Recovery (PITR)**.

Можно иметь:

```text
base backup
+
архив WAL
```

и восстановить БД не только на момент создания backup, но и на определённый момент времени в пределах доступной цепочки WAL.

Упрощённо:

```text
Base Backup
    +
WAL 1
    +
WAL 2
    +
WAL 3
    +
WAL 4
    ↓
восстановление
    ↓
состояние БД на нужный момент
```

Это особенно важно для восстановления после серьёзного сбоя или ошибочного изменения данных.

---

# 10. 📦 WAL и файлы WAL

WAL хранится в специальной области PostgreSQL.

Основной каталог:

```text
pg_wal/
```

В нём находятся WAL-сегменты.

Их размер и структура зависят от версии PostgreSQL и настроек.

Важно понимать:

```text
WAL
≠
табличные файлы
```

Это отдельный поток журналирования изменений.

---

# 11. 🧠 WAL и Buffer Cache

В PostgreSQL данные сначала работают через память:

```text
Application
     ↓
PostgreSQL
     ↓
Shared Buffers
     ↓
Disk
```

WAL идёт отдельным логическим потоком:

```text
Изменение
   ├──────────────→ Shared Buffers
   │
   └──────────────→ WAL
```

Перед надёжной фиксацией транзакции необходимый WAL должен быть записан достаточно надёжно.

А изменённые страницы таблиц могут быть сброшены на диск позже.

---

# 12. ⚡ Почему это эффективно

Если бы PostgreSQL при каждом изменении сразу синхронно записывал соответствующие страницы таблиц:

```text
UPDATE
 ↓
запись большой страницы
 ↓
fsync
 ↓
следующее изменение
```

это было бы дорого.

WAL позволяет работать с последовательным журналом изменений:

```text
Изменения
   ↓
последовательная запись WAL
   ↓
данные таблиц записываются позже
```

Это одна из причин, почему WAL является эффективным механизмом обеспечения надёжности.

---

# 13. ⚠️ WAL занимает место

Чем больше изменений происходит в БД, тем больше WAL может генерироваться.

На объём WAL влияют, среди прочего:

* количество изменений;
* характер операций;
* размер изменяемых данных;
* настройки;
* checkpoint;
* репликация;
* архивирование WAL.

Поэтому необходимо контролировать:

```text
WAL volume
+
disk usage
+
replication lag
+
archiving
```

---

# 14. ⏸️ Checkpoint и WAL

**Checkpoint** — момент, когда PostgreSQL обеспечивает запись достаточно большого набора изменённых данных из памяти на диск и фиксирует точку, от которой recovery может продолжаться более эффективно.

Упрощённо:

```text
Изменения
   ↓
WAL WAL WAL WAL
   ↓
Checkpoint
   ↓
много изменённых страниц
записано на диск
```

После сбоя PostgreSQL не обязательно должен проигрывать весь WAL с самого начала существования БД.

Он использует checkpoint как одну из опорных точек восстановления.

---

# 15. 🔗 WAL и репликация vs backup

WAL участвует сразу в нескольких важных механизмах:

```text
                    WAL
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
 Crash Recovery   Replication    PITR
        │            │            │
     сбой БД       Replica      восстановление
```

Но:

> **WAL сам по себе не заменяет полноценный backup.**

Для надёжного восстановления обычно нужна комбинация:

```text
Base Backup
+
WAL Archive
```

---

# 16. 🧠 WAL и MVCC

WAL и MVCC — разные механизмы, но они работают вместе.

### MVCC

Определяет:

```text
какую версию строки
видит транзакция
```

### WAL

Обеспечивает:

```text
как восстановить изменения
после сбоя
```

Упрощённо:

```text
MVCC
→ версии строк
→ snapshots
→ visibility

WAL
→ журнал изменений
→ recovery
→ durability
```

---

# 17. 🎯 Типичный вопрос на собеседовании

### Что произойдёт, если PostgreSQL упадёт после COMMIT, но до записи изменённой страницы таблицы?

Ответ:

> Если необходимая WAL-информация была надёжно записана, после перезапуска PostgreSQL выполнит recovery и воспроизведёт необходимые изменения из WAL. Поэтому изменение, подтверждённое COMMIT, не зависит от того, успела ли соответствующая страница таблицы попасть на диск до сбоя.

---

# 18. ⚠️ WAL ≠ лог приложения

Не следует путать:

```text
Application logs
```

и:

```text
PostgreSQL WAL
```

Лог приложения:

```text
"User 123 created order"
```

WAL:

```text
низкоуровневые записи изменений,
необходимые PostgreSQL для recovery
```

WAL предназначен для внутренней надёжности и восстановления PostgreSQL.

```text
WAL
│
├── Write-Ahead Log
│
├── журнал предзаписи
│
├── фиксирует информацию об изменениях
│   до записи соответствующих страниц данных
│
├── обеспечивает Durability
│
├── используется при crash recovery
│
├── является основой физической репликации
│
├── используется для PITR
│
└── работает вместе с checkpoints
```

### Формула для собеседования

> **WAL — Write-Ahead Log, журнал предзаписи PostgreSQL. Перед записью изменённых страниц данных PostgreSQL сначала обеспечивает запись соответствующей информации в WAL. Это позволяет после сбоя восстановить состояние БД, а также использовать WAL для физической репликации и Point-in-Time Recovery.**

```text
Изменение
    ↓
WAL
    ↓
COMMIT
    ↓
данные на диск позже
    ↓
Crash
    ↓
Recovery из WAL
```
