# 🔄 MVCC (Multiversion Concurrency Control)

## 🎯 Ответ на собеседовании

**MVCC (Multiversion Concurrency Control)** — механизм управления конкурентным доступом к данным, при котором база данных хранит несколько версий строк, чтобы разные транзакции могли видеть данные, соответствующие их **снимку (snapshot)**.

В PostgreSQL MVCC позволяет транзакциям **читать данные без блокировки записей**, которые изменяются другими транзакциями, в большинстве обычных случаев.

При `UPDATE` PostgreSQL не просто изменяет существующую строку «на месте». Создаётся новая версия строки, а старая версия сохраняется до тех пор, пока она нужна для других транзакций.

Упрощённо:

```text
Старая версия строки
        ↓
    UPDATE
        ↓
Новая версия строки
```

Каждая транзакция определяет, **какие версии строк ей разрешено видеть**.

---

## 🎤 Суперкоротко

> **MVCC** — механизм многоверсионного управления конкурентным доступом. PostgreSQL хранит версии строк и использует снимки транзакций, поэтому читатели обычно не блокируют писателей, а каждая транзакция видит согласованный набор данных согласно своему уровню изоляции.

---

## 📌 Зачем нужен MVCC

Представим:

```text
Транзакция A: читает строку
Транзакция B: изменяет эту строку
```

Без многоверсионности возникла бы проблема:

```text
A читает
   ↓
B блокирует строку
   ↓
A ждёт
```

MVCC позволяет использовать разные версии:

```text
          строка
             ↓
      ┌──────┴──────┐
      ↓             ↓
старая версия   новая версия
      ↓             ↓
  транзакция A   транзакция B
```

Поэтому чтение и изменение одной строки могут в значительной степени выполняться параллельно.

---

# 🧱 Как MVCC работает в PostgreSQL

В PostgreSQL строка имеет служебную информацию о её версии.

В частности, важны:

```text
xmin
xmax
```

Упрощённо:

* `xmin` — транзакция, которая создала версию строки;
* `xmax` — транзакция, которая сделала версию невидимой, например удалением или обновлением.

Важно: `xmin` и `xmax` — это **идентификаторы транзакций**, а не время создания/изменения строки.

---

## 🔄 Что происходит при UPDATE

Допустим, есть:

```text
id = 1
balance = 100
```

Выполняем:

```python
UPDATE accounts
SET balance = 200
WHERE id = 1;
```

Упрощённо PostgreSQL делает:

```text
Старая версия:

id = 1
balance = 100
     ↓
   UPDATE
     ↓
Новая версия:

id = 1
balance = 200
```

Старая версия не исчезает мгновенно.

Она может быть нужна транзакциям, которые начали работать со старым snapshot.

---

# 📸 Snapshot

**Snapshot** — это представление о том, какие транзакции активны и какие версии строк доступны конкретной транзакции.

Можно представить:

```text
Транзакция A
    ↓
создала snapshot
    ↓
видит версии, доступные
этому snapshot
```

Если после создания snapshot другая транзакция изменит строку, первая транзакция не обязательно сразу увидит новую версию.

Это зависит от уровня изоляции.

---

# 🧩 Пример с двумя транзакциями

Предположим:

```text
balance = 100
```

### Транзакция A

```python
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
```

Получает:

```text
100
```

### Транзакция B

```python
BEGIN;

UPDATE accounts
SET balance = 200
WHERE id = 1;

COMMIT;
```

Теперь существует новая версия:

```text
старое → 100
новое  → 200
```

Что увидит транзакция A, зависит от её уровня изоляции.

При стандартном для PostgreSQL:

```text
READ COMMITTED
```

каждая команда `SELECT` получает новый snapshot.

Поэтому новый `SELECT` после `COMMIT` транзакции B уже может увидеть:

```text
200
```

---

# 🔐 MVCC и блокировки

Важно не говорить:

> «MVCC полностью устраняет блокировки».

Это неправильно.

MVCC **уменьшает необходимость блокировать строки для чтения**, но блокировки всё равно существуют.

Например, блокировки нужны при:

* изменении одних и тех же данных;
* некоторых DDL-операциях;
* явном `SELECT ... FOR UPDATE`;
* конфликтующих операциях;
* изменении структуры базы.

Поэтому:

```text
MVCC ≠ отсутствие блокировок
```

Правильнее:

> MVCC позволяет большинству обычных операций чтения не блокировать изменяемые строки.

---

# 🆚 Обычная модель vs MVCC

### Без многоверсионности

Упрощённо:

```text
Writer
   ↓
LOCK
   ↓
Reader ждёт
```

### MVCC

```text
             строка
               ↓
       ┌───────┴───────┐
       ↓               ↓
 старая версия     новая версия
       ↓               ↓
    Reader          Writer
```

Читатель может использовать подходящую ему версию.

---

# 🎯 MVCC и уровни изоляции

MVCC тесно связан с **изоляцией транзакций**.

Основные уровни:

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

В PostgreSQL:

```text
READ UNCOMMITTED
```

фактически работает как:

```text
READ COMMITTED
```

---

## READ COMMITTED

В PostgreSQL это стандартный уровень.

Каждая команда получает собственный snapshot.

Например:

```text
Transaction A
    SELECT → 100

Transaction B
    UPDATE → 200
    COMMIT

Transaction A
    SELECT → 200
```

То есть два `SELECT` внутри одной транзакции могут увидеть разные версии данных.

Это связано с **non-repeatable read**.

---

## REPEATABLE READ

При `REPEATABLE READ` транзакция работает с согласованным snapshot.

Упрощённо:

```text
BEGIN
  ↓
snapshot
  ↓
SELECT → 100

другая транзакция меняет → 200

SELECT → 100
```

Транзакция продолжает видеть данные согласно своему snapshot.

---

## SERIALIZABLE

Самый строгий уровень.

Цель:

> результат конкурентного выполнения должен быть эквивалентен некоторому последовательному выполнению транзакций.

PostgreSQL использует механизмы контроля сериализуемости поверх MVCC.

При конфликте транзакция может завершиться ошибкой сериализации:

```text
could not serialize access
```

Тогда приложение обычно должно повторить транзакцию.

---

# 🗑️ Почему старые версии нужно удалять

Если после `UPDATE` старая версия всегда оставалась бы навсегда:

```text
100
200
300
400
500
...
```

таблица постоянно росла бы.

Поэтому PostgreSQL периодически удаляет версии строк, которые больше не нужны никакой транзакции.

Этим занимается:

```text
VACUUM
```

---

# 🧹 MVCC и VACUUM

Из-за MVCC PostgreSQL получает важную особенность:

```text
UPDATE
   ↓
создаётся новая версия
   ↓
старая версия становится неактуальной
   ↓
старую версию позже можно очистить
   ↓
VACUUM
```

Поэтому MVCC напрямую связан с **VACUUM**.

Если старые версии долго нельзя удалить, возникает:

```text
bloat
```

— разрастание таблиц и индексов из-за большого количества устаревших версий.

---

# 💡 Почему длинные транзакции опасны

Представим:

```text
Transaction A
BEGIN
   ↓
долго не завершается
```

В это время другие транзакции постоянно обновляют строки:

```text
100 → 200 → 300 → 400 → 500
```

Некоторые старые версии могут всё ещё требоваться для snapshot долгой транзакции.

Поэтому PostgreSQL не может сразу удалить их.

Результат:

```text
длинная транзакция
       ↓
старые версии дольше живут
       ↓
VACUUM не может всё очистить
       ↓
больше bloat
```

---

# 🔗 MVCC и DELETE

`DELETE` также не означает мгновенное физическое удаление строки.

Упрощённо:

```python
DELETE FROM users
WHERE id = 10;
```

Старая версия становится невидимой для будущих snapshot.

Но физическое место строки может быть очищено позже:

```text
DELETE
  ↓
строка становится невидимой
  ↓
VACUUM
  ↓
очистка
```

---

# 🔗 MVCC и INSERT

При `INSERT` создаётся новая версия строки.

Упрощённо:

```text
INSERT
  ↓
новая строка
  ↓
xmin = текущая транзакция
```

Другие транзакции увидят её только тогда, когда она станет видимой согласно правилам snapshot и статусу транзакции.

---

# 📊 MVCC и видимость строк

Очень упрощённо PostgreSQL при чтении проверяет:

```text
Какая транзакция создала версию?
        ↓
xmin

Какая транзакция сделала её невидимой?
        ↓
xmax

Эти транзакции уже завершены?
        ↓
Snapshot их видит?
        ↓
Можно ли показывать эту версию?
```

Поэтому PostgreSQL может выбрать подходящую версию одной логической строки.

---

# 🔄 Цепочка версий

Если строка много раз обновлялась:

```text
version 1
   ↓ UPDATE
version 2
   ↓ UPDATE
version 3
   ↓ UPDATE
version 4
```

Для разных snapshot потенциально могут быть видимы разные версии.

После того как старые версии больше никому не нужны:

```text
VACUUM
   ↓
очистка старых tuple
```

---

# 🧠 MVCC и «грязное чтение»

**Dirty Read** — когда транзакция видит незакоммиченные изменения другой транзакции.

В PostgreSQL обычное чтение не позволяет просто увидеть незакоммиченные изменения другой транзакции.

Например:

```text
Transaction A:
UPDATE balance = 500
но COMMIT ещё не был выполнен

Transaction B:
SELECT balance
```

B не должна просто увидеть незакоммиченное `500`.

Это одна из гарантий изоляции.

---

# ⚠️ MVCC не решает все проблемы конкурентности

Например, возможна ситуация:

```text
Баланс = 100

Transaction A:
прочитала 100

Transaction B:
прочитала 100

A:
записала 50

B:
записала 70
```

Если бизнес-операция неправильно спроектирована, можно получить логическую проблему конкурентного доступа.

Для подобных случаев могут использоваться:

```text
SELECT ... FOR UPDATE
```

или:

```text
UPDATE ... WHERE ...
```

или оптимистическая блокировка / version column, либо более высокий уровень изоляции — в зависимости от задачи.

---

# 🆚 MVCC и SELECT FOR UPDATE

Обычный:

```python
SELECT *
FROM accounts
WHERE id = 1;
```

— читает подходящую версию согласно snapshot.

А:

```python
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

— не просто читает строку, а устанавливает блокировку, чтобы другие конфликтующие операции не могли свободно изменить её до завершения транзакции.

То есть:

```text
MVCC
→ обычное согласованное чтение

FOR UPDATE
→ чтение + блокировка для последующего изменения
```

---

# 🚀 Преимущества MVCC

### 1. Чтение не блокирует обычную запись

Это повышает конкурентность.

### 2. Запись не блокирует обычное чтение

Читатель может использовать подходящую версию строки.

### 3. Согласованные snapshot

Транзакция получает определённое представление данных.

### 4. Хорошая параллельность

Много читателей и писателей могут работать одновременно.

---

# ⚠️ Недостатки MVCC

Главная цена — **хранение нескольких версий строк**.

Это приводит к:

* дополнительному расходу места;
* необходимости `VACUUM`;
* возможному bloat;
* дополнительной работе при обновлениях;
* проблемам при долгих транзакциях.

Поэтому MVCC — не «бесплатный» механизм.

---

# 🧩 MVCC, Snapshot и VACUUM

Эти три понятия удобно связывать вместе:

```text
                 MVCC
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
   Версии строк          Snapshot
        │                   │
        │             определяет,
        │             что видно
        │                   │
        └─────────┬─────────┘
                  ↓
        Старые версии больше
        никому не нужны
                  ↓
               VACUUM
                  ↓
          очистка старых версий
```

# 🎤 Частые вопросы на собеседовании

### Что такое MVCC?

> Это механизм многоверсионного управления конкурентным доступом, при котором база хранит версии строк и использует snapshot, чтобы транзакции могли работать с согласованным представлением данных.

### Зачем нужен MVCC?

> Чтобы повысить конкурентность. В частности, обычные чтения могут выполняться без блокировки строк, изменяемых другими транзакциями.

### Создаётся ли новая версия строки при UPDATE в PostgreSQL?

> Да. PostgreSQL использует модель MVCC, поэтому обновление приводит к появлению новой версии tuple, а старая версия остаётся до тех пор, пока она нужна.

### Зачем нужен VACUUM?

> Для очистки старых версий строк, которые больше не нужны ни одной транзакции, и для обслуживания таблиц после работы MVCC.

### Почему долгие транзакции опасны?

> Они могут удерживать старые snapshot, из-за чего PostgreSQL дольше не может удалить старые версии строк. Это может приводить к накоплению dead tuples и bloat.

### MVCC полностью исключает блокировки?

> Нет. MVCC уменьшает необходимость блокировок для обычного чтения, но блокировки всё равно используются для конфликтующих изменений, явных блокировок и некоторых других операций.

### Что такое snapshot?

> Это представление о состоянии транзакций, относительно которого PostgreSQL определяет, какие версии строк видимы конкретной транзакции.

```text

→ создаётся новая версия строки.

Старая версия
→ может быть нужна другим snapshot.

Snapshot
→ определяет, какие версии транзакция видит.

Обычное чтение
→ обычно не блокирует изменяемые строки.

VACUUM
→ очищает старые версии, которые больше не нужны.

Длинные транзакции
→ могут мешать очистке старых версий
→ могут приводить к bloat.

MVCC ≠ отсутствие блокировок.

MVCC тесно связан с:
- транзакциями;
- snapshot;
- уровнями изоляции;
- xmin/xmax;
- VACUUM;

```
