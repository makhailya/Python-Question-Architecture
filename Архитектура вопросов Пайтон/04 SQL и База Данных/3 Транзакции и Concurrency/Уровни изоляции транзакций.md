# 🔐 Уровни изоляции транзакций

## 🎯 Ответ на собеседовании

**Уровень изоляции транзакции** определяет, насколько одна транзакция изолирована от изменений, выполняемых другими параллельными транзакциями.

Чем выше уровень изоляции, тем больше гарантий получает транзакция относительно конкурентных изменений, но обычно это достигается за счёт большей стоимости или большего количества конфликтов.

Стандартно выделяют 4 уровня:

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

В PostgreSQL фактически используются:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

`READ UNCOMMITTED` в PostgreSQL фактически работает как `READ COMMITTED`.

---

## 🎤 Суперкоротко

> Уровни изоляции определяют, какие изменения других транзакций может видеть текущая транзакция и какие аномалии конкурентного выполнения допускаются. В PostgreSQL по умолчанию используется `READ COMMITTED`, где каждый SQL-запрос получает собственный snapshot. Более строгие уровни — `REPEATABLE READ` и `SERIALIZABLE`.

---

# 📊 Четыре уровня

| Уровень          | Dirty Read | Non-repeatable Read | Phantom Read |
| ---------------- | ---------- | ------------------- | ------------ |
| READ UNCOMMITTED | ❌*         | ✅                   | ✅            |
| READ COMMITTED   | ❌          | ✅                   | ✅            |
| REPEATABLE READ  | ❌          | ❌                   | ❌**          |
| SERIALIZABLE     | ❌          | ❌                   | ❌            |

* В PostgreSQL `READ UNCOMMITTED` фактически работает как `READ COMMITTED`.

** В PostgreSQL `REPEATABLE READ` не допускает phantom reads в обычном смысле за счёт snapshot isolation, хотя стандарт SQL формулирует гарантии несколько иначе.

---

# 1️⃣ READ UNCOMMITTED

Самый слабый уровень изоляции.

Теоретически позволяет одной транзакции читать **незакоммиченные изменения** другой транзакции.

Это называется:

```text id="qf8f0h"
Dirty Read
```

Например:

```text id="5q6m3k"
Transaction A
    ↓
UPDATE balance = 500
    ↓
COMMIT ещё нет

Transaction B
    ↓
SELECT balance
    ↓
может увидеть 500
```

Если A выполнит:

```text id="h5y8q0"
ROLLBACK
```

получается, что B прочитала данные, которые никогда не были зафиксированы.

---

## 🐘 PostgreSQL

В PostgreSQL:

```python id="fj4x5r"
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

фактически работает как:

```text id="1x4g4s"
READ COMMITTED
```

То есть PostgreSQL **не допускает dirty read**.

На собеседовании лучше сказать:

> В стандарте SQL `READ UNCOMMITTED` допускает dirty read, но PostgreSQL фактически реализует его как `READ COMMITTED`.

---

# 2️⃣ READ COMMITTED

Это **уровень изоляции по умолчанию в PostgreSQL**.

Главная особенность:

> **Каждая команда получает собственный snapshot.**

Например:

```text id="rx8j1a"
Transaction A:

BEGIN;

SELECT balance;
→ 100
```

Параллельно:

```text id="kzqf8h"
Transaction B:

UPDATE accounts
SET balance = 200;

COMMIT;
```

После этого A выполняет:

```text id="4jz4cl"
SELECT balance;
→ 200
```

То есть два `SELECT` внутри одной транзакции могут увидеть разные данные.

Это называется:

```text id="1xjyd9"
Non-repeatable Read
```

---

# 🔄 READ COMMITTED

Упрощённо:

```text id="2x9j0p"
Transaction A

SELECT → snapshot 1
             ↓
        balance = 100

Transaction B
UPDATE → 200
COMMIT

Transaction A

SELECT → snapshot 2
             ↓
        balance = 200
```

Каждый SQL-запрос получает актуальный snapshot на момент своего начала.

---

# 3️⃣ REPEATABLE READ

`REPEATABLE READ` обеспечивает более сильную изоляцию.

В PostgreSQL транзакция работает с согласованным snapshot.

Например:

```text id="4qv7ma"
Transaction A

BEGIN
 ↓
snapshot
 ↓
SELECT → 100
```

Параллельно:

```text id="r8khq2"
Transaction B

UPDATE → 200
COMMIT
```

A снова выполняет:

```text id="kr5y8d"
SELECT
→ 100
```

Она продолжает видеть данные согласно своему snapshot.

---

## 🧠 READ COMMITTED vs REPEATABLE READ

Главное различие:

```text id="g8q1x7"
READ COMMITTED

SELECT
 ↓
новый snapshot

SELECT
 ↓
новый snapshot
```

А:

```text id="v0yq8d"
REPEATABLE READ

BEGIN
 ↓
snapshot
 ↓
SELECT
 ↓
SELECT
 ↓
SELECT
```

Все запросы транзакции используют одно согласованное представление данных.

---

# 4️⃣ SERIALIZABLE

Самый строгий стандартный уровень.

Цель:

> Результат параллельного выполнения транзакций должен быть эквивалентен некоторому последовательному выполнению этих транзакций.

То есть:

```text id="s8r1pm"
Transaction A
Transaction B
```

должны вести себя так, будто:

```text id="w3q2hc"
A → B
```

или:

```text id="j2c8v4"
B → A
```

а не давать результат, который невозможно получить при последовательном выполнении.

---

# ⚠️ SERIALIZABLE может завершить транзакцию ошибкой

Для обеспечения сериализуемости PostgreSQL может обнаружить конфликт и отменить одну из транзакций.

Например:

```text id="y5y4qh"
ERROR:
could not serialize access due to
concurrent update
```

В таком случае приложение обычно должно:

```text id="n3c7me"
ROLLBACK
   ↓
повторить транзакцию
```

Поэтому `SERIALIZABLE` требует готовности приложения к **retry**.

---

# 🧩 Аномалии изоляции

Для понимания уровней важно знать три классические аномалии.

---

## 1. Dirty Read

Транзакция читает незакоммиченные изменения другой транзакции.

```text id="z8s0wy"
A:
UPDATE → 500
COMMIT ещё нет

B:
SELECT → 500 ❌
```

Если A сделает:

```text id="a4e7bs"
ROLLBACK
```

данных `500` никогда не существовало в зафиксированном состоянии.

---

## 2. Non-repeatable Read

Одна транзакция дважды читает одну строку и получает разные значения.

```text id="qz3y4x"
A:
SELECT → 100

B:
UPDATE → 200
COMMIT

A:
SELECT → 200
```

Первое и второе чтение отличаются.

---

## 3. Phantom Read

Транзакция повторяет запрос по условию и получает **другой набор строк**.

Например:

```text id="f0xq7a"
A:
SELECT *
FROM users
WHERE age > 30;

→ 100 строк
```

B добавляет:

```text id="1m0g3d"
INSERT INTO users(age)
VALUES (40);

COMMIT;
```

A снова выполняет:

```text id="0i6t1s"
SELECT *
FROM users
WHERE age > 30;

→ 101 строк
```

Новая строка — **phantom**.

---

# 📊 Как запомнить уровни

```text id="6twqzz"

самая слабая изоляция
      ↓

      ↓

      ↓

```

Упрощённо:

```text id="wh0g87"
Больше изоляции
       ↓
меньше допустимых аномалий
       ↓
больше гарантий
       ↓
потенциально больше конфликтов / стоимость
```

# 🧠 Уровень изоляции и MVCC

MVCC — один из ключевых механизмов, с помощью которых PostgreSQL реализует изоляцию.

Связь:

```text id="6v1p0j"
Transaction
    ↓
Isolation Level
    ↓
Snapshot
    ↓
MVCC
    ↓
какие версии строк видны
```

Но:

> **MVCC и Isolation Level — не одно и то же.**

MVCC — механизм многоверсионного управления конкурентным доступом.

Isolation Level — набор гарантий, которые получает транзакция.

---

# ⚠️ Уровень изоляции не отменяет блокировки

Например:

```python id="c0m0hs"
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

явно устанавливает блокировку строки.

Поэтому:

```text id="47q6z1"
MVCC
≠
отсутствие блокировок
```

PostgreSQL сочетает:

```text id="6y3r0v"
MVCC
+
Locks
+
Isolation Levels
```

# 💳 Практический пример: банковский перевод

Представим:

```text id="e7x7b4"
A = 1000 ₽
B = 500 ₽
```

Нужно перевести:

```text id="5y8x9g"
300 ₽
```

Транзакция:

```python id="b0b8gm"
BEGIN;

UPDATE accounts
SET balance = balance - 300
WHERE id = 1;

UPDATE accounts
SET balance = balance + 300
WHERE id = 2;

COMMIT;
```

Здесь:

### Atomicity

Обе операции выполняются вместе.

### Consistency

Баланс и ограничения остаются корректными.

### Isolation

Другие транзакции не должны получить некорректное промежуточное состояние.

### Durability

После `COMMIT` изменения сохраняются.

Уровень изоляции отвечает именно за **Isolation**.

# 🎯 Какой уровень использовать?

Нет правила:

> «Всегда используем SERIALIZABLE».

На практике выбирают минимальный уровень, который обеспечивает необходимую корректность конкретной операции.

Часто:

```text id="0m4a1k"
READ COMMITTED
```

достаточен для обычных CRUD-операций.

Для задач, где нужен стабильный snapshot:

```text id="6s3gq4"
REPEATABLE READ
```

Для строгой сериализуемости:

```text id="n7v1k9"
SERIALIZABLE
```

Но конкретный выбор зависит от бизнес-логики и конкурентных сценариев.

---

# 🧩 Сравнение PostgreSQL

| Уровень          | Snapshot                | Что важно                       |
| ---------------- | ----------------------- | ------------------------------- |
| READ UNCOMMITTED | Как READ COMMITTED      | Dirty Read не допускается       |
| READ COMMITTED   | На каждый statement     | Возможен Non-repeatable Read    |
| REPEATABLE READ  | На транзакцию           | Согласованный snapshot          |
| SERIALIZABLE     | Строгая сериализуемость | Возможны serialization failures |

# 🎤 Частые вопросы на собеседовании

### Какой уровень изоляции используется в PostgreSQL по умолчанию?

> `READ COMMITTED`.

### Что происходит в READ COMMITTED?

> Каждый SQL statement получает собственный snapshot. Поэтому два `SELECT` в одной транзакции могут увидеть разные значения, если между ними другая транзакция зафиксировала изменения.

### Чем REPEATABLE READ отличается от READ COMMITTED?

> В PostgreSQL `READ COMMITTED` использует новый snapshot для каждого statement, а `REPEATABLE READ` сохраняет согласованный snapshot на уровне транзакции.

### Что такое SERIALIZABLE?

> Уровень изоляции, который обеспечивает поведение, эквивалентное некоторому последовательному выполнению транзакций. При конфликте PostgreSQL может отменить транзакцию, и приложение должно её повторить.

### Что такое Dirty Read?

> Чтение незакоммиченных изменений другой транзакции.

### Что такое Non-repeatable Read?

> Повторное чтение одной строки внутри транзакции возвращает другое значение из-за изменения и commit другой транзакции.

### Что такое Phantom Read?

> Повторный запрос по условию возвращает другой набор строк из-за добавления, удаления или изменения подходящих строк другой транзакцией.

### Как MVCC связан с уровнями изоляции?

> MVCC предоставляет механизм версий строк и snapshot, а уровень изоляции определяет правила, по которым транзакция видит эти версии и взаимодействует с конкурентными изменениями.

### Какой уровень изоляции выбрать?

> Нужно выбрать минимальный уровень, который обеспечивает необходимые бизнес-инварианты и корректность конкурентных операций. `READ COMMITTED` часто достаточен, но для более строгих требований могут использоваться `REPEATABLE READ` или `SERIALIZABLE`.

```text
                TRANSACTION
                     │
                     ↓
             ISOLATION LEVEL
                     │

          ↓          ↓          ↓
    READ COMMITTED  REPEATABLE  SERIALIZABLE
                     READ
          │           │           │
     snapshot      один        строгая
     на каждый     snapshot     сериализация

          │           │           │
          └───────────┼───────────┘
                      ↓
                    MVCC
                      ↓
             видимость версий
```
