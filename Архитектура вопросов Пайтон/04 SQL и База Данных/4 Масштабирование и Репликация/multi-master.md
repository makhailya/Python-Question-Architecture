# 🔄 Multi-Master репликация

## 🎯 Ответ на собеседовании

**Multi-Master репликация** — это архитектура, в которой **несколько экземпляров БД одновременно могут принимать операции записи и чтения**, а изменения реплицируются между ними.

Главная сложность — **конфликты**, когда разные узлы одновременно изменяют одни и те же данные. Поэтому multi-master требует механизмов обнаружения, разрешения конфликтов и контроля консистентности.

> В отличие от Master-Slave / Primary-Replica, где запись обычно идёт через один Primary, в Multi-Master несколько узлов являются источниками записи.

---
### Формула для собеседования

> **Multi-Master — это схема репликации, при которой несколько экземпляров БД одновременно принимают записи и чтения. Главное преимущество — высокая доступность и возможность распределять запись между узлами. Главный недостаток — сложность поддержания консистентности: при одновременных изменениях возникают конфликты, поэтому нужны механизмы их обнаружения и разрешения.**
> 
## 🎤 Суперкоротко

```text
Multi-Master:

        ┌──────────────┐
        │   Master A   │
        │  READ/WRITE  │
        └──────┬───────┘
               ↕
          репликация
               ↕
        ┌──────┴───────┐
        │   Master B   │
        │  READ/WRITE  │
        └──────────────┘
```

Оба узла могут принимать:

```text
READ  ✅
WRITE ✅
```

Главная проблема:

```text
Master A ── UPDATE user → name = Ivan
                    ↘
                     конфликт
                    ↗
Master B ── UPDATE user → name = Petr
```

# 1. 🔗 Чем Multi-Master отличается от Primary-Replica

### Primary-Replica

```text
             WRITE
               ↓
          ┌─────────┐
          │ Primary │
          └────┬────┘
               │
          replication
          ↙          ↘
    ┌──────────┐  ┌──────────┐
    │ Replica  │  │ Replica  │
    │  READ    │  │  READ    │
    └──────────┘  └──────────┘
```

Обычно:

```text
Primary  → READ + WRITE
Replica  → READ
```

### Multi-Master

```text
          ┌──────────┐
          │ Master A │
          │READ/WRITE│
          └─────┬────┘
                ↕
           replication
                ↕
          ┌─────┴────┐
          │ Master B │
          │READ/WRITE│
          └──────────┘
```

Оба узла могут принимать записи.

---

# 2. 🎯 Зачем нужен Multi-Master

Основная идея — **не иметь единственного узла, через который обязательно должны проходить все записи**.

Потенциальные цели:

* высокая доступность;
* работа из нескольких регионов;
* локальные записи ближе к пользователю;
* отсутствие единственного write-primary;
* распределение write-нагрузки;
* отказоустойчивость.

Например:

```text
Europe
  │
  ▼
Master EU

Asia
  │
  ▼
Master ASIA
```

Пользователь из Европы может писать в европейский узел, а пользователь из Азии — в азиатский.

---

# 3. ⚠️ Главная проблема — конфликт записей

Представим, что есть:

```text
user_id = 10
balance = 1000
```

Два Master одновременно получают старое значение.

Master A:

```python
UPDATE accounts
SET balance = 900
WHERE id = 10;
```

Master B одновременно:

```python
UPDATE accounts
SET balance = 800
WHERE id = 10;
```

Оба изменения должны попасть на другой узел.

Возникает вопрос:

> Какое значение должно стать итоговым?

```text
900?
800?
```

Это **write conflict**.

---

# 4. 💥 Почему конфликты сложны

В Primary-Replica архитектуре есть один источник записи:

```text
Primary
   ↓
изменение
   ↓
Replica
```

Конфликтов между независимыми источниками записи обычно нет.

В Multi-Master:

```text
Master A
   │
   ├── WRITE X
   │
   └─────────────┐
                 ↓
               sync
                 ↓
Master B
   │
   └── WRITE Y
```

Если `X` и `Y` затрагивают одни данные, необходимо определить порядок или правило разрешения конфликта.

---

# 5. 🧩 Стратегии разрешения конфликтов

Конкретный механизм зависит от технологии, но концептуально используются разные подходы.

### Last Write Wins

Побеждает изменение, которое считается более поздним.

```text
A → name = Ivan
B → name = Petr

       ↓

Petr
```

Проблема:

> Более поздняя запись может перезаписать корректное изменение.

---

### Conflict Detection

Система обнаруживает конфликт:

```text
A → UPDATE X
B → UPDATE X

      ↓

CONFLICT
```

После этого приложение или специальный механизм должен решить, что делать.

---

### Application-Level Resolution

Конфликт разрешает само приложение.

Например:

```text
A → quantity = 5
B → quantity = 7

→ бизнес-логика определяет правильный результат
```

Это сложнее, но позволяет учитывать смысл данных.

---

# 6. 🕐 Проблема порядка событий

В распределённой системе разные узлы могут видеть события в разном порядке.

Например:

```text
Master A:

A1 → A2 → A3
```

Master B может получить:

```text
A1 → A3 → A2
```

Поэтому системе нужны механизмы определения:

* порядка операций;
* причинно-следственных связей;
* конфликтов;
* актуальности версии данных.

В конкретных системах для этого могут использоваться разные механизмы: версии, timestamps, sequence numbers, логические часы и т. п.

---

# 7. 🌍 Multi-Master в разных регионах

Один из интересных сценариев:

```text
                 Internet
                /        \
               /          \
              ▼            ▼
        ┌──────────┐  ┌──────────┐
        │ Master EU│  │Master USA │
        │ READ/WRITE│ │READ/WRITE │
        └─────┬────┘  └────┬─────┘
              │             │
              └──────↔──────┘
                 replication
```

Преимущество:

```text
Пользователь EU
      ↓
Master EU
```

и:

```text
Пользователь USA
      ↓
Master USA
```

Можно уменьшить latency для записи.

Но появляется сложность:

```text
EU изменил данные
      ↓
USA ещё не получил изменение
```

То есть возникает проблема **replication lag** и возможной временной рассогласованности.

---

# 8. 🕒 Eventual Consistency

Во многих распределённых multi-master системах возможна **eventual consistency**.

Это означает, что после изменения разные узлы могут некоторое время иметь разные состояния, но при отсутствии новых конфликтующих изменений они должны в итоге прийти к согласованному состоянию.

Например:

```text
t1:
Master A → balance = 900
Master B → balance = 1000

t2:
репликация

Master A → 900
Master B → 900
```

Но это зависит от конкретной системы и её модели консистентности.

---

# 9. 🔐 Сильная консистентность vs доступность

Multi-Master особенно сложен при сетевых проблемах.

Например:

```text
Master A  X  Master B
          network partition
```

Связь между узлами потеряна.

Оба узла всё ещё могут принимать записи:

```text
A → WRITE X
B → WRITE Y
```

После восстановления связи:

```text
A ↔ B
```

возникают конфликты, которые нужно разрешить.

Это одна из фундаментальных проблем распределённых систем.

---

# 10. 🧠 Multi-Master не означает «магическое масштабирование»

На первый взгляд:

```text
1 Master
   ↓
2 Masters
   ↓
3 Masters
```

кажется, что write throughput просто масштабируется.

На практике не всё так просто.

Каждый дополнительный master может увеличить:

* количество репликационного трафика;
* количество потенциальных конфликтов;
* сложность координации;
* требования к консистентности;
* сложность мониторинга;
* сложность восстановления.

Поэтому:

> Multi-Master увеличивает доступность и потенциально распределяет запись, но одновременно значительно увеличивает распределённую сложность.

---

# 11. 🔄 Multi-Master и отказ одного узла

Допустим:

```text
Master A ❌
```

Если Master B продолжает принимать:

```text
READ  ✅
WRITE ✅
```

то система потенциально может продолжить работу.

Это одно из преимуществ multi-master.

В Primary-Replica архитектуре при падении Primary необходимо:

```text
Replica
   ↓
promotion
   ↓
новый Primary
```

и нужен механизм failover.

---

# 12. ⚠️ Multi-Master и split-brain

Особенно опасная ситуация:

```text
        сеть разделилась

       A       X       B
```

Оба узла считают себя активными и продолжают принимать записи:

```text
A → WRITE
B → WRITE
```

После восстановления связи могут появиться противоречивые изменения.

Это называют **split-brain**.

Поэтому реальные системы должны иметь механизмы предотвращения или корректного разрешения такой ситуации.

---

# 13. 🆔 Проблема генерации ID

Если несколько master одновременно создают записи:

```text
Master A → INSERT
Master B → INSERT
```

нельзя просто использовать локальный счётчик:

```text
A → id = 100
B → id = 100
```

может возникнуть конфликт.

Поэтому распределённые системы могут использовать:

* UUID;
* ULID;
* Snowflake-подобные ID;
* диапазоны ID для разных узлов;
* другие распределённые генераторы идентификаторов.

Например:

```text
Master A → UUID
Master B → UUID
```

вероятность коллизии практически исключается при корректном использовании.

---

# 14. 📊 Multi-Master vs Primary-Replica

| Характеристика          | Primary-Replica                     | Multi-Master                          |
| ----------------------- | ----------------------------------- | ------------------------------------- |
| Запись                  | Обычно один Primary                 | Несколько Master                      |
| Чтение                  | Primary + Replicas                  | Все активные узлы                     |
| Конфликты записи        | Значительно проще                   | Главная проблема                      |
| Failover                | Требуется promotion                 | Другой Master может продолжить запись |
| Масштабирование чтения  | ✅                                   | ✅                                     |
| Масштабирование записи  | Ограничено Primary                  | Потенциально распределяется           |
| Архитектурная сложность | Ниже                                | Значительно выше                      |
| Split-brain риск        | Есть при failover/сетевых проблемах | Особенно важен                        |
| Геораспределение        | Возможно                            | Один из распространённых сценариев    |
| Консистентность         | Проще контролировать                | Сложнее                               |

# 15. 🧩 Multi-Master и конфликт транзакций

Представим:

```text
Initial:
balance = 1000
```

Master A:

```python id="8gr1mi"
UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

Получает:

```text
900
```

Master B:

```python id="9p2q9u"
UPDATE accounts
SET balance = balance - 200
WHERE id = 1;
```

Получает:

```text
800
```

Если изменения просто перезаписываются:

```text
900 ↔ 800
```

то одна операция может потеряться.

Поэтому для финансовой логики простого:

```text
Last Write Wins
```

может быть недостаточно.

Нужна модель, которая учитывает **бизнес-инварианты**.

---

# 16. 🏗️ Когда Multi-Master оправдан

Multi-Master имеет смысл, когда действительно нужны:

* запись из нескольких регионов;
* высокая доступность записи;
* отсутствие единственного write-primary;
* распределённая инфраструктура;
* снижение latency записи в разных географических точках.

Но если задача просто:

```text
много SELECT
```

обычно проще использовать:

```text
Primary
   ↓
Read Replicas
```

А не усложнять систему multi-master.

---

# 17. ⚠️ Основные недостатки

```text
Multi-Master
│
├── сложная синхронизация
├── конфликты записей
├── сложнее обеспечить консистентность
├── replication lag
├── split-brain
├── сложнее failover
├── сложнее мониторинг
├── сложнее backup/recovery
├── распределённые транзакции
└── больше сетевого трафика
```

Поэтому multi-master — не «следующий обязательный уровень» после Primary-Replica.

Это архитектурный выбор под конкретные требования.

### Формула для собеседования
