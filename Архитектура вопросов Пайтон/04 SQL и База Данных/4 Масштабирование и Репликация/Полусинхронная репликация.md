# 🔄 Полусинхронная репликация

## 🎤 Короткий ответ

**Полусинхронная репликация** — это компромисс между синхронной и асинхронной репликацией: Primary после записи **ждёт подтверждение хотя бы от одной реплики** (или заданного минимального числа реплик), прежде чем считать операцию подтверждённой клиенту.

Это повышает надёжность по сравнению с полностью асинхронной репликацией, но обычно сохраняет меньшую задержку и зависимость от реплик, чем строгая синхронная репликация.

## 🎯 Формула для собеседования

> **Полусинхронная = Primary ждёт ACK минимум от одной реплики → клиент получает OK → остальные реплики синхронизируются асинхронно.**

```python id="p8k3m1"
Client
   ↓
Primary
   ↓
Replica 1 → ACK
   ↓
Client получает OK

Replica 2
Replica 3
   ↓
синхронизируются позже
```

---

## 🔹 Зачем нужна

Основная идея — получить **компромисс между надёжностью и производительностью**.

### Асинхронная

```python id="a7x2q9"
Primary → COMMIT → Client OK
             ↓
          Replica
```

Primary не ждёт реплику.

Плюс:

* минимальная задержка записи;
* выше доступность.

Минус:

* Primary может подтвердить запись, которая ещё не попала ни на одну реплику.

---

### Синхронная

```python id="s4m6k2"
Primary → Replica 1 → ACK
   ↓
Client OK
```

Primary ждёт требуемое количество подтверждений.

Плюс:

* выше гарантия сохранности подтверждённых данных.

Минус:

* задержка записи зависит от реплики;
* проблемы с репликой могут блокировать запись.

---

### Полусинхронная

```python id="h5n8r3"
             ┌→ Replica 1 → ACK ─┐
Primary ─────┤                   ├→ Client OK
             ├→ Replica 2       │
             └→ Replica 3       │
```

Primary ждёт **минимально необходимое количество ACK**, например одного.

После этого клиенту возвращается успешный результат, а остальные реплики могут продолжать догонять Primary.

---

# 🔹 Пример

Допустим, есть:

```text
Primary
Replica 1
Replica 2
Replica 3
```

Настройка:

> Для подтверждения записи достаточно ACK от **одной реплики**.

Происходит:

```text
1. Client → INSERT
2. Primary записывает изменение
3. Primary → Replica 1
4. Replica 1 → ACK
5. Primary → Client: OK
6. Replica 2 и Replica 3 продолжают репликацию
```

Если после шага 5 Primary выйдет из строя, у нас уже есть копия изменения на Replica 1.

---

# 🔹 Главное отличие от синхронной

Разница заключается прежде всего в **количестве обязательных подтверждений**.

| Тип            | Когда Primary подтверждает запись                 |
| -------------- | ------------------------------------------------- |
| Асинхронная    | Не ждёт ACK реплик                                |
| Полусинхронная | Ждёт минимум одну/заданное небольшое число реплик |
| Синхронная     | Ждёт все требуемые по политике реплики            |

Важно: термин **«полусинхронная» не означает обязательно ровно одну реплику**.

Конкретная система может требовать:

```text
1 ACK
2 ACK
N ACK
```

Главное — Primary ждёт **минимально необходимое подтверждение**, а не все реплики.

---

# 🔹 Что происходит при отказе реплики

Предположим:

```text
Primary
├── Replica 1 ❌
├── Replica 2 ✅
└── Replica 3 ✅
```

Если политика требует:

```text
минимум 1 ACK
```

то Primary может продолжить принимать записи, получая подтверждение от Replica 2 или Replica 3.

Это важное преимущество перед конфигурацией, где для завершения записи требуются конкретные недоступные реплики.

Но точное поведение зависит от конкретной СУБД и её настроек.

---

# 🔹 Надёжность

Полусинхронная репликация уменьшает окно потери подтверждённых данных.

При асинхронной:

```text
Primary
   ↓
COMMIT
   ↓
Client OK
   ↓
❌ Primary crash
   ↓
Replica ещё не получила запись
```

Последняя подтверждённая запись потенциально может потеряться при переключении на реплику.

При полусинхронной:

```text
Primary
   ↓
Replica → ACK
   ↓
COMMIT / подтверждение
   ↓
Client OK
```

Уже существует как минимум одна реплика с подтверждённой копией в соответствии с выбранной семантикой ACK.

---

# 🔹 Цена полусинхронности

Появляется зависимость от:

* сети между Primary и репликой;
* скорости реплики;
* дискового I/O реплики;
* количества требуемых ACK.

Поэтому:

```text
Надёжность       ↑
Задержка записи  ↑
Зависимость от реплик ↑
```

Но обычно компромисс получается мягче, чем при ожидании нескольких/всех синхронных реплик.

---

# 🔹 Важный нюанс: что означает ACK

**ACK не всегда означает одно и то же.**

В зависимости от СУБД подтверждение может означать, например:

* реплика получила данные;
* записала WAL;
* сбросила WAL на диск;
* применила изменения.

Поэтому на собеседовании лучше сказать:

> «Полусинхронная репликация ждёт подтверждение от минимально необходимого числа реплик, а точная гарантия зависит от того, что именно система считает ACK».

Это точнее, чем просто говорить «реплика записала данные».

# 🔹 PostgreSQL

В PostgreSQL похожая модель реализуется через механизм **synchronous replication** с настройками:

```python id="q2v7n4"
synchronous_commit
synchronous_standby_names
```

Можно определить, сколько standby должно подтвердить операцию перед завершением транзакции.

Например, концептуально:

```text
Primary
   │
   ├── Standby 1 → ACK
   │
   ├── Standby 2
   │
   └── Standby 3
```

Если политика требует подтверждения хотя бы от одной standby, Primary ждёт этот ACK, а остальные standby могут отставать.

Конкретная семантика зависит от настроек PostgreSQL и уровня подтверждения.

---

# 🔹 Полусинхронная ≠ резервная копия

Это принципиально.

Репликация:

```text
Primary → Replica
```

не заменяет backup.

Если выполнить:

```python id="r6c1w8"
DELETE FROM users;
```

и изменение успешно реплицируется, оно может удалиться и на реплике.

Для защиты от таких ситуаций нужны:

* backup;
* WAL archiving;
* Point-in-Time Recovery (PITR).

# 🔹 Сравнение трёх вариантов

| Характеристика                                     | Асинхронная | Полусинхронная                 | Синхронная                |
| -------------------------------------------------- | ----------- | ------------------------------ | ------------------------- |
| Ждёт реплику                                       | ❌           | ✅ минимум одну/требуемое число | ✅ требуемые реплики       |
| Задержка записи                                    | Низкая      | Средняя                        | Выше                      |
| Надёжность подтверждённой записи                   | Ниже        | Средняя/выше                   | Выше                      |
| Зависимость от реплик                              | Низкая      | Средняя                        | Высокая                   |
| Реплика может отставать                            | ✅           | ✅ для необязательных реплик    | Ограниченно для требуемых |
| Возможность потери последних подтверждённых данных | Выше        | Ниже                           | Ниже                      |

## 🧠 Пример для собеседования

**Интервьюер:**

> Чем полусинхронная репликация отличается от синхронной?

**Ответ:**

> «При полусинхронной репликации Primary ждёт подтверждение только от минимально необходимого количества реплик, например одной, после чего подтверждает запись клиенту. При строгой синхронной репликации Primary ждёт подтверждений от всех реплик, требуемых политикой. Поэтому полусинхронная модель является компромиссом между надёжностью и задержкой записи».

---

## 🔑 Ключевая схема

```text
Асинхронная:
Primary ─────────────→ Client OK
   │
   └────────────→ Replica


Полусинхронная:
Primary ──→ Replica ──→ ACK ──→ Client OK
   │
   ├────────────→ Replica
   └────────────→ Replica


Синхронная:
Primary ──→ Replica 1 ──→ ACK
        ──→ Replica 2 ──→ ACK
        ──→ Replica 3 ──→ ACK
                    ↓
                 Client OK
```

### 🎤 Формула

> **Async — не ждём.
> Semi-sync — ждём минимум необходимое число ACK.
> Sync — ждём все ACK, которые требует политика.**
