# 🔄 Репликация базы данных

## 🎯 Ответ на собеседовании

**Репликация** — это процесс поддержания одной или нескольких копий базы данных на других узлах.

Обычно есть **Primary** — основной узел, который принимает записи, и **Replica(s)** — копии, которые получают изменения от Primary.

Репликация используется прежде всего для:

* отказоустойчивости;
* масштабирования чтения;
* резервирования;
* уменьшения времени восстановления после отказа.

Главное:

> **Репликация копирует данные между узлами, но сама по себе не распределяет данные.**

---
# 🎤 Формулировка для собеседования

> **Репликация — это поддержание копий данных на нескольких узлах. Обычно Primary принимает записи, а Replica получает изменения и может обслуживать чтение. Репликация используется для отказоустойчивости, failover и масштабирования чтения. Она бывает синхронной и асинхронной. При асинхронной репликации возникает replication lag, поэтому сразу после записи чтение с реплики может вернуть устаревшие данные. Репликация отличается от шардирования: репликация копирует данные, а шардирование распределяет их между узлами.**
> 
## 🎤 Суперкоротко

```python
Primary
   │
   ├──► Replica 1
   ├──► Replica 2
   └──► Replica 3
```

**Primary** — пишет.
**Replica** — получает копию данных и может обслуживать чтение.

```python
Replication → копируем данные
Sharding    → разделяем данные
```

# 🧠 Зачем нужна репликация

Представим один сервер:

```python
Application
     │
     ▼
 PostgreSQL
```

Если сервер вышел из строя:

```python
PostgreSQL ❌
     ↓
сервис недоступен
```

С репликацией:

```python
              ┌───────────┐
              │  Primary  │
              └─────┬─────┘
                    │
             ┌──────┴──────┐
             ▼             ▼
        ┌─────────┐   ┌─────────┐
        │Replica 1│   │Replica 2│
        └─────────┘   └─────────┘
```

Если Primary выходит из строя, одну из реплик можно сделать новым Primary.

Это называется:

**Failover**.

# 1. 📝 Primary и Replica

### Primary

Основной узел.

Обычно принимает:

```python
INSERT
UPDATE
DELETE
```

А также может обслуживать:

```python
SELECT
```

### Replica

Получает изменения от Primary.

Обычно используется для:

```python
SELECT
```

Схема:

```python
             WRITE
Application ────────► Primary
                         │
                         │ replication
                  ┌──────┴──────┐
                  ▼             ▼
              Replica 1     Replica 2
                  │             │
                  └──── SELECT ─┘
```

---

# 2. 📚 Репликация для чтения

Если приложение делает:

```python
10% WRITE
90% READ
```

одного Primary может стать недостаточно именно по чтению.

Можно использовать:

```python
                Application
                 /        \
              WRITE       READ
                │           │
                ▼           ▼
             Primary     Replicas
                           /   \
                          ▼     ▼
                       Replica Replica
```

Записи идут на Primary.

Чтения распределяются между репликами.

Это называется:

**Read Scaling / Read Replicas.**

---

# 3. ⚠️ Replication Lag

Одна из главных проблем репликации.

Изменение сначала появляется на Primary:

```python
Primary
balance = 500
```

А Replica ещё не успела его получить:

```python
Replica
balance = 1000
```

Это:

**Replication Lag** — задержка репликации.

---

## Пример

```python
# WRITE
UPDATE accounts
SET balance = 500
WHERE id = 1;
```

Запрос завершился успешно.

Сразу после этого:

```python
# READ FROM REPLICA

SELECT balance
FROM accounts
WHERE id = 1;
```

может вернуть:

```python
1000
```

если Replica ещё не получила изменение.

Поэтому после критичной записи иногда нужно читать именно с Primary.

---

# 4. 🔀 Read-After-Write

Это частный случай проблемы репликации.

Пользователь сделал:

```python
UPDATE profile
SET name = 'Ivan';
```

Затем сразу:

```python
SELECT name
FROM profile;
```

Если `SELECT` отправить на отстающую Replica, пользователь может получить старое значение.

Схема:

```python
WRITE
  ↓
Primary
  ↓
ещё не успело попасть на Replica
  ↓
READ
  ↓
старые данные
```

Для таких операций применяют стратегии:

* чтение с Primary;
* ожидание нужного состояния реплики;
* маршрутизация связанных запросов на Primary;
* настройка системы на необходимый уровень consistency.

# 5. 🔄 Синхронная и асинхронная репликация

## Асинхронная

Primary не ждёт подтверждения от Replica перед завершением записи.

```python
Application
     │
     ▼
 Primary
     │
     └────► Replica
```

Primary может подтвердить:

```python
COMMIT
```

до того, как Replica полностью применит изменение.

### Плюсы

* меньшая задержка записи;
* Primary не зависит от скорости Replica;
* проще масштабировать географически.

### Минус

При внезапной потере Primary последние изменения могут ещё не успеть попасть на Replica.

---

## Синхронная

Primary ждёт подтверждения от Replica перед завершением операции.

```python
Application
     │
     ▼
 Primary
     │
     ▼
 Replica
     │
     ▼
 подтверждение
     │
     ▼
 COMMIT
```

### Плюс

Меньше риск потери подтверждённых данных при отказе Primary.

### Минусы

* выше latency записи;
* отказ/задержка Replica может повлиять на Primary;
* сложнее конфигурация.

---

# 🆚 Синхронная vs асинхронная

|                              | Асинхронная | Синхронная |
| ---------------------------- | ----------- | ---------- |
| Latency записи               | Ниже        | Выше       |
| Primary ждёт Replica         | ❌           | ✅          |
| Риск потери последних данных | Выше        | Ниже       |
| Зависимость от Replica       | Ниже        | Выше       |
| Производительность           | Выше        | Ниже       |
| Сложность                    | Ниже        | Выше       |

# 6. 🧩 Streaming Replication в PostgreSQL

В PostgreSQL распространённый механизм — **Streaming Replication**.

Упрощённо:

```python
Primary
   │
   ▼
 WAL
   │
   ▼
Replica
```

**WAL (Write-Ahead Log)** содержит информацию, необходимую для восстановления и воспроизведения изменений.

Replica получает WAL от Primary и применяет изменения.

Условно:

```python
UPDATE
   ↓
WAL
   ↓
Replica
   ↓
Replay WAL
   ↓
изменение появляется на Replica
```

# 7. 🧱 Репликация ≠ Backup

Очень важное различие.

### Репликация

```python
Primary ─────► Replica
```

Изменения быстро распространяются на копию.

Если случайно выполнить:

```python
DELETE FROM users;
```

это изменение может также попасть на Replica.

Поэтому Replica **не заменяет полноценный backup**.

### Backup

Это отдельная копия данных, предназначенная для восстановления.

Например:

```python
Database
   │
   └──► Backup
```

Для защиты от:

* случайного удаления;
* повреждения данных;
* ошибок приложения;
* некоторых видов катастрофических отказов.

---

# 8. 🔥 Failover

Если Primary выходит из строя:

```python
Primary ❌
    │
    ▼
Replica
```

одна из Replica может стать новым Primary:

```python
Old Primary ❌

Replica 1
   ↓
New Primary
```

Это называется:

**Failover**.

Но важно:

> Репликация сама по себе не означает автоматический failover.

Для автоматического переключения нужен дополнительный механизм управления кластером.

---

# 9. 🧭 High Availability

Репликация может быть частью архитектуры **High Availability (HA)**.

Например:

```python
             Application
                  │
             HA / Proxy
                  │
          ┌───────┴───────┐
          ▼               ▼
       Primary          Replica
          │               │
          └───────────────┘
```

При отказе Primary система может переключить трафик на Replica.

В PostgreSQL для подобных архитектур могут использоваться дополнительные инструменты управления кластером и failover.

# 10. 🆚 Репликация vs Sharding

Это один из самых важных вопросов.

### Репликация

```python
Primary
   │
   ├──► Replica 1
   └──► Replica 2
```

Каждая копия содержит примерно **весь набор данных**.

Цель:

* HA;
* резервирование;
* масштабирование чтения.

### Sharding

```python
Shard 1 → users 1–100000
Shard 2 → users 100001–200000
Shard 3 → users 200001–300000
```

Данные **разделены** между узлами.

Цель:

* масштабирование объёма данных;
* масштабирование нагрузки;
* выход за пределы одного сервера.

---

# 11. 🔗 Репликация + Sharding

Их можно использовать одновременно.

Например:

```python
                Application
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Shard 1    Shard 2    Shard 3
          │          │          │
        ┌─┴─┐      ┌─┴─┐      ┌─┴─┐
        ▼   ▼      ▼   ▼      ▼   ▼
      Rep  Rep    Rep  Rep    Rep  Rep
```

Здесь:

**Sharding** распределяет данные.

**Replication** создаёт копии каждого shard.

---

# 12. ⚠️ Основные проблемы репликации

### Replication Lag

Replica отстаёт от Primary.

### Failover

Нужно корректно переключить роли.

### Split Brain

Два узла начинают считать себя Primary.

```python
       Primary A
          ↕
       Primary B

      ❌ конфликт
```

Для этого нужны механизмы координации и выбор лидера.

### Consistency

Нужно понимать, насколько допустимо читать устаревшие данные.

### Дополнительные ресурсы

Реплики требуют:

* CPU;
* RAM;
* диска;
* сети.

# 13. 📊 Что мониторить

При репликации важно смотреть:

```python
Replication Lag
WAL generation
WAL replay
Replica health
Replication connections
Disk usage
Network
```

Особенно важно:

> **не только абсолютное значение lag, но и его динамика.**

Если lag постоянно растёт:

```python
0 → 100 → 500 → 5000 → 50000
```

значит Replica не успевает за Primary.

# 🧠 Типичная архитектура

Для приложения с большой нагрузкой на чтение:

```python
                         ┌──────────────┐
                         │ Application  │
                         └──────┬───────┘
                                │
                   ┌────────────┴────────────┐
                   │                         │
                 WRITE                      READ
                   │                         │
                   ▼                         ▼
              ┌─────────┐             ┌───────────┐
              │ Primary │────────────►│ Replica 1 │
              └─────────┘             └───────────┘
                   │
                   └──────────────────►┌───────────┐
                                       │ Replica 2 │
                                       └───────────┘
```

Так можно увеличить количество операций чтения без переноса всех записей на несколько независимых БД.
