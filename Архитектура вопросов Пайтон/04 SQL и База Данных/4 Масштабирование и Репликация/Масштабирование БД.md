# 🗄️ Масштабирование базы данных

## 🎯 Ответ на собеседовании

**Масштабирование БД** — это увеличение способности базы данных обрабатывать растущую нагрузку: больше запросов, пользователей, данных и операций.

Основные подходы:

1. **[[Вертикальное масштабирование (Scale Up)]]** — усиление одного сервера.
2. **[[Репликация]]** — создание копий БД для распределения нагрузки.
3. **[[Шардинг (Sharding)]]** — разделение данных между несколькими серверами.
4. **[[Партиционирование]] (Partitioning)** — разделение одной таблицы на части внутри БД.
5. **[[Оптимизация]]** — индексы, запросы, кэширование, connection pooling и т.д.

На практике обычно используют **комбинацию** этих подходов.

---

## 🎤 Суперкоротко

> **Scale Up** — мощнее один сервер.
> **Read Replicas** — распределяем чтение между копиями.
> **Sharding** — распределяем данные между разными БД/серверами.
> **Partitioning** — делим большую таблицу на части внутри одной БД.

Главная идея:

```python
Рост нагрузки
      │
      ├── оптимизация
      ├── кэш
      ├── Scale Up
      ├── Replication
      ├── Partitioning
      └── Sharding
```

---

# 1. 📈 Вертикальное масштабирование — Scale Up

Увеличиваем ресурсы одного сервера:

```python
Сервер
├── CPU ↑
├── RAM ↑
├── SSD ↑
└── IOPS ↑
```

Например:

```python
16 GB RAM → 64 GB RAM
4 CPU     → 16 CPU
SSD       → более быстрый SSD
```

### Плюсы

* просто внедрить;
* приложение почти не меняется;
* не нужно распределять данные;
* сохраняется единая БД.

### Минусы

* есть физический предел;
* дорогой сервер;
* одна точка отказа без HA;
* при достижении предела дальше масштабировать сложно.

---

# 2. 🔁 Репликация

Создаём несколько копий базы данных.

```python
              ┌──────────────┐
              │   Primary    │
              └──────┬───────┘
                     │
            ┌────────┴────────┐
            ▼                 ▼
      ┌──────────┐      ┌──────────┐
      │ Replica 1│      │ Replica 2│
      └──────────┘      └──────────┘
```

Primary обычно принимает записи:

```python
INSERT
UPDATE
DELETE
```

Реплики могут обслуживать чтение:

```python
SELECT
```

Это называется:

**Read Replicas / реплики для чтения.**

---

## ⚠️ Репликация не равна шардингу

При репликации:

```python
Primary
   │
   ├── Replica 1 → копия ВСЕХ данных
   └── Replica 2 → копия ВСЕХ данных
```

При шардинге:

```python
Shard 1 → пользователи 1–100000
Shard 2 → пользователи 100001–200000
Shard 3 → пользователи 200001–300000
```

То есть:

> **Репликация копирует данные. Шардинг распределяет данные.**

---

# 3. ⚖️ Read/Write Splitting

Можно разделить запросы:

```python
             Application
                  │
          ┌───────┴───────┐
          │               │
       WRITE             READ
          │               │
          ▼               ▼
       Primary         Replicas
```

Например:

```python
INSERT → Primary
UPDATE → Primary
DELETE → Primary

SELECT → Replica
```

### Проблема: replication lag

Реплика может отставать от Primary:

```python
Primary:
balance = 500

Replica:
balance = 1000
```

Если сразу после записи выполнить чтение с реплики, можно получить старое значение.

Это называется:

**Replication Lag.**

Поэтому для критичных чтений иногда используют Primary.

---

# 4. 🧩 Партиционирование — Partitioning

**Partitioning** — разделение одной логической таблицы на физические части — партиции.

Например:

```python
orders
├── orders_2024
├── orders_2025
└── orders_2026
```

Для приложения это может выглядеть как одна таблица:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01';
```

PostgreSQL может читать только необходимые партиции.

Это называется:

**Partition Pruning.**

---

## Виды partitioning

### RANGE

Разделение по диапазону:

```python
orders_2025
orders_2026
orders_2027
```

Часто используется для дат.

### LIST

Разделение по конкретным значениям:

```python
users_ru
users_fi
users_de
```

### HASH

Распределение по хешу ключа:

```python
hash(user_id) → partition
```

Полезно для равномерного распределения данных.

# 5. 🚀 Шардинг — Sharding

**Sharding** — горизонтальное распределение данных между несколькими независимыми узлами.

Например:

```python
                Application
                     │
             Sharding Router
             /       |       \
            ▼        ▼        ▼
        Shard 1   Shard 2   Shard 3
```

Каждый shard хранит **свою часть данных**.

Например, по `user_id`:

```python
user_id 1–100000     → Shard 1
user_id 100001–200000 → Shard 2
user_id 200001–300000 → Shard 3
```

---

# 🔑 Shard Key

**Shard Key** — поле, по которому определяется, в какой shard попадёт запись.

Например:

```python
user_id
```

Условно:

```python
shard = hash(user_id) % 4
```

Получаем:

```python
user_id → hash → shard
```

---

## ⚠️ Выбор shard key очень важен

Хороший shard key должен обеспечивать:

* равномерное распределение данных;
* равномерную нагрузку;
* возможность быстро определить нужный shard;
* минимальное количество запросов сразу к нескольким shards.

Плохой ключ может создать:

**Hot Shard** 🔥

Например:

```python
Все новые записи → Shard 1

Shard 1 🔥🔥🔥
Shard 2
Shard 3
Shard 4
```

Формально shards четыре, но фактически нагрузка концентрируется на одном.

---

# 6. 🔀 Scatter-Gather

Проблема возникает, если запрос не содержит shard key.

Например:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Если данные распределены по `user_id`, приложение может не знать, где находится пользователь.

Тогда запрос приходится отправлять во все shards:

```python
           Query
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
    Shard 1 Shard 2 Shard 3
       │     │     │
       └─────┼─────┘
             ▼
          Merge
```

Это:

**Scatter-Gather Query.**

Он может быть значительно дороже обычного запроса к одному shard.

---

# 7. 🗃️ Репликация + Шардинг

Эти технологии можно комбинировать.

Например:

```python
                 Application
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Shard 1    Shard 2    Shard 3
          │          │          │
       ┌──┴──┐     ┌─┴──┐     ┌─┴──┐
       ▼     ▼     ▼    ▼     ▼    ▼
     Replica Replica Replica Replica ...
```

Получаем:

* **Sharding** → распределяет данные;
* **Replication** → создаёт копии;
* **Read replicas** → масштабируют чтение;
* **Failover** → повышает отказоустойчивость.

---

# 8. 💾 Кэширование

Не обязательно каждое чтение отправлять в БД.

Можно использовать Redis:

```python
Application
     │
     ▼
   Redis
     │
     ├── cache hit → вернуть данные
     │
     └── cache miss
             │
             ▼
            DB
```

Например:

```python
GET user:123
```

Если данные есть в Redis:

```python
Redis → response
```

БД вообще не используется.

### Плюсы

* уменьшает нагрузку на БД;
* ускоряет чтение;
* хорошо работает для часто запрашиваемых данных.

### Проблема

**Cache Invalidation** — поддержание актуальности кэша.

---

# 9. 🔌 Connection Pooling

Большое количество соединений к БД тоже создаёт нагрузку.

Вместо:

```python
Request
   ↓
создать connection
   ↓
query
   ↓
закрыть connection
```

используют pool:

```python
          Connection Pool
        /      |      |     \
       DB     DB     DB      DB
```

Приложение переиспользует существующие соединения.

Например:

**PgBouncer** используется как connection pooler для PostgreSQL.

---

# 10. 🔍 Оптимизация запросов

Перед сложным масштабированием нужно проверить, действительно ли проблема в мощности БД.

Используют:

```python
EXPLAIN
EXPLAIN ANALYZE
```

Например:

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Можно обнаружить:

* Seq Scan вместо Index Scan;
* неправильный индекс;
* плохую оценку количества строк;
* дорогой JOIN;
* сортировку;
* большое количество прочитанных страниц.

Иногда один правильный индекс эффективнее, чем новый сервер.

# 11. 🧱 Основные уровни масштабирования

Практически удобно двигаться примерно так:

```python
1. Оптимизация SQL
        ↓
2. Индексы
        ↓
3. Connection Pooling
        ↓
4. Кэширование
        ↓
5. Vertical Scaling
        ↓
6. Read Replicas
        ↓
7. Partitioning
        ↓
8. Sharding
```

Это не строгий порядок для всех систем, но хорошая инженерная последовательность.

---

# 🆚 Partitioning vs Sharding

|                | Partitioning                                      | Sharding                       |
| -------------- | ------------------------------------------------- | ------------------------------ |
| Где происходит | В рамках БД                                       | Между узлами/БД                |
| Данные         | Части одной логической таблицы                    | Части общего набора данных     |
| Сервер         | Обычно один кластер                               | Несколько узлов                |
| Цель           | Управление большими таблицами, производительность | Горизонтальное масштабирование |
| Сложность      | Ниже                                              | Выше                           |
| JOIN           | Проще                                             | Может быть сложным             |
| Транзакции     | Проще                                             | Сложнее                        |

Упрощённо:

> **Partitioning — делим таблицу.**
> **Sharding — делим данные между серверами.**

---

# 🆚 Replication vs Sharding

|                               | Replication                   | Sharding            |
| ----------------------------- | ----------------------------- | ------------------- |
| Что происходит                | Копирование данных            | Разделение данных   |
| Каждый узел                   | Может иметь весь набор данных | Хранит только часть |
| Масштабирование чтения        | ✅                             | ✅                   |
| Масштабирование объёма данных | Ограниченно                   | ✅                   |
| Отказоустойчивость            | ✅                             | Может быть          |
| Сложность                     | Средняя                       | Высокая             |

# ⚠️ Основные проблемы масштабирования

При росте системы появляются:

### Replication Lag

```python
Primary ──► Replica
              ↓
          данные отстают
```

### Hot Shard

```python
Shard 1 🔥
Shard 2
Shard 3
Shard 4
```

### Cross-Shard Query

Запрос приходится выполнять на нескольких shards.

### Distributed Transactions

Транзакция затрагивает несколько узлов.

```python
Shard 1
   +
Shard 2
   +
Shard 3
```

Это значительно сложнее обычной локальной транзакции.

### Consistency

При репликации и распределении данных приходится выбирать баланс между:

* консистентностью;
* доступностью;
* задержкой.



# 🎤 Формулировка для собеседования

> **Масштабирование БД — это увеличение её способности выдерживать рост нагрузки и объёма данных. Начинают обычно с оптимизации запросов и индексов, затем используют кэширование, connection pooling и вертикальное масштабирование. Для масштабирования чтения применяют репликацию и read replicas. Для больших таблиц — partitioning. Когда одного узла уже недостаточно по объёму данных или нагрузке, используют sharding. При этом появляются дополнительные проблемы: replication lag, hot shards, cross-shard запросы и распределённые транзакции.**
