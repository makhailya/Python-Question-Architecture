# 🗂️ Партиционирование БД (Partitioning)

## 🎯 Ответ на собеседовании

**Партиционирование** — это разделение большой таблицы на несколько физических частей — **партиций**, при этом для приложения таблица обычно остаётся одной логической таблицей.

Главная цель — упростить работу с большими объёмами данных и ускорить запросы, которые позволяют определить нужные партиции.

Например, таблицу `orders` можно разделить по годам:

```python
orders
├── orders_2024
├── orders_2025
├── orders_2026
└── orders_2027
```

Запрос:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

может обратиться только к нужной партиции.

Это называется **Partition Pruning**.

---

## 🎤 Суперкоротко

> **Partitioning — это разделение одной большой таблицы на физические части внутри БД. Для приложения она остаётся логически одной таблицей. Основной выигрыш — управление большими объёмами данных и возможность читать только нужные партиции через partition pruning.**

```python
Одна логическая таблица
        │
        ├── Partition 1
        ├── Partition 2
        ├── Partition 3
        └── Partition 4
```

# 🧠 Зачем нужно партиционирование

Представим таблицу:

```python
orders
```

В ней:

```python
500 000 000 строк
```

Один огромный объект становится неудобным для:

* чтения;
* удаления старых данных;
* обслуживания;
* резервного копирования отдельных частей;
* управления историческими данными.

Можно разделить её:

```python
orders
│
├── orders_2023
├── orders_2024
├── orders_2025
└── orders_2026
```

При этом приложение продолжает обращаться к:

```python
SELECT *
FROM orders;
```

# 1. 📅 RANGE Partitioning

Данные распределяются по диапазонам.

Самый распространённый пример — даты.

```python
orders
├── orders_2024
├── orders_2025
├── orders_2026
└── orders_2027
```

Условно:

```python
2024-01-01 → 2025-01-01
2025-01-01 → 2026-01-01
2026-01-01 → 2027-01-01
```

Особенно удобно для:

* логов;
* событий;
* заказов;
* временных рядов;
* исторических данных.

---

# 2. 📋 LIST Partitioning

Разделение по конкретным значениям.

Например:

```python
users
├── users_europe
├── users_asia
└── users_america
```

Условно:

```python
Europe  → Partition 1
Asia    → Partition 2
America → Partition 3
```

Можно использовать:

* регион;
* тип клиента;
* статус;
* категорию.

---

# 3. #️⃣ HASH Partitioning

Данные распределяются по хешу ключа.

Условно:

```python
hash(user_id) → partition
```

Например:

```python
user_id
   ↓
  hash
   ↓
Partition 0 / 1 / 2 / 3
```

Полезно, когда нужно получить относительно равномерное распределение данных и нет естественного диапазона.

---

# 🆚 Три основных стратегии

| Тип   | Принцип         | Пример    |
| ----- | --------------- | --------- |
| RANGE | Диапазоны       | Дата      |
| LIST  | Список значений | Регион    |
| HASH  | Хеширование     | `user_id` |

---

# 4. 🚀 Partition Pruning

Одна из главных причин использовать партиционирование.

Допустим:

```python
orders
├── 2024
├── 2025
├── 2026
└── 2027
```

Запрос:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

PostgreSQL может определить, что нужны только:

```python
orders_2026
```

и не читать:

```python
orders_2024
orders_2025
orders_2027
```

Это называется:

**Partition Pruning**.

---

# 🔥 Почему это ускоряет запрос

Без partitioning:

```python
orders
500 млн строк
     ↓
поиск
```

С partitioning:

```python
orders
     │
     ├── 2024 ❌
     ├── 2025 ❌
     ├── 2026 ✅
     └── 2027 ❌
```

Но важно:

> Partitioning **не гарантирует ускорение любого запроса**.

Если запрос не содержит условия, позволяющего исключить партиции:

```python
SELECT *
FROM orders;
```

PostgreSQL может обратиться ко всем партициям.

---

# 5. 🛠️ Пример в PostgreSQL

Создаём partitioned table:

```python
CREATE TABLE orders (
    id BIGINT,
    created_at DATE NOT NULL,
    amount NUMERIC
) PARTITION BY RANGE (created_at);
```

Создаём партиции:

```python
CREATE TABLE orders_2025
PARTITION OF orders
FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE orders_2026
PARTITION OF orders
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

Теперь можно писать:

```python
INSERT INTO orders (id, created_at, amount)
VALUES (1, '2026-05-10', 1500);
```

PostgreSQL сам определит нужную партицию:

```python
orders_2026
```

---

# 6. 🧩 Партиционирование прозрачно для приложения

Приложение работает с родительской таблицей:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01';
```

Ему обычно не нужно писать:

```python
SELECT *
FROM orders_2026;
```

Маршрутизацией записей и чтением нужных партиций занимается PostgreSQL.

---

# 7. 🗑️ Удаление старых данных

Очень полезный сценарий — большие исторические таблицы.

Допустим:

```python
orders
├── 2023
├── 2024
├── 2025
└── 2026
```

Нужно удалить данные за 2023 год.

Без partitioning:

```python
DELETE FROM orders
WHERE created_at < '2024-01-01';
```

Это может быть огромной операцией.

С partitioning можно удалить или отсоединить целую партицию.

Концептуально:

```python
orders_2023
      ↓
отдельная физическая часть
      ↓
DROP / DETACH
```

Это может быть значительно эффективнее, чем удалять миллионы строк по одной.

---

# 8. 🧹 Partition Maintenance

Партиционирование удобно для управления жизненным циклом данных.

Например:

```python
2023 → архив
2024 → редко используется
2025 → активно читается
2026 → горячие данные
```

Можно управлять партициями независимо:

```python
orders_2023 → удалить
orders_2024 → архивировать
orders_2026 → активно обслуживать
```

# 9. 📊 Индексы и партиции

Индексы можно создавать на partitioned table.

Например:

```python
CREATE INDEX idx_orders_created_at
ON orders (created_at);
```

В PostgreSQL работа с индексами партиционированных таблиц имеет свои особенности: физически индексы существуют на отдельных партициях.

Условно:

```python
orders
│
├── orders_2025
│     └── index
│
├── orders_2026
│     └── index
│
└── orders_2027
      └── index
```

Это позволяет каждой партиции иметь собственную физическую структуру индекса.

# 10. 🧱 Partitioning ≠ Sharding

Очень важный вопрос.

### Partitioning

Разделяем таблицу на части:

```python
                PostgreSQL
                    │
                 orders
              /     |     \
             ▼      ▼      ▼
           2024    2025    2026
```

### Sharding

Разделяем данные между разными узлами:

```python
             Database Cluster
              /      |      \
             ▼       ▼       ▼
          Shard 1  Shard 2  Shard 3
```

Главное:

> **Partitioning — разделение таблицы внутри БД. Sharding — распределение данных между узлами.**

---

# 🆚 Partitioning vs Replication

|                               | Partitioning     | Replication        |
| ----------------------------- | ---------------- | ------------------ |
| Цель                          | Разделить данные | Скопировать данные |
| Данные                        | Части таблицы    | Копии              |
| Узлы                          | Может быть один  | Несколько          |
| Масштабирование чтения        | Ограниченно      | ✅                  |
| HA                            | ❌                | ✅                  |
| Управление большими таблицами | ✅                | Не основная цель   |

---

# 11. 🔥 Проблемы Partitioning

Партиционирование не является бесплатным.

### 1. Сложность архитектуры

Нужно правильно выбрать:

* partition key;
* количество партиций;
* размер диапазонов;
* стратегию создания новых партиций.

---

### 2. Слишком много партиций

Если создать тысячи или десятки тысяч маленьких партиций:

```python
orders
├── p1
├── p2
├── p3
├── ...
└── p10000
```

возникают дополнительные накладные расходы:

* планирование запросов;
* управление объектами;
* индексы;
* обслуживание.

Поэтому партиции не стоит делать чрезмерно мелкими без причины.

---

### 3. Неправильный partition key

Если запросы почти никогда не используют partition key:

```python
PARTITION BY RANGE (created_at)
```

но запросы постоянно идут по:

```python
WHERE user_id = 123
```

partition pruning может не помочь.

---

# 12. 🔑 Partition Key

**Partition Key** — колонка или набор колонок, по которым PostgreSQL определяет партицию.

Например:

```python
PARTITION BY RANGE (created_at)
```

Здесь:

```python
created_at
```

— partition key.

Хороший ключ желательно выбирать исходя из:

* характера данных;
* запросов;
* распределения нагрузки;
* жизненного цикла данных;
* необходимости удалять/архивировать группы данных.

---

# 13. 🧩 Subpartitioning

Партиции можно дополнительно разделять.

Например:

```python
orders
│
├── 2025
│    ├── Europe
│    └── Asia
│
└── 2026
     ├── Europe
     └── Asia
```

Это называется:

**Subpartitioning**.

Но сложность архитектуры при этом увеличивается.

---

# 14. 📈 Partitioning и масштабирование

Важно правильно понимать:

> **Partitioning само по себе не является полноценным горизонтальным масштабированием.**

Оно может улучшить:

* управление большими таблицами;
* partition pruning;
* обслуживание данных;
* удаление старых данных;
* локализацию операций.

Но все партиции могут находиться на одном сервере:

```python
             One PostgreSQL
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        p2024    p2025    p2026
```

Если этот сервер перегружен CPU/RAM, partitioning само по себе проблему не решит.

# 🎤 Формулировка для собеседования

> **Партиционирование — это разделение большой таблицы на физические части, называемые партициями, при сохранении одной логической таблицы для приложения. В PostgreSQL основные стратегии — RANGE, LIST и HASH. Один из главных механизмов оптимизации — partition pruning, когда планировщик исключает ненужные партиции из запроса. Партиционирование особенно полезно для больших таблиц, временных данных и управления жизненным циклом данных. Оно отличается от sharding тем, что partitioning обычно происходит внутри одного экземпляра или кластера БД, а sharding распределяет данные между независимыми узлами.**

## 📌 Формула

```python
Partitioning
=
One logical table
+
Multiple physical partitions
+
Partition Key
+
Partition Pruning
+
Better data lifecycle management
```

### Три основные стратегии:

```python
RANGE
→ диапазоны

LIST
→ конкретные значения

HASH
→ хеширование
```

### Главное отличие:

```python
Partitioning → делим таблицу
Replication  → копируем данные
Sharding     → распределяем данные между узлами
```
