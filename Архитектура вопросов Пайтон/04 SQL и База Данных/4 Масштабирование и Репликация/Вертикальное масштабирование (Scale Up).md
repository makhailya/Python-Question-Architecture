# 🖥️ Вертикальное масштабирование (Scale Up)

## 🎯 Ответ на собеседовании

**Вертикальное масштабирование (Scale Up)** — это увеличение вычислительных ресурсов **одного сервера**, на котором работает база данных.

Увеличивают:

* CPU;
* RAM;
* объём и скорость SSD;
* IOPS;
* сетевую пропускную способность.

При этом архитектура приложения и сама БД обычно остаются на **одном узле**.

---

## 🎤 Суперкоротко

> **Scale Up — делаем один сервер мощнее.** Добавляем CPU, RAM, более быстрый диск и сеть вместо добавления новых серверов.

```python
Сервер
│
├── CPU  4 → 16 ядер
├── RAM  16 → 64 GB
├── SSD  → более быстрый NVMe
└── IOPS → ↑
```

---

# 🧠 Пример

Допустим, PostgreSQL работает на сервере:

```python
CPU: 4 cores
RAM: 16 GB
SSD: 500 GB
```

Нагрузка выросла, и сервер начал упираться в RAM и CPU.

Вместо добавления нескольких серверов можно сделать:

```python
CPU: 16 cores
RAM: 64 GB
SSD: 2 TB NVMe
```

Это и есть:

**Vertical Scaling / Scale Up.**

---

# 📈 Что именно масштабируют

### CPU

Больше CPU позволяет обрабатывать больше вычислений параллельно.

Особенно важно для:

* сложных запросов;
* JOIN;
* сортировок;
* агрегаций;
* большого количества одновременных операций.

---

### RAM

Дополнительная RAM позволяет хранить больше полезных данных в памяти.

Для PostgreSQL это особенно важно, потому что кэширование страниц уменьшает количество обращений к диску.

Условно:

```python
RAM
 ↓
больше данных в памяти
 ↓
меньше I/O
 ↓
быстрее запросы
```

---

### SSD / IOPS

Более быстрый диск помогает при:

* большом количестве случайных чтений;
* записи;
* WAL;
* checkpoint;
* работе с большими объёмами данных.

Важно различать:

**объём диска** и **скорость диска**.

Можно увеличить:

```python
500 GB → 2 TB
```

но это не обязательно увеличит производительность.

А можно заменить диск на более быстрый:

```python
SATA SSD → NVMe
```

и получить более высокую производительность I/O.

---

# 🔄 Scale Up vs Scale Out

Это один из главных вопросов на собеседовании.

## Scale Up

```python
      Один сервер
          │
    ┌─────┴─────┐
    │           │
   CPU         RAM
    ↑           ↑
  больше      больше
```

Увеличиваем мощность существующего сервера.

## Scale Out

```python
       Load Balancer
        /    |    \
       ↓     ↓     ↓
    Server Server Server
```

Добавляем новые серверы.

**Scale Out = Horizontal Scaling.**

---

# 🆚 Сравнение

|                        | Scale Up                         | Scale Out                                  |
| ---------------------- | -------------------------------- | ------------------------------------------ |
| Подход                 | Усилить сервер                   | Добавить серверы                           |
| Архитектура            | Проще                            | Сложнее                                    |
| Изменение приложения   | Обычно минимальное               | Может потребоваться                        |
| Верхний предел         | Есть                             | Выше                                       |
| Отказоустойчивость     | Сам по себе не повышает          | Может повысить                             |
| Стоимость              | Мощное железо может быть дорогим | Можно использовать несколько обычных узлов |
| Распределённые системы | Не требуются                     | Часто требуются                            |

---

# ✅ Преимущества Scale Up

### 1. Простота

Не нужно распределять данные между серверами.

```python
Application
     ↓
 PostgreSQL
```

вместо:

```python
Application
     ↓
Distributed Database
   /    |    \
 DB     DB     DB
```

---

### 2. Не требуется распределённая логика

Не нужно решать:

* на какой сервер отправить запрос;
* как распределить данные;
* как синхронизировать узлы;
* как выполнять cross-shard запросы;
* как организовать распределённые транзакции.

---

### 3. Можно быстро получить прирост производительности

Если проблема действительно в нехватке ресурсов, увеличение RAM/CPU/IOPS может дать существенный эффект без изменения приложения.

---

# ❌ Недостатки Scale Up

## 1. Физический предел

Нельзя бесконечно увеличивать:

```python
CPU ↑
RAM ↑
SSD ↑
```

В какой-то момент сервер достигнет максимальной конфигурации.

---

## 2. Дорогие компоненты

Очень мощный сервер может стоить значительно дороже нескольких обычных.

---

## 3. Single Point of Failure

Если база работает на одном сервере:

```python
       PostgreSQL
           │
        Server
           ❌
```

отказ сервера может привести к недоступности БД.

**Scale Up сам по себе не обеспечивает отказоустойчивость.**

Для этого нужны дополнительные механизмы, например репликация и failover.

---

## 4. Нельзя бесконечно решить проблему ростом железа

Если нагрузка продолжает расти:

```python
Server
  ↓
CPU 90%
  ↓
Upgrade
  ↓
CPU 60%
  ↓
Рост нагрузки
  ↓
CPU 90%
  ↓
Upgrade
  ↓
...
```

в какой-то момент потребуется **Scale Out** или более распределённая архитектура.

---

# 🗄️ Scale Up для PostgreSQL

Для PostgreSQL вертикальное масштабирование может выглядеть так:

```python
PostgreSQL Server

CPU       ↑
RAM       ↑
NVMe      ↑
IOPS      ↑
Network   ↑
```

Но перед покупкой нового сервера стоит проверить:

```python
EXPLAIN ANALYZE
```

и выяснить, где именно находится bottleneck.

Например, проблема может быть не в CPU, а в:

```python
плохом SQL
    ↓
Seq Scan
    ↓
огромное количество строк
```

В таком случае правильный индекс может быть эффективнее увеличения сервера.

---

# 🔍 Масштабирование не равно оптимизация

Важно различать:

### Оптимизация

Уменьшаем стоимость существующей операции:

```python
плохой запрос
    ↓
индекс / оптимизация SQL
    ↓
меньше CPU + I/O
```

### Scale Up

Добавляем ресурсы:

```python
CPU 4 → 16
RAM 16 → 64 GB
```

Правильный подход:

> **Сначала найти bottleneck, затем выбрать способ масштабирования.**

---

# ⚠️ Когда Scale Up — хороший выбор

Scale Up особенно удобен, если:

* БД пока помещается на одном сервере;
* архитектура должна оставаться простой;
* нет необходимости распределять данные;
* нагрузка выросла умеренно;
* приложение плохо готово к распределённой архитектуре;
* нужно быстро увеличить производительность.

---

# 🚀 Когда Scale Up уже недостаточно

Если:

```python
RAM → максимум
CPU → максимум
Disk I/O → максимум
```

и нагрузка продолжает расти, рассматривают:

```python
Read Replicas
Partitioning
Sharding
Scale Out
```

Например:

```python
                 Application
                      │
                Load Balancer
                      │
             ┌────────┴────────┐
             ▼                 ▼
         DB Primary       Read Replica
             │                 │
             └───────┬─────────┘
                     ▼
                 PostgreSQL
```

---

# 🧩 Важное различие

**Scale Up не означает увеличение диска.**

Можно увеличить только:

```python
RAM
```

или:

```python
CPU
```

или:

```python
IOPS
```

или несколько ресурсов одновременно.

Цель — устранить конкретное ограничение.

# 🎤 Формулировка для собеседования

> **Вертикальное масштабирование, или Scale Up, — это увеличение ресурсов существующего сервера: CPU, RAM, дисковой подсистемы и сети. Для БД это самый простой способ увеличить производительность, потому что не требуется распределять данные между узлами. Основные недостатки — физический предел масштабирования, стоимость мощного оборудования и то, что Scale Up сам по себе не решает проблему отказоустойчивости. Если одного узла становится недостаточно, рассматривают горизонтальное масштабирование, репликацию, partitioning или sharding.**
