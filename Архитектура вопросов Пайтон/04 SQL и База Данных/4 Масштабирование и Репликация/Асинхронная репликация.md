# Асинхронная репликация 🔄

## 🎤 Короткий ответ

**Асинхронная репликация** — это режим, при котором Primary **не ждёт подтверждения от реплик перед тем, как подтвердить запись клиенту**. Поэтому запись быстрее и доступность выше, но реплики могут отставать, а при отказе Primary существует риск потери последних изменений, которые ещё не успели попасть на реплику.

---

## 🎯 Формула для собеседования

```text id="q7m3x9"
Client
  ↓
Primary
  ↓
COMMIT
  ↓
Client получает OK
  ↓
Primary → Replica
         ↓
       позже
```

**Главная мысль:**

> Primary подтверждает запись, не дожидаясь ACK от реплик.

---

# 1. Что такое асинхронная репликация

Есть:

```text id="m4n8c2"
          Primary
         /       \
        ↓         ↓
   Replica 1   Replica 2
```

Клиент выполняет:

```sql id="v6q2r8"
INSERT INTO users (name)
VALUES ('Ilya');
```

Primary выполняет запись и может сразу ответить клиенту:

```text id="x3m7n5"
Client
  │
  │ INSERT
  ↓
Primary
  │
  ├──→ COMMIT
  │
  └──→ Replica
          ↓
        позже
```

Primary **не ждёт**, пока Replica подтвердит получение изменения.

---

# 2. Главное отличие от синхронной

### Синхронная

```text id="p8c4m1"
Primary
   ↓
Replica
   ↓
ACK
   ↓
Primary
   ↓
Client
```

### Асинхронная

```text id="n5x9q3"
Primary
   ├──→ Client
   │      ↑
   │    COMMIT
   │
   └──→ Replica
          ↓
        позже
```

То есть:

```text id="r2m7v8"
Синхронная:
WRITE → ждём Replica → COMMIT

Асинхронная:
WRITE → COMMIT → Replica догоняет позже
```

---

# 3. Почему она быстрее

При асинхронной репликации нет необходимости ждать сетевой round trip до реплики.

Синхронно:

```text id="c7n3m9"
Primary
   ↓
сеть
   ↓
Replica
   ↓
ACK
   ↓
сеть
   ↓
Primary
   ↓
COMMIT
```

Асинхронно:

```text id="x5q8m2"
Primary
   ↓
COMMIT
   ↓
Client
```

Репликация продолжается независимо.

Поэтому обычно:

* ниже latency записи;
* выше потенциальный throughput;
* меньше зависимость записи от состояния реплики.

---

# 4. Главный недостаток — replication lag

Поскольку реплика может получать изменения позже:

```text id="m8r4c1"
Primary
  │
  │ LSN = 1000
  │
  ↓
Replica
  │
  │ LSN = 950
```

Реплика отстаёт.

Это называется:

**Replication Lag — задержка репликации.**

Упрощённо:

```text id="q6v2n9"
Primary: 1000
Replica: 950

Lag ≈ 50 единиц WAL/позиции
```

Точная метрика зависит от СУБД и того, что именно измеряется.

---

# 5. Что видит клиент

Возникает важный эффект:

```text id="z4m8c2"
Client
  ↓
Primary
  ↓
INSERT
  ↓
OK
```

Сразу после этого:

```text id="n7x3q5"
Client
  ↓
Replica
  ↓
SELECT
```

реплика может **ещё не видеть запись**.

Получается:

```text id="p2r8m4"
WRITE → Primary
READ  → Replica

WRITE уже успешен,
но READ ещё не видит изменение.
```

Это один из вариантов **eventual consistency**.

---

# 6. Eventual Consistency

При нормальной работе:

```text id="c5m9x2"
Primary
   ↓
изменение
   ↓
Replica
```

через некоторое время реплика догоняет Primary.

То есть:

```text id="v8q3n6"
сейчас:
Primary ≠ Replica

через некоторое время:
Primary ≈ Replica
```

Поэтому асинхронная репликация часто приводит к модели **eventual consistency** для чтения с реплик.

Важно:

> Это не означает, что вся система обязательно является eventually consistent во всех аспектах. Речь прежде всего о согласованности данных между источником записи и отстающими репликами.

---

# 7. Самый важный риск — отказ Primary

Представим:

```text id="k3m7q9"
Primary
  │
  │ INSERT
  ↓
COMMIT → Client получил OK
  │
  X
Primary crashed
```

Но изменение ещё не дошло до Replica:

```text id="x6n2v4"
Replica
  │
  └── старое состояние
```

Если теперь Replica становится новым Primary:

```text id="r9c4m8"
старые данные
+
последние изменения потеряны
```

Поэтому:

> При асинхронной репликации существует риск потери последних подтверждённых изменений при отказе Primary, если они ещё не были реплицированы.

---

# 8. Пример с банковским балансом

Допустим:

```text id="m5q8c2"
balance = 10 000
```

Клиент снимает:

```text id="v3n7x9"
2 000
```

Primary:

```text id="p8r4m1"
balance = 8 000
```

Клиент получает:

```text id="q6m2v8"
OK
```

Но Replica ещё содержит:

```text id="x9c3n5"
balance = 10 000
```

Если Primary сразу выходит из строя и система переключается на эту реплику, может возникнуть расхождение.

---

# 9. Replication Lag

Lag может появляться из-за:

* высокой нагрузки на Primary;
* медленной сети;
* высокой нагрузки на Replica;
* медленного диска;
* большого потока WAL;
* долгого применения изменений на реплике.

Например:

```text id="r4m8x2"
Primary
   │
   │ 100 MB/s изменений
   ↓
Replica
   │
   │ применяет 70 MB/s
   ↓
Lag растёт
```

Пока скорость применения ниже скорости генерации изменений, отставание увеличивается.

---

# 10. Lag может уменьшиться

Если Primary генерирует:

```text id="c7n2m5"
50 MB/s
```

а Replica применяет:

```text id="v8q4x1"
100 MB/s
```

реплика постепенно догонит Primary.

То есть важно смотреть не только на наличие lag, но и на **скорость его изменения**.

```text id="m3r7n9"
Lag растёт   → Replica не успевает
Lag уменьшается → Replica догоняет
```

---

# 11. Read Scaling

Одна из главных причин использования реплик:

```text id="x5m8q2"
              Primary
              ↓ WRITE
               │
       ┌───────┴───────┐
       ↓               ↓
   Replica 1       Replica 2
       ↓               ↓
     READ            READ
```

Записи идут на Primary.

Чтения можно распределять между репликами.

Это позволяет разгрузить Primary.

---

# 12. Но Read Replica может вернуть устаревшие данные

Например:

```text id="n4q8v2"
POST /payment
      ↓
Primary
      ↓
200 OK
```

Затем:

```text id="c7m3x9"
GET /payment
      ↓
Replica
      ↓
404 / старое состояние
```

если реплика ещё не успела применить изменение.

Это называется **stale read**.

---

# 13. Как решают проблему stale reads

Один из вариантов — после критической записи читать с Primary:

```text id="p8x2m5"
WRITE → Primary
READ  → Primary
```

Для обычных чтений:

```text id="r3n7c9"
READ → Replica
```

Другие варианты зависят от СУБД и архитектуры:

* routing чтений;
* ожидание определённой позиции репликации;
* session/causal consistency;
* sticky reads;
* synchronous replication для отдельных гарантий.

---

# 14. Асинхронная репликация и WAL

В PostgreSQL изменения передаются репликам через **WAL**.

Упрощённо:

```text id="m6q9x3"
Transaction
    ↓
WAL на Primary
    ↓
передача WAL
    ↓
Standby
    ↓
replay WAL
```

При асинхронной репликации Primary не обязан ждать, пока Standby подтвердит этот процесс перед ответом клиенту.

---

# 15. Асинхронная репликация не означает отсутствие надёжности

Это важный нюанс.

Асинхронная репликация всё равно даёт:

* копию данных на реплике;
* возможность failover;
* возможность масштабировать чтение;
* дополнительную защиту от отказа Primary.

Просто гарантия сохранности **самых последних изменений** слабее, чем при синхронной репликации.

---

# 16. Асинхронная репликация и backup

Как и в случае синхронной репликации:

```text id="v2m7q4"
Replica ≠ Backup
```

Если пользователь случайно удалил данные:

```sql id="x8n3c5"
DELETE FROM users;
```

изменение тоже может попасть на реплику.

Поэтому нужны отдельные:

* backup;
* WAL archiving;
* PITR;
* процедуры восстановления.

---

# 17. Почему асинхронная репликация часто удобна

Она уменьшает зависимость записи от реплик:

```text id="q5r8m2"
Replica slow ❌

       ↓

Primary
       ↓
может продолжать принимать WRITE
```

При синхронной схеме:

```text id="c3n7x9"
Replica slow ❌
       ↓
Primary ждёт
       ↓
WRITE latency ↑
```

При асинхронной:

```text id="m8v2q6"
Replica slow ❌
       ↓
Lag ↑
       ↓
Primary продолжает WRITE
```

Это принципиальная разница.

---

# 18. Цена асинхронности

Получаем классический компромисс:

```text id="r7m3x8"
Асинхронная репликация
        │
        ├── Latency записи ↓
        ├── Throughput записи ↑
        ├── Доступность записи ↑
        │
        └── Replication Lag ↑
                 │
                 └── риск потери
                     последних изменений ↑
```

---

# 19. Сравнение с синхронной

|                                                    | Синхронная                                      | Асинхронная  |
| -------------------------------------------------- | ----------------------------------------------- | ------------ |
| Primary ждёт реплику                               | Да                                              | Нет          |
| ACK от реплики перед подтверждением                | Требуется согласно политике                     | Не требуется |
| Latency записи                                     | Выше                                            | Ниже         |
| Replication lag                                    | Может быть ограничен требованиями подтверждения | Возможен     |
| Stale reads с реплики                              | Зависит от архитектуры/гарантий                 | Возможны     |
| Риск потери последних изменений при отказе Primary | Ниже                                            | Выше         |
| Зависимость записи от реплики                      | Выше                                            | Ниже         |
| Доступность записи при проблемах реплики           | Может снижаться                                 | Обычно выше  |

# 20. Типичный production-сценарий

```text id="x4m8n2"
                 ┌─────────────┐
                 │   Primary   │
                 │   WRITE     │
                 └──────┬──────┘
                        │
                 async replication
                  ┌─────┴─────┐
                  ↓           ↓
             Replica 1    Replica 2
                READ          READ
```

Клиент:

```text id="m7q3v8"
WRITE → Primary
READ  → Replica
```

Но для операций, где критична свежесть:

```text id="c5n9x2"
WRITE → Primary
READ  → Primary
```

---

# 21. Важный вопрос на собеседовании

### «Может ли клиент получить OK, а данные потом потеряться?»

**Да, при определённых условиях.**

Например:

```text id="v8m2r6"
1. Primary получил WRITE
2. Primary подтвердил COMMIT клиенту
3. Replica ещё не получила изменение
4. Primary вышел из строя
5. Failover произошёл на отстающую Replica
```

Последняя подтверждённая запись может быть потеряна.

Именно это является одним из главных trade-off асинхронной репликации.

---

# 22. Важный нюанс: потеря данных ≠ потеря всей БД

Речь обычно идёт не о том, что:

```text
вся база исчезнет
```

а о том, что:

```text
последние изменения,
которые ещё не успели реплицироваться,
могут отсутствовать на новой Primary.
```

# 🔥 Главное для собеседования

### Что такое асинхронная репликация?

> Это режим, при котором Primary не ждёт подтверждения от реплик перед подтверждением записи клиенту. Реплики получают и применяют изменения позже.

### Главный плюс?

**Меньше latency и выше доступность записи.**

### Главный минус?

**Replication lag и риск потери последних подтверждённых изменений при отказе Primary.**

### Что такое Replication Lag?

> Отставание реплики от Primary по состоянию репликации.

```text id="k4m8x2"
Primary  →  LSN 1000
Replica  →  LSN 950

       ↓

Replication Lag
```

### Что такое stale read?

> Чтение с реплики, которая ещё не успела применить последние изменения.

```text id="n7q3c5"
WRITE → Primary
          ↓
        COMMIT
          ↓
READ → Replica
          ↓
старые данные
```

## 🧠 Финальная формула

```text id="x8m4r2"
              Client
                │
               WRITE
                ↓
             Primary
                │
          ┌─────┴─────┐
          ↓           ↓
       COMMIT      WAL → Replica
          ↓                  ↓
       Client              позже
                              ↓
                           Replica
```

```text id="q3v7n9"
Асинхронная репликация
        ↓
Primary не ждёт ACK
        ↓
быстрее WRITE
        ↓
Replica догоняет позже
        ↓
Replication Lag возможен
        ↓
stale reads возможны
        ↓
при отказе Primary
последние не реплицированные изменения
могут быть потеряны
```

**Короткая формула для запоминания:**

> **Асинхронная = Primary не ждёт реплику → запись быстрее → возможен lag → возможны устаревшие чтения и потеря последних изменений при отказе Primary.**
