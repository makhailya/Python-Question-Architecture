# Seq Scan в PostgreSQL 🔎

## 🎯 Ответ на собеседовании

**Seq Scan (Sequential Scan)** — последовательное сканирование таблицы, при котором PostgreSQL читает страницы таблицы последовательно и проверяет строки на соответствие условию.

`Seq Scan` не является автоматически плохим. Он часто оптимален, когда нужно прочитать большую часть таблицы, таблица небольшая или условие имеет низкую селективность.

---

## 🎤 Суперкоротко

```python
Seq Scan
    ↓
последовательно читаем таблицу
    ↓
проверяем строки
    ↓
возвращаем подходящие
```

Главное:

> **Seq Scan — это не ошибка и не признак отсутствия индекса. Это один из вариантов плана, который PostgreSQL выбирает на основе стоимости.**

---

# 1. Простой пример

Есть таблица:

```python
SELECT *
FROM users;
```

PostgreSQL может выбрать:

```python
Seq Scan on users
```

То есть последовательно прочитать таблицу.

Если таблица содержит:

```python
1 000 000 строк
```

PostgreSQL условно идёт:

```python
Страница 1
    ↓
Страница 2
    ↓
Страница 3
    ↓
...
Страница N
```

и читает данные последовательно.

---

# 2. Seq Scan с WHERE

Например:

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE age > 30;
```

План может выглядеть так:

```python
Seq Scan on users
  Filter: (age > 30)
```

В этом случае PostgreSQL:

```python
Table
  ↓
Seq Scan
  ↓
проверка age > 30
  ↓
подходящие строки
```

Условие после `Filter` проверяется для строк, которые были прочитаны.

---

# 3. Почему Seq Scan может быть быстрее индекса

Допустим, таблица:

```python
1 000 000 строк
```

Запрос:

```python
WHERE age > 18
```

и условию соответствует:

```python
900 000 строк
```

Использовать индекс для поиска 900 000 строк может оказаться невыгодно.

Проще:

```python
прочитать таблицу последовательно
```

чем:

```python
индекс
  ↓
найти огромное количество строк
  ↓
ходить по таблице за каждой строкой
```

Поэтому PostgreSQL может выбрать:

```python
Seq Scan
```

---

# 4. Seq Scan и селективность

**Селективность** — насколько сильно условие сокращает количество строк.

### Высокая селективность

```python
WHERE id = 123
```

Из:

```python
1 000 000 строк
```

получаем:

```python
1 строку
```

Индекс обычно очень полезен.

---

### Низкая селективность

```python
WHERE is_active = true
```

Допустим:

```python
1 000 000 строк
↓
900 000 строк
```

Индекс может не дать преимущества.

PostgreSQL может выбрать:

```python
Seq Scan
```

---

# 5. Seq Scan на маленькой таблице

Даже если есть индекс:

```python
CREATE INDEX users_email_idx
ON users(email);
```

PostgreSQL может использовать:

```python
Seq Scan
```

если таблица очень маленькая.

Например:

```python
users = 100 строк
```

Чтение небольшой таблицы последовательно может быть дешевле, чем:

```python
Index
  ↓
Table
```

из-за накладных расходов на использование индекса.

---

# 6. Что показывает EXPLAIN

Например:

```python
EXPLAIN
SELECT *
FROM users
WHERE age > 30;
```

Можно получить:

```python
Seq Scan on users
  (cost=0.00..1800.00 rows=500000 width=64)
  Filter: (age > 30)
```

Разберём:

### `Seq Scan on users`

Последовательно читаем таблицу `users`.

### `cost`

```python
0.00..1800.00
```

Оценочная стоимость выполнения узла.

Это **не миллисекунды**.

### `rows`

```python
rows=500000
```

Планировщик ожидает получить примерно 500 000 строк.

### `width`

```python
width=64
```

Оценочный средний размер строки.

### `Filter`

```python
Filter: (age > 30)
```

Условие фильтрации.

---

# 7. Seq Scan + EXPLAIN ANALYZE

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE age > 30;
```

Например:

```python
Seq Scan on users
  (cost=0.00..1800.00 rows=500000 width=64)
  (actual time=0.020..120.000 rows=480000 loops=1)
  Filter: (age > 30)
  Rows Removed by Filter: 520000
```

Здесь появляется фактическая информация.

Планировщик ожидал:

```python
rows=500000
```

Фактически:

```python
actual rows=480000
```

И PostgreSQL отбросил:

```python
Rows Removed by Filter: 520000
```

---

# 8. `Rows Removed by Filter`

Очень полезный показатель.

Например:

```python
Rows Removed by Filter: 900000
```

Это означает, что огромное количество прочитанных строк не прошло условие.

Например:

```python
Seq Scan
    ↓
1 000 000 строк прочитано
    ↓
900 000 отброшено
    ↓
100 000 возвращено
```

Это может быть поводом проверить, можно ли сделать запрос эффективнее.

Но само по себе большое значение ещё **не доказывает**, что нужен индекс.

Нужно смотреть весь план и стоимость запроса.

---

# 9. Seq Scan vs Index Scan

Представим:

```python
1 000 000 строк
```

### Запрос 1

```python
WHERE id = 500000
```

Ожидаем:

```python
1 строка
```

Часто:

```python
Index Scan
```

будет выгоднее.

---

### Запрос 2

```python
WHERE age > 18
```

Ожидаем:

```python
950 000 строк
```

Часто:

```python
Seq Scan
```

может быть выгоднее.

---

# 10. Seq Scan не означает «индекс не работает»

Допустим:

```python
CREATE INDEX idx_users_age
ON users(age);
```

А PostgreSQL показывает:

```python
Seq Scan on users
```

Это **не значит**, что индекс сломан.

Planner мог решить:

```python
Seq Scan
↓
дешевле
```

чем:

```python
Index Scan
↓
дороже
```

PostgreSQL выбирает план с минимальной **оценочной стоимостью**.

---

# 11. Когда Seq Scan действительно стоит исследовать

Например, запрос:

```python
SELECT *
FROM users
WHERE id = 123456;
```

А план:

```python
Seq Scan on users
  Filter: (id = 123456)
```

и:

```python
users = 10 000 000 строк
```

при этом `id` уникальный.

Тогда уже стоит проверить:

* существует ли индекс;
* используется ли правильное условие;
* актуальна ли статистика;
* типы данных;
* нет ли преобразования типов;
* почему planner считает Seq Scan дешевле.

---

# 12. Статистика

PostgreSQL принимает решение на основе статистики.

Если статистика устарела, planner может неправильно оценить:

```python
rows
```

Например:

```python
rows=10
actual rows=500000
```

После обновления статистики:

```python
ANALYZE users;
```

план может измениться.

---

# 13. Seq Scan и `BUFFERS`

Можно использовать:

```python
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE age > 30;
```

Например:

```python
Seq Scan on users
  (actual time=0.020..120.000 rows=480000 loops=1)
  Buffers: shared hit=5000 read=3000
```

Это позволяет дополнительно понять, сколько страниц было:

```python
shared hit
```

и сколько пришлось прочитать:

```python
shared read
```

---

# 14. Seq Scan читает страницы, а не «строки по одной»

Важно не представлять Seq Scan буквально как:

```python
строка 1
строка 2
строка 3
...
```

Физически PostgreSQL работает со **страницами (blocks/pages)** таблицы.

Упрощённо:

```python
Disk / Cache
    ↓
Page 1
    ↓
Page 2
    ↓
Page 3
    ↓
...
```

Внутри страниц находятся строки.

Поэтому точнее говорить:

> PostgreSQL последовательно сканирует страницы таблицы и проверяет находящиеся в них строки.

---

# 15. Почему последовательное чтение эффективно

Современные диски и файловая система хорошо работают с последовательным чтением.

Сравнение:

```python
Seq Scan:

Page 1 → Page 2 → Page 3 → Page 4
```

против:

```python
Index Scan:

Index
 ↓
Page 150
 ↓
Page 4
 ↓
Page 900
 ↓
Page 17
```

При большом количестве найденных строк последовательное чтение может оказаться эффективнее.

---

# 16. Как PostgreSQL выбирает Seq Scan

Упрощённо planner сравнивает варианты:

```python
Seq Scan
    VS
Index Scan
    VS
Bitmap Scan
```

и оценивает их стоимость.

Учитываются различные факторы:

* размер таблицы;
* количество ожидаемых строк;
* селективность;
* статистика;
* стоимость чтения страниц;
* стоимость обращения к индексу;
* стоимость получения строк из таблицы;
* сортировка и другие операции плана.

После этого выбирается наиболее выгодный план по оценке planner.

---

# 17. Пример из практики

Есть:

```python
orders
```

и:

```python
10 000 000 строк
```

Запрос:

```python
SELECT *
FROM orders
WHERE status = 'completed';
```

Если:

```python
90% заказов = completed
```

то:

```python
Seq Scan
```

может быть абсолютно нормальным.

Но если:

```python
0.01% заказов = completed
```

а индекса по `status` нет, можно исследовать возможность индекса:

```python
CREATE INDEX idx_orders_status
ON orders(status);
```

После этого снова:

```python
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE status = 'completed';
```

и сравнить планы.

---

# 18. Важная мысль про индексы

Нельзя применять правило:

```python
Seq Scan → плохо
Index Scan → хорошо
```

Правильнее:

```python
Seq Scan
    ↓
может быть оптимальным

Index Scan
    ↓
может быть оптимальным

Bitmap Scan
    ↓
может быть оптимальным
```

Всё зависит от конкретного запроса и данных.

---

## 🧠 Главное

```python
Seq Scan
    ↓
последовательное сканирование страниц таблицы
    ↓
проверка строк
    ↓
Filter
    ↓
результат
```

**Чаще подходит**, когда:

* таблица небольшая;
* нужно прочитать большую часть таблицы;
* условие имеет низкую селективность;
* последовательное чтение дешевле обращения через индекс.

**Не является автоматически проблемой**, если PostgreSQL выбрал его осознанно.

На собеседовании:

> **Seq Scan — последовательное сканирование таблицы. PostgreSQL читает страницы таблицы последовательно и проверяет строки. Если запрос возвращает значительную часть таблицы или таблица небольшая, Seq Scan может быть быстрее Index Scan. Поэтому сам факт Seq Scan не означает проблему — нужно смотреть на весь план, стоимость и фактические показатели EXPLAIN ANALYZE.**
