# 🔗 One-to-One (1:1) — связь один к одному в SQL

## 🎤 Формула для собеседования

**One-to-One (1:1)** — это связь между двумя таблицами, при которой одной записи первой таблицы соответствует не более одной записи второй таблицы, и наоборот.

В PostgreSQL обычно реализуется через **Foreign Key + UNIQUE** либо через общий Primary Key.

Пример: пользователь и его профиль.

```sql
user_id BIGINT NOT NULL UNIQUE REFERENCES users(id)
```

- `FOREIGN KEY` — гарантирует существование связанной записи.
- `UNIQUE` — запрещает несколько профилей у одного пользователя.
- `NOT NULL` — запрещает профиль без пользователя.

**Важно:** такая реализация гарантирует максимум один профиль на пользователя, но не обязывает каждого пользователя иметь профиль.

## 1. Как работает связь 1:1

Представим Backend-приложение с пользователями.

У каждого пользователя может быть один дополнительный профиль, содержащий биографию и аватар.

**Таблица users**

| id (PK) | username |
|---|---|
| 1 | ilya |
| 2 | anna |
| 3 | petr |

**Таблица profiles**

| id (PK) | user_id (FK, UNIQUE) | bio |
|---|---|---|
| 101 | 1 | Python Developer |
| 102 | 2 | Designer |

Схематично:

```text
users                         profiles
┌────────────────┐            ┌────────────────────┐
│ id (PK)        │◄───────────│ user_id (FK, UNIQUE)│
│ username       │    1:1     │ id (PK)            │
└────────────────┘            │ bio                │
                              └────────────────────┘
```

Иван имеет один профиль, Анна — один, а Пётр пока не имеет профиля.

Это допустимая связь 1:1.

**Главное правило:** один пользователь не может иметь два профиля, и один профиль не может принадлежать двум пользователям.

## 2. Реализация One-to-One в PostgreSQL

Создадим две таблицы.

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE profiles (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE REFERENCES users(id),
    bio TEXT
);
```

Разберём ключевую строку:

```sql
user_id BIGINT NOT NULL UNIQUE REFERENCES users(id)
```

| Элемент | За что отвечает |
|---|---|
| `user_id` | Идентификатор связанного пользователя |
| `BIGINT` | Тип данных |
| `NOT NULL` | Профиль обязательно принадлежит пользователю |
| `UNIQUE` | У пользователя может быть максимум один профиль |
| `REFERENCES users(id)` | Пользователь должен существовать |

Обрати внимание: `PRIMARY KEY` у `profiles.id` обеспечивает уникальность самих профилей, а `UNIQUE` у `profiles.user_id` — именно связь 1:1.

## 3. Проверяем связь на практике

Добавим двух пользователей:

```sql
INSERT INTO users (username)
VALUES ('ilya'), ('anna');
```

Предположим, они получили `id = 1` и `id = 2`.

Создадим профиль для Ивана:

```sql
INSERT INTO profiles (user_id, bio)
VALUES (1, 'Python Backend Developer');
```

Запрос выполнится успешно.

Попробуем создать ещё один профиль для того же пользователя:

```sql
INSERT INTO profiles (user_id, bio)
VALUES (1, 'Second profile');
```

PostgreSQL вернёт ошибку:

```text
ERROR: duplicate key value violates
unique constraint "profiles_user_id_key"
```

**Почему?**

Потому что значение `user_id = 1` уже существует в таблице `profiles`.

Теперь попробуем:

```sql
INSERT INTO profiles (user_id, bio)
VALUES (999, 'Unknown user');
```

Если пользователя `999` нет, возникнет ошибка Foreign Key.

Получается, что два ограничения решают разные задачи:

```text
UNIQUE      → нельзя создать второй профиль

FOREIGN KEY → нельзя создать профиль
              для несуществующего пользователя
```

## 4. Что будет, если убрать UNIQUE?

Допустим, мы написали:

```sql
CREATE TABLE profiles (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id)
);
```

Теперь база разрешит:

```sql
INSERT INTO profiles (id, user_id)
VALUES
    (101, 1),
    (102, 1),
    (103, 1);
```

Один пользователь будет иметь три профиля.

```text
User 1
  ├── Profile 101
  ├── Profile 102
  └── Profile 103
```

Это уже **One-to-Many (1:N)**.

Именно поэтому для связи 1:1 обычно нужен `UNIQUE` на внешнем ключе.

## 5. Альтернативный вариант — Shared Primary Key

Иногда дополнительный `profiles.id` вообще не нужен.

Можно сделать `user_id` одновременно первичным и внешним ключом.

```sql
CREATE TABLE profiles (
    user_id BIGINT PRIMARY KEY REFERENCES users(id),
    bio TEXT,
    avatar_url TEXT
);
```

Теперь:

```text
users                 profiles
┌──────────────┐      ┌──────────────────┐
│ id = 1       │◄─────│ user_id = 1      │
│ username     │      │ bio              │
└──────────────┘      └──────────────────┘
```

Почему это работает?

Потому что `PRIMARY KEY` уже обеспечивает:

- `UNIQUE`.
- `NOT NULL`.

А `REFERENCES` добавляет проверку существования пользователя.

**Сравнение двух подходов**

| Подход | Особенность |
|---|---|
| Отдельный `profiles.id` + `user_id UNIQUE` | Профиль имеет собственный идентификатор |
| `user_id PRIMARY KEY REFERENCES users(id)` | Профиль использует идентификатор пользователя |

Второй вариант часто удобен, если профиль существует только как расширение пользователя и ему не нужен отдельный идентификатор.

## 6. Обязательная и необязательная связь

Важный вопрос: **обязательно ли каждому пользователю иметь профиль?**

Нет, не обязательно.

В нашей схеме:

```text
User 1 → Profile 1
User 2 → Profile 2
User 3 → Нет профиля
```

Это связь с кратностью:

```text
users (1) ─── (0..1) profiles
```

Для одного пользователя существует от нуля до одного профиля.

А каждый существующий профиль обязательно принадлежит одному пользователю благодаря `NOT NULL` и `FOREIGN KEY`.

**Важный нюанс:** `NOT NULL` в таблице `profiles` не заставляет создавать профиль для каждого пользователя. Он лишь запрещает существующий профиль без `user_id`.

Чтобы гарантировать обязательное существование записи с обеих сторон, нужны дополнительные механизмы или другое проектирование схемы.

## 7. Как получить данные через JOIN

Предположим, нужно получить пользователя вместе с профилем.

```sql
SELECT
    users.id,
    users.username,
    profiles.bio
FROM users
LEFT JOIN profiles
    ON users.id = profiles.user_id;
```

Результат:

| id | username | bio |
|---|---|---|
| 1 | ilya | Python Developer |
| 2 | anna | Designer |
| 3 | petr | NULL |

Почему `LEFT JOIN`, а не `INNER JOIN`?

`LEFT JOIN` вернёт всех пользователей, даже если профиль отсутствует.

`INNER JOIN` вернёт только тех пользователей, у которых есть связанная запись в `profiles`.

Для необязательной связи 1:1 это важное различие.

## 8. One-to-One в SQLAlchemy 2.x

Теперь рассмотрим реализацию на Python.

```python
from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    username: Mapped[str] = mapped_column(String(100), unique=True)

    profile: Mapped["Profile | None"] = relationship(
        back_populates="user"
    )


class Profile(Base):
    __tablename__ = "profiles"

    id: Mapped[int] = mapped_column(primary_key=True)

    user_id: Mapped[int] = mapped_column(
        ForeignKey("users.id"),
        unique=True,
        nullable=False,
    )

    bio: Mapped[str | None]

    user: Mapped["User"] = relationship(
        back_populates="profile"
    )
```

### Разбор основных строк

`class Base(DeclarativeBase)` — создаём базовый класс для ORM-моделей.

`__tablename__` — указываем название таблицы.

`primary_key=True` — задаём первичный ключ.

`ForeignKey("users.id")` — указываем, что `user_id` ссылается на `users.id`.

`unique=True` — гарантируем, что один пользователь не сможет иметь несколько профилей.

`nullable=False` — запрещаем профиль без пользователя.

`relationship()` — описываем связь между Python-объектами.

`back_populates` — связываем два направления отношения.

Особенно важна типизация:

```python
profile: Mapped["Profile | None"]
```

Она означает, что у пользователя может быть один профиль или `None`.

А здесь:

```python
user: Mapped["User"]
```

каждый профиль связан с одним пользователем.

### Как обращаться к связанным объектам

После загрузки объектов через SQLAlchemy:

```python
user.profile  # Один Profile или None

profile.user  # Один User
```

Обрати внимание: здесь нет списка.

Для 1:N мы бы использовали:

```python
orders: Mapped[list["Order"]]
```

А для 1:1 — одиночный объект.

**Важно:** типизация `Mapped["Profile | None"]` помогает ORM понимать направление связи, но уникальность на уровне базы всё равно должна обеспечиваться ограничением `UNIQUE`.

## 9. Когда применять One-to-One

Связь 1:1 часто встречается в Backend-приложениях.

**Пользователь и настройки**

```text
users ─── user_settings
```

Настройки можно вынести отдельно, если они образуют самостоятельную часть модели.

**Пользователь и дополнительный профиль**

```text
users ─── profiles
```

Основная таблица хранит учётную запись, дополнительная — биографию и аватар.

**Сотрудник и дополнительные кадровые сведения**

```text
employees ─── employee_details
```

Разделение может быть полезно для управления доступом к разным категориям данных.

**Когда не стоит использовать 1:1?**

Если данные всегда используются вместе, имеют одинаковый жизненный цикл и нет причины их разделять, одна таблица может оказаться проще.

Связь 1:1 не является обязательной только потому, что у сущности много полей.

## 10. Что происходит при удалении пользователя

Допустим, пользователь имеет профиль.

По умолчанию PostgreSQL не позволит удалить пользователя, если это нарушит внешний ключ.

Но можно задать:

```sql
CREATE TABLE profiles (
    user_id BIGINT PRIMARY KEY
        REFERENCES users(id)
        ON DELETE CASCADE,
    bio TEXT
);
```

Теперь при удалении пользователя его профиль удалится автоматически.

```text
DELETE User
    |
    v
DELETE Profile
```

Для профиля, который не имеет смысла без пользователя, такое поведение может быть логичным.

Но `CASCADE` нужно выбирать исходя из бизнес-правил, а не применять автоматически ко всем связям.

## 11. Типичные ошибки

**Ошибка №1. Использовать только Foreign Key**

```sql
user_id BIGINT REFERENCES users(id)
```

Это не гарантирует связь 1:1, потому что `user_id` может повторяться.

**Ошибка №2. Считать, что PRIMARY KEY у profiles.id достаточно**

```sql
id BIGINT PRIMARY KEY,
user_id BIGINT REFERENCES users(id)
```

Уникальность `profiles.id` никак не запрещает повторять `user_id`.

**Ошибка №3. Путать NOT NULL и обязательность профиля**

`NOT NULL` запрещает профиль без пользователя, но не заставляет пользователя иметь профиль.

**Ошибка №4. Использовать список в SQLAlchemy для 1:1**

Если отношение действительно 1:1, обычно удобнее одиночный тип:

```python
Mapped["Profile | None"]
```

а не:

```python
Mapped[list["Profile"]]
```

**Ошибка №5. Забывать ограничение UNIQUE в базе**

Даже если ORM описывает одиночный объект, база должна самостоятельно гарантировать нужную уникальность.

## 🎤 Вопросы на собеседовании

**1. Что такое One-to-One?**

Связь, при которой одной записи первой таблицы соответствует не более одной записи второй таблицы, и наоборот.

**2. Как реализовать 1:1 в PostgreSQL?**

Через `FOREIGN KEY + UNIQUE` либо через общий первичный ключ.

**3. Почему нужен UNIQUE?**

Чтобы запретить несколько дочерних записей, ссылающихся на одну родительскую.

**4. Может ли пользователь существовать без профиля?**

Да, если бизнес-правила и схема допускают необязательную связь.

**5. Чем 1:1 отличается от 1:N?**

В 1:1 внешний ключ уникален, а в 1:N его значения могут повторяться.

**6. Что такое Shared Primary Key?**

Подход, при котором первичный ключ дочерней таблицы одновременно является внешним ключом на родительскую.

**7. Как реализовать 1:1 в SQLAlchemy?**

Через `ForeignKey`, `unique=True` и `relationship()` с одиночным типом `Mapped`.

**8. Зачем использовать LEFT JOIN при 1:1?**

Чтобы получать записи родительской таблицы, даже если связанная запись отсутствует.

**9. Нужно ли всегда разделять данные на две таблицы для 1:1?**

Нет. Если данные логически принадлежат одной сущности и нет причин их разделять, одна таблица может быть удобнее.

**10. Что произойдёт при удалении родительской записи?**

Зависит от настройки внешнего ключа: по умолчанию нарушение ссылки запрещено, а при `ON DELETE CASCADE` дочерняя запись удаляется автоматически.

## 🧪 Мини-задание

Представь, что ты разрабатываешь Backend-сервис.

Есть две сущности:

- `users` — учётные записи.
- `user_settings` — персональные настройки.

Требования:

1. Пользователь может существовать без настроек.
2. У пользователя может быть максимум одна запись настроек.
3. Настройки не могут существовать без пользователя.
4. При удалении пользователя настройки должны удаляться автоматически.

Попробуй самостоятельно написать `CREATE TABLE` для обеих таблиц.

Подсказка: тебе понадобятся `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` (либо общий первичный ключ) и `ON DELETE CASCADE`.

## 🧠 Итог

**One-to-One = одна запись ↔ максимум одна связанная запись.**

```text
FOREIGN KEY → проверяет существование связи

UNIQUE      → запрещает несколько связанных записей

NOT NULL    → делает ссылку обязательной для дочерней записи

CASCADE     → управляет удалением зависимой записи
```

Самое важное для собеседования: **одного Foreign Key недостаточно для 1:1. Уникальность внешнего ключа должна быть закреплена ограничением базы данных.**
