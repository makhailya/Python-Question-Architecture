# #️⃣ Hash-индекс в PostgreSQL

## 🎯 Ответ на собеседовании

**Hash-индекс — это индекс PostgreSQL, предназначенный прежде всего для быстрого поиска по условию равенства `=`.**

Он использует хеширование: значение индексируемого поля преобразуется в хеш, по которому PostgreSQL определяет, где искать нужные записи.

Пример:

```python
CREATE INDEX idx_users_email_hash
ON users USING HASH (email);
```

После этого индекс может быть полезен для:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Но Hash-индекс не предназначен для:

```text
< > <= >=
BETWEEN
ORDER BY
```

В большинстве обычных случаев **B-tree остаётся более универсальным выбором**, поэтому Hash используется значительно реже.

---

## 🎤 Суперкоротко

```text
Hash
  ↓
хеширование значения
  ↓
поиск по точному совпадению
  ↓
=
```

Главное:

```text
Hash
→ хорошо для =

B-tree
→ = + диапазоны + сортировка
```

---

# 🔹 Что такое Hash-индекс

Hash-индекс использует **хеш-функцию**.

Условно:

```text
email
  ↓
hash()
  ↓
bucket
  ↓
нужные записи
```

Например:

```text
"user@example.com"
        ↓
      hash
        ↓
    bucket #42
```

Другому значению:

```text
"admin@example.com"
        ↓
      hash
        ↓
    bucket #17
```

Идея состоит в том, чтобы быстро определить область, в которой находится нужное значение.

---

# 🔹 Создание Hash-индекса

Синтаксис:

```python
CREATE INDEX idx_users_email_hash
ON users USING HASH (email);
```

Ключевое слово:

```python
USING HASH
```

указывает PostgreSQL использовать именно Hash-индекс.

Для сравнения B-tree:

```python
CREATE INDEX idx_users_email_btree
ON users USING BTREE (email);
```

Но для B-tree `USING BTREE` обычно можно не указывать:

```python
CREATE INDEX idx_users_email
ON users (email);
```

потому что B-tree используется по умолчанию.

---

# 🔹 Основной сценарий — `=`

Hash хорошо подходит для:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Или:

```python
SELECT *
FROM users
WHERE username = 'ilya';
```

Или:

```python
SELECT *
FROM products
WHERE sku = 'ABC-123';
```

Общая идея:

```text
WHERE column = value
```

---

# 🔹 Почему Hash плохо подходит для диапазонов

Представим значения:

```text
10
20
30
40
50
60
70
```

B-tree хранит их в упорядоченном виде:

```text
10 → 20 → 30 → 40 → 50 → 60 → 70
```

Поэтому запрос:

```python
WHERE age BETWEEN 30 AND 60
```

естественно соответствует структуре B-tree.

Hash работает иначе:

```text
10 → bucket A
20 → bucket F
30 → bucket B
40 → bucket H
50 → bucket C
60 → bucket A
70 → bucket D
```

Значения не образуют полезной сортированной последовательности.

Поэтому Hash не является подходящим индексом для:

```python
WHERE age > 30
```

или:

```python
WHERE age BETWEEN 30 AND 60
```

---

# 🔹 Hash и `ORDER BY`

Hash-индекс не хранит значения в полезном порядке.

Поэтому он не предназначен для:

```python
SELECT *
FROM users
ORDER BY age;
```

B-tree здесь значительно лучше подходит:

```text
B-tree
→ значения упорядочены
→ можно использовать порядок индекса

Hash
→ значения распределены по hash
→ порядка значений нет
```

---

# 🔹 Hash и B-tree

Главное сравнение:

| Возможность     | B-tree | Hash |
| --------------- | -----: | ---: |
| `=`             |      ✅ |    ✅ |
| `>`             |      ✅ |    ❌ |
| `<`             |      ✅ |    ❌ |
| `>=`            |      ✅ |    ❌ |
| `<=`            |      ✅ |    ❌ |
| `BETWEEN`       |      ✅ |    ❌ |
| `ORDER BY`      |      ✅ |    ❌ |
| Универсальность |    ⭐⭐⭐ |    ⭐ |

Поэтому:

```text
B-tree
→ универсальный индекс

Hash
→ специализированный индекс для равенства
```

---

# 🔹 Что такое hash collision

У хеш-функции возможны **коллизии**.

Коллизия — ситуация, когда разные значения дают один и тот же хеш.

Условно:

```text
"value_A"
    ↓
  hash()
    ↓
bucket 10


"value_B"
    ↓
  hash()
    ↓
bucket 10
```

Получается:

```text
value_A ──┐
          ├──→ bucket 10
value_B ──┘
```

Это нормально для хеш-структур.

Поэтому Hash-индекс должен уметь корректно работать с коллизиями и в конечном итоге проверять соответствие искомому значению.

Главная мысль:

```text
одинаковый hash
≠
одинаковое значение
```

---

# 🔹 Hash-индекс не хранит только hash

Важно не думать:

```text
hash
→ нашли bucket
→ автоматически нашли строку
```

Хеширование определяет область поиска, но PostgreSQL должен корректно определить соответствующие индексные записи и строки.

Коллизии возможны, поэтому хеш сам по себе не является уникальным идентификатором значения.

---

# 🔹 Hash не гарантирует уникальность

Обычный Hash-индекс:

```python
CREATE INDEX idx_users_email
ON users USING HASH (email);
```

не означает:

```text
email уникальный
```

Он предназначен для ускорения поиска.

Если нужна гарантия уникальности, используется ограничение:

```python
ALTER TABLE users
ADD CONSTRAINT users_email_unique
UNIQUE (email);
```

То есть:

```text
INDEX
→ производительность

UNIQUE
→ целостность данных
```

---

# 🔹 Hash и SELECT

Предположим:

```text
users = 10 000 000 строк
```

и есть:

```python
CREATE INDEX idx_users_email_hash
ON users USING HASH (email);
```

Запрос:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

PostgreSQL может использовать Hash-индекс для поиска.

Но важно:

```text
индекс существует
≠
PostgreSQL обязан его использовать
```

Как и для B-tree, решение принимает **query planner**.

---

# 🔹 Planner

PostgreSQL сравнивает возможные планы выполнения.

Например:

```text
                    SQL
                     ↓
                  Planner
                 /       \
                ↓         ↓
           Seq Scan    Index Scan
                          ↓
                        Hash
```

Если таблица маленькая:

```text
100 строк
```

planner может решить:

```text
Seq Scan дешевле
```

даже если Hash-индекс существует.

---

# 🔹 Hash и NULL

При работе с Hash-индексом важно учитывать семантику SQL `NULL`.

`NULL` означает:

```text
значение неизвестно / отсутствует
```

Поэтому:

```python
WHERE email = NULL
```

не является правильным способом поиска `NULL`.

Используется:

```python
WHERE email IS NULL
```

Это уже вопрос не столько Hash, сколько общей логики SQL и `NULL`.

---

# 🔹 Когда Hash может иметь смысл

Hash имеет смысл рассматривать, когда:

```text
нужен точный поиск
+
используется =
+
не нужны диапазоны
+
не нужна сортировка
```

Например:

```python
WHERE external_id = 'abc123'
```

или:

```python
WHERE some_code = 'XYZ'
```

Но перед выбором Hash всё равно нужно проверить реальный workload и план выполнения.

---

# 🔹 Почему Hash используется реже B-tree

Основная причина — **B-tree уже очень хорошо решает большинство обычных задач**.

B-tree умеет:

```text
=
<
>
<=
>=
BETWEEN
ORDER BY
```

Hash в основном:

```text
=
```

Поэтому вместо:

```python
CREATE INDEX idx_users_email
ON users USING HASH (email);
```

во многих обычных случаях достаточно:

```python
CREATE INDEX idx_users_email
ON users (email);
```

и получить B-tree.

---

# 🔹 Hash не значит «всегда O(1)»

В теории хеш-таблица часто ассоциируется с:

```text
O(1)
```

Но не стоит отвечать на собеседовании:

> «Hash-индекс всегда работает за O(1)».

Реальная производительность зависит от:

* распределения данных;
* количества коллизий;
* размера структуры;
* работы с диском;
* состояния кэша;
* стоимости получения самой строки;
* конкретного плана PostgreSQL.

Лучше сказать:

> Hash-структуры обеспечивают эффективный поиск по равенству, но реальная стоимость запроса зависит от конкретной структуры индекса и плана выполнения.

---

# 🔹 Hash vs Hash Join

Это **две разные вещи**.

### Hash-индекс

Это структура для ускорения поиска по индексу:

```python
CREATE INDEX ...
USING HASH
```

### Hash Join

Это алгоритм соединения таблиц:

```python
SELECT *
FROM users u
JOIN orders o
    ON u.id = o.user_id;
```

PostgreSQL может выбрать:

```text
Hash Join
```

даже если в таблицах вообще нет Hash-индексов.

Поэтому:

```text
Hash Index
≠
Hash Join
```

Это хороший момент для собеседования.

---

# 🔹 Hash Index vs B-tree Index

Условный сценарий:

```text
WHERE id = 100
```

Оба индекса потенциально подходят:

```text
B-tree → да
Hash   → да
```

Но:

```text
WHERE id > 100
```

лучше:

```text
B-tree → да
Hash   → нет
```

И:

```text
ORDER BY id
```

```text
B-tree → да
Hash   → нет
```

Поэтому B-tree является более универсальным.

# 🎤 Типовые вопросы на собеседовании

### Что такое Hash-индекс?

> Hash-индекс — индексная структура, основанная на хешировании и предназначенная прежде всего для эффективного поиска по равенству `=`.

### Чем Hash отличается от B-tree?

> Hash ориентирован на точное равенство, а B-tree поддерживает равенство, диапазонные операции и сортировку. Поэтому B-tree более универсален.

### Можно ли использовать Hash для `>`?

> Нет, Hash не предназначен для диапазонных сравнений. Для таких запросов обычно используется B-tree.

### Можно ли использовать Hash для `ORDER BY`?

> Нет, Hash не поддерживает полезный порядок значений, поэтому для сортировки подходит B-tree.

### Что такое коллизия?

> Коллизия возникает, когда разные значения имеют одинаковый хеш. Хеш-структура должна корректно обрабатывать такие ситуации.

### Hash всегда быстрее B-tree?

> Нет. Нельзя говорить, что Hash всегда быстрее. Выбор зависит от запроса, данных и плана выполнения PostgreSQL. B-tree обычно предпочтительнее как более универсальный индекс.

### Почему Hash используется реже?

> Потому что его область применения уже: в основном поиск по `=`. B-tree дополнительно поддерживает диапазоны и сортировку.

### Hash-индекс гарантирует уникальность?

> Нет. Индекс сам по себе не гарантирует уникальность. Для этого используется `UNIQUE` или `PRIMARY KEY`.

### Hash Index и Hash Join — это одно и то же?

> Нет. Hash Index — структура индекса. Hash Join — алгоритм выполнения JOIN. PostgreSQL может использовать Hash Join независимо от наличия Hash-индекса.

                           │

В отличие от B-tree:

```text
B-tree
→ значения упорядочены

```

Hash:

```text
Hash
→ значения распределяются по hash
→ =
→ нет полезного порядка
→ нет диапазонного поиска
```
