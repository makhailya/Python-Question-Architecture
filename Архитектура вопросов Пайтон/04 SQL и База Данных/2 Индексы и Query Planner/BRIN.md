# 📦 BRIN индекс в PostgreSQL

## 🎯 Ответ на собеседовании

**BRIN (Block Range Index) — это компактный индекс PostgreSQL, который хранит сводную информацию не для каждой строки, а для диапазонов физических блоков таблицы.**

Например, для каждого диапазона блоков PostgreSQL может хранить:

```text
MIN(value)
MAX(value)
```

Если данные физически хорошо коррелируют со значением столбца, PostgreSQL может быстро исключить большие участки таблицы.

BRIN особенно полезен для:

* очень больших таблиц;
* логов;
* временных рядов;
* событий;
* данных, которые добавляются примерно в порядке `created_at`, `id` и т. п.

Пример:

```python
CREATE INDEX idx_logs_created_at
ON logs USING BRIN (created_at);
```

Главная идея:

```text
B-tree
→ индексирует отдельные значения

BRIN
→ индексирует диапазоны блоков
```

---

## 🎤 Суперкоротко

```text
BRIN
→ Block Range Index
→ информация о диапазонах блоков
→ очень маленький индекс
→ хорошо для огромных таблиц
→ особенно при корреляции данных
→ не хранит отдельную запись для каждой строки
```

Ментальная модель:

```text
Таблица

блоки 1–100
→ created_at: min ... max

блоки 101–200
→ created_at: min ... max

блоки 201–300
→ created_at: min ... max
```

Запрос:

```text
created_at > X
```

может позволить PostgreSQL сразу отбросить диапазоны блоков, где подходящих значений точно нет.

---

# 🔹 Что означает BRIN

BRIN:

**Block Range Index**

То есть:

```text
индекс диапазонов блоков
```

Ключевое здесь — **block range**.

PostgreSQL хранит таблицу физически в страницах/блоках.

Упрощённо:

```text
Таблица
│
├── Block 1
├── Block 2
├── Block 3
├── ...
├── Block N
```

BRIN объединяет несколько последовательных блоков в диапазон:

```text
Block 1 ──────┐
Block 2       │
Block 3       ├── Range 1
Block 4       │
Block 5 ──────┘

Block 6 ──────┐
Block 7       │
Block 8       ├── Range 2
Block 9       │
Block 10 ─────┘
```

И хранит информацию о каждом таком диапазоне.

---

# 🔹 Что хранит BRIN

Для многих типов данных BRIN может хранить примерно такую информацию:

```text
Range 1
→ MIN(created_at)
→ MAX(created_at)

Range 2
→ MIN(created_at)
→ MAX(created_at)

Range 3
→ MIN(created_at)
→ MAX(created_at)
```

Например:

```text
Range 1
→ 2026-01-01 ... 2026-01-05

Range 2
→ 2026-01-05 ... 2026-01-10

Range 3
→ 2026-01-10 ... 2026-01-15
```

Если запрос:

```python
WHERE created_at >= '2026-01-12'
```

BRIN может определить:

```text
Range 1
→ точно не подходит

Range 2
→ точно не подходит

Range 3
→ потенциально подходит
```

И PostgreSQL не обязан читать первые два диапазона.

---

# 🔹 Почему BRIN такой маленький

Представим:

```text
1 000 000 000 строк
```

B-tree условно строит индекс вокруг отдельных индексируемых значений:

```text
строка 1
строка 2
строка 3
...
строка 1 000 000 000
```

BRIN работает гораздо грубее:

```text
1 000 000 000 строк
        ↓
диапазоны блоков
        ↓
несколько тысяч / десятков тысяч записей
```

Поэтому BRIN может быть **на порядки меньше B-tree** на больших таблицах.

Главная идея:

```text
B-tree
→ детальная информация

BRIN
→ приблизительная / агрегированная информация
```

---

# 🔹 Самое важное условие — корреляция

BRIN особенно эффективен, когда значение столбца связано с физическим порядком строк.

Это называется **корреляцией**.

Например, таблица логов:

```text
id | created_at
---+-------------------
1  | 2026-01-01
2  | 2026-01-01
3  | 2026-01-02
4  | 2026-01-02
5  | 2026-01-03
...
```

Данные добавляются последовательно:

```text
старые записи
      ↓
новые записи
      ↓
физический порядок таблицы
```

Получается:

```text
физический порядок
        ≈
created_at
```

Это хороший сценарий для BRIN.

---

# 🔹 Что такое корреляция

Упрощённо:

```text
значение столбца
       ↕
физическое расположение строки
```

Если строки:

```text
Block 1 → даты января
Block 2 → даты февраля
Block 3 → даты марта
```

то корреляция высокая.

BRIN отлично может сказать:

```text
ищем март
→ январь не нужен
→ февраль не нужен
→ смотрим март
```

---

# 🔹 Плохая корреляция

Представим:

```text
Block 1
→ даты: январь, март, июль, декабрь

Block 2
→ даты: февраль, апрель, август, ноябрь

Block 3
→ даты: январь, июнь, сентябрь, декабрь
```

Теперь почти каждый блок может содержать нужное значение.

BRIN не сможет эффективно исключить большие диапазоны.

То есть:

```text
плохая корреляция
→ BRIN теряет преимущество
```

---

# 🔹 Типичный сценарий — логи

Есть огромная таблица:

```text
logs
```

с миллиардами записей:

```text
id
created_at
level
message
```

Записи постоянно добавляются.

Например:

```python
CREATE INDEX idx_logs_created_at
ON logs USING BRIN (created_at);
```

Запрос:

```python
SELECT *
FROM logs
WHERE created_at >= '2026-09-01';
```

BRIN может быстро определить:

```text
старые блоки
→ не нужны

новые блоки
→ потенциально нужны
```

Это очень типичный сценарий использования.

---

# 🔹 BRIN не ищет конкретную строку

Это важное отличие от B-tree.

B-tree:

```text
WHERE id = 12345
        ↓
B-tree
        ↓
конкретная индексная запись
        ↓
строка
```

BRIN:

```text
WHERE created_at >= X
        ↓
BRIN
        ↓
какие диапазоны блоков потенциально подходят?
        ↓
чтение соответствующих блоков
        ↓
проверка строк
```

Поэтому BRIN — более грубый индекс.

---

# 🔹 Lossy nature

BRIN является **lossy**-индексом в том смысле, что информация в нём недостаточно точна, чтобы определить конкретные строки.

Например:

```text
Range 10
→ MIN = 100
→ MAX = 200
```

Запрос:

```text
WHERE value = 150
```

BRIN говорит:

```text
Range 10
→ потенциально подходит
```

Но это не означает, что значение `150` действительно есть в каждой или даже в какой-либо строке диапазона.

Поэтому PostgreSQL должен прочитать соответствующие блоки и проверить реальные строки.

Модель:

```text
BRIN
 ↓
кандидаты
 ↓
Heap Scan
 ↓
проверка условия
 ↓
точный результат
```

# 🔹 BRIN vs B-tree

Это одно из главных сравнений.

| Характеристика             | B-tree             | BRIN                  |
| -------------------------- | ------------------ | --------------------- |
| Индексирует                | Отдельные значения | Диапазоны блоков      |
| Размер                     | Больше             | Очень маленький       |
| Точность                   | Высокая            | Грубее                |
| Диапазонный поиск          | Отлично            | Хорошо при корреляции |
| Огромные таблицы           | Да                 | Особенно хорошо       |
| Нужна корреляция           | Нет                | Желательно            |
| Поиск конкретного значения | Отлично            | Не основная задача    |
| Стоимость обслуживания     | Выше               | Обычно ниже           |

Упрощённо:

```text
B-tree
→ точность

BRIN
→ компактность
```

# 🔹 BRIN vs GIN

Это совершенно разные задачи.

```text
GIN
→ JSONB
→ ARRAY
→ Full Text Search
→ элемент → строки
```

```text
BRIN
→ диапазоны физических блоков
→ огромные таблицы
→ коррелированные данные
```

Например:

```text
JSONB
→ GIN
```

а:

```text
created_at
+
огромная таблица
+
данные идут по времени
→ BRIN
```
