# TID Scan в PostgreSQL 🎯

## 🎯 Ответ на собеседовании

**TID Scan** — это способ доступа PostgreSQL к строке таблицы по её физическому идентификатору **TID (Tuple ID)**.

В PostgreSQL TID представлен значением `ctid`, которое указывает физическое расположение версии строки в таблице:

```python
ctid = (номер страницы, позиция строки на странице)
```

Например:

```python
(10, 5)
```

означает примерно:

```python
страница 10
позиция строки 5
```

PostgreSQL может использовать `TID Scan`, когда запрос обращается к строке непосредственно через `ctid`.

---

## 🎤 Суперкоротко

```python
TID Scan
    ↓
получаем TID / ctid
    ↓
находим физическое расположение строки
    ↓
читаем строку из heap
```

Пример:

```python
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

План:

```python
Tid Scan on users
```

---

# 1. Что такое TID

**TID (Tuple Identifier)** — физический идентификатор строки в PostgreSQL.

Он представлен системной колонкой:

```python
ctid
```

Например:

```python
SELECT ctid, id, name
FROM users;
```

Результат может выглядеть примерно так:

```python
ctid   | id | name
-------+----+------
(0,1)  | 1  | Ivan
(0,2)  | 2  | Alex
(0,3)  | 3  | Olga
```

`ctid` можно условно представить как:

```python
(page, position)
```

То есть:

```python
(0,1)
 ↑  ↑
 │  └── позиция строки
 └───── страница таблицы
```

---

# 2. Как работает TID Scan

Запрос:

```python
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

PostgreSQL уже знает:

```python
страница = 10
строка = 5
```

Поэтому ему не нужно:

```python
Seq Scan
```

или:

```python
Index Scan
```

Он может непосредственно обратиться к нужному физическому месту:

```python
ctid
 ↓
Heap Page 10
 ↓
Tuple 5
 ↓
Row
```

Именно это и называется:

```python
Tid Scan
```

---

# 3. Пример EXPLAIN

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

План может выглядеть примерно так:

```python
Tid Scan on users
  (cost=0.00..4.01 rows=1 width=64)
  (actual time=0.010..0.011 rows=1 loops=1)
  TID Cond: (ctid = '(10,5)'::tid)
```

Главное здесь:

```python
Tid Scan
```

→ PostgreSQL выполняет поиск непосредственно по TID.

```python
TID Cond
```

→ условие поиска использует `ctid`.

---

# 4. TID Scan и Index Scan

Это принципиально разные способы доступа.

### Index Scan

```python
WHERE id = 100
```

Если есть индекс:

```python
Index
  ↓
найти запись
  ↓
получить TID
  ↓
Heap
```

### TID Scan

```python
WHERE ctid = '(10,5)'
```

Здесь TID уже известен:

```python
TID
 ↓
Heap
```

То есть можно сразу обратиться к физическому расположению строки.

---

# 5. Почему TID Scan очень быстрый

Если PostgreSQL уже знает:

```python
ctid = '(10,5)'
```

ему не нужно искать строку среди миллионов записей.

Есть практически прямой адрес:

```python
Page 10
   ↓
Tuple 5
```

Схематично:

```python
10 000 000 строк

Seq Scan
    ↓
проверять множество страниц/строк

Index Scan
    ↓
Index → TID → Heap

TID Scan
    ↓
известный TID → Heap
```

Но это не означает, что `ctid` нужно использовать вместо обычного `PRIMARY KEY`.

---

# 6. `ctid` — физический, а не логический идентификатор

Очень важный момент для собеседования.

`id`:

```python
id = 100
```

— логический идентификатор записи.

`ctid`:

```python
ctid = '(10,5)'
```

— физическое расположение конкретной версии строки.

Поэтому:

```python
id
```

может оставаться неизменным,

а:

```python
ctid
```

может измениться.

---

# 7. Почему `ctid` может измениться

В PostgreSQL `UPDATE` может создать **новую версию строки**.

Например:

```python
до UPDATE:

ctid = (10,5)
```

После изменения строки:

```python
UPDATE users
SET name = 'Alex'
WHERE id = 100;
```

новая версия строки может оказаться уже в другом физическом месте:

```python
после UPDATE:

ctid = (10,8)
```

Поэтому нельзя считать `ctid` постоянным идентификатором записи.

---

# 8. MVCC и TID

Это связано с механизмом **MVCC** PostgreSQL.

При обновлении PostgreSQL не обязательно просто «перезаписывает ту же самую строку».

Могут существовать разные версии tuple:

```python
старая версия
    ↓
новая версия
```

У каждой версии есть своё физическое расположение.

Поэтому:

```python
ctid
```

идентифицирует **конкретную физическую версию tuple**, а не абстрактную сущность пользователя.

---

# 9. TID Scan не использует обычный индекс

Например:

```python
CREATE INDEX idx_users_id
ON users(id);
```

Запрос:

```python
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

не означает:

```python
Index Scan using idx_users_id
```

Потому что поиск выполняется по:

```python
ctid
```

PostgreSQL получает физический адрес напрямую.

---

# 10. Где TID Scan может использоваться

TID Scan — специализированный механизм.

Он может быть полезен, когда:

* физический TID уже известен;
* нужно обратиться к конкретной строке;
* PostgreSQL может напрямую использовать TID для доступа.

Например:

```python
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

Но в обычном приложении запросы обычно строятся вокруг:

```python
PRIMARY KEY
UNIQUE
INDEX
```

а не вокруг `ctid`.

---

# 11. TID Scan с несколькими TID

PostgreSQL также может работать с несколькими TID.

Например:

```python
SELECT *
FROM users
WHERE ctid IN ('(10,5)', '(20,3)');
```

В зависимости от запроса и версии PostgreSQL план может использовать TID-based scan.

Идея остаётся той же:

```python
TID
 ↓
физическое расположение
 ↓
Heap
```

---

# 12. `ctid` можно посмотреть напрямую

```python
SELECT ctid, *
FROM users
LIMIT 10;
```

Например:

```python
ctid   | id | name
-------+----+------
(0,1)  | 1  | Ivan
(0,2)  | 2  | Alex
(0,3)  | 3  | Olga
```

Это полезно для понимания физического устройства PostgreSQL.

---

# 13. `ctid` ≠ `PRIMARY KEY`

Нельзя делать:

```python
ctid
```

заменой:

```python
id
```

### `PRIMARY KEY`

```python
id = 100
```

характеризует логическую сущность.

### `ctid`

```python
ctid = '(10,5)'
```

характеризует физическое расположение tuple.

Поэтому:

```python
PRIMARY KEY
→ постоянный логический идентификатор

ctid
→ физический адрес конкретной версии строки
```

---

# 14. TID Scan vs Seq Scan

|                                   | Seq Scan        | TID Scan                   |
| --------------------------------- | --------------- | -------------------------- |
| Ищет по всей таблице              | Да              | Нет                        |
| Использует `ctid`                 | ❌               | ✅                          |
| Физический адрес известен заранее | ❌               | ✅                          |
| Типичный сценарий                 | Массовое чтение | Точечный физический доступ |
| Использует обычный индекс         | ❌               | ❌                          |

---

# 15. TID Scan vs Index Scan

|                                 | Index Scan                | TID Scan            |
| ------------------------------- | ------------------------- | ------------------- |
| Использует индекс               | ✅                         | ❌                   |
| Использует `ctid`               | Получает TID через индекс | Использует напрямую |
| Нужно искать значение в индексе | ✅                         | ❌                   |
| Доступ к heap                   | Обычно да                 | Да                  |
| Типичный поиск                  | `WHERE id = ...`          | `WHERE ctid = ...`  |

Схематично:

```python
Index Scan:

id = 100
   ↓
Index
   ↓
TID
   ↓
Heap
```

```python
TID Scan:

ctid = '(10,5)'
       ↓
     Heap
       ↓
     Row
```

---

# 16. Почему нельзя использовать TID для обычного API

Представим REST API:

```python
GET /users/100
```

Плохая идея:

```python
GET /users/(10,5)
```

Потому что:

* `ctid` может измениться;
* он отражает физическую структуру таблицы;
* он не предназначен как бизнес-идентификатор;
* он связывает приложение с внутренним устройством PostgreSQL.

Правильно использовать:

```python
id
```

или другой стабильный ключ.

---

# 17. Как читать TID Scan в EXPLAIN

Например:

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE ctid = '(10,5)';
```

Условный результат:

```python
Tid Scan on users
  (cost=0.00..4.01 rows=1 width=64)
  (actual time=0.015..0.016 rows=1 loops=1)
  TID Cond: (ctid = '(10,5)'::tid)
```

Разбираем:

```python
Tid Scan
```

→ используется TID-доступ.

```python
TID Cond
```

→ условие поиска по физическому идентификатору.

```python
rows=1
```

→ planner ожидает одну строку.

```python
actual rows=1
```

→ фактически найдена одна строка.

# 18. Все основные Scan рядом

Теперь у нас получается следующая картина:

```python
Seq Scan
    ↓
Table → проверяем строки
```

```python
Index Scan
    ↓
Index → Heap → Rows
```

```python
Index Only Scan
    ↓
Index → Result
```

```python
Bitmap Index Scan
    ↓
Index → Bitmap
```

```python
Bitmap Heap Scan
    ↓
Bitmap → Heap → Rows
```

```python
TID Scan
    ↓
TID → Heap → Row
```

## 🧠 Главное

**TID Scan**:

```python
ctid
 ↓
физическое расположение tuple
 ↓
Heap
 ↓
Row
```

`ctid` имеет вид:

```python
(page, position)
```

Например:

```python
(10, 5)
```

Главные свойства:

* `ctid` — физический идентификатор tuple;
* TID Scan позволяет обратиться к строке по этому идентификатору;
* это специализированный способ доступа;
* `ctid` может измениться после `UPDATE`;
* `ctid` не является заменой `PRIMARY KEY`;
* в обычных приложениях поиск обычно выполняется по логическим ключам и индексам.

> **TID Scan — специализированный тип сканирования PostgreSQL, который обращается к строкам непосредственно по их физическому идентификатору TID (`ctid`).**
