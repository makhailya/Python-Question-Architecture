# 🗂️ Типы индексов в PostgreSQL

## 🎯 Ответ на собеседовании

**Индекс в PostgreSQL — это отдельная структура данных, которая позволяет быстрее находить строки по определённым условиям, не просматривая всю таблицу.**

Основные типы индексов в PostgreSQL:

* **[[B-tree]]** — индекс по умолчанию, подходит для `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, сортировки;
* **[[Hash]]** — для сравнений на равенство `=`;
* **[[GIN]]** — эффективен для поиска по составным значениям: `JSONB`, массивам, полнотекстовому поиску;
* **[[GiST]]** — обобщённое дерево для специальных типов данных и операций, например геометрии и диапазонов;
* **[[SP-GiST]]** — для структур данных, которые можно эффективно разделять на непересекающиеся области;
* **[[BRIN]]** — компактный индекс для очень больших таблиц, когда физический порядок данных коррелирует со значением столбца.

На практике **[[B-tree]] используется чаще всего**, а остальные типы выбираются под конкретный тип данных и операторы поиска.

---

## 🎤 Суперкоротко

```text
B-tree   → обычные сравнения и сортировка
Hash     → =
GIN      → JSONB, массивы, полнотекстовый поиск
GiST     → геометрия, диапазоны и специальные типы
SP-GiST  → специальные разбиения данных
BRIN     → огромные таблицы + корреляция физического порядка
```

---

# 🔹 1. B-tree

**B-tree — индекс по умолчанию в PostgreSQL.**

Создание:

```python
CREATE INDEX idx_users_email
ON users (email);
```

Подходит для:

```python
WHERE email = 'user@example.com'
```

```python
WHERE age > 30
```

```python
WHERE age BETWEEN 20 AND 40
```

```python
ORDER BY created_at;
```

То есть B-tree хорошо работает с операциями:

```text
=
<
>
<=
>=
BETWEEN
ORDER BY
```

### Пример

Есть таблица:

```text
users

id | email
---+------------------
1  | a@test.ru
2  | b@test.ru
3  | c@test.ru
...
```

Без индекса PostgreSQL может выполнить:

```text
Sequential Scan
→ проверить строки одну за другой
```

С индексом:

```text
Index Scan
→ найти значение в индексе
→ получить нужные строки
```

---

# 🔹 2. Hash

**Hash-индекс предназначен прежде всего для поиска по равенству `=`.**

Создание:

```python
CREATE INDEX idx_users_email_hash
ON users USING HASH (email);
```

Использование:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Главное ограничение:

```text
Hash
→ хорошо для =

Hash
→ не предназначен для диапазонов и сортировки
```

Например:

```python
WHERE age > 30
```

не является типичным сценарием для Hash.

Поэтому в большинстве обычных случаев **B-tree предпочтительнее**.

---

# 🔹 3. GIN

**GIN (Generalized Inverted Index)** — обобщённый инвертированный индекс.

Он особенно полезен, когда одна строка содержит **множество значений**, и нужно искать по отдельным элементам.

Типичные случаи:

* `JSONB`;
* массивы;
* полнотекстовый поиск.

---

## GIN + массивы

Например:

```text
products

id | tags
---+-------------------------
1  | {python,backend,sql}
2  | {python,django}
3  | {java,backend}
```

Создаём:

```python
CREATE INDEX idx_products_tags
ON products USING GIN (tags);
```

Теперь можно эффективно выполнять поиск по элементам массива:

```python
SELECT *
FROM products
WHERE tags @> ARRAY['python'];
```

---

## GIN + JSONB

Например:

```text
users

id | data
---+--------------------------------
1  | {"role": "admin", "age": 30}
2  | {"role": "user", "age": 25}
```

Индекс:

```python
CREATE INDEX idx_users_data
ON users USING GIN (data);
```

GIN часто используется для запросов к `JSONB`.

Например:

```python
SELECT *
FROM users
WHERE data @> '{"role": "admin"}';
```

---

# 🔹 4. GiST

**GiST (Generalized Search Tree)** — обобщённое дерево поиска.

Это не просто индекс для одного конкретного типа данных. PostgreSQL использует GiST как основу для индексации различных специализированных структур.

Типичные области применения:

* геометрические данные;
* диапазоны;
* специальные типы данных;
* некоторые расширения PostgreSQL.

Например, с диапазонами:

```python
CREATE INDEX idx_reservations_period
ON reservations USING GIST (period);
```

После этого можно эффективно выполнять операции над диапазонами.

GiST особенно важен в связке с расширениями PostgreSQL, например PostGIS.

---

# 🔹 5. SP-GiST

**SP-GiST (Space-Partitioned GiST)** — индекс для структур данных, которые можно эффективно разделять на непересекающиеся области.

Он подходит для определённых типов данных, где обычная B-tree или GiST-структура не является оптимальной.

Применяется, например, для некоторых:

* геометрических структур;
* пространственных данных;
* деревьев;
* специализированных операторных классов.

Создание:

```python
CREATE INDEX idx_points
ON points USING SPGIST (location);
```

Главная идея:

```text
GiST
→ обобщённое дерево поиска

SP-GiST
→ разбиение пространства/значений на области
```

Это специализированный тип индекса, который обычно выбирают под конкретный операторный класс.

---

# 🔹 6. BRIN

**BRIN (Block Range INdex)** — очень компактный индекс, который хранит информацию не о каждой строке, а о диапазонах блоков таблицы.

Особенно полезен для **очень больших таблиц**, когда значения физически расположены примерно в том же порядке, что и индексируемое поле.

Например:

```text
logs

id | created_at
---+-------------------
1  | 2026-01-01
2  | 2026-01-01
3  | 2026-01-02
4  | 2026-01-02
...
```

Если данные постоянно добавляются примерно в порядке `created_at`, значения хорошо коррелируют с физическим расположением строк.

Создание:

```python
CREATE INDEX idx_logs_created_at
ON logs USING BRIN (created_at);
```

---

## Почему BRIN такой компактный?

Условно:

```text
B-tree:

строка 1 → значение
строка 2 → значение
строка 3 → значение
...
строка 1 000 000 → значение


BRIN:

блок 1–128
→ min / max

блок 129–256
→ min / max

блок 257–384
→ min / max
```

То есть BRIN хранит **сводную информацию по диапазонам блоков**, а не полноценную запись для каждой строки.

Поэтому:

```text
BRIN
→ очень маленький размер
→ дешёвое обслуживание
→ хорошо для огромных таблиц
```

Но точность поиска ниже, чем у B-tree.

---

# 📊 Сравнение типов индексов

| Тип         | Основное применение                       |          Размер | Типичный сценарий         |
| ----------- | ----------------------------------------- | --------------: | ------------------------- |
| **B-tree**  | Сравнения, сортировка                     |         Средний | `=`, `>`, `<`, `ORDER BY` |
| **Hash**    | Равенство                                 |         Средний | `=`                       |
| **GIN**     | Составные значения                        |         Большой | `JSONB`, массивы, FTS     |
| **GiST**    | Специализированный поиск                  |         Зависит | диапазоны, геометрия      |
| **SP-GiST** | Пространственное/разделяемое пространство |         Зависит | специальные структуры     |
| **BRIN**    | Большие таблицы                           | Очень маленький | временные ряды, логи      |

---

# 🔹 B-tree vs Hash

На собеседовании часто спрашивают:

> Почему обычно используют B-tree, а не Hash?

Потому что B-tree поддерживает гораздо больше операций:

```text
B-tree
→ =
→ <
→ >
→ <=
→ >=
→ BETWEEN
→ сортировку
```

Hash:

```text
Hash
→ в основном =
```

Поэтому для обычных индексов PostgreSQL по умолчанию использует B-tree.

---

# 🔹 B-tree vs GIN

Это индексы для разных задач.

```text
B-tree
→ одно значение

email = 'a@test.ru'
age > 30
created_at < ...
```

```text
GIN
→ набор значений внутри одного поля

JSONB
ARRAY
полнотекстовый поиск
```

Например:

```text
tags = {python, backend, postgres}
```

Для поиска по отдельным элементам такого массива GIN подходит значительно лучше обычного B-tree.

---

# 🔹 B-tree vs BRIN

Здесь ключевое различие — **размер таблицы и корреляция данных**.

### B-tree

```text
Большая таблица
→ индексируем практически каждое значение
→ быстрый поиск
→ индекс занимает больше места
```

### BRIN

```text
Огромная таблица
+
значения коррелируют с физическим порядком
→ индекс очень маленький
→ PostgreSQL быстро исключает ненужные блоки
```

Например, таблица логов:

```text
created_at
↓
2026-01-01
2026-01-02
2026-01-03
...
2026-12-31
```

Если записи добавляются последовательно по времени, BRIN может быть очень эффективен.

---

# 🔹 Индекс не гарантирует Index Scan

Важно понимать:

```text
CREATE INDEX
≠
PostgreSQL всегда использует индекс
```

PostgreSQL анализирует стоимость разных планов.

Например:

```text
Таблица = 100 строк
Нужно вернуть = 90 строк
```

Иногда быстрее:

```text
Seq Scan
```

чем:

```text
Index Scan
→ поиск в индексе
→ переходы к таблице
→ получение большого количества строк
```

Поэтому PostgreSQL выбирает план на основе статистики и оценки стоимости.

Посмотреть план:

```python
EXPLAIN
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Более подробно:

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'user@example.com';
```

---

# 🔹 Индекс имеет цену

Индекс ускоряет чтение, но не бесплатен.

При:

```python
INSERT
UPDATE
DELETE
```

PostgreSQL должен поддерживать соответствующие индексы.

Поэтому:

```text
Больше индексов
→ быстрее некоторые SELECT
→ медленнее INSERT/UPDATE/DELETE
→ больше места на диске
→ больше работы для VACUUM/обслуживания
```

Индекс нужно создавать не просто потому, что он существует, а под реальные запросы.

---

# 🔹 Составной индекс

Индекс можно создать сразу по нескольким колонкам:

```python
CREATE INDEX idx_users_name_age
ON users (name, age);
```

Это:

```text
(name, age)
```

а не два независимых индекса.

Порядок колонок имеет значение.

Например:

```python
CREATE INDEX idx_users_name_age
ON users (name, age);
```

особенно полезен для запросов, начинающихся с `name`:

```python
WHERE name = 'Илья'
```

или:

```python
WHERE name = 'Илья'
AND age = 31
```

Но выбор порядка колонок зависит от реальных запросов и распределения данных.

---

# 🔹 Частичный индекс

Можно индексировать только часть строк:

```python
CREATE INDEX idx_active_users
ON users (email)
WHERE is_active = true;
```

Теперь индекс содержит только активных пользователей.

Это может быть выгодно, если:

```text
активных пользователей мало
```

и запросы часто используют:

```python
WHERE is_active = true
AND email = 'user@example.com'
```

---

# 🔹 Уникальный индекс

`UNIQUE` гарантирует отсутствие одинаковых значений.

```python
CREATE UNIQUE INDEX idx_users_email_unique
ON users (email);
```

Но на практике чаще используют:

```python
ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

PostgreSQL создаёт соответствующий уникальный индекс для поддержки ограничения.

Важно:

```text
INDEX
→ ускорение поиска

UNIQUE
→ ограничение целостности данных

UNIQUE INDEX
→ уникальность + индексная структура
```

---

# 🔹 Как PostgreSQL выбирает индекс

Упрощённо:

```text
SQL-запрос
    ↓
Planner / Optimizer
    ↓
оценивает стоимость вариантов
    ↓
Seq Scan?
Index Scan?
Bitmap Index Scan?
...
    ↓
выбирает план
```

Поэтому наличие индекса ещё не означает его использование.

# 🎤 Типовые вопросы на собеседовании

### Какие типы индексов есть в PostgreSQL?

> Основные типы — B-tree, Hash, GIN, GiST, SP-GiST и BRIN. B-tree используется по умолчанию. GIN хорошо подходит для JSONB, массивов и полнотекстового поиска, GiST и SP-GiST — для специализированных структур, а BRIN — для очень больших таблиц с хорошей корреляцией физического порядка данных.

### Какой индекс используется по умолчанию?

> B-tree.

### Какой индекс выбрать для JSONB?

> Обычно GIN, если нужны эффективные запросы по содержимому JSONB.

### Для чего нужен BRIN?

> BRIN хранит агрегированную информацию о диапазонах блоков таблицы. Он особенно эффективен на очень больших таблицах, когда физический порядок строк хорошо коррелирует со значением индексируемого столбца, например для временных рядов.

### Hash или B-tree?

> B-tree универсальнее: поддерживает равенство, диапазоны и сортировку. Hash в основном предназначен для операций равенства.

### Индекс всегда ускоряет SELECT?

> Нет. PostgreSQL выбирает план выполнения на основе стоимости. Для маленькой таблицы или запроса, возвращающего большую часть строк, Seq Scan может быть быстрее.

### Есть ли недостатки у индексов?

> Да. Они занимают место и увеличивают стоимость `INSERT`, `UPDATE` и `DELETE`, потому что индекс тоже нужно поддерживать.

# 🎯 Формула выбора

```text
Обычные значения
→ B-tree

Только равенство
→ Hash (если действительно подходит)

JSONB / ARRAY / полнотекстовый поиск
→ GIN

Диапазоны / геометрия / специальные типы
→ GiST

Специальные структуры с пространственным разбиением
→ SP-GiST

Огромная таблица + сильная корреляция
→ BRIN
```

**Главная мысль:** тип индекса выбирают не «по скорости вообще», а **по характеру данных и операторам, которые используются в реальных запросах**.
