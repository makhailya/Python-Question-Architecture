# EXPLAIN в PostgreSQL 🔍

## 🎯 Ответ на собеседовании

**EXPLAIN** — команда PostgreSQL, которая показывает **план выполнения SQL-запроса**, то есть как PostgreSQL собирается получить результат: какие таблицы читать, использовать ли индекс, какой алгоритм JOIN выбрать, где выполнять сортировку и агрегацию.

С помощью `EXPLAIN` можно анализировать и оптимизировать производительность запросов.

[[EXPLAIN ANALYZE]] дополнительно **реально выполняет запрос** и показывает фактические показатели выполнения.

---

## 🎤 Суперкоротко

```python
EXPLAIN — показывает план выполнения запроса.

EXPLAIN ANALYZE — выполняет запрос и показывает
план + фактические показатели.

Главное смотреть:
- Seq Scan / Index Scan
- стоимость
- estimated rows vs actual rows
- время выполнения
- количество loops
```

---

# 1. Что делает EXPLAIN

Например:

```python
EXPLAIN SELECT * FROM users WHERE id = 100;
```

PostgreSQL может показать:

```python
Index Scan using users_pkey on users
  Index Cond: (id = 100)
```

Это означает:

* PostgreSQL использует индекс;
* индекс называется `users_pkey`;
* поиск выполняется по условию `id = 100`.

---

# 2. EXPLAIN не выполняет запрос

Обычный:

```python
EXPLAIN SELECT * FROM users WHERE age > 30;
```

**не выполняет сам `SELECT`**.

Он показывает, какой план PostgreSQL собирается использовать.

Это позволяет безопасно исследовать даже `SELECT`-запросы.

---

# 3. EXPLAIN ANALYZE

```python
EXPLAIN ANALYZE
SELECT * FROM users WHERE age > 30;
```

Здесь PostgreSQL:

1. строит план;
2. реально выполняет запрос;
3. собирает фактическую статистику;
4. показывает результат.

Например:

```python
Seq Scan on users
  (cost=0.00..180.00 rows=5000 width=64)
  (actual time=0.020..2.500 rows=4800 loops=1)
```

Здесь уже можно сравнить:

```python
estimated rows = 5000
actual rows    = 4800
```

Если оценки сильно отличаются, это может указывать на проблемы со статистикой или кардинальностью.

---

# 4. Основные части плана

Пример:

```python
Index Scan using users_age_idx on users
  (cost=0.29..100.50 rows=100 width=64)
  (actual time=0.030..0.500 rows=95 loops=1)
  Index Cond: (age > 30)
```

Разберём.

### `Index Scan`

PostgreSQL использует индекс для поиска строк.

---

### `cost`

```python
cost=0.29..100.50
```

Это **оценка стоимости**, а не время в миллисекундах.

Формат:

```python
startup_cost..total_cost
```

Например:

```python
cost=10.00..500.00
```

* `10.00` — стоимость получения первой строки;
* `500.00` — оценочная стоимость получения всего результата.

**Важно:** `cost` нельзя напрямую интерпретировать как миллисекунды.

---

### `rows`

```python
rows=100
```

Количество строк, которое PostgreSQL **ожидает получить** на этом этапе.

---

### `width`

```python
width=64
```

Средний ожидаемый размер строки в байтах.

---

### `actual time`

```python
actual time=0.030..0.500
```

Фактическое время:

* до получения первой строки;
* до получения всех строк.

Единица измерения — **миллисекунды**.

---

### `loops`

```python
loops=10
```

Сколько раз данный узел реально выполнялся.

---

# 5. Seq Scan

```python
Seq Scan on users
```

**Sequential Scan** — PostgreSQL последовательно читает таблицу.

Условно:

```python
1 → 2 → 3 → 4 → 5 → ... → N
```

Проверяется множество строк.

Это **не обязательно плохо**.

Например, если запрос возвращает большую часть таблицы:

```python
SELECT * FROM users;
```

использование индекса может оказаться бессмысленным.

PostgreSQL может выбрать `Seq Scan`, потому что это дешевле.

---

# 6. Index Scan

```python
Index Scan using users_pkey on users
```

PostgreSQL использует индекс для поиска строк.

Например:

```python
SELECT *
FROM users
WHERE id = 123;
```

Если `id` индексирован, PostgreSQL может использовать:

```python
Index Scan
```

Это особенно эффективно для поиска небольшого количества строк.

---

# 7. Index Only Scan

```python
Index Only Scan using users_email_idx on users
```

PostgreSQL может получить необходимые данные **не обращаясь непосредственно к таблице**, а только из индекса.

Например, если индекс содержит все необходимые для запроса значения:

```python
SELECT email
FROM users
WHERE email = 'test@example.com';
```

Потенциальное преимущество:

```python
Index Scan
    ↓
Index → Table

Index Only Scan
    ↓
Index
```

Но фактическая возможность полностью обойти таблицу зависит, в частности, от **visibility map** и состояния страниц.

---

# 8. Bitmap Index Scan

Для большого количества подходящих строк PostgreSQL может использовать bitmap-план:

```python
Bitmap Index Scan
        ↓
Bitmap Heap Scan
        ↓
      Table
```

Например:

```python
SELECT *
FROM users
WHERE age BETWEEN 20 AND 40;
```

Индекс сначала помогает определить подходящие страницы/строки, после чего PostgreSQL читает соответствующие страницы таблицы.

---

# 9. JOIN в EXPLAIN

PostgreSQL имеет несколько основных алгоритмов JOIN.

### Nested Loop

```python
Nested Loop
```

Для каждой строки одной стороны ищутся соответствия на другой.

Хорошо работает, например, когда одна сторона маленькая и на второй есть подходящий индекс.

---

### Hash Join

```python
Hash Join
```

PostgreSQL строит hash-структуру для одной стороны и использует её для поиска соответствий.

Часто эффективен для больших наборов данных при соединении по равенству:

```python
users.id = orders.user_id
```

---

### Merge Join

```python
Merge Join
```

Соединяет два уже упорядоченных набора данных.

Особенно полезен, когда данные уже отсортированы или сортировка оказывается выгодной.

---

# 10. Sort

В плане можно увидеть:

```python
Sort
```

Например:

```python
SELECT *
FROM users
ORDER BY age;
```

PostgreSQL может выполнить отдельную сортировку.

Если подходящий индекс позволяет получить строки уже в нужном порядке, сортировка иногда может быть устранена.

---

# 11. Aggregate

Для агрегатных функций:

```python
SELECT COUNT(*)
FROM users;
```

в плане могут появляться:

```python
Aggregate
```

или, в зависимости от запроса и выбранного плана:

```python
GroupAggregate
HashAggregate
```

Например:

```python
SELECT age, COUNT(*)
FROM users
GROUP BY age;
```

PostgreSQL должен сгруппировать данные и вычислить агрегаты.

---

# 12. Filter и Index Cond

Очень важное различие.

### Index Cond

```python
Index Cond: (age > 30)
```

Условие используется самим индексом для поиска.

### Filter

```python
Filter: (status = 'active')
```

Строки уже получены из источника, после чего PostgreSQL дополнительно фильтрует их.

Условно:

```python
Index
  ↓
найдены строки
  ↓
Filter
  ↓
результат
```

Большое количество отфильтрованных строк может быть сигналом для оптимизации.

---

# 13. Estimated vs Actual

Одна из самых важных вещей при анализе:

```python
rows=100
actual rows=100
```

Оценка хорошая.

Но если:

```python
rows=100
actual rows=100000
```

PostgreSQL сильно ошибся в оценке.

Это может повлиять на выбор плана.

Например, оптимизатор ожидал:

```python
100 строк
```

и выбрал `Nested Loop`.

А фактически оказалось:

```python
100000 строк
```

Для такого объёма другой алгоритм JOIN мог бы быть эффективнее.

---

# 14. Почему PostgreSQL ошибается в rows

Планировщик использует **статистику**, собранную по таблицам.

Статистика может стать устаревшей после большого количества изменений данных.

Обычно PostgreSQL обновляет её через `ANALYZE` / `VACUUM ANALYZE` и механизм autovacuum.

Можно вручную:

```python
ANALYZE users;
```

После этого PostgreSQL получает более актуальную статистику для планирования запросов.

---

# 15. EXPLAIN для UPDATE и DELETE

С `UPDATE` и `DELETE` нужно быть осторожным.

```python
EXPLAIN DELETE FROM users
WHERE id = 100;
```

Обычный `EXPLAIN` показывает план, **не выполняя удаление**.

Но:

```python
EXPLAIN ANALYZE
DELETE FROM users
WHERE id = 100;
```

уже **реально выполнит DELETE**.

То же самое относится к `UPDATE`.

Поэтому `EXPLAIN ANALYZE` нельзя бездумно запускать на изменяющих данные запросах.

---

# 16. Полезные параметры EXPLAIN

Можно получить больше информации:

```python
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE age > 30;
```

### `ANALYZE`

Реально выполняет запрос и показывает фактические показатели.

### `BUFFERS`

Показывает информацию о чтении/использовании страниц:

```python
Buffers: shared hit=100
         shared read=20
```

Условно:

* `hit` — страница была найдена в PostgreSQL buffer
