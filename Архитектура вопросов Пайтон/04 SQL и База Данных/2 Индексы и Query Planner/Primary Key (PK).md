# 🔑 Primary Key (PK) — первичный ключ в SQL

## 🎤 Короткий ответ

**Primary Key (первичный ключ)** — это ограничение в реляционной базе данных, которое однозначно идентифицирует каждую строку таблицы.

Первичный ключ обладает тремя основными свойствами:

- **Уникальность** — значения не могут повторяться.
- **NOT NULL** — значение не может отсутствовать.
- **Один Primary Key на таблицу** — при этом он может состоять из нескольких столбцов.

Первичный ключ используется для идентификации записей, построения связей между таблицами и обеспечения целостности данных.

## 🗣️ Ответ на собеседовании

Primary Key — это первичный ключ таблицы, который позволяет однозначно идентифицировать каждую запись.

Например, в таблице пользователей я могу использовать поле `id` в качестве первичного ключа. Даже если у двух пользователей совпадают имена, их идентификаторы будут различаться.

На уровне базы данных Primary Key гарантирует уникальность и запрещает `NULL`.

Первичный ключ может быть простым, состоящим из одного столбца, или составным — из нескольких.

В PostgreSQL при создании Primary Key автоматически создаётся уникальный B-tree индекс, если подходящего индекса ещё нет. Это помогает эффективно искать записи по идентификатору.

Также Primary Key часто используется как цель для Foreign Key — внешнего ключа, связывающего таблицы.

При этом важно понимать, что Primary Key — это логическое ограничение целостности, а индекс — физическая структура для поиска данных.

## 📚 Разбор поглубже

### 1. Что такое Primary Key

Представим таблицу пользователей:

| id | name | email |
|---|---|---|
| 1 | Иван | ivan@mail.ru |
| 2 | Анна | anna@mail.ru |
| 3 | Иван | ivan2@mail.ru |

Имена могут повторяться, но `id` уникален.

Поэтому именно `id` удобно использовать как Primary Key.

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
);
```

Здесь:

- `id` — идентификатор пользователя.
- `INTEGER` — целочисленный тип данных.
- `PRIMARY KEY` — ограничение первичного ключа.
- `name` и `email` — обычные столбцы.

База данных не позволит добавить двух пользователей с одинаковым `id`.

### 2. Какие ограничения накладывает Primary Key

Primary Key объединяет два важных требования.

**Уникальность**

```sql
INSERT INTO users (id, name)
VALUES (1, 'Иван');

INSERT INTO users (id, name)
VALUES (1, 'Анна');
```

Второй запрос завершится ошибкой, потому что `id = 1` уже существует.

**Запрет NULL**

```sql
INSERT INTO users (id, name)
VALUES (NULL, 'Пётр');
```

Этот запрос тоже завершится ошибкой.

`NULL` означает отсутствие значения. Для первичного ключа это недопустимо.

### 3. Автоматическая генерация Primary Key

В PostgreSQL удобно использовать `GENERATED AS IDENTITY`.

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);
```

Теперь идентификатор генерируется автоматически:

```sql
INSERT INTO users (name)
VALUES ('Иван')
RETURNING id;
```

Пример результата:

```text
 id
----
  1
```

Разберём:

- `BIGINT` — 64-битное целое число.
- `GENERATED ALWAYS AS IDENTITY` — PostgreSQL генерирует идентификатор с помощью последовательности.
- `PRIMARY KEY` — обеспечивает уникальность и запрет `NULL`.
- `RETURNING id` — возвращает идентификатор добавленной записи.

**Важный нюанс:** автоматически сгенерированные идентификаторы не обязаны идти без пропусков.

Например, после отката транзакции значение последовательности может оказаться пропущенным.

Primary Key гарантирует уникальность, но не непрерывную нумерацию.

### 4. Простой и составной Primary Key

**Простой Primary Key** состоит из одного столбца.

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name TEXT NOT NULL
);
```

**Составной Primary Key (Composite Primary Key)** состоит из нескольких столбцов.

Например, таблица товаров в заказах:

```sql
CREATE TABLE order_items (
    order_id BIGINT,
    product_id BIGINT,
    quantity INTEGER NOT NULL,

    PRIMARY KEY (order_id, product_id)
);
```

Здесь уникальна именно комбинация:

```text
(order_id, product_id)
```

Пример:

| order_id | product_id | quantity |
|---|---|---|
| 1 | 10 | 2 |
| 1 | 20 | 1 |
| 2 | 10 | 5 |

Такие записи допустимы.

А вот повторная комбинация `(1, 10)` будет запрещена.

Составной Primary Key полезен для таблиц связей Many-to-Many, если одна и та же пара значений не должна повторяться.

### 5. Primary Key и Foreign Key

Это два связанных понятия.

- **Primary Key** идентифицирует запись.
- **Foreign Key** ссылается на ключ другой или той же таблицы.

Пример:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    amount NUMERIC(10, 2) NOT NULL
);
```

Связь:

```text
users
┌──────────────┐
│ id (PK)      │
│ name         │
└──────┬───────┘
       │
       │ 1:N
       │
       v
orders
┌──────────────┐
│ id (PK)      │
│ user_id (FK) │
│ amount       │
└──────────────┘
```

Один пользователь может иметь много заказов.

При этом `orders.user_id` ссылается на `users.id`.

База данных не позволит создать заказ с несуществующим пользователем, если внешний ключ активен и не предусмотрено специальное поведение.

### 6. Primary Key vs UNIQUE

Оба ограничения обеспечивают уникальность, но не полностью эквивалентны.

| Характеристика | PRIMARY KEY | UNIQUE |
|---|---|---|
| Уникальность | Да | Да |
| Разрешает NULL | Нет | В PostgreSQL обычно да |
| Количество ограничений на таблицу | Одно | Несколько |
| Составной ключ | Да | Да |
| Автоматический уникальный индекс в PostgreSQL | Да | Да |

Пример:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    email TEXT UNIQUE
);
```

Здесь:

- `id` — основной идентификатор записи.
- `email` — уникальное значение, но не первичный ключ.

В PostgreSQL обычное ограничение `UNIQUE` допускает несколько `NULL`, поскольку по умолчанию `NULL` не считается равным другому `NULL`.

Если email обязателен, нужно добавить `NOT NULL`:

```sql
email TEXT NOT NULL UNIQUE
```

Начиная с PostgreSQL 15 также существует `UNIQUE NULLS NOT DISTINCT`, позволяющее считать `NULL` одинаковыми для проверки уникальности.

### 7. Primary Key и индексы

В PostgreSQL создание Primary Key автоматически приводит к созданию уникального B-tree индекса.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name TEXT
);
```

Логически:

```text
PRIMARY KEY
    |
    ├── Уникальность
    ├── Запрет NULL
    └── Уникальный B-tree индекс
```

Запрос:

```sql
SELECT *
FROM users
WHERE id = 100;
```

может использовать индекс для быстрого поиска.

Но **наличие индекса не гарантирует, что PostgreSQL всегда его выберет**.

Для небольшой таблицы планировщик может предпочесть `Seq Scan` — последовательное чтение.

Проверить план можно так:

```sql
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE id = 100;
```

Важно различать:

- `PRIMARY KEY` — ограничение целостности данных.
- `INDEX` — структура, помогающая ускорять определённые операции.

Также в PostgreSQL первичный ключ не означает физическую сортировку строк таблицы по этому ключу.

### 8. Какие типы данных использовать для Primary Key

На практике часто выбирают `BIGINT` или `UUID`.

**BIGINT**

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

Преимущества:

- Компактный размер — 8 байт.
- Простое сравнение.
- Удобен для внутренних идентификаторов.
- Хорошо подходит для большинства обычных Backend-приложений.

**UUID**

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL
);
```

UUID занимает 16 байт.

Преимущества:

- Идентификаторы можно генерировать независимо в разных системах.
- Удобен для распределённых приложений.
- Не раскрывает простую последовательную нумерацию записей.

Недостатки:

- Индексы обычно крупнее, чем для `BIGINT`.
- Некоторые варианты UUID, например случайные UUIDv4, могут приводить к менее локальным вставкам в B-tree.
- Идентификаторы менее удобны для чтения человеком.

UUIDv7 частично улучшает локальность вставок благодаря временной упорядоченности.

**Что выбрать?**

Для обычного Backend-сервиса `BIGINT IDENTITY` часто является хорошим вариантом по умолчанию.

UUID стоит рассматривать, если нужны независимо генерируемые идентификаторы, распределённое создание сущностей или другие соответствующие архитектурные требования.

### 9. Primary Key в SQLAlchemy

Пример модели SQLAlchemy 2.x:

```python
from sqlalchemy import BigInteger, Identity, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        BigInteger,
        Identity(),
        primary_key=True,
    )

    name: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
    )
```

Разберём:

`DeclarativeBase` — базовый класс для декларативного описания ORM-моделей.

`__tablename__` — имя таблицы в базе данных.

`Mapped[int]` — типизированное ORM-поле.

`mapped_column()` — описание столбца.

`Identity()` — генерация идентификатора средствами PostgreSQL.

`primary_key=True` — указание, что поле входит в первичный ключ.

Для ORM первичный ключ особенно важен: SQLAlchemy использует его для идентификации объектов в **Identity Map** — механизме, который помогает отслеживать экземпляры одной и той же записи в рамках сессии.

### 10. Можно ли изменить Primary Key?

Да, технически это возможно.

```sql
UPDATE users
SET id = 200
WHERE id = 100;
```

Но на практике первичные ключи обычно стараются делать стабильными.

Почему?

Потому что на них могут ссылаться другие таблицы.

Если изменить значение ключа, связанные записи могут нарушить ограничения Foreign Key.

Поведение зависит от настройки внешнего ключа, например `ON UPDATE CASCADE`.

Поэтому хороший первичный ключ обычно:

- Уникален.
- Не содержит `NULL`.
- Стабилен во времени.
- Не зависит от изменяемых бизнес-данных.

### 11. Natural Key vs Surrogate Key

Это ещё один вопрос, который встречается на собеседованиях.

**Natural Key (естественный ключ)** — идентификатор, который уже существует в предметной области.

Например, уникальный артикул товара.

```sql
CREATE TABLE products (
    sku TEXT PRIMARY KEY,
    name TEXT NOT NULL
);
```

**Surrogate Key (суррогатный ключ)** — искусственный идентификатор, созданный специально для базы данных.

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL
);
```

Второй подход часто удобнее, потому что артикул может измениться, а внутренний `id` останется прежним.

| Критерий | Natural Key | Surrogate Key |
|---|---|---|
| Основан на бизнес-данных | Да | Нет |
| Может изменяться | Иногда | Обычно нет |
| Удобен для связей | Зависит от значения | Обычно да |
| Пример | SKU | BIGINT ID, UUID |

### 12. Типичные ошибки

**Ошибка 1. Считать Primary Key просто индексом.**

Primary Key — это ограничение целостности. В PostgreSQL для его обеспечения создаётся уникальный индекс.

**Ошибка 2. Считать, что Primary Key всегда называется id.**

Название может быть любым.

```sql
CREATE TABLE countries (
    country_code CHAR(2) PRIMARY KEY
);
```

**Ошибка 3. Считать, что Primary Key всегда состоит из одного столбца.**

Он может быть составным.

**Ошибка 4. Считать, что автоматически генерируемые ID всегда идут подряд.**

Последовательности могут иметь пропуски.

**Ошибка 5. Использовать изменяемое поле как Primary Key без необходимости.**

Например, email пользователя может измениться. Часто удобнее использовать отдельный стабильный идентификатор.

**Ошибка 6. Путать Primary Key и Foreign Key.**

Первичный ключ идентифицирует строку, внешний — задаёт ссылку на ключ другой или той же таблицы.

**Ошибка 7. Считать, что Primary Key автоматически создаёт индексы на всех Foreign Key.**

В PostgreSQL индекс на ссылающемся столбце внешнего ключа автоматически не создаётся. При необходимости его добавляют отдельно.

## 🎤 Вопросы на собеседовании

**1. Что такое Primary Key?**

Ограничение, обеспечивающее уникальную идентификацию каждой строки таблицы.

**2. Может ли Primary Key содержать NULL?**

Нет.

**3. Может ли таблица иметь несколько Primary Key?**

Нет, только один. Но он может включать несколько столбцов.

**4. Чем Primary Key отличается от UNIQUE?**

Primary Key обязательно запрещает `NULL` и существует в единственном экземпляре на таблицу. Ограничений UNIQUE может быть несколько.

**5. Создаёт ли Primary Key индекс в PostgreSQL?**

Да, уникальный B-tree индекс, если подходящего ещё нет.

**6. Может ли Primary Key состоять из нескольких столбцов?**

Да. Это составной первичный ключ.

**7. Чем Primary Key отличается от Foreign Key?**

Primary Key идентифицирует запись, Foreign Key обеспечивает ссылочную целостность между записями.

**8. Что лучше использовать: BIGINT или UUID?**

Зависит от архитектуры. BIGINT компактен и удобен для обычных приложений, UUID полезен для независимой генерации идентификаторов.

**9. Что такое Surrogate Key?**

Искусственный идентификатор, не имеющий самостоятельного бизнес-смысла, например `id`.

**10. Почему Primary Key важен для SQLAlchemy?**

ORM использует первичный ключ для идентификации записей и отслеживания объектов внутри сессии.

**11. Гарантирует ли Primary Key физическую сортировку таблицы?**

Нет. В PostgreSQL строки не обязаны храниться в порядке первичного ключа.

**12. Может ли Foreign Key ссылаться не на Primary Key?**

Да. В PostgreSQL внешний ключ может ссылаться также на подходящий уникальный ключ или допустимый уникальный индекс.

## 🧪 Мини-задание

Создай две таблицы в PostgreSQL:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username TEXT NOT NULL UNIQUE
);

CREATE TABLE posts (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    title TEXT NOT NULL
);
```

Попробуй:

1. Добавить двух пользователей с одинаковым `username`.
2. Добавить пост с несуществующим `user_id`.
3. Добавить два поста с одинаковым `id`.
4. Проверить индексы таблицы через `\d users` в `psql`.

Подумай, какое ограничение сработает в каждом случае.

**Главное, что нужно запомнить:** `PRIMARY KEY` = уникальность + `NOT NULL` + идентификация строки. В PostgreSQL он дополнительно обеспечивается уникальным B-tree индексом.
