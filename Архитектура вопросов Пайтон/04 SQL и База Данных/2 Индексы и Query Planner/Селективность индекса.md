# Селективность индекса в PostgreSQL 🎯

## 🎯 Ответ на собеседовании

**Селективность** — это способность условия отбора сильно уменьшать количество строк, которые нужно обработать.

Чем меньше строк подходит под условие относительно общего количества строк, тем **выше селективность** и тем потенциально полезнее индекс.

Например:

```python
Таблица: 1 000 000 строк

WHERE id = 123
→ 1 строка
→ высокая селективность
→ Index Scan вероятно выгоден
```

А:

```python
Таблица: 1 000 000 строк

WHERE gender = 'M'
→ 500 000 строк
→ низкая селективность
→ Seq Scan может оказаться выгоднее
```

Важно:

> **Высокая селективность не гарантирует использование индекса. Окончательное решение принимает PostgreSQL Planner.**

---

## 🎤 Суперкоротко

```python
Селективность
    ↓
насколько условие уменьшает количество строк

мало совпадений
    ↓
высокая селективность
    ↓
индекс часто полезен

много совпадений
    ↓
низкая селективность
    ↓
Seq Scan / Bitmap Scan может быть выгоднее
```

---

# 1. Простая интуиция

Представим таблицу:

```python
1 000 000 пользователей
```

Запрос:

```python
WHERE id = 123
```

Находим:

```python
1 пользователя
```

Условие очень хорошо отбирает данные.

Это **высокая селективность**.

---

Другой запрос:

```python
WHERE country = 'Russia'
```

Допустим:

```python
700 000 пользователей
```

подходят под условие.

Такое условие значительно хуже сокращает объём данных.

Селективность ниже.

---

# 2. Условно можно представить формулой

Для понимания можно использовать:

```python
селективность ≈ количество подходящих строк / общее количество строк
```

Например:

```python
10 / 1 000 000 = 0.00001
```

Очень мало строк соответствует условию.

Высокая селективность.

Другой пример:

```python
800 000 / 1 000 000 = 0.8
```

Очень большая доля таблицы соответствует условию.

Селективность низкая.

⚠️ В PostgreSQL терминологию селективности важно не привязывать к одной универсальной формуле: planner использует более сложные статистические оценки. Формула выше — удобная модель для понимания.

---

# 3. Высокая селективность

Пример:

```python
SELECT *
FROM users
WHERE id = 123456;
```

Если:

```python
1 000 000 строк
↓
1 строка
```

то:

```python
высокая селективность
```

Индекс:

```python
id → Index
```

может быстро найти нужную запись.

План часто может быть:

```python
Index Scan
```

---

# 4. Низкая селективность

Например:

```python
SELECT *
FROM users
WHERE is_active = true;
```

Допустим:

```python
1 000 000 строк
↓
950 000 строк
```

Индекс по:

```python
is_active
```

может оказаться малоэффективным.

Почему?

Потому что PostgreSQL всё равно должен получить огромное количество строк.

В такой ситуации:

```python
Seq Scan
```

может быть дешевле.

---

# 5. Селективность и Index Scan

Упрощённая логика:

```python
Высокая селективность
        ↓
мало подходящих строк
        ↓
Index Scan
        ↓
получить только нужные строки
```

А:

```python
Низкая селективность
        ↓
много подходящих строк
        ↓
Index Scan может быть дорогим
        ↓
Bitmap Scan или Seq Scan
```

Но это **не жёсткое правило**.

Planner учитывает стоимость всего плана.

---

# 6. Пример с таблицей

Пусть:

```python
users = 10 000 000 строк
```

Есть индекс:

```python
CREATE INDEX idx_users_age
ON users(age);
```

### Запрос №1

```python
SELECT *
FROM users
WHERE age = 25;
```

Допустим:

```python
10 000 000
      ↓
100 000
```

Только 1% строк.

Индекс может быть очень полезен.

---

### Запрос №2

```python
SELECT *
FROM users
WHERE age >= 18;
```

Допустим:

```python
10 000 000
      ↓
9 000 000
```

90% строк.

Planner может предпочесть:

```python
Seq Scan
```

---

# 7. Селективность ≠ уникальность

Это разные понятия.

### Уникальность

Говорит:

> Может ли несколько строк иметь одинаковое значение?

Например:

```python
PRIMARY KEY
UNIQUE
```

обычно обеспечивают уникальность.

### Селективность

Говорит:

> Насколько конкретное условие сокращает множество строк?

Например:

```python
WHERE email = 'a@example.com'
```

если email уникален:

```python
1 000 000
      ↓
1
```

очень селективное условие.

---

# 8. Кардинальность

В контексте PostgreSQL часто встречается понятие **cardinality**.

Упрощённо:

> Кардинальность — количество строк/уникальных значений, связанное с конкретным набором данных или результатом.

Например:

```python
users = 1 000 000 строк
```

и:

```python
country
```

имеет:

```python
5 уникальных значений
```

Кардинальность множества значений небольшая.

Например:

```python
Russia
USA
Germany
France
China
```

Условие:

```python
WHERE country = 'Russia'
```

может возвращать огромную долю таблицы.

---

# 9. Высокая кардинальность и селективность

Часто:

```python
id
```

имеет высокую кардинальность:

```python
1 000 000 строк
≈
1 000 000 уникальных id
```

Поиск:

```python
WHERE id = 123
```

очень селективен.

А:

```python
gender
```

может иметь:

```python
2–3 уникальных значения
```

Поиск по нему часто менее селективен.

Поэтому индекс по `id` обычно гораздо эффективнее для точечного поиска.

---

# 10. Но низкая кардинальность не означает «индекс бесполезен»

Это важная оговорка.

Индекс по столбцу с небольшим количеством уникальных значений **не всегда бесполезен**.

Например:

```python
status
```

имеет:

```python
pending
completed
cancelled
```

Индекс может быть полезен, если одно из значений встречается редко.

Например:

```python
WHERE status = 'pending'
```

если:

```python
10 000 000 строк
↓
5 000 строк
```

условие очень селективно.

Поэтому нельзя говорить:

> «У столбца мало уникальных значений → индекс бесполезен».

Нужно смотреть на конкретное условие и распределение данных.

---

# 11. Распределение значений имеет значение

Допустим:

```python
status:
completed = 9 900 000
pending   = 50 000
failed    = 50 000
```

Индекс:

```python
status
```

может быть гораздо полезнее для:

```python
WHERE status = 'pending'
```

чем для:

```python
WHERE status = 'completed'
```

Потому что:

```python
pending
    ↓
0.5% строк
```

а:

```python
completed
    ↓
99% строк
```

Селективность зависит не только от самого столбца, но и от **конкретного значения и распределения данных**.

---

# 12. Селективность и составной индекс

Допустим:

```python
CREATE INDEX idx_users_country_age
ON users(country, age);
```

Запрос:

```python
WHERE country = 'Russia'
  AND age = 25;
```

Комбинация условий может быть гораздо более селективной, чем каждое условие отдельно.

Например:

```python
country = Russia
→ 500 000 строк

age = 25
→ 100 000 строк

country + age
→ 10 000 строк
```

Именно поэтому порядок и состав колонок составного индекса важны.

---

# 13. Селективность и Bitmap Scan

Низкая/средняя селективность не обязательно означает:

```python
Seq Scan
```

Может быть:

```python
Bitmap Index Scan
        ↓
Bitmap Heap Scan
```

Например:

```python
10 000 000 строк
        ↓
500 000 совпадений
```

Для такого объёма:

```python
Index Scan
```

может быть дорогим из-за большого количества обращений к heap.

Но:

```python
Bitmap Scan
```

может оказаться выгодным.

---

# 14. Селективность и EXPLAIN ANALYZE

Проверяем:

```python
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE status = 'pending';
```

Например:

```python
Index Scan using idx_users_status on users
  (cost=0.42..100.00 rows=5000 width=64)
  (actual time=0.020..2.000 rows=4800 loops=1)
```

Planner ожидал:

```python
rows=5000
```

Получил:

```python
actual rows=4800
```

Оценка хорошая.

---

Другой случай:

```python
rows=5000
actual rows=500000
```

Planner сильно ошибся.

Это может означать проблемы с оценкой распределения данных или статистикой.

---

# 15. Статистика PostgreSQL

Planner использует статистику таблиц для оценки количества строк.

Например:

```python
ANALYZE users;
```

обновляет статистику.

На основе неё PostgreSQL оценивает:

```python
сколько строк подходит условию
```

и выбирает:

```python
Seq Scan
Index Scan
Bitmap Scan
```

или другие варианты плана.

---

# 16. Селективность и Partial Index

Если часто нужен только небольшой сегмент данных, можно использовать **частичный индекс**.

Например:

```python
CREATE INDEX idx_orders_pending
ON orders(created_at)
WHERE status = 'pending';
```

Если:

```python
pending = 1%
```

таблицы, индекс получается значительно более узким.

Запрос:

```python
SELECT *
FROM orders
WHERE status = 'pending'
  AND created_at > '2026-01-01';
```

может эффективно использовать такой индекс.

Идея:

```python
вся таблица
    ↓
10 000 000 строк

partial index
    ↓
только pending
    ↓
100 000 строк
```

---

# 17. Селективность и NULL

Например:

```python
WHERE email IS NULL
```

Если:

```python
1% строк = NULL
```

условие достаточно селективное.

Если:

```python
90% строк = NULL
```

оно значительно менее селективно.

Поэтому наличие `NULL` само по себе не делает индекс бесполезным — важно распределение данных.

---

# 18. Селективность и JOIN

Селективность важна не только для `WHERE`.

Она влияет и на JOIN.

Например:

```python
SELECT *
FROM users u
JOIN orders o
    ON o.user_id = u.id
WHERE u.id = 100;
```

Если:

```python
WHERE u.id = 100
```

оставляет одну строку, PostgreSQL может выбрать эффективный:

```python
Nested Loop
```

и использовать индекс на:

```python
orders.user_id
```

То есть селективность фильтра может сильно влиять на весь план.

---

# 19. Главное заблуждение

❌ Неправильно:

> «Если индекс существует, PostgreSQL обязательно его использует».

Правильно:

> «PostgreSQL использует индекс, если считает его выгодным. Селективность — один из важных факторов, влияющих на это решение.»

---

# 20. Как объяснить на собеседовании

Вопрос:

> **«Что такое селективность индекса?»**

Хороший ответ:

> «Селективность показывает, насколько условие отбора сокращает количество строк. Если из миллиона строк условие возвращает одну тысячу, оно высокоселективное, и индекс часто будет эффективен. Если условие возвращает большую часть таблицы, селективность низкая, и PostgreSQL может предпочесть Seq Scan или Bitmap Scan. При этом окончательное решение принимает planner на основе статистики и стоимости всего плана.»

---

## 🧠 Главное

```python
Селективность
    ↓
насколько условие сокращает количество строк
```

```python
мало совпадений
    ↓
высокая селективность
    ↓
Index Scan часто выгоден
```

```python
среднее количество совпадений
    ↓
Bitmap Scan может быть выгоден
```

```python
очень много совпадений
    ↓
Seq Scan может быть выгоден
```

Но:

> **Селективность — не единственный фактор. PostgreSQL принимает решение на основе стоимости плана, статистики, размера таблицы, распределения данных и других факторов.**

### Связка всех изученных тем:

```python
Селективность
      ↓
Planner
      ↓
┌──────────────┬──────────────────┬───────────────┐
↓              ↓                  ↓
Seq Scan    Index Scan       Bitmap Scan
                                   ↓
                         Bitmap Index Scan
                                   ↓
                         Bitmap Heap Scan
```

**Ключевая мысль:** чем меньше строк нужно получить относительно размера таблицы, тем сильнее аргумент в пользу индексного доступа — но окончательное решение всегда принимает PostgreSQL Planner.
