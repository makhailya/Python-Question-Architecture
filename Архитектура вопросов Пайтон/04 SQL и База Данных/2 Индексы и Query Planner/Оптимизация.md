# ⚡ Оптимизация базы данных

## 🎯 Ответ на собеседовании

**Оптимизация БД** — это комплекс мер, направленных на уменьшение стоимости операций с базой данных и повышение производительности без необходимости просто увеличивать ресурсы сервера.

Основные направления:

* оптимизация SQL-запросов;
* правильные индексы;
* анализ планов через [[EXPLAIN]];
* уменьшение количества данных, которые читаются и передаются;
* оптимизация [[JOIN]] и сортировок;
* правильная работа с транзакциями;
* кэширование;
* connection pooling;
* актуальная статистика `ANALYZE`;
* partitioning для больших таблиц.

Главный принцип:

> **Сначала найти bottleneck, затем оптимизировать именно его.**

```python id="w8n4kc"
Оптимизация БД

Найти bottleneck

EXPLAIN ANALYZE

```

Не нужно сразу:

```python id="n3m7qa"
"База медленная → добавим CPU"
```

Сначала нужно понять **почему** она медленная.

---

# 1. 🔍 Найти узкое место

**Bottleneck** — компонент, который ограничивает производительность системы.

Например:

```python id="p5r2vx"
Application
     ↓
PostgreSQL
     ↓
Seq Scan 🔥
     ↓
500 млн строк
```

В таком случае проблема может быть в запросе или отсутствии индекса, а не в недостатке CPU.

Другой вариант:

```python id="j7c4mz"
SQL хороший
     ↓
Index Scan
     ↓
Disk I/O 🔥
```

Тогда нужно исследовать дисковую подсистему.

---

# 2. 🧪 EXPLAIN

Для анализа запроса используют:

```python id="q6m9wp"
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

`EXPLAIN` показывает **планировочный план**, который PostgreSQL собирается использовать.

Например:

```python id="a2x7kn"
Seq Scan on users
```

или:

```python id="f8r3yc"
Index Scan using idx_users_email on users
```

---

# 3. 🔬 EXPLAIN ANALYZE

`EXPLAIN ANALYZE` не просто показывает план, а **реально выполняет запрос** и показывает фактические показатели.

```python id="v5k8mq"
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE email = 'test@example.com';
```

Можно сравнить:

```python id="m3q9xa"
Estimated rows → 1
Actual rows    → 100000
```

Сильное расхождение может говорить о плохой статистике или неверных оценках планировщика.

---

# 4. 📊 Что смотреть в EXPLAIN

Основные показатели:

### `cost`

```python id="n7x4cq"
cost=0.42..8.44
```

Это **оценочная стоимость**, а не миллисекунды.

---

### `rows`

Количество строк, которое планировщик ожидает получить.

```python id="r5m8vp"
rows=10
```

---

### `actual time`

Фактическое время выполнения узла.

```python id="t2k6nz"
actual time=0.025..0.031
```

---

### `loops`

Сколько раз выполнялся узел.

```python id="y8q3md"
loops=1000
```

---

### `Buffers`

Полезно использовать:

```python id="c4w7px"
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

Можно увидеть информацию о чтении страниц из памяти и диска.

---

# 5. 📑 Индексы

Один из основных способов оптимизации запросов.

Например:

```python id="z3n6ka"
CREATE INDEX idx_users_email
ON users (email);
```

Вместо:

```python id="v8m2qy"
Seq Scan
→ проверить множество строк
```

PostgreSQL может использовать:

```python id="b6x9wr"
Index Scan
→ быстро найти нужные строки
```

Но:

> **Индекс не гарантирует ускорение.**

Планировщик сам выбирает наиболее дешёвый план.

---

# 6. 🎯 Селективность

**Селективность** — доля строк, удовлетворяющих условию.

Например:

```python id="k4p8ns"
1 000 000 строк
10 подходящих
```

Условие имеет высокую селективность.

```python id="m7q2cx"
1 000 000 строк
900 000 подходящих
```

Селективность низкая.

При высокой селективности индекс часто выгоден.

При низкой PostgreSQL может выбрать:

```python id="d5w9zr"
Seq Scan
```

потому что чтение большого количества строк через индекс может оказаться дороже.

---

# 7. 🧩 Композитные индексы

Если запрос часто использует несколько колонок:

```python id="u3x7mb"
SELECT *
FROM orders
WHERE user_id = 10
  AND status = 'paid';
```

может быть полезен:

```python id="c8n5qa"
CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
```

Но порядок колонок важен.

```python id="s6m2vd"
(user_id, status)
```

Наиболее предсказуемо эффективен для условий, начинающихся с:

```python id="r9x4kp"
user_id
```

То есть:

```python id="h7c3mn"
WHERE user_id = ...
```

и:

```python id="q5v8za"
WHERE user_id = ...
  AND status = ...
```

---

# 8. 🪶 Не выбирать лишние данные

Плохой вариант:

```python id="j4n7xc"
SELECT *
FROM users;
```

если нужны только два поля.

Лучше:

```python id="m8q2vp"
SELECT id, name
FROM users;
```

Это уменьшает:

* объём чтения;
* передачу данных;
* потребление памяти;
* работу приложения.

Особенно важно для больших таблиц.

---

# 9. 🔢 LIMIT

Если нужны только первые несколько записей:

```python id="t6p3yw"
SELECT id, name
FROM users
ORDER BY created_at DESC
LIMIT 20;
```

`LIMIT` может существенно уменьшить объём работы, особенно вместе с подходящим индексом.

Например:

```python id="k9r4mb"
CREATE INDEX idx_users_created_at
ON users (created_at DESC);
```

Тогда PostgreSQL потенциально может быстро получить первые нужные записи, не сортируя всю таблицу.

---

# 10. 🔗 Оптимизация JOIN

JOIN может стать дорогим при больших таблицах.

Например:

```python id="c5x8qn"
SELECT *
FROM orders o
JOIN users u
  ON u.id = o.user_id;
```

Полезно проверить:

* индексы;
* количество строк;
* условия фильтрации;
* порядок выполнения;
* план JOIN.

PostgreSQL может использовать:

```python id="z7m3pv"
Nested Loop
Hash Join
Merge Join
```

---

# 11. 🚫 Не делать JOIN раньше необходимого

Если сначала соединить огромные таблицы:

```python id="w4n8kc"
10 млн rows
     JOIN
20 млн rows
```

а потом отфильтровать:

```python id="q3x6mv"
WHERE status = 'active'
```

объём работы может быть большим.

Нужно писать запрос так, чтобы оптимизатор мог эффективно применить фильтры.

Например:

```python id="s8k2ry"
SELECT ...
FROM orders o
JOIN users u
  ON u.id = o.user_id
WHERE o.status = 'paid';
```

PostgreSQL сам строит план, поэтому не стоит механически переписывать SQL ради «порядка строк» без проверки `EXPLAIN`.

---

# 12. 🧹 ANALYZE

PostgreSQL использует статистику таблиц для выбора плана.

Статистику обновляет:

```python id="x5q9mb"
ANALYZE users;
```

Планировщик получает информацию о:

* количестве строк;
* распределении значений;
* NULL;
* наиболее частых значениях;
* гистограммах;
* корреляции.

Если статистика устарела:

```python id="n7c3vp"
плохая статистика
      ↓
неверная оценка rows
      ↓
неудачный план
      ↓
медленный запрос
```

Обычно статистикой автоматически занимается **autovacuum/analyze**.

---

# 13. 🧹 VACUUM

В PostgreSQL из-за MVCC появляются старые версии строк.

`VACUUM` помогает очищать dead tuples:

```python id="q8m2xa"
UPDATE
   ↓
новая версия строки
   ↓
старая версия становится dead
   ↓
VACUUM
   ↓
место можно использовать повторно
```

Также VACUUM обновляет visibility map, что помогает `Index Only Scan`.

Важно:

> `VACUUM` и `ANALYZE` решают разные задачи.

```python id="f4n9kc"
VACUUM
→ обслуживание MVCC

ANALYZE
→ статистика для planner
```

# 14. 💾 Кэширование

Если одни и те же данные читаются очень часто, можно использовать Redis:

```python id="r2x7mv"
Application
     │
     ▼
   Redis
     │
     ├── HIT  → данные
     │
     └── MISS
          ↓
          DB
```

Это уменьшает количество запросов к БД.

Но появляется новая проблема:

**Cache Invalidation**.

После изменения данных нужно правильно обновлять или удалять кэш.

# 15. 🔌 Connection Pooling

Создание нового соединения для каждого запроса дорого.

Плохой сценарий:

```python id="n6q3wr"
Request
  ↓
connect
  ↓
query
  ↓
disconnect
```

Лучше:

```python id="p8m4ya"
       Connection Pool
      /      |      \
   conn    conn    conn
      \      |      /
       PostgreSQL
```

Соединения переиспользуются.

Для PostgreSQL часто используют:

**PgBouncer**.

# 16. 📦 Batch Operations

Много отдельных запросов:

```python id="x3k7mq"
INSERT
INSERT
INSERT
INSERT
INSERT
```

может быть менее эффективно, чем пакетная операция.

Например:

```python id="v9r2cz"
INSERT INTO users (name)
VALUES
    ('Ivan'),
    ('Petr'),
    ('Anna');
```

Batching уменьшает количество round trips:

```python id="j5m8xp"
1000 запросов
    ↓
много network round trips

1 batch
    ↓
меньше round trips
```

# 17. 🌐 Уменьшение количества запросов

Иногда проблема не в одном медленном запросе, а в их количестве.

Классический пример — **N+1 Query Problem**.

Например:

```python id="k7v3mn"
SELECT * FROM users;

SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
...
```

Получаем:

```python id="b4x9qa"
1 запрос users
+
N запросов orders
=
N + 1
```

Лучше использовать JOIN, batch-запросы или возможности ORM для eager loading.

---

# 18. 📚 Pagination

Плохой вариант для очень больших таблиц:

```python id="y6m2wc"
SELECT *
FROM orders
ORDER BY id
LIMIT 50 OFFSET 1000000;
```

Чем больше `OFFSET`, тем больше строк может потребоваться пропустить.

Для больших объёмов часто используют **Keyset Pagination / Cursor Pagination**:

```python id="t8q4mz"
SELECT *
FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 50;
```

При подходящем индексе это может быть значительно эффективнее.

---

# 19. 🗂️ Partitioning

Для очень больших таблиц можно использовать партиционирование:

```python id="m5x8kp"
orders
├── 2024
├── 2025
├── 2026
└── 2027
```

Если запрос содержит partition key:

```python id="q7c3nv"
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01'
```

PostgreSQL может использовать:

**Partition Pruning**
