# 🧩 Композитный индекс

## 🎯 Ответ на собеседовании

**Композитный индекс (composite index)** — это индекс, построенный **сразу по нескольким колонкам**.

Например:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

Такой индекс может быть полезен для запросов, которые фильтруют или сортируют данные по `city` и `age`.

Главный нюанс — **порядок колонок в композитном индексе имеет значение**.

Индекс:

```python
(city, age)
```

и индекс:

```python
(age, city)
```

— это разные индексы и могут эффективно использоваться для разных запросов.

---

## 🎤 Суперкоротко

> Композитный индекс — индекс по нескольким колонкам. Порядок колонок важен: обычно эффективно используются условия по ведущим, то есть левым, колонкам индекса. Например, индекс `(city, age)` хорошо подходит для поиска по `city` и по `city + age`, но не обязательно эффективен для поиска только по `age`.

---

## 📌 Простой пример

Есть таблица:

```python
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    city TEXT,
    age INTEGER,
    name TEXT
);
```

Создадим индекс:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

Структура индекса концептуально:

```text
(city, age)
```

То есть сначала учитывается:

```text
city
```

а внутри одинаковых `city` —:

```text
age
```

Упрощённо:

```text
Moscow
 ├── 20
 ├── 25
 ├── 30
 └── 40

Paris
 ├── 18
 ├── 25
 └── 35

London
 ├── 21
 ├── 30
 └── 45
```

---

## 🔑 Порядок колонок — главное

Для индекса:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

условие:

```python
WHERE city = 'Moscow'
```

хорошо соответствует индексу.

Условие:

```python
WHERE city = 'Moscow'
  AND age = 30
```

тоже хорошо соответствует индексу.

А вот:

```python
WHERE age = 30
```

не использует преимущество ведущей колонки `city` так же эффективно.

Это называют **правилом левой части индекса (leftmost prefix)**.

---

## 🧠 Правило левого префикса

Для индекса:

```python
CREATE INDEX idx_users_city_age_name
ON users (city, age, name);
```

условно хорошо подходят:

```text
(city)
(city, age)
(city, age, name)
```

Например:

```python
SELECT *
FROM users
WHERE city = 'Moscow';
```

```python
SELECT *
FROM users
WHERE city = 'Moscow'
  AND age = 30;
```

```python
SELECT *
FROM users
WHERE city = 'Moscow'
  AND age = 30
  AND name = 'Ivan';
```

А запрос только по:

```python
WHERE age = 30
```

или:

```python
WHERE name = 'Ivan'
```

не получает той же выгоды от структуры `(city, age, name)`.

⚠️ Это упрощённая модель. Реальный PostgreSQL-планировщик может использовать индекс и в более сложных случаях, например частично, для других условий или через Bitmap Scan. Поэтому правильнее говорить:

> **Наиболее предсказуемая эффективность композитного B-tree индекса достигается при использовании его ведущих колонок.**

---

## 📊 Почему порядок важен

Рассмотрим два индекса:

```python
CREATE INDEX idx_1
ON users (city, age);
```

и:

```python
CREATE INDEX idx_2
ON users (age, city);
```

Они предназначены не совсем для одного и того же.

### `(city, age)`

Хорош для:

```python
WHERE city = 'Moscow'
```

и:

```python
WHERE city = 'Moscow'
  AND age = 30
```

### `(age, city)`

Хорош для:

```python
WHERE age = 30
```

и:

```python
WHERE age = 30
  AND city = 'Moscow'
```

Поэтому порядок колонок выбирают **из реальных запросов приложения**.

---

## 🔎 Композитный индекс и WHERE

Допустим:

```python
CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
```

Запрос:

```python
SELECT *
FROM orders
WHERE user_id = 100
  AND status = 'paid';
```

Это хороший кандидат для такого индекса.

Потому что индекс соответствует структуре фильтра:

```text
user_id → status
```

---

## 🔢 Композитный индекс и ORDER BY

Композитный индекс может быть полезен не только для `WHERE`, но и для сортировки.

Например:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

Запрос:

```python
SELECT *
FROM users
WHERE city = 'Moscow'
ORDER BY age;
```

может хорошо использовать такой индекс.

Индекс уже организован по:

```text
city → age
```

поэтому PostgreSQL потенциально может избежать отдельной сортировки или уменьшить её стоимость.

---

## ⚡ Композитный индекс и LIMIT

Очень полезный сценарий:

```python
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);
```

Запрос:

```python
SELECT *
FROM orders
WHERE user_id = 100
ORDER BY created_at DESC
LIMIT 10;
```

Такой индекс хорошо соответствует запросу:

```text
user_id
   ↓
created_at DESC
   ↓
первые 10 строк
```

Это может позволить PostgreSQL быстро получить последние заказы пользователя, не сортируя большое количество строк.

---

## 🧩 Композитный индекс vs несколько отдельных индексов

Допустим, запрос:

```python
SELECT *
FROM users
WHERE city = 'Moscow'
  AND age = 30;
```

Можно создать два отдельных индекса:

```python
CREATE INDEX idx_users_city
ON users (city);

CREATE INDEX idx_users_age
ON users (age);
```

Или один композитный:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

Это **не одно и то же**.

PostgreSQL иногда может использовать несколько отдельных индексов одновременно через:

```text
BitmapAnd
```

Но композитный индекс может быть более подходящим для определённого шаблона запросов, особенно когда важен порядок колонок и сортировка.

---

## 🆚 Композитный индекс vs два отдельных

| Вариант            | Особенность                                                                       |
| ------------------ | --------------------------------------------------------------------------------- |
| `(city, age)`      | Один индекс, учитывающий порядок колонок                                          |
| `(city)` + `(age)` | Два независимых индекса                                                           |
| BitmapAnd          | PostgreSQL может объединить отдельные индексы                                     |
| `(city, age)`      | Может эффективно поддерживать фильтрацию и сортировку по соответствующему порядку |

Нельзя сказать, что композитный индекс **всегда** лучше двух отдельных.

Нужно смотреть на реальные запросы и `EXPLAIN`.

---

## 🎯 Как выбирать порядок колонок

Это один из самых важных вопросов на собеседовании.

Не существует универсального правила:

> «Первой всегда ставим колонку с высокой кардинальностью».

Это слишком упрощённо.

При проектировании учитывают:

### 1. Типичные условия запросов

Если большинство запросов:

```python
WHERE user_id = ?
  AND status = ?
```

может быть полезен:

```python
(user_id, status)
```

### 2. Ведущая колонка

Если есть запросы:

```python
WHERE user_id = ?
```

то `user_id` обычно имеет смысл сделать первой колонкой:

```python
(user_id, status)
```

### 3. Сортировку

Например:

```python
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 20
```

логично рассмотреть:

```python
(user_id, created_at DESC)
```

### 4. Диапазоны

Диапазонное условие может влиять на то, насколько эффективно будут использоваться следующие колонки индекса.

Например:

```python
WHERE user_id = 100
  AND created_at >= '2026-01-01'
```

индекс:

```python
(user_id, created_at)
```

естественно соответствует такому запросу.

---

## ⚠️ Селективность колонок

Селективность важна, но нельзя сводить выбор порядка только к ней.

Например:

```text
status
→ active / inactive
```

имеет небольшое количество различных значений.

А:

```text
user_id
→ миллионы различных значений
```

имеет высокую кардинальность.

Но если приложение почти всегда выполняет:

```python
WHERE status = ?
  AND user_id = ?
```

нужно смотреть на **реальный workload**, а не механически ставить первой колонку с большей кардинальностью.

---

## 📌 Композитный индекс и уникальность

Композитный индекс может быть уникальным:

```python
CREATE UNIQUE INDEX idx_user_email
ON users (user_id, email);
```

Это означает, что комбинация:

```text
(user_id, email)
```

должна быть уникальной.

Например:

```text
(1, 'a@example.com')  → допустимо
(1, 'b@example.com')  → допустимо
(2, 'a@example.com')  → допустимо
(1, 'a@example.com')  → ❌ дубликат
```

Уникальность распространяется на **комбинацию колонок**, а не на каждую колонку отдельно.

---

## 🔗 Композитный индекс и JOIN

Композитный индекс может быть полезен и для JOIN, если запрос использует соответствующие колонки.

Например:

```python
SELECT *
FROM orders o
JOIN users u
    ON o.user_id = u.id
WHERE o.status = 'paid';
```

Можно рассмотреть индекс:

```python
CREATE INDEX idx_orders_user_status
ON orders (user_id, status);
```

Но конкретный порядок и полезность зависят от плана запроса.

Поэтому окончательную проверку выполняют через:

```python
EXPLAIN ANALYZE
```

---

## 🔬 Как проверить эффективность

Например:

```python
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM users
WHERE city = 'Moscow'
  AND age = 30;
```

Можно посмотреть, использует ли PostgreSQL индекс:

```text
Index Scan
Index Cond: ...
```

или, например:

```text
Bitmap Index Scan
```

А может выбрать:

```text
Seq Scan
```

Это не обязательно означает, что индекс плохой.

Нужно смотреть на:

* размер таблицы;
* количество подходящих строк;
* стоимость плана;
* статистику;
* реальное время выполнения.

---

## 🆚 Композитный индекс и покрывающий индекс

Эти понятия не исключают друг друга.

Можно создать **композитный покрывающий индекс**:

```python
CREATE INDEX idx_orders_user_status
ON orders (user_id, status)
INCLUDE (amount, created_at);
```

Здесь:

```text
user_id, status
```

— ключевые колонки индекса.

А:

```text
amount, created_at
```

— дополнительные `INCLUDE`-колонки.

Такой индекс одновременно:

* является композитным;
* может покрывать определённые запросы;
* потенциально позволяет использовать `Index Only Scan`.

---

## ⚠️ Минусы композитных индексов

Чем больше колонок в индексе, тем:

* больше размер индекса;
* дороже `INSERT`;
* дороже `UPDATE`;
* дороже `DELETE`;
* больше памяти и дискового пространства требуется;
* больше индексов нужно обслуживать.

Поэтому не стоит создавать индексы:

```python
(a, b, c, d, e, f, g)
```

без понимания реальных запросов.

---

## 🧠 Ментальная модель

```text
Индекс:

(city, age, name)
   ↓
   ↓
   └── name
   └──── age
   └────── city
```

Главная идея:

```text
(city)
(city, age)
(city, age, name)
```

используют ведущую часть индекса лучше, чем:

```text
(age)
(name)
```

для индекса:

```text
(city, age, name)
```

## 🎤 Частые вопросы на собеседовании

### Что такое композитный индекс?

> Это индекс по нескольким колонкам. Он позволяет эффективно обслуживать определённые запросы, использующие эти колонки. Порядок колонок имеет значение.

### Почему важен порядок колонок?

> Потому что B-tree индекс организован с учётом порядка ключей. Ведущие колонки формируют левый префикс индекса, поэтому индекс `(a, b)` и `(b, a)` эффективны для разных шаблонов запросов.

### Индекс `(a, b)` используется для `WHERE b = ...`?

> Не обязательно эффективно. В первую очередь индекс ориентирован на ведущую колонку `a`. PostgreSQL может использовать индекс и в других вариантах плана, например частично или через Bitmap Scan, но нельзя рассчитывать на тот же эффект, что при использовании ведущей колонки.

### Что лучше: `(a, b)` или два индекса `(a)` и `(b)`?

> Зависит от запросов. Композитный индекс хорошо подходит для конкретного сочетания и порядка условий, а отдельные индексы дают больше независимости и могут быть объединены PostgreSQL через BitmapAnd. Выбор нужно проверять по реальному workload и `EXPLAIN`.

### Нужно ли первым ставить колонку с максимальной кардинальностью?

> Нет, это не универсальное правило. Порядок выбирают исходя из реальных запросов, фильтрации, сортировки, диапазонов и других особенностей workload.

```text
Композитный индекс = индекс по нескольким колонкам.

Пример:
(city, age, name)

Порядок колонок важен.

Главное правило:
ведущие (левые) колонки индекса наиболее важны
для его эффективного использования.

Индекс:
(city, age)

Хорошо подходит для:
(city)
(city, age)

Но не означает такую же эффективность для:
(age)

Композитный индекс может помогать:
- WHERE
- ORDER BY
- LIMIT
- JOIN

Композитный индекс может одновременно быть:
- уникальным;
- покрывающим.

Не нужно автоматически считать,
что композитный индекс лучше нескольких отдельных.
Решение принимают на основе реальных запросов
и EXPLAIN ANALYZE.
```
