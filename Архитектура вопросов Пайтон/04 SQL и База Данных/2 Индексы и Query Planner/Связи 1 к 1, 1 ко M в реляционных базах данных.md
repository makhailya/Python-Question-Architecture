# 🔗 Связи 1:1, 1:N, M:N в реляционных базах данных

## 🎤 Короткий ответ

В реляционных базах данных выделяют три основных типа связей между таблицами:

- **[[One-to-One]] (1:1)** — одной записи первой таблицы соответствует не более одной записи второй таблицы.
- **[[One-to-Many]] (1:N)** — одной записи первой таблицы может соответствовать множество записей второй.
- **[[Many-to-Many]] (M:N)** — множеству записей одной таблицы может соответствовать множество записей другой.

Связи обычно реализуются с помощью **Foreign Key (внешних ключей)** и дополнительных ограничений.

Для связи M:N используется промежуточная таблица, которая содержит внешние ключи на обе связанные таблицы.

## 🗣️ Ответ на собеседовании

В реляционных базах данных есть три основных типа связей: один к одному, один ко многим и многие ко многим.

Связь один к одному, например, может быть между пользователем и его профилем. Обычно она реализуется через внешний ключ с ограничением `UNIQUE`, чтобы одному пользователю соответствовал максимум один профиль.

Один ко многим — самая распространённая связь. Например, один пользователь может создать много заказов. В этом случае в таблице заказов хранится `user_id`, который ссылается на `users.id`. При этом `user_id` не должен быть уникальным.

Многие ко многим — например, товары и категории. Один товар может находиться в нескольких категориях, а категория содержать много товаров. Для этого создаётся промежуточная таблица `product_categories`, в которой хранятся `product_id` и `category_id`.

В PostgreSQL целостность таких связей обеспечивается внешними ключами, а уникальность при необходимости — через `UNIQUE` или составной `PRIMARY KEY`.

В SQLAlchemy связи между объектами описываются через `relationship()`, а ограничения на уровне базы — через `ForeignKey`.

## 📚 Разбор поглубже

### 1. Что такое связь между таблицами

Представим интернет-магазин.

В системе есть:

- Пользователи.
- Профили пользователей.
- Заказы.
- Товары.
- Категории товаров.

Все эти сущности связаны между собой.

Например:

```text
Пользователь ─── Профиль       1:1

Пользователь ─── Заказы        1:N

Товары ─── Категории           M:N
```

В реляционной базе данных связи обычно создаются через внешние ключи.

Важно понимать: **тип связи определяется не названием столбца, а ограничениями и бизнес-правилами.**

Например, наличие `user_id` в таблице ещё не означает, что связь автоматически будет 1:1.

Для этого потребуются дополнительные ограничения.

---

### 2. One-to-One (1:1) — один к одному

Связь 1:1 означает, что одной записи таблицы A соответствует не более одной записи таблицы B, и наоборот.

Пример: пользователь и его дополнительный профиль.

```text
users                        profiles
┌──────────────┐             ┌────────────────┐
│ id (PK)      │◄────────────│ user_id (FK)   │
│ username     │     1:1     │ bio            │
└──────────────┘             │ avatar         │
                             └────────────────┘
```

Данные:

**users**

| id | username |
|---|---|
| 1 | ilya |
| 2 | anna |

**profiles**

| user_id | bio |
|---|---|
| 1 | Python Developer |
| 2 | Designer |

Каждый профиль принадлежит одному пользователю.

И один пользователь может иметь не более одного профиля.

SQL:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username TEXT NOT NULL UNIQUE
);

CREATE TABLE profiles (
    user_id BIGINT PRIMARY KEY
        REFERENCES users(id),
    bio TEXT,
    avatar TEXT
);
```

Здесь `profiles.user_id` одновременно:

- `PRIMARY KEY` — уникально идентифицирует профиль.
- `FOREIGN KEY` — ссылается на пользователя.

Таким образом, у пользователя не может быть двух профилей.

**Нюанс:** такая схема гарантирует максимум один профиль на пользователя, но не гарантирует, что профиль существует у каждого пользователя. Это необязательная связь со стороны `users`.

Другой вариант реализации — отдельный `profiles.id` и `user_id UNIQUE NOT NULL`.

### 3. Когда используется 1:1

Связь один к одному полезна, когда нужно логически разделить данные одной сущности.

Например:

- `users` и `user_settings`.
- `users` и `profiles`.
- `employees` и `employee_credentials`.

Зачем разделять данные?

Допустим, основная таблица `users` часто используется для авторизации, а дополнительный профиль содержит большой текст биографии и другие редко используемые поля.

Разделение может сделать модель более удобной и обеспечить отдельное управление доступом.

Но не стоит создавать связь 1:1 без необходимости: иногда все данные логичнее хранить в одной таблице.

---

### 4. One-to-Many (1:N) — один ко многим

Это одна из самых распространённых связей в Backend.

Пример: один пользователь может иметь много заказов.

```text
users                         orders
┌──────────────┐              ┌────────────────┐
│ id (PK)      │◄─────────────│ user_id (FK)   │
│ username     │     1:N      │ id (PK)        │
└──────────────┘              │ amount         │
                              └────────────────┘
```

**users**

| id | username |
|---|---|
| 1 | ilya |
| 2 | anna |

**orders**

| id | user_id | amount |
|---|---|---|
| 101 | 1 | 1500 |
| 102 | 1 | 2500 |
| 103 | 1 | 700 |
| 104 | 2 | 1200 |

Здесь:

- Пользователь `1` имеет три заказа.
- Пользователь `2` имеет один заказ.
- Каждый заказ принадлежит одному пользователю.

SQL:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    amount NUMERIC(10, 2) NOT NULL
);
```

Ключевой момент:

```sql
user_id BIGINT NOT NULL REFERENCES users(id)
```

У `user_id` нет ограничения `UNIQUE`.

Поэтому значение может повторяться:

```text
user_id = 1
user_id = 1
user_id = 1
```

Именно это позволяет одному пользователю иметь несколько заказов.

### 5. Как получить данные по связи 1:N

Например, все заказы пользователя:

```sql
SELECT *
FROM orders
WHERE user_id = 1;
```

Получить имя пользователя вместе с заказами:

```sql
SELECT
    users.username,
    orders.id,
    orders.amount
FROM users
JOIN orders
    ON users.id = orders.user_id;
```

Посчитать количество заказов каждого пользователя:

```sql
SELECT
    users.id,
    users.username,
    COUNT(orders.id) AS orders_count
FROM users
LEFT JOIN orders
    ON users.id = orders.user_id
GROUP BY users.id, users.username;
```

Почему `LEFT JOIN`?

Потому что он позволяет показать пользователей даже без заказов.

Для них `orders_count` будет равен нулю.

### 6. One-to-Many и Many-to-One — в чём разница

Это одна и та же связь, рассматриваемая с разных сторон.

```text
User → Orders     1:N

Order → User      N:1
```

Один пользователь имеет много заказов.

Но каждый заказ принадлежит одному пользователю.

В SQLAlchemy это особенно заметно:

```python
user.orders  # Список заказов

order.user   # Один пользователь
```

**Запомни:** One-to-Many и Many-to-One — два направления одной связи.

### 7. Many-to-Many (M:N) — многие ко многим

Пример: товары и категории.

Один товар может относиться к нескольким категориям.

И одна категория может содержать множество товаров.

Например:

**products**

| id | name |
|---|---|
| 1 | MacBook |
| 2 | iPhone |
| 3 | iPad |

**categories**

| id | name |
|---|---|
| 10 | Apple |
| 20 | Ноутбуки |
| 30 | Смартфоны |
| 40 | Планшеты |

MacBook относится к категориям `Apple` и `Ноутбуки`.

iPhone относится к категориям `Apple` и `Смартфоны`.

Как реализовать такую связь?

Через промежуточную таблицу.

```text
products               product_categories              categories
┌─────────────┐         ┌────────────────────┐          ┌─────────────┐
│ id (PK)     │◄────────│ product_id (FK)    │          │ id (PK)     │
│ name        │         │ category_id (FK)   │─────────►│ name        │
└─────────────┘         └────────────────────┘          └─────────────┘

              1:N                          N:1
```

Получается, что связь M:N физически реализована через две связи 1:N.

### 8. Создание связи M:N в PostgreSQL

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE categories (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE product_categories (
    product_id BIGINT NOT NULL
        REFERENCES products(id),

    category_id BIGINT NOT NULL
        REFERENCES categories(id),

    PRIMARY KEY (product_id, category_id)
);
```

Разберём промежуточную таблицу.

`product_id` ссылается на товар.

`category_id` ссылается на категорию.

А составной ключ:

```sql
PRIMARY KEY (product_id, category_id)
```

запрещает дублирование одинаковой пары.

Например, нельзя дважды добавить связь:

```text
MacBook → Apple
MacBook → Apple
```

Но можно:

```text
MacBook → Apple
MacBook → Ноутбуки
iPhone  → Apple
```

### 9. Как получить данные по связи M:N

Получить все категории конкретного товара:

```sql
SELECT
    categories.name
FROM categories
JOIN product_categories
    ON categories.id = product_categories.category_id
WHERE product_categories.product_id = 1;
```

Получить все товары категории `Apple`:

```sql
SELECT
    products.name
FROM products
JOIN product_categories
    ON products.id = product_categories.product_id
JOIN categories
    ON categories.id = product_categories.category_id
WHERE categories.name = 'Apple';
```

Здесь используются два `JOIN`, потому что между товарами и категориями находится промежуточная таблица.

### 10. Когда промежуточная таблица содержит дополнительные данные

Иногда связь M:N сама по себе является полноценной бизнес-сущностью.

Например, студенты и курсы.

Студент может записаться на несколько курсов, а курс может иметь много студентов.

Но у записи на курс могут быть дополнительные атрибуты:

- Дата регистрации.
- Статус обучения.
- Оценка.
- Дата завершения.

```sql
CREATE TABLE enrollments (
    student_id BIGINT NOT NULL
        REFERENCES students(id),

    course_id BIGINT NOT NULL
        REFERENCES courses(id),

    enrolled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    status TEXT NOT NULL DEFAULT 'active',

    PRIMARY KEY (student_id, course_id)
);
```

Теперь `enrollments` — не просто техническая таблица, а сущность «Запись на курс».

В ORM такой подход часто называют **Association Object**.

### 11. Сравнение всех типов связей

| Характеристика | 1:1 | 1:N | M:N |
|---|---|---|---|
| Пример | User–Profile | User–Orders | Product–Category |
| Foreign Key | Да | Да | Два FK в таблице связи |
| UNIQUE на FK | Обычно да | Нет | Уникальна пара |
| Промежуточная таблица | Обычно нет | Нет | Да |
| Количество связанных записей | Не более одной | Много с одной стороны | Много с обеих сторон |

Упрощённая схема:

```text
1:1
User ───────── Profile

1:N
User ────────< Order

M:N
Product >────< Category
          |
          v
   ProductCategory
```

### 12. Связи в SQLAlchemy 2.x

В SQLAlchemy используются два основных механизма:

- `ForeignKey` — ограничение на уровне базы данных.
- `relationship()` — связь между Python-объектами в ORM.

#### One-to-One

```python
from sqlalchemy import ForeignKey
from sqlalchemy.orm import Mapped, mapped_column, relationship


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    profile: Mapped["Profile | None"] = relationship(
        back_populates="user"
    )


class Profile(Base):
    __tablename__ = "profiles"

    user_id: Mapped[int] = mapped_column(
        ForeignKey("users.id"),
        primary_key=True,
    )

    user: Mapped["User"] = relationship(
        back_populates="profile"
    )
```

Обрати внимание:

```python
profile: Mapped["Profile | None"]
```

Это означает, что профиль может отсутствовать.

А `user_id` является первичным ключом таблицы профилей, поэтому дублирование невозможно на уровне БД.

#### One-to-Many

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    orders: Mapped[list["Order"]] = relationship(
        back_populates="user"
    )


class Order(Base):
    __tablename__ = "orders"

    id: Mapped[int] = mapped_column(primary_key=True)

    user_id: Mapped[int] = mapped_column(
        ForeignKey("users.id")
    )

    user: Mapped["User"] = relationship(
        back_populates="orders"
    )
```

Здесь:

```python
user.orders
```

возвращает коллекцию заказов.

А:

```python
order.user
```

возвращает одного пользователя.

#### Many-to-Many

```python
from sqlalchemy import Column, ForeignKey, Table
from sqlalchemy.orm import Mapped, mapped_column, relationship


product_categories = Table(
    "product_categories",
    Base.metadata,

    Column(
        "product_id",
        ForeignKey("products.id"),
        primary_key=True,
    ),

    Column(
        "category_id",
        ForeignKey("categories.id"),
        primary_key=True,
    ),
)


class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True)

    categories: Mapped[list["Category"]] = relationship(
        secondary=product_categories,
        back_populates="products",
    )


class Category(Base):
    __tablename__ = "categories"

    id: Mapped[int] = mapped_column(primary_key=True)

    products: Mapped[list["Product"]] = relationship(
        secondary=product_categories,
        back_populates="categories",
    )
```

Здесь ключевой параметр:

```python
secondary=product_categories
```

Он сообщает SQLAlchemy, через какую промежуточную таблицу реализована связь.

**Важно:** это три независимых примера моделей. Для запуска каждого нужен общий `Base`, созданный через `DeclarativeBase`, а также соответствующие определения таблиц.

### 13. Связи и загрузка данных в SQLAlchemy

Когда мы обращаемся к связанным объектам:

```python
user.orders
```

ORM может выполнить дополнительный SQL-запрос.

Если получить 100 пользователей и для каждого отдельно загрузить заказы, можно столкнуться с проблемой **N+1 queries**.

Например:

```text
1 запрос → получить пользователей

100 запросов → получить заказы каждого

Итого: 101 запрос
```

Для оптимизации используют стратегии загрузки, например `selectinload()`:

```python
from sqlalchemy import select
from sqlalchemy.orm import selectinload


stmt = (
    select(User)
    .options(selectinload(User.orders))
)

users = session.scalars(stmt).all()
```

Это позволяет загрузить пользователей и их заказы пакетно, вместо отдельного запроса для каждого пользователя.

Для Backend-разработчика важно не только уметь создавать связи, но и понимать, как ORM загружает связанные данные.

### 14. Как выбирать тип связи при проектировании БД

Главный вопрос:

**Сколько записей одной сущности может быть связано с одной записью другой сущности?**

Например:

**Пользователь — профиль**

Может ли пользователь иметь два профиля?

Если нет — 1:1.

**Пользователь — заказ**

Может ли пользователь иметь несколько заказов?

Да.

Может ли один заказ принадлежать нескольким пользователям?

В выбранной модели — нет.

Значит, 1:N.

**Студент — курс**

Может ли студент посещать несколько курсов?

Да.

Может ли один курс иметь нескольких студентов?

Да.

Значит, M:N.

Тип связи определяется бизнес-правилами, а не исключительно техническими предпочтениями.

### 15. Типичные ошибки

**Ошибка 1. Считать, что Foreign Key автоматически создаёт связь 1:1.**

Без `UNIQUE` один и тот же внешний ключ может повторяться.

**Ошибка 2. Создавать M:N без промежуточной таблицы.**

В нормальной реляционной модели связь многие ко многим реализуется через отдельное отношение.

**Ошибка 3. Путать 1:N и N:1.**

Это два направления одной и той же связи.

**Ошибка 4. Забывать составной Primary Key или UNIQUE в таблице M:N.**

Если одинаковая пара не должна повторяться, это нужно закрепить ограничением.

**Ошибка 5. Считать relationship() заменой Foreign Key.**

`relationship()` работает на уровне ORM. Целостность данных обеспечивает ограничение БД.

**Ошибка 6. Не учитывать необязательные связи.**

Например, пользователь может существовать без профиля. Это влияет на `NULL`, ограничения и модель ORM.

**Ошибка 7. Не учитывать N+1.**

Неправильная загрузка связанных объектов может привести к большому количеству SQL-запросов.

**Ошибка 8. Создавать связи без анализа предметной области.**

Например, если заказ может содержать много товаров, не стоит ограничивать его одним `product_id` в таблице `orders`. Обычно нужна таблица `order_items`.

## 🎤 Вопросы на собеседовании

**1. Какие типы связей существуют в реляционных БД?**

One-to-One, One-to-Many и Many-to-Many.

**2. Как реализовать связь 1:1?**

Через внешний ключ с ограничением уникальности или общий первичный ключ.

**3. Как реализовать связь 1:N?**

Разместить Foreign Key на стороне «многие».

**4. Как реализовать связь M:N?**

Создать промежуточную таблицу с двумя внешними ключами.

**5. Чем 1:N отличается от N:1?**

Это одна связь, рассматриваемая с противоположных сторон.

**6. Почему в M:N нужен составной Primary Key?**

Чтобы предотвратить дублирование одинаковых пар, если это соответствует бизнес-правилам.

**7. Может ли связь 1:1 быть необязательной?**

Да. Например, пользователь может существовать без дополнительного профиля.

**8. Может ли одна таблица иметь несколько Foreign Key?**

Да. Например, заказ может ссылаться на пользователя, адрес доставки и способ оплаты.

**9. Как SQLAlchemy описывает связи?**

Через `ForeignKey` и `relationship()`. Для M:N обычно применяется `secondary`.

**10. Что такое N+1?**

Проблема, когда после одного запроса на получение списка объектов выполняется отдельный запрос для каждого объекта при загрузке связанных данных.

**11. Когда использовать selectinload()?**

Когда нужно эффективно загрузить коллекции связанных объектов, уменьшив количество SQL-запросов.

**12. Чем отличается связь между таблицами от JOIN?**

Связь описывает структуру данных и ограничения, а JOIN соединяет строки при выполнении конкретного запроса.
