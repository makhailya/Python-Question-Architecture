# 🌳 B-tree индекс в PostgreSQL

## 🎯 Ответ на собеседовании

**B-tree — стандартный и наиболее универсальный тип индекса в PostgreSQL.** Он организован в виде сбалансированного дерева и позволяет эффективно выполнять поиск по равенству, диапазонам и сортировке.

Он хорошо подходит для:

```text
=
<
>
<=
>=
BETWEEN
ORDER BY
```

Например:

```python
CREATE INDEX idx_users_age
ON users (age);
```

После этого запрос:

```python
SELECT *
FROM users
WHERE age > 30;
```

может использовать B-tree индекс вместо полного последовательного сканирования таблицы.

---

## 🎤 Суперкоротко

```text
B-tree
│
├── индекс по умолчанию в PostgreSQL
├── сбалансированное дерево
├── быстрый поиск
├── поддерживает диапазоны
├── поддерживает сортировку
└── подходит для большинства обычных запросов
```

Главная идея:

```text
             [50]
            /    \
        [20,30]  [70,90]
        /  |  \    /  \
      ... ... ... ... ...
```

Дерево остаётся **сбалансированным**, поэтому поиск не превращается в последовательный просмотр всех элементов.

---

# 🔹 Что такое B-tree

B-tree расшифровывается как **Balanced Tree** — сбалансированное дерево.

В контексте PostgreSQL это индексная структура, которая хранит ключи в отсортированном виде и организует их в дерево.

Упрощённо:

```text
                    [50]
                   /    \
              [20, 30]  [70, 90]
              /   |  \   /   |   \
             ... ... ... ... ... ...
```

Поиск не идёт по всем значениям подряд.

Например, ищем:

```text
70
```

Вместо:

```text
1 → 2 → 3 → 4 → ... → 70
```

движемся по дереву:

```text
50
 ↓
70
 ↓
нашли
```

---

# 🔹 Почему дерево называется сбалансированным

Все листовые узлы находятся примерно на одной глубине.

Это позволяет сохранять предсказуемую сложность поиска:

```text
O(log N)
```

где:

```text
N
→ количество индексируемых элементов
```

Поэтому при большом количестве строк поиск через индекс может быть значительно эффективнее полного сканирования таблицы.

---

# 🔹 Как выглядит B-tree индекс

Упрощённая модель:

```text
                    ROOT
                      │
              ┌───────┴───────┐
              ↓               ↓
           BRANCH           BRANCH
          /      \          /      \
         ↓        ↓        ↓        ↓
       LEAF     LEAF      LEAF     LEAF
```

На нижнем уровне находятся значения индекса, связанные с соответствующими строками таблицы.

Например:

```text
users

id | age
---+----
1  | 35
2  | 20
3  | 50
4  | 25
```

B-tree позволяет организовать значения:

```text
20
25
35
50
```

в индексную структуру.

---

# 🔹 Создание B-tree индекса

Явно:

```python
CREATE INDEX idx_users_age
ON users USING BTREE (age);
```

Но `USING BTREE` можно не писать:

```python
CREATE INDEX idx_users_age
ON users (age);
```

Потому что **B-tree является типом индекса по умолчанию**.

---

# 🔹 Поиск по `=`

Один из основных сценариев:

```python
SELECT *
FROM users
WHERE age = 30;
```

B-tree умеет быстро находить значение:

```text
age = 30
```

То же относится к:

```python
SELECT *
FROM users
WHERE email = 'user@example.com';
```

Поэтому B-tree часто используется для:

* `id`;
* `email`;
* `username`;
* внешних ключей;
* дат;
* числовых полей.

---

# 🔹 Поиск по диапазону

Одно из главных преимуществ B-tree.

Например:

```python
SELECT *
FROM users
WHERE age > 30;
```

или:

```python
SELECT *
FROM users
WHERE age BETWEEN 20 AND 30;
```

или:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01';
```

Почему это удобно?

Потому что значения в B-tree **упорядочены**.

Условно:

```text
10  20  30  40  50  60  70  80
        ↑───────────────↑
             диапазон
```

---

# 🔹 B-tree и ORDER BY

B-tree также может помогать при сортировке.

Например:

```python
CREATE INDEX idx_users_age
ON users (age);
```

Запрос:

```python
SELECT *
FROM users
ORDER BY age;
```

Поскольку значения индекса уже упорядочены, PostgreSQL в некоторых случаях может использовать индекс для получения строк в нужном порядке.

Также существует обратное направление:

```python
SELECT *
FROM users
ORDER BY age DESC;
```

---

# 🔹 Почему B-tree подходит для диапазонов

Представим индекс:

```text
10
20
30
40
50
60
70
80
90
```

Запрос:

```python
WHERE age BETWEEN 30 AND 70
```

можно представить как:

```text
10  20 [30 40 50 60 70] 80  90
         ↑─────────↑
          нужный диапазон
```

B-tree хорошо подходит для таких операций именно благодаря упорядоченности ключей.

---

# 🔹 B-tree и уникальность

B-tree может использоваться для поддержки `UNIQUE`.

Например:

```python
CREATE UNIQUE INDEX idx_users_email
ON users (email);
```

Теперь два пользователя не смогут иметь одинаковый `email`.

Но важно разделять понятия:

```text
B-tree
→ структура индекса

UNIQUE
→ ограничение уникальности
```

PostgreSQL может использовать уникальный B-tree индекс для обеспечения ограничения `UNIQUE`.

---

# 🔹 Составной B-tree индекс

Можно создать индекс по нескольким колонкам:

```python
CREATE INDEX idx_users_name_age
ON users (name, age);
```

Здесь порядок важен:

```text
(name, age)
```

не равно:

```text
(age, name)
```

---

## Правило левой части

Упрощённо составной индекс:

```text
(name, age)
```

особенно хорошо подходит для запросов, использующих `name`:

```python
WHERE name = 'Илья';
```

и:

```python
WHERE name = 'Илья'
AND age = 31;
```

Но индекс не следует воспринимать как два независимых индекса.

```text
(name, age)
```

не означает:

```text
INDEX(name)
+
INDEX(age)
```

---

# 🔹 Почему порядок колонок важен

Допустим:

```python
CREATE INDEX idx_users_city_age
ON users (city, age);
```

Условно индекс организован вокруг:

```text
city
  ↓
age
```

Поэтому запрос:

```python
WHERE city = 'Москва'
AND age = 30;
```

хорошо соответствует структуре индекса.

А запрос только:

```python
WHERE age = 30;
```

не использует индекс так же эффективно во всех случаях, потому что первая колонка индекса — `city`.

При проектировании составного индекса нужно смотреть **на реальные запросы**, а не просто перечислять часто используемые колонки.

---

# 🔹 B-tree и NULL

B-tree умеет индексировать `NULL`.

Например:

```python
CREATE INDEX idx_users_email
ON users (email);
```

Индекс может содержать записи, где:

```text
email IS NULL
```

Поэтому индекс потенциально может использоваться и для:

```python
SELECT *
FROM users
WHERE email IS NULL;
```

Конкретный план всё равно выбирает PostgreSQL.

---

# 🔹 B-tree не означает, что индекс всегда будет использован

Очень важный момент на собеседовании.

Есть индекс:

```python
CREATE INDEX idx_users_age
ON users (age);
```

Но PostgreSQL **не обязан** использовать его для каждого запроса по `age`.

Например, таблица содержит всего:

```text
100 строк
```

и запрос возвращает:

```text
95 строк
```

В таком случае PostgreSQL может решить, что быстрее:

```text
Seq Scan
```

чем:

```text
Index Scan
```

Потому что использование индекса тоже имеет стоимость.

---

# 🔹 Seq Scan vs Index Scan

### Seq Scan

```text
Таблица
 ↓
прочитать строки последовательно
 ↓
проверить условие
```

Условно:

```text
1 → 2 → 3 → 4 → 5 → ... → N
```

### Index Scan

```text
Запрос
 ↓
B-tree
 ↓
найти нужные значения
 ↓
получить соответствующие строки
```

Условно:

```text
             B-tree
               ↓
             поиск
               ↓
          нужные строки
```

---

# 🔹 EXPLAIN

Проверить план выполнения можно:

```python
EXPLAIN
SELECT *
FROM users
WHERE age = 30;
```

А увидеть фактическое выполнение:

```python
EXPLAIN ANALYZE
SELECT *
FROM users
WHERE age = 30;
```

Например, PostgreSQL может выбрать:

```text
Index Scan
```

или:

```text
Seq Scan
```

В зависимости от статистики, размера таблицы, селективности условия и стоимости операций.

---

# 🔹 Селективность

**Селективность** показывает, насколько условие сокращает количество подходящих строк.

Например:

```text
Таблица: 1 000 000 строк
```

Запрос:

```python
WHERE id = 12345
```

вероятно вернёт:

```text
1 строку
```

Высокая селективность → индекс особенно полезен.

А:

```python
WHERE is_active = true
```

может вернуть:

```text
900 000 строк
```

В таком случае использование индекса может оказаться невыгодным.

Упрощённо:

```text
Мало подходящих строк
→ индекс часто выгоден

Много подходящих строк
→ Seq Scan может быть выгоднее
```

---

# 🔹 B-tree и LIKE

Здесь есть важный нюанс.

Запрос:

```python
WHERE username LIKE 'ilya%'
```

может использовать B-tree при подходящей конфигурации и операторном классе.

Но:

```python
WHERE username LIKE '%ilya%'
```

обычный B-tree обычно не может эффективно использовать для поиска произвольной подстроки.

Причина:

```text
'ilya%'
→ известен префикс

'%ilya%'
→ начало неизвестно
```

Для поиска подстрок часто используют другие решения, например `pg_trgm` + GIN/GiST.

---

# 🔹 B-tree и текстовые поля

B-tree отлично подходит для:

```python
WHERE email = 'user@example.com';
```

или:

```python
WHERE username = 'ilya';
```

Но индекс выбирается исходя из типа операции.

Например:

```text
точное равенство
→ B-tree

диапазон
→ B-tree

префиксный поиск
→ B-tree может подходить

поиск произвольной подстроки
→ обычно нужен другой подход
```

---

# 🔹 B-tree и даты

Очень распространённый backend-сценарий:

```python
CREATE INDEX idx_orders_created_at
ON orders (created_at);
```

Теперь запросы:

```python
SELECT *
FROM orders
WHERE created_at >= '2026-01-01';
```

или:

```python
SELECT *
FROM orders
WHERE created_at BETWEEN '2026-01-01'
                      AND '2026-02-01';
```

естественно соответствуют возможностям B-tree.

Поэтому индексы по `created_at` часто встречаются в таблицах:

* заказов;
* логов;
* событий;
* платежей;
* сообщений.

---

# 🔹 B-tree и внешний ключ

Например:

```text
orders.user_id
        ↓
users.id
```

Для `users.id` индекс обычно существует благодаря `PRIMARY KEY`.

Но для `orders.user_id` PostgreSQL **автоматически не обязан создавать индекс только потому, что это FOREIGN KEY**.

Поэтому часто создают:

```python
CREATE INDEX idx_orders_user_id
ON orders (user_id);
```

Особенно если часто выполняются:

```python
SELECT *
FROM orders
WHERE user_id = 123;
```

или JOIN:

```python
SELECT *
FROM users u
JOIN orders o
    ON o.user_id = u.id;
```

---

# 🔹 B-tree и JOIN

Индекс может помогать при соединении таблиц.

Например:

```python
SELECT *
FROM users u
JOIN orders o
    ON o.user_id = u.id;
```

Если на `orders.user_id` есть подходящий индекс:

```python
CREATE INDEX idx_orders_user_id
ON orders (user_id);
```

PostgreSQL может использовать его в выбранном плане JOIN.

Но опять же:

```text
индекс есть
≠
индекс обязательно используется
```

Решение принимает planner.

---

# 🔹 Индекс хранится отдельно от таблицы

Важно понимать архитектурно:

```text
                PostgreSQL
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       Таблица              Индекс
          │                   │
      реальные             B-tree
       строки             структура
```

Индекс не является просто «отсортированной таблицей».

Это отдельная структура, которую PostgreSQL поддерживает вместе с таблицей.

Поэтому изменение данных может требовать изменения индекса.

---

# 🔹 Цена B-tree индекса

Индекс ускоряет чтение, но имеет стоимость.

```text
CREATE INDEX
      ↓
занимает место на диске
      +
INSERT становится дороже
      +
UPDATE может стать дороже
      +
DELETE может стать дороже
```

Почему?

Потому что при изменении индексируемого значения PostgreSQL должен поддерживать соответствующую индексную структуру.

Поэтому создавать индексы на каждый столбец — плохая практика.

---

# 🔹 B-tree и UPDATE

Например:

```python
UPDATE users
SET age = 31
WHERE id = 10;
```

Если `age` индексирован:

```python
CREATE INDEX idx_users_age
ON users (age);
```

изменение `age` может потребовать обновления индексной структуры.

Поэтому большое количество индексов увеличивает стоимость записи.

---

# 🔹 B-tree и PRIMARY KEY

Когда создаётся:

```python
CREATE TABLE users (
    id BIGINT PRIMARY KEY
);
```

PostgreSQL создаёт уникальный индекс для поддержки `PRIMARY KEY`.

Обычно это B-tree.

Поэтому:

```text
PRIMARY KEY
      ↓
уникальность
      +
индексная структура
```

---

# 🔹 B-tree и UNIQUE

Аналогично:

```python
CREATE TABLE users (
    email TEXT UNIQUE
);
```

PostgreSQL создаёт уникальный индекс для поддержки ограничения.

Это позволяет эффективно проверять:

```text
email уже существует?
```

---

# 🔹 Когда B-tree — хороший выбор

Используй B-tree, когда запросы выглядят примерно так:

```python
WHERE id = 123
```

```python
WHERE email = 'a@test.ru'
```

```python
WHERE price > 1000
```

```python
WHERE created_at BETWEEN ...
```

```python
ORDER BY created_at
```

```python
WHERE age >= 18
```

То есть:

```text
равенство
+
сравнение
+
диапазоны
+
сортировка
```

---

# 🔹 Когда B-tree — не лучший выбор

Не стоит автоматически использовать B-tree для задач вроде:

```text
JSONB
ARRAY
полнотекстовый поиск
пространственные данные
поиск произвольной подстроки
```

Для них могут быть лучше:

```text
JSONB / ARRAY
→ GIN

диапазоны / геометрия
→ GiST

специализированные структуры
→ SP-GiST

огромные таблицы + корреляция
→ BRIN

подстроки
→ pg_trgm + GIN/GiST
```

---

# 📊 B-tree vs другие индексы

| Тип         | Основная задача                        |
| ----------- | -------------------------------------- |
| **B-tree**  | `=`, диапазоны, сортировка             |
| **Hash**    | `=`                                    |
| **GIN**     | JSONB, ARRAY, полнотекстовый поиск     |
| **GiST**    | диапазоны, геометрия, специальные типы |
| **SP-GiST** | специализированное разбиение           |
| **BRIN**    | огромные таблицы + корреляция          |

Главное:

```text
B-tree
→ универсальный

Остальные
→ более специализированные
```

# 🎤 Типовые вопросы на собеседовании

### Что такое B-tree?

> B-tree — сбалансированная индексная структура, используемая PostgreSQL по умолчанию. Она хранит ключи в упорядоченном виде и эффективна для поиска по равенству, диапазонам и сортировки.

### Почему B-tree подходит для `>` и `<`?

> Потому что значения в B-tree упорядочены, поэтому можно эффективно находить нужный диапазон значений.

### Какова сложность поиска?

> В типичном случае поиск в B-tree имеет логарифмическую сложность — `O(log N)` по высоте дерева.

### Почему PostgreSQL иногда не использует B-tree?

> Planner оценивает стоимость выполнения запроса. Если нужно вернуть большую часть таблицы или таблица маленькая, `Seq Scan` может оказаться дешевле `Index Scan`.

### B-tree используется только для `=`?

> Нет. Это одна из его ключевых особенностей. Он также хорошо подходит для диапазонов и операций сортировки.

### Что будет, если создать слишком много B-tree индексов?

> Увеличится использование диска и стоимость операций записи, потому что индексы нужно поддерживать при `INSERT`, `UPDATE` и `DELETE`.

### В чём проблема с `LIKE '%text%'`?

> Обычный B-tree не предназначен для эффективного поиска произвольной подстроки с ведущ
