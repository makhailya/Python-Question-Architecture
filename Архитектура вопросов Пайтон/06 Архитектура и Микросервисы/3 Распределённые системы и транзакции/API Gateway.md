### API Gateway

## Формула для собеседования

**API Gateway = единая точка входа в микросервисную систему, которая маршрутизирует запросы и централизует общие инфраструктурные задачи.**

## Короткий ответ

API Gateway — компонент, через который клиенты обращаются к микросервисам. Он выполняет маршрутизацию запросов, может проверять токены, ограничивать частоту обращений, логировать запросы, завершать TLS-соединения и агрегировать ответы нескольких сервисов.

Gateway скрывает внутреннюю структуру системы от клиентов, но добавляет дополнительный сетевой переход и сам может стать узким местом.

## Ответ на собеседовании

API Gateway — это единая точка входа для клиентов в микросервисную архитектуру. Вместо того чтобы обращаться к каждому сервису отдельно, клиент отправляет запросы в gateway, который направляет их нужным сервисам.

Обычно API Gateway отвечает за маршрутизацию, аутентификацию, rate limiting, логирование, TLS termination и, при необходимости, агрегацию ответов. Это позволяет централизовать инфраструктурные задачи и скрыть внутреннюю структуру системы от клиента.

Главные недостатки — дополнительная задержка, риск возникновения единой точки отказа и потенциальное узкое место при высокой нагрузке. Поэтому gateway должен масштабироваться, иметь мониторинг и быть отказоустойчивым. Бизнес-логику лучше оставлять в соответствующих сервисах, чтобы gateway не превратился в монолит.

## 1. Как работает API Gateway

```text
                 Web / Mobile Client
                         |
                         v
                   API Gateway
                    /    |    \
                   v     v     v
              User     Order  Payment
             Service  Service Service
```

Клиенту не нужно знать адреса всех внутренних сервисов. Gateway принимает запрос, выбирает целевой сервис и передаёт ему запрос. Ответ возвращается клиенту через gateway.

## 2. Основные функции

| Функция | Назначение |
|---|---|
| Routing | Направляет запрос в нужный сервис |
| Authentication | Проверяет личность клиента |
| Authorization | Проверяет права доступа, если эта ответственность делегирована gateway |
| Rate Limiting | Ограничивает частоту запросов |
| Logging | Фиксирует обращения и ошибки |
| TLS Termination | Завершает HTTPS/TLS-соединение |
| Aggregation | Собирает данные из нескольких сервисов |
| Caching | Кэширует подходящие ответы |
| Transformation | Преобразует запросы и ответы |
| Observability | Передаёт метрики и трассировки |

Не каждый gateway реализует все эти функции. Конкретный набор зависит от архитектуры и используемого продукта.

## 3. API Gateway и бизнес-логика

Gateway подходит для общих инфраструктурных и интеграционных задач:

- маршрутизации;
- проверки токена;
- ограничения нагрузки;
- преобразования протоколов;
- объединения нескольких ответов для клиента.

Но бизнес-правила, например расчёт стоимости заказа или проверка возможности отмены платежа, должны находиться в соответствующих сервисах.

Если gateway начинает содержать множество бизнес-правил и тесно связывается с конкретными сервисами, его изменение становится сложным, а сама точка входа превращается в монолитный компонент.

## 4. Преимущества и недостатки

**Преимущества:**
- единая точка входа;
- централизованные инфраструктурные политики;
- сокрытие внутренней структуры сервисов;
- возможность агрегировать ответы;
- удобная интеграция разных типов клиентов.

**Недостатки:**
- дополнительный сетевой переход;
- потенциальное узкое место;
- риск единой точки отказа без резервирования;
- дополнительная сложность конфигурации и эксплуатации;
- опасность переноса бизнес-логики в gateway.

## 5. API Gateway и Reverse Proxy

API Gateway часто реализуется поверх reverse proxy, но понятия не идентичны.

- **Reverse Proxy** — принимает запросы и передаёт их внутренним серверам.
- **API Gateway** — выполняет роль входного API-слоя и дополнительно может предоставлять аутентификацию, rate limiting, трансформации, агрегацию и другие API-ориентированные функции.

Например, Nginx может работать как reverse proxy и выполнять часть задач gateway. Для полноценного API Gateway могут потребоваться дополнительные модули или отдельная платформа.

## 6. Примеры решений

- **Nginx** — reverse proxy, балансировка нагрузки и маршрутизация; может использоваться как часть API Gateway.
- **KrakenD** — API Gateway с возможностями агрегации и трансформации ответов.
- **Ocelot** — API Gateway для приложений на платформе .NET.
- **Kong** — API Gateway с системой плагинов и политиками управления API.

## 7. Частые вопросы на собеседовании

**Зачем нужен API Gateway?**

Чтобы предоставить клиентам единую точку входа, централизовать общие инфраструктурные задачи и скрыть внутренние адреса сервисов.

**Может ли API Gateway стать узким местом?**

Да. Поэтому необходимы мониторинг, масштабирование, отказоустойчивое развёртывание и разумные ограничения нагрузки.

**Должна ли бизнес-логика находиться в gateway?**

Как правило, нет. Основные бизнес-правила должны принадлежать соответствующим сервисам. Gateway отвечает преимущественно за инфраструктурные и интеграционные задачи.

**Чем API Gateway отличается от Load Balancer?**

Load Balancer распределяет запросы между доступными экземплярами сервиса. API Gateway дополнительно управляет API-запросами и может выполнять аутентификацию, rate limiting, агрегацию и трансформацию данных.

**API Gateway — это обязательный компонент микросервисов?**

Нет. Он полезен, когда нужна единая точка входа и централизованные политики. Для небольшой системы достаточно reverse proxy или прямых вызовов, если это соответствует требованиям.

## 8. Шпаргалка

- API Gateway — единая точка входа.
- Routing — направление запросов к сервисам.
- Rate limiting — ограничение частоты запросов.
- TLS termination — завершение TLS-соединения.
- Aggregation — объединение ответов нескольких сервисов.
- Главные риски — задержка, узкое место и единая точка отказа.
- Бизнес-логику следует оставлять в профильных сервисах.
