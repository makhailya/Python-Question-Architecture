# 💾 Transaction — транзакция

## 🎯 Ответ на собеседовании

**Транзакция** — это группа операций с базой данных, которая рассматривается как единое целое.

Либо все изменения успешно фиксируются через `COMMIT`[[COMMIT]], либо при ошибке изменения отменяются через `ROLLBACK`. 

Например, перевод денег:

```text id="4f8y1m"
Счёт A
  ↓
-1000 ₽
  ↓
Счёт B
  ↓
+1000 ₽
```

Обе операции должны выполниться вместе.

Если списание прошло, а начисление нет — данные становятся некорректными.

Поэтому:

```text id="v8gq2p"
BEGIN
  ↓
-1000 ₽ с A
  ↓
+1000 ₽ на B
  ↓
COMMIT
```

При ошибке:

```text id="w7n4kq"
ROLLBACK
```

---

## 🎤 Суперкоротко

> **Transaction — атомарная группа операций с БД: либо фиксируются все изменения, либо ни одно.**

```text id="7v4k3p"
BEGIN
  ↓
Operation 1
  ↓
Operation 2
  ↓
Operation 3
  ↓
COMMIT

или

ROLLBACK
```

---

# 🔹 Зачем нужны транзакции

Без транзакции:

```text id="c9n2vz"
1. Списать деньги      ✅
2. Начислить деньги    ❌
```

Получаем:

```text id="r5m1cx"
Деньги списались,
но не зачислились.
```

С транзакцией:

```text id="p7k3dw"
BEGIN
  ↓
Списание
  ↓
Начисление ❌
  ↓
ROLLBACK
```

Результат:

```text id="6z1q8s"
Оба изменения отменены.
```

---

# 🧩 Жизненный цикл транзакции

```text id="q8f3lm"
BEGIN
  ↓
SQL operations
  ↓
проверки
  ↓
COMMIT
```

Если произошла ошибка:

```text id="s4k2px"
BEGIN
  ↓
SQL operations
  ↓
ERROR
  ↓
ROLLBACK
```

### Основные команды

```python id="d5v7ka"
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

При ошибке:

```python id="m8r2yc"
ROLLBACK;
```

---

# 🧱 ACID

Транзакции обычно рассматриваются через свойства **ACID**.

| Свойство            | Значение        |
| ------------------- | --------------- |
| **A — Atomicity**   | Атомарность     |
| **C — Consistency** | Согласованность |
| **I — Isolation**   | Изоляция        |
| **D — Durability**  | Долговечность   |

---

## 1. ⚛️ Atomicity — атомарность

**Всё или ничего.**

```text id="e6p2ra"
Operation A ✅
Operation B ✅
Operation C ❌
      ↓
ROLLBACK
      ↓
A ❌
B ❌
C ❌
```

---

## 2. ✅ Consistency — согласованность

После завершения транзакции база должна оставаться в состоянии, удовлетворяющем её ограничениям и правилам целостности.

Например:

```text id="v9c1px"
balance >= 0
```

или:

```text id="n4w7tz"
email UNIQUE
```

Транзакция не должна оставлять БД в состоянии, нарушающем её инварианты.

---

## 3. 🔒 Isolation — изоляция

Параллельные транзакции не должны неконтролируемо влиять друг на друга.

Например:

```text id="k2m8qs"
Transaction A
      │
      │
      ├──── Database
      │
      │
Transaction B
```

Уровень изоляции определяет, какие изменения одной транзакции доступны другой.

---

## 4. 💾 Durability — долговечность

После успешного:

```text id="h3p6nv"
COMMIT
```

изменения должны сохраняться даже при последующем сбое системы.

Упрощённо:

```text id="r8x4wb"
COMMIT
  ↓
данные зафиксированы
  ↓
crash
  ↓
данные не должны потеряться
```

---

# 🔒 Transaction и Race Condition

Транзакции помогают контролировать конкурентные операции, но:

> **Транзакция сама по себе не устраняет все Race Condition.**

Например:

```text id="m7c3za"
A → SELECT balance
B → SELECT balance
A → UPDATE
B → UPDATE
```

В зависимости от изоляции и логики можно получить некорректное поведение.

Для защиты могут потребоваться:

* `UNIQUE`;
* `SELECT ... FOR UPDATE`;
* подходящий isolation level;
* optimistic locking;
* атомарные SQL-операции.

---

# 🔐 Transaction + SELECT FOR UPDATE

Например, перевод денег.

```python id="n6t8qw"
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

COMMIT;
```

`FOR UPDATE` блокирует выбранную строку до завершения транзакции.

Другая транзакция, пытающаяся получить конфликтующую блокировку, будет ждать.

---

# 📊 Isolation Levels

Уровень изоляции определяет поведение конкурентных транзакций.

В PostgreSQL:

```text id="a4v9cp"
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

Также стандарт SQL определяет `READ UNCOMMITTED`, но в PostgreSQL он фактически работает как `READ COMMITTED`.

---

## 🔹 READ COMMITTED

Каждая команда видит данные, зафиксированные до начала этой команды.

Это стандартный уровень в PostgreSQL.

---

## 🔹 REPEATABLE READ

В рамках транзакции используется согласованный снимок данных.

Повторное чтение одной и той же строки не должно неожиданно показать изменения, зафиксированные другими транзакциями после начала транзакции.

---

## 🔹 SERIALIZABLE

Самый строгий уровень.

База старается обеспечить результат, эквивалентный последовательному выполнению транзакций.

При конфликте транзакция может завершиться ошибкой сериализации:

```text id="p2k6md"
Serialization Failure
       ↓
Retry Transaction
```

---

# 🔄 Transaction + Retry

Здесь появляется важная связь:

```text id="v3k8za"
Transaction
     ↓
Serialization Failure
     ↓
Rollback
     ↓
Retry
     ↓
Transaction снова
```

То есть **Retry может применяться не только к HTTP-запросам, но и к транзакциям**.

---

# 🔑 Transaction + Idempotency

Например, API принимает:

```text id="c6x1mv"
Idempotency-Key: abc-123
```

Можно выполнить:

```text id="f7n2kr"
BEGIN
  ↓
создать idempotency record
  ↓
создать Payment
  ↓
COMMIT
```

Если что-то пошло не так:

```text id="w4m8sp"
ROLLBACK
```

Откатываются изменения этой транзакции.

Это помогает избежать ситуации:

```text id="z1p5qb"
Idempotency Key существует
       +
Payment не существует
```

---

# 🧹 Transaction + Deduplication

При обработке события:

```text id="x9r3kd"
event_id = 123
```

можно выполнить:

```text id="j6v2mq"
BEGIN
  ↓
зарегистрировать event_id
  ↓
изменить данные
  ↓
COMMIT
```

Если транзакция успешно завершилась:

```text id="e5c8nz"
event_id = 123
Order updated
```

При повторном событии:

```text id="u7d4px"
event_id = 123
      ↓
UNIQUE conflict
      ↓
duplicate
      ↓
skip
```

---

# 🧩 Transaction в Python

Например, Django:

```python id="k4x8sd"
from django.db import transaction

with transaction.atomic():
    account.balance -= 1000
    account.save()

    target.balance += 1000
    target.save()
```

Если внутри блока возникает исключение, транзакция откатывается.

---

# 🐘 Transaction в PostgreSQL

Через `psycopg` концептуально:

```python id="p7m3qa"
with connection.transaction():
    cursor.execute(
        "UPDATE accounts SET balance = balance - %s WHERE id = %s",
        (1000, 1),
    )

    cursor.execute(
        "UPDATE accounts SET balance = balance + %s WHERE id = %s",
        (1000, 2),
    )
```

Обе операции относятся к одной транзакции.

---

# ⚠️ Важное правило

Не стоит держать транзакцию открытой дольше необходимого.

Плохо:

```text id="j5n8rq"
BEGIN
  ↓
HTTP request
  ↓
внешний API
  ↓
несколько секунд
  ↓
COMMIT
```

Пока транзакция открыта, могут удерживаться:

* блокировки;
* соединение с БД;
* ресурсы БД.

Лучше:

```text id="z8c4mp"
получить необходимые данные
      ↓
короткая транзакция
      ↓
COMMIT
      ↓
внешний вызов
```

Конкретная архитектура зависит от задачи.

---

# 🌐 Distributed Transaction

Обычная транзакция:

```text id="v5r2nd"
Service
  ↓
PostgreSQL
  ↓
Transaction
```

А распределённая:

```text id="q7m3xb"
Service A
  ↓
DB A

Service B
  ↓
DB B
```

Нельзя обычным `COMMIT` PostgreSQL атомарно зафиксировать изменения сразу в двух независимых БД.

Для таких случаев используются специальные подходы:

```text id="d6p9kw"
2PC
Saga
Outbox
```

---

# 🔄 Local Transaction vs Distributed Transaction

### Local Transaction

Одна БД:

```text id="m3x7pc"
Service
  ↓
PostgreSQL
  ↓
BEGIN
  ↓
COMMIT / ROLLBACK
```

### Distributed Transaction

Несколько независимых ресурсов:

```text id="q1v8nz"
Service A → DB A
     +
Service B → DB B
```

Здесь возникают проблемы частичного отказа.

---

# 🧠 Transaction vs Atomicity

Это не одно и то же.

**Atomicity** — свойство:

> Всё или ничего.

**Transaction** — механизм, с помощью которого СУБД обеспечивает атомарное выполнение группы операций и другие свойства ACID.

```text id="t8m4vc"
Transaction
    ↓
Atomicity
Consistency
Isolation
Durability
```

---

# 🧠 Главное

> **Транзакция объединяет несколько операций БД в единое целое. При успешном выполнении изменения фиксируются через `COMMIT`, при ошибке — откатываются через `ROLLBACK`.**

Ключевые понятия:

```text id="r6k2wx"
Transaction
   ↓
ACID
   ├── Atomicity
   ├── Consistency
   ├── Isolation
   └── Durability
```

Для Backend особенно важно понимать связи:

```text id="n4c8sq"
Transaction
     ↓
Isolation
     ↓
Race Condition
     ↓
Locks / UNIQUE
```

и:

```text id="b7x3mz"
Transaction
     ↓
Idempotency
     ↓
Deduplication
     ↓
Retry
```

### Формула для собеседования

> **Транзакция — это группа операций БД, выполняемая как единое целое. Она обеспечивает свойства ACID: атомарность, согласованность, изоляцию и долговечность. При проектировании конкурентных операций транзакции обычно используются вместе с ограничениями БД, блокировками и подходящим уровнем изоляции.**
