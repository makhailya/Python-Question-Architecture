# Strangler Pattern — конспект для Python Backend

## Формула для собеседования

**Strangler Pattern** — это стратегия постепенной миграции с монолита на новую архитектуру, при которой функциональность переносится по частям, а трафик постепенно переключается со старой системы на новые сервисы. Это позволяет отказаться от рискованного одномоментного переписывания (*Big Bang Rewrite*).

## Короткий ответ

Strangler Pattern позволяет постепенно заменять монолит новыми сервисами. Gateway или маршрутизатор направляет запросы либо в старую систему, либо в новые компоненты. Когда вся необходимая функциональность перенесена и проверена, старую систему можно отключить.

## Ответ на собеседовании

Strangler Pattern — это подход к эволюционной миграции устаревшей системы. Вместо того чтобы переписывать весь монолит целиком, мы постепенно выносим его функциональность в отдельные сервисы.

Например, если у нас есть интернет-магазин на Django, мы можем сначала вынести каталог товаров в отдельный сервис на FastAPI. Затем настраиваем маршрутизацию так, чтобы запросы к каталогу шли в новый сервис, а оформление заказов пока продолжало работать в монолите.

После проверки нового сервиса переносим следующую функциональность. В результате монолит постепенно уменьшается, а новая архитектура развивается без необходимости единовременно переписывать всю систему.

Главное преимущество — снижение риска миграции. Основные сложности — временное сосуществование двух систем, интеграция между ними, согласованность данных и поддержка промежуточной архитектуры.

## 1. Как работает Strangler Pattern

Миграция обычно проходит в несколько этапов.

1. **Анализ монолита.** Определяем границы функциональности, которую можно безопасно перенести.
2. **Выделение компонента.** Создаём новый сервис с собственным API и необходимой бизнес-логикой.
3. **Настройка маршрутизации.** Gateway, reverse proxy или другой маршрутизатор определяет, куда направить запрос.
4. **Переключение трафика.** Перенаправляем запросы к перенесённой функциональности на новый сервис.
5. **Проверка и стабилизация.** Проверяем корректность ответов, производительность, ошибки и данные.
6. **Удаление старой реализации.** После полного переноса и проверки отключаем соответствующую функциональность в монолите.

### Пример миграции интернет-магазина

<text>Исходная архитектура</text>

```text
Клиент
   |
   v
Django-монолит
   ├── Каталог
   ├── Заказы
   ├── Пользователи
   └── Оплата
```

<text>Промежуточная архитектура</text>

```text
                    +--> Django-монолит
                    |    ├── Заказы
Клиент --> Gateway -+    ├── Пользователи
                    |    └── Оплата
                    |
                    +--> Catalog Service (FastAPI)
```

На этом этапе каталог уже работает в отдельном сервисе, а остальная функциональность остаётся в монолите.

<text>Целевая архитектура</text>

```text
Клиент
   |
   v
Gateway
   ├── Catalog Service
   ├── Order Service
   ├── User Service
   └── Payment Service
```

Это лишь иллюстрация возможного результата: Strangler Pattern не требует обязательно переходить к микросервисам. Цель — безопасно заменить старую реализацию подходящей новой архитектурой.

## 2. Роль Gateway и маршрутизатора

Маршрутизатор обеспечивает постепенный переход от старой системы к новой.

Он может принимать решения на основе:

- URL или HTTP-маршрута;
- версии API;
- типа операции;
- настроек маршрутизации;
- доли трафика — например, при поэтапном переключении пользователей.

Например:

```text
GET /api/catalog/*  --> Catalog Service
GET /api/orders/*   --> Django-монолит
POST /api/orders/*  --> Django-монолит
```

В этом примере каталог обслуживается новым сервисом, а заказы пока обрабатываются монолитом.

**Важно:** Gateway не обязан содержать бизнес-логику. Его основная задача — маршрутизация запросов и применение правил доступа и трафика.

## 3. Преимущества

- **Снижение риска:** не нужно заменять всю систему за один релиз.
- **Поэтапная миграция:** команды могут переносить отдельные функциональные области независимо.
- **Быстрая обратная связь:** новый компонент можно проверять в реальных условиях до переноса следующих частей.
- **Возможность отката:** трафик можно вернуть на старую реализацию, если это предусмотрено архитектурой и совместимостью данных.
- **Контролируемые изменения:** проще ограничить область проблем при неудачной миграции.

## 4. Недостатки и риски

- **Две системы одновременно:** старый монолит и новые сервисы нужно поддерживать параллельно.
- **Сложность интеграции:** возникают дополнительные сетевые вызовы, контракты API и зависимости.
- **Согласованность данных:** необходимо определить, какая система является источником истины для каждой сущности.
- **Дублирование логики:** часть бизнес-правил может временно существовать в обеих системах.
- **Технический долг:** промежуточная архитектура может сохраняться дольше запланированного.
- **Сложность наблюдаемости:** необходимо отслеживать запросы, проходящие через несколько компонентов.

### На что обратить внимание при миграции

1. Не допускайте неконтролируемой двойной записи одних и тех же данных.
2. Определите владельца каждой сущности и правила синхронизации.
3. Используйте версионирование API и проверяйте обратную совместимость.
4. Добавьте метрики, логи, трассировку и возможность переключить маршрутизацию обратно.
5. Заранее определите критерии, по которым старая реализация будет окончательно удалена.

## 5. Strangler Pattern vs Big Bang Rewrite

| Критерий | Strangler Pattern | Big Bang Rewrite |
|---|---|---|
| Подход | Постепенная замена | Полная замена за один переход |
| Риск миграции | Обычно ниже при грамотной организации | Обычно выше |
| Срок миграции | Часто длительный | Разработка может быть длительной, переключение — одномоментным |
| Сосуществование систем | Да, на переходном этапе | Обычно минимальное или отсутствует |
| Откат | Возможен по компонентам, если предусмотрен | Может быть сложным и дорогостоящим |
| Технический долг | Может временно увеличиваться | Может сохраняться в старой системе до переключения |
| Основная сложность | Интеграция и постепенное переключение | Полнота новой реализации и риск перехода |

**Вывод:** Strangler Pattern особенно полезен для критичных систем, которые нельзя надолго останавливать ради полной замены. Однако он не устраняет риски, а позволяет распределить и контролировать их.

## 7. Частые вопросы на собеседовании

**Зачем нужен Strangler Pattern?**

Чтобы постепенно заменить монолит или устаревшую систему, не переписывая всё приложение одномоментно.

**Почему паттерн называется Strangler?**

Название связано с образом растения-обвивателя, которое постепенно разрастается вокруг дерева. Новая система шаг за шагом принимает на себя функциональность старой.

**Обязательно ли использовать API Gateway?**

Нет. Подойдёт и другой механизм маршрутизации: reverse proxy, маршрутизатор на уровне приложения или инфраструктурный слой. Важно уметь направлять запросы между старой и новой реализациями.

**Можно ли откатить миграцию?**

Да, если предусмотрена возможность вернуть трафик на старую реализацию. Но откат может оказаться сложным, если новая система уже изменила данные, схему хранения или внешние контракты.

**В чём главная сложность?**

Не столько в создании нового сервиса, сколько в безопасном сосуществовании двух реализаций: согласованности данных, совместимости API, маршрутизации и контроле переходного периода.

**Чем Strangler Pattern отличается от Big Bang Rewrite?**

Strangler переносит функциональность постепенно и позволяет проверять каждый этап. Big Bang предполагает замену всей системы в рамках одного крупного перехода.

**Всегда ли результатом должны стать микросервисы?**

Нет. Новая архитектура может быть модульным монолитом или другой системой. Паттерн описывает способ миграции, а не обязательную целевую архитектуру.

## 8. Шпаргалка

- **Цель:** постепенная замена старой системы.
- **Основная идея:** переносить функциональность по частям.
- **Механизм:** маршрутизация запросов между старой и новой реализациями.
- **Главное преимущество:** снижение риска одномоментной миграции.
- **Главный риск:** длительное сосуществование систем и сложность интеграции.
- **Ключевое требование:** контролируемое переключение трафика и данных.
- **Тип подхода:** стратегия эволюционной миграции, а не отдельный микросервис или инструмент.
