# 🔄 2PC — Two-Phase Commit

## 🎯 Ответ на собеседовании

**2PC (Two-Phase Commit)** — это протокол управления **распределённой транзакцией**, который позволяет нескольким участникам согласованно выполнить `COMMIT` или `ROLLBACK`.

В 2PC есть **координатор** и несколько **участников**.

```text
                 Coordinator
                /     |     \
               ↓      ↓      ↓
           Service A Service B Service C
              DB        DB        DB
```

Протокол проходит в две фазы:

1. **Prepare** — все участники сообщают, готовы ли они зафиксировать транзакцию.
2. **Commit** — если все готовы, координатор даёт команду `COMMIT`. Если хотя бы один не готов — выполняется `ROLLBACK`.

---

## 🎤 Суперкоротко

**2PC — это протокол распределённых транзакций: сначала все участники готовятся к commit, затем координатор либо подтверждает commit для всех, либо инициирует rollback.**

---

# 🧩 Зачем нужен 2PC

Представим микросервисную систему:

```text
Order Service
     ↓
Order DB

Payment Service
     ↓
Payment DB
```

Нужно выполнить:

```text
1. Создать заказ
2. Провести оплату
```

Если заказ создали:

```text
Order DB → ✅
```

а оплата не прошла:

```text
Payment DB → ❌
```

получается неконсистентное состояние.

2PC пытается добиться результата:

```text
Обе БД → COMMIT
       ИЛИ
Обе БД → ROLLBACK
```

---

# 1️⃣ Фаза Prepare

Первая фаза называется **Prepare**.

Координатор спрашивает каждого участника:

> «Готов ли ты зафиксировать транзакцию?»

```text
Coordinator
    │
    ├──→ Order DB
    │       ↓
    │      YES
    │
    ├──→ Payment DB
    │       ↓
    │      YES
    │
    └──→ Product DB
            ↓
           YES
```

Каждый участник:

* выполняет необходимые операции;
* проверяет, может ли зафиксировать изменения;
* подготавливается к `COMMIT`;
* сообщает координатору результат.

---

# 2️⃣ Фаза Commit

Если **все участники ответили YES**:

```text
Coordinator
    │
    ├──→ Order DB    → COMMIT
    ├──→ Payment DB  → COMMIT
    └──→ Product DB  → COMMIT
```

Транзакция считается успешно завершённой.

---

# ❌ Если один участник ответил NO

Например:

```text
Order DB      → YES
Payment DB    → YES
Product DB    → NO
```

Координатор принимает решение:

```text
ROLLBACK
```

и сообщает его участникам:

```text
Coordinator
    │
    ├──→ Order DB    → ROLLBACK
    ├──→ Payment DB  → ROLLBACK
    └──→ Product DB  → ROLLBACK
```

---

# 🔄 Полная схема

```text
                Coordinator
                     │
              ───────┴───────
              Phase 1: Prepare
              ────────────────
               /      |      \
              ↓       ↓       ↓
             DB1     DB2     DB3
              │       │       │
             YES     YES     YES
              \       |       /
               ───────┬───────
                       ↓
              Phase 2: Commit
                       ↓
               /       |       \
              ↓        ↓        ↓
           COMMIT   COMMIT   COMMIT
```

Если хотя бы один:

```text
NO
```

то вместо `COMMIT`:

```text
ROLLBACK
```

---

# 🧠 Два участника

Самый простой пример:

```text
          Coordinator
             /    \
            ↓      ↓
       Order DB  Payment DB
```

### Prepare

```text
Coordinator
   │
   ├──→ Order DB   → YES
   └──→ Payment DB → YES
```

### Commit

```text
Coordinator
   │
   ├──→ Order DB   → COMMIT
   └──→ Payment DB → COMMIT
```

---

# ⚠️ Главная проблема 2PC

2PC имеет серьёзный недостаток — **блокировку ресурсов и зависимость от координатора**.

Представим:

```text
Prepare
  ↓
DB1 → YES
DB2 → YES
  ↓
Coordinator
  ↓
❌ упал
```

Участники уже подготовились, но не получили окончательное решение.

Они могут оставаться в неопределённом состоянии и удерживать ресурсы.

```text
DB1 → waiting
DB2 → waiting
```

Поэтому 2PC может снижать производительность и доступность распределённой системы.

---

# 🚨 Проблема координатора

Координатор — критически важный компонент.

```text
          Coordinator ❌
             /    \
            ↓      ↓
          DB1      DB2
```

Если он недоступен в определённый момент протокола, участники могут не знать, какое окончательное решение принято.

Поэтому для production-систем необходимы механизмы отказоустойчивости координатора.

---

# 🐢 Почему 2PC может быть медленным

Вместо одного:

```text
COMMIT
```

нужно выполнить несколько сетевых взаимодействий:

```text
Coordinator
    ↓
Prepare
    ↓
Participants
    ↓
Responses
    ↓
Commit / Rollback
```

То есть появляются:

* сетевые задержки;
* ожидание участников;
* блокировки;
* дополнительные сообщения.

---

# 🆚 2PC vs обычная транзакция

### Обычная транзакция

Одна БД:

```text
BEGIN
 ↓
Operation 1
 ↓
Operation 2
 ↓
COMMIT
```

База данных сама управляет транзакцией.

### 2PC

Несколько ресурсов:

```text
              Coordinator
             /     |     \
            ↓      ↓      ↓
           DB1    DB2    DB3
```

Нужен дополнительный протокол координации.

---

# 🆚 2PC vs Saga

Это очень частый вопрос на собеседовании.

| 2PC                             | Saga                           |
| ------------------------------- | ------------------------------ |
| Two-Phase Commit                | Sequence of local transactions |
| Координатор                     | Orchestrator или choreography  |
| Prepare → Commit                | Local transaction → Event      |
| Rollback                        | Compensating action            |
| Сильнее стремится к атомарности | Eventual consistency           |
| Может блокировать ресурсы       | Обычно меньше блокировок       |
| Высокая стоимость координации   | Хорошо подходит микросервисам  |

Пример Saga:

```text
Create Order
     ↓
Reserve Product
     ↓
Charge Payment
```

Если оплата не удалась:

```text
Charge Payment ❌
       ↓
Release Product
       ↓
Cancel Order
```

Здесь нет общего `ROLLBACK` для всех сервисов.

---

# 🧠 Важный нюанс

2PC не означает:

> «Мы просто сделали два `COMMIT` подряд».

Неправильно:

```text
DB1 → COMMIT
DB2 → COMMIT
```

Потому что:

```text
DB1 → COMMIT ✅
DB2 → COMMIT ❌
```

и система снова окажется в неконсистентном состоянии.

2PC — именно **протокол координации**, который разделяет процесс на `Prepare` и `Commit`.

---

# 🎯 Главное

```text
             2PC
              │
       ┌──────┴──────┐
       ↓             ↓
    Prepare        Commit
       │             │
       ↓             ↓
Все готовы?       COMMIT всем
       │
   ┌───┴───┐
   ↓       ↓
 YES      NO
   ↓       ↓
Commit   Rollback
```

### Формула для собеседования

**2PC = Coordinator + Participants + Prepare + Commit/Rollback**

Если все участники готовы:

**Prepare → YES → Commit**

Если хотя бы один не готов:

**Prepare → NO → Rollback**

Главный недостаток:

**2PC обеспечивает согласованность ценой дополнительных сетевых взаимодействий, ожидания и потенциальной блокировки ресурсов.**

В микросервисах часто вместо 2PC используют **Saga + eventual consistency + compensating transactions**.
