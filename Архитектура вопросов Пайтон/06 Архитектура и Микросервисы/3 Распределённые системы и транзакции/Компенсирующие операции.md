# 🔄 Компенсирующие операции

## 🎯 Ответ на собеседовании

**Компенсирующая операция** — это бизнес-операция, которая отменяет или компенсирует результат ранее успешно выполненной локальной транзакции в распределённой системе.

Она используется в паттерне **Saga**, когда одна из последующих операций завершается ошибкой.

Важно: компенсация — это **не `ROLLBACK` базы данных**. Она выполняется отдельной транзакцией и представляет собой обратное бизнес-действие.

---

## 🎤 Суперкоротко

> Компенсирующая операция — это отдельное бизнес-действие, которое компенсирует уже выполненную операцию, если Saga не смогла завершиться полностью.

Например:

```text
Создали заказ
      ↓
Списали деньги
      ↓
Не удалось зарезервировать товар
      ↓
Вернули деньги ← компенсирующая операция
```

---

## 🔹 Зачем нужны компенсирующие операции

В микросервисах у каждого сервиса может быть своя БД.

Например:

```text
Order Service    → orders DB
Payment Service  → payments DB
Inventory Service → inventory DB
```

Нельзя сделать обычный:

```python
ROLLBACK
```

из `Order Service`, чтобы автоматически отменить изменения в `Payment Service`.

Поэтому Saga использует **компенсацию**.

---

## 🔹 Пример Saga

Пусть пользователь покупает товар.

### Шаг 1 — создать заказ

```text
Order Service
Создать заказ → SUCCESS
```

### Шаг 2 — списать деньги

```text
Payment Service
Списать 5000 ₽ → SUCCESS
```

### Шаг 3 — зарезервировать товар

```text
Inventory Service
Резервирование → ERROR
```

Saga не может просто откатить предыдущие операции через общий `ROLLBACK`.

Она запускает компенсацию:

```text
Inventory → ERROR
       ↓
Compensate Payment
       ↓
Вернуть 5000 ₽
       ↓
Compensate Order
       ↓
Отменить заказ
```

---

## 🔹 Обычная транзакция vs компенсация

| Обычная транзакция             | Компенсирующая операция                    |
| ------------------------------ | ------------------------------------------ |
| `ROLLBACK` отменяет изменения  | Выполняется новое бизнес-действие          |
| Работает внутри транзакции БД  | Обычно отдельная транзакция                |
| Атомарна относительно одной БД | Может выполняться в распределённой системе |
| Мгновенный откат               | Может выполняться позже                    |
| Технический механизм           | Бизнес-логика                              |

Главное различие:

```text
ROLLBACK
→ отменяет транзакцию БД

COMPENSATION
→ исправляет бизнес-результат отдельной операцией
```

## 🔹 Примеры компенсирующих операций

| Исходная операция     | Компенсация                |
| --------------------- | -------------------------- |
| Создать заказ         | Отменить заказ             |
| Списать деньги        | Вернуть деньги             |
| Зарезервировать товар | Освободить резерв          |
| Забронировать билет   | Отменить бронь             |
| Начислить бонусы      | Списать начисленные бонусы |
| Создать доставку      | Отменить доставку          |

## ⚠️ Компенсация не всегда является точным обратным действием

Например:

```text
Отправили товар клиенту
```

Нельзя просто сделать:

```text
ROLLBACK
```

Товар уже физически отправлен.

Компенсацией может быть:

```text
Создать возврат
→ получить товар обратно
→ вернуть деньги
```

То есть компенсация должна учитывать **бизнес-смысл операции**, а не просто технически возвращать состояние БД.

---

## 🔹 Компенсация должна быть идемпотентной

В распределённых системах сообщение может быть доставлено повторно.

Например:

```text
RefundPayment(order_id=123)
```

может прийти дважды.

Нельзя допустить:

```text
Вернуть 5000 ₽
Вернуть ещё 5000 ₽
```

Поэтому компенсация должна быть **идемпотентной**:

```python
if refund_already_processed(order_id):
    return

create_refund(order_id)
```

Повторный вызов должен приводить к тому же бизнес-результату.

## 🔹 Saga и компенсирующие операции

Упрощённо:

```text
Local Transaction 1
        ↓
Local Transaction 2
        ↓
Local Transaction 3
        ↓
      ERROR
        ↓
Compensation 2
        ↓
Compensation 1
```

То есть Saga состоит из:

```text
локальные транзакции
        +
компенсирующие операции
```

---

## 🔹 Choreography и Orchestration

### Choreography

Сервисы реагируют на события друг друга:

```text
OrderCreated
      ↓
Payment Service
      ↓
PaymentCompleted
      ↓
Inventory Service
      ↓
ReservationFailed
      ↓
Payment Service → Refund
```

Нет единого центрального координатора.

### Orchestration

Есть центральный **Saga Orchestrator**:

```text
        Saga Orchestrator
        /       |       \
       ↓        ↓        ↓
    Order    Payment  Inventory
       ↑        ↑        ↑
       └── compensation ──┘
```

Оркестратор решает, какую компенсацию запустить при ошибке.

---

## 🔥 Главное

```text
Saga
  ↓
Локальные транзакции
  ↓
Ошибка
  ↓
Компенсирующие операции
  ↓
Бизнес-система приходит в согласованное состояние
```

**Ключевая фраза для собеседования:**

> Компенсирующая операция — это отдельная бизнес-транзакция, которая компенсирует результат ранее выполненной локальной транзакции в случае ошибки последующего шага Saga. Это не `ROLLBACK`, а новое действие, поэтому компенсация должна учитывать бизнес-логику и обычно быть идемпотентной.
