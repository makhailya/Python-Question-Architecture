# 🧹 Deduplication — дедупликация

## 🎯 Ответ на собеседовании

**Deduplication** — механизм обнаружения и отбрасывания повторно полученных сообщений или операций.

Она нужна в системах, где одно сообщение может быть доставлено несколько раз.

Например:

```text
Kafka
  ↓
Consumer
  ↓
Event #123
  ↓
обработка
  ↓
сбой до подтверждения
  ↓
Event #123 повторно
```

Consumer должен определить:

> **Это новое событие или мы уже его обрабатывали?**

Для этого используется уникальный идентификатор события:

```text
event_id = 123
```

Если `event_id` уже обработан — сообщение повторно не выполняется.

---

## 🎤 Суперкоротко

> **Deduplication — обнаружение и отбрасывание дублей.**

```text
Event #123
   ↓
обработать ✅
   ↓
Event #123
   ↓
уже обработан
   ↓
пропустить ⛔
```

---

# 🔹 Зачем нужна дедупликация

В распределённых системах часто используется модель:

```text
At-Least-Once Delivery
```

Она гарантирует, что сообщение будет доставлено **как минимум один раз**, но допускает повторную доставку.

Например:

```text
Producer
   ↓
Broker
   ↓
Consumer
```

Consumer получил сообщение:

```text
Event #100
```

Обработал его:

```text
создал заказ
```

Но произошёл сбой до фиксации подтверждения.

Broker считает, что сообщение не было успешно обработано, и отправляет его снова:

```text
Event #100
```

Без дедупликации:

```text
Event #100 → создать заказ
Event #100 → создать заказ ещё раз
```

С дедупликацией:

```text
Event #100 → создать заказ
Event #100 → уже обработан → пропустить
```

---

# 🔑 Основной принцип

У каждого сообщения должен быть уникальный идентификатор:

```python id="8f7h2x"
{
    "event_id": "evt-123",
    "order_id": 500,
    "amount": 1000
}
```

Consumer хранит информацию об обработанных событиях:

```text
evt-123 → processed
evt-124 → processed
evt-125 → processed
```

При получении нового сообщения:

```text
event_id
   ↓
проверка
   ↓
┌─────────────────────┐
│ уже существует?     │
└─────────────────────┘
      ↓           ↓
     Да           Нет
      ↓            ↓
   пропустить    обработать
```

# 🗄️ Дедупликация через БД

Один из распространённых вариантов — таблица обработанных событий:

```text
processed_events

event_id
processed_at
```

При обработке:

```python id="w9f1y3"
INSERT INTO processed_events (event_id)
VALUES ('evt-123');
```

Если `event_id` уже существует, БД отклонит повторную запись благодаря:

```text
UNIQUE(event_id)
```

---

# 🔒 Почему UNIQUE важнее простой проверки

Плохой вариант:

```python id="5tq8l1"
if not event_exists(event_id):
    process_event()
```

Возможна **race condition**:

```text
Consumer A ──┐
             ├── event_exists? → нет
Consumer B ──┘
             └── event_exists? → нет
```

Оба consumer могут начать обработку.

Поэтому проверку необходимо защищать механизмами БД.

Например:

```text
UNIQUE(event_id)
```

и транзакцией.

# 🔄 Deduplication + Transaction

Для критичных операций важно, чтобы:

```text
проверка/регистрация события
        +
бизнес-изменение
```

были согласованы.

Например:

```text
BEGIN
   ↓
зарегистрировать event_id
   ↓
изменить Order
   ↓
COMMIT
```

Если транзакция завершилась успешно:

```text
event_id = evt-123
Order обновлён
```

При повторной доставке:

```text
evt-123 уже зарегистрирован
        ↓
не выполнять бизнес-операцию повторно
```

# 📨 Deduplication в Kafka

Типичный сценарий:

```text
Producer
   ↓
Kafka Topic
   ↓
Consumer
```

Сообщение:

```python id="h5g2m8"
{
    "event_id": "evt-123",
    "type": "payment_completed"
}
```

Consumer получает:

```text
evt-123
```

Обрабатывает его и фиксирует:

```text
evt-123 → processed
```

Если Kafka доставляет:

```text
evt-123
```

ещё раз:

```text
evt-123
   ↓
уже processed
   ↓
skip
```

# 🐇 Deduplication в RabbitMQ

Похожий подход применяется при повторной доставке сообщения.

```text
RabbitMQ
   ↓
Consumer
   ↓
message_id / event_id
   ↓
проверка
```

Если сообщение уже обработано:

```text
→ не выполнять бизнес-операцию повторно
→ ACK
```

Конкретная реализация зависит от приложения.

# 🐍 Deduplication в Celery

Celery-задача тоже может выполняться повторно:

```text
Task #123
   ↓
Worker
   ↓
processing
   ↓
ошибка / retry
   ↓
Task #123
```

Если задача не рассчитана на повторное выполнение, можно использовать уникальный идентификатор операции:

```text
task_id / operation_id / business_id
```

и проверять, была ли операция уже выполнена.

Например:

```text
order_id = 500
operation = "send_invoice"
```

Уникальная комбинация:

```text
(order_id, operation)
```

не позволяет выполнить одну бизнес-операцию дважды.

---

# 🔑 Deduplication Key

**Deduplication Key** — идентификатор, по которому система определяет, что две операции являются одним и тем же событием.

Например:

```text
event_id = evt-123
```

или:

```text
order_id + operation_type
```

Например:

```text
order_id = 500
operation = payment
```

→ уникальный ключ операции:

```text
500:payment
```

# 🔁 Idempotency vs Deduplication

Эти понятия близки, но не одинаковы.

### Idempotency

Свойство самой операции:

> Повторное выполнение не изменяет конечный результат повторно.

```text
PUT user/1
PUT user/1
PUT user/1

→ одно конечное состояние
```

### Deduplication

Механизм обнаружения дублей:

> Мы уже видели эту операцию, поэтому не обрабатываем её повторно.

```text
event_id = 123
event_id = 123
       ↓
второй → duplicate
```

Связь:

```text
Deduplication
      ↓
обнаружить повтор
      ↓
не выполнить повторно
      ↓
Idempotent Consumer
```

---

# ⚠️ Deduplication не всегда означает «просто удалить дубль»

При обнаружении дубликата нужно определить правильное поведение.

Например:

```text
Event #123 уже обработан
```

Можно:

```text
→ пропустить
→ вернуть сохранённый результат
→ ACK сообщение
→ вернуть предыдущий результат API
```

Всё зависит от типа системы.

# ⏳ TTL обработанных событий

Таблица обработанных событий может постоянно расти.

Поэтому иногда записи удаляют после определённого периода:

```text
event_id
   ↓
processed
   ↓
24 часа
   ↓
удалить
```

Но TTL нужно выбирать с учётом максимального времени возможной повторной доставки.

Если удалить запись слишком рано:

```text
event_id удалён
       ↓
старый duplicate
       ↓
система считает его новым
```

и операция может выполниться повторно.

# 🌐 Webhook и Deduplication

Webhook может прийти несколько раз:

```text
Payment Provider
       ↓
Webhook #123
       ↓
наш сервер
```

Если ответ не был получен:

```text
Webhook #123
Webhook #123
Webhook #123
```

Сервер использует:

```text
event_id
```

и обрабатывает событие только один раз.

```text
Webhook #123 → process ✅
Webhook #123 → duplicate ⛔
Webhook #123 → duplicate ⛔
```

```text
                ┌──────────────┐
                │    Broker    │
                └──────┬───────┘
                       │
                  message
                       ↓
                ┌──────────────┐
                │   Consumer   │
                └──────┬───────┘
                       │
                  event_id
                       ↓
                ┌──────────────┐
                │     DB       │
                │              │

                │ event_id     │
                └──────┬───────┘
                       │
                ┌──────┴───────┐
                │              │
             новый          duplicate
                │              │
                ↓              ↓
             process         skip
```

# 🔗 Связь с Retry

```text
Ошибка
  ↓
Retry
  ↓
повторная доставка
  ↓
Deduplication
  ↓
обнаружили duplicate
  ↓
не выполняем операцию повторно
```

Поэтому:

```text
Retry
  +
At-Least-Once
  +
Deduplication
  +
Idempotency
```

— очень важная комбинация для распределённых систем.

# 🧠 Главное

> **Deduplication — механизм обнаружения и обработки повторно доставленных сообщений или операций. Обычно используется уникальный `event_id` или другой ключ дедупликации, который хранится в надёжном хранилище, часто с `UNIQUE` constraint.**

### Формула для собеседования

> **В системах с At-Least-Once Delivery одно сообщение может прийти несколько раз. Consumer сохраняет идентификаторы уже обработанных сообщений и при повторной доставке определяет duplicate и не выполняет бизнес-операцию повторно. Для защиты от race condition используется уникальное ограничение в БД и транзакция.**

```text
Retry
  ↓
Duplicate
  ↓
Deduplication
  ↓
Idempotent Consumer
  ↓
безопасная повторная обработка
```
