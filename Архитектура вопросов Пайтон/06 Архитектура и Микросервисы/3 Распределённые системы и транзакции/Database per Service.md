# Database per Service — конспект для Python Backend

## Формула для собеседования

**Database per Service** — это архитектурный паттерн, при котором каждый микросервис владеет собственными данными и управляет ими через свою базу данных. Другие сервисы не обращаются напрямую к этой базе, а взаимодействуют с владельцем данных через API или события.

Главная цель — **слабая связанность и независимое развитие сервисов**.

## Короткий ответ

В архитектуре Database per Service у каждого микросервиса есть собственное хранилище данных. Например, сервис заказов использует PostgreSQL, а сервис каталога — MongoDB. Сервисы не читают и не изменяют чужие таблицы напрямую, а получают нужные данные через API или обмен событиями.

Это повышает автономность и позволяет выбирать технологию хранения под конкретные задачи. При этом усложняются межсервисные запросы, транзакции и обеспечение согласованности данных.

## Ответ на собеседовании

Database per Service — это паттерн микросервисной архитектуры, согласно которому каждый сервис является владельцем своих данных и самостоятельно определяет способ их хранения.

Например, в интернет-магазине сервис заказов может использовать PostgreSQL, каталог товаров — MongoDB, а сервис аналитики — отдельное хранилище для отчётов. Сервис заказов не выполняет SQL-запросы к базе каталога напрямую. Если ему нужны сведения о товаре, он получает их через API каталога или использует локальную проекцию данных, синхронизируемую событиями.

Основные преимущества — независимость сервисов, возможность выбирать разные СУБД, отдельное масштабирование и изменение схемы без прямого влияния на другие сервисы.

Главные сложности — распределённые транзакции, eventual consistency, дублирование данных и необходимость организовывать межсервисное взаимодействие.

Важно: **Database per Service не обязательно означает отдельный физический сервер или отдельный кластер СУБД для каждого сервиса**. Несколько сервисов могут использовать один кластер, но должны иметь изолированные базы, схемы или другие границы владения данными и не зависеть от чужих внутренних таблиц.

## 1. Как работает Database per Service

Представим интернет-магазин, состоящий из трёх сервисов.

```text id="dbps7b"
                 Клиент
                    |
               API Gateway
             /      |      \
            v       v       v
       Catalog    Order    Payment
       Service    Service   Service
          |          |        |
          v          v        v
       MongoDB   PostgreSQL PostgreSQL
```

Каждый сервис:

1. Владеет своей моделью данных.
2. Сам выполняет чтение и запись в своё хранилище.
3. Предоставляет другим сервисам необходимые операции через API или события.
4. Может изменять внутреннюю схему данных без согласования каждой детали с другими сервисами.

Например, `Order Service` может хранить идентификатор товара, цену на момент покупки и количество. Для получения актуального описания товара он обращается к `Catalog Service`, но не читает его таблицы напрямую.

### Что означает изоляция базы

Изоляция определяется прежде всего **границей владения данными**, а не обязательно физическим расположением хранилища.

Возможные варианты:

- отдельный сервер или кластер СУБД;
- отдельная база данных в одном кластере;
- отдельная схема с разграниченными правами доступа.

Для строгой изоляции сервису следует предоставить права только на собственные данные. Общий кластер может быть допустимым решением, если сервисы не зависят от чужих схем и могут независимо управлять своими данными.

## 2. Как сервисы обмениваются данными

Если у каждого сервиса своя база, обычный SQL JOIN между таблицами разных сервисов не должен быть способом интеграции. Вместо этого используют несколько подходов.

### Вариант 1. Синхронный API

Один сервис обращается к другому по HTTP или gRPC.

Например:

```text id="dbps7c"
Order Service
     |
     | GET /products/123
     v
Catalog Service
     |
     v
Catalog DB
```

**Плюсы:**
- можно получить актуальные данные в момент запроса;
- понятный контракт взаимодействия;
- проще организовать обычный сценарий чтения.

**Минусы:**
- дополнительная задержка;
- зависимость от доступности вызываемого сервиса;
- риск каскадных сбоев.

Для повышения устойчивости применяют тайм-ауты, ограниченные повторы и Circuit Breaker.

### Вариант 2. Обмен событиями

Сервис публикует событие, а другие сервисы обновляют свои локальные представления данных.

Например:

```text id="dbps7d"
Catalog Service
      |
      | ProductUpdated
      v
 Message Broker
      |
      v
 Order Service / Search Service
      |
      v
 Локальная проекция данных
```

Для доставки событий могут использоваться Kafka, RabbitMQ или другие брокеры.

**Плюсы:**
- слабая связанность;
- возможность работать независимо от временной недоступности источника;
- удобно строить локальные проекции для чтения.

**Минусы:**
- данные обновляются не мгновенно;
- возможны повторная доставка и изменение порядка событий;
- необходимо обрабатывать ошибки и обеспечивать идемпотентность.

Для надёжной публикации событий вместе с изменениями в базе часто используют **Transactional Outbox**.

## 3. Как выполнять операции между несколькими базами

В монолите можно выполнить одну транзакцию SQL, изменяющую несколько таблиц. При Database per Service обычная локальная транзакция не охватывает автоматически базы разных сервисов.

Например, оформление заказа может затрагивать:

- `Order Service` — создание заказа;
- `Payment Service` — проведение платежа;
- `Inventory Service` — резервирование товара.

Если один шаг завершится ошибкой, нельзя рассчитывать на автоматический общий `ROLLBACK` для всех сервисов.

Для таких сценариев применяют **Saga Pattern** — последовательность локальных транзакций с компенсирующими действиями при неудаче.

Пример:

```text id="dbps7e"
Создать заказ
     |
     v
Зарезервировать товар
     |
     v
Провести оплату
     |
     +---- успех ---> Подтвердить заказ
     |
     +---- ошибка --> Освободить резерв
                      Отменить заказ
```

Компенсация не всегда означает точное возвращение системы в предыдущее состояние: например, уже выполненный возврат денег может потребовать отдельной операции и учёта бизнес-правил.

Связанные темы: [[Saga]], [[Transactional Outbox]], [[Event Sourcing]].

## 4. Преимущества

- **Автономность:** сервис может развиваться и выпускаться независимо.
- **Слабая связанность:** меньше зависимостей от чужих схем и SQL-запросов.
- **Выбор технологий:** можно подбирать СУБД под характер нагрузки и модель данных.
- **Независимое масштабирование:** можно масштабировать хранилище конкретного сервиса.
- **Изоляция изменений:** изменение внутренней схемы одной базы не требует автоматически менять схемы других сервисов.
- **Изоляция доступа:** проще ограничить сервис правами на собственные данные.

## 5. Недостатки и сложности

- **Распределённые транзакции:** одна бизнес-операция может затрагивать несколько баз.
- **Согласованность данных:** копии информации в разных сервисах могут временно различаться.
- **Сложные запросы:** объединение данных требует API-композиции, локальных проекций или аналитического слоя.
- **Дополнительная инфраструктура:** нужны мониторинг, резервное копирование, миграции и обслуживание нескольких хранилищ.
- **Сетевые зависимости:** межсервисные запросы добавляют задержки и точки отказа.
- **Дублирование данных:** несколько сервисов могут хранить собственные представления одной сущности.

Database per Service снижает связанность на уровне данных, но не устраняет сложность распределённой системы — часть сложности переносится в интеграцию и управление согласованностью.

## 6. Database per Service vs общая база данных

| Критерий | Database per Service | Общая база данных |
|---|---|---|
| Владение данными | У каждого сервиса своё | Несколько сервисов используют общую базу |
| Независимость схем | Выше | Схемы и изменения могут пересекаться |
| Межсервисные JOIN | Обычно не используются | Технически возможны |
| Транзакции между сущностями | Требуют отдельного решения | Возможны в одной транзакции, если данные находятся в одной СУБД |
| Выбор СУБД | Для каждого сервиса отдельно | Обычно ограничен общей технологией |
| Эксплуатация | Больше отдельных ресурсов и процессов | Проще на старте |
| Масштабирование | Можно масштабировать отдельные хранилища | Общая база может стать узким местом |

**Практический вывод:** общая база может быть оправдана для небольшого приложения или модульного монолита. Database per Service полезен, когда независимость сервисов действительно нужна и команда готова поддерживать распределённое взаимодействие.

## 7. Типичные ошибки

- **Общая база с прямым доступом всех сервисов.** Формально сервисы разделены, но границы владения данными нарушены.
- **Отдельная база ради каждой мелкой функции.** Излишнее дробление увеличивает эксплуатационную сложность.
- **Синхронные вызовы для каждого поля.** Цепочки API-запросов могут создавать высокую задержку и каскадные отказы.
- **Попытка поддерживать мгновенную согласованность везде.** Часто это усложняет систему без достаточной бизнес-необходимости.
- **Отсутствие владельца сущности.** Неясно, какой сервис может изменять данные и какой источник считать авторитетным.
- **Двойная запись без надёжного механизма.** Запись в БД и публикация события могут расходиться при сбое.

## 8. Частые вопросы на собеседовании

**Обязательно ли каждому сервису иметь отдельный физический сервер БД?**

Нет. Можно использовать общий кластер, но владение данными должно быть изолировано. Физическое разделение — инфраструктурное решение, а не обязательное условие паттерна.

**Могут ли два сервиса использовать PostgreSQL?**

Да. Паттерн не требует разных СУБД. Например, оба сервиса могут использовать PostgreSQL, но управлять своими данными независимо.

**Можно ли использовать JOIN между базами сервисов?**

В рамках собственной базы — да. Прямой доступ к чужим таблицам и межсервисные JOIN создают связанность и противоречат основной идее паттерна. Для объединения данных используют API, события или отдельные проекции.

**Как обеспечить согласованность данных?**

Выбор зависит от бизнес-требований. Используют синхронные API, события, Transactional Outbox и Saga. Часто допустима eventual consistency — согласованность, достигаемая со временем.

**Как построить отчёт по данным нескольких сервисов?**

Можно собирать данные через API, формировать отдельную read-модель или передавать события в аналитическое хранилище. Выбор зависит от объёма данных, актуальности и сложности запросов.

**Как проводить миграции схемы?**

Каждый сервис управляет миграциями собственной базы. Изменения API и событийных контрактов следует выполнять с учётом обратной совместимости, чтобы независимые релизы не ломали потребителей.

## 9. Шпаргалка

- **Идея:** каждый сервис владеет собственными данными.
- **Главный принцип:** чужие данные — через контракт, а не через прямой доступ к чужим таблицам.
- **Изоляция:** логическая граница владения важнее физического расположения сервера.
- **Обмен:** HTTP/gRPC, события и локальные проекции.
- **Транзакции между сервисами:** часто Saga вместо общей ACID-транзакции.
- **Согласованность:** нередко eventual consistency.
- **Преимущество:** автономность и независимое развитие.
- **Цена:** сложность интеграции, согласованности и эксплуатации.
