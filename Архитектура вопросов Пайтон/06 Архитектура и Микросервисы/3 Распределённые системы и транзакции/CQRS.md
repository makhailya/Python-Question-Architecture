# CQRS — конспект для Python Backend

## Формула для собеседования

**CQRS = Command Query Responsibility Segregation = разделение операций записи и чтения.**

## Короткий ответ

CQRS — архитектурный паттерн, который разделяет операции изменения состояния системы (**Command**) и получения данных (**Query**). Для чтения и записи можно использовать разные модели данных, а при необходимости — разные базы данных.

## Ответ на собеседовании

CQRS расшифровывается как Command Query Responsibility Segregation. Его основная идея — разделить операции, которые изменяют состояние системы, и операции, которые только читают данные.

В обычном CRUD-приложении одна модель часто используется и для чтения, и для записи. В CQRS модели можно разделить: команда изменяет данные через write-модель, а запрос получает данные через read-модель, оптимизированную для конкретного сценария.

Это полезно, когда у системы сложная бизнес-логика, много операций чтения или разные требования к производительности записи и чтения. При этом CQRS усложняет архитектуру, поэтому для обычного CRUD-сервиса он часто избыточен.

> **Как запомнить:** CQRS — это не отдельная база данных и не обязательно микросервисы. Это принцип разделения чтения и записи. Разные модели и базы данных — возможная реализация, а не обязательное требование.

## 1. Как работает CQRS

В классическом CRUD-приложении одна модель обслуживает и чтение, и запись:

```text
Client
   |
   v
Application
   |
   v
Database
```

При CQRS потоки разделяются:

```text
                 +------------------+
Client --------> | Command Handler  |
                 +------------------+
                          |
                          v
                    Write Model
                          |
                          v
                    Write Database
                          |
                          | синхронизация
                          v
                    Read Database
                          ^
                          |
                 +------------------+
Client --------> |  Query Handler   |
                 +------------------+
```

Это концептуальная схема. В простом варианте обе модели могут работать с одной базой данных, а разделение существует только на уровне кода.

### Command — команда

Команда выражает намерение изменить состояние системы.

Примеры:

- `CreateOrder` — создать заказ.
- `CancelOrder` — отменить заказ.
- `ChangeUserEmail` — изменить email.
- `TransferMoney` — перевести деньги.

Команда может пройти проверку бизнес-правил, изменить данные и завершиться ошибкой, если операция недопустима.

### Query — запрос

Запрос получает данные и не должен изменять состояние системы.

Примеры:

- `GetOrderById` — получить заказ.
- `ListUserOrders` — показать заказы пользователя.
- `GetSalesReport` — получить отчёт о продажах.

Query может возвращать специальную DTO-модель, оптимизированную для отображения на экране.

## 2. CQRS и обычный CRUD

| Критерий | CRUD | CQRS |
|---|---|---|
| Модель | Часто общая | Чтение и запись разделены |
| Запись | Создание, обновление, удаление | Commands |
| Чтение | Получение данных | Queries |
| Сложность | Обычно ниже | Обычно выше |
| Оптимизация чтения | В рамках общей модели | Отдельная read-модель |
| Согласованность | Часто синхронная | Может быть eventual consistency |

**Важно:** CQRS не требует двух физических баз данных. Начать можно с двух отдельных обработчиков и моделей в одном приложении.

## 3. CQRS в Python Backend

Пример упрощённого разделения команд и запросов:

```python
from dataclasses import dataclass


@dataclass
class CreateOrder:
    user_id: int
    amount: float


def create_order(command: CreateOrder) -> int:
    if command.amount <= 0:
        raise ValueError("Amount must be positive")

    # Здесь сохраняем заказ через write-модель.
    order_id = 123
    return order_id


def get_order(order_id: int) -> dict:
    # Здесь получаем данные через read-модель.
    return {
        "id": order_id,
        "status": "created",
    }
```

В этом примере разделение только логическое. В реальном приложении вместо заглушек будут репозитории, транзакции, модели SQLAlchemy и обработчики команд и запросов.

### Как это организовать с FastAPI

```text
app/
├── api/
│   └── orders.py
├── commands/
│   └── create_order.py
├── queries/
│   └── get_order.py
├── repositories/
│   ├── write_repository.py
│   └── read_repository.py
└── models/
```

Это возможный вариант структуры, а не обязательный стандарт. В небольшом проекте отдельные каталоги могут быть лишними.

## 4. Когда нужны разные базы данных

Например, интернет-магазин обрабатывает заказы.

- Write-модель обеспечивает корректное создание заказа, проверку бизнес-правил и транзакции.
- Read-модель объединяет данные заказа, доставки и оплаты в готовое представление.
- Read-база может быть оптимизирована под отчёты и быстрые запросы.

При этом данные между моделями нужно синхронизировать. Если обновление read-модели происходит асинхронно, пользователь некоторое время может видеть устаревшую информацию.

Это называется **eventual consistency — согласованность в конечном счёте**.

Не стоит использовать асинхронную синхронизацию там, где бизнес требует немедленно видеть результат записи.

## 5. CQRS и Event Sourcing

Эти паттерны часто применяют вместе, но они решают разные задачи.

| Паттерн | Основная идея |
|---|---|
| CQRS | Разделение чтения и записи |
| Event Sourcing | Хранение последовательности событий, меняющих состояние |

CQRS может работать без Event Sourcing. Например, команда обновляет строку в PostgreSQL, а запрос читает подготовленное представление из другой таблицы.

Event Sourcing также не требует CQRS, хотя их совместное применение встречается часто.

Связанные темы: [[Event Sourcing]], [[Микросервисы — 7 архитектурных паттернов]].

## 6. Преимущества и недостатки

**Преимущества:**
- Независимая оптимизация чтения и записи.
- Возможность создавать специализированные read-модели.
- Более явное разделение бизнес-команд и запросов.
- Возможность масштабировать нагрузку чтения отдельно.

**Недостатки:**
- Дополнительная сложность кода и инфраструктуры.
- Синхронизация read- и write-моделей.
- Возможная eventual consistency.
- Сложнее отлаживать, тестировать и поддерживать данные в согласованном состоянии.

## 7. Частые вопросы на собеседовании

**CQRS — это микросервисный паттерн?**

Нет. Его можно использовать в монолите, модульном монолите или распределённой системе.

**Обязательно ли иметь две базы данных?**

Нет. Разделение может существовать только в коде. Отдельные хранилища нужны, если это оправдано нагрузкой или требованиями к моделям данных.

**CQRS всегда ускоряет приложение?**

Нет. Он может повысить производительность при разных профилях чтения и записи, но добавляет накладные расходы и сложность.

**Почему возникает eventual consistency?**

Потому что изменения write-модели могут передаваться в read-модель асинхронно. Между записью и обновлением представления существует задержка.

**Чем Command отличается от Query?**

Command выражает намерение изменить состояние. Query возвращает данные и не должен менять состояние системы.

**Когда CQRS не нужен?**

Когда приложение представляет собой обычный CRUD-сервис без сложных требований к масштабированию, чтению и бизнес-логике.

## 8. Шпаргалка

- CQRS = Command Query Responsibility Segregation.
- Command — изменение состояния.
- Query — чтение данных без изменения состояния.
- Разные модели не означают обязательные разные базы.
- Eventual consistency возможна, но не обязательна.
- CQRS и Event Sourcing — разные паттерны.
- Выбирать CQRS стоит по требованиям системы, а не ради модной архитектуры.
