# Event Sourcing — конспект для Python Backend

## Формула для собеседования

**Event Sourcing = хранение истории изменений в виде событий вместо хранения только текущего состояния объекта.**

## Короткий ответ

Event Sourcing — архитектурный паттерн, при котором система сохраняет последовательность событий, произошедших с объектом, а его текущее состояние можно восстановить, последовательно применив эти события.

Например, вместо хранения только текущего баланса счёта система сохраняет события `AccountOpened`, `MoneyDeposited` и `MoneyWithdrawn`.

## Ответ на собеседовании

Event Sourcing — это паттерн хранения данных, при котором источником истины является последовательность событий, описывающих изменения состояния системы.

Вместо того чтобы просто обновлять запись в базе данных, приложение добавляет новое событие в историю. Текущее состояние можно восстановить, применив все события в правильном порядке.

Например, для банковского счёта система хранит события пополнения и снятия средств, а не только итоговый баланс. Это позволяет восстановить состояние счёта на определённый момент времени и проследить, как оно изменялось.

Преимущества Event Sourcing — полная история изменений, возможность аудита и восстановления состояния. Недостатки — усложнение архитектуры, управление версиями событий, обработка повторной доставки и необходимость учитывать согласованность данных.

Event Sourcing часто используют вместе с CQRS, но эти паттерны решают разные задачи: Event Sourcing определяет способ хранения изменений, а CQRS разделяет операции чтения и записи.

## 1. Как работает Event Sourcing

В обычной модели приложение хранит текущее состояние:

```text
Account
├── id: 42
└── balance: 700
```

После пополнения или снятия денег баланс обновляется. Предыдущие значения сами по себе не сохраняются в этой записи.

При Event Sourcing приложение хранит историю событий:

```text
AccountOpened(initial_balance=0)
MoneyDeposited(amount=1000)
MoneyWithdrawn(amount=200)
MoneyWithdrawn(amount=100)
```

Текущее состояние рассчитывается из последовательности событий:

\[
1000 - 200 - 100 = 700
\]

Таким образом, журнал событий становится источником истины, а текущий баланс — результатом применения событий.

### Основные компоненты

- **Event Store** — хранилище неизменяемых событий.
- **Event** — факт, который уже произошёл.
- **Aggregate** — объект доменной модели, который обеспечивает бизнес-правила и формирует события.
- **Projection** — представление данных, построенное на основе событий.
- **Snapshot** — сохранённое промежуточное состояние, ускоряющее восстановление.

## 2. Команда, событие и состояние

Эти понятия важно различать на собеседовании.

| Понятие | Значение | Пример |
|---|---|---|
| Command | Намерение выполнить действие | `WithdrawMoney` |
| Event | Факт произошедшего изменения | `MoneyWithdrawn` |
| State | Текущее состояние объекта | `balance = 700` |
| Projection | Представление данных для чтения | Баланс и история операций |
| Snapshot | Сохранённое состояние на определённой версии | Баланс после 1000 событий |

Команда может быть отклонена. Например, снятие суммы, превышающей доступный баланс, не должно порождать событие успешного снятия.

Событие, напротив, описывает уже произошедший факт. Обычно оно формулируется в прошедшем времени: `OrderCreated`, `PaymentReceived`, `MoneyWithdrawn`.

## 3. Пример на Python

Упрощённая модель банковского счёта:

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class MoneyDeposited:
    amount: int


@dataclass(frozen=True)
class MoneyWithdrawn:
    amount: int


def apply_event(balance: int, event: object) -> int:
    if isinstance(event, MoneyDeposited):
        return balance + event.amount

    if isinstance(event, MoneyWithdrawn):
        return balance - event.amount

    raise ValueError("Unknown event")


events = [
    MoneyDeposited(1000),
    MoneyWithdrawn(200),
    MoneyWithdrawn(100),
]

balance = 0
for event in events:
    balance = apply_event(balance, event)

print(balance)  # 700
```

Здесь события представлены объектами Python, а функция `apply_event` восстанавливает состояние.

Это демонстрация принципа, а не полноценная production-реализация. В реальном приложении дополнительно потребуются:

- постоянное хранилище событий;
- идентификаторы агрегатов и версии;
- атомарное сохранение событий;
- проверка бизнес-правил;
- защита от конфликтующих записей;
- обработка повторной доставки событий.

## 4. Event Store: как хранить события

События обычно сохраняют в append-only журнале: новые записи добавляются, а старые события не переписываются при каждом изменении состояния.

Пример структуры таблицы в PostgreSQL:

```sql
CREATE TABLE account_events (
    event_id UUID PRIMARY KEY,
    account_id BIGINT NOT NULL,
    version BIGINT NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (account_id, version)
);
```

Пример записи:

```json
{
  "event_type": "MoneyDeposited",
  "payload": {
    "amount": 1000,
    "currency": "RUB"
  }
}
```

В реальном Event Store тип события и его данные могут храниться в отдельных полях или в едином сериализованном представлении.

**Важно:** обычная таблица PostgreSQL может реализовать простое хранилище событий, но для production-системы нужно отдельно решить вопросы конкурентной записи, версионирования, целостности журнала, доставки событий и восстановления.

### Зачем нужна версия события

У каждого агрегата можно хранить последовательность версий: `1`, `2`, `3` и так далее.

Если два запроса одновременно прочитали версию `5`, оба могут попытаться записать шестое событие. Ограничение уникальности `(account_id, version)` помогает обнаружить конфликт.

Один из запросов должен повторно прочитать актуальное состояние и проверить операцию. Это пример оптимистической конкуренции.

## 5. Восстановление состояния и replay

**Replay** — повторное применение сохранённых событий для восстановления состояния.

Например:

```text
События 1–1000
       |
       v
Восстановление состояния счёта
       |
       v
Текущий баланс
```

Replay также позволяет построить новое представление данных из старых событий.

Но обработчики событий, формирующие состояние, должны быть детерминированными: одинаковая последовательность событий должна приводить к одинаковому результату.

Если при replay использовать текущий курс валют, актуальное время или внешний API, результат может отличаться от первоначального. Значения, необходимые для воспроизведения бизнес-решения, следует фиксировать в событии.

## 6. Snapshot — снимок состояния

Если у агрегата накопились тысячи или миллионы событий, проигрывать всю историю при каждом запросе дорого.

Snapshot сохраняет состояние после определённого количества событий:

```text
События 1–1000
       |
       v
Snapshot версии 1000
       |
       +--> События 1001–1100
                    |
                    v
             Текущее состояние
```

Для восстановления достаточно загрузить snapshot и применить последующие события.

Snapshot — это оптимизация, а не замена журнала событий. Если snapshot потерян, состояние должно оставаться восстанавливаемым из событий.

## 7. Event Sourcing и CQRS

Паттерны часто применяют совместно.

| Критерий | Event Sourcing | CQRS |
|---|---|---|
| Что определяет | Как хранить изменения | Как разделять чтение и запись |
| Главная идея | История событий — источник истины | Command и Query имеют разные модели |
| Обязателен ли второй read-store | Нет | Нет |
| Можно применять отдельно | Да | Да |

Типичная совместная архитектура:

```text
Command
   |
   v
Aggregate
   |
   v
Event Store
   |
   v
Event Publisher / Processor
   |
   v
Projection
   |
   v
Read Database
   |
   v
Query
```

После сохранения события обработчик обновляет read-модель. Если обновление асинхронное, чтение может временно возвращать устаревшие данные.

Подробнее: [[CQRS — конспект для Python Backend]].

## 8. Проекции и согласованность

Projection — это представление данных, построенное из событий.

Например, события заказов могут формировать разные проекции:

- список заказов пользователя;
- отчёт о продажах;
- количество заказов по статусам;
- аналитическую витрину.

Одни и те же события могут использоваться для нескольких представлений.

При асинхронной обработке проекции обычно обновляются не мгновенно. Это приводит к eventual consistency — согласованности в конечном счёте.

Для критичных операций нельзя бездумно полагаться на отстающую проекцию. Проверку доступного баланса или другого инварианта следует выполнять на стороне, которая отвечает за корректность изменения состояния.

## 9. Надёжная доставка событий

Одно из основных практических ограничений — связь записи события с публикацией в брокер сообщений.

Предположим, приложение сохранило событие в PostgreSQL, но упало до публикации в Kafka. Другие сервисы не узнают об изменении.

Для решения этой проблемы часто применяют **Transactional Outbox**:

1. В одной транзакции сохраняют бизнес-изменение и запись о событии в outbox-таблице.
2. Отдельный процесс публикует события в брокер.
3. После успешной публикации запись отмечают обработанной или удаляют согласно принятой политике.

Даже при надёжной доставке возможны повторные сообщения. Поэтому потребители должны обрабатывать события идемпотентно — повторная обработка не должна повторно применять бизнес-эффект.

Связанные темы: [[Микросервисы — 7 архитектурных паттернов]], [[Отказоустойчивость в Backend-разработке]].

## 10. Версионирование событий

Формат событий со временем меняется. Например, старое событие заказа содержало только `amount`, а новая версия также содержит `currency`.

Проблема: старые события продолжают храниться и должны оставаться читаемыми.

Варианты решения:

- добавлять новые необязательные поля с совместимыми значениями по умолчанию;
- хранить версию схемы события;
- преобразовывать старые события при чтении;
- использовать upcaster — компонент, преобразующий старый формат события в новый формат для обработки.

Не следует просто менять смысл старого поля или удалять данные, от которых зависят обработчики исторических событий.

## 11. Преимущества и недостатки

### Преимущества

- Полная история бизнес-изменений.
- Возможность аудита и расследования инцидентов.
- Восстановление состояния на определённый момент времени.
- Возможность перестраивать проекции.
- Поддержка сложных доменных процессов.

### Недостатки

- Более сложная архитектура и эксплуатация.
- Необходимость управлять версиями событий.
- Сложности с конкурентной записью и повторной доставкой.
- Задержки обновления проекций.
- Дополнительные требования к мониторингу и восстановлению.

### Когда использовать

Event Sourcing оправдан, когда история изменений является важной частью предметной области: финансовые операции, аудит, сложные процессы заказа, системы с необходимостью воспроизводить прошлое состояние.

Для простого CRUD-приложения, где достаточно хранить актуальное состояние и несколько технических логов, этот паттерн обычно избыточен.

## 12. Частые вопросы на собеседовании

**Чем Event Sourcing отличается от обычного аудита?**

Обычный аудит часто хранит историю для расследований, а текущее состояние остаётся основным источником истины. В Event Sourcing источником истины служит журнал событий, из которого можно восстановить состояние.

**Можно ли изменять или удалять события?**

Обычно сохранённые события считаются неизменяемыми. Исправление бизнес-ошибки отражают новым компенсирующим событием. Юридические требования к удалению персональных данных требуют отдельного проектирования.

**Что такое replay?**

Повторное применение событий для восстановления состояния или перестроения проекции.

**Зачем нужны snapshot?**

Чтобы не применять всю историю при каждом восстановлении агрегата.

**Что произойдёт, если одно событие обработается дважды?**

Без защиты бизнес-эффект может примениться повторно. Поэтому нужны идемпотентность, идентификаторы событий и контроль обработанных сообщений.

**Обязательно ли использовать Kafka?**

Нет. Kafka может обеспечивать передачу событий между компонентами, но само хранилище Event Sourcing не обязано быть Kafka. Это разные роли инфраструктуры.

**Как Event Sourcing связан с микросервисами?**

События могут помогать интегрировать сервисы, но Event Sourcing не требует микросервисной архитектуры и может применяться внутри одного приложения.

## 13. Шпаргалка

- **Event Sourcing:** источник истины — история событий.
- **Event Store:** хранит события.
- **Replay:** повторное применение событий.
- **Snapshot:** ускоряет восстановление состояния.
- **Projection:** строит представление для чтения.
- **CQRS:** разделяет чтение и запись, но не требует Event Sourcing.
- **Transactional Outbox:** помогает надёжно публиковать события после фиксации транзакции.
- **Idempotency:** защищает от повторного применения бизнес-эффекта.
- **Versioning:** сохраняет совместимость с историческими событиями.
