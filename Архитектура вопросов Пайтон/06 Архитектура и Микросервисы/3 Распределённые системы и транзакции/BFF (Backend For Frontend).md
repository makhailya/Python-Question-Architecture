### BFF (Backend For Frontend)

## Формула для собеседования

**BFF = отдельный backend-слой, адаптированный под потребности конкретного типа клиента: Web, Mobile или Admin.**

## Короткий ответ

BFF — архитектурный паттерн, при котором для разных типов клиентов создаются отдельные backend-слои. Каждый BFF предоставляет API, подходящий конкретному интерфейсу, и при необходимости агрегирует данные из нескольких внутренних сервисов.

Например, мобильному приложению нужен компактный ответ, веб-приложению — дополнительные данные для страницы, а административной панели — расширенная информация и инструменты управления.

## Ответ на собеседовании

BFF расшифровывается как Backend For Frontend. Это паттерн, при котором создаётся отдельный backend для конкретного типа клиента: например, мобильного приложения, веб-сайта или административной панели.

У разных клиентов могут отличаться требования к формату данных, количеству запросов, производительности и авторизации. BFF адаптирует API под эти требования и может объединять ответы нескольких микросервисов, чтобы клиенту не приходилось самостоятельно вызывать множество endpoint'ов.

Преимущества — более удобный API для каждого клиента, меньше лишних данных и снижение сложности фронтенда. Недостатки — дополнительные компоненты, стоимость поддержки и риск дублирования логики. BFF не заменяет микросервисы, а служит адаптационным слоем между клиентом и внутренней системой.

## 1. Как работает BFF

```text
       Web Client      Mobile App      Admin Panel
           |                |                |
           v                v                v
       Web BFF          Mobile BFF         Admin BFF
           |                |                |
           +----------------+----------------+
                            |
                  Внутренние сервисы
                 /        |         \
                v         v          v
             Users      Orders     Payments
```

Каждый клиент обращается к своему BFF, а тот взаимодействует с необходимыми внутренними сервисами.

Например, мобильный BFF может получить профиль пользователя и последние заказы, объединить данные и вернуть клиенту один компактный JSON-ответ.

## 2. Зачем нужен BFF

Представим страницу заказа в интернет-магазине.

- **Web:** нужны подробные данные заказа, история статусов и информация о доставке.
- **Mobile:** нужен компактный ответ, чтобы уменьшить объём передаваемых данных.
- **Admin:** нужны дополнительные сведения, история операций и административные действия.

Без BFF клиентам приходится использовать общий API, делать несколько запросов и самостоятельно объединять ответы.

С BFF каждый интерфейс получает данные в удобном для него формате.

## 3. Что должен делать BFF

Типичные обязанности:

- адаптация структуры API под клиента;
- агрегация ответов нескольких сервисов;
- преобразование данных в DTO;
- сокращение количества запросов со стороны клиента;
- обработка клиентских сценариев;
- передача контекста пользователя и проверка доступа в рамках принятой модели безопасности.

При этом бизнес-правила должны оставаться в профильных сервисах. Например, расчёт цены заказа не следует дублировать в Web BFF и Mobile BFF.

## 4. Пример на Python и FastAPI

Допустим, мобильному приложению нужны профиль пользователя и последние заказы.

```python
from fastapi import FastAPI
import httpx

app = FastAPI()


@app.get("/mobile/home")
async def mobile_home():
    async with httpx.AsyncClient(timeout=3.0) as client:
        profile_response = await client.get(
            "http://users-service/users/me"
        )
        orders_response = await client.get(
            "http://orders-service/orders/recent"
        )

    profile_response.raise_for_status()
    orders_response.raise_for_status()

    profile = profile_response.json()
    orders = orders_response.json()

    return {
        "name": profile["name"],
        "recent_orders": orders[:3],
    }
```

Это упрощённый пример агрегации на уровне BFF. В production-коде необходимо отдельно продумать обработку ошибок, аутентификацию, передачу контекста пользователя и повторное использование HTTP-клиента.

Также независимые запросы можно выполнять параллельно, если это безопасно и оправдано требованиями к задержке.

## 5. BFF и API Gateway

Эти паттерны часто используются вместе, но отвечают за разные задачи.

| Критерий | API Gateway | BFF |
|---|---|---|
| Главная цель | Единая точка входа и инфраструктурные политики | Адаптация API под конкретный клиент |
| Основная ответственность | Маршрутизация, ограничения, общие политики | Клиентские сценарии, DTO, агрегация |
| Количество | Часто общий gateway | Может быть несколько BFF |
| Бизнес-логика | Обычно минимальная | Клиентская оркестрация, но не владение доменными правилами |

Типичная схема:

```text
Web ──────┐
          v
       API Gateway
          |
          +── Web BFF ───────┐
          |                  |
Mobile ───+── Mobile BFF ────+──> Микросервисы
          |                  |
Admin ────+── Admin BFF ─────┘
```

В некоторых системах BFF сам выполняет функции gateway, поэтому отдельный API Gateway не всегда нужен.

## 6. Преимущества и недостатки

**Преимущества:**
- API адаптирован под конкретный клиент;
- меньше лишних данных и сетевых запросов;
- проще фронтенд;
- можно независимо развивать клиентские API;
- можно учитывать особенности мобильной сети и интерфейса.

**Недостатки:**
- больше сервисов и точек отказа;
- дополнительные расходы на развёртывание и мониторинг;
- риск дублирования кода;
- необходимость поддерживать несколько API;
- агрегация может увеличивать задержку, если внутренние вызовы выполняются последовательно.

## 7. Когда использовать BFF

BFF полезен, когда:

- у Web, Mobile и Admin существенно различаются сценарии;
- клиенты требуют разные представления данных;
- фронтенд вынужден вызывать слишком много сервисов;
- мобильному приложению важно уменьшить число сетевых обращений;
- команды клиентов развиваются независимо.

BFF может быть избыточным, если у приложения один клиент, API простой, а требования к данным почти не отличаются.

## 8. Частые вопросы на собеседовании

**BFF — это микросервис?**

Он может быть реализован как отдельный сервис, но BFF — прежде всего архитектурный паттерн, а не требование к способу развёртывания.

**Чем BFF отличается от API Gateway?**

Gateway обеспечивает общий вход и инфраструктурные политики, а BFF адаптирует API под конкретный клиент. Эти обязанности иногда совмещаются.

**Можно ли размещать бизнес-логику в BFF?**

Допустима логика оркестрации клиентского сценария и преобразования данных. Но основные доменные правила должны принадлежать соответствующим сервисам, чтобы не дублироваться между BFF.

**Обязательно ли создавать отдельный BFF для каждого клиента?**

Нет. Отдельные BFF оправданы, когда различия между клиентами достаточно существенны.

**Как BFF уменьшает количество запросов?**

Он агрегирует данные из нескольких внутренних сервисов и возвращает клиенту единый ответ.

## 9. Шпаргалка

- BFF = Backend For Frontend.
- Отдельный адаптационный слой под Web, Mobile или Admin.
- Адаптирует API и агрегирует данные.
- Снижает сложность клиентского кода и количество запросов.
- Может использоваться совместно с API Gateway.
- Не заменяет микросервисы и не должен дублировать доменные правила.
