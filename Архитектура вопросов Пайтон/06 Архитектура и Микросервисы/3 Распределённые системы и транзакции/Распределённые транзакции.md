# 🔄 Распределённые транзакции

## 🎯 Ответ на собеседовании

**Распределённая транзакция** — это транзакция, которая затрагивает несколько независимых ресурсов или сервисов, например несколько баз данных.

Главная проблема — обеспечить согласованность данных, если операция должна выполниться сразу в нескольких местах.

Например:

```text
Order Service
     ↓
Order DB

Payment Service
     ↓
Payment DB
```

Создание заказа и списание денег происходят в разных сервисах и, возможно, в разных базах данных.

Нельзя просто сделать один обычный `COMMIT` для обеих БД.

---

## 🎤 Суперкоротко

**Распределённая транзакция — это транзакция, которая затрагивает несколько независимых ресурсов. Главная проблема — сохранить согласованность данных при частичном сбое.**

---

## 🧩 Пример проблемы

Пользователь покупает товар.

Нужно:

```text
1. Создать заказ
2. Списать деньги
3. Уменьшить остаток товара
```

В микросервисной архитектуре:

```text
Order Service
     ↓
Order DB

Payment Service
     ↓
Payment DB

Product Service
     ↓
Product DB
```

Представим:

```text
Создали заказ       ✅
Списали деньги      ✅
Уменьшили остаток   ❌
```

Получается неконсистентное состояние:

```text
Заказ создан
Деньги списаны
Товар не зарезервирован
```

---

## ❓ Почему обычная транзакция БД не подходит

В одной базе можно сделать:

```python
BEGIN

INSERT order
UPDATE balance
UPDATE product

COMMIT
```

Если что-то пошло не так:

```text
ROLLBACK
```

Все изменения откатываются.

Но если данные находятся в разных БД:

```text
Order DB
Payment DB
Product DB
```

одна локальная транзакция не может просто охватить их все.

---

# 2PC — Two-Phase Commit

Один из подходов к распределённым транзакциям — **2PC (Two-Phase Commit)**.

Суть — есть координатор, который управляет несколькими участниками транзакции.

```text
              Coordinator
              /    |    \
             ↓     ↓     ↓
          Order  Payment Product
            DB      DB      DB
```

2PC состоит из двух фаз.

---

## 1️⃣ Prepare

Координатор спрашивает участников:

```text
"Вы готовы выполнить транзакцию?"
```

```text
Coordinator
    │
    ├──→ Order DB   → YES
    ├──→ Payment DB → YES
    └──→ Product DB → YES
```

Если все готовы:

```text
YES
YES
YES
```

переходим ко второй фазе.

---

## 2️⃣ Commit

Координатор говорит:

```text
"Подтверждаем транзакцию."
```

```text
Coordinator
    │
    ├──→ Order DB   → COMMIT
    ├──→ Payment DB → COMMIT
    └──→ Product DB → COMMIT
```

Если хотя бы один участник не готов:

```text
YES
YES
NO
```

координатор инициирует откат:

```text
ROLLBACK
```

---

## ⚠️ Недостатки 2PC

Главная проблема — **блокировки и зависимость от координатора**.

Если координатор упал в неподходящий момент, участники могут долго ждать решения.

Также 2PC:

* сложнее;
* создаёт дополнительный overhead;
* плохо масштабируется для некоторых распределённых систем;
* увеличивает связанность компонентов.

Поэтому в микросервисах часто предпочитают **Saga**.

---

# 🧩 Saga

**Saga** — паттерн управления распределённой бизнес-транзакцией через последовательность локальных транзакций.

Вместо одной глобальной транзакции:

```text
BEGIN
   ↓
все сервисы
   ↓
COMMIT
```

каждый сервис выполняет собственную локальную транзакцию.

```text
Order Service
     ↓
локальная транзакция
     ↓
Payment Service
     ↓
локальная транзакция
     ↓
Product Service
     ↓
локальная транзакция
```

---

## 🔄 Компенсирующие операции

Если одна из операций завершилась ошибкой, выполняются **компенсирующие действия**.

Например:

```text
1. Создали заказ       ✅
2. Списали деньги      ✅
3. Резерв товара       ❌
```

Тогда:

```text
Отменить заказ
      ↓
Вернуть деньги
```

То есть вместо `ROLLBACK` используется бизнес-операция, которая компенсирует предыдущие изменения.

---

## 🧠 Пример Saga

```text
Create Order
     ↓
Reserve Product
     ↓
Charge Payment
     ↓
Send Notification
```

Если оплата не прошла:

```text
Create Order       ✅
Reserve Product    ✅
Charge Payment     ❌
        ↓
Release Product
        ↓
Cancel Order
```

Это и есть идея **compensating transactions**.

---

# 🔀 Виды Saga

Обычно выделяют два основных подхода.

## 1. Choreography

Сервисы взаимодействуют через события.

```text
Order Service
     ↓
order.created
     ↓
Kafka
     ↓
Payment Service
     ↓
payment.completed
     ↓
Kafka
     ↓
Product Service
```

Центрального координатора нет.

Каждый сервис реагирует на события.

### Плюсы

* меньше централизованной логики;
* хорошо подходит для event-driven архитектуры.

### Минусы

* сложнее понять весь workflow;
* сложнее отлаживать;
* при большом количестве сервисов поток событий может стать запутанным.

---

## 2. Orchestration

Есть отдельный **Saga Orchestrator**, который управляет последовательностью действий.

```text
              Orchestrator
             /      |      \
            ↓       ↓       ↓
         Order   Payment   Product
```

Orchestrator говорит:

```text
1. Создай заказ
2. Зарезервируй товар
3. Сними оплату
```

Если что-то не получилось:

```text
"Отмени заказ"
"Освободи резерв"
```

### Плюсы

* workflow находится в одном месте;
* проще контролировать последовательность;
* проще понимать бизнес-процесс.

### Минусы

* появляется дополнительный компонент;
* orchestrator может стать слишком сложным.

---

# 🆚 2PC vs Saga

| 2PC                                 | Saga                                    |
| ----------------------------------- | --------------------------------------- |
| Одна распределённая транзакция      | Последовательность локальных транзакций |
| Координатор                         | Orchestrator или события                |
| Commit/Rollback                     | Компенсирующие операции                 |
| Сильнее ориентирован на атомарность | Eventual consistency                    |
| Может блокировать ресурсы           | Обычно меньше блокировок                |
| Сложнее масштабировать              | Хорошо подходит для микросервисов       |

---

# ⏳ Eventual Consistency

Saga часто работает с моделью **eventual consistency** — данные могут быть временно несогласованными, но система должна прийти к согласованному состоянию.

Например:

```text
Заказ создан
      ↓
Payment pending
      ↓
Payment completed
      ↓
Order paid
```

Между этими состояниями может пройти некоторое время.

Это нормально для распределённой системы, если итоговое состояние корректно.

---

# 📨 Kafka и распределённые транзакции

Kafka часто используется для реализации событийного взаимодействия в Saga.

Например:

```text
Order Service
     │
     ↓
order.created
     │
     ↓
   Kafka
     │
     ↓
Payment Service
     │
     ↓
payment.completed
     │
     ↓
   Kafka
     │
     ↓
Order Service
```

Сервисы не используют одну общую транзакцию БД.

Они обмениваются событиями.

---

# ⚠️ Главная проблема Saga

Saga не даёт обычный `ROLLBACK` всей системы.

Например:

```text
Создали заказ
     ↓
Списали деньги
     ↓
Ошибка
```

Нельзя просто сказать:

```text
ROLLBACK EVERYTHING
```

Нужно выполнить компенсацию:

```text
Возврат денег
     ↓
Отмена заказа
```

Поэтому Saga требует продуманной бизнес-логики компенсации.

---

# 🎯 Когда это используется

Распределённые транзакции особенно актуальны в:

* микросервисной архитектуре;
* платёжных системах;
* интернет-магазинах;
* банковских системах;
* event-driven системах;
* системах с несколькими независимыми БД.

---

# 🧠 Главное

```text
Распределённая транзакция
        ↓
Несколько сервисов / БД
        ↓
Нужно сохранить согласованность
        ↓
┌─────────────────┐
│      2PC        │
│  Prepare/Commit │
└─────────────────┘

или

┌─────────────────┐
│      Saga       │
│ Local Tx +      │
│ Compensation    │
└─────────────────┘
```

**2PC** → пытается выполнить одну распределённую транзакцию через координатора.

**Saga** → разбивает операцию на локальные транзакции и использует компенсирующие действия при ошибках.

**Eventual consistency** → система может быть временно несогласованной, но в итоге должна прийти к согласованному состоянию.

### Формула для собеседования

**Распределённая транзакция = несколько независимых ресурсов + необходимость согласованного результата.**

**Основные подходы: 2PC и Saga.**

Для микросервисов особенно важно знать:

**Saga = локальные транзакции + события/оркестрация + компенсирующие операции.**
