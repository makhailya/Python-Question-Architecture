# Реляционная транзакция 🗄️

## 🎯 Ответ на собеседовании

**Транзакция** — это логически единая последовательность операций над базой данных, которая выполняется как одно целое.

Главный принцип:

> Либо выполняются **все операции транзакции**, либо **не выполняется ни одна**.

Транзакция обеспечивает свойства **ACID**:

```text
Atomicity     — атомарность
Consistency   — согласованность
Isolation     — изоляция
Durability    — долговечность
```

Пример перевода денег:

```text
Списать 100 ₽ с A
        +
Зачислить 100 ₽ на B
```

Обе операции должны произойти вместе.

Если списание прошло, а зачисление упало — транзакция должна выполнить **ROLLBACK**.

---

## 🎤 Суперкоротко

> Транзакция — это неделимая логическая операция над БД. Она объединяет несколько SQL-операций и гарантирует ACID: атомарность, согласованность, изоляцию и долговечность. Завершение транзакции выполняется через COMMIT, а отмена — через ROLLBACK.

---

# 1. Зачем нужны транзакции?

Представим перевод:

```text
Счёт A: 1000 ₽
Счёт B: 500 ₽
```

Нужно перевести 200 ₽:

```text
1. A -= 200
2. B += 200
```

После операции:

```text
A = 800
B = 700
```

Но представим:

```text
A -= 200       ✅
B += 200       ❌ ошибка
```

Без транзакции:

```text
A = 800
B = 500
```

200 ₽ исчезли.

С транзакцией:

```text
BEGIN

A -= 200
B += 200

COMMIT
```

Если вторая операция падает:

```text
ROLLBACK
```

И база возвращается к исходному состоянию.

---

# 2. Жизненный цикл транзакции

Упрощённо:

```text
BEGIN
  ↓
SQL операции
  ↓
SQL операции
  ↓
COMMIT
```

Или при ошибке:

```text
BEGIN
  ↓
SQL операция
  ↓
ошибка
  ↓
ROLLBACK
```

---

# 3. BEGIN

`BEGIN` начинает транзакцию.

```python
BEGIN;
```

После этого SQL-операции относятся к одной транзакции.

Например:

```python
BEGIN;

UPDATE accounts
SET balance = balance - 200
WHERE id = 1;

UPDATE accounts
SET balance = balance + 200
WHERE id = 2;
```

Изменения ещё не считаются окончательно зафиксированными.

---

# 4. COMMIT

`COMMIT` подтверждает транзакцию.

```python
COMMIT;
```

После `COMMIT` изменения становятся постоянными.

Схема:

```text
BEGIN
 ↓
UPDATE
 ↓
UPDATE
 ↓
COMMIT
 ↓
изменения зафиксированы
```

---

# 5. ROLLBACK

`ROLLBACK` отменяет изменения текущей транзакции.

```python
ROLLBACK;
```

Например:

```text
BEGIN
 ↓
UPDATE A
 ↓
UPDATE B
 ↓
ошибка
 ↓
ROLLBACK
```

Результат:

```text
База возвращается
к состоянию до BEGIN
```

---

# 6. ACID

ACID — четыре свойства транзакций.

```text
A — Atomicity
C — Consistency
I — Isolation
D — Durability
```

---

# 7. Atomicity — атомарность

Транзакция выполняется **целиком или не выполняется вообще**.

Например:

```text
Перевод денег

1. Списать
2. Зачислить
```

Нельзя получить:

```text
1 → успешно
2 → ошибка
```

при зафиксированной транзакции.

Должно быть:

```text
обе операции → COMMIT
```

или:

```text
ошибка → ROLLBACK
```

### Формулировка на собеседовании

> Атомарность гарантирует, что транзакция является неделимой: либо фиксируются все её изменения, либо ни одно.

---

# 8. Consistency — согласованность

После успешной транзакции база должна оставаться в состоянии, удовлетворяющем её ограничениям и правилам.

Например:

```text
balance >= 0
```

или:

```text
email UNIQUE
```

или:

```text
order.user_id → существующий user
```

Если транзакция нарушает ограничение:

```text
INSERT
   ↓
constraint violation
   ↓
ROLLBACK
```

---

# 9. Isolation — изоляция

Параллельные транзакции не должны неконтролируемо влиять друг на друга.

Например:

```text
Transaction A
       │
       │
       ├──────────┐
                  ↓
             Database
                  ↑
       ┌──────────┤
       │
Transaction B
```

Несколько пользователей могут одновременно изменять данные.

Уровень изоляции определяет, **что одна транзакция может видеть из изменений другой**.

---

# 10. Durability — долговечность

После успешного:

```text
COMMIT
```

изменения должны сохраняться даже после сбоя системы.

Упрощённо:

```text
Transaction
    ↓
 COMMIT
    ↓
данные зафиксированы
    ↓
перезапуск БД
    ↓
данные остаются
```

Именно это обеспечивает долговечность зафиксированных изменений.

---

# 11. Уровни изоляции

В SQL обычно рассматривают четыре уровня:

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

От более слабой изоляции к более строгой:

```text
READ UNCOMMITTED
       ↓
READ COMMITTED
       ↓
REPEATABLE READ
       ↓
SERIALIZABLE
```

Чем выше изоляция, тем меньше аномалий параллельного выполнения, но потенциально выше стоимость и вероятность блокировок/конфликтов.

---

# 12. READ COMMITTED

Транзакция видит только **зафиксированные** изменения других транзакций.

В PostgreSQL это уровень изоляции по умолчанию.

Например:

```text
Transaction A        Transaction B

UPDATE balance
       │
       ├────────────→ не COMMIT
       │
SELECT balance  ← не видит
                 незакоммиченные изменения
```

После `COMMIT` другой транзакции изменения становятся видимыми для последующих запросов.

---

# 13. REPEATABLE READ

В рамках транзакции чтения работают относительно стабильного снимка данных.

Упрощённо:

```text
BEGIN
 ↓
SELECT → состояние A
 ↓
другая транзакция меняет данные
 ↓
SELECT → тот же снимок
```

Это даёт более сильную изоляцию, чем `READ COMMITTED`.

---

# 14. SERIALIZABLE

Самый строгий стандартный уровень.

Идея:

> Результат параллельного выполнения должен быть эквивалентен некоторому последовательному выполнению транзакций.

Упрощённо:

```text
T1 → полностью
T2 → полностью
```

хотя физически они могут выполняться параллельно.

При конфликте БД может завершить одну транзакцию ошибкой сериализации, после чего приложение обычно должно повторить её.

---

# 15. Аномалии конкурентного доступа

При параллельных транзакциях возможны различные аномалии.

Основные:

### Dirty Read

Чтение незакоммиченных данных другой транзакции.

```text
T1: UPDATE
T2: SELECT ← видит изменения T1 до COMMIT
```

---

### Non-Repeatable Read

Один и тот же запрос внутри транзакции возвращает разные результаты.

```text
T1: SELECT → 100

T2: UPDATE → 200
T2: COMMIT

T1: SELECT → 200
```

---

### Phantom Read

Повторный запрос возвращает новые/исчезнувшие строки, удовлетворяющие условию.

```text
T1: SELECT WHERE price > 100
    → 5 строк

T2: INSERT строку с price = 200
T2: COMMIT

T1: повторный SELECT
    → 6 строк
```

---

# 16. SAVEPOINT

Иногда нужно откатить только часть операций.

Для этого используется **SAVEPOINT**.

```python
BEGIN;

INSERT INTO users ...;

SAVEPOINT user_created;

INSERT INTO orders ...;

ROLLBACK TO SAVEPOINT user_created;

COMMIT;
```

Получается:

```text
BEGIN
 ↓
операция A
 ↓
SAVEPOINT
 ↓
операция B
 ↓
ROLLBACK TO SAVEPOINT
 ↓
операция A остаётся
 ↓
COMMIT
```

То есть `ROLLBACK TO SAVEPOINT` не отменяет всю транзакцию.

---

# 17. COMMIT vs ROLLBACK vs SAVEPOINT

| Команда                 | Назначение                      |
| ----------------------- | ------------------------------- |
| `BEGIN`                 | начать транзакцию               |
| `COMMIT`                | зафиксировать изменения         |
| `ROLLBACK`              | отменить всю текущую транзакцию |
| `SAVEPOINT`             | создать точку отката            |
| `ROLLBACK TO SAVEPOINT` | откатиться к точке              |
| `RELEASE SAVEPOINT`     | удалить savepoint               |

---

# 18. Транзакция в PostgreSQL

Типичный SQL:

```python
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Если произошла ошибка:

```python
ROLLBACK;
```

---

# 19. Транзакция в Python

Например, с PostgreSQL-драйвером:

```python
try:
    connection.execute(
        "UPDATE accounts SET balance = balance - 100 WHERE id = 1"
    )

    connection.execute(
        "UPDATE accounts SET balance = balance + 100 WHERE id = 2"
    )

    connection.commit()

except Exception:
    connection.rollback()
    raise
```

Идея:

```text
try
 ↓
операции
 ↓
commit

except
 ↓
rollback
```

---

# 20. Транзакции в Django

В Django обычно используется:

```python
from django.db import transaction


with transaction.atomic():
    account_a.balance -= 100
    account_a.save()

    account_b.balance += 100
    account_b.save()
```

Если внутри блока возникает исключение:

```text
atomic()
   ↓
ROLLBACK
```

Если всё прошло успешно:

```text
atomic()
   ↓
COMMIT
```

`transaction.atomic()` — стандартный механизм управления транзакциями в Django.

---

# 21. Почему транзакция не решает всё?

Транзакция хорошо работает внутри **одной БД**.

Например:

```text
Service
   ↓
PostgreSQL
   └── transaction
```

Но если:

```text
Service A
   ↓
PostgreSQL A

Service B
   ↓
PostgreSQL B
```

то одна локальная транзакция не может атомарно охватить обе БД.

Например:

```text
DB A → COMMIT ✅
DB B → ошибка ❌
```

Получается частично выполненная операция.

Отсюда появляется проблема **распределённых транзакций**.

---

# 22. Локальная транзакция vs распределённая

### Локальная

```text
BEGIN
 ↓
DB
 ├── UPDATE
 ├── INSERT
 └── DELETE
 ↓
COMMIT
```

Одна транзакционная система.

### Распределённая

```text
Service A       Service B
    ↓               ↓
   DB A            DB B
```

Нужно согласовать изменение нескольких независимых ресурсов.

Для этого существуют подходы:

* 2PC;
* Saga;
* Outbox;
* компенсационные операции.

---

# 23. Транзакция и блокировки

При параллельной работе транзакций БД может использовать блокировки.

Например:

```python
SELECT ...
FOR UPDATE;
```

Идея:

```text
T1
 ↓
заблокировала строку
 ↓
изменяет её

T2
 ↓
пытается изменить ту же строку
 ↓
ждёт
```

Это позволяет защищаться от некоторых race condition.

Но чрезмерное использование блокировок может привести к:

* снижению производительности;
* ожиданию;
* deadlock.

---

# 24. Deadlock

**Deadlock** — взаимная блокировка транзакций.

Например:

```text
T1:
заблокировала A
↓
ждёт B

T2:
заблокировала B
↓
ждёт A
```

Получается:

```text
T1 → ждёт T2
↑          ↓
└──────────┘
```

Ни одна транзакция не может продолжить работу.

СУБД обнаруживает deadlock и обычно прерывает одну из транзакций.

---

# 25. Транзакция и Race Condition

Race condition возникает, когда результат зависит от порядка выполнения параллельных операций.

Например:

```text
balance = 100

T1 читает 100
T2 читает 100

T1 → 100 - 80 = 20
T2 → 100 - 50 = 50
```

Одна из проблем — оба потока работали с устаревшим состоянием.

Решение может включать:

```text
транзакции
+
изоляцию
+
блокировки
+
атомарные SQL-операции
```

Но конкретное решение зависит от сценария.

---

# 26. Транзакция и Idempotency

Это разные концепции.

### Transaction

Гарантирует корректность группы операций в рамках транзакционной системы.

```text
A + B
↓
оба COMMIT
или
оба ROLLBACK
```

### Idempotency

Позволяет безопасно повторить операцию.

```text
request #123
↓
обработан

request #123 повторно
↓
результат не должен привести
к повторному нежелательному эффекту
```

Они могут использоваться вместе.

---

# 27. Транзакция и Kafka

Важно понимать границу.

```text
PostgreSQL transaction
        ↓
      COMMIT
        ↓
Kafka publish
```

Это **две разные системы**.

Если PostgreSQL успешно закоммитил данные:

```text
DB → COMMIT ✅
Kafka → publish ❌
```

может возникнуть рассинхронизация.

Это классическая проблема **Dual Write**.

Для неё часто используют **Transactional Outbox**:

```text
BEGIN
 ↓
изменение бизнес-данных
 ↓
запись события в Outbox
 ↓
COMMIT
 ↓
отдельный процесс публикует Outbox → Kafka
```

# 28. Схема полной транзакции

```text
                 TRANSACTION

                    BEGIN
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       INSERT       UPDATE      DELETE
          │           │           │
          └───────────┼───────────┘
                      ↓
                 все успешно?
                  /        \
                да          нет
                ↓            ↓
             COMMIT       ROLLBACK
                ↓            ↓
           изменения       отмена
           сохранены       изменений
```

# 29. Что важно сказать на собеседовании

Если спрашивают:

> Что такое транзакция?

Ответ:

> Транзакция — это логически единая последовательность операций над БД, которая выполняется атомарно. Она обеспечивает свойства ACID: атомарность, согласованность, изоляцию и долговечность. При успешном выполнении изменения фиксируются через COMMIT, при ошибке отменяются через ROLLBACK.

Если спрашивают:

> Зачем нужна транзакция?

> Чтобы несколько связанных изменений выполнялись как единое целое и база не оказалась в промежуточном некорректном состоянии.

Если спрашивают:

> Чем отличается COMMIT от ROLLBACK?

> COMMIT фиксирует изменения транзакции, а ROLLBACK отменяет незакоммиченные изменения.

Если спрашивают:

> Что такое уровень изоляции?

> Это правила, определяющие, какие изменения параллельных транзакций видит текущая транзакция и какие аномалии конкурентного доступа допускаются.

# 30. Итог

```text
Транзакция
│
├── BEGIN
│
├── SQL operations
│
├── COMMIT
│      └── сохранить изменения
│
└── ROLLBACK
       └── отменить изменения
```

### ACID

```text
A — Atomicity
    всё или ничего

C — Consistency
    база остаётся согласованной

I — Isolation
    параллельные транзакции изолированы

D — Durability
    COMMIT переживает сбой
```

### Связь с распределёнными системами

```text
Локальная транзакция
        ↓
одна БД
        ↓
ACID

Несколько сервисов / БД
        ↓
локальных транзакций недостаточно
        ↓
2PC / Saga / Outbox
```

> **Транзакция отвечает за атомарное изменение данных в рамках транзакционной системы. Для нескольких независимых систем нужны дополнительные механизмы координации.**
