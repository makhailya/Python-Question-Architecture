# Dead Letter Exchange и Dead Letter Queue в RabbitMQ ☠️

## 🎯 Ответ на собеседовании

**Dead Letter Exchange (DLX) — Exchange, куда RabbitMQ может направлять сообщения, которые не удалось нормально обработать.**

После маршрутизации через DLX сообщение может попасть в **Dead Letter Queue (DLQ)**.

DLQ используют для:

* сообщений после исчерпания retry;
* отклонённых сообщений;
* сообщений, которые истекли по TTL;
* переполненных очередей при соответствующей политике.

Типичная схема:

```text
Main Queue
    ↓
Consumer
    ↓
ошибка
    ↓
Retry
    ↓
ошибка
    ↓
DLX
    ↓
DLQ
```

**Главное:** DLX — это Exchange, а DLQ — Queue.

---

## 🎤 Суперкоротко

```text
DLX → маршрутизирует проблемные сообщения
DLQ → хранит проблемные сообщения
```

Или:

> **DLX — куда отправить, DLQ — где хранить.**

---

# Зачем нужен DLQ

Представим обычную очередь:

```text
orders_queue
```

В неё приходят задачи:

```text
Order 1
Order 2
Order 3
Order 4
```

Consumer пытается обработать `Order 3`:

```text
Order 3
   ↓
Consumer
   ↓
ERROR
```

Если бесконечно делать `requeue`, получится:

```text
Queue
 ↓
Consumer
 ↓
ERROR
 ↓
Queue
 ↓
Consumer
 ↓
ERROR
 ↓
Queue
 ↓
...
```

Это плохо.

Поэтому после определённого количества попыток сообщение можно отправить в DLQ:

```text
orders_queue
      ↓
   Consumer
      ↓
    ERROR
      ↓
    Retry
      ↓
    ERROR
      ↓
    DLX
      ↓
orders_dlq
```

---

# DLX и DLQ — разные вещи

Это один из главных вопросов на собеседовании.

### DLX

**Dead Letter Exchange**

Это Exchange, через который RabbitMQ маршрутизирует dead-letter сообщения.

### DLQ

**Dead Letter Queue**

Это Queue, в которой эти сообщения можно хранить и анализировать.

Схема:

```text
Main Queue
    ↓
   DLX
    ↓
  DLQ
```

Поэтому неправильно говорить:

> DLX — это очередь для плохих сообщений.

Правильно:

> **DLX — Exchange для маршрутизации dead-letter сообщений, а DLQ — Queue, куда они попадают.**

---

# Что такое Dead Letter

**Dead letter** — сообщение, которое RabbitMQ больше не обрабатывает как обычное сообщение в исходной Queue и которое переводится в dead-letter-маршрутизацию.

Например:

```text
Message
   ↓
Main Queue
   ↓
Consumer
   ↓
❌ обработка не удалась
   ↓
Dead Letter
   ↓
DLX
   ↓
DLQ
```

---

# Когда сообщение может стать Dead Letter

Типичные причины:

### 1. Reject / NACK без requeue

Например:

```text
NACK
requeue = false
```

Сообщение не возвращается в основную Queue и может быть dead-lettered.

---

### 2. Истёк TTL

Если у сообщения или Queue настроен TTL:

```text
Message
   ↓
Queue
   ↓
TTL expired
   ↓
DLX
   ↓
DLQ
```

---

### 3. Queue переполнена

При соответствующей конфигурации и политике, если Queue достигает ограничения длины, сообщения могут быть dead-lettered.

---

### 4. Другие политики RabbitMQ

Dead-lettering определяется конфигурацией Queue и параметрами RabbitMQ.

Поэтому нельзя говорить, что **любая ошибка автоматически отправляет сообщение в DLQ**.

---

# NACK + requeue

Рассмотрим:

```text
Consumer
   ↓
ошибка
   ↓
NACK
   ↓
requeue = true
```

Сообщение возвращается:

```text
Queue
   ↑
   │
NACK + requeue
   │
Consumer
```

Это ещё **не DLQ**.

---

# NACK + no requeue

Если:

```text
NACK
requeue = false
```

то сообщение не возвращается в исходную Queue.

При настроенном DLX оно может быть направлено туда:

```text
Main Queue
    ↓
Consumer
    ↓
NACK
requeue = false
    ↓
DLX
    ↓
DLQ
```

---

# Retry + DLQ

Один из типичных production-сценариев:

```text
                    ┌──────────────┐
                    │  Main Queue  │
                    └──────┬───────┘
                           ↓
                       Consumer
                           ↓
                        ERROR
                           ↓
                         Retry
                           ↓
                     ┌─────┴─────┐
                     │           │
                  успех       ошибка
                     │           │
                    ACK        Retry
                                  ↓
                              ошибка
                                  ↓
                                DLX
                                  ↓
                                DLQ
```

Например:

```text
Attempt 1 → ERROR
Attempt 2 → ERROR
Attempt 3 → ERROR
Attempt 4 → DLQ
```

---

# Зачем нужна DLQ

DLQ нужна не просто для хранения ошибок.

Она позволяет:

* анализировать проблемные сообщения;
* находить причины ошибок;
* повторно обрабатывать сообщения после исправления проблемы;
* отделять плохие сообщения от нормального потока;
* не блокировать основную Queue.

Например:

```text
orders_queue
     ↓
99 999 успешных сообщений
     ↓
10 проблемных
     ↓
orders_dlq
```

Основной поток продолжает работать.

---

# DLQ как «карантин»

Полезная модель:

```text
Main Queue
    ↓
обычная обработка
    ↓
ошибка
    ↓
DLQ
    ↓
анализ
```

DLQ можно рассматривать как **карантин для сообщений**, которые требуют отдельного внимания.

Например, сообщение содержит некорректные данные:

```text
{
    "order_id": null
}
```

Вместо бесконечного retry оно отправляется в DLQ.

---

# Повторная обработка из DLQ

После исправления причины ошибки сообщение можно попытаться обработать снова.

Например:

```text
DLQ
 ↓
исправили bug
 ↓
reprocess
 ↓
Main Exchange
 ↓
Main Queue
 ↓
Consumer
```

Схема:

```text
orders_dlq
    ↓
reprocess
    ↓
orders_exchange
    ↓
orders_queue
    ↓
Consumer
```

Важно контролировать повторную обработку, чтобы не создать новый бесконечный цикл.

---

# DLQ и идемпотентность

DLQ тесно связана с идемпотентностью.

Представим:

```text
Message
   ↓
Consumer
   ↓
DB operation
   ↓
ошибка после изменения DB
```

При повторной обработке та же операция может выполниться ещё раз.

Поэтому Consumer должен учитывать возможность повторной доставки.

Например:

```text
Message ID
    ↓
проверить, обрабатывалось ли сообщение
    ↓
если нет → обработать
    ↓
сохранить факт обработки
```

Это помогает сделать обработку идемпотентной.

---

# DLQ и мониторинг

В production важно мониторить:

```text
DLQ message count
```

Например:

```text
orders_dlq = 0
```

Нормальная ситуация.

Но:

```text
orders_dlq = 10 000
```

может означать серьёзную проблему:

* сломался Consumer;
* изменился формат сообщения;
* недоступна БД;
* недоступен внешний API;
* ошибка в бизнес-логике.

Поэтому DLQ — хороший источник сигналов для мониторинга.

---

# DLQ не исправляет ошибку

Важно понимать:

> **DLQ не решает проблему обработки.**

Она только изолирует проблемное сообщение.

Например:

```text
Consumer
   ↓
ERROR
   ↓
DLQ
```

Ошибка всё ещё существует.

После этого разработчик должен выяснить причину.

---

# DLX и обычный Exchange

DLX — это не отдельный принцип маршрутизации.

DLX — обычный Exchange RabbitMQ, который используется как **dead-letter exchange**.

Он может быть, например:

```text
Direct Exchange
```

или:

```text
Topic Exchange
```

и использовать соответствующие routing keys/bindings.

---

# Пример

Есть:

```text
orders_exchange
```

Основная Queue:

```text
orders_queue
```

И DLX:

```text
orders_dlx
```

DLQ:

```text
orders_dlq
```

Схема:

```text
                    orders_exchange
                          │
                          ▼
                    orders_queue
                          │
                          ▼
                       Consumer
                          │
                    ┌─────┴─────┐
                    │           │
                  успех       ошибка
                    │           │
                   ACK       no requeue
                                │
                                ▼
                          orders_dlx
                                │
                                ▼
                           orders_dlq
```

---

# DLQ и TTL

TTL можно использовать для реализации задержек или временного хранения сообщений.

Например:

```text
retry_queue
    ↓
TTL = 30 секунд
    ↓
DLX
    ↓
main_queue
```

Получается:

```text
Main Queue
    ↓
ошибка
    ↓
Retry Queue
    ↓
30 секунд
    ↓
DLX
    ↓
Main Queue
```

Так можно реализовать retry с задержкой.

---

# Почему нельзя просто использовать requeue

Простой `requeue`:

```text
ERROR
 ↓
requeue
 ↓
ERROR
 ↓
requeue
 ↓
...
```

может привести к бесконечному циклу.

DLQ позволяет сделать:

```text
ERROR
 ↓
retry
 ↓
retry
 ↓
retry
 ↓
DLQ
```

То есть система получает **контролируемое поведение при ошибках**.

---

# DLQ в микросервисной архитектуре

Например:

```text
Order Service
      ↓
orders_exchange
      ↓
orders_queue
      ↓
Payment Service
```

Если Payment Service не может обработать сообщение:

```text
orders_queue
      ↓
Payment Service
      ↓
ERROR
      ↓
DLX
      ↓
payment_dlq
```

Теперь команда может отдельно исследовать:

```text
payment_dlq
```

не останавливая основной поток сообщений.

---

# 🎯 Частые вопросы на собеседовании

### Что такое DLQ?

DLQ — Dead Letter Queue, очередь для сообщений, которые не удалось обработать обычным способом и которые были направлены в dead-letter-маршрутизацию.

### Что такое DLX?

DLX — Dead Letter Exchange, Exchange, через который RabbitMQ маршрутизирует dead-letter сообщения.

### DLX и DLQ — одно и то же?

Нет.

> **DLX — Exchange, DLQ — Queue.**

### Когда сообщение попадает в DLQ?

Например, после reject/NACK без requeue, истечения TTL или при определённых ограничениях Queue — если настроена соответствующая dead-letter-маршрутизация.

### Что такое requeue?

Возврат сообщения в исходную Queue для повторной обработки.

### Зачем нужна DLQ?

Чтобы проблемные сообщения не зацикливались в основной Queue и чтобы их можно было отдельно анализировать и при необходимости повторно обработать.

### Можно ли повторно обработать сообщение из DLQ?

Да, обычно его можно вернуть в основной поток после устранения причины ошибки.

### DLQ гарантирует отсутствие потери сообщений?

Нет. Надёжность зависит от всей конфигурации RabbitMQ, persistence, acknowledgements, dead-letter routing и поведения Consumer.

### Зачем нужна идемпотентность при использовании DLQ?

Потому что сообщение может быть обработано повторно, поэтому повторная обработка не должна приводить к некорректному повторному выполнению бизнес-операции.

---

# 🧠 Итоговая схема

```text
                 Producer
                    │
                    ▼
              Main Exchange
                    │
                    ▼
               Main Queue
                    │
                    ▼
                 Consumer
                    │
              ┌─────┴─────┐
              │           │
            успех       ошибка
              │           │
             ACK      Retry / NACK
                          │
                     ┌────┴────┐
                     │         │
                  requeue    no requeue
                     │         │
                     │         ▼
                     │        DLX
                     │         │
                     │         ▼
                     │        DLQ
                     │
                     └──→ повторная обработка
```

### Формула для собеседования

> **DLX — Exchange для dead-letter маршрутизации, DLQ — Queue для хранения проблемных сообщений. Они позволяют изолировать сообщения после неудачной обработки, ограничить бесконечные retry и при необходимости выполнить повторную обработку.**

```text
ACK          → успешно обработано
NACK         → ошибка
requeue      → вернуть в Queue
Retry        → повторить обработку
DLX          → маршрутизировать dead letter
DLQ          → хранить проблемные сообщения
Idempotency  → безопасно повторять обработку
```
