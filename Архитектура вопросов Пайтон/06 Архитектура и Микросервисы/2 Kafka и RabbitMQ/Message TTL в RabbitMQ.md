# Message TTL в RabbitMQ ⏱️

## 🎯 Ответ на собеседовании

**TTL (Time-To-Live) в RabbitMQ — это время, в течение которого сообщение или очередь могут хранить сообщения.**

Если сообщение превышает заданный TTL, RabbitMQ удаляет его или, при настроенном Dead Letter Exchange, отправляет в DLX.

TTL часто используют для:

* удаления устаревших сообщений;
* ограничения времени жизни задач;
* реализации задержки перед Retry через `TTL + DLX`;
* защиты очереди от накопления старых сообщений.

Важно различать:

* **Message TTL** — TTL конкретного сообщения;
* **Queue TTL / expiration** — время жизни очереди.

---

## 🎤 Суперкоротко

```text
Message TTL
    ↓
сообщение слишком старое
    ↓
RabbitMQ удаляет его
или
    ↓
DLX
```

Для Retry:

```text
Main Queue
    ↓ ошибка
Retry Queue
    ↓ TTL
DLX
    ↓
Main Queue
```

---

# Что такое TTL

TTL расшифровывается как:

**Time-To-Live — время жизни.**

Например:

```text
TTL = 30 секунд
```

Это означает, что сообщение не должно оставаться актуальным бесконечно.

После истечения TTL RabbitMQ может удалить сообщение или dead-letter'ить его при соответствующей конфигурации.

---

# Зачем нужен TTL

Представим очередь уведомлений:

```text
notification_queue
```

Сообщение:

```text
"Отправить пользователю скидку"
```

Если сообщение пролежало в очереди 24 часа, оно может потерять смысл.

TTL позволяет сказать:

```text
Это сообщение актуально только 10 минут.
```

Например:

```text
TTL = 600 секунд
```

После этого сообщение считается просроченным.

---

# Message TTL

TTL можно задавать для сообщений.

Концептуально:

```python
message = {
    "body": "process order",
    "expiration": "30000"
}
```

Здесь:

```text
30000 ms = 30 секунд
```

То есть сообщение имеет TTL 30 секунд.

---

# TTL на уровне Queue

TTL можно задать и через аргументы очереди.

Например:

```python
queue_arguments = {
    "x-message-ttl": 30000
}
```

Это означает:

```text
Сообщения в этой Queue
имеют TTL 30 секунд.
```

---

# Message TTL vs Queue TTL

Не путай эти понятия.

| Механизм               | Что ограничивает        |
| ---------------------- | ----------------------- |
| Message TTL            | время жизни сообщений   |
| Queue TTL / expiration | время жизни самой Queue |

Например:

```text
Message TTL = 30 секунд
```

означает:

> сообщение может устареть.

А:

```text
Queue expiration = 5 минут
```

относится к существованию самой очереди при соответствующей настройке.

---

# TTL + DLX

Одна из самых полезных комбинаций:

```text
TTL + Dead Letter Exchange
```

Она позволяет организовать задержку перед повторной обработкой.

Например:

```text
Main Queue
    ↓
ошибка
    ↓
Retry Queue
    ↓
TTL = 30 секунд
    ↓
DLX
    ↓
Main Queue
```

Получается:

```text
сообщение
   ↓
ошибка
   ↓
подождать 30 сек
   ↓
повторить обработку
```

---

# Пример Retry Queue

Допустим, основной Consumer получил:

```text
payment.created
```

Но внешний API временно недоступен.

Вместо бесконечного `requeue`:

```text
Consumer
   ↓ ошибка
Retry Queue
```

У Retry Queue:

```text
TTL = 30 секунд
```

После истечения TTL сообщение становится dead letter и через DLX возвращается в основную очередь.

```text
Main Queue
    ↓
Consumer
    ↓
❌ temporary error
    ↓
Retry Queue
    ↓
30 sec TTL
    ↓
DLX
    ↓
Main Queue
    ↓
Consumer
```

---

# Несколько Retry Queue

Можно сделать разные задержки:

```text
retry_5s
retry_30s
retry_5m
```

Например:

```text
1-я ошибка
    ↓
retry_5s
    ↓
5 секунд
    ↓
Main Queue

2-я ошибка
    ↓
retry_30s
    ↓
30 секунд
    ↓
Main Queue

3-я ошибка
    ↓
retry_5m
    ↓
5 минут
    ↓
Main Queue

4-я ошибка
    ↓
DLQ
```

Это простой вариант реализации backoff.

---

# TTL не равен точному таймеру

Важный нюанс для собеседования:

**TTL не следует воспринимать как гарантию того, что сообщение будет удалено ровно в момент `TTL`.**

RabbitMQ обрабатывает истечение TTL в рамках работы очереди и внутренней обработки истёкших сообщений.

Поэтому TTL лучше рассматривать как:

> **минимальное/целевое время жизни сообщения, а не высокоточный планировщик.**

Для точных задержек обычно используют специализированные механизмы.

---

# Что происходит с истёкшим сообщением

Есть два основных варианта.

### Без DLX

```text
Message
   ↓
TTL expired
   ↓
Message удаляется
```

### С DLX

```text
Message
   ↓
TTL expired
   ↓
Dead Letter Exchange
   ↓
Dead Letter Queue
```

Таким образом TTL может быть частью Retry/DLQ-механизма.

---

# TTL и ACK

TTL и ACK решают совершенно разные задачи.

### TTL

Отвечает:

> Сколько сообщение может оставаться актуальным?

### ACK

Отвечает:

> Успешно ли Consumer обработал сообщение?

Например:

```text
Message
   ↓
Consumer
   ↓
processing
   ↓
ACK
```

TTL здесь не заменяет ACK.

---

# Что если сообщение уже Consumer'ом?

Это важный нюанс.

TTL в первую очередь связан с сообщениями, находящимися в очереди.

Если сообщение уже доставлено Consumer и находится в состоянии:

```text
unacked
```

это уже другая стадия обработки.

Нельзя рассматривать TTL как универсальный timeout выполнения задачи Consumer.

Для ограничения времени обработки используются другие механизмы.

---

# TTL и Retry

TTL особенно полезен для временных ошибок:

```text
DB temporarily unavailable
API timeout
HTTP 503
HTTP 429
network error
```

Например:

```text
Consumer
   ↓
HTTP 503
   ↓
Retry Queue
   ↓
TTL 30 sec
   ↓
Main Queue
```

---

# TTL и бесконечный Retry

Нельзя просто сделать:

```text
error
 ↓
requeue
 ↓
error
 ↓
requeue
 ↓
error
 ↓
...
```

Получается бесконечный цикл.

Лучше:

```text
Attempt 1
   ↓
5 sec
   ↓
Attempt 2
   ↓
30 sec
   ↓
Attempt 3
   ↓
5 min
   ↓
DLQ
```

То есть:

**ограниченное количество попыток + задержка + DLQ.**

---

# TTL и Dead Letter

Важно понимать направление:

```text
TTL
 ↓
истечение сообщения
 ↓
dead lettering
 ↓
DLX
 ↓
Queue
```

DLX — это Exchange.

DLQ — это Queue.

Поэтому:

```text
TTL → DLX → DLQ
```

а не:

```text
TTL → DLQ напрямую
```

---

# TTL и приоритет

TTL не определяет приоритет сообщения.

Например:

```text
TTL = 60 секунд
```

не означает:

> это сообщение обработают первым.

TTL отвечает только за срок жизни.

Приоритет — отдельный механизм RabbitMQ.

---

# TTL и порядок сообщений

TTL может приводить к тому, что некоторые сообщения перестают быть актуальными раньше других.

Поэтому нельзя строить бизнес-логику на предположении:

> «Все сообщения будут обработаны строго в порядке публикации».

TTL может привести к удалению/Dead Letter сообщений.

---

# Практический пример

Есть очередь:

```text
order_notifications
```

Сообщения должны быть обработаны максимум за 10 минут.

Настраиваем:

```text
x-message-ttl = 600000
```

Получаем:

```text
Producer
   ↓
Exchange
   ↓
order_notifications
   ↓
Consumer
```

Если Consumer успел:

```text
Message
   ↓
process
   ↓
ACK
```

Если сообщение слишком долго ждало:

```text
Message
   ↓
TTL expired
   ↓
DLX / удаление
```

---

# TTL + Retry + DLQ

Продакшен-схема может выглядеть так:

```text
                 ┌──────────────┐
                 │  Main Queue  │
                 └──────┬───────┘
                        ↓
                    Consumer
                        │
                 ┌──────┴──────┐
                 │             │
              success        error
                 │             │
                ACK            ↓
                         Retry Queue
                              │
                           TTL 30s
                              │
                              ↓
                             DLX
                              │
                              ↓
                         Main Queue
                              │
                         повторная
                         обработка
                              │
                         после N попыток
                              ↓
                             DLQ
```

---

# TTL и Kafka Retention

Не путай RabbitMQ TTL с Kafka Retention.

### RabbitMQ TTL

Ограничивает время жизни сообщения:

```text
Message
   ↓
TTL
   ↓
expired
```

### Kafka Retention

Определяет, как долго Kafka хранит записи:

```text
Partition
   ↓
Retention
   ↓
старые записи удаляются
```

Kafka не удаляет сообщение потому, что Consumer его прочитал.

---

# TTL vs Kafka Retention

| RabbitMQ TTL                        | Kafka Retention                      |
| ----------------------------------- | ------------------------------------ |
| Время жизни сообщения               | Время хранения записи                |
| Может использоваться для Retry      | Определяет срок хранения event log   |
| Истёкшее сообщение может уйти в DLX | Старые записи удаляются по retention |
| Связан с очередями                  | Связан с partition/log               |

# 🎯 Частые вопросы на собеседовании

### Что такое TTL?

> TTL — Time-To-Live, время жизни сообщения или другого ресурса RabbitMQ в зависимости от настройки.

### Зачем нужен Message TTL?

> Чтобы ограничить время актуальности сообщения и автоматически обрабатывать просроченные сообщения.

### Можно ли использовать TTL для Retry?

Да. Частая схема:

```text
Retry Queue → TTL → DLX → Main Queue
```

### TTL удаляет сообщение?

Да, истёкшее сообщение может быть удалено; если настроен dead lettering, оно может быть направлено через DLX.

### TTL и ACK — это одно и то же?

Нет.

**TTL — срок жизни сообщения.**

**ACK — подтверждение успешной обработки Consumer.**

### TTL — это точный таймер?

Нет. TTL не следует использовать как механизм высокоточной задержки.

### Что будет при бесконечном Retry?

Можно получить бесконечный цикл и Retry Storm. Поэтому обычно ограничивают число попыток и после этого отправляют сообщение в DLQ.

### Для чего TTL используют вместе с DLX?

Для реализации задержки между попытками обработки:

```text
Retry Queue
    ↓
TTL
    ↓
DLX
    ↓
Main Queue
```

---

# 🧠 Итоговая схема

```text
Message
   │
   ├── TTL не истёк
   │       ↓
   │    Consumer
   │       ↓
   │      ACK
   │
   └── TTL истёк
           ↓
       ┌───┴────┐
       ↓        ↓
    Delete     DLX
                 ↓
                DLQ
```

А для Retry:

```text
Main Queue
    ↓
  error
    ↓
Retry Queue
    ↓
  TTL
    ↓
  DLX
    ↓
Main Queue
```

### Формула для собеседования

> **TTL ограничивает время жизни сообщения. После истечения TTL сообщение может быть удалено или dead-lettered через DLX. TTL часто используют вместе с Retry Queue и DLX для реализации задержки между повторными попытками обработки.**
