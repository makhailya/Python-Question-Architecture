# Retry в RabbitMQ 🔄

## 🎯 Ответ на собеседовании

**Retry — механизм повторной попытки обработки сообщения после временной ошибки.**

Например, Consumer не смог обратиться к внешнему API:

```text
Message
   ↓
Consumer
   ↓
API недоступен
   ↓
Retry
   ↓
повторная обработка
```

Retry нужен прежде всего для **временных ошибок**:

* временная недоступность БД;
* сетевой сбой;
* внешний API вернул `5xx`;
* временная перегрузка сервиса.

При постоянной ошибке бесконечно повторять сообщение нельзя. Обычно используют ограниченное количество попыток, после чего сообщение отправляют в **DLQ**.

Типичная схема:

```text
Main Queue
    ↓
Consumer
    ↓
ERROR
    ↓
Retry #1
    ↓
ERROR
    ↓
Retry #2
    ↓
ERROR
    ↓
Retry #3
    ↓
DLQ
```

---

## 🎤 Суперкоротко

> **Retry повторяет обработку сообщения при временной ошибке. Количество попыток ограничивают, а после исчерпания retry сообщение отправляют в DLQ.**

---

# Зачем нужен Retry

Не каждая ошибка означает, что сообщение плохое.

Например:

```text
Consumer
   ↓
Payment API
   ↓
HTTP 503
```

Причина может быть временной.

Через несколько секунд:

```text
Payment API
   ↓
HTTP 200
```

Поэтому логично попробовать ещё раз.

```text
Attempt 1 → 503
Attempt 2 → 503
Attempt 3 → 200
```

Сообщение успешно обработано.

---

# Retry vs повторная доставка

Не стоит полностью отождествлять эти понятия.

### Повторная доставка

RabbitMQ снова доставляет неподтверждённое сообщение.

Например:

```text
Queue
  ↓
Consumer
  ↓
💥 crash
  ↓
message redelivered
```

### Retry

Это уже **организованный механизм повторной попытки**, обычно с контролем:

* количества попыток;
* задержки;
* типа ошибки;
* конечного маршрута.

Например:

```text
Attempt 1
   ↓
wait 5 sec
   ↓
Attempt 2
   ↓
wait 30 sec
   ↓
Attempt 3
   ↓
DLQ
```

---

# Почему бесконечный requeue — плохой Retry

Наивная реализация:

```text
ERROR
 ↓
NACK + requeue=true
 ↓
Queue
 ↓
Consumer
 ↓
ERROR
 ↓
NACK + requeue=true
 ↓
Queue
 ↓
...
```

Проблема:

```text
CPU ↑
Network ↑
Queue processing ↑
```

И сообщение может бесконечно крутиться.

Поэтому Retry должен быть **ограниченным и контролируемым**.

---

# Количество попыток

Обычно задают максимальное число попыток.

Например:

```text
MAX_RETRIES = 3
```

Схема:

```text
Attempt 1
   ↓
ERROR
   ↓
Attempt 2
   ↓
ERROR
   ↓
Attempt 3
   ↓
ERROR
   ↓
DLQ
```

Если третья попытка успешна:

```text
Attempt 3
   ↓
SUCCESS
   ↓
ACK
```

---

# Retry с задержкой

Иногда нельзя сразу повторять запрос.

Например:

```text
Payment API → 503
```

Бессмысленно делать:

```text
retry
retry
retry
retry
```

мгновенно.

Лучше:

```text
Attempt 1
   ↓
wait 5 sec
   ↓
Attempt 2
   ↓
wait 30 sec
   ↓
Attempt 3
```

Такой подход называется **delayed retry**.

---

# Exponential Backoff

Один из распространённых вариантов — **экспоненциальная задержка**.

Например:

```text
Retry 1 → 1 сек
Retry 2 → 2 сек
Retry 3 → 4 сек
Retry 4 → 8 сек
Retry 5 → 16 сек
```

Формула может выглядеть примерно так:

```text
delay = base × 2^attempt
```

Например:

```text
base = 1

attempt 0 → 1 sec
attempt 1 → 2 sec
attempt 2 → 4 sec
attempt 3 → 8 sec
```

В production часто добавляют **jitter** — случайную небольшую составляющую.

Это уменьшает ситуацию, когда тысячи сообщений одновременно повторяются после одинаковой задержки.

---

# Почему нужен Backoff

Представим внешний сервис временно недоступен.

Без backoff:

```text
1000 сообщений
     ↓
1000 retry
     ↓
сервис перегружен
     ↓
ошибка
     ↓
1000 retry
     ↓
...
```

Получается дополнительная нагрузка на уже проблемный сервис.

С backoff:

```text
1000 сообщений
      ↓
постепенные retry
      ↓
нагрузка распределяется
```

---

# Retry Queue

Один из способов реализовать задержку — отдельная Retry Queue.

Схема:

```text
Main Queue
    ↓
Consumer
    ↓
ERROR
    ↓
Retry Queue
    ↓
ожидание
    ↓
Main Queue
```

Например:

```text
main_queue
    ↓
retry_queue_30s
    ↓
30 секунд
    ↓
main_queue
```

После нескольких попыток:

```text
main_queue
    ↓
retry_queue
    ↓
retry_queue
    ↓
retry_queue
    ↓
DLQ
```

---

# Retry Queue + TTL

В RabbitMQ задержку можно организовать с использованием **TTL** и dead-letter routing.

Например:

```text
retry_queue
    ↓
TTL = 30 секунд
    ↓
DLX
    ↓
main_queue
```

Получается:

```text
Main Queue
    ↓
Consumer
    ↓
ERROR
    ↓
Retry Queue
    ↓
30 sec
    ↓
DLX
    ↓
Main Queue
```

Это позволяет не делать мгновенный `requeue`.

---

# Несколько Retry Queue

Можно использовать разные задержки:

```text
main_queue
    ↓
retry_5s
    ↓
retry_30s
    ↓
retry_5m
    ↓
DLQ
```

Например:

```text
Attempt 1 → ошибка
       ↓
5 секунд
       ↓
Attempt 2 → ошибка
       ↓
30 секунд
       ↓
Attempt 3 → ошибка
       ↓
5 минут
       ↓
Attempt 4 → ошибка
       ↓
DLQ
```

---

# Retry и тип ошибки

Не каждую ошибку стоит повторять.

Например:

### Временная ошибка

```text
HTTP 503
Connection timeout
Database temporarily unavailable
```

Можно retry.

### Постоянная ошибка

```text
Invalid JSON
Invalid order_id
Missing required field
Business rule violation
```

Бесконечный retry обычно бессмысленен.

Лучше:

```text
ERROR
 ↓
DLQ
```

---

# Retryable vs Non-Retryable

Удобно разделять ошибки:

| Ошибка                    | Retry               |
| ------------------------- | ------------------- |
| Network timeout           | ✅                   |
| HTTP 503                  | ✅                   |
| HTTP 429                  | ✅ с backoff         |
| Database connection error | ✅                   |
| Invalid JSON              | ❌                   |
| Некорректные данные       | ❌                   |
| Нарушение бизнес-правила  | ❌                   |
| Несуществующий ресурс     | зависит от сценария |

Главная идея:

> **Retry имеет смысл для ошибок, которые потенциально могут исчезнуть.**

---

# Retry и HTTP 429

Например, внешний API вернул:

```text
HTTP 429 Too Many Requests
```

Это означает, что запросов слишком много.

Неправильно:

```text
429
 ↓
retry immediately
 ↓
429
 ↓
retry immediately
 ↓
429
```

Лучше использовать:

```text
429
 ↓
backoff
 ↓
retry
```

Если API передаёт `Retry-After`, его также можно учитывать.

---

# Retry и HTTP 5xx

Например:

```text
HTTP 503 Service Unavailable
```

Это часто временная ошибка.

Можно:

```text
503
 ↓
Retry
```

Но количество попыток должно быть ограничено.

---

# Retry и ACK

Очень важно понимать порядок.

### Успех

```text
Message
   ↓
Consumer
   ↓
обработка
   ↓
SUCCESS
   ↓
ACK
```

### Ошибка + Retry

```text
Message
   ↓
Consumer
   ↓
ERROR
   ↓
Retry
```

ACK при этом не должен подтверждать неуспешную обработку как окончательно завершённую.

---

# Retry и DLQ

Эти механизмы дополняют друг друга.

```text
Retry
  ↓
повторить несколько раз
  ↓
всё ещё ошибка
  ↓
DLQ
```

То есть:

**Retry отвечает на вопрос:**

> Попробовать ещё раз?

**DLQ отвечает на вопрос:**

> Что делать, если нормальная обработка так и не удалась?

---

# Retry и идемпотентность

Retry означает повторную обработку.

Следовательно, Consumer должен учитывать возможность повторного выполнения бизнес-операции.

Например:

```text
Message
   ↓
создать заказ
   ↓
ошибка
   ↓
Retry
   ↓
создать заказ ещё раз
```

Без идемпотентности можно получить:

```text
Order #100
Order #100
```

или два одинаковых платежа.

Поэтому часто используют:

* `message_id`;
* `idempotency_key`;
* уникальные ограничения БД;
* таблицу обработанных сообщений;
* upsert.

Например:

```text
message_id = abc123
```

Consumer проверяет:

```text
abc123 уже обработан?
```

Если да:

```text
не выполнять операцию повторно
```

---

# Retry и транзакция БД

Допустим, Consumer получает сообщение:

```text
OrderCreated
```

и обновляет БД.

Надёжная последовательность:

```text
Message
   ↓
Consumer
   ↓
BEGIN
   ↓
DB operation
   ↓
COMMIT
   ↓
ACK
```

При ошибке:

```text
Message
   ↓
Consumer
   ↓
DB operation
   ↓
ERROR
   ↓
ROLLBACK
   ↓
Retry
```

Это предотвращает подтверждение сообщения до успешного завершения бизнес-операции.

---

# Retry Storm

**Retry storm** — ситуация, когда большое количество сообщений одновременно начинает повторно обрабатываться.

Например:

```text
External API
     ↓
     503
     ↓
100 000 messages
     ↓
100 000 retries
```

Если retry выполняется сразу:

```text
API overload
     ↓
503
     ↓
Retry
     ↓
API overload
     ↓
503
```

Возникает положительная обратная связь.

Для борьбы используют:

* exponential backoff;
* jitter;
* ограничение retry;
* rate limiting;
* circuit breaker;
* DLQ.

---

# Retry и Circuit Breaker

Это разные механизмы.

### Retry

> Попробовать операцию ещё раз.

### Circuit Breaker

> Временно перестать отправлять запросы в явно неработающий сервис.

Например:

```text
API
 ↓
ошибки
 ↓
Circuit Breaker OPEN
 ↓
запросы временно не отправляются
```

После паузы система проверяет:

```text
API восстановился?
```

Если да:

```text
Circuit Breaker → CLOSED
```

Retry и Circuit Breaker часто используются вместе.

# 🎯 Частые вопросы на собеседовании

### Что такое Retry?

Retry — повторная попытка обработки сообщения после временной ошибки.

### Зачем нужен Retry?

Чтобы переживать временные сбои без потери сообщения.

### Нужно ли делать retry для любой ошибки?

Нет. Retry имеет смысл прежде всего для временных ошибок.

### Почему нельзя бесконечно использовать requeue?

Это может создать бесконечный цикл и значительно увеличить нагрузку на систему.

### Что такое exponential backoff?

Стратегия, при которой задержка между повторными попытками постепенно увеличивается.

### Зачем нужен jitter?

Чтобы избежать синхронных повторных запросов большого количества workers.

### Что делать после исчерпания retry?

Обычно отправить сообщение в DLQ и отдельно разобраться с причиной ошибки.

### Чем Retry отличается от DLQ?

> **Retry повторяет обработку, DLQ изолирует сообщение, которое не удалось обработать.**

### Что такое Retry Storm?

Массовые повторные попытки, которые сами создают дополнительную нагрузку и могут усугубить исходную проблему.

### Почему важна идемпотентность?

Потому что retry может привести к повторному выполнению одной и той же бизнес-операции.

# 🧠 Итоговая схема

```text
                         Main Queue
                              │
                              ▼
                           Consumer
                              │
                         ┌────┴────┐
                         │         │
                       успех     ошибка
                         │         │
                        ACK        │
                                   ▼
                                 Retry
                                   │
                          ┌────────┴────────┐
                          │                 │
                       успех             ошибка
                          │                 │
                         ACK                ▼
                                      следующий Retry
                                           │
                                      после N попыток
                                           │
                                           ▼
                                          DLQ
```

### Формула для собеседования

> **Retry используется для временных ошибок. Повторные попытки должны иметь ограничение и обычно использовать backoff. После исчерпания retry сообщение отправляют в DLQ. Поскольку retry может привести к повторной обработке, Consumer должен быть идемпотентным.**

```text
Temporary error
      ↓
Retry
      ↓
Backoff
      ↓
Retry
      ↓
N attempts
      ↓
DLQ
```
