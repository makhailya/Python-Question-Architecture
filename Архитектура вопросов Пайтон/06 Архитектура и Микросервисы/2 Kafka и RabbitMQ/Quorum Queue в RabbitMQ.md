# Quorum Queue в RabbitMQ 🛡️

## 🎯 Ответ на собеседовании

**Quorum Queue — это реплицируемый тип очереди RabbitMQ, предназначенный для повышения отказоустойчивости. Данные очереди хранятся на нескольких узлах кластера, поэтому отказ одного узла не обязательно приводит к потере доступности очереди.**

Quorum Queue построена на алгоритме **Raft** и использует несколько реплик.

Главная идея:

```text
Обычная Queue
    ↓
один узел
    ↓
отказ узла = проблема

Quorum Queue
    ↓
несколько узлов
    ↓
отказ части узлов = очередь может продолжить работу
```

**Quorum Queue ≠ просто Durable Queue.**

`Durable` означает сохранение очереди после перезапуска брокера.

`Quorum` означает **репликацию и отказоустойчивость внутри кластера**.

---

## 🎤 Суперкоротко

```text
Quorum Queue
      ↓
несколько реплик
      ↓
RabbitMQ Cluster
      ↓
Raft
      ↓
отказ части узлов
      ↓
очередь продолжает работу
```

---

# Зачем нужна Quorum Queue

Представим RabbitMQ Cluster:

```text
       RabbitMQ Cluster

    Node 1    Node 2    Node 3
       │         │         │
       └────┬────┴────┬────┘
            │
       Quorum Queue
```

Если очередь существует только на одном узле:

```text
Queue
  ↓
Node 1
```

и Node 1 выходит из строя, доступность очереди может быть потеряна.

Quorum Queue решает эту задачу за счёт репликации.

---

# Репликация

Допустим, у нас:

```text
replication factor = 3
```

Получаем:

```text
Node 1 → Replica
Node 2 → Replica
Node 3 → Replica
```

Условно:

```text
             Quorum Queue
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Node 1    Node 2    Node 3
       copy      copy      copy
```

При отказе одного узла остальные реплики могут продолжить работу.

---

# Что такое Quorum

Quorum — это большинство реплик.

Для трёх реплик:

```text
3 реплики
↓
quorum = 2
```

То есть большинство составляет:

```text
2 из 3
```

Для пяти:

```text
5 реплик
↓
quorum = 3
```

Общая идея:

```text
quorum = большинство
```

Это позволяет системе принимать решения даже при отказе части узлов.

---

# Raft

Quorum Queue использует алгоритм консенсуса **Raft**.

Raft позволяет репликам согласованно определять состояние очереди.

Упрощённо:

```text
Leader
   │
   ├──→ Follower
   │
   └──→ Follower
```

Один экземпляр является лидером, остальные поддерживают реплику состояния.

---

# Leader

У Quorum Queue есть Leader.

Упрощённо:

```text
              Leader
             /      \
            ↓        ↓
        Follower   Follower
```

Операции проходят через Leader и реплицируются.

Если Leader становится недоступен, кластер может выбрать нового Leader при наличии необходимого большинства.

---

# Что происходит при падении Leader

Например:

```text
Node 1 → Leader
Node 2 → Follower
Node 3 → Follower
```

Node 1 выходит из строя:

```text
Node 1 → ❌
Node 2 → Follower
Node 3 → Follower
```

При наличии quorum:

```text
Node 2 + Node 3
       ↓
 новый Leader
```

Очередь может продолжить работу.

---

# Quorum Queue vs Durable Queue

Это очень важное различие.

## Durable Queue

```text
durable = true
```

означает:

> Очередь должна пережить перезапуск RabbitMQ.

Но это не означает автоматическую репликацию между узлами.

---

## Quorum Queue

Предназначена для:

> репликации данных и высокой отказоустойчивости в RabbitMQ Cluster.

---

# Сравнение

| Durable Queue                     | Quorum Queue                    |
| --------------------------------- | ------------------------------- |
| Переживает restart                | Реплицируется                   |
| Может находиться на одном узле    | Несколько реплик                |
| Не является механизмом consensus  | Использует Raft                 |
| Дешевле                           | Больше ресурсов                 |
| Не решает отказ узла сама по себе | Предназначена для node failures |

Поэтому:

```text
Durable
≠
Highly Available
```

---

# Persistent Message и Quorum Queue

Эти механизмы тоже нельзя путать.

### Persistent Message

Относится к сохранению сообщения.

```text
Message
   ↓
persistent
```

### Quorum Queue

Относится к архитектуре самой очереди:

```text
Queue
 ↓
replicas
 ↓
nodes
```

Они решают разные задачи.

---

# Publisher Confirm + Quorum Queue

Эти механизмы хорошо работают вместе.

Например:

```text
Producer
   ↓
publish
   ↓
Quorum Queue
   ↓
replication
   ↓
Publisher Confirm
```

Producer получает подтверждение публикации согласно семантике Publisher Confirms.

Но:

> **Publisher Confirm не означает, что Consumer обработал сообщение.**

Это всё ещё только подтверждение на стороне публикации.

---

# Consumer ACK + Quorum Queue

ACK находится уже на другом этапе:

```text
Producer
   ↓
RabbitMQ
   ↓
Quorum Queue
   ↓
Consumer
   ↓
processing
   ↓
ACK
```

Получается:

```text
Publisher Confirm
→ подтверждение публикации

Consumer ACK
→ подтверждение обработки
```

---

# Полная цепочка надёжности

Для критичного сообщения можно получить примерно такую архитектуру:

```text
Producer
   │
   │ publish
   ▼
Exchange
   │
   ▼
Quorum Queue
   │
   ├── Replica 1
   ├── Replica 2
   └── Replica 3
   │
   ▼
Consumer
   │
   ▼
DB transaction
   │
   ▼
COMMIT
   │
   ▼
ACK
```

А Producer контролирует публикацию через:

```text
Publisher Confirm
```

---

# Quorum Queue и потеря узла

Представим три реплики:

```text
Node 1
Node 2
Node 3
```

Отказал:

```text
Node 1 ❌
```

Остаются:

```text
Node 2
Node 3
```

Большинство всё ещё существует:

```text
2 / 3
```

Поэтому система может продолжить работу.

---

# А если потеряли большинство?

Например:

```text
Node 1 ❌
Node 2 ❌
Node 3
```

Осталась:

```text
1 / 3
```

Это уже не quorum.

В таком случае RabbitMQ не может просто продолжать работу так, будто всё нормально.

Это принципиальный момент:

> **Quorum Queue защищает от отказа части узлов, но не от потери большинства.**

---

# Почему нельзя просто сделать 2 реплики

Для quorum-систем обычно предпочтительнее нечётное число реплик:

```text
3
5
7
```

Например:

```text
3 replicas
→ можно потерять 1

5 replicas
→ можно потерять 2
```

При этом большее количество реплик увеличивает расходы на:

* сеть;
* storage;
* replication;
* CPU;
* latency.

Поэтому просто увеличивать число реплик бесконечно не имеет смысла.

---

# Quorum Queue и производительность

Репликация имеет стоимость.

При записи необходимо поддерживать согласованное состояние реплик.

Это означает дополнительные:

```text
network I/O
storage I/O
CPU
```

Поэтому Quorum Queue обычно выбирают там, где:

> **надёжность важнее минимальной latency и максимальной производительности.**

---

# Quorum Queue и обычная Queue

Упрощённо:

```text
Classic Queue

Producer
   ↓
Node
   ↓
Queue
   ↓
Consumer
```

Quorum Queue:

```text
Producer
   ↓
Leader
   ├── Replica
   ├── Replica
   └── Replica
   ↓
Consumer
```

---

# Quorum Queue и Cluster

Важно различать:

### RabbitMQ Cluster

Это несколько RabbitMQ nodes:

```text
Node 1
Node 2
Node 3
```

### Quorum Queue

Это конкретный тип Queue, который использует репликацию внутри кластера.

То есть:

```text
RabbitMQ Cluster
        ↓
Quorum Queue
        ↓
несколько реплик
```

Сам факт наличия RabbitMQ Cluster **не означает, что каждая Queue автоматически становится quorum queue**.

---

# Quorum Queue и Exchange

Exchange сам по себе не является хранилищем сообщений.

Схема:

```text
Producer
   ↓
Exchange
   ↓
Quorum Queue
```

Exchange занимается маршрутизацией.

Quorum Queue занимается хранением и репликацией сообщений.

---

# Quorum Queue и DLQ

Quorum Queue можно использовать как Queue для:

* основной обработки;
* Retry;
* DLQ.

Например:

```text
Main Quorum Queue
       ↓
    Consumer
       ↓
     error
       ↓
    Retry
       ↓
      DLX
       ↓
   Quorum DLQ
```

Конкретная архитектура зависит от требований к надёжности.

---

# Quorum Queue и TTL

TTL тоже может использоваться вместе с Quorum Queue.

Например:

```text
Main Queue
    ↓
Retry Queue
    ↓
TTL
    ↓
DLX
    ↓
Main Queue
```

При этом Retry Queue может быть quorum queue, если её сообщения также критичны и требуют повышенной отказоустойчивости.

---

# Quorum Queue и Priority

Это отдельная тема.

Не следует делать вывод:

```text
Quorum Queue
=
Priority Queue
```

Нет.

```text
Quorum
→ отказоустойчивость

Priority
→ порядок предпочтительной доставки
```

---

# Когда использовать Quorum Queue

Хороший кандидат:

* платежи;
* заказы;
* критичные бизнес-события;
* задачи, потеря которых недопустима;
* системы с требованиями к высокой доступности;
* production RabbitMQ Cluster.

Например:

```text
Payment Service
       ↓
RabbitMQ
       ↓
Quorum Queue
       ↓
Payment Consumer
```

---

# Когда можно использовать другую Queue

Если задача:

* некритичная;
* легко восстанавливается;
* допускает потерю;
* требует максимальной производительности;
* не нуждается в репликации;

можно рассматривать другие варианты Queue.

Выбор зависит от требований системы.

---

# Quorum Queue и Exactly Once

Очень важный момент:

**Quorum Queue не гарантирует Exactly Once Processing.**

Даже при:

```text
Quorum Queue
+
Publisher Confirm
+
Consumer ACK
```

возможны повторные доставки.

Например:

```text
Consumer
   ↓
обработал сообщение
   ↓
DB COMMIT
   ↓
💥 crash
   ↓
ACK не дошёл
```

RabbitMQ может доставить сообщение снова.

Поэтому:

```text
Quorum Queue
+
At-least-once
+
Idempotency
```

часто являются частью надёжной архитектуры.

---

# Типичный вопрос: «Зачем Quorum Queue, если есть Persistent Message?»

Правильный ответ:

> **Persistent Message помогает сохранять сообщение, а Quorum Queue реплицирует состояние очереди между узлами для отказоустойчивости. Это разные уровни защиты.**

---

# Типичный вопрос: «Durable Queue достаточно для HA?»

Нет.

```text
Durable
→ пережить restart

Quorum
→ репликация и отказоустойчивость
```

Durable сам по себе не означает полноценную high availability.

---

# Типичный вопрос: «Что будет при падении одного узла?»

Если остаётся quorum:

```text
Replica 1 ❌
Replica 2 ✅
Replica 3 ✅
```

Quorum Queue может продолжить работу и выбрать нового Leader при необходимости.

---

# Типичный вопрос: «Что будет при потере большинства?»

Если quorum потерян:

```text
1 / 3
```

очередь не может продолжать операции, требующие согласованного большинства, как будто ничего не произошло.

Это цена консенсуса:

> **Лучше остановиться, чем принять потенциально противоречивое состояние.**

---

# 🧠 Главное сравнение RabbitMQ-механизмов

```text
Durable Queue
    ↓
пережить restart

Persistent Message
    ↓
сохранить сообщение

Publisher Confirm
    ↓
подтвердить публикацию

Consumer ACK
    ↓
подтвердить обработку

Quorum Queue
    ↓
репликация + отказоустойчивость

TTL
    ↓
срок жизни сообщения

DLX / DLQ
    ↓
обработка проблемных сообщений

Priority
    ↓
предпочтительный порядок доставки

Prefetch
    ↓
сколько сообщений можно выдать заранее
```

# 🎯 Формула для собеседования

> **Quorum Queue — реплицируемый тип очереди RabbitMQ, предназначенный для высокой отказоустойчивости. Она использует алгоритм Raft и хранит состояние на нескольких узлах кластера. При отказе части узлов очередь может продолжить работу при сохранении quorum. Quorum Queue отличается от Durable Queue: durable защищает от потери очереди при restart, а quorum обеспечивает репликацию и устойчивость к отказу узлов.**
