# 📨 Брокеры сообщений

## 🎯 Ответ на собеседовании

**Брокер сообщений** — это промежуточный компонент, который принимает сообщения от одного сервиса, временно хранит их и передаёт другим сервисам-получателям.

Он позволяет организовать **асинхронное взаимодействие** между компонентами системы.

Например:

```text
Order Service
      │
      │ message
      ↓
 Message Broker
      │
      ├────→ Notification Service
      │
      └────→ Analytics Service
```

Вместо прямого вызова одного сервиса другим отправитель передаёт сообщение брокеру, а получатель обрабатывает его позже.

Примеры брокеров сообщений: **RabbitMQ, Apache Kafka, Redis Streams, NATS**.

---

## 🎤 Суперкоротко

**Брокер сообщений — это посредник между сервисами, который принимает, хранит и доставляет сообщения, позволяя организовать асинхронное взаимодействие и уменьшить связанность сервисов.**

---

## 🔄 Зачем нужен брокер

Без брокера:

```text
Order Service
      │
      │ HTTP
      ↓
Notification Service
```

Order Service должен знать:

* где находится Notification Service;
* как вызвать его API;
* что делать при его недоступности;
* как повторить запрос.

С брокером:

```text
Order Service
      │
      ↓
   RabbitMQ
      │
      ↓
Notification Service
```

Order Service просто публикует сообщение.

---

## ⚙️ Как это работает

Упрощённая схема:

```text
Producer
   │
   │ message
   ↓
Broker
   │
   │ message
   ↓
Consumer
```

### Producer

**Producer** — сервис, который отправляет сообщение.

```text
Order Service → message
```

### Broker

**Broker** принимает сообщение и управляет его доставкой.

```text
message
   ↓
Broker
```

### Consumer

**Consumer** — сервис, который получает и обрабатывает сообщение.

```text
Broker → Notification Service
```

---

## 📨 Что такое сообщение

Сообщение содержит данные, необходимые для обработки события или команды.

Например:

```python
{
    "event": "order_created",
    "order_id": 123,
    "user_id": 456
}
```

На практике формат зависит от брокера и системы. Это может быть JSON, Protobuf или другой формат.

---

## 🧵 Очередь сообщений

Один из основных механизмов — **очередь**.

```text
Producer
   │
   ├── Message 1
   ├── Message 2
   └── Message 3
          ↓
      ┌─────────┐
      │ Queue   │
      └────┬────┘
           ↓
        Consumer
```

Сообщения помещаются в очередь и обрабатываются consumer'ами.

---

## 👥 Несколько Consumer

Можно запустить несколько экземпляров одного сервиса:

```text
             ┌──→ Consumer 1
             │
Queue ───────┼──→ Consumer 2
             │
             └──→ Consumer 3
```

Это позволяет распределять нагрузку.

Например, если обработка одного сообщения занимает много времени, можно увеличить количество consumer'ов.

---

## 🔀 Очередь vs Pub/Sub

Это важное различие.

### Queue

Сообщение обычно обрабатывается **одним consumer'ом** из группы.

```text
             ┌──→ Consumer 1
             │
Queue ───────┼──→ Consumer 2
             │
             └──→ Consumer 3
```

Одно сообщение достаёт один consumer.

### Pub/Sub

Одно событие получают **несколько независимых подписчиков**.

```text
                 ┌──→ Notification
                 │
Event ─→ Broker ─┼──→ Analytics
                 │
                 └──→ Email Service
```

Каждый подписчик получает событие и обрабатывает его самостоятельно.

---

## 🔥 Пример из интернет-магазина

Пользователь создаёт заказ.

```text
Client
  ↓
Order Service
  ↓
Message Broker
  ├──→ Email Service
  ├──→ Notification Service
  └──→ Analytics Service
```

Order Service публикует событие:

```python
{
    "event": "order_created",
    "order_id": 123
}
```

Дальше разные сервисы самостоятельно реагируют на это событие.

Order Service при этом не должен ждать завершения отправки email или аналитики.

---

## ⏱️ Синхронное vs асинхронное взаимодействие

### Синхронное

```text
Order Service
      │
      │ HTTP
      ↓
Email Service
      │
      ↓
   response
```

Order Service ждёт ответ.

### Асинхронное

```text
Order Service
      │
      ↓
Message Broker
      │
      ↓
Email Service
```

Order Service отправил сообщение и может продолжить работу.

---

## 🛡️ Что происходит при падении Consumer

Одна из важных возможностей брокера — возможность **не потерять сообщение**, если consumer временно недоступен.

Упрощённо:

```text
Producer
   ↓
Queue
   ↓
Consumer ❌
```

Сообщение остаётся в очереди и может быть обработано после восстановления consumer.

Конкретное поведение зависит от брокера и настроек подтверждения доставки.

---

## ✅ ACK

**ACK (acknowledgement)** — подтверждение успешной обработки сообщения.

```text
Broker
   ↓ message
Consumer
   ↓
обработка
   ↓
ACK
   ↓
Broker
```

После успешного ACK брокер может удалить сообщение из очереди.

Если consumer завершился с ошибкой до подтверждения, брокер в зависимости от конфигурации может вернуть сообщение в очередь или применить другую политику обработки.

---

## 🔁 Retry

Если обработка сообщения завершилась ошибкой, можно повторить попытку.

```text
Message
   ↓
Consumer
   ↓
Ошибка
   ↓
Retry
   ↓
Consumer
```

Например:

```text
1-я попытка ❌
2-я попытка ❌
3-я попытка ✅
```

Часто используется **exponential backoff** — увеличение интервала между попытками.

---

## 💀 Dead Letter Queue

Если сообщение невозможно обработать после определённого количества попыток, его можно отправить в **Dead Letter Queue (DLQ)**.

```text
Queue
  ↓
Consumer
  ↓
❌
  ↓
Retry
  ↓
❌
  ↓
DLQ
```

DLQ позволяет отдельно анализировать проблемные сообщения, не блокируя основную очередь.

---

## 📦 RabbitMQ

**RabbitMQ** — классический брокер сообщений, широко используемый для очередей и асинхронных задач.

Упрощённая схема:

```text
Producer
   ↓
Exchange
   ↓
Queue
   ↓
Consumer
```

### Exchange

**Exchange** принимает сообщения от producer и определяет, в какие очереди их направить.

Основные типы:

* Direct;
* Fanout;
* Topic;
* Headers.

---

## 🦁 Apache Kafka

**Apache Kafka** — распределённая платформа потоковой передачи событий.

Упрощённо:

```text
Producer
   ↓
Kafka Topic
   ↓
Consumer
```

Kafka особенно хорошо подходит для:

* больших потоков событий;
* event streaming;
* аналитики;
* интеграции большого количества сервисов;
* хранения событий определённое время.

В Kafka сообщения записываются в **топики**, которые разделены на **партиции**.

---

## 🆚 RabbitMQ vs Kafka

| RabbitMQ                                   | Kafka                                  |
| ------------------------------------------ | -------------------------------------- |
| Классический message broker                | Event streaming platform               |
| Очереди и маршрутизация                    | Topics и partitions                    |
| Сильный акцент на доставке сообщений       | Сильный акцент на потоках событий      |
| Сообщение обычно удаляется после обработки | Сообщения хранятся по retention policy |
| Удобен для task queues                     | Хорош для event streaming              |
| Сложная маршрутизация через exchanges      | Высокая пропускная способность         |

Важно: Kafka тоже может использоваться как механизм асинхронного взаимодействия, но её модель отличается от классической очереди RabbitMQ.

---

## 🐍 Брокеры и Python

В Python брокеры часто используются вместе с **Celery**.

Например:

```text
FastAPI
   │
   │ отправляет задачу
   ↓
RabbitMQ / Redis
   │
   ↓
Celery Worker
   │
   ↓
Выполнение задачи
```

Например, пользователь зарегистрировался:

```text
FastAPI
   ↓
"Отправить email"
   ↓
Broker
   ↓
Celery Worker
   ↓
Email
```

HTTP-запросу не нужно ждать выполнения долгой задачи.

## ⚠️ Проблемы, которые нужно учитывать

При работе с брокерами появляются вопросы распределённых систем:

* повторная доставка;
* дубликаты сообщений;
* порядок сообщений;
* потеря сообщений;
* retry;
* идемпотентность;
* ACK;
* DLQ;
* мониторинг очередей;
* backpressure.

### Идемпотентность

Consumer должен по возможности корректно обрабатывать повторное сообщение.

Например:

```text
Message: create_payment(order_id=123)

Получили два раза
       ↓
Не должны создать две оплаты
```

Поэтому обработчики часто делают **идемпотентными**.

---

## 🧠 Брокер уменьшает связанность

Без брокера:

```text
Order
 ├──→ Email
 ├──→ Analytics
 └──→ Notification
```

Order Service знает о других сервисах.

С брокером:

```text
                ┌──→ Email
                │
Order → Broker ─┼──→ Analytics
                │
                └──→ Notification
```

Order Service знает только о брокере и формате события.

Это уменьшает **coupling** между сервисами.

---

## 🎯 Главное

```text
Producer
    ↓
Message
    ↓
Message Broker
    ↓
Queue / Topic
    ↓
Consumer
    ↓
Processing
    ↓
ACK
```

Брокер сообщений позволяет:

* асинхронно взаимодействовать сервисам;
* буферизовать нагрузку;
* распределять задачи между consumer'ами;
* делать retry;
* использовать DLQ;
* уменьшать связанность сервисов;
* строить event-driven архитектуру.

### Формула для собеседования

**Брокер сообщений = [[Producer]] → Broker → [[Consumer в Kafka]]**

**[[RabbitMQ]]** — классический брокер очередей и маршрутизации.

**[[Kafka]]** — распределённая платформа для потоковой передачи и хранения событий.

**Главная идея:** сервис не обязан напрямую ждать другой сервис — он может передать сообщение брокеру, а обработка произойдёт асинхронно.
