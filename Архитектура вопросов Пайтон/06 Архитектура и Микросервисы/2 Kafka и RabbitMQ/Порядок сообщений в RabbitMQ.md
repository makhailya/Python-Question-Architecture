# Порядок сообщений в RabbitMQ 📋

## 🎯 Ответ на собеседовании

**RabbitMQ в рамках одной [[Queue]] обычно доставляет сообщения в порядке FIFO, но строгий порядок обработки не гарантируется при наличии нескольких Consumer'ов, [[Prefetch]], повторных доставок и Priority.**

Важно различать:

* порядок публикации;
* порядок нахождения сообщений в Queue;
* порядок доставки Consumer'ам;
* порядок завершения обработки.

Для строгого последовательного обработки обычно нужен **один Consumer** и отсутствие механизмов, нарушающих последовательность, либо специальная архитектура.

---

## 🎤 Суперкоротко

```text
Одна Queue + один Consumer
        ↓
     FIFO проще сохранить

Одна Queue + несколько Consumer
        ↓
   порядок обработки
     не гарантирован
```

Главная мысль:

> **RabbitMQ не гарантирует глобальный порядок обработки сообщений.**

---

# Что такое FIFO

FIFO:

**First In → First Out**

То есть:

```text
A
B
C
```

приходят в таком порядке:

```text
A → B → C
```

Это естественная модель обычной очереди.

---

# Простая Queue

Представим:

```text
Producer
   ↓
Queue
   │
   ├── A
   ├── B
   └── C
   ↓
Consumer
```

Один Consumer получает:

```text
A → B → C
```

Это наиболее простой сценарий сохранения порядка.

---

# Один Consumer

При одном Consumer:

```text
Queue
   ↓
Consumer
```

сообщения обычно доставляются последовательно:

```text
A
↓
B
↓
C
```

Если обработка также последовательная:

```text
A → обработка
B → обработка
C → обработка
```

то порядок завершения сохраняется.

---

# Несколько Consumer

Теперь:

```text
Queue
   ↓
┌───────────┐
│           │
Consumer 1  Consumer 2
```

RabbitMQ распределяет сообщения между Consumer'ами.

Например:

```text
A → Consumer 1
B → Consumer 2
C → Consumer 1
D → Consumer 2
```

Теперь обработка может завершиться:

```text
B → A → D → C
```

Поэтому:

> **При нескольких Consumer строгий порядок обработки не гарантируется.**

---

# Почему несколько Consumer нарушают порядок

Допустим:

```text
A → Consumer 1
B → Consumer 2
```

Consumer 1 выполняет:

```text
A → 10 секунд
```

Consumer 2:

```text
B → 1 секунда
```

Получаем:

```text
B завершён
A завершён
```

Хотя:

```text
A был опубликован раньше B
```

То есть:

```text
порядок доставки
    ≠
порядок завершения
```

---

# Delivery Order vs Processing Order

Это важное различие.

### Delivery Order

Порядок, в котором RabbitMQ доставляет сообщения Consumer'ам.

### Processing Order

Порядок, в котором приложение фактически выполняет/завершает обработку.

Например:

```text
Queue:

A
B
C
```

RabbitMQ может доставить:

```text
A → Consumer 1
B → Consumer 2
```

Но:

```text
B обработан
A обработан
```

---

# ACK и порядок

ACK тоже влияет на поведение системы.

Например:

```text
A → Consumer
B → Consumer
```

Consumer может:

```text
A → обработка 10 сек
B → обработка 1 сек
```

Тогда:

```text
B → ACK
A → ACK
```

ACK не заставляет RabbitMQ ждать A перед обработкой B.

---

# Prefetch

`prefetch` определяет, сколько сообщений RabbitMQ может заранее доставить Consumer'у без ACK.

Например:

```text
prefetch = 10
```

Consumer может получить:

```text
A
B
C
D
...
```

заранее.

Если обработка выполняется параллельно, порядок завершения может отличаться.

```text
A → 10 sec
B → 2 sec
C → 1 sec

завершение:

C → B → A
```

---

# Prefetch = 1

При:

```text
prefetch = 1
```

Consumer получает следующее сообщение после подтверждения предыдущего.

Схематично:

```text
A
 ↓
processing
 ↓
ACK
 ↓
B
 ↓
processing
 ↓
ACK
 ↓
C
```

Это помогает контролировать последовательность обработки одним Consumer.

Но важно:

> `prefetch=1` сам по себе не является абсолютной гарантией глобального порядка всей системы.

---

# Priority нарушает обычный FIFO

Мы уже рассматривали Priority.

Например:

```text
A → priority=1
B → priority=10
C → priority=5
```

RabbitMQ может доставить:

```text
B → C → A
```

Поэтому:

```text
FIFO
+
Priority
```

нельзя рассматривать как строгий FIFO.

---

# Requeue

Теперь рассмотрим ошибку обработки.

```text
A
 ↓
Consumer
 ↓
ошибка
 ↓
requeue
```

Сообщение возвращается в Queue.

Его последующее положение/повторная доставка зависит от механики RabbitMQ и конкретной конфигурации.

Поэтому при использовании `requeue` нельзя строить бизнес-логику на строгом глобальном порядке.

---

# Redelivery

Если Consumer получил:

```text
A
```

но не отправил ACK и отключился:

```text
A
 ↓
Consumer
 ↓
💥 crash
```

RabbitMQ может доставить сообщение снова:

```text
A → Consumer 2
```

Получается:

```text
A
B
C
```

а затем:

```text
A → redelivery
```

Появляется повторная доставка.

Поэтому Consumer должен быть **идемпотентным**.

---

# RabbitMQ и порядок событий

Представим события пользователя:

```text
user.created
user.updated
user.deleted
```

Важно, чтобы они обрабатывались именно в этом порядке:

```text
created
   ↓
updated
   ↓
deleted
```

Если события попадут к разным Consumer'ам:

```text
Consumer 1 → created
Consumer 2 → updated
Consumer 1 → deleted
```

может возникнуть:

```text
updated
   ↓
created
```

с точки зрения завершения обработки.

Это может привести к неконсистентному состоянию.

---

# Как сохранять порядок

Если для конкретной сущности важен строгий порядок, часто используют:

```text
один последовательный Consumer
```

Например:

```text
Queue
 ↓
Consumer
 ↓
event 1
 ↓
event 2
 ↓
event 3
```

---

# Порядок только для одной сущности

Часто не требуется глобальный порядок всех сообщений.

Например:

```text
User 1:
A → B → C

User 2:
X → Y → Z
```

Нам важно сохранить порядок только внутри одного пользователя.

Можно архитектурно разделить потоки так, чтобы события одной сущности обрабатывались последовательно.

Это позволяет сохранить:

```text
User 1: A → B → C
```

при этом:

```text
User 2: X → Y → Z
```

может обрабатываться параллельно.

---

# RabbitMQ vs Kafka

Здесь важно сравнить модели.

### RabbitMQ

```text
Queue
   ↓
Consumer
```

Порядок зависит от:

* количества Consumer;
* prefetch;
* ACK;
* requeue;
* redelivery;
* priority;
* параллельности обработки.

### Kafka

Kafka гарантирует порядок:

> **внутри одной Partition.**

```text
Partition 0:

offset 0 → A
offset 1 → B
offset 2 → C
```

Consumer читает:

```text
A → B → C
```

в порядке offset.

Но между разными Partition глобального порядка нет.

---

# RabbitMQ Queue vs Kafka Partition

| RabbitMQ                                            | Kafka                                                    |
| --------------------------------------------------- | -------------------------------------------------------- |
| Queue                                               | Partition                                                |
| Обычно FIFO-модель                                  | Строгий порядок внутри Partition                         |
| Несколько Consumer могут нарушить порядок обработки | Один Consumer в группе обрабатывает конкретную Partition |
| ACK                                                 | Offset                                                   |
| Requeue / redelivery                                | Replay через offset                                      |
| Priority возможен                                   | Нет обычной priority queue                               |

---

# Порядок и масштабирование

Здесь возникает фундаментальный компромисс:

```text
Больше Consumer
      ↓
больше параллелизма
      ↓
меньше гарантий порядка
```

И наоборот:

```text
Один Consumer
      ↓
меньше параллелизма
      ↓
проще сохранить порядок
```

То есть:

> **Строгий порядок и максимальный throughput часто конфликтуют.**

---

# Почему нельзя просто добавить Consumer

Допустим:

```text
Queue
 ↓
Consumer 1
```

и порядок работает.

Добавляем:

```text
Consumer 2
```

Получаем:

```text
Queue
 ├──→ Consumer 1
 └──→ Consumer 2
```

Теперь задачи могут выполняться параллельно.

Если бизнес-логика зависит от порядка, простое горизонтальное масштабирование может её сломать.

---

# Идемпотентность

Из-за:

* ACK;
* redelivery;
* retry;
* requeue;
* crash;

одно сообщение может быть обработано несколько раз.

Поэтому:

```text
RabbitMQ
    ↓
Consumer
    ↓
Idempotent processing
```

очень важна.

Например:

```python
if event_id_already_processed(event_id):
    return

process_event(event)
save_event_id(event_id)
```

На практике проверку и запись идентификатора делают атомарно, например через уникальное ограничение БД.

---

# Порядок и Transaction

Представим:

```text
event 1 → DB update
event 2 → DB update
```

Если event 2 обработался раньше event 1:

```text
event 2
   ↓
DB

event 1
   ↓
DB
```

итоговое состояние может быть неправильным.

Поэтому для state-changing событий нужно учитывать:

* порядок;
* version number;
* sequence number;
* timestamp — осторожно, не всегда достаточно;
* optimistic locking;
* идемпотентность.

---

# Versioning событий

Можно добавить версию состояния:

```python id="f8j4qt"
{
    "entity_id": 123,
    "version": 5,
    "status": "paid"
}
```

Consumer может проверить:

```text
текущая версия = 4
событие = version 5
```

→ обработать.

Если пришло:

```text
version 3
```

после version 5:

```text
❌ устаревшее событие
```

Так можно дополнительно защищаться от нарушения порядка.

---

# Практический пример

Есть:

```text
Order #123
```

События:

```text
1. order.created
2. order.paid
3. order.shipped
```

Правильный порядок:

```text
created
   ↓
paid
   ↓
shipped
```

Если:

```text
shipped
```

обработается раньше:

```text
paid
```

может возникнуть ошибка бизнес-логики.

Поэтому для таких событий важно проектировать последовательную обработку.

# Частые вопросы на собеседовании

### Гарантирует ли RabbitMQ порядок сообщений?

> RabbitMQ обычно сохраняет порядок FIFO внутри Queue при простом последовательном потреблении, но строгий порядок обработки не гарантируется при нескольких Consumer'ах, параллельной обработке, prefetch, Priority, redelivery и requeue.

### Что будет при двух Consumer?

Сообщения распределяются между Consumer'ами, поэтому порядок завершения обработки не гарантируется.

### Поможет ли `prefetch=1`?

Да, он уменьшает количество сообщений, выданных Consumer'у без ACK, и помогает последовательной обработке одним Consumer'ом. Но это не абсолютная гарантия глобального порядка.

### Влияет ли Priority на порядок?

Да. Более приоритетное сообщение может быть доставлено раньше низкоприоритетного.

### Что происходит при падении Consumer?

Не подтверждённое сообщение может быть redelivered другому Consumer'у.

### Как обеспечить строгий порядок?

Наиболее простой вариант — последовательная обработка одним Consumer'ом и отказ от механизмов, которые меняют порядок. Для масштабирования используют архитектуру, сохраняющую порядок только там, где он действительно нужен.

### Где Kafka гарантирует порядок?

> Внутри одной Partition.

# 🧠 Главная схема

```text
                  RabbitMQ Queue
                       │
             ┌─────────┴─────────┐
             │                   │
        Consumer 1          Consumer 2
             │                   │
          A → 10s             B → 1s
             │                   │
             └─────────┬─────────┘
                       ↓
               B завершён первым
```

Поэтому:

```text
Порядок публикации
       ≠
Порядок доставки
       ≠
Порядок завершения
```

---

# Формула для собеседования

> **RabbitMQ обычно работает по FIFO-модели внутри Queue, но строгий порядок обработки не гарантируется при нескольких Consumer'ах и параллельной обработке. Prefetch, Priority, requeue и redelivery также влияют на порядок. Если порядок критичен, обработку нужно сериализовать или архитектурно гарантировать порядок для конкретной сущности.**
