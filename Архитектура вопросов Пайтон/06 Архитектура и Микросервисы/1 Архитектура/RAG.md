# 🧠 RAG (Retrieval-Augmented Generation)

## 🎤 Короткий ответ

RAG — это подход, при котором языковая модель перед генерацией ответа получает релевантную информацию из внешнего источника: базы знаний, документов или базы данных. Сначала система находит подходящие фрагменты по запросу пользователя, затем передаёт их вместе с запросом в LLM. Это позволяет отвечать на основе актуальных данных и внутренних документов, не переобучая модель.

## 🗣️ Ответ на собеседовании

RAG расшифровывается как Retrieval-Augmented Generation — генерация, дополненная поиском.

Основная проблема обычной LLM заключается в том, что она опирается на знания, полученные при обучении, и не обязательно знает актуальную информацию или содержимое закрытых корпоративных документов.

RAG решает эту проблему: перед генерацией ответа система выполняет поиск по внешней базе знаний и добавляет найденные фрагменты в контекст модели.

Обычно процесс состоит из двух этапов. На этапе подготовки документы разбиваются на небольшие фрагменты — chunks, после чего для них создаются embeddings и сохраняются в векторном хранилище. На этапе запроса система преобразует вопрос пользователя в embedding, находит похожие фрагменты, при необходимости ранжирует их и передаёт наиболее релевантные вместе с вопросом в LLM.

В результате модель формирует ответ с опорой на найденный контекст. При этом RAG не гарантирует абсолютную точность: качество зависит от документов, разбиения на chunks, поиска, ранжирования и самого промпта.

RAG полезен для корпоративных помощников, поиска по технической документации, внутренним базам знаний и систем поддержки пользователей.

## 📚 Разбор поглубже

### 1. Что такое RAG

RAG — архитектурный подход, который объединяет поиск информации (Retrieval) и генерацию текста (Generation).

Вместо того чтобы просить модель ответить только на основе её обученных параметров, приложение сначала ищет релевантные данные и передаёт их модели.

**Важно различать:**
- **LLM** — модель, которая генерирует ответ.
- **RAG** — механизм, который подбирает внешний контекст для генерации.
- **Fine-tuning** — дополнительное обучение модели на примерах.
- **Embedding** — числовое представление текста, используемое для поиска семантически похожих фрагментов.

### 2. Как работает RAG

Типичный RAG-пайплайн состоит из двух частей.

#### Этап A. Индексация документов

1. **Загрузка:** приложение получает PDF, DOCX, Markdown, HTML или другие документы.
2. **Извлечение текста:** содержимое документов преобразуется в текст.
3. **Chunking:** текст разбивается на фрагменты.
4. **Embeddings:** каждый фрагмент преобразуется в вектор.
5. **Индексация:** текст, embedding и метаданные сохраняются в хранилище.

```text
Документы
    ↓
Извлечение текста
    ↓
Разбиение на chunks
    ↓
Создание embeddings
    ↓
Vector Database
```

#### Этап B. Обработка запроса

1. Пользователь задаёт вопрос.
2. Система создаёт embedding запроса либо использует другой механизм поиска.
3. Выполняется поиск релевантных фрагментов.
4. При необходимости результаты фильтруются или переупорядочиваются с помощью reranker.
5. Найденный контекст вместе с вопросом передаётся в LLM.
6. Модель генерирует ответ.

```text
Вопрос пользователя
        ↓
Поиск в базе знаний
        ↓
Релевантные фрагменты
        ↓
Формирование промпта
        ↓
LLM
        ↓
Ответ пользователю
```

### 3. Основные компоненты

| Компонент | Назначение |
|---|---|
| Document Loader | Загружает документы |
| Text Splitter | Разбивает документы на chunks |
| Embedding Model | Преобразует текст в векторы |
| Vector Database | Хранит векторы и поддерживает поиск |
| Retriever | Находит подходящие фрагменты |
| Reranker | Повторно оценивает и сортирует результаты поиска |
| Prompt Template | Формирует инструкции и контекст для LLM |
| LLM | Генерирует итоговый ответ |

### 4. Chunking — разбиение документов

Chunking — процесс разделения длинного документа на небольшие фрагменты.

Например, документ объёмом 20 000 токенов можно разделить на chunks по 500 токенов с небольшим перекрытием.

**Зачем это нужно:**
- Весь документ может не поместиться в контекст модели.
- Поиск по небольшим фрагментам помогает найти конкретный ответ.
- Модель получает меньше нерелевантной информации.

**Проблемы выбора размера:**
- Слишком маленькие chunks могут потерять контекст.
- Слишком большие chunks могут содержать много лишней информации.
- Перекрытие (overlap) помогает сохранить связь между соседними фрагментами, но увеличивает объём хранения и поиска.

Размер chunks подбирают экспериментально с учётом структуры документов, длины вопросов и качества поиска.

### 5. Embeddings и векторный поиск

Embedding — вектор чисел, представляющий смысл текста в пространстве, обученном embedding-моделью.

Например, фразы «Как сбросить пароль?» и «Восстановление доступа к аккаунту» могут быть семантически близки, хотя слова в них отличаются.

Векторная база позволяет искать близкие embeddings по метрике сходства или расстояния, например:
- cosine similarity;
- dot product;
- Euclidean distance.

Сам embedding не хранит текст в удобном для чтения виде и не гарантирует, что два похожих по смыслу текста будут найдены при любых настройках. Качество зависит от embedding-модели, данных и стратегии поиска.

### 6. Способы поиска

**Semantic Search** — поиск по смысловой близости embeddings. Полезен, когда запрос сформулирован другими словами, чем исходный документ.

**Keyword Search** — поиск по словам и терминам, например через полнотекстовый поиск.

**Hybrid Search** — сочетание семантического и лексического поиска. Полезен, когда важно находить как смысловые совпадения, так и точные названия, коды ошибок или идентификаторы.

**Reranking** — дополнительное ранжирование уже найденных кандидатов более точной моделью. Оно может повысить релевантность результатов, но добавляет вычислительные затраты и задержку.

### 7. Пример RAG на Python

Упрощённая схема с готовым retriever и LLM-клиентом:

```python
def answer_question(question: str) -> str:
    documents = retriever.invoke(question)

    context = "\n\n".join(
        document.page_content
        for document in documents
    )

    prompt = f"""
Ответь на вопрос, используя контекст.
Если информации недостаточно, сообщи об этом.

Контекст:
{context}

Вопрос:
{question}
"""

    response = llm.invoke(prompt)
    return response.content
```

Здесь `retriever` и `llm` предполагаются уже настроенными объектами.

Это демонстрация основного потока, а не готовая production-реализация. В реальном приложении нужно учитывать ограничения контекста, источники и метаданные документов, ошибки поиска, безопасность и проверку качества ответов.

### 8. RAG vs Fine-tuning

| Критерий | RAG | Fine-tuning |
|---|---|---|
| Основная цель | Предоставить модели внешний контекст | Изменить поведение модели через обучение |
| Новые документы | Обычно достаточно обновить индекс | Может потребоваться новое обучение |
| Актуальные данные | Подходит для часто обновляемой информации | Не предназначен для оперативного обновления фактов |
| Источники ответа | Можно сохранять найденные фрагменты и ссылки | Знания не обязательно можно привязать к конкретному источнику |
| Инфраструктура | Поиск, хранилище, LLM | Обучение или дообучение и хранение модели |

RAG и fine-tuning не исключают друг друга: их можно использовать совместно.

### 9. Преимущества и ограничения

**Преимущества:**
- Доступ к внутренним и обновляемым документам.
- Возможность указывать источники ответа.
- Нет необходимости переобучать модель при каждом обновлении базы.
- Можно контролировать доступ к документам на уровне приложения.

**Ограничения:**
- Нерелевантные результаты поиска приводят к слабым ответам.
- Потеря контекста при chunking ухудшает качество.
- Большой объём найденного текста увеличивает затраты и задержку.
- LLM может неверно интерпретировать контекст или добавить неподтверждённые утверждения.
- Утечки данных и prompt injection возможны, если документы и результаты поиска обрабатываются без достаточных мер защиты.

### 10. Как оценивать качество RAG

Оценивать нужно не только ответ LLM, но и всю цепочку.

- **Retrieval quality:** нашлись ли нужные документы и фрагменты.
- **Context relevance:** действительно ли найденный контекст относится к вопросу.
- **Faithfulness / groundedness:** подтверждается ли ответ предоставленным контекстом.
- **Answer relevance:** отвечает ли результат на вопрос пользователя.
- **Latency и cost:** сколько времени и ресурсов занимает обработка.

Для диагностики полезно отдельно проверять поиск, затем генерацию на заранее подготовленном контексте, а после — весь пайплайн.

### 11. Типичные ошибки

1. Считать, что RAG устраняет галлюцинации полностью.
2. Использовать только векторный поиск, даже когда важны точные коды и названия.
3. Выбирать размер chunks без тестирования.
4. Передавать в LLM слишком много нерелевантного контекста.
5. Не сохранять метаданные и происхождение документов.
6. Не проверять, имеет ли пользователь право читать найденные документы.
7. Считать, что наличие векторной базы само по себе означает наличие качественного RAG.

## 🎤 Вопросы на собеседовании

**1. Что означает RAG?**

Retrieval-Augmented Generation — генерация ответа языковой моделью с использованием информации, найденной во внешнем источнике.

**2. Зачем нужны embeddings?**

Они представляют текст в виде векторов и позволяют искать фрагменты по семантической близости.

**3. Чем RAG отличается от fine-tuning?**

RAG подаёт найденную информацию в контекст при запросе, а fine-tuning изменяет параметры модели в процессе дополнительного обучения.

**4. Что такое chunking?**

Разбиение документов на фрагменты, которые удобнее индексировать, искать и передавать модели.

**5. Почему RAG может давать неправильные ответы?**

Поиск может не найти нужный фрагмент, контекст может оказаться неполным, а LLM — неверно его интерпретировать.

**6. Что такое reranking?**

Повторная оценка и сортировка найденных кандидатов, чтобы передать модели наиболее релевантные фрагменты.

**7. Как улучшить качество RAG?**

Настроить chunking, проверить embedding-модель, использовать hybrid search и reranking, оценивать качество поиска отдельно от генерации и тестировать систему на реальных вопросах.

**8. Где применяется RAG?**

В корпоративных помощниках, поиске по документации, системах поддержки, внутренних базах знаний и приложениях, которым требуется отвечать по частным или обновляемым данным.
