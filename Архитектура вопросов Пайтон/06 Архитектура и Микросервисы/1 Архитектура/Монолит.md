# 🧱 Монолит

## 🎯 Ответ на собеседовании

**Монолитная архитектура** — это архитектура, в которой приложение представляет собой **единое развёртываемое приложение**, содержащее несколько функциональных компонентов и бизнес-логику.

Например:

```text id="f8k2qm"
             ┌──────────────────────┐
             │       Backend        │
             │                      │
             │  Users               │
             │  Orders              │
             │  Payments            │
             │  Products            │
             │  Auth                │
             │                      │
             └──────────┬───────────┘
                        ↓
                   PostgreSQL
```

Все основные компоненты находятся внутри одного приложения и обычно разворачиваются **как единое целое**.

---

## 🎤 Суперкоротко

**Монолит = одно приложение, в котором сосредоточена основная бизнес-логика и которое разворачивается как единое целое.**

```text id="a6s3pz"
Client
   ↓
Monolith
   ↓
Database
```

# 🧩 Как устроен монолит

Например, интернет-магазин:

```text id="q7n4kx"
                Monolith
┌─────────────────────────────────┐
│                                 │
│  Authentication                 │
│  Users                          │
│  Products                       │
│  Orders                         │
│  Payments                       │
│  Notifications                  │
│                                 │
└───────────────┬─────────────────┘
                ↓
           PostgreSQL
```

Все модули могут быть логически разделены внутри кода:

```text id="w8m2rx"
app/
├── users/
├── products/
├── orders/
├── payments/
└── notifications/
```

Но при этом они являются частью **одного приложения**.

---

# 🚀 Развёртывание

Основная особенность монолита — **единое развёртывание**.

Например:

```text id="x5k9vc"
Code
 ↓
Build
 ↓
Docker Image
 ↓
Container
```

Если изменить только модуль `Orders`, обычно разворачивается **всё приложение**.

---

# 🐍 Пример с FastAPI

Можно иметь один FastAPI-проект:

```text id="d3q7nb"
FastAPI
│
├── /users
├── /products
├── /orders
├── /payments
└── /auth
```

При этом это всё один backend:

```text id="z8v4kp"
Client
   ↓
FastAPI
   ↓
PostgreSQL
```

# ✅ Плюсы монолита

### 1. Простота разработки

На начальном этапе проще создать одно приложение, чем множество отдельных сервисов.

### 2. Простое развёртывание

Нужно развернуть одно приложение:

```text id="n6c2qw"
Build → Deploy
```

### 3. Простое взаимодействие между модулями

Компоненты могут напрямую вызывать код друг друга:

```python id="f4p8km"
order = order_service.create_order(user_id)
```

Не нужно использовать HTTP, очереди сообщений или RPC.

### 4. Проще отлаживать

Логи и код находятся в одном приложении.

### 5. Меньше инфраструктурной сложности

Не нужно сразу управлять:

```text id="b5x9qz"
10 сервисами
10 Docker-контейнерами
service discovery
message broker
distributed tracing
```

# ❌ Минусы монолита

### 1. Сложнее масштабировать отдельные части

Если сильно нагружен только `Payments`, нельзя легко масштабировать исключительно этот модуль.

Обычно масштабируется всё приложение:

```text id="q9m3fd"
Monolith × 1
     ↓
Monolith × 2
     ↓
Monolith × 3
```

### 2. Большой код становится сложнее поддерживать

Со временем приложение может превратиться в большой связанный код:

```text id="r7k4zs"
Users ↔ Orders ↔ Payments ↔ Products
```

Изменение одного компонента может повлиять на другие.

### 3. Единое развёртывание

Даже небольшое изменение может потребовать повторного deployment всего приложения.

### 4. Единая точка отказа

Если монолит полностью перестал работать:

```text id="w2v8kc"
Monolith ❌
    ↓
всё приложение недоступно
```

При этом правильное горизонтальное масштабирование и отказоустойчивая инфраструктура могут существенно снизить этот риск.

---

# 🆚 Монолит vs Микросервисы

|                           | Монолит                  | Микросервисы               |
| ------------------------- | ------------------------ | -------------------------- |
| Архитектура               | Одно приложение          | Набор независимых сервисов |
| Deployment                | Обычно общий             | Независимый                |
| Масштабирование           | Обычно всего приложения  | Отдельных сервисов         |
| Взаимодействие            | Вызовы внутри приложения | HTTP/RPC/очереди           |
| Инфраструктура            | Проще                    | Сложнее                    |
| Отладка                   | Проще                    | Сложнее                    |
| Начало проекта            | Часто проще              | Сложнее                    |
| Независимость компонентов | Ниже                     | Выше                       |

# 🧱 Модульный монолит

Важно понимать, что **монолит не обязательно означает "весь код в одном файле"**.

Хороший вариант — **модульный монолит**:

```text id="k3x7pa"
Monolith
│
├── Users Module
├── Orders Module
├── Payments Module
└── Products Module
```

Модули логически изолированы, но всё приложение по-прежнему разворачивается как единое целое.

Это позволяет сохранить простоту монолита и при этом подготовить архитектуру к возможному дальнейшему выделению сервисов.

---

# 🆚 Монолит ≠ плохая архитектура

Монолит часто является **рациональным выбором для небольшого проекта**.

Например:

```text id="p8q4vd"
Небольшая команда
       ↓
Небольшой продукт
       ↓
Мало нагрузки
       ↓
Монолит
```

Не всегда имеет смысл начинать сразу с микросервисов.

Микросервисная архитектура добавляет распределённые системы, сетевые взаимодействия, мониторинг, deployment и другие инфраструктурные задачи.

# 🧠 Главное

```text id="u6m2qx"
Монолит

          ┌─────────────────────┐
Client →  │      Backend        │
          │                     │
          │ Users               │
          │ Orders              │
          │ Products            │
          │ Payments            │
          │ Auth                │
          └──────────┬──────────┘
                     ↓
                 Database
```

**Монолит — это архитектура, при которой приложение является единым развёртываемым целым, даже если внутри оно разделено на отдельные модули.**

Главная формулировка для собеседования:

> **Монолитная архитектура — это архитектура, в которой основные компоненты приложения находятся в одном развёртываемом приложении. Это упрощает разработку, deployment и взаимодействие между компонентами, но по мере роста проекта усложняет независимое масштабирование и развитие отдельных частей системы.**
