# 🔹 Микросервисы

## 🎯 Ответ на собеседовании

**Микросервисная архитектура** — это архитектурный подход, при котором приложение разбивается на небольшие независимые сервисы, каждый из которых отвечает за отдельную бизнес-функцию.

Микросервисы могут разрабатываться, развёртываться и масштабироваться независимо друг от друга и обычно взаимодействуют через сеть — например, [[HTTP]]/[[REST]], [[gRPC]] или [[Брокеры сообщений|Брокеры сообщений]].

Например, интернет-магазин можно разделить на сервисы:

```python
Пользователи → User Service
Товары      → Product Service
Заказы      → Order Service
Оплата      → Payment Service
Уведомления → Notification Service
```

Каждый сервис отвечает за свою область ответственности.

---

## 🎤 Суперкоротко

**Микросервисы — это архитектура, где приложение разбито на независимые сервисы, каждый отвечает за отдельную бизнес-функцию и может независимо развёртываться и масштабироваться.**

## 🧩 Основная идея

Вместо одного большого приложения:

```text
                ┌─────────────────────┐
                │     Монолит          │
                │                     │
                │ Users               │
                │ Products            │
                │ Orders              │
                │ Payments            │
                │ Notifications       │
                └─────────────────────┘
```

используются отдельные сервисы:

```text
                ┌──────────────┐
                │ API Gateway  │
                └──────┬───────┘
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
 ┌──────────┐    ┌──────────┐    ┌──────────┐
 │  Users   │    │ Products │    │  Orders  │
 │ Service  │    │ Service  │    │ Service  │
 └──────────┘    └──────────┘    └────┬─────┘
                                       │
                                  ┌────↓─────┐
                                  │ Payments │
                                  │ Service  │
                                  └──────────┘
```

---

## 🏗️ Что обычно характерно для микросервиса

Каждый сервис обычно:

* имеет отдельную бизнес-ответственность;
* имеет собственный код;
* может иметь собственную БД;
* может независимо развёртываться;
* может независимо масштабироваться;
* взаимодействует с другими сервисами через API или сообщения.

Например:

```text
Order Service
      │
      ├── PostgreSQL
      │
      └── обращается к
             ↓
       Payment Service
```

---

## 🗄️ Собственная база данных

В микросервисной архитектуре часто используется принцип:

**Database per Service**

```text
User Service      → PostgreSQL
Product Service   → PostgreSQL
Order Service     → PostgreSQL
Payment Service   → PostgreSQL
```

Сервисы не должны напрямую обращаться к таблицам друг друга.

Например:

```text
❌ Order Service → напрямую читает таблицы Payment Service

✅ Order Service → API → Payment Service
```

Это позволяет сохранять независимость сервисов.

При этом "собственная БД" не обязательно означает физически отдельный сервер БД — это может быть отдельная схема, база или другой изолированный storage, в зависимости от архитектуры.

---

## 🔌 Как микросервисы взаимодействуют

Основные варианты:

### HTTP / REST

```text
Order Service
      │
      │ HTTP
      ↓
Payment Service
```

Например:

```python
POST /payments
GET /payments/{payment_id}
```

### gRPC

Используется для высокопроизводительного взаимодействия между сервисами.

```text
Order Service
      │
      │ gRPC
      ↓
Payment Service
```

### Message Broker

Например, Kafka или RabbitMQ.

```text
Order Service
      │
      ↓
 Message Broker
      │
      ↓
Notification Service
```

Это позволяет использовать асинхронное взаимодействие.

## ⚖️ Преимущества

### 1. Независимое масштабирование

Если нагрузка сильно выросла только на Order Service:

```text
Order Service × 10
User Service  × 2
Payment       × 2
```

Не нужно масштабировать всё приложение целиком.

### 2. Независимый deployment

Можно обновить один сервис:

```text
Order Service v2
```

не выкатывая остальные сервисы.

### 3. Изоляция ответственности

Каждый сервис отвечает за конкретную бизнес-область.

Это упрощает развитие больших систем.

### 4. Технологическая независимость

Разные сервисы потенциально могут использовать разные технологии.

Например:

```text
User Service      → Python
Payment Service   → Java
Recommendation    → Python
```

Но использовать разные технологии без необходимости не стоит — это увеличивает сложность системы.

### 5. Изоляция отказов

Проблема в одном сервисе не обязательно должна полностью остановить систему.

Например:

```text
Notification Service ❌

Orders              ✅
Payments            ✅
Products            ✅
```

## ❌ Недостатки

Главная проблема микросервисов — **значительно возросшая распределённая сложность**.

### 1. Сложнее инфраструктура

Появляются:

* API Gateway;
* service discovery;
* балансировщики;
* брокеры сообщений;
* контейнеры;
* Kubernetes;
* мониторинг;
* централизованные логи;
* distributed tracing.

### 2. Сетевое взаимодействие

В монолите:

```python
order_service.create_payment()
```

В микросервисах:

```text
Order Service
      │
      │ HTTP/gRPC
      ↓
Payment Service
```

Сеть может быть недоступна, медленной или вернуть ошибку.

### 3. Сложнее транзакции

В монолите можно относительно просто использовать одну транзакцию БД:

```text
BEGIN
   ↓
Create Order
   ↓
Create Payment
   ↓
COMMIT
```

В микросервисах операции могут находиться в разных БД.

Поэтому используются паттерны распределённых систем, например **Saga**.

### 4. Сложнее отладка

Один запрос пользователя может пройти через несколько сервисов:

```text
Client
  ↓
API Gateway
  ↓
Order Service
  ↓
Payment Service
  ↓
Notification Service
```

Поэтому нужны correlation/request ID, централизованные логи и distributed tracing.

## 🔥 Монолит vs микросервисы

| Монолит                           | Микросервисы                          |
| --------------------------------- | ------------------------------------- |
| Одно приложение                   | Несколько сервисов                    |
| Один deployment                   | Независимый deployment                |
| Обычно проще инфраструктура       | Инфраструктура сложнее                |
| Проще локальная разработка        | Сложнее локальная разработка          |
| Масштабируется приложение целиком | Сервисы можно масштабировать отдельно |
| Проще транзакции                  | Распределённые транзакции сложнее     |
| Обычно проще отладка              | Нужен distributed tracing             |
| Подходит для небольших проектов   | Особенно полезны для крупных систем   |

## 🧱 Микросервис ≠ просто отдельный Python-проект

Важно.

Если мы сделали:

```text
users.py
orders.py
payments.py
```

это **не микросервисы**.

Это может быть модульный монолит.

Для микросервисов сервисы должны быть отдельными развёртываемыми компонентами:

```text
users-service/
orders-service/
payments-service/
```

Например:

```text
users-service → container → deployment
orders-service → container → deployment
payments-service → container → deployment
```

## 🧩 Модульный монолит и микросервисы

**Модульный монолит**:

```text
┌─────────────────────────────┐
│          Application        │
│                             │
│ Users │ Orders │ Payments  │
└─────────────────────────────┘
```

Модули логически разделены, но приложение разворачивается целиком.

**Микросервисы**:

```text
┌─────────┐  ┌─────────┐  ┌──────────┐
│ Users   │  │ Orders  │  │ Payments │
│ Service │  │ Service │  │ Service  │
└─────────┘  └─────────┘  └──────────┘
```

Каждый сервис разворачивается отдельно.

## 🚪 API Gateway

Перед микросервисами часто находится **API Gateway**.

```text
Client
   ↓
API Gateway
   ├──→ User Service
   ├──→ Product Service
   ├──→ Order Service
   └──→ Payment Service
```

Gateway может выполнять:

* маршрутизацию;
* аутентификацию;
* rate limiting;
* TLS termination;
* логирование;
* агрегацию запросов.

---

## 🔄 Пример реального сценария

Пользователь оформляет заказ:

```text
Client
  ↓
API Gateway
  ↓
Order Service
  ↓
Product Service
  ↓
Payment Service
  ↓
Notification Service
```

Например:

1. `Order Service` создаёт заказ.
2. Проверяет наличие товара через `Product Service`.
3. Передаёт запрос на оплату в `Payment Service`.
4. После успешной оплаты публикуется событие.
5. `Notification Service` отправляет уведомление пользователю.

## 📨 Синхронное и асинхронное взаимодействие

**Синхронно:**

```text
Order Service
      │
      │ HTTP
      ↓
Payment Service
      │
      ↓
   response
```

Order Service ждёт ответ.

**Асинхронно:**

```text
Order Service
      │
      ↓
   Kafka/RabbitMQ
      │
      ↓
Notification Service
```

Order Service не обязан ждать завершения обработки.

## 🧠 Главная проблема микросервисов

На собеседовании полезно сказать:

> **Основная сложность микросервисной архитектуры — не разделение приложения на сервисы, а управление распределённой системой.**

Появляются:

```text
Network failures
Timeouts
Retries
Consistency
Distributed transactions
Service discovery
Observability
Message delivery
```

Поэтому микросервисы не являются автоматически "лучше" монолита.

---

## 🎯 Когда использовать микросервисы

Микросервисы оправданы, когда:

* система достаточно большая;
* есть несколько независимых бизнес-доменов;
* разные команды работают над разными частями;
* требуется независимое масштабирование;
* необходим независимый deployment;
* система уже имеет высокую нагрузку или сложность.

Для небольшого проекта часто лучше:

```text
Модульный монолит
        ↓
простота
        ↓
быстрая разработка
        ↓
при необходимости → выделение микросервисов
```

## 💡 Главное

```text
Микросервисы
    ↓
Независимые сервисы
    ↓
Каждый отвечает за свою бизнес-функцию
    ↓
Независимый deployment
    ↓
Независимое масштабирование
    ↓
Взаимодействие через сеть / сообщения
    ↓
Больше гибкости
    +
Больше распределённой сложности
```

### Формула для собеседования

**Микросервисная архитектура = независимые сервисы + отдельная бизнес-ответственность + сетевое взаимодействие + независимое развёртывание и масштабирование.**
