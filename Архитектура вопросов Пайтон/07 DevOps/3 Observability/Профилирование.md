# 🔬 Профилирование (Profiling)

## 🎤 Короткий ответ

**Профилирование (Profiling)** — это анализ работы программы, чтобы определить, **какие функции и операции потребляют больше всего CPU, памяти и других ресурсов**.

В отличие от tracing, который показывает путь конкретного запроса, profiling показывает **внутреннее потребление ресурсов процессом или кодом**.

Например:

```text id="p4m8qx"
CPU:
calculate_report()     → 45%
process_data()         → 30%
serialize_response()   → 15%
```

Профилирование помогает найти **узкие места производительности (bottlenecks)** и понять, что именно оптимизировать.

## 🎯 Формула для собеседования

> **Profiling = измерение потребления ресурсов → поиск bottleneck → оптимизация.**

```text
Profiling
   ↓
CPU / Memory / I/O
   ↓
Находим горячие места
   ↓
Оптимизируем код
   ↓
Проверяем результат
```

---

# 🔹 Что именно профилируют

Профилирование может анализировать разные ресурсы:

```text
CPU
Memory
I/O
Threads
Locks
Async tasks
```

Для Python особенно часто интересны:

* CPU time;
* количество вызовов функций;
* время выполнения функций;
* потребление памяти;
* создание объектов;
* блокировки;
* ожидание I/O.

---

# 🔹 CPU Profiling

**CPU profiling** показывает, какие функции потребляют процессорное время.

Например:

```text id="c7m3vx"
process_orders()       50%
calculate_price()      25%
serialize_data()       15%
other                  10%
```

Если `process_orders()` занимает половину CPU, именно его стоит исследовать в первую очередь.

---

# 🔹 Wall Time vs CPU Time

Важно различать два времени.

### CPU Time

Время, которое процесс реально выполнял инструкции на CPU.

### Wall Time

Реальное прошедшее время.

Например:

```text id="w8q2mc"
Запрос начал выполняться
        ↓
  ждём PostgreSQL 900 ms
        ↓
CPU работает 100 ms
        ↓
Запрос завершён
```

Получается:

```text id="m5q7vx"
Wall time = 1000 ms
CPU time  = 100 ms
```

Профилирование CPU может показать небольшую загрузку CPU, хотя операция долго выполняется.

Причина — процесс **ждал I/O**.

---

# 🔹 CPU-bound vs I/O-bound

Это важное различие для backend.

### CPU-bound

Основное время уходит на вычисления.

```text id="x4m8qp"
Python
  ↓
сложные вычисления
  ↓
CPU 100%
```

Здесь profiling CPU особенно полезен.

### I/O-bound

Процесс в основном ждёт:

```text id="k6m3vx"
PostgreSQL
Redis
HTTP API
Disk
Network
```

Например:

```text id="n8q4mc"
CPU       → 10%
PostgreSQL → 90% времени
```

Здесь CPU profiler не обязательно покажет главную проблему. Полезнее tracing и профилирование I/O/ожиданий.

---

# 🔹 Python `cProfile`

В Python есть встроенный CPU profiler:

```python id="r7m2qx"
import cProfile

cProfile.run("process_data()")
```

Он показывает статистику вызовов функций.

Например:

```text id="v4m8kc"
ncalls  tottime  cumtime  function
1000    0.120    0.120    calculate_price
1       0.050    0.300    process_orders
```

---

# 🔹 `tottime` и `cumtime`

Это частый вопрос на собеседовании.

### `tottime`

Время, которое функция потратила **непосредственно внутри себя**, без учёта вызываемых функций.

### `cumtime`

Общее время функции **вместе с вызванными ею функциями**.

Например:

```text id="q5m8vx"
A()
 └── B()
      └── C()
```

Если:

```text id="p3q7mc"
A cumtime = 1.0 sec
A tottime = 0.1 sec
```

значит большая часть времени была потрачена внутри вызываемых функций.

---

# 🔹 `timeit`

**`timeit`** используется для точного измерения времени выполнения небольших фрагментов кода.

Например:

```python id="z8m4qx"
import timeit

result = timeit.timeit(
    "sum(range(1000))",
    number=10000,
)

print(result)
```

`timeit` хорошо подходит для:

* сравнения двух реализаций;
* небольших benchmark;
* измерения конкретной операции.

Но это не полноценный profiler приложения.

---

# 🔹 CPU Profiler vs Benchmark

Это разные задачи.

### Benchmark

Отвечает:

> **Сколько времени занимает операция?**

Например:

```text id="d6m8vx"
algorithm A → 100 ms
algorithm B → 60 ms
```

### Profiler

Отвечает:

> **На что именно уходит время внутри программы?**

Например:

```text id="u4q7mc"
function_a → 50%
function_b → 30%
function_c → 10%
```

---

# 🔹 Memory Profiling

**Memory profiling** позволяет понять, куда расходуется RAM.

Например:

```text id="m8q3vx"
process_data() → 500 MB
load_dataframe() → 300 MB
cache_results() → 150 MB
```

Это помогает искать:

* чрезмерное потребление памяти;
* memory leak;
* большие объекты;
* ненужное копирование данных.

---

# 🔹 `memory_profiler`

Для Python существует `memory_profiler`, который позволяет измерять изменение памяти по функциям/строкам.

Концептуально:

```text id="p7m4qx"
Before:
200 MB

load_data():
+500 MB

After:
700 MB
```

Это позволяет определить участок программы, который резко увеличивает использование памяти.

---

# 🔹 Memory Leak

**Memory leak** — ситуация, когда программа удерживает объекты, которые больше не нужны, из-за чего память постепенно растёт.

Например:

```text id="l3m8vx"
100 MB
 ↓
200 MB
 ↓
400 MB
 ↓
800 MB
 ↓
1.5 GB
```

Если память не освобождается, процесс в итоге может получить:

```text id="x6q2mc"
Out Of Memory
```

Профилирование памяти помогает найти объекты, которые продолжают удерживаться.

---

# 🔹 Python и Garbage Collector

В Python память управляется автоматически.

Основные механизмы:

```text id="g5m8qx"
Reference Counting
        +
Cyclic Garbage Collector
```

Но автоматическое управление памятью **не означает**, что память всегда будет освобождаться сразу.

Например, если объект всё ещё имеет ссылку:

```python id="v2q7mc"
cache = {}

cache["data"] = large_object
```

GC не удалит `large_object`, пока на него существует ссылка.

---

# 🔹 Sampling Profiling

Один из распространённых подходов — **sampling profiler**.

Профайлер периодически смотрит:

> Где сейчас выполняется программа?

Например:

```text id="s8m4qx"
t1 → function_a
t2 → function_a
t3 → function_b
t4 → function_a
t5 → function_a
```

Получаем:

```text id="j3q7vx"
function_a → ~80%
function_b → ~20%
```

Sampling обычно имеет небольшой overhead и хорошо подходит для production profiling.

---

# 🔹 Instrumentation Profiling

Другой подход — **instrumentation profiling**.

Профайлер непосредственно оборачивает/инструментирует вызовы функций:

```text id="i4m8qx"
function start
      ↓
function execute
      ↓
function finish
```

Можно получить подробную информацию о вызовах.

Недостаток — instrumentation обычно создаёт больший overhead.

---

# 🔹 Profiling в Production

Постоянно включать тяжёлый profiler в production может быть дорого.

Причины:

* дополнительная нагрузка;
* увеличение latency;
* большой объём данных.

Поэтому часто применяют:

```text id="y7m3qx"
Sampling
   ↓
Выборочная профилировка
   ↓
Анализ production workload
```

Или запускают profiling только при необходимости.

---

# 🔹 Pyroscope

**Pyroscope** — система continuous profiling.

Упрощённая схема:

```text id="p5m8qx"
Application
     ↓
Profiler
     ↓
Pyroscope
     ↓
Profiles
     ↓
Analysis
```

Она позволяет собирать профили приложения в течение длительного времени и анализировать, куда уходят CPU и другие ресурсы.

---

# 🔹 Continuous Profiling

**Continuous Profiling** — регулярный сбор профилей приложения во время его работы.

Вместо:

```text id="c8m4qx"
Проблема
   ↓
Запустили profiler
   ↓
Получили профиль
```

можно иметь:

```text id="a6q2vx"
Production
    ↓
Continuous Profiling
    ↓
Профили за часы/дни
    ↓
Сравнение
```

Это позволяет обнаруживать постепенные изменения производительности.

# 🔹 Profiling + Tracing

Эти инструменты хорошо дополняют друг друга.

Tracing показывает:

```text id="t4m8qx"
Request
  ↓
Order Service
  ↓
Payment Service
  ↓
PostgreSQL
```

Profiling показывает:

```text id="p8q3vx"
Payment Service

calculate_fee()    45% CPU
serialize_data()   25% CPU
validate_order()   15% CPU
```

Получается:

```text id="x7m4qc"
Tracing
   ↓
Нашли проблемный сервис
   ↓
Profiling
   ↓
Нашли горячую функцию
   ↓
Оптимизация
```

# 🔹 Profiling + Metrics

Metrics могут показать:

```text id="m3q8vx"
CPU = 95%
```

Но не объясняют, **какая функция** использует CPU.

Дальше:

```text id="k6m4qx"
Metrics
   ↓
CPU ↑
   ↓
Profiler
   ↓
calculate_report() = 70% CPU
```

---

# 🔹 Profiling + Logs

Logs могут сообщить:

```python id="r8m3qx"
ERROR: report generation failed
```

Tracing покажет:

```text id="t5q7mc"
Trace
 ↓
Report Service
 ↓
generate_report()
```

А profiler:

```text id="p4m8vx"
generate_report()
   ↓
parse_data() = 60% CPU
```

Вместе получается гораздо более полная диагностика.

---

# 🔹 Типичный цикл оптимизации

Профилирование не должно превращаться в оптимизацию «на глаз».

Правильный цикл:

```text id="o7m3qx"
1. Измерить
      ↓
2. Найти bottleneck
      ↓
3. Изменить код
      ↓
4. Снова измерить
      ↓
5. Сравнить результат
```

Главный принцип:

> **Don't guess — measure.**

---

# 🔹 Пример

Есть функция:

```python id="e4m8qx"
def calculate_total(items):
    total = 0

    for item in items:
        for other in items:
            if item["id"] == other["id"]:
                total += item["price"]

    return total
```

Profiler может показать:

```text id="q7m3vx"
calculate_total() → 95% CPU
```

После анализа алгоритм можно изменить.

Например, вместо двойного цикла использовать более подходящую структуру данных.

После оптимизации снова запускаем profiler и benchmark:

```text id="v5m8qx"
Before → 2.5 sec
After  → 0.15 sec
```

Таким образом подтверждаем, что оптимизация действительно помогла.

# 🔹 Профилирование и Python GIL

Для CPU-bound Python-кода важно помнить про **GIL** в CPython.

Если один процесс использует несколько threads для CPU-bound Python bytecode, GIL ограничивает параллельное выполнение Python bytecode.

Поэтому profiling помогает определить:

```text id="g3m7qx"
CPU-bound?
   ↓
Да
   ↓
Где bottleneck?
   ↓
Алгоритм / Python code / C extension?
```

В зависимости от результата могут рассматриваться:

* оптимизация алгоритма;
* multiprocessing;
* native/C-extensions;
* специализированные библиотеки;
* изменение архитектуры.

# 🔹 Частые вопросы на собеседовании

### Что такое Profiling?

> Анализ выполнения программы для определения потребления ресурсов и поиска узких мест производительности.

### Что показывает CPU profiler?

> Какие функции и операции потребляют процессорное время.

### Что такое Memory profiling?

> Анализ использования памяти объектами и участками программы.

### Что такое bottleneck?

> Компонент или операция, ограничивающая производительность системы.

### Что такое `cProfile`?

> Встроенный в Python profiler для анализа вызовов функций и времени их выполнения.

### `tottime` vs `cumtime`?

> `tottime` — время непосредственно внутри функции, `cumtime` — время функции вместе с вызываемыми ею функциями.

### `timeit` vs `cProfile`?

> `timeit` измеряет время выполнения небольшого фрагмента кода, `cProfile` показывает, где внутри программы тратится время.

### Что такое sampling profiler?

> Профайлер, который периодически снимает состояние выполнения программы и по выборке определяет горячие участки.

### Что такое continuous profiling?

> Постоянный или регулярный сбор профилей работающего приложения, в том числе production.

### Можно ли постоянно профилировать production?

> Можно, но необходимо учитывать overhead. Поэтому часто используют sampling и специализированные инструменты continuous profiling.

### Tracing vs Profiling?

> Tracing показывает путь конкретного запроса через систему, profiling показывает, какие функции и ресурсы потребляют время или память.

# 🔑 Главное

```text id="b8m4qx"
                    Profiling
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
         CPU          Memory          I/O
          │             │             │
          ↓             ↓             ↓
      Functions      Objects       Waiting
          │             │             │
          └─────────────┼─────────────┘
                        ↓
                   Bottleneck
                        ↓
                    Optimize
                        ↓
                    Measure again
```

> **Metrics** → видим проблему
> **Logs** → узнаём детали события
> **Tracing** → находим проблемный участок запроса
> **Profiling** → находим горячую функцию/ресурс
> **Benchmark** → измеряем результат оптимизации
