# 📝 Логи (Observability)

## 🎤 Короткий ответ

**Логи (Logs)** — это записи о событиях, которые происходят внутри приложения или инфраструктуры.

Они помогают понять **что произошло, когда произошло и при каких обстоятельствах**.

Например:

```python
2026-09-16 21:10:42 ERROR
service=payment
message="Database connection timeout"
```

Логи особенно полезны для диагностики ошибок и расследования проблем, тогда как метрики показывают общую картину состояния системы.

## 🎯 Формула для собеседования

> **Лог = время + уровень + источник + сообщение + контекст события.**

В production предпочтительны **структурированные логи**, например JSON, чтобы их было удобно искать, фильтровать и анализировать.

---

# 🔹 Что такое лог

Лог — это запись о событии.

Например приложение может записать:

```python
User authenticated successfully
```

или:

```python
Database connection failed
```

или:

```python
Order created
```

Логи могут описывать:

* ошибки;
* HTTP-запросы;
* авторизацию;
* бизнес-события;
* обращения к БД;
* работу фоновых задач;
* запуск и остановку приложения;
* инфраструктурные события.

---

# 🔹 Зачем нужны логи

Основная задача логов — **диагностика и расследование событий**.

Например:

```text
Пользователь сообщает:
"Заказ не создаётся"
```

Метрики могут показать:

```text
Error Rate ↑
```

А лог может показать:

```python
ERROR payment_service
Database timeout
order_id=12345
```

То есть:

```text
Metrics → обнаружили проблему
Logs    → получили детали
Traces  → нашли путь запроса
```

---

# 🔹 Структура лога

Типичный лог может содержать:

```text
timestamp
level
service
message
request_id
trace_id
user_id
exception
additional context
```

Например:

```python
2026-09-16T21:10:42
level=ERROR
service=payment
request_id=abc123
message="Database timeout"
```

Чем больше полезного контекста есть в логе, тем проще расследовать проблему.

---

# 🔹 Log Level

**Log Level** показывает серьёзность события.

Наиболее распространённые уровни:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

### DEBUG

Подробная диагностическая информация.

```python
DEBUG: SQL query executed
```

Обычно используется при разработке или глубокой диагностике.

### INFO

Нормальные события приложения.

```python
INFO: User authenticated
INFO: Order created
```

### WARNING

Потенциальная проблема, но приложение пока может продолжать работать.

```python
WARNING: Redis response time is high
```

### ERROR

Ошибка, из-за которой конкретная операция не выполнилась.

```python
ERROR: Failed to create order
```

### CRITICAL

Критическая ошибка, которая может означать серьёзную неисправность системы.

```python
CRITICAL: Database unavailable
```

---

# 🔹 Логирование в Python

В Python стандартная библиотека предоставляет модуль:

```python
import logging

logger = logging.getLogger(__name__)

logger.debug("Debug information")
logger.info("User authenticated")
logger.warning("Redis latency is high")
logger.error("Failed to create order")
logger.critical("Database unavailable")
```

---

# 🔹 Почему `logging`, а не `print()`

`print()` просто выводит текст.

```python
print("Database error")
```

У `logging` есть:

* уровни;
* форматирование;
* handlers;
* фильтры;
* разные destinations;
* timestamps;
* интеграция с системами сбора логов.

Поэтому в production обычно используют **logging**, а не `print()`.

---

# 🔹 Logger

**Logger** — объект, через который приложение создаёт записи.

```python
import logging

logger = logging.getLogger(__name__)

logger.info("Application started")
```

`__name__` позволяет получить logger, связанный с текущим Python-модулем.

---

# 🔹 Handler

**Handler** определяет, **куда отправляется лог**.

Например:

```text
Logger
   ↓
Handler
   ├── Console
   ├── File
   └── External system
```

Например:

```python
logging.StreamHandler()
```

отправляет записи в поток вывода.

---

# 🔹 Formatter

**Formatter** определяет формат записи.

Например:

```python
"%(asctime)s %(levelname)s %(name)s %(message)s"
```

Результат:

```text
2026-09-16 21:10:42 ERROR payment Database timeout
```

---

# 🔹 Logger → Handler → Formatter

Важная схема для собеседования:

```text
Application
     ↓
  Logger
     ↓
  Handler
     ↓
 Formatter
     ↓
Console / File / Log system
```

---

# 🔹 Structured Logging

В production часто используют **структурированные логи**.

Вместо:

```python
"User 123 created order 456"
```

можно записать данные структурированно:

```python
{
    "event": "order_created",
    "user_id": 123,
    "order_id": 456,
    "service": "orders"
}
```

Это удобнее для систем поиска и анализа логов.

Например можно выполнить поиск:

```text
service="orders"
event="order_created"
```

---

# 🔹 Почему JSON часто используют для логов

JSON удобен тем, что отдельные поля можно обработать программно.

Например:

```python
{
    "timestamp": "2026-09-16T21:10:42Z",
    "level": "ERROR",
    "service": "payment",
    "request_id": "abc123",
    "error": "database_timeout"
}
```

Система логирования может отдельно индексировать:

```text
level
service
request_id
error
```

а не искать эти значения внутри одной строки.

---

# 🔹 Request ID

**Request ID** позволяет связать логи с одним HTTP-запросом.

Например:

```text
Request ID = abc123
```

И дальше:

```text
FastAPI:
request_id=abc123

Payment:
request_id=abc123

Database:
request_id=abc123
```

Можно найти все записи, относящиеся к одному запросу.

---

# 🔹 Trace ID

В распределённых системах используется **Trace ID**.

Например:

```text
Client
  ↓
API Gateway
  ↓
Order Service
  ↓
Payment Service
  ↓
PostgreSQL
```

Весь запрос может иметь:

```text
trace_id = abc123
```

Тогда логи разных сервисов можно связать с одним distributed trace.

```text
Trace abc123
     │
     ├── API log
     ├── Order log
     ├── Payment log
     └── DB span
```

---

# 🔹 Logs + Metrics + Traces

Три источника telemetry дополняют друг друга.

```text
             Observability
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    Metrics       Logs       Traces
       │           │           │
      Что?       Что было?    Где?
       │           │           │
       └───────────┼───────────┘
                   ↓
              Диагностика
```

Пример:

```text
Metrics:
P95 latency = 2 sec

        ↓

Logs:
Database timeout

        ↓

Trace:
PostgreSQL span = 1.8 sec
```

---

# 🔹 Где хранятся логи

В небольшой системе:

```text
Application
     ↓
stdout/stderr
```

В Kubernetes это особенно распространённый подход:

```text
Container
    ↓
stdout/stderr
    ↓
Kubernetes logging
    ↓
Log collector
    ↓
Centralized storage
```

Например:

```text
Application
     ↓
stdout
     ↓
Promtail / Fluent Bit / Vector
     ↓
Loki / Elasticsearch
     ↓
Grafana / Kibana
```

Конкретный стек зависит от архитектуры.

---

# 🔹 Почему логи централизуют

Представим Kubernetes:

```text
Node 1
 ├── Pod A
 └── Pod B

Node 2
 ├── Pod C
 └── Pod D

Node 3
 └── Pod E
```

Если каждый Pod пишет логи локально, искать проблему неудобно.

Централизованный сбор позволяет искать:

```text
trace_id=abc123
```

сразу по всем сервисам и экземплярам.

---

# 🔹 Log Aggregation

**Log Aggregation** — централизованный сбор логов из разных источников.

```text
Pod A ─┐
Pod B ─┤
Pod C ─┼──→ Collector → Storage → UI
Pod D ─┤
Pod E ─┘
```

Преимущества:

* единый поиск;
* фильтрация;
* корреляция;
* хранение;
* анализ ошибок.

---

# 🔹 ELK / Elastic Stack

Популярный стек:

```text
Elasticsearch
Logstash
Kibana
```

Упрощённо:

```text
Application
     ↓
Logstash
     ↓
Elasticsearch
     ↓
Kibana
```

**Elasticsearch** — хранение и поиск.

**Logstash** — сбор/обработка данных.

**Kibana** — визуализация и поиск.

---

# 🔹 Loki

Другой распространённый вариант:

```text
Application
     ↓
Collector
     ↓
Loki
     ↓
Grafana
```

Loki ориентирован на централизованное хранение и поиск логов и хорошо интегрируется с Grafana.

---

# 🔹 Что нельзя писать в логи

В логи нельзя без необходимости отправлять чувствительные данные:

```text
Пароли
Токены
API keys
Cookie
Полные данные банковских карт
Секреты
```

Например плохо:

```python
logger.info(f"User password: {password}")
```

Также нужно осторожно относиться к персональным данным.

---

# 🔹 Log Rotation

Логи постоянно растут.

Если приложение пишет:

```text
10 GB/day
```

то локальный диск быстро заполнится.

**Log rotation** позволяет:

```text
app.log
app.log.1
app.log.2
app.log.3
```

и удалять/архивировать старые файлы согласно политике хранения.

В централизованных системах аналогичная задача решается через **retention policy**.

---

# 🔹 Log Retention

**Retention** определяет, сколько времени хранятся логи.

Например:

```text
Application logs → 14 дней
Security logs    → 90 дней
Audit logs       → 1 год
```

Конкретный срок зависит от требований системы и регулирования.

---

# 🔹 Ошибки и Stack Trace

При исключениях полезно сохранять traceback.

В Python:

```python
try:
    process_payment()
except Exception:
    logger.exception("Payment processing failed")
```

`logger.exception()` используется внутри `except` и добавляет информацию об исключении вместе с traceback.

Это значительно полезнее:

```python
logger.error("Payment failed")
```

потому что traceback помогает определить место возникновения ошибки.

---

# 🔹 Хороший и плохой лог

### Плохо

```python
logger.error("Something went wrong")
```

Непонятно:

* что произошло;
* где;
* с каким запросом;
* какой объект затронут.

### Лучше

```python
logger.error(
    "Failed to create order",
    extra={
        "order_id": order_id,
        "request_id": request_id,
    },
)
```

Ещё лучше — использовать структурированный logging с явными полями.

# 🔹 Логи в Kubernetes

Для контейнеризированного приложения хороший базовый подход:

```text
Application
     ↓
stdout / stderr
     ↓
Container runtime
     ↓
Log collector
     ↓
Centralized storage
```

Не стоит рассчитывать на локальные файлы внутри контейнера как на долговременное хранилище логов.

Контейнер может быть удалён вместе со своей файловой системой.

# 🔹 Частые вопросы на собеседовании

### Что такое лог?

> Запись о событии, произошедшем в приложении или инфраструктуре, содержащая информацию, необходимую для анализа и диагностики.

### Зачем нужны логи?

> Для диагностики ошибок, расследования событий и понимания контекста работы системы.

### Какие есть уровни логирования?

> Обычно DEBUG, INFO, WARNING, ERROR и CRITICAL.

### Почему logging лучше print?

> Logging поддерживает уровни, handlers, форматирование, фильтрацию и отправку данных в различные системы.

### Что такое structured logging?

> Логирование событий в структурированном формате с отдельными полями, например JSON.

### Что такое Request ID?

> Идентификатор HTTP-запроса, позволяющий связать логи, относящиеся к одному запросу.

### Что такое Trace ID?

> Идентификатор distributed trace, позволяющий связать операции и telemetry одного запроса между сервисами.

### Что такое Log Aggregation?

> Централизованный сбор логов от разных приложений, контейнеров и серверов.

### Зачем нужны Log Levels?

> Чтобы разделять сообщения по важности и управлять объёмом диагностической информации.

### Что такое Log Rotation?

> Механизм ограничения роста локальных log-файлов за счёт ротации, архивирования и удаления старых файлов.

### Что такое retention?

> Политика, определяющая, как долго сохраняются логи.

### Что такое `logger.exception()`?

> Метод Python logging для записи сообщения об ошибке вместе с traceback внутри обработчика исключения.

# 🔑 Главное

```text
                     Logs
                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
    Level          Structured        Context
       │               │                │
 DEBUG/INFO        JSON/fields     request_id
 WARNING/ERROR                     trace_id
 CRITICAL                          service
       │
       ↓
   Log Collector
       ↓
 Central Storage
       ↓
 Search / Dashboard / Alert
```

> **Логи отвечают на вопрос «что произошло и в каком контексте».**

> **Metrics → что происходит с системой.**

> **Logs → что произошло и какие детали.**

> **Traces → через какие компоненты прошёл конкретный запрос.**
