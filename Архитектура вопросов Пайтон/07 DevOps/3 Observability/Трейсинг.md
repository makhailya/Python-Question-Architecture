# 🔎 Трейсинг (Distributed Tracing)

## 🎤 Короткий ответ

**Трейсинг (Tracing)** — это отслеживание пути **одного конкретного запроса** через несколько компонентов распределённой системы.

Он позволяет увидеть:

* через какие сервисы прошёл запрос;
* сколько времени занял каждый этап;
* где произошла ошибка;
* какой сервис или операция стали причиной задержки.

Основные понятия:

> **Trace → Span → Trace ID → Context Propagation.**

---

## 🎯 Формула для собеседования

> **Trace = полный путь запроса, Span = отдельная операция внутри Trace, Trace ID = идентификатор всего запроса.**

Например:

```text id="8k2m4p"
Client
   ↓
API Gateway        20 ms
   ↓
Order Service      50 ms
   ↓
Payment Service   700 ms
   ↓
PostgreSQL        650 ms
```

По Trace сразу видно, что основная задержка находится на этапе обращения к PostgreSQL.

---

# 🔹 Зачем нужен Tracing

В монолите найти проблему относительно просто:

```text id="3m7q9x"
Client
  ↓
Application
  ↓
Database
```

Но в микросервисной архитектуре:

```text id="6p4v8n"
Client
   ↓
API Gateway
   ↓
User Service
   ↓
Order Service
   ↓
Payment Service
   ↓
Notification Service
   ↓
PostgreSQL
   ↓
Redis
```

Если запрос занимает 3 секунды, по одной только метрике:

```text
P95 latency = 3 sec
```

непонятно, **где именно потрачены эти 3 секунды**.

Tracing позволяет разложить запрос:

```text id="9x5m2k"
Total: 3000 ms

Gateway       20 ms
User Service  30 ms
Order Service 100 ms
Payment       850 ms
PostgreSQL    2000 ms
```

---

# 🔹 Trace

**Trace** — это полный путь одного запроса через систему.

Например:

```text id="r7m3qk"
Trace ID: abc123

Client
  │
  └── API Gateway
        │
        └── Order Service
              │
              ├── Redis
              │
              └── PostgreSQL
```

Один Trace может включать десятки или сотни операций.

---

# 🔹 Span

**Span** — отдельная операция внутри Trace.

Например:

```text id="t4q8mx"
Trace
 │
 ├── HTTP GET /orders
 │
 ├── PostgreSQL SELECT
 │
 ├── Redis GET
 │
 └── HTTP POST /payment
```

Каждый Span имеет собственные характеристики:

```text id="m8p3vx"
Operation
Start time
Duration
Service
Status
Attributes
```

Например:

```text id="c5q7mk"
Span:
operation = SELECT orders
service   = order-service
duration  = 120 ms
status    = OK
```

---

# 🔹 Trace ID

**Trace ID** идентифицирует весь запрос.

Например:

```text id="v2m6qx"
trace_id = 7f83b1657ff1
```

Этот ID передаётся между сервисами.

В результате можно связать:

```text id="x8q4mc"
API Gateway
trace_id=7f83b1657ff1

Order Service
trace_id=7f83b1657ff1

Payment Service
trace_id=7f83b1657ff1
```

И найти весь путь одного запроса.

---

# 🔹 Span ID

Кроме Trace ID у каждого Span есть собственный:

```text id="p3m7vx"
span_id
```

Получается:

```text id="n6q2kc"
Trace ID
   │
   ├── Span ID A
   ├── Span ID B
   ├── Span ID C
   └── Span ID D
```

**Trace ID** связывает весь запрос.

**Span ID** идентифицирует конкретную операцию.

---

# 🔹 Parent Span

Spans образуют дерево.

Например:

```text id="q8m4vx"
HTTP Request
│
├── PostgreSQL Query
│
├── Redis GET
│
└── HTTP Payment Request
      │
      └── PostgreSQL Query
```

У дочернего Span есть ссылка на **Parent Span**.

Это позволяет восстановить структуру выполнения.

---

# 🔹 Context Propagation

Самое важное в distributed tracing — передача tracing-контекста между сервисами.

Например:

```text id="m5q8vx"
Service A
   │
   │ trace_id=abc123
   ↓
Service B
   │
   │ trace_id=abc123
   ↓
Service C
```

Service B должен получить tracing context от Service A и передать его дальше.

Иначе трассировка разорвётся.

---

# 🔹 Как передаётся Trace Context

Для HTTP часто используется стандартный механизм **W3C Trace Context**.

В запросе передаётся заголовок:

```text id="w4m7qx"
traceparent
```

Упрощённо:

```text id="9q3m8v"
Client
  ↓
traceparent
  ↓
Service A
  ↓
traceparent
  ↓
Service B
```

Таким образом разные сервисы понимают, что относятся к одному Trace.

---

# 🔹 Пример распределённого запроса

Представим интернет-магазин.

Пользователь:

```text id="a6m2qx"
POST /orders
```

Запрос проходит:

```text id="k8q4mv"
API Gateway
      ↓
Order Service
      ↓
Payment Service
      ↓
Bank API
      ↓
PostgreSQL
```

Tracing может показать:

```text id="j3m7qx"
Trace: abc123

API Gateway       15 ms
Order Service     40 ms
Payment Service  900 ms
Bank API         850 ms
PostgreSQL        30 ms
```

Теперь понятно, что задержка находится не в PostgreSQL, а во внешнем Bank API.

---

# 🔹 Waterfall

Tracing-инструменты часто отображают Trace как **waterfall**.

Упрощённо:

```text id="z4m8qx"
0ms                         1000ms

Gateway    ███
Order         ███████
Payment          █████████████████
Bank API           ███████████████
PostgreSQL             ██
```

По такой диаграмме легко увидеть:

* последовательные операции;
* параллельные операции;
* длительные Span;
* ошибки;
* зависимости между сервисами.

---

# 🔹 Ошибки в Trace

Span может иметь статус:

```text id="r6m3vx"
OK
ERROR
```

Например:

```text id="n8q2mc"
Trace
 │
 ├── API Gateway       OK
 ├── Order Service     OK
 └── Payment Service   ERROR
        │
        └── PostgreSQL timeout
```

Это позволяет быстро определить место сбоя.

---

# 🔹 Tracing и Logs

Tracing и Logs тесно связаны.

Например Span содержит:

```text id="k5m8qx"
trace_id = abc123
span_id  = xyz789
```

А лог:

```python id="v7q3mx"
logger.error(
    "Payment failed",
    extra={
        "trace_id": "abc123",
        "span_id": "xyz789",
    },
)
```

Теперь можно:

```text id="m2q8vx"
Trace
  ↓
конкретный Span
  ↓
Logs
  ↓
детальная ошибка
```

Это называется **корреляцией telemetry**.

---

# 🔹 Tracing и Metrics

Metrics показывают общую картину:

```text id="f4m7qx"
P95 latency = 800 ms
```

Tracing позволяет исследовать конкретный случай:

```text id="p8m3vc"
Trace #123

API        20 ms
Orders     50 ms
Payment   700 ms
```

Получается:

```text id="x6q2mk"
Metrics
   ↓
Обнаружили проблему
   ↓
Tracing
   ↓
Нашли конкретную операцию
   ↓
Logs
   ↓
Нашли детали ошибки
```

# 🔹 Sampling

Tracing может генерировать огромное количество данных.

Например:

```text id="q3m8vx"
1 000 000 запросов
       ↓
1 000 000 traces
```

Хранить всё может быть дорого.

Поэтому используется **sampling** — выборка Trace для сохранения.

Например:

```text id="v5q7mc"
100 000 запросов
       ↓
10% sampling
       ↓
10 000 traces
```

Можно использовать разные стратегии:

* сохранять случайную выборку;
* сохранять ошибки;
* сохранять медленные запросы;
* использовать adaptive/tail sampling.

Особенно полезно сохранять проблемные traces.

---

# 🔹 Head Sampling и Tail Sampling

### Head Sampling

Решение о сохранении Trace принимается в начале обработки.

```text id="h4m8qx"
Request
   ↓
Sampling decision
   ↓
Trace
```

Просто и дёшево, но в начале ещё неизвестно, закончится ли запрос ошибкой.

### Tail Sampling

Решение принимается после того, как Trace уже собран.

```text id="t7m3vx"
Request
   ↓
Trace collected
   ↓
Анализ
   ↓
Save / Drop
```

Например можно сохранять:

```text id="d5q8mk"
ERROR traces
Slow traces
Certain services
```

Tail sampling позволяет лучше сохранять интересные traces, но требует дополнительной инфраструктуры.

# 🔹 OpenTelemetry

**OpenTelemetry (OTel)** — открытый стандарт и набор инструментов для instrumentation и передачи telemetry.

Он работает с:

```text id="o6m3qx"
Metrics
Logs
Traces
```

Для tracing приложение можно инструментировать через OpenTelemetry SDK/API.

Упрощённая схема:

```text id="p4q8vx"
Python Application
        ↓
OpenTelemetry SDK
        ↓
OTel Collector
        ↓
Tracing Backend
```

---

# 🔹 OpenTelemetry Collector

**OpenTelemetry Collector** — отдельный компонент, который может:

* принимать telemetry;
* обрабатывать её;
* фильтровать;
* добавлять атрибуты;
* экспортировать в backend.

Например:

```text id="c7m3qx"
FastAPI
   ↓
OpenTelemetry
   ↓
OTel Collector
   ↓
┌───────────────┐
│ Trace Backend │
└───────────────┘
```

Collector позволяет не привязывать приложение напрямую к конкретной системе хранения.

---

# 🔹 Пример для FastAPI

Приложение:

```python id="f8m4qx"
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"user_id": user_id}
```

После instrumentation tracing может автоматически создавать Span для HTTP-запроса:

```text id="k2q7mv"
GET /users/123

Trace ID: abc123
Duration: 35 ms
Status: 200
```

Также instrumentation может создавать Span для обращений к:

```text id="r5m8qx"
PostgreSQL
Redis
HTTP clients
```

---

# 🔹 Instrumentation

**Instrumentation** — добавление в приложение механизма, который автоматически или вручную создаёт telemetry.

Например:

```text id="z8m3qx"
FastAPI
 ↓
HTTP Span

SQLAlchemy
 ↓
Database Span

Redis client
 ↓
Redis Span
```

Есть:

### Automatic instrumentation

Инструмент автоматически создаёт Span для поддерживаемых библиотек.

### Manual instrumentation

Разработчик сам создаёт Span для важной бизнес-операции.

Например:

```python id="m4q8vx"
with tracer.start_as_current_span("create_order"):
    create_order()
```

---

# 🔹 Что полезно добавлять в Span

Span может содержать attributes:

```text id="v7m2qx"
http.method = POST
http.route = /orders
http.status_code = 200
service.name = order-service
db.system = postgresql
```

Это позволяет фильтровать и анализировать traces.

Но высококардинальные данные нужно добавлять осторожно.

Например, не стоит без необходимости помещать в telemetry:

```text id="x5q8mv"
password
access token
полные персональные данные
```

---

# 🔹 Tracing в Kubernetes

В Kubernetes tracing особенно полезен для микросервисов:

```text id="k3m7qx"
                    Kubernetes
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   order-service   payment-service   user-service
        │                │                │
        └──────────── Trace ──────────────┘
                         ↓
                   Trace Backend
```

Pod может быть уничтожен или пересоздан, но Trace показывает путь конкретного запроса независимо от того, на каком Pod он выполнялся.

# 🔹 Tracing vs Profiling

Это разные инструменты.

### Tracing

Показывает:

> **Где и сколько времени занял конкретный запрос?**

```text id="p7m4qx"
HTTP → Service → DB
```

### Profiling

Показывает:

> **На что процесс тратит CPU и память?**

Например:

```text id="r8q3mc"
CPU:
function_a → 40%
function_b → 30%
function_c → 20%
```

То есть:

```text id="z5m8vx"
Tracing   → путь запроса
Profiling → использование ресурсов процессом
```

# 🔹 Частые вопросы на собеседовании

### Что такое Distributed Tracing?

> Технология отслеживания одного запроса через несколько сервисов распределённой системы.

### Что такое Trace?

> Полный путь одного запроса через систему.

### Что такое Span?

> Отдельная операция внутри Trace.

### Чем Trace ID отличается от Span ID?

> Trace ID идентифицирует весь запрос, Span ID — конкретную операцию внутри него.

### Что такое Parent Span?

> Span, породивший дочернюю операцию; вместе они образуют дерево выполнения.

### Что такое Context Propagation?

> Передача tracing-контекста между сервисами, чтобы операции разных сервисов можно было связать в один Trace.

### Что такое `traceparent`?

> HTTP-заголовок стандарта W3C Trace Context, используемый для передачи tracing-контекста между компонентами.

### Зачем нужен Sampling?

> Чтобы уменьшить объём и стоимость хранения traces, сохраняя наиболее полезную часть данных.

### Что такое OpenTelemetry?

> Открытый набор API, SDK и инструментов для instrumentation, сбора и передачи telemetry, включая traces.

### Что такое Instrumentation?

> Добавление в приложение механизма сбора telemetry, автоматически или вручную.

### Tracing vs Logs?

> Tracing показывает путь и длительность операций запроса, Logs дают детальные записи событий.

### Tracing vs Metrics?

> Metrics показывают агрегированное состояние системы, Tracing позволяет исследовать конкретные запросы.

### Tracing vs Profiling?

> Tracing показывает путь запроса, Profiling показывает, какие функции и ресурсы потребляют время CPU или память.

# 🔑 Главное

```text id="n4m8qx"
                       Trace
                         │
                  Trace ID = abc123
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
      Span             Span             Span
        │                │                │
    API Gateway      Order Service    PostgreSQL
      20 ms             50 ms            700 ms
        │                │                │
        └────────────────┼────────────────┘
                         ↓
                  Полный путь запроса
```

> **Trace** → весь путь запроса
> **Span** → отдельная операция
> **Trace ID** → идентификатор всего запроса
> **Span ID** → идентификатор операции
> **Context Propagation** → передача контекста между сервисами
> **Sampling** → выборка traces
> **OpenTelemetry** → стандартный инструментарий для telemetry
> **Tracing** → помогает найти, **где именно запрос стал медленным или упал**
