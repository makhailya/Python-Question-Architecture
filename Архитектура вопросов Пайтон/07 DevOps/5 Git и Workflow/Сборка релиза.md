# 🚀 Сборка релиза

## 🎤 Короткий ответ

**Сборка релиза** — это процесс подготовки конкретной версии приложения к выпуску: код собирается, устанавливаются зависимости, выполняются тесты и проверки, создаются артефакты (например, Docker Image), после чего эта версия готова к развёртыванию.

Типичный процесс:

**Git → Build → Tests → Checks → Artifact → Version/Tag → Deploy**

---

## 🎯 Формула для собеседования

> **Сборка релиза = взять конкретную версию кода → проверить её → собрать воспроизводимый артефакт → пометить версией → передать на развёртывание.**

Главная идея: **в production должна попасть не просто "последняя версия кода", а конкретный проверенный артефакт определённой версии.**

---

## 📦 Что такое релиз

**Релиз (Release)** — версия приложения, которую подготовили для доставки пользователям или развёртывания в production.

Например:

```python
v1.4.0
```

В релиз могут входить:

* исходный код;
* зависимости;
* конфигурация;
* миграции БД;
* Docker Image;
* документация;
* release notes.

## 1. Фиксируем версию кода

Для релиза нужно точно определить, какой код мы выпускаем.

Например:

```python
git checkout main
git pull
git tag v1.4.0
```

Tag позволяет однозначно определить состояние репозитория.

Например:

```python
v1.4.0 → commit a8f31c2
```

Это важно для:

* воспроизводимости;
* rollback;
* аудита;
* понимания, какой код находится в production.

---

# 2. Установка зависимостей

CI устанавливает зависимости проекта.

Для Poetry:

```python
poetry install
```

Или:

```python
poetry install --only main
```

Зависимости должны фиксироваться lock-файлом:

```python
poetry.lock
```

Это позволяет получить предсказуемое окружение.

---

# 3. Запуск тестов

Перед сборкой релиза запускаются автоматические тесты.

Например:

```python
pytest
```

Дополнительно могут запускаться:

```python
flake8 .
black --check .
mypy .
```

То есть проверяется:

* корректность кода;
* тесты;
* стиль;
* типы;
* безопасность;
* зависимости.

Если проверка не прошла — релиз обычно не собирается.

---

# 4. Сборка артефакта

**Артефакт** — результат сборки, который можно передать дальше на развёртывание.

Например:

```python
Docker Image
```

Для Python Backend:

```python
docker build -t my-api:v1.4.0 .
```

Получаем:

```python
my-api:v1.4.0
```

Теперь production разворачивает именно этот Image.

---

# 🐳 Почему Docker удобен для релизов

Без контейнера можно получить ситуацию:

```python
Код
 ↓
Python 3.13
 ↓
Зависимости
 ↓
Production
```

Но окружение может отличаться.

С Docker:

```python
Dockerfile
    ↓
Docker Image
    ↓
Container
```

Image содержит:

* приложение;
* зависимости;
* runtime;
* системные зависимости;
* инструкции запуска.

Поэтому один и тот же Image можно использовать в:

```python
Test → Staging → Production
```

# 🏷️ Версионирование

Часто используется **Semantic Versioning (SemVer)**:

```python
MAJOR.MINOR.PATCH
```

Например:

```python
1.4.2
```

### MAJOR

Несовместимые изменения API:

```python
1.4.2 → 2.0.0
```

### MINOR

Новая функциональность без нарушения совместимости:

```python
1.4.0 → 1.5.0
```

### PATCH

Исправление ошибок:

```python
1.4.0 → 1.4.1
```

# 📌 Tag + Docker Image

Хорошая практика — связывать версию Git и Image:

```python
Git:

```

Ещё надёжнее использовать commit SHA:

```python

```

Тогда можно точно определить, из какого commit собран Image.

Docker Registry

# 🧪 Test → Staging → Production

Один из распространённых подходов:

```python
Build Image
     ↓
   Test
     ↓
  Staging
     ↓
Production
```

При этом желательно использовать **тот же самый артефакт**.

Например:

```python
my-api:v1.4.0
```

сначала тестируется в staging, а затем этот же Image отправляется в production.

Не стоит заново собирать Image между staging и production, иначе содержимое потенциально может отличаться.

# 🔐 Конфигурация и секреты

Секреты не должны попадать внутрь Docker Image.

Плохо:

```python
DATABASE_PASSWORD=123456
```

в Dockerfile.

Лучше:

```python
Container
    ↓
Environment Variables / Secret Manager
    ↓
Application
```

Например:

```python
DATABASE_URL
REDIS_URL
SECRET_KEY
```

В Kubernetes для этого используются:

* ConfigMap;
* Secret;
* внешние Secret Manager.

# 🗃️ Миграции базы данных

Если релиз меняет структуру БД, в pipeline может присутствовать этап миграции.

Например, Django:

```python
python manage.py migrate
```

Alembic:

```python
alembic upgrade head
```

Важно учитывать совместимость:

```python
Application v1
       ↓
Database
       ↓
Migration
       ↓
Application v2
```

Миграции должны выполняться контролируемо, особенно при rolling deployment.

---

# ↩️ Rollback

Если новый релиз работает неправильно, необходимо иметь возможность вернуться к предыдущей версии.

Например:

```python
Production
    ↓
v1.4.0 ❌
    ↓
rollback
    ↓
v1.3.2 ✅
```

Если Docker Images версионируются:

```python
my-api:v1.3.2
my-api:v1.4.0
```

rollback становится значительно проще.

# 🧱 Воспроизводимость сборки

**Воспроизводимая сборка** означает, что из одного и того же исходного состояния можно получить одинаковый или эквивалентный артефакт.

Для этого фиксируют:

* версию кода;
* зависимости;
* lock-файл;
* базовый Docker Image;
* параметры сборки.

Например:

```python
Git commit
+
poetry.lock
+
Dockerfile
+
Base Image
        ↓
Reproducible Build
```

# 🆚 Сборка vs релиз vs деплой

| Понятие      | Что означает                            |
| ------------ | --------------------------------------- |
| **Build**    | Собрать приложение/артефакт             |
| **Release**  | Подготовить конкретную версию к выпуску |
| **Deploy**   | Развернуть артефакт в окружении         |
| **Rollback** | Вернуться к предыдущей версии           |

Пример:

```python
Code
 ↓
Build
 ↓
Artifact v1.4.0
 ↓
Release
 ↓
Deploy
 ↓
Production
```

# 🆚 CI vs CD

**CI (Continuous Integration)**:

```python
commit
 ↓
build
 ↓
tests
 ↓
checks
```

Проверяет, что изменения можно интегрировать.

**CD (Continuous Delivery/Deployment)**:

```python
tested artifact
       ↓
    staging
       ↓
 production
```

Доставляет проверенный артефакт дальше.

# ⚠️ Типичные проблемы

### Сборка зависит от текущего состояния окружения

Например:

```python
Works on developer's machine
        ↓
Fails in CI
```

Решение:

* Docker;
* lock-файлы;
* фиксированные версии;
* CI.

### В production попал не тот commit

Решение:

```python
Git Tag
+
Commit SHA
+
Versioned Artifact
```

### Нельзя сделать rollback

Причины:

* Image перезаписан;
* нет версий;
* миграция БД необратима;
* старый артефакт удалён.

### Секреты попали в Image

Нужно хранить секреты отдельно от артефакта.

# 🎤 Как рассказать на собеседовании

> **Сборка релиза — это процесс подготовки конкретной версии приложения к развёртыванию. Обычно CI берёт определённый commit, устанавливает фиксированные зависимости, запускает тесты и проверки, после чего собирает артефакт, например Docker Image. Артефакт получает версию или commit SHA, отправляется в Registry и затем разворачивается через CD. Такой подход позволяет воспроизводимо доставлять одну и ту же проверенную версию в staging и production и при необходимости делать rollback.**

# ❓ Частые вопросы на собеседовании

### Что является результатом сборки?

**Артефакт**, например:

* Docker Image;
* wheel-пакет Python;
* архив приложения;
* бинарный файл.

### Зачем нужна версия релиза?

Чтобы однозначно определить, какая версия приложения была собрана и развёрнута.

### Зачем нужен Docker Registry?

Для хранения и доставки собранных Docker Images.

### Почему нельзя просто собрать приложение прямо на production?

Это делает окружение менее предсказуемым и усложняет контроль версии и rollback.

### Что такое rollback?

Возврат production на предыдущую проверенную версию.

### Должен ли staging и production использовать один и тот же Image?

В хорошо организованном pipeline — **да, желательно продвигать один и тот же проверенный артефакт**, а не пересобирать его заново.

### Где должны храниться секреты?

Вне Docker Image и исходного кода — например, в Secret Manager, Kubernetes Secret или переменных окружения, в зависимости от инфраструктуры.
