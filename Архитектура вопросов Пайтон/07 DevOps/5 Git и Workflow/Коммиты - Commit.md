# 📌 Коммиты в Git

## 🎤 Короткий ответ

**Commit** — это зафиксированная точка в истории Git, которая сохраняет состояние проекта и информацию об изменениях.

Типичный путь:

```text
Working Directory
       ↓ git add
Staging Area
       ↓ git commit
Commit
       ↓ git push
Remote Repository
```

Создание коммита:

```bash
git add .
git commit -m "Add user authentication"
```

Каждый коммит имеет уникальный идентификатор, родительские коммиты, автора, время создания и сообщение.

---

## 🗣️ Ответ на собеседовании

Коммит — это объект Git, который фиксирует определённое состояние проекта в истории.

Перед созданием коммита изменения сначала попадают в staging area через `git add`. Затем `git commit` создаёт запись в истории, содержащую информацию о состоянии проекта, авторе, времени, сообщении и родительском коммите.

Коммиты образуют граф истории:

```text
A ── B ── C
```

Обычный коммит имеет одного родителя, а merge-коммит может иметь несколько.

Важно, что коммит создаётся **локально**. `git push` нужен уже для передачи локальных коммитов в удалённый репозиторий.

Коммиты позволяют просматривать историю, сравнивать изменения, возвращаться к предыдущим состояниям и организовывать работу с ветками.

## 📚 Разбор поглубже

### 1. Что такое commit

Коммит — это **зафиксированное состояние проекта** в определённый момент времени.

Например:

```text
A ── B ── C
```

Можно представить:

```text
A → первая версия
B → добавили авторизацию
C → добавили тесты
```

Каждый коммит позволяет восстановить соответствующее состояние проекта.

---

### 2. Как создаётся коммит

Изменяем файл:

```python
def hello():
    return "Hello"
```

Проверяем:

```bash
git status
```

Добавляем изменения в staging:

```bash
git add app.py
```

Создаём commit:

```bash
git commit -m "Add hello function"
```

Получается:

```text
Working Directory
       ↓
    git add
       ↓
Staging Area
       ↓
  git commit
       ↓
    Commit
```

---

### 3. Коммит создаётся из staging

Очень важно:

```bash
git commit
```

не означает:

> «возьми вообще все изменения в папке».

Git фиксирует то, что находится в **staging area**.

Например:

```text
Изменены:
├── app.py
├── models.py
└── tests.py
```

Добавили только:

```bash
git add app.py
```

Тогда commit может содержать изменения только `app.py`.

---

### 4. Один commit может содержать изменения нескольких файлов

Например:

```bash
git add app.py models.py tests.py
git commit -m "Add user model"
```

Один commit может зафиксировать изменения сразу в нескольких файлах.

Поэтому commit — это не обязательно:

```text
1 файл = 1 commit
```

Логическая единица коммита — **набор связанных изменений**.

---

### 5. Commit имеет идентификатор

Каждый commit получает идентификатор на основе SHA-1 в традиционной модели Git.

Например:

```text
a83f1e2b9c...
```

В `git log --oneline` обычно отображается сокращённый вариант:

```bash
git log --oneline
```

Например:

```text
a83f1e2 Add authentication
c72b913 Add user model
4d8a210 Initial commit
```

По этому идентификатору можно ссылаться на конкретный commit.

---

### 6. Из чего состоит commit

Упрощённо commit содержит:

```text
Commit
├── ссылка на tree
├── parent commit
├── author
├── committer
├── timestamp
└── message
```

### `tree`

Указывает на структуру файлов проекта в этом состоянии.

### `parent`

Указывает на предыдущий commit.

### `author`

Автор изменений.

### `committer`

Тот, кто создал данный commit-объект.

### `message`

Описание коммита.

---

### 7. Commit и история

Обычная история:

```text
A ── B ── C ── D
```

Например:

```text
A  Initial commit
│
B  Add database
│
C  Add authentication
│
D  Add tests
```

Каждый следующий commit ссылается на предыдущий.

Получается цепочка:

```text
D
↓
C
↓
B
↓
A
```

---

### 8. Commit-граф

Git на самом деле хранит историю как **граф**, а не просто как линейный список.

Например:

```text
A ── B ── C
      \
       D ── E
```

Здесь две ветки истории.

```text
main
A ── B ── C

feature
     \
      D ── E
```

Это особенно важно при изучении `merge` и `rebase`.

---

### 9. Parent commit

Обычный commit имеет одного родителя.

```text
A ── B ── C
```

Для:

```text
C
```

родитель:

```text
B
```

Для первого commit родителя обычно нет.

---

### 10. Merge commit

После merge может появиться commit с двумя родителями:

```text
      C
     / \
A ── B   M
     \ /
      D
```

У `M`:

```text
parent 1 → C
parent 2 → D
```

Поэтому commit-граф может иметь разветвления и слияния.

---

### 11. Commit и Branch

Ветка — это не контейнер, внутри которого находятся commits.

Упрощённо branch — это **ссылка на commit**.

```text
A ── B ── C
          ↑
         main
```

После нового commit:

```text
A ── B ── C ── D
               ↑
              main
```

Ветка просто переместилась на новый commit.

---

### 12. HEAD

`HEAD` указывает на текущую позицию пользователя.

Например:

```text
HEAD
 ↓
main
 ↓
C
```

После нового commit:

```text
HEAD
 ↓
main
 ↓
D
```

Поэтому:

```bash
git log
```

показывает историю начиная с текущей позиции.

---

### 13. Посмотреть историю

Основная команда:

```bash
git log
```

Компактный вариант:

```bash
git log --oneline
```

Граф:

```bash
git log --oneline --graph --decorate --all
```

Очень полезный вариант для понимания веток:

```bash
git log --oneline --graph --decorate --all
```

Он показывает:

* commits;
* ветки;
* HEAD;
* связи между commit;
* merge.

---

### 14. Посмотреть конкретный commit

```bash
git show <commit>
```

Например:

```bash
git show a83f1e2
```

Можно увидеть:

* информацию о commit;
* автора;
* дату;
* сообщение;
* изменения файлов.

---

### 15. Commit vs изменения

Git хранит историю не просто как набор команд:

```text
изменить строку 10
удалить строку 20
добавить строку 30
```

Коммит описывает определённое состояние дерева файлов через Git objects.

Концептуально:

```text
Commit
   ↓
Tree
   ├── app.py → Blob
   ├── models.py → Blob
   └── tests/ → Tree
```

Это помогает понять внутреннюю модель Git.

---

### 16. Blob, Tree, Commit

Основные объекты Git:

```text
Git Objects
├── Blob
│   └── содержимое файла
├── Tree
│   └── структура каталогов и ссылки на файлы
├── Commit
│   └── состояние + metadata + parent
└── Tag
    └── именованная ссылка на объект
```

Для понимания commit достаточно помнить:

```text
Commit
   ↓
Tree
   ↓
состояние файлов
```

---

### 17. Commit не равен `git push`

Это частая ошибка новичков.

```bash
git commit -m "Add feature"
```

создаёт commit **локально**.

Он ещё не обязательно находится на GitHub/GitLab.

Чтобы отправить его:

```bash
git push
```

Получаем:

```text
git commit
    ↓
Local Repository
    ↓ git push
Remote Repository
```

---

### 18. Хороший commit

В командной разработке желательно, чтобы commit был:

* логически целостным;
* небольшим настолько, насколько это разумно;
* понятным по сообщению;
* не смешивал несвязанные задачи.

Например:

```text
Add JWT authentication
```

лучше, чем:

```text
fix
```

Ещё хуже:

```text
changes
```

Хорошее сообщение отвечает на вопрос:

> Что было изменено?

---

### 19. Atomic commit

Полезное понятие — **атомарный коммит**.

Идея:

> один commit содержит одну логически завершённую задачу или изменение.

Например:

```text
Add JWT authentication
```

может содержать:

```text
auth service
JWT validation
tests
```

если это части одной логической задачи.

А вот:

```text
Add JWT + refactor database + change README + fix CSS
```

смешивает несколько независимых задач и затрудняет review и откат.

---

### 20. Commit message

Формат зависит от командного соглашения.

Один распространённый вариант:

```text
feat: add JWT authentication
fix: handle expired token
refactor: extract user service
test: add authentication tests
docs: update README
```

Это соответствует подходу **Conventional Commits**.

Но конкретный формат определяется правилами проекта.

---

### 21. Изменение последнего commit

Если забыли добавить файл:

```bash
git add forgotten.py
git commit --amend
```

Это изменяет последний commit.

Можно изменить только сообщение:

```bash
git commit --amend -m "Add authentication"
```

Важно:

> `--amend` переписывает последний commit.

Поэтому с уже опубликованными коммитами нужно использовать осторожно.

---

### 22. Отмена commit: `revert`

Если commit уже опубликован и нужно отменить его изменения:

```bash
git revert <commit>
```

Git создаст новый commit:

```text
A ── B ── C ── D
          ↑    ↑
        bad   revert
```

`D` отменяет изменения `C`.

История при этом сохраняется.

---

### 23. Удаление последнего commit: `reset`

Можно переместить `HEAD` назад:

```bash
git reset HEAD~1
```

В зависимости от режима изменится состояние staging и working tree.

Например:

```bash
git reset --soft HEAD~1
```

уберёт commit, но оставит изменения подготовленными в staging.

```bash
git reset --mixed HEAD~1
```

уберёт commit и staging, но сохранит изменения в рабочей директории.

```bash
git reset --hard HEAD~1
```

может удалить изменения из working tree.

---

### 24. `reset` vs `revert`

|                            | `reset`                     | `revert`                                 |
| -------------------------- | --------------------------- | ---------------------------------------- |
| Что делает                 | Перемещает историю/HEAD     | Создаёт новый commit                     |
| Старый commit              | Может стать недостижимым    | Остаётся в истории                       |
| История                    | Может переписываться        | Не переписывается                        |
| Для опубликованной истории | Осторожно                   | Обычно подходит лучше                    |
| Типичный сценарий          | Исправить локальную историю | Безопасно отменить опубликованный commit |

---

### 25. Commit и `diff`

До commit можно посмотреть изменения:

```bash
git diff
```

После:

```bash
git diff HEAD
```

можно увидеть различия между рабочим состоянием и текущим commit.

А между двумя commit:

```bash
git diff <commit1> <commit2>
```

Например:

```bash
git diff a83f1e2 c72b913
```

---

### 26. Commit и checkout / switch

Можно переключиться на конкретный commit:

```bash
git switch --detach <commit>
```

Например:

```bash
git switch --detach a83f1e2
```

Теперь `HEAD` не указывает на обычную ветку.

Это называется:

**detached HEAD**.

Состояние удобно для просмотра или проверки старой версии, но если делать новые commits, нужно понимать, что они не будут автоматически принадлежать существующей ветке.

---

### 27. Почему нельзя бездумно менять опубликованные commits

Представим:

```text
Remote:
A ── B ── C

Local:
A ── B ── C'
```

Если локально переписали историю через:

```bash
git rebase
```

или:

```bash
git commit --amend
```

старый commit может получить новый hash.

При попытке `push` Git может отклонить обновление.

Для принудительного обновления существует:

```bash
git push --force-with-lease
```

Но это операция, которую следует выполнять осознанно, поскольку она может переписать историю удалённой ветки.

---

### 28. Безопасный принцип работы с историей

Упрощённо:

```text
Локальная личная ветка
→ историю можно переписывать осторожно

Общая опубликованная ветка
→ историю лучше не переписывать
→ используем revert для отмены
```

Особенно важно это понимать при `rebase`, `reset`, `amend` и force push.

## 🎤 Вопросы на собеседовании

**Что такое commit?**

Зафиксированная точка истории Git, содержащая состояние проекта и метаданные, включая родительский commit.

**Где создаётся commit после `git commit`?**

В локальном репозитории. Для отправки его на remote используется `git push`.

**Что находится в commit?**

Ссылка на tree, родительский commit или commits, author, committer, timestamp и commit message.

**Сколько родителей у обычного commit?**

Обычно один. У merge commit может быть два и более.

**Что такое commit hash?**

Идентификатор Git-объекта commit, используемый для ссылки на конкретную точку истории.

**Что такое atomic commit?**

Логически целостный commit, содержащий одну связанную задачу или изменение.

**Что делает `git commit --amend`?**

Перезаписывает последний commit, например добавляя забытые изменения или изменяя сообщение.

**Как отменить уже опубликованный commit?**

Обычно через:

```bash
git revert <commit>
```

Он создаёт новый commit, отменяющий изменения исходного.

**Чем `reset` отличается от `revert`?**

`reset` может переписать историю, переместив `HEAD`, а `revert` создаёт новый commit с обратными изменениями.

**Что такое merge commit?**

Commit, который объединяет две или более линии истории и поэтому обычно имеет несколько родителей.

**Что такое `HEAD`?**

Ссылка на текущую позицию в истории Git, обычно через текущую ветку.

**Как посмотреть историю?**

```bash
git log
git log --oneline
git log --oneline --graph --decorate --all
```

**Как посмотреть конкретный commit?**

```bash
git show <commit>
```

**Формула для собеседования:**

> **Commit — это зафиксированная точка истории Git. Он создаётся из изменений staging area, имеет hash, metadata, ссылку на состояние файлов и parent commit. Обычные commits образуют историю, merge commits могут иметь нескольких родителей. `commit` сохраняет изменения локально, а `push` отправляет их в remote.**
