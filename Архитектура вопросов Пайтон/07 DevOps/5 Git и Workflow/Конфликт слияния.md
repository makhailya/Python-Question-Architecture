# ⚔️ Конфликт слияния в Git

## 🎤 Короткий ответ

**Конфликт слияния (merge conflict)** возникает, когда Git не может автоматически объединить изменения из двух веток.

Чаще всего это происходит, когда обе ветки изменили **один и тот же участок файла несовместимым образом**.

Git останавливает merge и помечает конфликт:

```text
<<<<<<< HEAD
версия текущей ветки
=======
версия другой ветки
>>>>>>> feature
```

Я вручную выбираю или объединяю правильный вариант, удаляю конфликтные маркеры, затем:

```bash
git add .
git commit
```

Если конфликт возник при `rebase`, после `git add` используется:

```bash
git rebase --continue
```

---

## 🗣️ Ответ на собеседовании

> Конфликт слияния возникает, когда Git не может автоматически определить, как объединить изменения из двух веток.
>
> Например, если в `main` и `feature` изменили одну и ту же строку по-разному, Git не может решить, какой вариант правильный. Он останавливает merge и добавляет в файл специальные маркеры конфликта.
>
> Я открываю конфликтующий файл, анализирую обе версии, выбираю одну или объединяю их вручную, удаляю маркеры и сохраняю файл.
>
> После этого при обычном merge выполняю `git add` и `git commit`. Если конфликт возник во время rebase — `git add` и `git rebase --continue`.
>
> Если я понимаю, что не хочу продолжать операцию, могу использовать `git merge --abort` или `git rebase --abort`.
>
> Важно, что конфликт — это не ошибка Git. Это ситуация, когда Git не может принять решение за разработчика.

# 📚 Разбор поглубже

## 1. Что такое конфликт слияния

Представим две ветки:

```text
A---B---C  main
     \
      D---E  feature
```

В `main` изменили одну строку:

```python
timeout = 10
```

→

```python
timeout = 30
```

А в `feature` эту же строку изменили иначе:

```python
timeout = 60
```

Когда Git пытается объединить ветки:

```bash
git switch main
git merge feature
```

он обнаруживает:

```text
main:    10 → 30
feature: 10 → 60
```

Git не знает, какое значение должно быть итоговым.

Возникает:

```text
CONFLICT
```

---

# 2. Как Git показывает конфликт

Файл может превратиться в:

```python
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature
```

Здесь:

```text
<<<<<<< HEAD
```

начало текущей версии.

```text
=======
```

разделитель двух вариантов.

```text
>>>>>>> feature
```

конец версии из другой ветки.

Это **служебные маркеры Git**, а не код Python.

---

# 3. Что означают две стороны

Допустим, выполняется:

```bash
git switch main
git merge feature
```

Тогда:

```text
HEAD
 ↓
main
```

и:

```text
feature
```

— ветка, изменения которой мы вливаем.

Получаем:

```text
<<<<<<< HEAD
версия main
=======
версия feature
>>>>>>> feature
```

Удобная модель:

```text
<<<<<<< HEAD
        ↓
текущая ветка

=======

другая сторона
        ↓
>>>>>>> feature
```

---

# 4. Как разрешить конфликт

Допустим, Git показал:

```python
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature
```

Мы решили, что правильный вариант:

```python
timeout = 60
```

Тогда файл должен стать:

```python
timeout = 60
```

Нужно удалить все маркеры:

```text
<<<<<<<
=======
>>>>>>>
```

После этого:

```bash
git add app.py
```

Git понимает:

> Конфликт в `app.py` разрешён.

Затем:

```bash
git commit
```

Merge завершается.

---

# 5. Полный алгоритм разрешения Merge Conflict

```text
git merge feature
        │
        ▼
    CONFLICT
        │
        ▼
   git status
        │
        ▼
Открыть конфликтующие файлы
        │
        ▼
Выбрать / объединить изменения
        │
        ▼
Удалить conflict markers
        │
        ▼
     git add
        │
        ▼
     git commit
        │
        ▼
      готово
```

Команды:

```bash
git switch main
git merge feature

git status

# исправляем конфликтующие файлы

git add .
git commit
```

---

# 6. `git status` во время конфликта

После возникновения конфликта:

```bash
git status
```

может показать:

```text
You have unmerged paths.

Unmerged paths:
  both modified:   app.py
```

Это означает, что Git видит конфликт и ожидает от разработчика его разрешения.

После исправления:

```bash
git add app.py
```

снова:

```bash
git status
```

Конфликтующий файл больше не должен находиться среди `unmerged paths`.

---

# 7. Не обязательно просто выбрать одну сторону

Самый важный момент: разрешение конфликта не всегда означает:

> «Оставить `ours` или `theirs`».

Можно объединить изменения.

Например:

```python
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature
```

Можно решить, что правильный результат:

```python
timeout = 45
```

Или вообще изменить архитектуру:

```python
timeout = config.DEFAULT_TIMEOUT
```

Git не знает бизнес-логику.

Он только показывает:

> «Я не смог автоматически получить итоговый вариант».

---

# 8. Конфликт ≠ ошибка Git

Конфликт — нормальная ситуация при совместной разработке.

Например:

```text
Developer A
     │
     ▼
main
     │
     └── изменил app.py


Developer B
     │
     ▼
feature
     │
     └── изменил app.py
```

Когда изменения встречаются:

```text
main ───────┐
            ├── merge → конфликт
feature ────┘
```

Это не означает, что Git работает неправильно.

Git просто не может определить, какое изменение соответствует требованиям проекта.

---

# 9. Конфликт может быть не только при Merge

Конфликты возможны при разных операциях.

### Merge

```bash
git merge feature
```

При конфликте:

```bash
git add .
git commit
```

Отмена:

```bash
git merge --abort
```

### Rebase

```bash
git rebase main
```

При конфликте:

```bash
git add .
git rebase --continue
```

Отмена:

```bash
git rebase --abort
```

### Stash

Даже:

```bash
git stash pop
```

может привести к конфликту, если текущий код уже изменился.

---

# 10. Merge Conflict vs Rebase Conflict

|                             | Merge               | Rebase                  |
| --------------------------- | ------------------- | ----------------------- |
| Может возникнуть конфликт   | ✅                   | ✅                       |
| Нужно исправить файлы       | ✅                   | ✅                       |
| `git add` после исправления | ✅                   | ✅                       |
| Продолжение                 | `git commit`        | `git rebase --continue` |
| Отмена                      | `git merge --abort` | `git rebase --abort`    |

Запомнить можно так:

```text
MERGE
  conflict
     ↓
  fix
     ↓
git add
     ↓
git commit
```

```text
REBASE
  conflict
     ↓
  fix
     ↓
git add
     ↓
git rebase --continue
```

# 11. `ours` и `theirs`

Git позволяет выбрать одну сторону конфликта целиком.

Например:

```bash
git restore --ours app.py
```

Оставить вариант текущей стороны.

Или:

```bash
git restore --theirs app.py
```

Оставить incoming-вариант.

После этого:

```bash
git add app.py
```

⚠️ Здесь важно не запоминать `ours = всегда main`, `theirs = всегда feature`.

Их смысл зависит от **контекста конкретной операции**. Особенно это важно при rebase.

# 12. Конфликт в нескольких файлах

Например:

```text
CONFLICT in:
    app.py
    models.py
    tests/test_auth.py
```

Сначала:

```bash
git status
```

Затем исправляем:

```text
app.py
models.py
tests/test_auth.py
```

Добавляем:

```bash
git add app.py
git add models.py
git add tests/test_auth.py
```

И завершаем merge:

```bash
git commit
```

Можно использовать:

```bash
git add .
```

если ты уверен, что все изменения в рабочей директории нужно включить.

---

# 13. Как отменить Merge Conflict

Если конфликтов много и проще начать заново:

```bash
git merge --abort
```

Git попытается вернуть состояние, которое было до начала merge.

Например:

```bash
git merge feature

# возникли многочисленные конфликты

git merge --abort
```

После этого можно:

* обновить ветку;
* обсудить изменения с коллегой;
* выбрать другой способ интеграции;
* повторить merge позже.

# 14. Конфликт при Pull Request

На GitHub конфликт может возникнуть в Pull Request.

Например:

```text
main:
A---B---C---F---G

feature:
     \
      D---E
```

Pull Request создавался, когда `main` была на `C`.

Потом `main` получила:

```text
F---G
```

и изменения пересеклись с `feature`.

GitHub может показать:

```text
This branch has conflicts that must be resolved.
```

Один из вариантов решения — обновить feature-ветку локально:

```bash
git fetch origin
git switch feature
git rebase origin/main
```

Разрешить конфликты:

```bash
git add .
git rebase --continue
```

После rebase опубликованную feature-ветку обычно обновляют:

```bash
git push --force-with-lease
```

Если такой workflow разрешён правилами проекта.

# 15. Логический конфликт

Очень важно отличать **технический merge conflict** от логической проблемы.

### Технический конфликт

Git остановился:

```text
<<<<<<<
=======
>>>>>>>
```

### Логическая проблема

Git успешно объединил код:

```python
if user:
    return user
```

Но программа после объединения работает неправильно.

Второго случая Git может вообще не обнаружить.

Поэтому после разрешения конфликта нужно запускать:

```bash
pytest
```

и другие проверки проекта.

---

# 16. Почему тесты особенно важны после конфликта

Предположим:

```text
main:
изменение API

feature:
изменение тестов
```

Git может успешно объединить их текстово.

Но итоговая комбинация может быть несовместимой:

```text
API изменился
   ↓
старый тест
   ↓
FAIL
```

Поэтому:

```text
разрешить конфликт
       ↓
git add
       ↓
завершить merge
       ↓
pytest / CI
```

Разрешённый Git-конфликт ещё не означает корректный код.

# 17. Как уменьшить количество конфликтов

Полностью избежать конфликтов нельзя, но можно уменьшить их количество.

### Чаще синхронизировать feature

```bash
git fetch origin
git rebase origin/main
```

или согласно workflow команды использовать merge.

### Делать небольшие commits

Вместо:

```text
Huge feature
```

лучше:

```text
Add repository
Add service
Add endpoint
Add tests
```

### Не смешивать независимые изменения

Например, не стоит одновременно:

```text
переписывать архитектуру
+
форматировать весь проект
+
добавлять новую feature
```

Это увеличивает область изменений и усложняет разрешение конфликтов.

### Не изменять без необходимости одни и те же участки

Если два разработчика постоянно редактируют один файл, вероятность конфликтов выше.

# 18. Инструменты для разрешения конфликтов

Конфликты можно разрешать:

* непосредственно в IDE;
* через VS Code;
* через PyCharm;
* через командную строку;
* через GitHub UI для некоторых сценариев.

В IDE обычно отображаются три области:

```text
Current
Incoming
Result
```

Условно:

```text
┌─────────────┬─────────────┐
│ Current     │ Incoming    │
│ main        │ feature     │
└─────────────┴─────────────┘
             │
             ▼
          Result
```

Это удобнее для сложных конфликтов, чем редактирование маркеров вручную.

# 19. Полезные команды

| Команда                     | Назначение                     |
| --------------------------- | ------------------------------ |
| `git status`                | Посмотреть конфликтующие файлы |
| `git diff`                  | Посмотреть изменения           |
| `git diff --ours`           | Посмотреть текущую сторону     |
| `git diff --theirs`         | Посмотреть incoming-сторону    |
| `git restore --ours file`   | Взять текущую версию файла     |
| `git restore --theirs file` | Взять incoming-версию          |
| `git add file`              | Отметить конфликт разрешённым  |
| `git merge --abort`         | Отменить merge                 |
| `git rebase --abort`        | Отменить rebase                |
| `git rebase --continue`     | Продолжить rebase              |

## 🎤 Вопросы на собеседовании

### Что такое конфликт слияния?

> Ситуация, когда Git не может автоматически объединить изменения из двух веток.

### Когда возникает merge conflict?

> Например, когда две ветки несовместимо изменили один участок файла или одна ветка удаляет изменения, которые другая изменяет.

### Как Git показывает конфликт?

```text
<<<<<<< HEAD
=======
>>>>>>> feature
```

### Что делать после исправления конфликта при merge?

```bash
git add .
git commit
```

### Что делать после исправления конфликта при rebase?

```bash
git add .
git rebase --continue
```

### Как отменить merge с конфликтом?

```bash
git merge --abort
```

### Как отменить rebase?

```bash
git rebase --abort
```

### Что такое `ours` и `theirs`?

> Это способы выбрать одну из сторон конфликта. Их точное значение зависит от контекста операции.

### Можно ли просто выбрать `ours` или `theirs`?

> Можно технически, но не всегда правильно логически. Нужно понимать смысл изменений и иногда вручную объединять обе версии.

### Означает ли отсутствие конфликта, что код корректен?

> Нет. Git проверяет возможность объединить изменения, но не понимает бизнес-логику. После разрешения конфликтов нужны тесты и CI-проверки.

### Главная формула

> **Конфликт слияния = Git не смог решить, как объединить изменения → разработчик выбирает или объединяет варианты → `git add` → завершает merge или rebase.**
