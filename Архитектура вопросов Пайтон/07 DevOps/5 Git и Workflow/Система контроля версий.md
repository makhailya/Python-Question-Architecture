# 🗂️ Система контроля версий

## 🎤 Короткий ответ

**Система контроля версий (VCS, Version Control System)** — это инструмент для отслеживания изменений в файлах проекта и управления историей этих изменений.

Она позволяет:

* хранить историю изменений;
* видеть, кто и что изменил;
* возвращаться к предыдущим версиям;
* работать нескольким разработчикам одновременно;
* создавать отдельные ветки разработки;
* объединять изменения.

Наиболее распространённая распределённая система контроля версий — **Git**.

---

## 🗣️ Ответ на собеседовании

Система контроля версий — это программный инструмент, который позволяет управлять изменениями в исходном коде и других файлах проекта.

Она хранит историю изменений, поэтому можно посмотреть, какие изменения были внесены, кем и когда, а при необходимости вернуться к предыдущему состоянию.

Также VCS позволяет нескольким разработчикам работать над одним проектом параллельно с помощью веток и механизмов объединения изменений.

Например, **Git** является распределённой системой контроля версий: у разработчика есть полноценная локальная история репозитория, а удалённый репозиторий, например в GitLab или GitHub, используется для обмена изменениями и совместной работы.

# 📚 Разбор поглубже

## 1. Что такое система контроля версий

Представим обычную разработку без VCS.

У нас могут появляться файлы:

```text
project_final.py
project_final2.py
project_final_new.py
project_final_new2.py
project_final_really_final.py
```

Проблемы:

* непонятно, что именно изменилось;
* сложно определить автора изменения;
* трудно вернуть старую версию;
* сложно объединять работу нескольких разработчиков;
* история проекта фактически теряется.

VCS решает эти проблемы системно.

Вместо множества копий проекта:

```text
Проект
  ↓
История изменений
  ↓
v1 → v2 → v3 → v4
```

---

# 2. Что хранит VCS

Система контроля версий хранит информацию об изменениях.

Упрощённо:

```text
Commit 1
   ↓
Commit 2
   ↓
Commit 3
   ↓
Commit 4
```

Каждый commit представляет определённое состояние проекта и содержит информацию об изменениях.

Например:

```text
A → B → C → D
```

Можно посмотреть:

* какие файлы изменились;
* какие строки добавились;
* какие строки удалились;
* кто сделал изменение;
* когда оно было сделано;
* сообщение коммита.

---

# 3. Основные возможности VCS

## История изменений

Можно посмотреть историю проекта:

```text
A → B → C → D
```

И понять, как проект развивался.

---

## Откат изменений

Если новая версия содержит ошибку, можно вернуться к предыдущему состоянию или отменить конкретное изменение.

Например:

```text
A → B → C → D
        ↑
     проблема
```

Можно использовать историю для восстановления или исправления проекта.

---

## Ветки

Можно вести несколько линий разработки:

```text
main
 A ── B ── C ───── F
           \
feature     D ── E
```

Например:

```text
main
feature/auth
feature/payment
bugfix/login
```

Это позволяет разрабатывать функциональность независимо.

---

## Объединение изменений

После завершения работы ветку можно объединить с другой:

```text
main
 A ── B ── C ───── F
           \       /
feature     D ── E
```

В Git для этого используются `merge` и `rebase` в зависимости от задачи и выбранного workflow.

---

## Совместная работа

Несколько разработчиков могут работать с одним проектом:

```text
Developer A ──┐
Developer B ──┼──→ Remote Repository
Developer C ──┘
```

Изменения передаются через удалённый репозиторий.

---

# 4. Локальная и распределённая VCS

Системы контроля версий можно условно разделить на несколько моделей.

### Централизованные

Есть центральный сервер, с которым работают разработчики.

Примеры:

* SVN;
* Perforce.

Упрощённо:

```text
Developer A ──┐
Developer B ──┼──→ Central Server
Developer C ──┘
```

---

### Распределённые

Каждый разработчик получает полноценную копию репозитория с историей.

Пример:

**Git**.

```text
           Remote Repository
             /    |    \
            /     |     \
       Developer A B    C
```

У каждого разработчика есть локальный репозиторий.

Это позволяет выполнять многие операции без подключения к серверу:

```text
git commit
git branch
git log
git diff
git merge
```

---

# 5. Git как система контроля версий

**Git — распределённая система контроля версий.**

Упрощённая архитектура:

```text
Working Directory
       │
       │ git add
       ▼
Staging Area
       │
       │ git commit
       ▼
Local Repository
       │
       │ git push
       ▼
Remote Repository
```

Например:

```text
Файл изменили
     ↓
git add
     ↓
Staging Area
     ↓
git commit
     ↓
Local Repository
     ↓
git push
     ↓
GitLab / GitHub
```

---

# 6. VCS не равно Git

Это важно.

**VCS** — общее понятие.

**Git** — конкретная система контроля версий.

Аналогично:

```text
VCS
├── Git
├── SVN
├── Mercurial
└── Perforce
```

Поэтому правильно говорить:

> Git — распределённая система контроля версий.

Но неправильно:

> Git и система контроля версий — два разных инструмента.

Git **является** системой контроля версий.

---

# 7. Git и GitLab

Здесь также важно не смешивать уровни.

```text
Система контроля версий
        │
        └── Git
              │
              └── Remote Repository
                       │
                       ├── GitHub
                       └── GitLab
```

Точнее:

* **VCS** — категория программ;
* **Git** — конкретная VCS;
* **GitLab/GitHub** — платформы, которые могут предоставлять удалённые Git-репозитории и инструменты вокруг разработки.

---

# 8. Что такое commit

**Commit** — зафиксированное изменение в истории Git.

Например:

```bash
git add .
git commit -m "Add authentication"
```

После этого появляется новая точка в истории:

```text
A → B → C
         ↑
       commit
```

Commit позволяет сохранить определённое состояние проекта в истории.

---

# 9. Почему commit важен

Без фиксации изменений история не формируется.

Например:

```text
Working Directory
      │
      │ изменения
      ▼
Staging Area
      │
      │ commit
      ▼
История Git
```

Поэтому Git позволяет не просто хранить текущие файлы, а формировать **историю проекта**.

---

# 10. Ветки и параллельная разработка

Допустим, в `main` находится стабильная версия:

```text
A → B → C
```

Разработчик создаёт ветку:

```text
A → B → C
         \
          D → E
```

В основной ветке при этом можно продолжать работу:

```text
A → B → C → F
         \
          D → E
```

После завершения работы изменения можно объединить.

---

# 11. Конфликты

Если несколько разработчиков изменили одни и те же участки файлов несовместимым образом, система контроля версий может не суметь автоматически объединить изменения.

Например:

```text
Developer A:
return user.name

Developer B:
return user.username
```

Git может остановить операцию объединения и потребовать ручного разрешения конфликта.

Это называется **merge conflict**.

Важно:

> Конфликт Git — это не обязательно ошибка в коде. Это невозможность автоматически определить, какое изменение должно остаться.

# 12. VCS и командная разработка

Типичный процесс:

```text
1. Clone
   ↓
2. Create branch
   ↓
3. Change code
   ↓
4. Commit
   ↓
5. Push
   ↓
6. Code Review
   ↓
7. Merge
```

Например:

```text
Developer
    │
    ├── git switch -c feature/auth
    ├── git add
    ├── git commit
    └── git push
             │
             ▼
          GitLab
             │
             ▼
      Merge Request
             │
             ▼
           main
```

# 14. VCS и резервное копирование — не одно и то же

VCS действительно хранит историю, но **не стоит воспринимать Git как полноценную систему резервного копирования**.

Например:

```text
Local Repository
       │
       └── GitLab
```

Наличие удалённого репозитория повышает устойчивость к потере локального компьютера.

Но backup-инфраструктура может иметь дополнительные требования:

* retention;
* snapshots;
* off-site copies;
* disaster recovery;
* восстановление инфраструктуры.

Поэтому:

> Git решает задачу управления версиями, а backup решает более широкую задачу восстановления данных.

## 🎤 Вопросы на собеседовании

### Что такое система контроля версий?

Инструмент для управления историей изменений проекта, позволяющий отслеживать, сравнивать, отменять и объединять изменения, а также организовывать совместную разработку.

### Что такое Git?

Git — распределённая система контроля версий.

### Git и GitHub/GitLab — это одно и то же?

Нет.

Git — VCS.

GitHub и GitLab — платформы, которые предоставляют удалённые Git-репозитории и дополнительные инструменты разработки.

### Зачем нужны ветки?

Для независимой разработки нескольких функций, исправлений или экспериментов без непосредственного изменения основной ветки.

### Что такое commit?

Зафиксированная точка в истории Git, содержащая изменения проекта.

### Что такое merge?

Операция объединения истории одной ветки с другой.

### Что такое remote repository?

Удалённый Git-репозиторий, доступный через сеть и используемый для обмена изменениями между разработчиками.

### Чем централизованная VCS отличается от распределённой?

В централизованной системе основная история находится на центральном сервере. В распределённой системе каждый разработчик обычно имеет полноценную локальную копию репозитория и его истории.

### Какая VCS используется чаще всего в современной разработке?

Git — одна из наиболее распространённых систем контроля версий и стандарт де-факто во многих командах разработки.
