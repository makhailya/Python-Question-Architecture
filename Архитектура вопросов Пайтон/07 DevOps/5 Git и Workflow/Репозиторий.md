# 📦 Репозиторий Git

## 🎤 Короткий ответ

**Git-репозиторий** — это хранилище проекта, в котором Git отслеживает файлы и хранит историю их изменений.

Репозиторий содержит не только текущие файлы проекта, но и метаданные Git: коммиты, ветки, ссылки, настройки и другие объекты.

Локальный репозиторий находится на компьютере разработчика, а удалённый — например, на GitHub или GitLab.

```text
Проект
├── Working Directory
├── Staging Area
└── .git/
    └── Git Repository
```

Создать локальный репозиторий:

```bash
git init
```

---

## 🗣️ Ответ на собеседовании

Git-репозиторий — это место, где Git хранит информацию о проекте и его истории. В локальном репозитории находятся Git-объекты, ссылки на ветки и другие служебные данные.

После выполнения `git init` в проекте создаётся каталог `.git`. Именно он содержит внутреннюю информацию Git.

Работа с репозиторием обычно выглядит так: мы изменяем файлы в Working Directory, через `git add` помещаем выбранные изменения в Staging Area, а `git commit` сохраняет их в истории локального репозитория.

Кроме локального репозитория может существовать удалённый репозиторий, например на GitHub или GitLab. С ним локальный репозиторий синхронизируется через `fetch`, `pull` и `push`.

Важно: **репозиторий — это не просто папка с исходным кодом**. Главная его ценность — история и структура объектов, которую Git использует для управления версиями.

## 📚 Разбор поглубже

### 1. Что такое Git-репозиторий

Упрощённо репозиторий можно представить так:

```text
my-project/
├── app.py
├── models.py
├── tests/
└── .git/
```

Исходный код находится в обычных файлах проекта.

А `.git/` содержит данные, необходимые Git для управления версиями.

Именно благодаря `.git` Git знает:

* какие были коммиты;
* какие существуют ветки;
* где находится `HEAD`;
* какие объекты входят в историю;
* какие есть ссылки и настройки репозитория.

---

### 2. `git init`

Чтобы превратить существующий каталог в Git-репозиторий:

```bash
git init
```

Например:

```bash
mkdir my-project
cd my-project
git init
```

Git создаст:

```text
my-project/
└── .git/
```

После этого можно проверить состояние:

```bash
git status
```

---

### 3. `.git` — сердце локального репозитория

Каталог:

```text
.git/
```

содержит внутренние данные Git.

Упрощённо:

```text
.git/
├── objects/
├── refs/
├── HEAD
├── config
└── ...
```

Не стоит вручную изменять содержимое `.git` без необходимости.

Обычно Git управляет этими файлами через команды:

```bash
git commit
git branch
git switch
git merge
git reset
...
```

---

### 4. `objects/`

В:

```text
.git/objects/
```

Git хранит объекты своего внутреннего хранилища.

Основные типы:

```text
Git objects
├── blob
├── tree
├── commit
└── tag
```

#### Blob

Хранит содержимое файла.

#### Tree

Описывает структуру каталогов и связывает имена файлов с объектами.

#### Commit

Описывает конкретное состояние проекта и связывает его с родительскими коммитами.

#### Tag

Позволяет именованно ссылаться на определённый объект, например релиз.

---

### 5. Как Git представляет файл

Упрощённая модель:

```text
commit
   │
   ▼
 tree
 ├── app.py ─────→ blob
 ├── models.py ──→ blob
 └── tests/ ─────→ tree
                    ├── test_api.py → blob
                    └── test_user.py → blob
```

То есть Git не хранит историю просто как набор копий папки.

Он использует связанные между собой объекты.

---

### 6. Commit в репозитории

Коммит содержит информацию о конкретной версии проекта.

Упрощённо:

```text
Commit
├── parent
├── tree
├── author
├── committer
├── timestamp
└── message
```

Например:

```text
A ── B ── C
```

Коммит `C` знает о своём родителе `B`, а `B` — о `A`.

Так формируется история.

---

### 7. Branch в репозитории

Ветка в Git — это не копия всех файлов проекта.

Упрощённо branch — это **ссылка на определённый commit**.

Например:

```text
A ── B ── C
          ↑
        main
```

После нового коммита:

```text
A ── B ── C ── D
               ↑
              main
```

То есть branch перемещается вместе с новыми коммитами.

Посмотреть ветки:

```bash
git branch
```

---

### 8. `HEAD`

`HEAD` показывает текущую позицию Git.

Обычно:

```text
HEAD
 ↓
main
 ↓
C
```

То есть:

```text
HEAD → branch → commit
```

При переключении:

```bash
git switch feature
```

получаем:

```text
HEAD
 ↓
feature
 ↓
D
```

---

### 9. Working Directory, Staging и Repository

Это три разных состояния, которые часто путают.

```text
┌─────────────────────┐
│ Working Directory   │
│ текущие файлы       │
└──────────┬──────────┘
           │ git add
           ▼
┌─────────────────────┐
│ Staging Area        │
│ изменения для       │
│ следующего commit   │
└──────────┬──────────┘
           │ git commit
           ▼
┌─────────────────────┐
│ Repository           │
│ сохранённая история │
└─────────────────────┘
```

Например:

```bash
git add app.py
```

ещё **не создаёт commit**.

Commit создаётся только:

```bash
git commit -m "Update app"
```

---

### 10. Локальный и удалённый репозиторий

Есть два понятия:

```text
Local Repository
       ↕
Remote Repository
```

### Локальный

На компьютере разработчика.

Например:

```text
project/.git/
```

### Удалённый

На сервере:

* GitHub;
* GitLab;
* Bitbucket;
* собственный Git-сервер.

Удалённый репозиторий обычно называют:

```text
origin
```

Но `origin` — **не обязательное имя**, а стандартное имя remote, которое Git обычно использует при клонировании.

---

### 11. `git clone`

Если репозиторий уже существует удалённо:

```bash
git clone git@github.com:user/project.git
```

Git:

1. скачивает репозиторий;
2. создаёт локальную рабочую директорию;
3. создаёт `.git`;
4. настраивает remote;
5. получает историю.

Упрощённо:

```text
Remote Repository
       │
       │ git clone
       ▼
Local Repository
       +
Working Directory
```

---

### 12. `git remote`

Посмотреть удалённые репозитории:

```bash
git remote -v
```

Например:

```text
origin  git@github.com:user/project.git (fetch)
origin  git@github.com:user/project.git (push)
```

Добавить remote:

```bash
git remote add origin git@github.com:user/project.git
```

---

### 13. `fetch`

```bash
git fetch origin
```

Получает новые объекты и информацию о ветках с remote.

Важно:

> `fetch` не должен автоматически менять твою текущую рабочую ветку.

Например:

```text
Local:
main → A

Remote:
origin/main → A ── B
```

После:

```bash
git fetch
```

может стать:

```text
main        → A
origin/main → B
```

Локальная `main` при этом остаётся на `A`.

---

### 14. `pull`

```bash
git pull
```

Получает изменения с remote и интегрирует их в текущую ветку.

Упрощённо часто можно представить:

```text
git pull
≈
git fetch
+
git merge
```

Но при использовании `--rebase`:

```bash
git pull --rebase
```

интеграция происходит через rebase.

Поэтому точнее говорить:

> `pull` — получение изменений с remote с последующей интеграцией в текущую ветку.

---

### 15. `push`

```bash
git push origin main
```

Отправляет локальные коммиты и связанные объекты в удалённый репозиторий.

```text
Local Repository
       │
       │ push
       ▼
Remote Repository
```

Например:

```text
Local main:
A ── B ── C

Remote main:
A ── B
```

После:

```bash
git push
```

remote может получить:

```text
A ── B ── C
```

---

### 16. Репозиторий и рабочая директория — не одно и то же

Это хороший вопрос на собеседовании.

Можно сказать:

> Рабочая директория содержит текущие файлы проекта, а Git-репозиторий содержит данные Git и историю версий. В стандартном локальном репозитории они находятся рядом, а служебные данные хранятся в `.git`.

То есть:

```text
project/
├── source code
├── tests
├── README
└── .git/  ← данные Git
```

---

### 17. Bare Repository

Есть особый вид репозитория — **bare repository**.

У него нет обычной рабочей директории.

Например:

```text
project.git/
├── objects/
├── refs/
├── HEAD
└── ...
```

Создать:

```bash
git init --bare
```

Bare repository часто используется как серверное хранилище Git.

Модель:

```text
Developer A
     │
     │ push
     ▼
Bare Repository
     ▲
     │ push
Developer B
```

Современные Git-серверы вроде GitHub и GitLab используют более сложную инфраструктуру, но концептуально bare repository — важное понятие Git.



```bash

```

### 19. Что происходит после `git init`

До:

```text
my-project/
├── app.py
└── README.md
```

Выполняем:

```bash
git init
```

После:

```text
my-project/
├── app.py
├── README.md
└── .git/
```

Но Git ещё не обязан иметь ни одного коммита.

Можно проверить:

```bash
git status
```

Затем:

```bash
git add .
git commit -m "Initial commit"
```

Теперь появилась история.

---

### 20. Repository может существовать без remote

Это важный момент.

Можно иметь полноценный Git-репозиторий:

```text
Local Repository
```

без:

```text
GitHub
GitLab
```

Например:

```bash
git init
git add .
git commit -m "Initial commit"
```

Всё будет работать локально.

Remote нужен только для синхронизации и совместной работы.

---

### 21. Repository и `.gitignore`

`.gitignore` находится в рабочем дереве проекта:

```text
project/
├── .gitignore
├── app.py
└── .git/
```

Он задаёт правила, какие **неотслеживаемые** файлы Git должен игнорировать.

Например:

```gitignore
__pycache__/
.venv/
.env
*.pyc
```

Но важно:

> `.gitignore` не перестаёт отслеживать файл, который уже был добавлен в репозиторий.

Если `.env` уже tracked:

```bash
git rm --cached .env
```

после чего правило `.gitignore` сможет предотвратить его повторное добавление.

### 22. Главное различие терминов

```text
Git
└── система контроля версий

Repository
└── хранилище истории и объектов Git

Working Directory
└── текущие файлы проекта

Staging Area
└── изменения для следующего commit

Commit
└── зафиксированное состояние проекта

Branch
└── ссылка на commit

Remote Repository
└── удалённая копия/источник Git-истории
```

## 🎤 Вопросы на собеседовании

**Что такое Git-репозиторий?**

Хранилище Git, содержащее историю проекта, Git-объекты, ссылки на ветки и служебную информацию.

**Что появляется после `git init`?**

В проекте создаётся каталог `.git`, содержащий внутренние данные локального Git-репозитория.

**Что находится в `.git`?**

В частности, Git objects, refs, `HEAD`, конфигурация и другие служебные данные.

**Чем репозиторий отличается от рабочей директории?**

Working Directory содержит текущие файлы проекта, а Repository содержит данные Git и историю версий.

**Что такое локальный репозиторий?**

Git-репозиторий на компьютере разработчика, содержащий локальную историю проекта.

**Что такое remote repository?**

Репозиторий, доступный через удалённый сервер, например GitHub или GitLab, с которым локальный репозиторий синхронизируется.

**Обязательно ли репозиторию иметь remote?**

Нет. Git может полностью работать локально.

**Что делает `git clone`?**

Создаёт локальную копию удалённого репозитория вместе с его историей и настройкой remote.

**Что такое `origin`?**

Обычно имя remote, автоматически назначаемое первому удалённому репозиторию при `git clone`. Это соглашение, а не специальное ключевое слово Git.

**Что такое bare repository?**

Репозиторий без рабочей директории. Он содержит Git-данные и часто используется как серверное хранилище.

**Какие основные объекты есть в Git?**

`blob`, `tree`, `commit` и `tag`.

**Что такое `HEAD`?**

Ссылка на текущую позицию в истории Git, обычно через текущую ветку на её последний commit.

**Формула для собеседования:**

> **Git-репозиторий — это хранилище истории и внутренних объектов Git. В локальном проекте его служебная часть находится в `.git`. Рабочие файлы находятся в Working Directory, выбранные изменения — в Staging Area, а зафиксированная история — в Repository. Репозиторий может быть локальным или удалённым, а синхронизация между ними выполняется через `fetch`, `pull` и `push`.**
