# 🌿 Git

## 🎤 Короткий ответ

**Git** — распределённая система контроля версий, которая позволяет отслеживать изменения в коде, сохранять историю, работать с ветками и синхронизировать изменения между разработчиками.

Основные сущности:

```text
Working Directory
      ↓ git add
Staging Area
      ↓ git commit
Local Repository
      ↓ git push
Remote Repository
```

Основные команды:

```bash
git status
git add
git commit
git log
git branch
git switch
git merge
git pull
git push
git fetch
```

## 🗣️ Ответ на собеседовании

Git — это распределённая система контроля версий. Она позволяет хранить историю изменений проекта, создавать отдельные ветки для разработки разных функций, возвращаться к предыдущим версиям и объединять изменения.

Главная особенность Git — каждый разработчик имеет локальный репозиторий с историей проекта. Поэтому большая часть операций, например `commit`, `branch` или просмотр истории, выполняется локально.

Изменения проходят несколько состояний: рабочая директория, staging area и локальный репозиторий. Сначала я изменяю файлы, затем через `git add` добавляю нужные изменения в staging, после чего `git commit` создаёт коммит в локальном репозитории. Для синхронизации с удалённым репозиторием используются `git fetch`, `git pull` и `git push`.

В командной разработке Git используется вместе с ветками, merge или rebase и системой code review.

## 📚 Разбор поглубже

### 1. Что такое Git

Git — **распределённая система контроля версий (DVCS)**.

Она позволяет:

* отслеживать изменения файлов;
* хранить историю проекта;
* создавать ветки;
* объединять изменения;
* работать нескольким разработчикам одновременно;
* возвращаться к предыдущим состояниям;
* синхронизировать локальный репозиторий с удалённым.

Git хранит не просто набор последних файлов, а историю изменений проекта в виде **коммитов**.

---

### 2. Git и GitHub — не одно и то же

Это важно не путать.

**Git** — система контроля версий.

**GitHub** — сервис для хранения Git-репозиториев и совместной разработки.

Аналогично:

```text
Git
├── GitHub
├── GitLab
└── Bitbucket
```

Git может работать полностью локально без GitHub.

---

### 3. Репозиторий

**Repository** — репозиторий Git, содержащий историю проекта и служебную информацию Git.

Создать репозиторий:

```bash
git init
```

Git создаст каталог:

```text
.git/
```

В нём хранится внутренняя информация Git.

Проверить состояние:

```bash
git status
```

---

### 4. Основная модель Git

Упрощённо работа выглядит так:

```text
┌──────────────────┐
│ Working Directory│
└────────┬─────────┘
         │ git add
         ▼
┌──────────────────┐
│  Staging Area    │
└────────┬─────────┘
         │ git commit
         ▼
┌──────────────────┐
│ Local Repository │
└────────┬─────────┘
         │ git push
         ▼
┌──────────────────┐
│ Remote Repository│
└──────────────────┘
```

Это одна из самых важных моделей Git для собеседования.

---

### 5. Working Directory

**Working Directory** — текущее состояние файлов проекта на диске.

Например:

```text
project/
├── app.py
├── models.py
└── README.md
```

Я изменил:

```python
def hello():
    return "Hello"
```

Git видит, что рабочая директория отличается от последнего коммита.

Проверить:

```bash
git status
```

---

### 6. Staging Area

**Staging Area** — промежуточная область, куда мы помещаем изменения, которые хотим включить в следующий коммит.

```bash
git add app.py
```

Теперь изменение `app.py` находится в staging.

Можно добавить всё:

```bash
git add .
```

Но в командной работе полезно понимать, что `git add` позволяет выбирать, **какие именно изменения войдут в следующий commit**.

---

### 7. Commit

`commit` фиксирует подготовленные в staging изменения в локальной истории Git.

```bash
git commit -m "Add user authentication"
```

После этого:

```text
Working Directory
      ↓
Staging
      ↓
Commit
```

Коммит содержит информацию о состоянии проекта и его родителе/родителях, поэтому из коммитов строится история.

---

### 8. Commit — это не просто diff

Упрощённо коммит можно представить как:

```text
Commit
├── ссылка на состояние файлов
├── parent commit
├── author
├── timestamp
└── message
```

У обычного коммита один родитель.

У merge-коммита может быть два и более родителей.

```text
A ── B ── C
      \    \
       D ── M
```

`M` объединяет истории веток.

---

### 9. Hash коммита

Каждый Git commit идентифицируется хешем.

Например:

```text
a83f1e2...
```

Можно посмотреть историю:

```bash
git log
```

Компактный вариант:

```bash
git log --oneline
```

Например:

```text
a83f1e2 Add authentication
c72b913 Add user model
4d8a210 Initial commit
```

Хеш позволяет однозначно ссылаться на конкретный объект истории.

---

### 10. HEAD

`HEAD` — специальная ссылка Git, которая показывает, **на какой коммит/ветку сейчас указывает текущий checkout**.

Например:

```text
HEAD
 ↓
main
 ↓
C
```

Когда переключаемся на другую ветку:

```bash
git switch develop
```

`HEAD` начинает указывать на `develop`.

```text
HEAD
 ↓
develop
 ↓
D
```

---

### 11. Branch

**Branch** — именованная ссылка на коммит, позволяющая вести отдельную линию разработки.

Например:

```text
A ── B ── C   main
      \
       D ── E feature
```

Создать ветку:

```bash
git branch feature
```

Переключиться:

```bash
git switch feature
```

Современный предпочтительный синтаксис:

```bash
git switch -c feature
```

Он одновременно создаёт и переключает на новую ветку.

---

### 12. Почему ветки дешёвые

В Git ветка — это не полная копия проекта.

Упрощённо ветка — это ссылка на определённый commit.

Поэтому создание ветки:

```bash
git branch feature
```

очень дешёвая операция.

```text
main ─────── C
              ↑
           feature
```

После нового коммита:

```text
main ─────── C
              \
feature        D
```

---

### 13. Merge

`merge` объединяет две линии истории.

Например:

```text
A ── B ── C       main
      \
       D ── E     feature
```

Переходим в `main`:

```bash
git switch main
```

И выполняем:

```bash
git merge feature
```

Git объединяет истории.

В зависимости от ситуации получится обычный merge commit или **fast-forward**.

---

### 14. Fast-forward

Если `main` не получил новых коммитов после создания `feature`:

```text
A ── B       main
      \
       C ── D feature
```

Git может просто передвинуть указатель `main`:

```text
A ── B ── C ── D
                ↑
          main, feature
```

Новый merge commit в этом случае не нужен.

Это называется **fast-forward**.

---

### 15. Rebase

`rebase` переносит коммиты одной ветки поверх другой базы.

До:

```text
A ── B ── C       main
      \
       D ── E     feature
```

После:

```text
A ── B ── C ── D' ── E'
                    ↑
                 feature
```

Коммиты `D` и `E` фактически получают новые идентификаторы.

Поэтому важное правило:

> **Rebase переписывает историю.**

Из-за этого с опубликованными общими ветками нужно обращаться осторожно.

---

### 16. Merge vs Rebase

| Merge                                           | Rebase                                    |
| ----------------------------------------------- | ----------------------------------------- |
| Объединяет истории                              | Переписывает историю                      |
| Может создать merge commit                      | Обычно создаёт линейную историю           |
| Не переписывает существующие коммиты            | Создаёт новые коммиты на новой базе       |
| Безопаснее для уже опубликованной общей истории | Осторожно с уже опубликованными коммитами |

Это не вопрос «какая команда лучше». Выбор зависит от workflow команды.

---

### 17. Remote Repository

Удалённый репозиторий — например:

```text
GitHub
GitLab
Bitbucket
```

Добавить remote:

```bash
git remote add origin git@github.com:user/project.git
```

Проверить:

```bash
git remote -v
```

Обычно `origin` — просто принятое имя удалённого репозитория.

Это не специальное слово Git.

---

### 18. `git push`

`push` отправляет локальные коммиты в удалённый репозиторий.

```bash
git push origin main
```

Схематично:

```text
Local Repository
      │
      │ push
      ▼
Remote Repository
```

Важно:

> `git push` отправляет коммиты, а не просто «синхронизирует папку».

---

### 19. `git fetch`

`fetch` получает информацию и новые объекты из remote, но **не изменяет текущую рабочую ветку**.

```bash
git fetch origin
```

После этого Git узнаёт о новых коммитах на сервере.

Например:

```text
origin/main
```

может переместиться вперёд, а локальный:

```text
main
```

останется на месте.

---

### 20. `git pull`

`git pull` — это комбинация получения изменений и их интеграции в текущую ветку.

Концептуально:

```text
git pull
≈
git fetch
+
git merge
```

В зависимости от настроек Git может использовать rebase:

```bash
git pull --rebase
```

Поэтому на собеседовании лучше не говорить, что `pull` **всегда** равен `fetch + merge`.

Точнее:

> `pull` получает изменения с remote и интегрирует их в текущую ветку; конкретный способ интеграции зависит от настроек и опций.

---

### 21. Типичный workflow

Например, нужно сделать новую функцию.

```bash
git switch main
git pull
git switch -c feature/auth
```

Работаем:

```text
изменили код
```

Проверяем:

```bash
git status
```

Добавляем:

```bash
git add .
```

Создаём commit:

```bash
git commit -m "Add authentication"
```

Отправляем:

```bash
git push -u origin feature/auth
```

После этого обычно создаётся Pull Request / Merge Request для code review.

---

### 22. `git status`

Одна из самых полезных команд:

```bash
git status
```

Она показывает:

* текущую ветку;
* изменённые файлы;
* staged changes;
* untracked files;
* иногда информацию о расхождении с remote.

Например:

```text
On branch feature/auth

Changes not staged for commit:
  modified: app.py

Untracked files:
  auth.py
```

---

### 23. `git diff`

Посмотреть изменения, которые ещё не попали в staging:

```bash
git diff
```

Посмотреть staged changes:

```bash
git diff --staged
```

Полезная последовательность:

```bash
git status
git diff
git add .
git diff --staged
git commit
```

Так можно проверить, что именно попадёт в коммит.

---

### 24. `.gitignore`

`.gitignore` описывает файлы и каталоги, которые Git не должен отслеживать.

Для Python-проекта, например:

```gitignore
__pycache__/
*.pyc
.venv/
.env
.idea/
```

Особенно важно:

```text
.env
```

если там находятся секреты.

Но `.gitignore` не удаляет уже отслеживаемый файл из Git.

Для уже tracked-файла нужно отдельно убрать его из индекса:

```bash
git rm --cached .env
```

---

### 25. `git restore`

Для отмены изменений в рабочей директории:

```bash
git restore app.py
```

Для удаления файла из staging:

```bash
git restore --staged app.py
```

Это современный способ разделять операции восстановления рабочего дерева и staging.

---

### 26. `git reset`

`reset` перемещает `HEAD` и в зависимости от режима может изменять staging и рабочую директорию.

Основные варианты:

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

Упрощённо:

```text
--soft
→ HEAD

--mixed
→ HEAD + staging

--hard
→ HEAD + staging + working tree
```

`--hard` опасен, потому что может удалить незакоммиченные изменения.

---

### 27. `git revert`

`revert` отменяет изменения определённого коммита **новым коммитом**.

```bash
git revert <commit>
```

Например:

```text
A ── B ── C
          ↓
          revert C
          ↓
A ── B ── C ── D
```

`D` содержит изменения, обратные `C`.

Это особенно удобно для уже опубликованной истории, потому что история не переписывается.

---

### 28. `reset` vs `revert`

| `reset`                                          | `revert`                                 |
| ------------------------------------------------ | ---------------------------------------- |
| Перемещает указатель истории                     | Создаёт новый commit                     |
| Может переписывать локальную историю             | Не переписывает историю                  |
| Часто используется для локальных изменений       | Удобен для отмены опубликованного commit |
| `--hard` может удалить незакоммиченные изменения | Создаёт явную отмену                     |

---

### 29. Типичная модель состояний файла

Удобно представлять Git так:

```text
                 git add
Working ─────────────────→ Staged
   ↑                         │
   │                         │ git commit
   │                         ▼
git restore              Repository
   │
   └──────── изменения ────────
```

И отдельно:

```text
Repository
    │
    │ git push
    ▼
Remote
```

## 🎤 Вопросы на собеседовании

**Что такое Git?**

Распределённая система контроля версий для отслеживания изменений и управления историей проекта.

**Чем Git отличается от GitHub?**

Git — инструмент контроля версий. GitHub — удалённая платформа для хранения Git-репозиториев и совместной работы.

**Что такое commit?**

Фиксация подготовленных изменений в локальной истории Git.

**Что такое staging area?**

Промежуточная область между рабочей директорией и commit, куда помещаются изменения для следующего коммита.

**Что делает `git add`?**

Добавляет выбранные изменения в staging area.

**Что делает `git commit`?**

Создаёт новый коммит из изменений, находящихся в staging.

**Что такое `HEAD`?**

Специальная ссылка Git на текущую позицию в истории — обычно текущую ветку и её последний commit.

**Что такое branch?**

Именованная ссылка на commit, позволяющая вести отдельную линию разработки.

**Что такое `git fetch`?**

Получает новые данные с remote, но не интегрирует их непосредственно в текущую рабочую ветку.

**Что такое `git pull`?**

Получает изменения с remote и интегрирует их в текущую ветку; конкретный способ интеграции зависит от настроек и опций.

**Чем `merge` отличается от `rebase`?**

`merge` объединяет истории, а `rebase` переносит коммиты на новую базу и тем самым переписывает их историю.

**Что такое fast-forward?**

Ситуация, когда указатель ветки можно просто переместить вперёд, потому что отдельного расхождения истории нет.

**Чем `reset` отличается от `revert`?**

`reset` перемещает указатель истории и может переписывать локальную историю. `revert` создаёт новый коммит, отменяющий изменения предыдущего.

**Зачем нужен `.gitignore`?**

Чтобы указать файлы и каталоги, которые Git не должен отслеживать.

**Формула для собеседования:**

> **Git — распределённая система контроля версий. Изменения проходят Working Directory → Staging Area → Commit → Remote. `add` готовит изменения, `commit` фиксирует их локально, `push` отправляет на remote, `fetch` получает информацию с remote, а `pull` получает и интегрирует изменения. Branch позволяет вести отдельную линию разработки, а merge и rebase используются для объединения историй.**
