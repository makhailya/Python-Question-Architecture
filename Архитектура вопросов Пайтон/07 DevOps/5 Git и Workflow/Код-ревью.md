# 👀 Код-ревью (Code Review)

## 🎤 Короткий ответ

**Code Review (код-ревью)** — это проверка изменений в коде другим разработчиком перед их попаданием в основную ветку.

Цель — найти:

* ошибки;
* потенциальные баги;
* проблемы архитектуры;
* проблемы читаемости;
* нарушения стандартов проекта;
* проблемы безопасности и производительности;
* отсутствие или недостаточность тестов.

Главная идея:

> **Code Review — не поиск виноватого, а проверка качества и корректности изменений.**

## 🎯 Формула для собеседования

> **Code Review = Diff → проверка логики + качества + тестов + безопасности → замечания → исправления → Approval → Merge.**

---

# 🔹 Где находится Code Review в workflow

Обычно процесс выглядит так:

```text
Feature branch
      ↓
    Commit
      ↓
     Push
      ↓
Merge Request / Pull Request
      ↓
   Code Review
      ↓
   CI / Tests
      ↓
   Approval
      ↓
    Merge
      ↓
     main
```

Code Review обычно происходит внутри **Merge Request / Pull Request**.

---

# 🔹 Что проверяет reviewer

Reviewer смотрит не только на то, работает ли код.

Основные направления:

```text
Correctness
Architecture
Readability
Tests
Security
Performance
Maintainability
Project conventions
```

---

# 🔹 1. Correctness — корректность

Главный вопрос:

> **Делает ли код то, что должен делать?**

Например:

```python
def get_discount(price):
    if price > 1000:
        return price * 0.9

    return price
```

Reviewer может проверить:

* правильно ли рассчитывается скидка;
* что происходит с `price <= 1000`;
* что происходит с отрицательной ценой;
* соответствует ли поведение требованиям.

---

# 🔹 2. Логические ошибки

Код может успешно пройти:

```text
pytest
↓
CI ✅
```

но при этом содержать ошибку в бизнес-логике.

Например:

```python
if user.is_admin or user.is_owner:
    delete_order()
```

Reviewer должен понять:

> Действительно ли **admin ИЛИ owner** имеют право удалять заказ?

Code Review позволяет находить ошибки, которые не всегда покрыты автоматическими тестами.

---

# 🔹 3. Архитектура

Reviewer смотрит:

> **Находится ли код в правильном месте?**

Например, в FastAPI-проекте:

```text
API endpoint
     ↓
Business logic
     ↓
Repository
     ↓
Database
```

Плохо, если endpoint содержит:

```python
@app.post("/orders")
async def create_order():
    # 100 строк бизнес-логики
    # SQL
    # отправка email
    # Redis
    # расчёты
```

Reviewer может предложить разделить ответственность.

---

# 🔹 4. Readability — читаемость

Код должен быть понятен другим разработчикам.

Плохо:

```python
x = [i for i in a if i["s"] and i["p"] > 100]
```

Если логика сложная, лучше дать понятные имена:

```python
expensive_active_products = [
    product
    for product in products
    if product["is_active"] and product["price"] > 100
]
```

Хороший code review не означает:

> «Я бы написал это по-другому».

Важно отличать **объективную проблему** от личного вкуса.

---

# 🔹 5. Тесты

Reviewer проверяет:

* есть ли тесты;
* покрывают ли они новую функциональность;
* проверяются ли edge cases;
* проверяются ли ошибки.

Например добавили:

```python
def calculate_discount(price):
    ...
```

Стоит проверить:

```text
price = 100
price = 1000
price = 1001
price = 0
invalid input
```

---

# 🔹 6. Security

Code Review может выявить уязвимости.

Например:

```python
query = f"SELECT * FROM users WHERE id = {user_id}"
```

Это потенциальная SQL injection.

Reviewer должен обратить внимание на способ формирования SQL.

В ORM:

```python
User.objects.filter(id=user_id)
```

или в SQLAlchemy использовать параметризованные запросы.

---

# 🔹 7. Performance

Reviewer может обнаружить проблемы производительности.

Например Django:

```python
for order in orders:
    print(order.user.name)
```

Если `user` не загружен заранее, может возникнуть:

```text
1 query → orders
N queries → users
```

То есть **N+1 problem**.

Reviewer может предложить:

```python
orders = Order.objects.select_related("user")
```

---

# 🔹 8. Обработка ошибок

Reviewer проверяет:

```text
Что произойдёт при ошибке?
```

Например:

```python
try:
    process_payment()
except Exception:
    pass
```

Проблема:

> Ошибка полностью проглатывается.

Лучше:

```python
try:
    process_payment()
except PaymentError:
    logger.exception("Payment failed")
    raise
```

Конкретная обработка зависит от требований приложения.

---

# 🔹 9. Logging

Reviewer смотрит:

* есть ли нужные логи;
* правильный ли log level;
* достаточно ли контекста;
* нет ли секретов в логах.

Плохо:

```python
logger.info(f"password={password}")
```

Пароли и токены не должны попадать в обычные логи.

---

# 🔹 10. Конфигурация и Secrets

Нельзя помещать секреты непосредственно в код:

```python
DATABASE_PASSWORD = "super-secret-password"
```

Обычно используются:

```text
Environment Variables
Secrets Manager
Kubernetes Secrets
CI/CD Secrets
```

Reviewer должен обращать внимание на случайно добавленные:

```text
API keys
passwords
tokens
private keys
```

---

# 🔹 Что такое Diff

**Diff** — изменения между версиями кода.

Например:

```text
- old_code
+ new_code
```

Reviewer в первую очередь смотрит именно на **diff**, а не весь проект целиком.

Пример:

```text
- timeout = 10
+ timeout = 30
```

Reviewer задаёт вопрос:

> Почему timeout увеличили до 30 секунд?

---

# 🔹 Inline Comment

Reviewer может оставить комментарий непосредственно около изменённой строки:

```text
Reviewer:
Здесь возможен N+1 query.
Можно использовать select_related().
```

Разработчик исправляет:

```text
select_related()
```

и обновляет MR.

---

# 🔹 Виды замечаний

Полезно разделять замечания по важности.

Например:

```text
Blocker
Major
Minor
Nit
```

### Blocker

Изменение нельзя принимать.

Например:

```text
Security vulnerability
Data loss
Critical bug
```

### Major

Серьёзная проблема, которую желательно исправить до merge.

### Minor

Небольшая проблема, не влияющая существенно на работу.

### Nit

Мелкое замечание по стилю или читаемости.

Важно:

> Названия и правила приоритетов зависят от команды.

---

# 🔹 Хороший комментарий в Code Review

Плохо:

```text
❌ Сделано неправильно.
```

Лучше:

```text
⚠️ Здесь запрос к users выполняется внутри цикла,
что может привести к N+1 запросам.

Можно загрузить пользователей заранее через select_related().
```

Хороший комментарий обычно содержит:

```text
Проблема
   ↓
Почему это проблема
   ↓
Возможное решение
```

---

# 🔹 Reviewer не должен переписывать весь код

Цель Review — не сделать код полностью таким, **как нравится reviewer**.

Например:

```python
result = calculate_total(items)
```

Если код:

* корректный;
* читаемый;
* соответствует стандартам проекта;
* покрыт тестами;

то замечание:

> «Я бы назвал переменную `total`»

может быть просто субъективным.

---

# 🔹 Автор MR и Reviewer

Роли разные.

### Автор

Отвечает за:

* реализацию;
* тесты;
* описание MR;
* исправление замечаний.

### Reviewer

Отвечает за:

* проверку изменений;
* поиск проблем;
* вопросы;
* предложения улучшений;
* оценку соответствия требованиям проекта.

```text
Author
   ↓
MR
   ↓
Reviewer
   ↓
Comments
   ↓
Author fixes
   ↓
Review again
   ↓
Approve
```

---

# 🔹 Approval

Если изменения устраивают reviewer:

```text
Approve
```

После необходимых approval и успешного CI MR может быть объединён.

Например:

```text
CI       ✅
Tests    ✅
Review   ✅
Approval ✅
   ↓
Merge
```

---

# 🔹 Что делать автору при замечании

Не стоит воспринимать замечание как личную критику.

Правильный процесс:

```text
Comment
   ↓
Понять проблему
   ↓
Исправить
   ↓
Добавить commit
   ↓
CI
   ↓
Reviewer проверяет снова
```

Если разработчик не согласен с замечанием, нормальный вариант — **обсудить техническую причину**, а не просто проигнорировать комментарий.

---

# 🔹 Self Review

Перед созданием MR полезно самостоятельно проверить собственный diff.

Например:

```text
git diff
```

Проверить:

```text
□ Нет случайных файлов
□ Нет debug print
□ Нет секретов
□ Тесты добавлены
□ Линтер проходит
□ Форматирование корректно
□ Нет ненужных изменений
□ Ошибки обработаны
```

Это называется **Self Review**.

# 🔹 Code Review и тесты

Наличие тестов не означает, что Review больше не нужен.

Например тест может проверять:

```python
assert calculate_total(items) == 100
```

Но reviewer может заметить:

```text
Функция выполняет SQL-запрос внутри цикла.
```

Тест может пройти, а production под нагрузкой будет работать медленно.

---

# 🔹 Code Review и Junior-разработчик

Для Junior Code Review особенно полезен как инструмент обучения.

Процесс:

```text
Написал код
    ↓
Получил замечание
    ↓
Понял принцип
    ↓
Исправил
    ↓
В следующий раз написал лучше
```

При этом reviewer должен объяснять **почему** изменение необходимо, когда это не очевидно.

---

# 🔹 Пример полного Code Review

Допустим, разработчик написал:

```python
@app.get("/orders")
async def get_orders():
    orders = await get_orders_from_db()

    result = []

    for order in orders:
        user = await get_user(order.user_id)
        result.append({
            "id": order.id,
            "user": user.name,
        })

    return result
```

Reviewer видит:

```text
1 query → orders
N queries → users
```

И оставляет комментарий:

```text
Здесь потенциальная N+1 проблема:
get_user() вызывается для каждого order.

Лучше получить связанные данные одним запросом
или использовать подход eager loading.
```

После исправления:

```text
DB:
1 query
```

В результате Code Review помог обнаружить проблему до production.

# 🔹 Code Review в команде

Типичный процесс:

```text
Developer A
     ↓
   MR/PR
     ↓
Developer B
     ↓
  Review
     ↓
┌────┴────┐
↓         ↓
Approve   Changes
             ↓
          Developer A
             ↓
           Fix
             ↓
          Review
```

В больших командах могут использовать:

* обязательное количество approvals;
* CODEOWNERS;
* protected branches;
* обязательный CI;
* автоматические линтеры;
* security scanners.

---

# 🔹 Что НЕ является целью Code Review

Code Review не должен превращаться в:

```text
❌ доказательство авторитета
❌ спор о личных предпочтениях
❌ переписывание всего проекта
❌ поиск ошибок ради количества комментариев
```

Основная цель:

> **Сделать изменения корректными, безопасными, понятными и поддерживаемыми.**

# 🔹 Частые вопросы на собеседовании

### Что такое Code Review?

> Проверка изменений в коде другим разработчиком перед их интеграцией в основную ветку.

### Что проверяют на Code Review?

> Корректность, архитектуру, читаемость, тесты, безопасность, производительность и соответствие стандартам проекта.

### Что такое Diff?

> Набор изменений между версиями кода.

### Что такое Approval?

> Подтверждение reviewer, что изменения прошли необходимую проверку.

### Кто отвечает за исправление замечаний?

> Автор Merge Request.

### Нужно ли исправлять каждое замечание reviewer?

> Не обязательно механически каждое; технические спорные моменты обсуждаются. Обязательные замечания исправляются согласно правилам команды.

### Code Review и CI — одно и то же?

> Нет. CI выполняет автоматические проверки, Code Review предполагает проверку изменений разработчиком.

### Почему Code Review нужен, если есть тесты?

> Тесты проверяют заранее определённые сценарии, а reviewer может обнаружить архитектурные, логические, security и maintainability-проблемы, которые тесты не покрывают.

### Что делать, если не согласен с reviewer?

> Обсудить техническую причину и привести аргументы, а не игнорировать замечание.

### Что такое Self Review?

> Самостоятельная проверка собственного diff перед отправкой изменений на Code Review.

# 🔑 Главное

```text
                 Code Review
                      │
                 Merge Request
                      │
                     Diff
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
   Correctness    Architecture    Security
       ↓              ↓              ↓
     Tests        Readability    Performance
       └──────────────┼──────────────┘
                      ↓
                  Comments
                      ↓
                  Fixes
                      ↓
                  Approval
                      ↓
                    Merge
```

> **Code Review** → человек проверяет изменения
> **CI** → автоматические проверки
> **Diff** → что именно изменилось
> **Comment** → замечание по изменению
> **Approval** → подтверждение reviewer
> **Merge** → интеграция изменений

### 🎤 Формула для собеседования

> **Code Review — это процесс проверки изменений другим разработчиком перед merge. Reviewer оценивает корректность, архитектуру, читаемость, тесты, безопасность и производительность. После исправления замечаний и прохождения CI изменения получают approval и могут быть объединены с целевой веткой.**
