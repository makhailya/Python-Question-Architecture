# 🔄 Rebase в Git

## 🎤 Короткий ответ

**Rebase** — это операция Git, которая переносит коммиты одной ветки на новую базу.

Например, если `feature` была создана от старого состояния `main`, а `main` за это время продвинулась, можно сделать:

```bash
git switch feature
git rebase main
```

Git возьмёт коммиты `feature`, временно уберёт их, переместит указатель ветки на актуальный `main`, а затем **воспроизведёт коммиты feature заново**.

В результате история становится линейной:

```text
A---B---C---D---E
        main  feature
```

Главное отличие от `merge`: **merge объединяет две линии истории, а rebase переписывает историю коммитов, создавая их новые версии на новой базе.**

---

## 🗣️ Ответ на собеседовании

> Rebase используется для переноса коммитов текущей ветки на другую базу. Например, если я работаю в `feature`, а `main` за это время получила новые коммиты, я могу сделать `git rebase main`.
>
> Git найдёт общий предок веток, временно снимет коммиты `feature`, переместит её базу на актуальный `main`, а затем применит эти изменения заново. При этом создаются новые коммиты с другими SHA.
>
> Основное преимущество rebase — более линейная и читаемая история без лишних merge commit. Но rebase переписывает историю, поэтому его опасно применять к коммитам, которые уже используются другими разработчиками.
>
> После rebase, если ветка уже была отправлена в удалённый репозиторий, обычный `git push` может быть отклонён. Обычно используется `git push --force-with-lease`, а не безусловный `--force`.

# 📚 Разбор поглубже

## 1. Зачем нужен Rebase

Представим, что мы создали `feature`:

```text
A---B---C  main
     \
      D---E  feature
```

Пока мы работали над `feature`, в `main` появились новые коммиты:

```text
A---B---C---F---G  main
     \
      D---E        feature
```

Теперь `feature` основана на старом состоянии `main`.

Можно сделать `merge`:

```text
A---B---C---F---G-------M  main
     \                 /
      D---E------------
```

Но появляется merge commit `M`.

Другой вариант:

```bash
git switch feature
git rebase main
```

Получится:

```text
A---B---C---F---G---D'---E'  feature
```

Теперь история линейная.

---

# 2. Что именно делает Rebase

Очень важно понимать механику, а не просто запоминать команду.

Было:

```text
A---B---C---F---G  main
     \
      D---E        feature
```

Git определяет общий предок:

```text
A---B
     \
      C---F---G  main
     \
      D---E      feature
```

Условно Git делает следующее:

### Шаг 1. Запоминает коммиты feature

```text
D
E
```

### Шаг 2. Перемещает базу feature

Теперь:

```text
A---B---C---F---G  main
```

### Шаг 3. Воспроизводит изменения D и E

Но уже поверх `G`:

```text
A---B---C---F---G---D'---E'
```

Обрати внимание на `'`.

Это **не те же самые коммиты**.

---

# 3. Почему после Rebase меняются SHA

Git-коммит зависит не только от текста изменений.

В коммите есть информация о:

* изменениях;
* родительском коммите;
* авторе;
* времени;
* сообщении;
* других метаданных.

После rebase у коммита меняется родитель:

```text
D → D'
```

Поэтому меняется SHA.

Например:

```text
До:

A---B---D
         SHA = abc123

После:

A---B---C---D'
             SHA = 91ef72
```

Даже если содержимое изменения практически такое же, `D'` — это уже **другой коммит**.

Отсюда главное свойство:

> **Rebase переписывает историю.**

---

# 4. Rebase не создаёт копию файлов

Это частая ошибка в понимании.

Rebase не означает:

> «Скопировать всю ветку в другую ветку».

Git работает с историей коммитов и изменениями.

Упрощённо:

```text
Старые коммиты
      ↓
временно убрать
      ↓
новая база
      ↓
повторно применить изменения
      ↓
новые коммиты
```

---

# 5. Основная команда

Находясь в `feature`:

```bash
git switch feature
git rebase main
```

После этого:

```text
main
  │
  ▼
A---B---C---F---G---D'---E'
                         ▲
                       feature
```

---

# 6. Более безопасный workflow

Перед rebase полезно получить актуальное состояние удалённого репозитория:

```bash
git fetch origin
```

Затем:

```bash
git switch feature
git rebase origin/main
```

Получаем:

```text
origin/main
     │
     ▼
A---B---C---F---G---D'---E'
                         ▲
                       feature
```

Это особенно полезно, если локальный `main` давно не обновлялся.

---

# 7. Rebase с конфликтом

Rebase тоже может привести к конфликтам.

Например:

```bash
git rebase main
```

Git сообщает о конфликте.

Проверяем:

```bash
git status
```

Исправляем конфликтующие файлы.

После исправления:

```bash
git add <file>
```

Продолжаем rebase:

```bash
git rebase --continue
```

Если конфликтов несколько, процесс повторяется:

```text
исправить
   ↓
git add
   ↓
git rebase --continue
   ↓
следующий конфликт
   ↓
исправить
   ↓
...
```

---

# 8. Как отменить Rebase

Если понимаем, что rebase пошёл не туда:

```bash
git rebase --abort
```

Git пытается вернуть состояние, которое было до начала rebase.

Например:

```bash
git rebase main

# конфликты / передумали

git rebase --abort
```

---

# 9. `git rebase --continue`

После разрешения конфликта:

```bash
git add .
git rebase --continue
```

Git продолжает воспроизводить следующие коммиты.

Полный цикл:

```bash
git rebase main

# конфликт

# исправляем файлы

git add .
git rebase --continue
```

---

# 10. `git rebase --skip`

Иногда конкретный коммит больше не нужен или его изменения уже присутствуют в новой базе.

Тогда можно пропустить текущий коммит:

```bash
git rebase --skip
```

Использовать это нужно осознанно: фактически изменения этого коммита будут исключены из результата rebase.

# 11. Rebase и Merge — главное сравнение

|                                                | Merge              | Rebase                 |
| ---------------------------------------------- | ------------------ | ---------------------- |
| Объединяет ветки                               | ✅                  | Через перенос коммитов |
| Сохраняет ветвление истории                    | ✅                  | ❌                      |
| Может создать merge commit                     | ✅                  | ❌                      |
| Переписывает существующие коммиты              | ❌                  | ✅                      |
| Создаёт новые SHA для переносимых коммитов     | ❌                  | ✅                      |
| История обычно линейная                        | ❌                  | ✅                      |
| Безопасен для уже опубликованной общей истории | Обычно да          | ⚠️ Нет                 |
| Основная идея                                  | Объединить истории | Перестроить историю    |

### На уровне графа

**Merge:**

```text
A---B---C-------M
     \         /
      D---E---
```

**Rebase:**

```text
A---B---C---D'---E'
```

# 12. Почему Rebase опасен для общей ветки

Представим:

```text
A---B---C---D  origin/feature
```

Ты уже отправил `feature` коллегам.

Затем выполняешь:

```bash
git rebase main
```

Получается:

```text
A---B---C---F---G---D'---E'
```

Старые `D` и `E` заменены новыми `D'` и `E'`.

Но у коллег всё ещё:

```text
A---B---C---D---E
```

Истории теперь расходятся.

Поэтому правило:

> **Не следует без необходимости делать rebase публичной ветки, которую уже используют другие разработчики.**

---

# 13. Rebase и Force Push

После rebase уже опубликованной собственной feature-ветки:

```bash
git push
```

может завершиться ошибкой:

```text
non-fast-forward
```

Потому что удалённая ветка содержит старую историю.

В таком случае используют:

```bash
git push --force-with-lease
```

Почему именно `--force-with-lease`?

Он проверяет, что удалённая ветка всё ещё находится в ожидаемом состоянии.

Это безопаснее, чем:

```bash
git push --force
```

Потому что обычный `--force` безусловно перезаписывает удалённую ссылку и может затереть чужие изменения.

# 14. Интерактивный Rebase

Есть ещё один очень важный вариант:

```bash
git rebase -i HEAD~3
```

`-i` означает **interactive**.

Он позволяет изменить несколько последних коммитов.

Например:

```text
pick  abc123 Add login
pick  def456 Fix typo
pick  789abc Fix login
```

Можно изменить действия:

```text
pick   abc123 Add login
squash def456 Fix typo
squash 789abc Fix login
```

В результате несколько коммитов объединятся:

```text
Add login
```

Вместо:

```text
Add login
Fix typo
Fix login
```

---

# 15. Основные команды Interactive Rebase

Часто встречаются:

| Команда  | Значение                                          |
| -------- | ------------------------------------------------- |
| `pick`   | Оставить коммит                                   |
| `reword` | Изменить сообщение                                |
| `edit`   | Остановиться для изменения коммита                |
| `squash` | Объединить с предыдущим и редактировать сообщение |
| `fixup`  | Объединить с предыдущим без сохранения сообщения  |
| `drop`   | Удалить коммит                                    |

Например:

```bash
git rebase -i HEAD~4
```

означает:

> «Открой последние 4 коммита для интерактивного редактирования истории».

# 16. Rebase vs Merge на практике

Допустим, есть:

```text
main:
A---B---C---F

feature:
     \
      D---E
```

### Вариант 1 — Merge

```bash
git switch main
git merge feature
```

Получаем:

```text
A---B---C---F---M
     \         /
      D---E---
```

История сохраняет факт параллельной разработки.

### Вариант 2 — Rebase

```bash
git switch feature
git rebase main
```

Получаем:

```text
A---B---C---F---D'---E'
```

История становится линейной.

# 17. Типичная стратегия Feature Branch

Один из распространённых вариантов:

```text
main
  │
  ├── feature/login
  │
  ├── feature/payment
  │
  └── feature/profile
```

Разработчик работает в:

```text
feature/login
```

За это время `main` меняется:

```text
A---B---C---F---G  main
     \
      D---E        feature/login
```

Перед созданием Pull Request разработчик обновляет свою ветку:

```bash
git fetch origin
git rebase origin/main
```

Получается:

```text
A---B---C---F---G---D'---E'  feature/login
```

После этого открывается Pull Request.

Конкретная политика команды может отличаться: некоторые команды предпочитают merge, другие — rebase или squash merge.

# 18. Частая ошибка: перепутать направление

Если выполнить:

```bash
git switch feature
git rebase main
```

это означает:

> **Перенести коммиты `feature` на вершину `main`.**

То есть:

```text
Было:

main     A---B---C---F---G
              \
feature         D---E

Стало:

main     A---B---C---F---G
                         \
feature                  D'---E'
```

А команда:

```bash
git switch main
git rebase feature
```

делает уже совершенно другое: коммиты `main`, отсутствующие в `feature`, будут воспроизведены поверх `feature`.

Поэтому всегда сначала смотри, **на какой ветке находишься**.

# 19. Как посмотреть историю

Для понимания результата rebase удобно использовать:

```bash
git log --oneline --graph --all
```

Например:

```text
* e12ab34 Add validation
* 9cd5678 Add login
* 81ab234 Update main
* 72ef345 Initial commit
```

После rebase история часто выглядит линейно, что упрощает чтение графа.

## 🎤 Вопросы на собеседовании

### Что такое rebase?

> Перенос коммитов одной ветки на новую базу с последующим воспроизведением этих коммитов.

### Чем rebase отличается от merge?

> Merge объединяет две истории и при необходимости создаёт merge commit. Rebase переписывает историю, создавая новые версии коммитов поверх другой базы.

### Почему после rebase меняется SHA?

> Потому что у перенесённого коммита меняется родительский коммит, а родитель является частью идентичности Git-коммита.

### Можно ли делать rebase публичной ветки?

> Технически можно, но это опасно, потому что rebase переписывает историю. Если другие разработчики уже используют эту ветку, можно создать проблемы при синхронизации.

### Что делать после конфликта во время rebase?

```bash
git add .
git rebase --continue
```

### Как отменить rebase?

```bash
git rebase --abort
```

### Что такое interactive rebase?

> Это режим `git rebase -i`, который позволяет изменять историю нескольких коммитов: менять сообщения, объединять коммиты, удалять их или редактировать.

### Почему после rebase может понадобиться force push?

> Потому что история локальной ветки была переписана и её коммиты больше не соответствуют истории удалённой ветки. Для собственной опубликованной ветки обычно безопаснее использовать `git push --force-with-lease`.

### Что предпочтительнее — merge или rebase?

> Универсального ответа нет. Merge сохраняет историю ветвления и безопасен для общей истории. Rebase позволяет получить более линейную историю, но переписывает коммиты. Выбор зависит от workflow команды.
