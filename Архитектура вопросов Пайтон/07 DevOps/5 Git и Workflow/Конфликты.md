# ⚔️ Конфликты в Git

## 🎤 Короткий ответ

**Merge conflict** возникает, когда Git не может автоматически объединить изменения из разных веток.

Обычно это происходит, когда две ветки изменили **один и тот же участок файла несовместимым образом**.

Git помечает конфликт прямо в файле:

```text
<<<<<<< HEAD
версия текущей ветки
=======
версия другой ветки
>>>>>>> feature
```

Я выбираю или объединяю правильный вариант, удаляю конфликтные маркеры, затем выполняю:

```bash
git add .
git commit
```

При `rebase` после разрешения конфликта используется:

```bash
git add .
git rebase --continue
```

---

## 🗣️ Ответ на собеседовании

> Конфликт в Git возникает, когда Git не может автоматически объединить изменения из двух веток. Чаще всего это происходит, когда разные ветки изменили один и тот же участок файла.
>
> При merge Git останавливает операцию и помечает конфликтующие места специальными маркерами `<<<<<<<`, `=======` и `>>>>>>>`.
>
> Я анализирую обе версии, выбираю одну или объединяю их вручную, удаляю маркеры, затем добавляю исправленный файл через `git add`.
>
> Если это merge, завершаю операцию через `git commit`. Если конфликт возник во время rebase — использую `git rebase --continue`.
>
> Если понимаю, что операцию лучше отменить, использую `git merge --abort` или `git rebase --abort`.
>
> Сам конфликт не означает ошибку Git — это ситуация, в которой Git не может определить правильный вариант за разработчика.

# 📚 Разбор поглубже

## 1. Что такое конфликт

Git умеет автоматически объединять огромное количество изменений.

Например:

```text
main:
A---B---C

feature:
     \
      D---E
```

Если изменения не пересекаются, Git может самостоятельно их объединить.

Но если обе ветки изменили один и тот же участок файла:

```text
main      → изменить строку 10
feature   → изменить строку 10
```

Git не знает, какая версия должна остаться.

Тогда возникает:

```text
CONFLICT
```

---

# 2. Простой пример

Допустим, в `main`:

```python
timeout = 10
```

А в `feature`:

```python
timeout = 30
```

Мы выполняем:

```bash
git switch main
git merge feature
```

Git обнаруживает конфликт.

Файл может выглядеть так:

```python
<<<<<<< HEAD
timeout = 10
=======
timeout = 30
>>>>>>> feature
```

Это **не синтаксис Python**.

Это специальные маркеры, которые Git добавил для обозначения конфликта.

---

# 3. Что означают маркеры

### `<<<<<<< HEAD`

Начало версии текущей ветки.

```text
<<<<<<< HEAD
timeout = 10
```

`HEAD` здесь указывает на текущую ветку/текущую версию, с которой выполняется операция.

---

### `=======`

Разделитель между двумя версиями:

```text
<<<<<<< HEAD
timeout = 10
=======
timeout = 30
>>>>>>> feature
```

---

### `>>>>>>> feature`

Конец версии из ветки, которую мы пытаемся объединить:

```text
>>>>>>> feature
```

Итого:

```text
<<<<<<< HEAD
версия текущей ветки
=======
версия incoming changes
>>>>>>> feature
```

---

# 4. Как разрешить конфликт

Допустим, мы решили оставить:

```python
timeout = 30
```

Тогда файл должен стать обычным Python-кодом:

```python
timeout = 30
```

Нужно удалить:

```text
<<<<<<< HEAD
=======
>>>>>>> feature
```

После этого Git нужно сообщить:

> «Я разрешил этот конфликт».

Для этого:

```bash
git add <file>
```

Проверяем:

```bash
git status
```

После этого завершаем merge:

```bash
git commit
```

---

# 5. Полный процесс Merge Conflict

Предположим:

```bash
git switch main
git merge feature
```

Git сообщает:

```text
CONFLICT (content): Merge conflict in app.py
```

### Шаг 1 — посмотреть состояние

```bash
git status
```

### Шаг 2 — открыть конфликтующий файл

```python
<<<<<<< HEAD
timeout = 10
=======
timeout = 30
>>>>>>> feature
```

### Шаг 3 — выбрать решение

Например:

```python
timeout = 30
```

### Шаг 4 — добавить файл

```bash
git add app.py
```

### Шаг 5 — завершить merge

```bash
git commit
```

Получится merge commit:

```text
A---B---C-------M
     \         /
      D---E---
```

---

# 6. `git status` во время конфликта

Очень полезная команда:

```bash
git status
```

Git может показать:

```text
You have unmerged paths.

Unmerged paths:
  both modified:   app.py
```

Это означает:

> Один и тот же файл изменён с обеих сторон, и конфликт ещё не разрешён.

После:

```bash
git add app.py
```

Git понимает, что конфликт этого файла разрешён.

---

# 7. Конфликт не обязательно означает одинаковую строку

Конфликт может возникнуть не только из-за буквально одной строки.

Например:

```text
main:
удалил функцию

feature:
изменил эту же функцию
```

Git может не знать, как совместить:

```text
удаление
```

и

```text
изменение
```

Поэтому важно понимать:

> Конфликт — это не просто «две одинаковые строки изменены по-разному».

Это ситуация, когда Git не может однозначно построить итоговый результат.

---

# 8. Конфликты при Rebase

При rebase процесс немного отличается.

Выполняем:

```bash
git switch feature
git rebase main
```

Git пытается воспроизвести коммиты `feature` поверх `main`.

Если возникает конфликт:

```text
CONFLICT (content): Merge conflict in app.py
```

Исправляем файл.

Затем:

```bash
git add app.py
```

Но здесь **не нужно делать обычный `git commit`**.

Нужно:

```bash
git rebase --continue
```

Git продолжит воспроизводить следующие коммиты.

---

# 9. Merge Conflict vs Rebase Conflict

|                    | Merge               | Rebase                  |
| ------------------ | ------------------- | ----------------------- |
| Возникает конфликт | Да                  | Да                      |
| Исправляем файл    | Да                  | Да                      |
| `git add`          | Да                  | Да                      |
| Продолжение        | `git commit`        | `git rebase --continue` |
| Отмена             | `git merge --abort` | `git rebase --abort`    |

Главное:

```text
Merge
  конфликт
     ↓
исправить
     ↓
git add
     ↓
git commit
```

```text
Rebase
  конфликт
     ↓
исправить
     ↓
git add
     ↓
git rebase --continue
```

---

# 10. Как отменить конфликт

Если во время merge понимаем, что проще начать заново:

```bash
git merge --abort
```

Git попробует вернуть состояние до начала merge.

Для rebase:

```bash
git rebase --abort
```

Вернёмся к состоянию до начала rebase.

---

# 11. `ours` и `theirs`

При разрешении конфликта Git позволяет использовать готовые варианты.

Например:

```bash
git checkout --ours app.py
```

оставит версию текущей ветки.

А:

```bash
git checkout --theirs app.py
```

оставит incoming-версию.

В современных версиях Git также можно использовать:

```bash
git restore --ours app.py
```

или:

```bash
git restore --theirs app.py
```

После этого:

```bash
git add app.py
```

⚠️ Важно: `ours` и `theirs` особенно важно правильно интерпретировать при **rebase**, потому что там контекст текущей и воспроизводимой истории отличается от обычного merge.

Поэтому перед использованием лучше проверить `git status` и понять, какую сторону ты действительно хочешь сохранить.

# 12. Конфликт в нескольких файлах

Например:

```text
CONFLICT in:
    app.py
    models.py
    tests/test_auth.py
```

Можно разрешать их по очереди:

```bash
git status
```

Исправить:

```text
app.py
models.py
tests/test_auth.py
```

Добавить:

```bash
git add app.py
git add models.py
git add tests/test_auth.py
```

Проверить:

```bash
git status
```

И завершить операцию.

# 13. Git не решает бизнес-логику

Очень важный момент.

Допустим:

```python
price = 100
```

В одной ветке:

```python
price = 150
```

В другой:

```python
price = 200
```

Git технически видит:

```text
100 → 150
100 → 200
```

Но он не знает:

> Должна цена быть 150 или 200?

Это уже **логическое решение разработчика**.

Поэтому разрешение конфликта — не просто механическая операция.

Нужно понять смысл изменений.

---

# 14. Merge conflict vs логическая ошибка

Это разные вещи.

### Merge conflict

Git физически не смог автоматически объединить изменения:

```text
<<<<<<<
=======
>>>>>>>
```

### Логическая ошибка

Git успешно объединил код:

```python
if user:
    return user
```

Но программа работает неправильно.

Конфликта Git при этом может вообще не быть.

Поэтому после разрешения конфликтов нужно запускать:

```bash
pytest
```

и другие проверки проекта.

# 15. Конфликты в Pull Request

На GitHub конфликт может появиться прямо в Pull Request.

Например:

```text
feature/login
      │
      ▼
Pull Request
      │
      ▼
     main
      │
      ✕
   conflict
```

Причина обычно в том, что целевая ветка изменилась после создания PR.

Например:

```text
main:
A---B---C---F---G

feature:
     \
      D---E
```

PR создан раньше, а `main` продолжила развиваться.

Разработчик может обновить feature через rebase:

```bash
git fetch origin
git switch feature
git rebase origin/main
```

После разрешения конфликтов:

```bash
git push --force-with-lease
```

Затем Pull Request снова проверяется.

---

# 16. Как уменьшать количество конфликтов

Полностью избежать конфликтов невозможно, но их можно уменьшить.

### Часто синхронизировать feature с main

Например:

```bash
git fetch origin
git rebase origin/main
```

### Делать небольшие коммиты

Вместо огромного коммита:

```text
Add entire payment system
```

лучше логически разделять изменения.

### Не менять без необходимости одни и те же файлы

Если несколько разработчиков постоянно редактируют один большой файл, вероятность конфликтов увеличивается.

### Не смешивать разные задачи

Например, в одном PR не стоит одновременно:

```text
переписывать архитектуру
+
форматировать весь проект
+
добавлять новую feature
```

Это значительно усложняет Code Review и повышает вероятность конфликтов.

# 17. Полезная последовательность команд

### Merge

```bash
git switch main
git pull
git merge feature
```

Если конфликт:

```bash
git status
```

Исправляем файлы.

```bash
git add .
git commit
```

Если нужно отменить:

```bash
git merge --abort
```

---

### Rebase

```bash
git fetch origin
git switch feature
git rebase origin/main
```

Если конфликт:

```bash
git status
```

Исправляем.

```bash
git add .
git rebase --continue
```

Если нужно отменить:

```bash
git rebase --abort
```

## 🎤 Вопросы на собеседовании

### Что такое конфликт в Git?

> Ситуация, когда Git не может автоматически объединить изменения из разных историй.

### Когда возникает конфликт?

> Например, когда две ветки несовместимо изменили один участок файла, либо одна ветка удаляет то, что другая изменяет.

### Как Git показывает конфликт?

```text
<<<<<<< HEAD
=======
>>>>>>> branch
```

### Что делать после исправления конфликта при merge?

```bash
git add .
git commit
```

### Что делать после исправления конфликта при rebase?

```bash
git add .
git rebase --continue
```

### Как отменить merge с конфликтом?

```bash
git merge --abort
```

### Как отменить rebase с конфликтом?

```bash
git rebase --abort
```

### Что такое `ours` и `theirs`?

> Это способы выбрать одну из сторон конфликта вместо ручного объединения. При этом нужно учитывать контекст операции, особенно при rebase.

### Конфликт — это ошибка Git?

> Нет. Это ситуация, в которой Git не может определить правильный итоговый вариант и передаёт решение разработчику.

### Нужно ли запускать тесты после разрешения конфликта?

> Да. Успешное разрешение конфликта означает только то, что Git получил синтаксически объединённый набор изменений. Логическая корректность должна дополнительно проверяться тестами и другими CI-проверками.
