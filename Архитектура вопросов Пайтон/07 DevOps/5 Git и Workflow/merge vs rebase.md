# 🔀 `merge` vs `rebase` в Git

## 🎤 Короткий ответ

**`merge` и `rebase` решают одну общую задачу — интегрировать изменения одной ветки с другой, но делают это по-разному.**

`merge` **объединяет две линии истории** и при необходимости создаёт `merge commit`:

```text
A---B---C-------M
     \         /
      D---E---
```

`rebase` **переносит коммиты одной ветки на новую базу и воспроизводит их заново**:

```text
A---B---C---D'---E'
```

Главное различие:

> **Merge сохраняет историю ветвления, а rebase переписывает историю и делает её линейной.**

---

## 🗣️ Ответ на собеседовании

> `merge` и `rebase` используются для интеграции изменений между ветками.
>
> При `merge` Git объединяет две истории. Если ветки после общего предка развивались независимо, создаётся merge commit с двумя родителями. При этом существующие коммиты не переписываются.
>
> При `rebase` Git берёт коммиты текущей ветки, переносит их на новую базу и воспроизводит их заново. Поэтому создаются новые коммиты с другими SHA, а история становится линейной.
>
> Например, если `main` ушла вперёд, feature-ветку можно либо смержить в `main`, сохранив ветвление, либо сделать rebase feature на `main`, получив линейную историю.
>
> Для общей опубликованной истории merge обычно безопаснее, потому что он её не переписывает. Rebase удобен для собственной feature-ветки перед Pull Request, но после уже опубликованного rebase может потребоваться `push --force-with-lease`.

# 📚 Разбор поглубже

## 1. Зачем вообще сравнивать `merge` и `rebase`

Представим:

```text
A---B---C  main
     \
      D---E  feature
```

Ветки разошлись от `B`.

Пока мы работали над `feature`, в `main` появились новые коммиты:

```text
A---B---C---F---G  main
     \
      D---E        feature
```

Теперь изменения двух веток нужно интегрировать.

Есть два основных подхода:

```text
merge
```

или:

```text
rebase
```

---

# 2. Что делает `merge`

Находимся в `main`:

```bash
git switch main
git merge feature
```

Получаем:

```text
A---B---C---F---G-------M  main
     \                 /
      D-------E--------
```

`M` — **merge commit**.

Он имеет двух родителей:

```text
        M
       / \
      G   E
```

При этом:

* `C`, `D`, `E`, `F`, `G` остаются теми же коммитами;
* история не переписывается;
* сохраняется информация о том, что ветки существовали параллельно.

---

# 3. Что делает `rebase`

Находимся в `feature`:

```bash
git switch feature
git rebase main
```

Git условно:

1. находит общий предок;
2. определяет коммиты `feature`, которых нет в `main`;
3. временно убирает их;
4. переносит базу на актуальный `main`;
5. воспроизводит изменения этих коммитов заново.

Было:

```text
A---B---C---F---G  main
     \
      D---E        feature
```

Станет:

```text
A---B---C---F---G---D'---E'  feature
```

`D'` и `E'` — **новые коммиты**.

---

# 4. Самое главное различие

### Merge

```text
A---B---C---F---G---M
     \             /
      D-----------E
```

Git говорит:

> «Я объединяю две существующие истории».

### Rebase

```text
A---B---C---F---G---D'---E'
```

Git говорит:

> «Я переношу изменения feature на новую базу и воспроизвожу их».

Поэтому:

```text
merge  → сохраняет историю
rebase → переписывает историю
```

---

# 5. Почему Rebase меняет SHA

Коммит Git зависит в том числе от своего родительского коммита.

Было:

```text
B
│
D
```

После rebase:

```text
G
│
D'
```

У `D'` уже другой родитель.

Поэтому SHA меняется:

```text
D  → abc123
D' → 789xyz
```

Даже если изменения в коде остались практически такими же.

Это фундаментальная причина, почему rebase считается **переписыванием истории**.

---

# 6. Fast-forward Merge

Есть отдельный случай.

Было:

```text
A---B  main
     \
      C---D  feature
```

`main` после создания `feature` не изменялась.

Выполняем:

```bash
git switch main
git merge feature
```

Git может просто передвинуть указатель:

```text
A---B---C---D
            ↑
        main, feature
```

Это **fast-forward**.

Отдельного merge commit нет.

Поэтому:

> Не каждый `merge` создаёт merge commit.

---

# 7. Сравнение истории

### Merge

```text
A---B---C---F---G-------M
     \                 /
      D---------------E
```

История показывает:

* где ветки разошлись;
* какие изменения развивались параллельно;
* где произошло объединение.

### Rebase

```text
A---B---C---F---G---D'---E'
```

История показывает одну последовательную линию.

---

# 8. Влияние на существующие коммиты

| Свойство                     |    `merge` |                               `rebase` |
| ---------------------------- | ---------: | -------------------------------------: |
| Объединяет изменения         |          ✅ |                                      ✅ |
| Сохраняет существующие SHA   |          ✅ |                     ❌ для перенесённых |
| Переписывает историю         |          ❌ |                                      ✅ |
| Может создать merge commit   |          ✅ |                                      ❌ |
| Сохраняет ветвление          |          ✅ |                                      ❌ |
| Делает историю линейной      | Обычно нет |                                      ✅ |
| Может потребовать force push | Обычно нет | После rebase опубликованной ветки — да |

# 9. Конфликты

Конфликт возможен и при `merge`, и при `rebase`.

## Merge

```bash
git switch main
git merge feature
```

При конфликте:

```text
CONFLICT
```

Исправляем файлы:

```bash
git add .
git commit
```

Отмена:

```bash
git merge --abort
```

---

## Rebase

```bash
git switch feature
git rebase main
```

При конфликте:

```text
CONFLICT
```

Исправляем:

```bash
git add .
git rebase --continue
```

Отмена:

```bash
git rebase --abort
```

Главное различие после разрешения:

```text
merge:
git add
git commit

rebase:
git add
git rebase --continue
```

---

# 10. Когда Rebase особенно удобен

Представим:

```text
main:
A---B---C---F---G

feature:
     \
      D---E
```

Ты единственный разработчик feature-ветки.

Перед Pull Request можно:

```bash
git fetch origin
git switch feature
git rebase origin/main
```

Получить:

```text
A---B---C---F---G---D'---E'
```

Теперь история feature выглядит линейной и содержит актуальную базу `main`.

Это упрощает чтение истории и иногда облегчает review.

---

# 11. Когда Merge удобен

Если ветка уже используется несколькими разработчиками:

```text
feature
   │
   ├── developer A
   ├── developer B
   └── developer C
```

переписывать её историю через rebase может создать проблемы для остальных.

Merge сохраняет существующие коммиты:

```text
A---B---C---F---G-------M
     \                 /
      D---E-----------
```

Другим разработчикам не приходится синхронизировать переписанную историю.

---

# 12. Главное правило про публичные ветки

Упрощённое правило:

> **Не переписывай rebase историю ветки, которую уже используют другие разработчики, без согласования с командой.**

Например, опасно делать:

```bash
git switch main
git rebase feature
```

если `main` уже опубликована и используется командой.

После rebase существующие ссылки на старые коммиты могут перестать соответствовать новой истории.

---

# 13. `force push` после Rebase

Допустим, feature уже была опубликована:

```text
GitHub:

A---B---C---D---E
```

После локального rebase:

```text
A---B---C---F---G---D'---E'
```

Истории больше не совпадают.

Обычный:

```bash
git push
```

может быть отклонён.

Для собственной feature-ветки обычно используют:

```bash
git push --force-with-lease
```

Почему именно `--force-with-lease`:

* позволяет обновить удалённую ветку после переписывания истории;
* дополнительно проверяет, что remote не изменился неожиданным образом.

Безусловный:

```bash
git push --force
```

опаснее, потому что может перезаписать чужую работу.

---

# 14. Merge и Rebase не являются «лучше/хуже»

Это разные стратегии работы с историей.

```text
merge
  ↓
сохранить историю ветвления

rebase
  ↓
получить линейную историю
```

Выбор зависит от workflow команды.

Например, команда может использовать:

```text
feature → rebase → Pull Request → merge
```

или:

```text
feature → Pull Request → merge commit
```

или:

```text
feature → Pull Request → squash merge
```

---

# 15. Squash — ещё один вариант

Не стоит путать:

```text
merge
rebase
squash
```

Например, feature содержит:

```text
D Add login
E Fix typo
F Fix tests
G Fix validation
```

При **squash merge** эти изменения могут попасть в `main` как один commit:

```text
A---B---C---S
```

где:

```text
S = Add login
```

При этом локальная история feature может оставаться отдельной.

То есть:

```text
merge   → объединить истории
rebase  → переписать базу и историю
squash  → объединить несколько изменений в один commit
```

# 17. Как объяснить на пальцах

Можно представить две команды разработчиков.

### Merge

Обе команды независимо построили дороги:

```text
       ┌─── D ─── E ───┐
A ─ B ─┤               ├── M
       └─── C ─── F ───┘
```

Потом дороги соединили.

История обеих дорог сохранилась.

### Rebase

Одну дорогу перестроили так, чтобы она начиналась от последней точки другой:

```text
A ─ B ─ C ─ F ─ G ─ D' ─ E'
```

Получилась одна линия.

# 19. Частые ошибки

### ❌ «Rebase просто переносит ветку»

Не совсем.

Он **переписывает коммиты**, воспроизводя их изменения на новой базе.

---

### ❌ «Merge всегда создаёт commit»

Нет.

Может быть fast-forward:

```text
A---B---C
```

---

### ❌ «Rebase не меняет код»

Он может не менять смысл изменений, но изменяет историю и создаёт новые commit objects.

---

### ❌ «После rebase SHA остаются прежними»

Нет.

Перенесённые коммиты получают новые SHA.

---

### ❌ «Rebase всегда лучше, потому что история красивее»

Нет универсального правила.

Линейность истории — одно преимущество, но переписывание истории может создавать проблемы в общей ветке.

---

### ❌ «Merge и Rebase делают одно и то же»

Они решают одну задачу интеграции изменений, но **изменяют историю по-разному**.

# 20. Формула для запоминания

```text
MERGE
├── объединяет две истории
├── сохраняет существующие коммиты
├── сохраняет ветвление

REBASE
├── меняет базу ветки
├── воспроизводит коммиты заново
├── создаёт новые SHA
├── делает историю линейной
└── переписывает историю
```

## 🎤 Вопросы на собеседовании

### В чём главное отличие `merge` от `rebase`?

> Merge объединяет две существующие истории, а rebase переносит коммиты одной ветки на новую базу и воспроизводит их заново.

### Что происходит с SHA после rebase?

> Перенесённые коммиты получают новые SHA, потому что у них меняются родительские коммиты.

### Создаёт ли merge новый commit?

> Не всегда. Если возможен fast-forward, новый merge commit не создаётся. Если истории разошлись, Git обычно создаёт merge commit.

### Можно ли делать rebase публичной ветки?

> Технически да, но это переписывает историю и может нарушить работу других разработчиков. Особенно нежелательно делать это с общей веткой без согласования.

### Почему после rebase нужен `--force-with-lease`?

> Если ветка уже была опубликована, после rebase её история больше не является продолжением remote-ветки. Поэтому обычный push может быть отклонён, и для собственной ветки используют `--force-with-lease`.

### Что делать при конфликте во время merge?

```bash
git add .
git commit
```

### Что делать при конфликте во время rebase?

```bash
git add .
git rebase --continue
```

### Что выбрать для feature-ветки перед Pull Request?

> Часто feature-ветку можно обновить через rebase на актуальный `main`, если это соответствует workflow команды. Это делает историю линейной, но переписывает историю feature.

### Как сформулировать различие одной фразой?

> **Merge сохраняет историю ветвления, rebase переписывает историю, перенося коммиты на новую базу.**
