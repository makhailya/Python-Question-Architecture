# 🚀 Деплой

## 🎯 Ответ на собеседовании

**Деплой (deployment)** — это процесс развёртывания приложения в окружении, где оно будет работать: на сервере, VM, контейнерах или в Kubernetes.

Цель деплоя — доставить новую версию приложения и запустить её в рабочем окружении.

Типичный процесс:

```text
Код
 ↓
Git
 ↓
CI/CD
 ↓
Build
 ↓
Docker Image
 ↓
Server
 ↓
Container
 ↓
Application
```

---

## 🎤 Суперкоротко

**Деплой — это процесс доставки и запуска новой версии приложения в целевом окружении.**

# 🖥️ Production

**Production** — окружение, в котором работает реальная версия приложения для пользователей.

Можно разделить окружения:

```text
Development
     ↓
Testing
     ↓
Staging
     ↓
Production
```

### Development

Разработчик работает локально.

```text
MacBook
 ↓
FastAPI
 ↓
PostgreSQL
```

### Staging

Среда, максимально похожая на production, где можно проверить новую версию.

```text
Staging Server
 ↓
Application
```

### Production

Рабочая система для пользователей.

```text
Users
  ↓
Production
```

# 🐳 Деплой через Docker

Один из распространённых вариантов для Python-приложения:

```text
Code
 ↓
Dockerfile
 ↓
Docker Image
 ↓
Docker Registry
 ↓
Server
 ↓
Docker Container
```

Например:

```python id="5zt2hs"
docker build -t my-api .
```

Получаем Docker Image.

Затем:

```python id="2gqk0e"
docker push registry.example.com/my-api
```

На сервере:

```python id="9l9g7w"
docker pull registry.example.com/my-api
```

И запускаем контейнер:

```python id="xw7l5a"
docker run -d my-api
```

# 🌐 Reverse Proxy

Перед приложением часто находится **Nginx**.

```text
Client
   ↓
Nginx
   ↓
FastAPI
```

Nginx может выполнять:

* reverse proxy;
* TLS termination;
* load balancing;
* раздачу static files;
* rate limiting;
* маршрутизацию.

# 🔐 Переменные окружения

Секреты и настройки не должны быть захардкожены в коде.

Например:

```python id="h0km6q"
DATABASE_URL
SECRET_KEY
API_KEY
REDIS_URL
```

Они передаются через environment variables или секрет-хранилище.

```text
Application
     ↑
Environment
     ↑
Secrets
```

# 🗄️ Миграции базы данных

Если новая версия приложения меняет структуру БД, перед или во время деплоя необходимо выполнить миграции.

Например, используется Alembic:

```python id="4em0jd"
alembic upgrade head
```

Схема:

```text
New Code
   ↓
DB Migration
   ↓
Application
```

Важно продумывать совместимость новой версии приложения со схемой БД, особенно при zero-downtime deployment.

# 🔄 Rolling Deployment

При **Rolling Deployment** новая версия выкатывается постепенно.

Например:

```text
Старая версия:

v1 v1 v1 v1

        ↓

v2 v1 v1 v1

        ↓

v2 v2 v1 v1

        ↓

v2 v2 v2 v2
```

Преимущество — не нужно останавливать всё приложение одновременно.

---

# 🔵🟢 Blue-Green Deployment

Есть два окружения:

```text
Blue  → текущая версия
Green → новая версия
```

Например:

```text
Users
  ↓
Load Balancer
  ↓
Blue v1
```

Новая версия:

```text
Green v2
```

После проверки переключаем трафик:

```text
Users
  ↓
Load Balancer
  ↓
Green v2
```

Если возникла проблема, можно быстро вернуть трафик на Blue.

---

# 🟡 Canary Deployment

При Canary Deployment новая версия получает только часть трафика.

```text
Users
   ↓
Load Balancer
   ├──→ v1 — 90%
   └──→ v2 — 10%
```

Если всё хорошо:

```text
v1 — 50%
v2 — 50%
```

Затем:

```text
v2 — 100%
```

Это снижает риск массового сбоя.

---

# ⏪ Rollback

**Rollback** — возврат к предыдущей рабочей версии.

Например:

```text
v1 → v2
       ↓
      ❌
       ↓
     rollback
       ↓
      v1
```

Rollback особенно важен, если после деплоя обнаружилась критическая ошибка.

---

# 🩺 Health Check

После деплоя необходимо проверить, что приложение работает.

Например:

```python id="c8eq2s"
GET /health
```

Ответ:

```python id="v6y2gs"
{
    "status": "ok"
}
```

Health check позволяет определить, доступен ли сервис.

В production также проверяют:

* подключение к БД;
* Redis;
* внешние сервисы;
* состояние worker'ов;
* ошибки в логах.

---

# 📊 Мониторинг

После деплоя важно не просто запустить приложение, а наблюдать за ним.

Контролируют:

```text
CPU
RAM
Disk
Latency
Errors
Requests/sec
Database
Consumer Lag
```

Используются:

* логи;
* метрики;
* алерты;
* distributed tracing.

# ⚙️ CI/CD + Deployment

CI/CD автоматизирует деплой.

   ↓

 ├── Lint
 └── Build
   ↓
Docker Image
   ↓
Registry
   ↓
CD
   ↓

   ↓

   ↓

```text

  ↓
❌
  ↓

```

# ☸️ Деплой в Kubernetes

В Kubernetes приложение обычно описывается через Deployment:

```text
Kubernetes
    ↓
Deployment
    ↓
Pods
    ├── FastAPI
    ├── FastAPI
    └── FastAPI
```

Kubernetes может:

* запускать несколько экземпляров;
* перезапускать упавшие контейнеры;
* масштабировать приложение;
* выполнять rolling update;
* распределять трафик.

# ⚠️ Что может пойти не так

При деплое возможны:

* приложение не запускается;
* ошибка миграции БД;
* неправильные environment variables;
* несовместимость зависимостей;
* проблемы с Docker;
* проблемы с сетью;
* нехватка CPU/RAM;
* недоступность БД;
* неправильная конфигурация Nginx;
* ошибки новой версии.

Поэтому deployment обычно сопровождается:

```text
Tests
+
Health Checks
+
Logs
+
Monitoring
+
Rollback
```

# 🆚 Deployment vs Release

Эти понятия иногда используют как синонимы, но технически их можно различать.

**Deployment** — техническое размещение новой версии приложения в окружении.

**Release** — предоставление этой версии функциональности пользователям.

Например:

```text
Deploy v2
   ↓
v2 находится на production
   ↓
Feature Flag OFF
   ↓
пользователи ещё не видят новую функцию
```

То есть deployment не обязательно означает немедленный release функциональности.
