# ⚙️ Процессы в Linux

## 🎤 Короткий ответ

**Процесс** — это выполняющийся экземпляр программы. У процесса есть собственное состояние и ресурсы, например адресное пространство памяти, файловые дескрипторы и идентификатор PID.

Linux управляет процессами: создаёт их, планирует выполнение на CPU, предоставляет им память и I/O, а также позволяет отправлять им сигналы.

Основные команды для работы:

```bash
ps aux
top
htop
pgrep
kill
```

Для Backend-разработчика процессы особенно важны, потому что серверное приложение, например FastAPI, PostgreSQL или Nginx, работает в виде одного или нескольких процессов.

---

## 🗣️ Ответ на собеседовании

Процесс — это выполняющийся экземпляр программы. Сама программа — это код и данные, которые могут находиться на диске, а процесс — уже запущенная программа с собственным состоянием и ресурсами.

У процесса есть PID, собственное виртуальное адресное пространство, регистры CPU, стек, heap, открытые файловые дескрипторы и другая служебная информация.

Linux kernel управляет процессами и планирует их выполнение на процессорах. Процессы могут создавать дочерние процессы, взаимодействовать между собой через IPC и получать сигналы.

Например, если я запускаю:

```bash
python app.py
```

Linux создаёт процесс Python, присваивает ему PID и выделяет необходимые ресурсы. Если приложение работает как Backend-сервис, этот процесс может принимать сетевые соединения и обрабатывать HTTP-запросы.

# 📚 Разбор поглубже

## 1. Программа и процесс

Это одно из главных различий.

**Программа** — набор инструкций и данных, обычно представленный файлом на диске.

**Процесс** — экземпляр программы, который выполняется в данный момент.

Например:

```text
python app.py
```

`app.py` — исходный код программы.

После запуска:

```text
app.py
   ↓
Python interpreter
   ↓
Process
   ↓
PID 1234
```

Одна программа может иметь несколько одновременно работающих процессов:

```text
app.py
 ├── Process 1001
 ├── Process 1002
 └── Process 1003
```

Каждый процесс имеет собственное состояние.

# 2. Что находится внутри процесса

Упрощённо процесс можно представить так:

```text
Process
├── PID
├── Virtual Address Space
│   ├── Code
│   ├── Data
│   ├── Heap
│   └── Stack
├── CPU Registers
├── File Descriptors
├── Environment Variables
├── Current Working Directory
├── User / Group IDs
└── Process State
```

Не все эти элементы физически принадлежат процессу в одинаковом смысле: например, таблицы процессов и часть служебной информации управляются ядром. Но это полезная модель для понимания того, что Linux отслеживает для процесса.

# 3. PID

Каждый процесс получает **PID — Process ID**.

Например:

```text
python app.py
      ↓
PID = 1234
```

Посмотреть процессы:

```bash
ps aux
```

Можно найти конкретный процесс:

```bash
pgrep python
```

или:

```bash
pgrep -f "app.py"
```

# 4. `ps`

`ps` показывает информацию о процессах.

Например:

```bash
ps aux
```

Можно получить:

```text
USER       PID %CPU %MEM COMMAND
ilya      1234  2.1  1.5 python app.py
nginx     1300  0.1  0.2 nginx
postgres  1400  0.5  3.2 postgres
```

Полезные варианты:

```bash
ps
ps aux
ps -ef
```

# 5. `top` и `htop`

`top` показывает процессы в реальном времени:

```bash
top
```

Можно видеть:

* PID;
* загрузку CPU;
* использование памяти;
* состояние процессов;
* время работы.

`htop` — более удобный интерактивный аналог:

```bash
htop
```

# 6. Родительский и дочерний процесс

Процессы в Linux образуют иерархию.

Например:

```text
systemd
├── nginx
│   ├── worker
│   └── worker
└── python
    └── child process
```

У процесса есть **parent process**.

Можно посмотреть PPID:

```bash
ps -o pid,ppid,cmd
```

Например:

```text
PID   PPID  CMD
1000     1  python app.py
1050  1000  python worker.py
```

Здесь:

```text
1000 → parent
1050 → child
```

# 7. `fork`

В Unix/Linux процесс может создать дочерний процесс с помощью системного вызова `fork()`.

Упрощённо:

```text
Parent Process
      │
    fork()
      │
 ┌────┴────┐
 ▼         ▼
Parent    Child
```

После `fork()` создаётся новый процесс, который первоначально получает копию адресного пространства родителя с учётом механизмов copy-on-write.

В Python `multiprocessing` на системах, использующих `fork`, может использовать этот механизм под капотом.

---

# 8. `exec`

`fork()` создаёт новый процесс, а семейство системных вызовов `exec*()` заменяет выполняемую программу в текущем процессе.

Упрощённая модель запуска:

```text
Parent
  │
  └── fork()
        │
        ▼
      Child
        │
        └── exec()
              │
              ▼
        New Program
```

То есть после `exec()` PID процесса обычно сохраняется, но его программа заменяется.

---

# 9. Почему `fork + exec` важны

Это фундаментальная модель Unix-процессов.

Например, shell выполняет:

```bash
ls -la
```

Упрощённо можно представить:

```text
Shell
  │
  ├── fork()
  │
  ▼
Child Process
  │
  └── exec("ls")
          ↓
        ls
```

Поэтому shell может запускать внешние программы, не заменяя сам себя.

---

# 10. Состояния процесса

Процесс не всегда выполняется на CPU.

Упрощённо можно представить состояния:

```text
        ┌─────────────┐
        │    Ready    │
        └──────┬──────┘
               │
            scheduled
               ↓
        ┌─────────────┐
        │   Running   │
        └──────┬──────┘
          │    │
       I/O│    │exit
          │    │
          ▼    ▼
     Waiting  Terminated
          │
          │ I/O completed
          └────────→ Ready
```

В Linux также существуют конкретные состояния, отображаемые, например, в `ps`.

Часто встречаются:

* `R` — running/runnable;
* `S` — interruptible sleep;
* `D` — uninterruptible sleep;
* `T` — stopped;
* `Z` — zombie.

---

# 11. Running и Runnable

Это важный нюанс.

Процесс в состоянии `R` в Linux может означать:

* фактически выполняется на CPU;
* готов к выполнению и ожидает своей очереди.

Поэтому `R` лучше понимать как **running/runnable**, а не просто «прямо сейчас выполняется».

---

# 12. Waiting

Процесс может ожидать событие.

Например, приложение ждёт:

```text
network I/O
disk I/O
timer
lock
child process
```

В это время нет смысла постоянно занимать CPU.

Поэтому процесс может перейти в состояние ожидания.

Например:

```text
Python
  │
  │ read(socket)
  ▼
Waiting
  │
  │ data arrived
  ▼
Runnable
  │
  ▼
Running
```

---

# 13. Zombie Process

**Zombie** — завершившийся процесс, информация о котором всё ещё сохраняется в таблице процессов, пока родитель не заберёт его статус завершения через `wait()`/`waitpid()`.

Упрощённо:

```text
Parent
  │
  └── Child
       │
       └── exit()
             ↓
          Zombie
```

Zombie уже не выполняется и не потребляет обычную память процесса, но занимает запись в таблице процессов.

Родитель должен выполнить:

```text
wait()
```

чтобы получить статус завершения и освободить эту запись.

---

# 14. Orphan Process

Если родительский процесс завершился раньше дочернего, дочерний процесс становится **orphan**.

В современных Linux-системах такой процесс может быть переназначен специальному процессу-subreaper или, в обычном случае, `init/systemd` с PID 1.

Упрощённо:

```text
Parent
  │
  └── Child
       │
       │ parent exits
       ▼
     Orphan
       │
       ▼
 adopted by PID 1 / subreaper
```

Не стоит путать:

```text
Zombie → child уже завершился, но parent ещё не забрал статус.

Orphan → child ещё работает, но его parent уже завершился.
```

---

# 15. PID 1

В обычной Linux-системе первым пользовательским процессом является процесс с PID 1.

На системах с `systemd`:

```text
PID 1 → systemd
```

Он играет важную роль в:

* запуске системы;
* управлении службами;
* обработке некоторых orphan-процессов;
* управлении жизненным циклом сервисов.

В контейнерах ситуация может отличаться: процесс с PID 1 внутри контейнера может быть непосредственно приложением или специальным init-процессом.

---

# 16. Планирование процессов

CPU физически может выполнять ограниченное количество потоков одновременно.

Если процессов больше:

```text
Processes:
P1
P2
P3
P4
P5
```

ядро планирует их выполнение.

Упрощённо:

```text
CPU
 │
 ├── P1
 ├── P3
 ├── P2
 ├── P1
 └── P4
```

Операционная система быстро переключает выполнение между runnable threads.

Это создаёт ощущение параллельного выполнения даже на одном CPU, хотя физически одновременно выполняется ограниченное число потоков.

На многоядерной системе несколько потоков могут реально выполняться одновременно на разных CPU.

---

# 17. Context Switch

**Context switch** — переключение CPU с одного выполняемого потока на другой.

Упрощённо:

```text
Thread A
   ↓
save context
   ↓
restore context B
   ↓
Thread B
```

Ядру необходимо сохранить состояние одного потока и восстановить состояние другого.

Частые переключения имеют стоимость, поэтому большее количество процессов/потоков не означает автоматически большую производительность.

---

# 18. Процесс и память

Каждый процесс имеет собственное **виртуальное адресное пространство**.

Например:

```text
Process A
└── Virtual Memory A

Process B
└── Virtual Memory B
```

Обычные процессы не могут напрямую обращаться к произвольной памяти друг друга.

Это важная часть изоляции процессов.

Для обмена данными используются специальные механизмы IPC или разделяемая память.

---

# 19. Process vs Thread

Процесс — более крупная единица изоляции.

Потоки находятся внутри процесса и разделяют его адресное пространство.

```text
Process
├── Thread 1
├── Thread 2
└── Thread 3
```

Потоки одного процесса обычно разделяют:

* heap;
* global data;
* открытые ресурсы процесса.

Но у каждого потока есть собственный:

* stack;
* registers;
* execution state.

---

# 20. Процессы и Python

В Python можно создавать отдельные процессы через `multiprocessing`.

Например:

```python
from multiprocessing import Process


def worker():
    print("Worker")


process = Process(target=worker)

process.start()
process.join()
```

Упрощённо:

```text
Main Process
     │
     └── Worker Process
```

Отдельные процессы имеют отдельные адресные пространства.

Это отличается от `threading`, где потоки одного процесса разделяют память.

---

# 21. Процессы и GIL

Для CPython важно различать процессы и потоки.

GIL ограничивает выполнение Python bytecode в нескольких потоках одного процесса определённым образом.

Отдельные процессы имеют отдельные адресные пространства и отдельные экземпляры интерпретатора, поэтому multiprocessing позволяет использовать несколько CPU cores для CPU-bound Python-кода.

Упрощённо:

```text
Process 1
└── Python interpreter
    └── GIL

Process 2
└── Python interpreter
    └── GIL
```

Поэтому процессы часто используются для CPU-bound задач.

# 22. Межпроцессное взаимодействие — IPC

Поскольку процессы изолированы, им нужны специальные механизмы для обмена данными.

**IPC — Inter-Process Communication.**

Основные варианты:

```text
IPC
├── Pipe
├── Queue
├── Shared Memory
├── Unix Socket
├── Signals
└── другие механизмы
```

В Python, например:

```python
from multiprocessing import Queue
```

можно использовать очередь для обмена сообщениями между процессами.

# 23. File Descriptors

Процесс имеет таблицу открытых файловых дескрипторов.

Например:

```text
Process
├── FD 0 → stdin
├── FD 1 → stdout
├── FD 2 → stderr
├── FD 3 → file
└── FD 4 → socket
```

Важно:

> File descriptor — это не обязательно обычный файл.

Через FD процесс может работать с:

* файлами;
* sockets;
* pipes;
* terminal;
* другими I/O-объектами.

---

# 24. Signals

Linux позволяет отправлять процессам сигналы.

Например:

```bash
kill -TERM 1234
```

отправляет процессу `PID 1234` сигнал `SIGTERM`.

Популярные сигналы:

```text
SIGTERM → корректное завершение
SIGKILL → принудительное завершение
SIGINT  → прерывание, например Ctrl+C
SIGHUP  → hangup; смысл зависит от приложения
```

### `SIGTERM`

Процесс может обработать сигнал и корректно завершиться.

### `SIGKILL`

Процесс не может обработать или проигнорировать `SIGKILL`.

---

# 25. `kill` не обязательно означает «убить»

Название команды может вводить в заблуждение.

```bash
kill -TERM 1234
```

не означает безусловное уничтожение процесса.

Команда `kill` отправляет **сигнал**.

Например:

```bash
kill -STOP 1234
```

может остановить выполнение процесса.

А:

```bash
kill -CONT 1234
```

возобновить его выполнение.

# 26. Приоритет процессов

Linux использует приоритеты планирования.

Для обычных процессов можно встретить значение **nice**.

Посмотреть:

```bash
ps -eo pid,ni,cmd
```

Запустить с определённым nice:

```bash
nice -n 10 python worker.py
```

Изменить:

```bash
renice 10 -p 1234
```

В общем случае:

> Чем выше значение nice, тем ниже приоритет обычного процесса относительно других процессов.

# 27. Process vs Service

Это тоже важно различать.

**Process** — выполняющийся экземпляр программы.

**Service** — логическая системная служба, обычно управляемая менеджером служб, например systemd.

Например:

```text
systemd
   │
   └── nginx.service
          │
          └── nginx processes
```

Одна service может управлять одним или несколькими процессами.

# 30. Как завершить процесс

Сначала обычно стоит попытаться корректно завершить процесс:

```bash
kill 1234
```

Это обычно:

```text
SIGTERM
```

Если процесс не завершился и есть основания для принудительного завершения:

```bash
kill -9 1234
```

Это:

```text
SIGKILL
```

Важно не использовать `SIGKILL` без необходимости: приложение не получает возможности выполнить cleanup.

# 31. Жизненный цикл процесса

Упрощённо:

```text
Create
  ↓
Ready / Runnable
  ↓
Running
  ↓
Waiting ───────┐
  ↓            │
Runnable ←─────┘
  ↓
Terminated
```

При создании процесса ядро выделяет и настраивает необходимые структуры и ресурсы.

Во время работы процесс может:

* выполняться;
* ждать I/O;
* быть вытеснен планировщиком;
* получать сигналы;
* создавать дочерние процессы;
* завершаться.

# 32. Что важно различать

### Программа vs процесс

```text
Программа → набор инструкций
Процесс   → выполняющийся экземпляр программы
```

### Процесс vs поток

```text
Process
├── Thread
├── Thread
└── Thread
```

Процессы изолированы по адресному пространству, потоки одного процесса обычно его разделяют.

### Zombie vs Orphan

```text
Zombie → уже завершился, parent ещё не забрал status

Orphan → ещё работает, parent уже завершился
```

### `SIGTERM` vs `SIGKILL`

```text
SIGTERM → можно обработать
SIGKILL → нельзя перехватить
```

### Process vs Service

```text
Process → выполняющийся экземпляр
Service → управляемая системная служба
```

## 🎤 Вопросы на собеседовании

### Что такое процесс?

Процесс — выполняющийся экземпляр программы со своим состоянием, виртуальным адресным пространством и ресурсами.

### Что такое PID?

Уникальный идентификатор процесса.

### Чем процесс отличается от программы?

Программа — код и данные, а процесс — экземпляр этой программы, который выполняется под управлением ОС.

### Чем процесс отличается от потока?

Процессы имеют отдельные адресные пространства, а потоки одного процесса обычно разделяют память и другие ресурсы процесса.

### Что такое PPID?

**Parent Process ID** — идентификатор родительского процесса.

### Что такое `fork()`?

Системный вызов, создающий новый процесс на основе вызывающего процесса.

### Что делает `exec()`?

Заменяет программу, выполняемую текущим процессом, на другую программу, сохраняя PID процесса.

### Что такое Zombie Process?

Завершившийся процесс, запись о котором остаётся в таблице процессов до тех пор, пока родитель не получит его статус через `wait()`/`waitpid()`.

### Что такое Orphan Process?

Работающий дочерний процесс, родитель которого завершился. Такой процесс переназначается системе или subreaper.

### Что такое context switch?

Переключение выполнения CPU между потоками/процессами с сохранением и восстановлением их контекста.

### Что такое IPC?

**Inter-Process Communication** — механизмы взаимодействия между процессами: pipes, queues, shared memory, Unix sockets и другие.

### Что такое file descriptor процесса?

Числовой идентификатор открытого I/O-объекта, например файла, socket или pipe.

### Что делает `kill`?

Отправляет процессу сигнал.

### Чем `SIGTERM` отличается от `SIGKILL`?

`SIGTERM` позволяет процессу обработать запрос на завершение и выполнить cleanup. `SIGKILL` процесс обработать не может и не может его перехватить.

### Как посмотреть процессы в Linux?

Например:

```bash
ps aux
top
htop
pgrep
```

### Как найти процесс Python?

```bash
pgrep python
```

или:

```bash
ps aux | grep python
```

### Как завершить процесс?

Сначала обычно:

```bash
kill PID
```

Если процесс не завершается и требуется принудительное завершение:

```bash
kill -9 PID
```

### Зачем Backend-разработчику понимать процессы?

Потому что серверное приложение выполняется в процессах. Понимание PID, памяти, CPU, сигналов, процессов-воркеров, file descriptors и жизненного цикла процессов необходимо для диагностики и эксплуатации Backend-приложений.
