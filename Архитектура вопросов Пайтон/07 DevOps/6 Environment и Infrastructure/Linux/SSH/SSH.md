# 🔐 SSH

## 🎤 Короткий ответ

**SSH (Secure Shell)** — сетевой протокол для безопасного удалённого доступа к компьютерам и серверам по сети.

Чаще всего SSH используют для:

* удалённого входа на Linux-сервер;
* выполнения команд;
* передачи файлов;
* создания защищённых туннелей;
* аутентификации по SSH-ключам.

Типичное подключение:

```bash
ssh user@server
```

SSH обычно работает поверх **TCP**, стандартный порт — **22**.

Для Backend-разработчика SSH — основной инструмент для работы с удалёнными Linux-серверами.

# 📚 Разбор поглубже

## 1. Что такое SSH

SSH расшифровывается как:

> **Secure Shell**

Это протокол семейства TCP/IP для защищённого взаимодействия с удалённым компьютером.

Основной сценарий:

```text
Мой компьютер
      │
      │ SSH
      ▼
Linux Server
      │
      └── Bash
```

Например:

```bash
ssh user@server
```

После подключения команды выполняются уже на удалённом сервере.

---

# 2. SSH Client и SSH Server

SSH использует клиент-серверную модель.

```text
SSH Client                    SSH Server
    │                              │
    │──── TCP connection ─────────>│
    │                              │
    │<──── authentication ────────>│
    │                              │
    │<──── encrypted channel ─────>│
```

### SSH Client

Запускается на компьютере, с которого мы подключаемся.

Например:

```bash
ssh user@server
```

### SSH Server

Работает на удалённом компьютере.

В Linux обычно используется:

```text
sshd
```

— SSH daemon.

Проверить службу можно:

```bash
sudo systemctl status ssh
```

или на некоторых дистрибутивах:

```bash
sudo systemctl status sshd
```

---

# 3. Подключение к серверу

Базовый синтаксис:

```bash
ssh user@host
```

Например:

```bash
ssh ilya@192.168.1.100
```

Здесь:

```text
ilya         → пользователь
192.168.1.100 → адрес сервера
```

Можно указать порт:

```bash
ssh -p 2222 ilya@192.168.1.100
```

По умолчанию SSH использует:

```text
TCP 22
```

---

# 4. Что происходит при подключении

Упрощённо процесс выглядит так:

```text
ssh user@server
       │
       ▼
DNS / IP resolution
       │
       ▼
TCP connection
       │
       ▼
SSH handshake
       │
       ▼
Server authentication
       │
       ▼
User authentication
       │
       ▼
Encrypted session
       │
       ▼
Remote shell
```

Важный момент:

> Сначала устанавливается защищённое SSH-соединение, после чего пользователь проходит аутентификацию.

---

# 5. Шифрование

SSH обеспечивает защищённый канал между клиентом и сервером.

Он обеспечивает, в частности:

* **конфиденциальность** — данные шифруются;
* **целостность** — изменения данных в канале обнаруживаются;
* **аутентификацию сервера**;
* **аутентификацию пользователя**.

Упрощённо:

```text
Client
  │
  │ encrypted data
  ▼
Internet
  │
  │ encrypted data
  ▼
Server
```

Поэтому передаваемые через SSH команды и данные защищены от простого перехвата в сети.

---

# 6. Аутентификация по паролю

Самый простой вариант:

```bash
ssh user@server
```

SSH-сервер запрашивает пароль пользователя.

```text
Client
   │
   │ username
   ▼
Server
   │
   │ password authentication
   ▼
Access granted
```

Для production-серверов часто предпочитают ключевую аутентификацию.

---

# 7. SSH Keys

SSH поддерживает криптографическую аутентификацию с помощью пары ключей:

```text
Private Key
Public Key
```

Например:

```text
~/.ssh/
├── id_ed25519
└── id_ed25519.pub
```

### Private Key

Секретный ключ.

> Его нельзя передавать другим людям или выкладывать в Git.

### Public Key

Открытый ключ.

Его можно разместить на сервере.

---

# 8. Как работает ключевая аутентификация

Упрощённо:

```text
Client
│
├── Private Key
│
└──────────────→ Server
                  │
                  └── Authorized Public Key
```

При подключении клиент доказывает серверу, что владеет соответствующим private key, не передавая сам private key серверу.

На сервере открытые ключи пользователя обычно находятся в:

```text
~/.ssh/authorized_keys
```

---

# 9. Создание SSH-ключа

Современный распространённый вариант:

```bash
ssh-keygen -t ed25519
```

Получаем:

```text
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

Где:

```text
id_ed25519
```

— private key.

```text
id_ed25519.pub
```

— public key.

---

# 10. `authorized_keys`

На сервере у пользователя может находиться:

```text
~/.ssh/authorized_keys
```

В нём находятся разрешённые public keys.

Упрощённо:

```text
Server
└── ~/.ssh/
    └── authorized_keys
        ├── public key A
        ├── public key B
        └── public key C
```

Если клиент доказывает владение соответствующим private key, сервер может разрешить вход.

---

# 11. Передача public key

Удобный способ:

```bash
ssh-copy-id user@server
```

После этого public key добавляется в `authorized_keys`.

Можно сделать это и вручную.

Важно:

> На сервер передаётся **public key**, а не private key.

---

# 12. `ssh-agent`

Если private key защищён passphrase, не обязательно вводить её при каждом SSH-подключении.

Для этого используется `ssh-agent`.

Упрощённо:

```text
Private Key
     ↓
ssh-agent
     ↓
SSH Client
     ↓
Server
```

Добавить ключ:

```bash
ssh-add ~/.ssh/id_ed25519
```

После этого SSH-клиент может использовать ключ через agent.

---

# 13. `known_hosts`

При первом подключении к серверу SSH может показать fingerprint сервера и спросить:

```text
Are you sure you want to continue connecting?
```

После подтверждения информация сохраняется в:

```text
~/.ssh/known_hosts
```

Упрощённо:

```text
Server
  ↓
Host Key / Fingerprint
  ↓
known_hosts
```

При следующих подключениях SSH может проверить, соответствует ли ключ сервера ранее известному.

---

# 14. Зачем нужен `known_hosts`

Это помогает обнаруживать ситуацию, когда сервер по тому же адресу неожиданно предъявляет другой host key.

Например:

```text
Раньше:
server → fingerprint A

Сейчас:
server → fingerprint B
```

SSH может предупредить о возможной проблеме.

Это связано, в частности, с защитой от **Man-in-the-Middle (MITM)** атак.

При легитимной переустановке сервера host key тоже может измениться, поэтому такое предупреждение не всегда означает атаку — его нужно проверять по контексту.

---

# 15. SSH Config

Чтобы не писать длинную команду:

```bash
ssh -p 2222 ilya@192.168.1.100
```

можно использовать:

```text
~/.ssh/config
```

Например:

```text
Host myserver
    HostName 192.168.1.100
    User ilya
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
```

После этого:

```bash
ssh myserver
```

SSH возьмёт параметры из конфигурации.

# 16. Передача файлов через SCP

SSH используется не только для shell.

Например:

```bash
scp app.py user@server:/home/user/
```

Скопировать файл с сервера:

```bash
scp user@server:/home/user/app.py .
```

Упрощённо:

```text
Local
  │
  │ SCP over SSH
  ▼
Server
```

# 17. SFTP

**SFTP — SSH File Transfer Protocol.**

Он предназначен для работы с файлами через SSH-соединение.

Например:

```bash
sftp user@server
```

После подключения можно выполнять операции вроде:

```text
ls
cd
get
put
```

Важно:

> SFTP — отдельный протокол передачи файлов поверх SSH, а не просто «scp в другом синтаксисе».

---

# 18. SSH Tunneling

SSH может создавать защищённые туннели.

Например:

```text
Local machine
      │
      │ SSH tunnel
      ▼
SSH Server
      │
      ▼
Internal Service
```

Это позволяет получить доступ к сервису через SSH-соединение.

---

# 19. Local Port Forwarding

Например, PostgreSQL доступен только на сервере:

```text
Server
└── PostgreSQL :5432
```

Можно создать локальный туннель:

```bash
ssh -L 5432:localhost:5432 user@server
```

Теперь:

```text
Local :5432
    │
    │ SSH tunnel
    ▼
Server localhost:5432
    │
    ▼
PostgreSQL
```

Приложение локально подключается к:

```text
localhost:5432
```

а трафик проходит через SSH на сервер.

---

# 20. Remote Port Forwarding

Есть и обратный сценарий:

```bash
ssh -R 8080:localhost:8000 user@server
```

Упрощённо:

```text
Server :8080
     │
     │ SSH tunnel
     ▼
Client :8000
```

Это называется **remote port forwarding**.

MacBook
   │

   │
   ├── Docker

# 22. SSH и Git

SSH используется и для работы с Git-репозиториями.

Например:

```text
git@github.com:user/project.git
```

или:

```text
git@gitlab.com:user/project.git
```

Тогда:

```bash
git clone git@gitlab.com:user/project.git
```

использует SSH-аутентификацию.

Схема:

```text
Git
 ↓
SSH
 ↓
GitLab / GitHub
```

Поэтому SSH важен одновременно для:

* администрирования серверов;
* Git;
* CI/CD;
* автоматизации.

# 23. SSH Agent Forwarding

В некоторых сценариях используется **agent forwarding**:

```bash
ssh -A user@server
```

Это позволяет удалённому серверу использовать ключи, доступные через локальный `ssh-agent`, для последующего SSH-доступа.

Например:

```text
Laptop
  │
  │ SSH
  ▼
Server A
  │
  │ SSH using forwarded agent
  ▼
Server B
```

Это мощная возможность, но её нужно применять осторожно: компрометация промежуточного сервера может создать дополнительные риски.

# 24. SSH и безопасность

Для production-сервера важно:

### Private key

Не передавать:

```text
id_ed25519
```

и не хранить его в Git.

### Public key

Можно размещать на сервере:

```text
id_ed25519.pub
```

### Passphrase

Private key желательно защищать passphrase.

### Root login

В production часто ограничивают прямой SSH-вход под `root` и используют обычного пользователя с `sudo`, в зависимости от политики инфраструктуры.

### Password authentication

Можно отключить парольную аутентификацию после настройки ключей, если это соответствует требованиям инфраструктуры.

### Ограничение доступа

SSH-порт и доступ к нему обычно ограничивают firewall/VPN/security groups.

# 25. SSH и порт

Стандартный порт:

```text
TCP 22
```

Но SSH-сервер можно настроить на другой порт.

Например:

```text
TCP 2222
```

Подключение:

```bash
ssh -p 2222 user@server
```

Изменение порта само по себе не является полноценной защитой — это лишь изменение точки подключения.

---

# 26. SSH connection vs SSH key

Это разные понятия.

### SSH connection

Сетевое соединение между клиентом и сервером.

```text
Client ←── TCP/SSH ──→ Server
```

### SSH key

Механизм криптографической аутентификации пользователя.

```text
Private Key + Public Key
```

Ключи используются **в рамках SSH-протокола**, но сам SSH не сводится только к ключам.

# 29. Что важно различать

### SSH vs SSH key

```text
SSH      → протокол
SSH key  → механизм аутентификации
```

### Private vs Public key

```text
Private key → хранится у владельца и не передаётся
Public key  → устанавливается на сервер
```

### `known_hosts` vs `authorized_keys`

```text
known_hosts
→ известные host keys серверов на клиенте

authorized_keys
→ разрешённые public keys пользователей на сервере
```

### SCP vs SFTP

```text
SCP  → копирование файлов
SFTP → интерактивный протокол работы с файлами
```

### SSH vs VPN

SSH обычно предоставляет доступ к конкретному серверу/туннелю.

VPN создаёт более широкий сетевой канал между хостами или сетями.

## 🎤 Вопросы на собеседовании

### Что такое SSH?

SSH — протокол безопасного удалённого доступа, обеспечивающий защищённое соединение, аутентификацию и передачу данных между клиентом и сервером.

### На каком порту работает SSH?

По умолчанию:

```text
TCP 22
```

Но сервер может быть настроен на другой порт.

### Что такое `sshd`?

SSH daemon — серверная часть SSH, которая принимает входящие SSH-подключения.

### Как подключиться к серверу?

```bash
ssh user@server
```

### Чем public key отличается от private key?

Private key является секретным и хранится у владельца. Public key размещается на сервере и используется для проверки криптографического доказательства владения соответствующим private key.

### Где на сервере обычно находится public key пользователя?

В:

```text
~/.ssh/authorized_keys
```

### Что такое `known_hosts`?

Файл на SSH-клиенте, содержащий известные host keys серверов, с которыми клиент уже взаимодействовал.

### Зачем нужен `ssh-agent`?

Для безопасного использования загруженных private keys без необходимости вводить их passphrase при каждом подключении.

### Что делает `ssh-keygen`?

Создаёт пару SSH-ключей.

Например:

```bash
ssh-keygen -t ed25519
```

### Что такое SSH tunneling?

Использование SSH-соединения для безопасной передачи трафика между локальными и удалёнными портами.

### Что делает `ssh -L`?

Создаёт local port forwarding:

```text
Local port → SSH → Remote service
```

### Что делает `ssh -R`?

Создаёт remote port forwarding:

```text
Remote port → SSH → Local service
```

### Используется ли SSH с Git?

Да. Например:

```bash
git clone git@gitlab.com:user/project.git
```

Git использует SSH как транспорт и механизм аутентификации.

### Почему SSH важен Backend-разработчику?

Потому что через SSH разработчик подключается к Linux-серверам, проверяет процессы и логи, управляет Docker и сервисами, диагностирует production и работает с удалёнными Git-репозиториями.
