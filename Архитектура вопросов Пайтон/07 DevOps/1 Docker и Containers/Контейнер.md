# 📦 Контейнер

## 🎤 Короткий ответ

**Контейнер** — это изолированное окружение для запуска приложения и его зависимостей. Контейнер использует **ядро операционной системы хоста**, но изолирует процессы, файловую систему, сеть и ресурсы от других контейнеров.

Контейнер обычно создаётся из **Docker Image** и является его запущенным экземпляром.

## 🎯 Формула для собеседования

> **Image → Container → процесс приложения.**

И главное отличие:

> **VM виртуализирует целую машину с Guest OS, а контейнер изолирует процессы и использует Kernel Host OS.**

---

# 🔹 Что такое контейнер

Представим обычный сервер:

```text id="r7m2kx"
Physical Server
      ↓
Host OS
      ↓
Docker Engine
      ↓
┌────────────┬────────────┬────────────┐
│ Container  │ Container  │ Container  │
│ FastAPI    │ PostgreSQL │ Redis      │
└────────────┴────────────┴────────────┘
```

Каждый контейнер имеет изолированное окружение, но все контейнеры используют **одно ядро Host OS**.

---

# 🔹 Container vs Image

Это один из самых важных моментов.

### Image

**Image** — неизменяемый шаблон.

```text id="v2m7qc"
Python Image
     ↓
   шаблон
```

### Container

**Container** — экземпляр Image, который запущен как процесс.

```text id="x9k4wp"
Python Image
     ↓
docker run
     ↓
Container
     ↓
Python application
```

Один Image может использоваться для создания нескольких контейнеров:

```text id="f5n8sr"
           Image
             │
      ┌──────┼──────┐
      ↓      ↓      ↓
     C1     C2     C3
```

---

# 🔹 Контейнер — не виртуальная машина

В VM:

```text id="a7q3mx"
Physical Server
      ↓
Hypervisor
      ↓
VM
      ↓
Guest OS
      ↓
Application
```

В контейнере:

```text id="k8r5vn"
Physical Server
      ↓
Host OS
      ↓
Container Runtime
      ↓
Container
      ↓
Application
```

Главное:

> В контейнере **нет отдельного полноценного Guest Kernel**.

Контейнер использует kernel Host OS.

---

# 🔹 Почему контейнер лёгкий

Контейнеру не нужно запускать отдельную операционную систему.

В VM:

```text id="u4q7xc"
VM
├── Guest Kernel
├── System services
├── Libraries
└── Application
```

В контейнере:

```text id="m8p3ky"
Container
├── Application
├── Dependencies
└── Filesystem
       ↓
  Host Kernel
```

Поэтому контейнеры обычно:

* быстрее запускаются;
* потребляют меньше ресурсов;
* занимают меньше места;
* позволяют запускать больше экземпляров на одном сервере.

---

# 🔹 Изоляция контейнера

Docker использует возможности Linux kernel для изоляции процессов.

Основные механизмы:

### Namespaces

Изолируют окружение процессов.

Например:

* PID;
* Network;
* Mount;
* User;
* IPC;
* UTS.

Условно:

```text id="n5c8rx"
Container A
   ↓
свои процессы
своя сеть
своя файловая система

Container B
   ↓
свои процессы
своя сеть
своя файловая система
```

---

### cgroups

**Control Groups** используются для ограничения и учёта ресурсов.

Например:

```text id="w6q2mp"
Container
   │
   ├── CPU: 2 cores
   ├── RAM: 512 MB
   └── PIDs: ограничение
```

То есть можно ограничить, сколько ресурсов контейнер способен потреблять.

---

# 🔹 Filesystem контейнера

Контейнер получает собственную файловую систему поверх Image.

Упрощённо:

```text id="e8r4vz"
Image
  ↓
Container writable layer
  ↓
Application changes
```

Изменения внутри контейнера обычно относятся к его writable layer.

Если удалить контейнер:

```text id="j5m9qx"
Container
   ↓
❌ удалён
```

изменения в его writable layer тоже исчезнут.

Поэтому для важных данных используют **Volume** или bind mount.

---

# 🔹 Volume

Например, PostgreSQL:

```text id="q2v7mc"
PostgreSQL Container
       │
       ↓
Postgres Volume
       │
       ↓
Persistent Data
```

Compose:

```python id="d8m4ks"
services:
  db:
    image: postgres:15
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Теперь данные находятся отдельно от жизненного цикла контейнера.

---

# 🔹 Контейнер должен быть относительно эфемерным

Хорошая практика:

> **Не хранить критические данные внутри writable layer контейнера.**

Вместо этого:

```text id="c7n3wp"
Container
   │
   ├── Application
   └── Temporary files

Volume
   │
   └── Persistent data
```

Контейнер можно удалить и создать заново:

```text id="z4m8qx"
Container
   ↓
DELETE
   ↓
NEW Container
   ↓
тот же Volume
```

---

# 🔹 Сеть контейнера

Контейнер получает виртуальный сетевой интерфейс.

```text id="p6x9rw"
Container
    ↓
Virtual Network Interface
    ↓
Docker Network
    ↓
Host Network
```

В Docker Compose контейнеры обычно могут обращаться друг к другу по имени сервиса:

```text id="m3q7vk"
app → db:5432
app → redis:6379
```

Например:

```python id="n9k2xs"
DATABASE_HOST=db
```

А не:

```python id="u4c8qp"
DATABASE_HOST=localhost
```

Потому что `localhost` внутри контейнера указывает на **сам контейнер**.

---

# 🔹 Один процесс — один основной контейнерный процесс

Типичная модель:

```text id="f7m3qa"
Container
   ↓
PID 1
   ↓
Application
```

Например:

```text id="p8x4nz"
Container
   ↓
uvicorn
   ↓
FastAPI
```

Docker управляет жизненным циклом основного процесса контейнера.

Если основной процесс завершился, контейнер обычно переходит в состояние `Exited`.

---

# 🔹 Запуск контейнера

Например:

```python id="q5m8vx"
docker run -d -p 8000:8000 myapp:1.0
```

Происходит:

```text id="t7n3kc"
Image
  ↓
Container created
  ↓
Container started
  ↓
Application running
```

---

# 🔹 Остановка и удаление

Остановить:

```python id="k3r9wp"
docker stop myapp
```

Запустить снова:

```python id="x8m4qc"
docker start myapp
```

Удалить:

```python id="v6p2nz"
docker rm myapp
```

Удаление контейнера не означает автоматическое удаление Image.

```text id="r2k7mx"
Image
  │
  ├── Container 1
  ├── Container 2
  └── Container 3
```

Можно удалить контейнер, но Image останется.

---

# 🔹 Container Runtime

Docker использует container runtime для запуска контейнеров.

Упрощённо:

```text id="m5q8vz"
Docker CLI
    ↓
Docker Engine
    ↓
Container Runtime
    ↓
Container
```

В Linux современный Docker использует **containerd**, а низкоуровневый запуск контейнерных процессов обычно выполняется через **runc**.

---

# 🔹 Контейнер и Docker Compose

Compose позволяет управлять несколькими контейнерами:

```text id="x3n7kc"
Docker Compose
      │
      ├── app
      ├── db
      ├── redis
      └── worker
```

Например:

```python id="w8m2qx"
services:
  app:
    build: .
    ports:
      - "8000:8000"

  db:
    image: postgres:15

  redis:
    image: redis:7
```

Запуск:

```python id="a4k9vr"
docker compose up -d
```

# 🔹 Healthcheck

Контейнер может быть:

```text id="q7m3xp"
running
```

но приложение внутри может не работать нормально.

Healthcheck позволяет Docker проверять состояние приложения:

```python id="c8n5mz"
healthcheck:
  test: ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"]
  interval: 10s
  timeout: 5s
  retries: 3
```

Состояния:

```text id="v4q8kc"
starting
   ↓
healthy
```

или:

```text id="p3m7xn"
starting
   ↓
unhealthy
```

Важно:

> **`unhealthy` не означает автоматически, что контейнер будет перезапущен.**

Healthcheck и restart policy — разные механизмы.

# 🔹 Контейнеры и масштабирование

Можно запустить несколько экземпляров одного Image:

```text id="s6k2wp"
              Image
                ↓
       ┌────────┼────────┐
       ↓        ↓        ↓
     app-1    app-2    app-3
```

Например, несколько экземпляров FastAPI могут обслуживать запросы через Load Balancer или reverse proxy.

```text id="q9m4vx"
              Nginx
             /  |  \
            ↓   ↓   ↓
         app-1 app-2 app-3
```

# 🔹 Контейнеры и микросервисы

Контейнеры часто используют для изоляции сервисов:

```text id="m7x3qk"
        Application
             │
   ┌─────────┼─────────┐
   ↓         ↓         ↓
 FastAPI  PostgreSQL  Redis
   │
 Celery
```

Но:

> **Контейнер ≠ микросервис.**

Контейнер — способ упаковки и запуска приложения.

Микросервис — архитектурный подход.

Можно иметь монолит в одном контейнере.

Контейнеры и виртуальные машины могут использоваться одновременно:

```text id="c9v5mx"
Physical Server

       ↓
    Linux VM
       ↓
     Docker
       ↓

```

Это очень распространённая архитектура.

# 🔹 Частые вопросы на собеседовании

### Что такое контейнер?

> Изолированное окружение для запуска приложения и его зависимостей, использующее ядро Host OS.

### Чем контейнер отличается от Image?

> Image — шаблон, Container — созданный из Image экземпляр, который запускает процессы.

### Контейнер — это VM?

> Нет. Контейнер не запускает отдельную полноценную ОС и использует kernel хоста.

### Почему контейнеры легче VM?

> Потому что не требуют отдельной Guest OS и её ядра.

### Что такое namespaces?

> Механизм Linux kernel для изоляции процессов, сети, файловой системы и других ресурсов.

### Что такое cgroups?

> Механизм Linux для ограничения и учёта потребления ресурсов процессами/контейнерами.

### Что происходит с данными после удаления контейнера?

> Данные writable layer контейнера удаляются вместе с контейнером. Для сохранения данных используют Volume или bind mount.

### Что такое Volume?

> Механизм хранения данных отдельно от жизненного цикла контейнера.

### Может ли несколько контейнеров использовать один Image?

> Да. Один Image может быть основой для множества контейнеров.

### Может ли один контейнер содержать несколько процессов?

> Да, технически может. Но обычно контейнер проектируют вокруг одного основного сервиса/процесса, чтобы проще управлять его жизненным циклом.

---

## 🔑 Главное

```text id="h8m4qz"
                 Docker Image
                      │
                 docker run
                      ↓
                  Container
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Process      Network    Filesystem
          │
          ↓
      Application

Container
    │
    ├── изоляция → namespaces
    ├── ресурсы  → cgroups
    ├── данные   → volumes
    └── сеть     → Docker Network
```

### 🎤 Финальная формула

> **Контейнер — это изолированный процесс с собственным окружением, файловой системой и сетевым пространством, который использует ядро Host OS. Обычно контейнер создаётся из Docker Image. В отличие от VM, ему не нужна отдельная Guest OS, поэтому контейнеры легче и быстрее запускаются.**
