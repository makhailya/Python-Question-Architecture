# Black 🖤

## 🎤 Короткий ответ

**Black** — это автоматический форматтер Python-кода, который приводит код к единому стилю по своим правилам.

Он **не проверяет бизнес-логику и не является линтером**: его основная задача — автоматически отформатировать код.

> **Black = Python-код → автоматическое форматирование → единый стиль.**

---

## 🎯 Формула для собеседования

**Код → Black → форматирование → единый стиль → меньше споров в Code Review**

```text id="b001"
Python-код
    ↓
   Black
    ↓
Отформатированный код
    ↓
Code Review / CI
```

---

# 1. Что такое Black

**Black** — opinionated code formatter для Python.

`Opinionated` означает, что Black сознательно предлагает достаточно жёсткий и единообразный стиль форматирования вместо большого количества настроек.

Главная идея:

> Разработчики не должны тратить время на споры о пробелах, переносах и оформлении кода.

---

# 2. Что делает Black

Black автоматически форматирует:

* пробелы;
* отступы;
* переносы строк;
* скобки;
* расположение элементов конструкций;
* длинные выражения;
* оформление коллекций;
* кавычки в соответствии с правилами Black;
* некоторые другие элементы синтаксического оформления.

Например:

```python id="b002"
def hello(name):
    print(f"Hello, {name}")
```

Если код написан не в стиле Black:

```python id="b003"
def hello( name ):
 print( f"Hello, {name}" )
```

Black приведёт его к единому формату.

# 3. Установка

Через `pip`:

```python id="b004"
pip install black
```

Если используется Poetry:

```python id="b005"
poetry add --group dev black
```

---

# 4. Запуск Black

Отформатировать текущий проект:

```python id="b006"
black .
```

Конкретный файл:

```python id="b007"
black app/main.py
```

Конкретную директорию:

```python id="b008"
black app/
```

Black изменяет файлы непосредственно.

---

# 5. Проверка без изменения файлов

В CI обычно используют:

```python id="b009"
black --check .
```

Black проверяет, соответствует ли код его правилам, но **не изменяет файлы**.

Если всё хорошо:

```text id="b010"
All done! ✨
```

Если форматирование отличается:

```text id="b011"
would reformat app/main.py
```

CI может завершить pipeline с ошибкой.

---

# 6. `black .` vs `black --check .`

| Команда           | Результат                           |
| ----------------- | ----------------------------------- |
| `black .`         | форматирует файлы                   |
| `black --check .` | только проверяет                    |
| `black --diff .`  | показывает предполагаемые изменения |

Например:

```python id="b012"
black --diff .
```

удобно использовать, чтобы увидеть, что Black собирается изменить.

---

# 7. Line Length

Одно из важных правил Black — ограничение длины строки.

По умолчанию:

```text id="b013"
88 символов
```

Например, длинное выражение Black может перенести:

```python id="b014"
result = some_function(
    first_argument,
    second_argument,
    third_argument,
)
```

При необходимости длину можно изменить:

```python id="b015"
black --line-length 100 .
```

Но обычно в проекте фиксируют одно значение для всей команды.

# 8. Конфигурация Black

Настройки проекта обычно можно хранить в:


Например:


# 9. Black и `pyproject.toml`

Для Python-проекта удобно хранить конфигурацию инструментов в одном месте:


Это делает настройки проекта воспроизводимыми для всей команды и CI.

---

# 10. Black не является линтером

Это принципиально.

### Black

```text id="b019"
Форматирует код
```

### Ruff

```text id="b020"
Анализирует код
```

Например:

```python id="b021"
import os

x = 10
```

Black может оставить:

```python id="b022"
import os

x = 10
```

Потому что форматирование корректное.

А линтер может сообщить:

```text id="b023"
F401 'os' imported but unused
```

То есть:

> **Black отвечает за внешний формат кода, а Ruff — за статические проверки.**

---

# 11. Black и Ruff

Сегодня возможны два распространённых подхода.

### Вариант 1 — Black + Ruff

```text id="b024"
Black
  ↓
formatting

Ruff
  ↓
linting
```

### Вариант 2 — только Ruff

```text id="b025"
Ruff
 ├── linting
 └── formatting
```

Во втором случае отдельный Black может быть не нужен.

Выбор зависит от проекта и его стандартов.

---

# 12. Black и PEP 8

**PEP 8** — руководство по стилю Python.

Black реализует определённый набор соглашений, близких к идеям PEP 8, но:

> **Black ≠ PEP 8.**

Правильнее:

```text id="b026"
PEP 8
 ↓
рекомендации по стилю

Black
 ↓
автоматическое форматирование
```

---

# 13. Black не исправляет ошибки программы

Например:

```python id="b027"
def calculate_price(price):
    return price * 0
```

С точки зрения синтаксического форматирования всё нормально.

Black не знает, что бизнес-логика может быть неправильной.

Для этого нужны:

* pytest;
* Code Review;
* линтеры;
* MyPy;
* другие анализаторы.

# 14. Black и Git

```text id="b028"

    ↓
```

Таким образом, в репозиторий попадает уже отформатированный код.

Это позволяет автоматически поддерживать единый стиль.

# 16. Black в CI/CD

В CI обычно не форматируют код автоматически, а **проверяют**:

```python id="b030"
black --check .
```

Например:

```text id="b031"
Git Push
    ↓
CI
    ↓
black --check .
    ↓
ruff check .
    ↓
mypy .
    ↓
pytest
    ↓
Build
```

Если Black обнаружит неотформатированные файлы:

```text id="b032"
CI → FAILED
```

---

# 17. Почему Black полезен в Code Review

Без форматтера reviewer может тратить время на замечания:

```text
«Здесь пробел»
«Здесь лучше перенести строку»
«Здесь неправильный отступ»
```

Black автоматизирует эти вопросы:

```text id="b033"
Developer
    ↓
Black
    ↓
единый формат
    ↓
Code Review
```

Reviewer может сосредоточиться на:

* архитектуре;
* бизнес-логике;
* безопасности;
* производительности;
* тестах.

---

# 18. Black и импорт

Black **не является специализированным инструментом сортировки импортов**.

Для этого традиционно используют, например:

```text id="b034"
isort
```

или соответствующую функциональность Ruff.

Поэтому типичная старая связка:

```text id="b035"
Black + isort + flake8
```

Современный вариант может быть:

```text id="b036"
Ruff
 ├── lint
 ├── import sorting
 └── format
```

---

# 19. Black и типизация

Black не проверяет типы:

```python id="b037"
def get_user(user_id: int) -> str:
    return user_id
```

Форматирование может быть полностью корректным.

А MyPy обнаружит несовместимость:

```text id="b038"
Incompatible return value type
```

Поэтому инструменты выполняют разные задачи:

```text id="b039"
Black → форматирование
Ruff  → linting
MyPy  → типы
pytest → поведение
```

# 21. Почему Black называют opinionated

Black специально не предоставляет бесконечное количество вариантов форматирования.

Например, команда не должна постоянно решать:

```text id="b042"
Как ставить пробел?
Как переносить строку?
Какие скобки использовать?
```

Вместо этого:

```text id="b043"
Black
 ↓
один стандарт
 ↓
вся команда
```

Это уменьшает количество субъективных решений.

# 🎤 Вопросы на собеседовании

### Что такое Black?

> Black — автоматический форматтер Python-кода, который приводит код к единому стилю по заданным правилам.

### Black — это линтер?

> Нет. Основная задача Black — форматирование. Линтер, например Ruff, анализирует код и ищет потенциальные ошибки и нарушения правил.

### Как запустить Black?

```python id="b044"
black .
```

### Как проверить форматирование без изменения файлов?

```python id="b045"
black --check .
```

### Где обычно конфигурируют Black?

> В `pyproject.toml`.

### Какой `line-length` используется по умолчанию?

> 88 символов.

### Может ли Black найти ошибку в бизнес-логике?

> Нет. Black занимается форматированием и не заменяет тесты, линтеры или Code Review.

### Зачем Black в CI?

> Чтобы автоматически проверять, соответствует ли код стандарту форматирования проекта.

### Зачем нужен Black, если есть Ruff?

> Ruff тоже умеет форматировать Python-код. Поэтому проект может использовать либо Black + Ruff, либо Ruff для обеих задач.
