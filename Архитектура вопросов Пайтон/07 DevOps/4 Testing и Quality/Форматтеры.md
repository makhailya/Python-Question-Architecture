# Форматтеры 🎨

## 🎤 Короткий ответ

**Форматтер** — это инструмент, который автоматически приводит исходный код к единому стилю форматирования по заданным правилам.

Например, **Black** или **Ruff Formatter** автоматически исправляют отступы, пробелы, переносы строк и другие элементы оформления.

> **Форматтер = код → автоматическое форматирование → единый стиль.**

---

## 🎯 Формула для собеседования

**Исходный код → Formatter → отформатированный код**

```text id="fmt001"
Python-код
    ↓
  Black / Ruff
    ↓
Единый стиль
    ↓
Code Review / CI
```

---

# 1. Зачем нужен форматтер

Без форматтера разработчики могут оформлять одинаковый код по-разному:

```python id="fmt002"
def hello(name): print(f"Hello, {name}")
```

или:

```python id="fmt003"
def hello(name):
    print(f"Hello, {name}")
```

Форматтер автоматически приводит код к принятому в проекте виду.

Главная цель:

* единый стиль;
* меньше ручной работы;
* меньше споров о форматировании;
* проще Code Review;
* одинаковый код у всей команды.

---

# 2. Что делает форматтер

Форматтер может автоматически изменять:

* пробелы;
* отступы;
* переносы строк;
* расположение скобок;
* длину строк;
* оформление коллекций;
* расположение некоторых конструкций;
* форматирование импортов — если это поддерживается отдельным инструментом/режимом.

Например:

```python id="fmt004"
numbers=[1,2,3,4,5]
```

может быть приведено к:

```python id="fmt005"
numbers = [1, 2, 3, 4, 5]
```

---

# 3. Black

**Black** — популярный opinionated formatter для Python.

Его идея:

> разработчики меньше обсуждают форматирование и больше занимаются кодом.

Форматирование:

```python id="fmt006"
black .
```

Black автоматически изменяет файлы.

Проверка без изменения файлов:

```python id="fmt007"
black --check .
```

---

# 4. Ruff Formatter

**Ruff** помимо linting умеет форматировать Python-код.

Форматирование:

```python id="fmt008"
ruff format .
```

Проверка:

```python id="fmt009"
ruff format --check .
```

Поэтому современный проект может использовать:

```text id="fmt010"
Ruff
 ├── linting
 └── formatting
```

и не использовать Black.

---

# 5. Black vs Ruff Formatter

|                                   | Black     | Ruff Formatter |
| --------------------------------- | --------- | -------------- |
| Форматирование Python             | ✅         | ✅              |
| Автоматическое исправление        | ✅         | ✅              |
| Проверка формата                  | `--check` | `--check`      |
| Скорость                          | высокая   | очень высокая  |
| Linting                           | ❌         | ✅              |
| Один инструмент для lint + format | ❌         | ✅              |

Оба решают задачу форматирования. Конкретный выбор зависит от проекта.

# 6. Formatter vs Linter

Это **главный вопрос на собеседовании**.

### Formatter

Отвечает:

> **«Как должен выглядеть код?»**

Он автоматически изменяет форматирование.

### Linter

Отвечает:

> **«Есть ли в коде проблемы или нарушения правил?»**

Например:

```text id="fmt011"
Formatter
    ↓
исправляет форматирование

Linter
    ↓
находит проблемы
```

---

## Пример

Исходный код:

```python id="fmt012"
import os

x=10
```

Formatter может сделать:

```python id="fmt013"
import os

x = 10
```

А линтер дополнительно скажет:

```text id="fmt014"
F401 'os' imported but unused
```

То есть:

```text id="fmt015"
Formatter → исправил внешний вид
Linter    → обнаружил неиспользуемый import
```

---

# 7. Formatter vs MyPy

**MyPy** занимается типами, а не форматированием.

Например:

```python id="fmt016"
def add(a: int, b: int) -> int:
    return a + b
```

Если написать:

```python id="fmt017"
result: int = "hello"
```

MyPy может обнаружить проблему типов.

Formatter на это не ориентирован.

```text id="fmt018"
Black / Ruff
    ↓
форматирование

MyPy
    ↓
типизация
```

---

# 8. Formatter vs pytest

`pytest` проверяет **поведение программы**.

Formatter не запускает тесты и не проверяет бизнес-логику.

```text id="fmt019"
Formatter
    ↓
«Код красиво и единообразно оформлен?»

pytest
    ↓
«Код работает правильно?»
```

---

# 9. PEP 8 и форматтер

**PEP 8** — руководство по стилю Python.

Форматтеры реализуют определённый набор правил форматирования.

Важно различать:

```text id="fmt020"
PEP 8
 ↓
рекомендации по стилю

Formatter
 ↓
автоматически форматирует код
```

То есть **PEP 8 ≠ форматтер**.

---

# 10. Форматтер не исправляет логику

Например:

```python id="fmt021"
def calculate_price(price):
    return price * 0
```

Форматтер не скажет:

> «Ты случайно умножаешь цену на ноль».

С точки зрения форматирования код может быть полностью корректным.

Для обнаружения логических ошибок нужны:

* тесты;
* Code Review;
* статический анализ;
* type checking;
* специализированные анализаторы.

---

# 11. Форматирование в CI

Форматтер часто запускают в CI.

Например:

```text id="fmt022"
Git Push
    ↓
CI
    ↓
ruff format --check .
    ↓
pytest
    ↓
mypy
    ↓
Build
```

Если код не соответствует формату:

```text id="fmt023"
ruff format --check .
        ↓
      FAILED
```

Pipeline может завершиться ошибкой.

---

# 12. Почему используют `--check`

В CI обычно не хотят, чтобы pipeline молча изменял код.

Поэтому:

```python id="fmt024"
ruff format --check .
```

означает:

> **«Проверь форматирование, но ничего не изменяй».**

Локально разработчик может выполнить:

```python id="fmt025"
ruff format .
```

и получить исправленный код.

То же самое с Black:

```python id="fmt026"
black .
```

и:

```python id="fmt027"
black --check .
```

# 14. Pre-commit + Formatter

Можно запускать форматтер перед commit:

```text id="fmt029"
git commit
    ↓
pre-commit
    ↓
Ruff Formatter
    ↓
если формат OK
    ↓
commit
```

Если форматирование не соответствует правилам, commit может быть остановлен.

# 16. Почему форматтер полезен для Code Review

Представь, что Pull Request содержит:

```text id="fmt032"
500 строк изменений
```

И половина diff состоит из:

```text
пробелы
отступы
переносы строк
кавычки
```

Это мешает reviewer'у увидеть реальные изменения.

Если форматирование автоматизировано:

```text id="fmt033"
Formatter
    ↓
единый стиль
    ↓
меньше шумных изменений
    ↓
Code Review проще
```

# 17. Opinionated Formatter

Black называют **opinionated formatter**.

Это означает, что он намеренно имеет достаточно жёсткие правила и предоставляет разработчику меньше решений:

> «Вот стандартный способ форматирования — используем его».

Преимущество:

```text id="fmt034"
меньше настроек
      ↓
меньше споров
      ↓
одинаковый код
```

# 🎤 Вопросы на собеседовании

### Что такое форматтер?

> Форматтер — инструмент, который автоматически приводит исходный код к единому стилю форматирования по заданным правилам.

### Какие форматтеры есть в Python?

> Один из наиболее известных — Black. Также Ruff имеет собственный formatter.

### Чем форматтер отличается от линтера?

> Форматтер автоматически изменяет код, чтобы привести его к единому стилю. Линтер анализирует код и сообщает о потенциальных ошибках и нарушениях правил.

### Может ли форматтер найти логическую ошибку?

> Нет. Его задача — форматирование, а не проверка бизнес-логики.

### Чем форматтер отличается от MyPy?

> Formatter занимается внешним оформлением кода, а MyPy выполняет статическую проверку типов.

### Зачем нужен `--check`?

> Он позволяет проверить, соответствует ли код правилам форматирования, не изменяя файлы. Это удобно для CI.

### Зачем форматтер в CI?

> Чтобы автоматически проверять единообразие кода и не пропускать неотформатированные изменения в основную ветку.
