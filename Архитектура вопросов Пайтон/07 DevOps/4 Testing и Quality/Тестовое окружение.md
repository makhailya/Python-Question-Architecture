# 🧪 Тестовое окружение

## 🎤 Короткий ответ

**Тестовое окружение (Test Environment)** — это отдельная среда, в которой приложение и его изменения **проверяются с помощью автоматических и ручных тестов** до передачи в production.

Оно должно быть максимально предсказуемым и по возможности близким к production, но использовать **тестовые данные и отдельные ресурсы**.

```text
Dev
 ↓
Test Environment
 ↓
Staging
 ↓
Production
```

## 🎯 Формула для собеседования

> **Test Environment = приложение + тестовые зависимости + тестовая конфигурация + тестовые данные → проверка качества изменений.**

---

# 🔹 Зачем нужно тестовое окружение

Разработчик может проверить код локально:

```text
Developer
   ↓
Local Dev
   ↓
pytest
```

Но локальное окружение не всегда отражает реальные условия.

Поэтому создают отдельную среду:

```text
Git
 ↓
CI
 ↓
Test Environment
 ↓
Tests
 ↓
Result
```

В ней можно проверить:

* API;
* базу данных;
* Redis;
* очереди;
* интеграции;
* взаимодействие нескольких сервисов;
* миграции;
* конфигурацию;
* автоматические тесты.

---

# 🔹 Из чего состоит

Для Python Backend:

```text
Test Environment
│
├── Application
├── Python
├── Dependencies
├── PostgreSQL
├── Redis
├── Message Broker
├── Test Configuration
├── Test Data
└── Test Runner
```

Например:

```text
FastAPI
   ↓
PostgreSQL Test
   ↓
Redis Test
   ↓
pytest
```

---

# 🔹 Test Environment vs Dev Environment

|                      | Dev                  | Test                      |
| -------------------- | -------------------- | ------------------------- |
| Основная цель        | Разработка           | Проверка                  |
| Кто использует       | Разработчики         | CI / QA / разработчики    |
| Данные               | Dev-данные           | Тестовые                  |
| Изменения            | Постоянные           | Контролируемые            |
| Debug                | Часто включён        | Обычно ограничен          |
| Автоматические тесты | Запускаются          | Основная задача           |
| Стабильность         | Может часто меняться | Должна быть предсказуемой |

Главная разница:

> **Dev предназначен для создания кода, Test — для проверки кода.**

---

# 🔹 Test Environment vs Staging

Эти понятия иногда используются по-разному в разных командах, поэтому важно смотреть на конкретный workflow.

Упрощённо:

```text
Dev
 ↓
Test
 ↓
Staging
 ↓
Production
```

### Test

Основная задача:

> Проверить функциональность и корректность изменений.

Например:

```text
pytest
integration tests
API tests
```

### Staging

Основная задача:

> Проверить приложение в окружении, максимально приближенном к production.

Например:

```text
Production-like infrastructure
        ↓
Final verification
        ↓
Production
```

В некоторых командах отдельного Test Environment может не быть, и тесты выполняются непосредственно в CI или staging.

---

# 🔹 Test Database

Тестовое окружение не должно использовать production database.

Например:

```text
Dev
 ↓
dev_db

Test
 ↓
test_db

Staging
 ↓
staging_db

Production
 ↓
production_db
```

Это защищает реальные данные от случайного изменения тестами.

---

# 🔹 Test Data

В тестовой БД используются специальные данные.

Например:

```text
User:
id = 1
email = test@example.com

Order:
id = 100
status = pending
```

Данные могут:

* создаваться перед тестом;
* очищаться после теста;
* загружаться fixtures;
* генерироваться фабриками.

---

# 🔹 Isolation

Тесты желательно изолировать друг от друга.

Плохо:

```text
Test A
 ↓
создал User #1
 ↓
Test B
 ↓
ожидает User #1
```

Теперь Test B зависит от Test A.

Лучше:

```text
Test A → собственные данные
Test B → собственные данные
Test C → собственные данные
```

Это делает тесты независимыми и воспроизводимыми.

---

# 🔹 Виды тестов

В тестовом окружении могут запускаться разные уровни тестирования.

```text
Unit Tests
    ↓
Integration Tests
    ↓
API / Functional Tests
    ↓
End-to-End Tests
```

---

# 🔹 Unit Test

Проверяет отдельную небольшую часть программы.

Например:

```python id="a8m3qx"
def test_calculate_total():
    assert calculate_total([10, 20]) == 30
```

Обычно unit-тесты:

* быстрые;
* изолированные;
* не требуют настоящей БД.

---

# 🔹 Integration Test

Проверяет взаимодействие компонентов.

Например:

```text
FastAPI
   ↓
PostgreSQL
```

Тест проверяет, что API действительно может:

```text
создать пользователя
       ↓
записать его в PostgreSQL
       ↓
получить пользователя
```

---

# 🔹 End-to-End Test

Проверяет полный пользовательский сценарий.

Например:

```text
POST /login
      ↓
Authentication
      ↓
Create Order
      ↓
Payment
      ↓
Response
```

E2E-тест максимально приближен к реальному сценарию, но обычно дороже и медленнее unit-тестов.

---

# 🔹 Docker в тестовом окружении

Docker позволяет создать одинаковое окружение для тестов.

Например:

```text
Docker Compose
      ↓
┌──────────────────────┐
│ FastAPI              │
│ PostgreSQL           │
│ Redis                │
└──────────────────────┘
      ↓
    pytest
```

Можно поднять инфраструктуру:

```python id="q6m8vx"
docker compose up -d
```

и затем запустить:

```python id="v4m2qx"
pytest
```

---

# 🔹 CI и Test Environment

Очень часто тестовое окружение связано с **CI/CD**.

Например:

```text
Developer
    ↓
git push
    ↓
Merge Request
    ↓
CI
    ↓
Build
    ↓
Test Environment
    ↓
pytest
    ↓
Integration Tests
    ↓
Result
```

Если тесты не прошли:

```text
CI ❌
```

и merge может быть запрещён правилами проекта.

---

# 🔹 Переменные окружения

Test Environment имеет собственную конфигурацию.

Например:

```text
DATABASE_URL=test_database
REDIS_URL=test_redis
DEBUG=false
ENVIRONMENT=test
```

В production:

```text
DATABASE_URL=production_database
REDIS_URL=production_redis
ENVIRONMENT=production
```

Код приложения может оставаться одинаковым, а конфигурация — различаться.

---

# 🔹 Secrets

Тестовая среда тоже может использовать секреты:

```text
DATABASE_PASSWORD
API_KEY
JWT_SECRET
```

Их не следует хранить непосредственно в Git.

В зависимости от инфраструктуры используются:

```text
CI/CD Secrets
Secret Manager
Kubernetes Secrets
Environment Variables
```

---

# 🔹 Mock и Test Environment

Не все внешние сервисы удобно использовать в тестовой среде.

Например приложение обращается к:

```text
Payment API
```

Вместо реального платежа можно использовать:

```text
Application
     ↓
Mock Payment API
```

Это позволяет тестировать:

* успешную оплату;
* отказ;
* timeout;
* ошибку сети.

Например:

```text
Payment API
   ↓
500 Internal Server Error
```

и проверить, корректно ли приложение обрабатывает ошибку.

---

# 🔹 Test Environment и реальные внешние сервисы

Иногда тесты используют настоящие тестовые окружения внешних сервисов:

```text
Application
    ↓
Test API
    ↓
External Service Sandbox
```

Например платёжный сервис может предоставить **sandbox**.

Это позволяет проверить интеграцию без выполнения реальных операций.

---

# 🔹 Reproducibility

Хорошее тестовое окружение должно быть воспроизводимым.

То есть желательно иметь возможность:

```text
Destroy
   ↓
Create
   ↓
Install
   ↓
Run tests
```

и получить одинаковый результат.

Docker, IaC и фиксированные версии зависимостей помогают этого добиться.

---

# 🔹 Production-like Environment

Чем ближе тестовое окружение к production по инфраструктуре, тем больше проблем можно обнаружить заранее.

Например:

```text
Production:
PostgreSQL 15
Redis 7
Python 3.13
Nginx
Kubernetes
```

Тестовая среда может использовать совместимые версии:

```text
Test:
PostgreSQL 15
Redis 7
Python 3.13
Nginx
Kubernetes
```

При этом данные и секреты должны быть отдельными.

---

# 🔹 Но Test Environment не обязан быть копией Production

Полная копия production может быть слишком дорогой.

Например:

```text
Production
10 Kubernetes Nodes
100 Pods
3 DB replicas
```

Test:

```text
2 Nodes
5 Pods
1 Test DB
```

Главное — сохранить необходимые для тестирования свойства системы.

---

# 🔹 Test Environment и миграции

Для backend-проектов важно проверять миграции БД.

Например:

```text
Migration
    ↓
Test Database
    ↓
Apply migration
    ↓
Tests
```

Это позволяет обнаружить ошибки до production:

```text
column missing
constraint conflict
migration failure
```

# 🔹 Частые вопросы на собеседовании

### Что такое тестовое окружение?

> Отдельная среда для выполнения автоматических и ручных тестов приложения и его интеграций.

### Зачем отдельное тестовое окружение?

> Чтобы проверять изменения в изолированной среде и не затрагивать production.

### Чем Test отличается от Dev?

> Dev предназначен для разработки и отладки, Test — для систематической проверки изменений.

### Чем Test отличается от Staging?

> Test обычно ориентирован на выполнение тестов, а Staging — на проверку приложения в максимально production-like окружении перед релизом. Конкретное разделение зависит от команды.

### Должна ли Test Database быть отдельной?

> Да, тесты не должны работать с production database.

### Зачем Docker в Test Environment?

> Для воспроизводимого запуска приложения и зависимостей с фиксированными версиями.

### Что такое test data?

> Данные, специально подготовленные для выполнения тестовых сценариев.

### Что такое test isolation?

> Независимость тестов друг от друга, чтобы результат одного теста не влиял на другой.

### Что такое mock?

> Объект или сервис-замена, имитирующий поведение реальной зависимости во время теста.

### Что такое sandbox?

> Безопасное тестовое окружение внешнего сервиса, позволяющее проверять интеграцию без воздействия на реальные операции.

### Как Test Environment связан с CI?

> CI может автоматически создавать или использовать тестовое окружение, запускать тесты и сообщать результат проверки.

# 🔑 Главное

```text
                    Test Environment
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
          App           Test DB       Redis
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                         Tests
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
            Unit       Integration     E2E
              │            │            │
              └────────────┼────────────┘
                           ↓
                         Result
                           │
                     ┌─────┴─────┐
                     ↓           ↓
                     ✅          ❌
                   дальше      исправить
```

> **Dev** → разрабатываем.
> **Test** → проверяем.
> **Staging** → финально проверяем production-like окружение.
> **Production** → обслуживаем реальных пользователей.
> **Test DB** → отдельная БД для тестов.
> **Test Data** → данные для тестовых сценариев.
> **Isolation** → тесты не зависят друг от друга.
> **Docker** → помогает сделать тестовое окружение воспроизводимым.
