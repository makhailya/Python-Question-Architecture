# Линтеры 🔍

## 🎤 Короткий ответ

**Линтер** — это инструмент статического анализа кода, который проверяет исходники **без запуска программы** и находит потенциальные ошибки, проблемы качества, нарушения стиля и правил проекта.

Например, **Ruff** может найти неиспользуемый импорт, подозрительный код или нарушение правила PEP 8.

> **Линтер = статический анализ → поиск проблем в коде → предупреждение/ошибка.**

---

## 🎯 Формула для собеседования

**Код → Линтер → статический анализ → найденные проблемы → исправление**

```text
Python-код
    ↓
  Ruff
    ↓
Статический анализ
    ↓
┌──────────────────────┐
│ unused import        │
│ ошибка/антипаттерн   │
│ нарушение правила   │
└──────────────────────┘
```

---

# 1. Что такое линтинг

**Linting** — автоматическая проверка исходного кода по набору правил.

Главная особенность:

> Код **не нужно запускать**, чтобы обнаружить многие проблемы.

Например:

```python
import os

def hello():
    print("Hello")
```

`os` здесь не используется.

Линтер может сообщить:

```text
F401 'os' imported but unused
```

---

# 2. Что проверяет линтер

В зависимости от инструмента линтер может искать:

### Ошибки

Например:

```python
def calculate():
    return undefined_variable
```

### Неиспользуемый код

```python
import os
import sys

print("Hello")
```

### Потенциально подозрительные конструкции

Например:

* недостижимый код;
* опасные конструкции;
* дублирование;
* неправильное использование API;
* ошибки импорта.

### Стиль

Например:

```python
x=10
```

вместо принятого в проекте:

```python
x = 10
```

Но конкретный набор проверок зависит от линтера и включённых правил.

---

# 3. Линтер не запускает программу

Это принципиальное отличие.

```text
Линтер
   ↓
анализирует исходный код
   ↓
без выполнения программы
```

А тест:

```text
Тест
   ↓
запускает код
   ↓
проверяет поведение
```

Поэтому линтер может найти:

```text
unused import
undefined name
bad syntax
style violation
```

Но он не проверит, например:

> «API действительно возвращает правильный результат при запросе к PostgreSQL».

Для этого нужны тесты.

---

# 4. Ruff

**Ruff** — современный быстрый Python-инструмент, который объединяет много возможностей статического анализа и форматирования.

Например:

```python
ruff check .
```

Запускает проверки линтера.

Автоматическое исправление:

```python
ruff check . --fix
```

---

# 5. Пример Ruff

Допустим:

```python
import os
import sys


def hello():
    print("Hello")
```

Ruff может обнаружить неиспользуемые импорты.

```text
F401 `os` imported but unused
F401 `sys` imported but unused
```

Можно попросить Ruff исправить часть таких проблем:

```python
ruff check . --fix
```

---

# 6. Правила линтера

Линтер использует набор правил.

Например, Ruff использует коды диагностик:

```text
F401
E501
E711
E712
```

Например:

```text
F401 → imported but unused
```

Это позволяет точно понимать, какое правило нарушено.

---

# 7. Конфигурация

Правила проекта обычно задаются в:

```text
pyproject.toml
```

Например:

```python
[tool.ruff]
line-length = 88

[tool.ruff.lint]
select = ["E", "F", "I"]
```

Здесь проект определяет, какие группы правил использовать.

# 8. Линтер и PEP 8

**PEP 8** — руководство по стилю Python-кода.

Линтеры могут проверять многие рекомендации PEP 8.

Например:

```python
def hello(name):
    print(f"Hello, {name}")
```

вместо плохо оформленного:

```python
def hello( name ):
 print( f"Hello, {name}" )
```

Но важно:

> **PEP 8 — это рекомендации/стандарт оформления, а линтер — инструмент автоматической проверки.**

# 9. Линтер vs Formatter

Это очень частый вопрос.

### Линтер

**Ищет проблемы.**

```text
Что здесь неправильно?
```

Например:

```text
F401 unused import
```

### Formatter

**Автоматически приводит код к единому формату.**

Например:

```python
x=  10
```

превращает в:

```python
x = 10
```

---

## Сравнение

|                           | Линтер | Formatter      |
| ------------------------- | ------ | -------------- |
| Ищет проблемы             | ✅      | частично       |
| Исправляет форматирование | иногда | ✅              |
| Проверяет стиль           | ✅      | ✅              |
| Ищет потенциальные ошибки | ✅      | ❌              |
| Пример                    | Ruff   | Black          |
| Основная задача           | анализ | форматирование |

Важно: **Ruff умеет не только linting, но и formatting**, поэтому современный Python-проект может использовать Ruff для обеих задач.

---

# 10. Ruff vs Black

Исторически часто встречалась связка:

```text
Ruff
 +
Black
```

Где:

```text
Ruff → linting
Black → formatting
```

Например:

```text
Code
 ↓
Ruff
 ↓
проверка правил
 ↓
Black
 ↓
единое форматирование
```

Но Ruff также имеет собственный formatter:

```python
ruff format .
```

Поэтому отдельный Black не всегда необходим.

---

# 11. Линтер vs MyPy

Это тоже важно для Python Backend.

### Ruff

Проверяет:

* стиль;
* потенциальные ошибки;
* импорты;
* различные статические правила.

### MyPy

Проверяет **типизацию**.

Например:

```python
def add(a: int, b: int) -> int:
    return a + b
```

Если написать:

```python
result: int = "hello"
```

MyPy может обнаружить несовместимость типов.

---

## Сравнение

|                        | Ruff                         | MyPy |
| ---------------------- | ---------------------------- | ---- |
| Линтинг                | ✅                            | ❌    |
| Стиль                  | ✅                            | ❌    |
| Неиспользуемые импорты | ✅                            | ❌    |
| Типы                   | частично/не как type checker | ✅    |
| Статический анализ     | ✅                            | ✅    |
| Форматирование         | ✅                            | ❌    |

---

# 12. Линтер vs pytest

Это принципиально разные инструменты.

### Ruff

Проверяет исходный код статически:

```text
«Код выглядит корректно с точки зрения правил?»
```

### pytest

Проверяет поведение программы:

```text
«Программа действительно работает правильно?»
```

Например:

```python
def divide(a: int, b: int) -> float:
    return a / b
```

Линтер может не найти проблем.

Но тест может обнаружить ошибку бизнес-логики.

```python
def test_divide():
    assert divide(10, 2) == 5
```

# 13. Типичный CI pipeline

Для Python Backend можно построить pipeline:

```text
Git Push
    ↓
CI
    ↓
┌──────────────┐
│ Ruff         │
│ MyPy         │
│ pytest       │
│ build        │
└──────────────┘
    ↓
Merge
```

Например:

```python
ruff check .
ruff format --check .
mypy .
pytest
```

Если линтер обнаружил ошибку:

```text
CI → Failed
```

и Merge Request может быть заблокирован правилами проекта.

# 14. Линтер в IDE

Линтер можно интегрировать в:

* PyCharm;
* VS Code;
* CI/CD;
* pre-commit.

Тогда ошибка показывается непосредственно во время разработки.

```text

import os

```

Это позволяет исправлять проблему ещё до commit.

# 15. Pre-commit

**Pre-commit** позволяет автоматически запускать проверки перед созданием commit.

Например:

```text
git commit
    ↓
pre-commit
    ↓
Ruff
    ↓
Black / Ruff format
    ↓
MyPy
    ↓
если всё OK → commit
```

Если проверка не прошла:

```text
commit → blocked
```

Это помогает не отправлять очевидные проблемы в репозиторий.

# 16. Линтер и Code Review

Линтер позволяет автоматизировать часть Code Review.

Например, вместо того чтобы reviewer вручную писал:

> «У тебя неиспользуемый импорт».

это делает CI:

```text
Ruff
 ↓
F401
 ↓
CI failed
```

Reviewer тогда больше концентрируется на:

* архитектуре;
* бизнес-логике;
* читаемости;
* корректности решения;
* производительности;
* безопасности.

---

# 17. Что линтер НЕ заменяет

Линтер не заменяет:

### Тесты

Не проверяет полноценное поведение приложения.

### Code Review

Не оценивает архитектурное решение так, как человек.

### MyPy

Если проект требует полноценной статической проверки типов, нужен type checker.

### Security Scanner

Для специализированного поиска уязвимостей могут использоваться отдельные инструменты.

# 19. Почему линтеры нужны команде

Без линтера каждый разработчик может писать код немного по-разному:

```text
Developer A → style A
Developer B → style B
Developer C → style C
```

С линтером появляются единые правила:

```text
              Project Rules
                   ↓
        ┌──────────┴──────────┐
        ↓                     ↓
 Developer A              Developer B
        ↓                     ↓
             одинаковые правила
```

Это уменьшает количество механических замечаний на Code Review.


# 🎤 Вопросы на собеседовании

### Что такое линтер?

> Линтер — инструмент статического анализа, который проверяет исходный код без его выполнения и выявляет потенциальные ошибки, нарушения стиля и правил проекта.

### Для чего нужен Ruff?

> Ruff используется для быстрого статического анализа Python-кода и может выполнять множество lint-проверок, а также форматирование.

### Чем линтер отличается от formatter?

> Линтер ищет проблемы и нарушения правил, а formatter автоматически приводит код к единому стилю форматирования.

### Чем Ruff отличается от MyPy?

> Ruff в первую очередь выполняет lint-проверки и форматирование, а MyPy анализирует типизацию Python-кода.

### Чем линтер отличается от pytest?

> Линтер анализирует исходный код без выполнения программы, а pytest запускает тесты и проверяет фактическое поведение приложения.

### Может ли линтер найти все ошибки?

> Нет. Он обнаруживает только проблемы, которые попадают под его правила и возможности статического анализа. Для проверки поведения нужны тесты и другие инструменты.

### Можно ли запускать линтер в CI?

> Да. Обычно линтер запускается в CI вместе с тестами, type checking и другими проверками. При нарушении правил pipeline может завершиться ошибкой.

```text
          ↓            ↓            ↓
      lint/style      types       behavior

                       ↓

                       ↓
                     Merge
```

### Самая важная формула

> **Линтер = статический анализ кода без запуска программы.**

**Ruff** — один из современных инструментов для Python, который может выполнять как **linting**, так и **formatting**.
