# 🔐 Синхронизация в многопоточности

## 🎤 Короткий ответ

**Синхронизация** — это механизм управления взаимодействием конкурентных потоков, чтобы они корректно работали с общими ресурсами и выполняли операции в необходимом порядке.

Она нужна прежде всего при наличии **shared mutable state**, чтобы избежать **[[Race Condition]]**, **[[Data Race]]**, потерянных обновлений и других ошибок конкурентного доступа.

В Python для этого используются `Lock`, `RLock`, [[Семафор (Semaphore) в Python]], `Condition`, `Event`, `Barrier`, а также `Queue` для безопасного обмена данными между потоками.

---

## 🗣️ Ответ на собеседовании

> Синхронизация в многопоточности нужна для управления доступом нескольких потоков к общим ресурсам и для обеспечения необходимого порядка выполнения операций.
>
> Основная проблема возникает, когда несколько потоков работают с общим изменяемым состоянием. Например, два потока одновременно изменяют один счётчик. Без синхронизации операции могут пересекаться, и одно обновление будет потеряно.
>
> Для защиты критической секции можно использовать `Lock`. Если один и тот же поток должен захватывать блокировку повторно, используется `RLock`. Для ограничения количества одновременно работающих потоков можно применять `Semaphore`, а для организации ожидания определённого состояния — `Condition` или `Event`.
>
> Кроме блокировок, часто используют `Queue`: вместо прямого доступа потоков к общему состоянию они обмениваются сообщениями через потокобезопасную очередь.
>
> При этом синхронизация должна быть минимальной и продуманной: чрезмерное использование блокировок снижает конкурентность, а неправильный порядок захвата нескольких locks может привести к deadlock.

# 📚 Разбор поглубже

## 1. Зачем нужна синхронизация

Представим:

```text
Thread A ──┐
Thread B ──┼──> Shared State
Thread C ──┘
```

Если потоки только читают данные:

```text
A ── READ ──┐
B ── READ ──┼──> data
C ── READ ──┘
```

обычно проблем с конкурентной записью нет.

Но если появляется изменение:

```text
A ── WRITE ──┐
B ── READ ───┼──> data
C ── WRITE ──┘
```

необходимо подумать о синхронизации.

Общая схема:

```text
Shared Mutable State
        ↓
Concurrent Access
        ↓
Race / Data Race
        ↓
Synchronization
```

---

# 2. Что именно синхронизируем

Синхронизировать можно не только переменную.

Например:

* доступ к объекту;
* критическую секцию;
* порядок выполнения;
* количество одновременно работающих потоков;
* ожидание события;
* обмен данными между потоками.

Поэтому существует несколько разных механизмов.

---

# 3. Lock

**`Lock`** — базовый механизм взаимного исключения.

Идея:

> Только один поток одновременно может владеть lock.

Пример:

```python
import threading


counter = 0
lock = threading.Lock()


def increment():
    global counter

    with lock:
        counter += 1
```

Без lock:

```text
Thread A ──┐
Thread B ──┼──> counter
Thread C ──┘
```

С lock:

```text
Thread A ── LOCK ── critical section ── UNLOCK
Thread B ── WAIT
Thread C ── WAIT
```

После освобождения lock следующий поток получает возможность войти.

---

# 4. Критическая секция

**Критическая секция** — участок кода, доступ к которому необходимо контролировать.

Например:

```python
with lock:
    balance -= amount
```

Критическая секция:

```text
┌──────────────────────┐
│ balance -= amount    │
└──────────────────────┘
```

Важно:

> Lock должен защищать именно тот набор операций, который должен выполняться согласованно.

Не обязательно блокировать весь метод:

```python
def process():
    # долгие вычисления

    with lock:
        # только работа с shared state
        ...

    # дальнейшая работа
```

Это позволяет сохранить больше конкурентности.

---

# 5. `with lock`

Предпочтительный способ работы с lock:

```python
with lock:
    critical_section()
```

Концептуально это соответствует:

```python
lock.acquire()

try:
    critical_section()
finally:
    lock.release()
```

`with` удобнее и безопаснее, потому что lock будет освобождён даже при исключении.

---

# 6. `RLock`

**`RLock` (Reentrant Lock)** позволяет одному и тому же потоку повторно захватывать одну блокировку.

Например:

```python
import threading


lock = threading.RLock()


def outer():
    with lock:
        inner()


def inner():
    with lock:
        print("Работа")
```

С обычным `Lock` такой сценарий может привести к блокировке самого себя.

```text
Thread A
   │
   ├── acquire Lock
   │
   └── вызывает inner()
           │
           └── пытается acquire тот же Lock
                    ↓
                  WAIT
```

С `RLock`:

```text
Thread A
   │
   ├── acquire
   ├── acquire снова
   ├── работа
   ├── release
   └── release
```

У `RLock` есть концепция **уровня рекурсивного захвата**: блокировка окончательно освобождается после соответствующего количества `release()`.

---

# 7. Lock vs RLock

| `Lock`                                         | `RLock`                                        |
| ---------------------------------------------- | ---------------------------------------------- |
| Обычная блокировка                             | Reentrant Lock                                 |
| Повторный захват тем же потоком не допускается | Повторный захват тем же потоком допускается    |
| Проще                                          | Сложнее                                        |
| Предпочтителен, если повторный захват не нужен | Используется, когда он действительно необходим |

Практическое правило:

> Если тебе не нужен reentrant behavior — обычно достаточно `Lock`.

---

# 8. Semaphore

**`Semaphore`** ограничивает количество потоков, которые одновременно могут пройти в определённую секцию.

Например:

```python
import threading


semaphore = threading.Semaphore(3)


def worker():
    with semaphore:
        do_work()
```

Если:

```text
Semaphore = 3
```

то одновременно могут работать максимум три потока внутри защищённой области.

```text
Thread 1 ──┐
Thread 2 ──┤
Thread 3 ──┼──> resource
Thread 4 ──┤
Thread 5 ──┘
            ↑
          WAIT
```

Типичное применение — ограничение количества одновременных обращений к ресурсу.

Например:

```text
100 threads
     ↓
Semaphore(10)
     ↓
максимум 10 одновременно
```

---

# 9. Lock vs Semaphore

Главное различие:

```text
Lock
→ максимум 1 поток
```

```text
Semaphore(5)
→ максимум 5 потоков
```

То есть:

```text
Lock ≈ 1 разрешение
Semaphore(N) ≈ N разрешений
```

Но семантически это разные примитивы: `Lock` выражает взаимное исключение, `Semaphore` — ограничение количества одновременно допущенных участников.

---

# 10. Event

**`Event`** позволяет одному потоку сообщить другим, что определённое событие произошло.

```python
import threading


event = threading.Event()


def worker():
    event.wait()
    print("Начинаю работу")


thread = threading.Thread(target=worker)
thread.start()

# что-то произошло
event.set()
```

Схема:

```text
Worker
   │
   └── wait()
        │
        │
        ▼
      Event
        ▲
        │
        │ set()
        │
Main Thread
```

После `set()` ожидающие потоки могут продолжить выполнение.

`Event` хорошо подходит для сценария:

> «Жди, пока произойдёт событие».

---

# 11. Condition

**`Condition`** используется, когда поток должен ждать выполнения определённого условия.

Например:

```text
Producer
   │
   └── добавил данные
            ↓
         Condition
            ↓
Consumer продолжает работу
```

Пример:

```python
import threading


condition = threading.Condition()
items = []


def consumer():
    with condition:
        while not items:
            condition.wait()

        item = items.pop(0)
        print(item)


def producer():
    with condition:
        items.append("data")
        condition.notify()
```

Здесь consumer не должен просто «ждать какое-то время».

Он ждёт именно:

```text
items не пуст
```

---

# 12. `wait()` и `notify()`

Типичный сценарий:

```text
Consumer
   │
   └── wait()
          ↓
        ждёт

Producer
   │
   ├── изменяет состояние
   └── notify()
          ↓
Consumer продолжает
```

Очень важная идея:

> `Condition` связывает ожидание потока с определённым состоянием общего ресурса.

---

# 13. Почему используется `while`, а не `if`

Правильный шаблон:

```python
with condition:
    while not items:
        condition.wait()

    item = items.pop()
```

а не:

```python
with condition:
    if not items:
        condition.wait()

    item = items.pop()
```

После пробуждения условие нужно **проверить снова**.

Потому что уведомление означает не:

> «Тебе гарантированно можно продолжать».

А скорее:

> «Возможно, состояние изменилось — проверь условие».

---

# 14. Barrier

**`Barrier`** позволяет нескольким потокам дождаться друг друга в определённой точке.

Например:

```python
import threading


barrier = threading.Barrier(3)


def worker():
    prepare_data()

    barrier.wait()

    process_data()
```

Схема:

```text
Thread 1 ── prepare ──┐
Thread 2 ── prepare ──┼── Barrier
Thread 3 ── prepare ──┘
                         ↓
                 все готовы
                         ↓
                  продолжение
```

Полезно, когда работа состоит из нескольких фаз.

---

# 15. Queue

`Queue` — один из самых практичных инструментов для многопоточности.

Вместо прямого доступа:

```text
Thread 1 ──┐
Thread 2 ──┼──> Shared Mutable State
Thread 3 ──┘
```

можно использовать:

```text
Producer
   │
   ▼
┌─────────┐
│  Queue  │
└─────────┘
   │
   ▼
Consumer
```

Пример:

```python
from queue import Queue
import threading


queue = Queue()


def producer():
    for i in range(10):
        queue.put(i)


def consumer():
    while True:
        item = queue.get()

        if item is None:
            break

        process(item)
        queue.task_done()
```

Здесь потоки не обязаны напрямую совместно изменять одну структуру данных.

---

# 16. Почему Queue иногда лучше Lock

Можно сделать:

```text
несколько потоков
        ↓
   общий список
        ↓
      Lock
```

Но архитектурно иногда проще:

```text
Producer
    ↓
  Queue
    ↓
Consumer
```

Это уменьшает количество shared mutable state и переводит взаимодействие в **message passing**.

То есть синхронизация достигается не только блокировками.

---

# 17. Deadlock

Неправильная синхронизация может привести к **deadlock**.

Например, есть два lock:

```text
Lock A
Lock B
```

Thread 1:

```text
acquire A
↓
wait B
```

Thread 2:

```text
acquire B
↓
wait A
```

Получается:

```text
Thread 1 ── holds A ──> waits B
                              ↑
                              │
Thread 2 ── holds B ──────────┘
           waits A
```

Никто не может продолжить.

---

# 18. Как предотвращать Deadlock

Один из основных подходов — **единый порядок захвата блокировок**.

Например, всегда:

```text
Lock A → Lock B
```

а не:

```text
Thread 1: A → B
Thread 2: B → A
```

То есть:

```text
Thread 1: A → B
Thread 2: A → B
```

Если всем потокам нужен одинаковый порядок, вероятность циклического ожидания значительно уменьшается.

# 19. Синхронизация и производительность

Синхронизация не бесплатна.

Если критическая секция слишком большая:

```python
with lock:
    # очень много работы
```

потоки начинают большую часть времени ждать.

```text
Thread 1 ── LOCK ────────────────
Thread 2       WAIT ─────────────
Thread 3       WAIT ─────────────
Thread 4       WAIT ─────────────
```

Конкурентность фактически уменьшается.

Поэтому хорошая практика:

```text
Снаружи
├── независимая работа
├── независимая работа
│
└── LOCK
      └── минимальная критическая секция
```

# 20. Синхронизация ≠ только Lock

Это принципиальный момент.

```text
Синхронизация
│
├── Mutual Exclusion
│   ├── Lock
│   └── RLock
│
├── Ограничение конкуренции
│   └── Semaphore
│
├── Ожидание состояния
│   └── Condition
│
├── Сигнал о событии
│   └── Event
│
├── Синхронизация фаз
│   └── Barrier
│
└── Обмен данными
    └── Queue
```

Поэтому на собеседовании не стоит отвечать:

> «Синхронизация — это Lock».

Точнее:

> **Lock — один из механизмов синхронизации.**

# 21. Синхронизация и Race Condition

Связь между темами:

```text
Несколько потоков
       ↓
Shared Mutable State
       ↓
Concurrent Access
       ↓
Race Condition / Data Race
       ↓
      нужен
       ↓
Synchronization
       ↓
Lock / Queue / Semaphore / ...
```

# 22. Практический пример

Допустим, есть склад:

```python
stock = 10
```

Два потока пытаются продать товар.

Без синхронизации:

```text
Thread A: проверяет stock
Thread B: проверяет stock

A: уменьшает
B: уменьшает
```

Можно получить некорректное состояние.

С `Lock`:

```python
lock = threading.Lock()


def sell():
    global stock

    with lock:
        if stock > 0:
            stock -= 1
            return True

    return False
```

Теперь проверка:

```text
stock > 0
```

и изменение:

```text
stock -= 1
```

выполняются как единая критическая секция относительно других потоков.

# 🎤 Вопросы на собеседовании

### Что такое синхронизация?

Управление конкурентным доступом потоков к общим ресурсам и координация их выполнения для обеспечения корректности программы.

### Зачем нужна синхронизация?

Чтобы предотвращать Race Condition, Data Race, Lost Update и обеспечивать необходимый порядок операций.

### Что такое Lock?

Механизм взаимного исключения, позволяющий только одному потоку одновременно выполнять защищённую критическую секцию.

### Чем `Lock` отличается от `RLock`?

`RLock` позволяет одному и тому же потоку повторно захватывать блокировку.

### Что такое Semaphore?

Механизм, ограничивающий количество потоков, которые одновременно могут получить доступ к ресурсу.

### Чем Semaphore отличается от Lock?

`Lock` допускает одного владельца, а `Semaphore(N)` позволяет одновременно пропустить до `N` участников.

### Что такое Condition?

Механизм, позволяющий потоку ждать определённого состояния и другому потоку уведомить его об изменении этого состояния.

### Что такое Event?

Механизм сигнализации: поток устанавливает событие через `set()`, а другие могут ждать его через `wait()`.

### Что такое Barrier?

Точка синхронизации, на которой несколько потоков ждут друг друга перед переходом к следующей фазе.

### Что такое Queue?

Потокобезопасная очередь, позволяющая организовать обмен данными между потоками.

### Можно ли решить все проблемы через Lock?

Технически можно пытаться, но это плохая стратегия. Разные задачи требуют разных примитивов, а избыточные locks ухудшают конкурентность и могут привести к deadlock.

### Что такое Deadlock?

Состояние, когда потоки взаимно ждут ресурсы, удерживаемые друг другом, и поэтому никто не может продолжить выполнение.

---

## 🧠 Формула для собеседования

> **Синхронизация = управление конкурентным доступом и порядком выполнения.**
>
> Основная проблема:
>
> **Shared Mutable State → Race Condition / Data Race.**
>
> Основные инструменты:
>
> **Lock → один поток**
>
> **RLock → повторный захват тем же потоком**
>
> **Semaphore → ограниченное количество потоков**
>
> **Condition → ждать состояние**
>
> **Event → сигнал о событии**
>
> **Barrier → ждать друг друга**
>
> **Queue → безопасный обмен данными**
>
> И главное:
>
> **синхронизация должна защищать необходимую критическую секцию, но не превращать всю многопоточность в последовательное выполнение.**
