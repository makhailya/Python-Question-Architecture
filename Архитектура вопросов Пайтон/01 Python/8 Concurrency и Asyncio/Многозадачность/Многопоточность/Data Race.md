# ⚡ Data Race

## 🎤 Короткий ответ

**Data Race** — это ситуация, когда несколько потоков или процессов **конкурентно обращаются к одной области памяти**, при этом хотя бы один из доступов является записью, и между этими операциями нет необходимой синхронизации.

Из-за этого один поток может читать данные в момент, когда другой их изменяет, либо несколько потоков могут одновременно изменять одно состояние.

**Data Race — частный случай более широкого понятия [[Race Condition]].**

---

## 🗣️ Ответ на собеседовании

> Data Race — это конкурентный доступ нескольких потоков или процессов к одной области памяти, когда как минимум одна операция является записью, а необходимая синхронизация отсутствует.
>
> Например, два потока одновременно изменяют общий объект или переменную. Один поток может читать значение, пока другой его изменяет, либо оба могут одновременно выполнять запись.
>
> В результате поведение программы может зависеть от конкретного порядка выполнения операций.
>
> Для предотвращения Data Race используют синхронизацию — например, `Lock`, `RLock`, `Semaphore`, `Queue` — либо проектируют систему так, чтобы минимизировать shared mutable state.
>
> Важно отличать Data Race от Race Condition: Data Race связан именно с конфликтующим доступом к общей памяти, а Race Condition — более широкое понятие, когда корректность зависит от порядка конкурентных событий.

# 📚 Разбор поглубже

## 1. Что такое Data Race

Название буквально означает **«гонка за данные»**.

Есть общий ресурс:

```text id="3g0h1a"
Shared Memory
     │
     ├── Thread A
     └── Thread B
```

Оба потока обращаются к одной области памяти:

```text id="a6d9xs"
Thread A ── READ/WRITE ──┐
                         ├── Shared Data
Thread B ── READ/WRITE ──┘
```

Если эти обращения конфликтуют и между ними нет необходимой синхронизации, возникает Data Race.

---

# 2. Условия Data Race

Для классического Data Race нужны три основных условия:

```text id="g2r6mb"
1. Общая область памяти
        +
2. Конкурентный доступ
        +
3. Хотя бы одна операция — запись
        +
4. Нет необходимой синхронизации
        ↓
     Data Race
```

Например:

```text id="w5d3qz"
Thread A: READ x
Thread B: WRITE x
```

Это потенциальный Data Race.

А:

```text id="k2z9la"
Thread A: READ x
Thread B: READ x
```

само по себе Data Race не создаёт, потому что оба только читают.

---

# 3. Простой пример

Допустим:

```python id="f7v2s4"
counter = 0
```

Два потока изменяют его:

```python id="z4wq1k"
def increment():
    global counter
    counter += 1
```

Концептуально:

```text id="q2s8fa"
Thread A:
    READ counter
    ↓
    ADD 1
    ↓
    WRITE counter

Thread B:
    READ counter
    ↓
    ADD 1
    ↓
    WRITE counter
```

Доступ к одному `counter` происходит конкурентно, причём оба потока выполняют запись.

---

# 4. Как выглядит конфликт

Пусть:

```text id="4c9j2m"
counter = 0
```

Возможна последовательность:

```text id="m1z7qp"
Thread A: READ counter → 0
Thread B: READ counter → 0

Thread A: WRITE counter → 1
Thread B: WRITE counter → 1
```

Получаем:

```text id="9b7v3k"
counter = 1
```

Хотя два увеличения логически должны были привести к:

```text id="0n2k8d"
counter = 2
```

Это классический пример проблемы конкурентного доступа к shared mutable state.

---

# 5. Data Race и `counter += 1`

Важно понимать, что:

```python id="3x1a6z"
counter += 1
```

не следует воспринимать как одну неделимую бизнес-операцию.

Концептуально:

```text id="w4k9pc"
counter += 1

      ↓

READ
  ↓
CALCULATE
  ↓
WRITE
```

Именно возможность пересечения этих операций создаёт проблему.

---

# 6. Data Race и Race Condition

Эти понятия часто путают.

### Data Race

Говорим о **конфликтующем доступе к памяти**:

```text id="b5h2qm"
Thread A ── WRITE ──┐
                    ├── same memory
Thread B ── READ ───┘
```

### Race Condition

Говорим о **зависимости корректности результата от порядка конкурентных событий**:

```text id="q8f4sd"
A → B
```

может дать другой результат, чем:

```text id="m6p1xc"
B → A
```

Поэтому:

```text id="v3r8nk"
Race Condition
│
├── Data Race
│
└── Другие race conditions
    без классического
    конфликта доступа к памяти
```

---

# 7. Пример Race Condition без Data Race

Представим:

```python id="a2n7vc"
if not account_locked:
    perform_operation()
```

Пусть два конкурентных процесса проверяют состояние:

```text id="s8f3kw"
Thread A:
    проверяет account_locked
        ↓
       False

Thread B:
    выполняет операцию,
    после чего меняет состояние

Thread A:
    продолжает операцию
```

Здесь проблема может быть в неправильном порядке событий и нарушении логического инварианта.

То есть Race Condition может быть шире, чем конкретный Data Race.

---

# 8. Data Race и GIL

Очень важный вопрос для Python.

> «Если в CPython есть GIL, значит Data Race невозможен?»

**Нет.**

GIL и синхронизация доступа к состоянию — разные вещи.

```text id="7k2q4m"
GIL
│
└── управление выполнением
    Python bytecode в CPython

Lock
│
└── синхронизация доступа
    к shared state
```

Нельзя использовать GIL как замену:

```python id="z7c3nq"
threading.Lock()
```

---

# 9. Data Race и атомарность

Здесь важно не делать слишком простой вывод:

> «Одна строка Python = атомарная операция».

Это неверно как универсальное правило.

Например:

```python id="n5h8x2"
counter += 1
```

нельзя рассматривать как атомарную операцию изменения общего состояния.

Для корректности нужно анализировать:

* какие операции выполняются;
* какое состояние является общим;
* может ли выполнение переключиться между ними;
* какая синхронизация используется;
* какие гарантии предоставляет конкретная реализация Python.

# 10. Как устранить Data Race

## Вариант 1 — Lock

```python id="q6v1ba"
import threading


counter = 0
lock = threading.Lock()


def increment():
    global counter

    with lock:
        counter += 1
```

Теперь доступ к критической секции синхронизирован.

```text id="e7p4sd"
Thread A
    │
    ├── acquire
    ├── READ
    ├── MODIFY
    ├── WRITE
    └── release
              │
              ↓
          Thread B
```

---

# 11. Вариант 2 — RLock

`RLock` — reentrant lock.

Один и тот же поток может захватывать его несколько раз, не блокируя сам себя.

```python id="z8k4mx"
lock = threading.RLock()


def outer():
    with lock:
        inner()


def inner():
    with lock:
        print("Работа")
```

Для обычной критической секции чаще достаточно `Lock`.

---

# 12. Вариант 3 — Queue

Иногда лучше не давать потокам напрямую изменять общие данные.

Вместо:

```text id="c1s7qm"
Thread A ──┐
Thread B ──┼──> shared state
Thread C ──┘
```

используют:

```text id="k9p3vz"
Thread A ──┐
Thread B ──┼──> Queue ──> Worker
Thread C ──┘
```

Это подход **message passing**.

Он позволяет уменьшить количество shared mutable state.

---

# 13. Вариант 4 — Immutable State

Если состояние нельзя изменить:

```text id="m4d8qa"
Immutable object
```

то проблема конкурентной записи существенно уменьшается.

Например, вместо изменения общего объекта можно создать новое состояние:

```python id="x3f7nb"
new_state = old_state.copy()
```

А затем передать его другой части программы.

Это одна из идей, используемых в concurrency design:

> Чем меньше общего изменяемого состояния, тем меньше потенциальных проблем синхронизации.

---

# 14. Data Race в multiprocessing

Data Race возможен не только между потоками.

Процессы обычно имеют отдельную память:

```text id="b6v2px"
Process A
└── Memory A

Process B
└── Memory B
```

Но если процессы используют:

* `SharedMemory`;
* shared `Value`;
* shared `Array`;
* memory-mapped data;
* другие механизмы общей памяти,

они также могут конкурировать за одно состояние.

```text id="q9m5kc"
Process A ──┐
            ├── Shared Memory
Process B ──┘
```

И здесь также нужна синхронизация.

---

# 15. Data Race в базах данных

Похожая проблема существует и на уровне БД.

Например:

```text id="u8r2md"
Transaction A ── READ balance = 1000
Transaction B ── READ balance = 1000

A ── UPDATE balance = 900
B ── UPDATE balance = 800
```

Здесь возникают уже **конкурентные транзакции**, и база данных использует механизмы изоляции, блокировок и MVCC для управления такими ситуациями.

Это уже отдельная ветка:

```text id="c5x8qa"
Concurrency
└── Database Concurrency
    ├── Transactions
    ├── Isolation Levels
    ├── MVCC
    ├── Locks
    └── Lost Update
```

# 16. Data Race и Lost Update

**Lost Update** — один из типичных результатов неправильного конкурентного доступа.

```text id="p7n3wd"
Initial = 100

A: READ 100
B: READ 100

A: WRITE 90
B: WRITE 80
```

Изменение A было потеряно.

Получаем:

```text id="j4s8mc"
Expected based on both operations
        ↓
       70

Actual
        ↓
       80
```

Конкретный механизм защиты зависит от системы: mutex в памяти приложения, optimistic/pessimistic locking, транзакции и т.д.

---

# 17. Почему Data Race опасен

Проблема в том, что ошибка может быть **недетерминированной**.

Сегодня:

```text id="x5c9qa"
100 запусков → всё работает
```

Завтра:

```text id="n2v7kb"
101-й запуск → неправильный результат
```

Порядок операций зависит от:

* планировщика;
* нагрузки;
* I/O;
* количества потоков;
* состояния CPU;
* timing;
* других факторов.

Поэтому такие ошибки особенно неприятны при отладке.

# 🎤 Вопросы на собеседовании

### Что такое Data Race?

Конкурентный доступ к одной области памяти, когда как минимум одна операция является записью и отсутствует необходимая синхронизация.

### Чем Data Race отличается от Race Condition?

Data Race — более конкретная проблема конфликтующего доступа к общей памяти. Race Condition — более широкая проблема, когда результат зависит от порядка конкурентных событий.

### Может ли быть Data Race, если оба потока только читают?

Нет, обычный Data Race требует хотя бы одну операцию записи.

### GIL устраняет Data Race?

Нет. GIL не является механизмом синхронизации состояния приложения.

### Как защитить данные?

Например:

```python id="c9q5wt"
with lock:
    shared_data.update(...)
```

Также можно использовать `Queue`, другие механизмы синхронизации или архитектуру без общего изменяемого состояния.

### Что такое Lost Update?

Ситуация, когда одно конкурентное изменение состояния перезаписывает другое изменение.

### Может ли Data Race быть между процессами?

Да, если они используют общую память.

### Почему Data Race сложно отлаживать?

Потому что результат зависит от конкретного порядка выполнения конкурентных операций и может проявляться непредсказуемо.

## 🧠 Формула для собеседования

> **Data Race = Shared Memory + Concurrent Access + хотя бы одна Write + отсутствие необходимой синхронизации.**
>
> Например:
>
> ```text
> Thread A ── WRITE ──┐
>                     ├── same memory
> Thread B ── READ ───┘
> ```
>
> **Data Race — частный случай Race Condition.**
>
> **GIL не заменяет Lock.**
>
> Решения: **Lock / RLock / Queue / message passing / уменьшение shared mutable state.**
