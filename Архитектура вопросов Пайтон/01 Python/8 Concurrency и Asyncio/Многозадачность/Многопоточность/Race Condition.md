# 🏁 Race Condition

## 🎤 Короткий ответ

**Race Condition** — это ситуация в конкурентной программе, когда результат зависит от **порядка выполнения операций нескольких потоков или процессов**.

Чаще всего проблема возникает, когда несколько потоков работают с **общим изменяемым состоянием**, а последовательность операций не защищена синхронизацией.

Например, два потока одновременно делают:

```python
counter += 1
```

Оба могут прочитать одно и то же старое значение и затем записать результат, из-за чего одно изменение потеряется.

## 🗣️ Ответ на собеседовании

> Race Condition — это состояние конкурентной программы, при котором правильность результата зависит от того, в каком порядке выполняются операции нескольких потоков или процессов.
>
> Типичный пример — несколько потоков изменяют общий счётчик. Операция `counter += 1` логически состоит из чтения значения, вычисления нового значения и записи результата. Если два потока выполняют эти действия с пересечением по времени, оба могут прочитать одно и то же значение и потерять одно из обновлений.
>
> Чтобы устранить такую проблему, нужно синхронизировать доступ к общему состоянию. Например, использовать `threading.Lock`, который позволяет только одному потоку одновременно выполнять критическую секцию.
>
> При этом Race Condition — более широкое понятие, чем Data Race. Data Race обычно относится непосредственно к неконтролируемому одновременному доступу к одной области памяти, когда хотя бы одна операция является записью. Race Condition может возникать и без такого прямого конфликта памяти — достаточно, чтобы результат зависел от порядка конкурентных событий.

# 📚 Разбор поглубже

## 1. Что такое Race Condition

Название происходит от идеи **«гонки»**: несколько участников конкурируют за изменение состояния, и результат зависит от того, кто и когда успел выполнить свою операцию.

Упрощённо:

```text
Thread A ──────────────┐
                       ├──> Shared State
Thread B ──────────────┘
```

Если порядок действий имеет значение:

```text
A → B
```

может дать другой результат, чем:

```text
B → A
```

Именно зависимость результата от порядка конкурентных событий является ключевой идеей Race Condition.

---

# 2. Классический пример — счётчик

Допустим:

```python
counter = 0
```

Есть два потока:

```python
def increment():
    global counter
    counter += 1
```

Мы ожидаем:

```text
Thread 1: +1
Thread 2: +1

0 → 1 → 2
```

Но `counter += 1` концептуально можно представить как:

```text
1. READ counter
2. ADD 1
3. WRITE counter
```

Теперь возможна такая последовательность:

```text
counter = 0

Thread 1: READ → 0
Thread 2: READ → 0

Thread 1: ADD → 1
Thread 2: ADD → 1

Thread 1: WRITE → 1
Thread 2: WRITE → 1
```

Получаем:

```text
Итог = 1
```

вместо ожидаемых:

```text
Итог = 2
```

Одно обновление потерялось.

---

# 3. Почему возникает Race Condition

Обычно нужны несколько условий:

```text
Shared State
     +
Concurrent Execution
     +
Multiple Operations
     +
No Required Ordering / Synchronization
     ↓
Race Condition
```

Например:

```text
Thread 1 ── read ── modify ── write
                         ↘
Thread 2 ── read ── modify ── write
```

Если эти операции пересекаются, результат может зависеть от конкретного interleaving.

---

# 4. Interleaving

**Interleaving** — чередование операций конкурентных задач.

Например:

```text
A1
A2
B1
B2
A3
B3
```

или:

```text
A1
B1
B2
A2
A3
B3
```

Если эти варианты дают разные результаты, программа может иметь Race Condition.

Это важная идея:

> Не обязательно, чтобы два потока буквально выполнялись в одну наносекунду. Достаточно, чтобы их операции могли выполняться в разных порядках.

---

# 5. Как исправить Race Condition

Самый простой вариант для потоков — `Lock`.

```python
import threading


counter = 0
lock = threading.Lock()


def increment():
    global counter

    with lock:
        counter += 1
```

Теперь:

```text
Thread 1
   │
   ├── acquire lock
   ├── read
   ├── modify
   ├── write
   └── release lock

Thread 2
   │
   └── ждёт
```

После освобождения блокировки второй поток может выполнить свою критическую секцию.

---

# 6. Критическая секция

**Критическая секция** — участок кода, доступ к которому должен быть синхронизирован.

Например:

```python
with lock:
    counter += 1
```

Здесь критическая секция:

```text
read → modify → write
```

Главная идея:

> Операции, которые должны восприниматься как единое неделимое действие относительно других потоков, выполняются под синхронизацией.

---

# 7. Race Condition без общего счётчика

Race Condition не ограничивается `counter`.

Например, есть банковский счёт:

```python
balance = 1000
```

Два потока одновременно проверяют:

```python
if balance >= 800:
    balance -= 800
```

Возможна логика:

```text
Thread A: balance >= 800? → Да
Thread B: balance >= 800? → Да

Thread A: снять 800
Thread B: снять 800
```

Хотя денег было только 1000.

Здесь проблема не только в переменной `balance`, а в том, что операция:

```text
проверить условие
      +
изменить состояние
```

должна быть согласованной.

---

# 8. Race Condition и GIL

Очень частый вопрос:

> «Если в CPython есть GIL, почему вообще возникает Race Condition?»

Потому что **GIL не является заменой синхронизации приложения**.

GIL ограничивает одновременное выполнение Python bytecode в обычной конфигурации CPython, но не гарантирует корректность произвольной последовательности операций над состоянием программы.

Схема:

```text
GIL
 │
 └── контролирует выполнение Python bytecode

Lock
 │
 └── контролирует доступ приложения
     к критической секции
```

Поэтому:

```python
counter += 1
```

нельзя автоматически считать безопасной бизнес-операцией только из-за наличия GIL.

---

# 9. Race Condition ≠ Data Race

Эти понятия близкие, но их полезно разделять.

### Race Condition

Более широкое понятие:

> Результат зависит от порядка конкурентных событий.

### Data Race

Более узкая ситуация:

> Несколько потоков/процессов конкурентно обращаются к одной области памяти, как минимум один доступ является записью, и между ними нет необходимой синхронизации.

Упрощённо:

```text
Race Condition
│
├── Data Race
│
└── Другие ситуации,
    где важен порядок событий
```

Поэтому:

> **Каждый Data Race может приводить к Race Condition, но Race Condition не обязательно является Data Race.**

Например, проблема может быть связана с неправильным порядком действий над несколькими независимыми объектами или событиями, даже если нет классического конфликта записи одной ячейки памяти.

---

# 10. Пример Race Condition без Data Race

Представим систему:

```text
Thread A:
    проверить → операция

Thread B:
    проверить → операция
```

Проблема может возникнуть из-за того, что:

```text
A проверил состояние
B изменил состояние
A продолжил работу
```

То есть ошибка связана с **неправильным порядком событий**, а не обязательно с одновременной записью одной переменной.

---

# 11. Другие способы устранения

`Lock` — не единственный вариант.

В зависимости от задачи используются:

```text
Synchronization
│
├── Lock
├── RLock
├── Semaphore
├── Condition
├── Event
├── Barrier
└── Queue
```

Иногда лучший способ — вообще отказаться от общего изменяемого состояния.

Например:

```text
❌ Shared mutable state

Thread 1 ──┐
Thread 2 ──┼──> shared object
Thread 3 ──┘
```

против:

```text
✅ Message passing

Thread 1 ──> Queue ──> Worker
Thread 2 ──> Queue ──> Worker
Thread 3 ──> Queue ──> Worker
```

`Queue` позволяет организовать безопасный обмен данными между потоками и уменьшить количество прямых взаимодействий с shared state.

---

# 12. Почему Lock тоже нужно использовать правильно

Можно защитить всё приложение одним огромным lock:

```python
with lock:
    # очень много кода
```

Но это может уничтожить преимущества конкурентного выполнения.

Получится:

```text
Thread 1 ── LOCK ──────────────── UNLOCK
Thread 2       WAIT ──────────────┘
Thread 3       WAIT ──────────────┘
```

Поэтому критическую секцию стараются делать **как можно меньше**, сохраняя при этом необходимую атомарность операции.

---

# 13. Deadlock

Синхронизация сама создаёт новые классы проблем.

Например:

```text
Thread 1:
    Lock A
    ↓
    ждёт Lock B

Thread 2:
    Lock B
    ↓
    ждёт Lock A
```

Получается:

```text
A → ждёт B
B → ждёт A
```

Никто не может продолжить.

Это называется **Deadlock**.

Поэтому при использовании нескольких блокировок нужно внимательно проектировать порядок их захвата.

# 🎤 Вопросы на собеседовании

### Что такое Race Condition?

Ситуация, когда результат конкурентной программы зависит от порядка выполнения операций нескольких потоков или процессов.

### Почему возникает Race Condition?

Обычно из-за конкурентного доступа к состоянию и отсутствия необходимой синхронизации или гарантированного порядка операций.

### Приведи простой пример.

Два потока одновременно увеличивают общий `counter`. Они могут оба прочитать старое значение и затем записать одинаковый результат, потеряв одно обновление.

### Что такое критическая секция?

Участок кода, работающий с общим состоянием, который должен выполняться согласованно относительно других конкурентных операций.

### Как исправить Race Condition?

Например, использовать `Lock` для защиты критической секции. Также можно использовать `Queue`, другие примитивы синхронизации или изменить архитектуру так, чтобы уменьшить shared mutable state.

### GIL устраняет Race Condition?

Нет.

### Race Condition и Data Race — одно и то же?

Нет. Race Condition — более широкое понятие. Data Race — конкретный вид конкурентной проблемы, связанный с конфликтующим доступом к общей памяти без необходимой синхронизации.

### Может ли Race Condition возникнуть без нескольких потоков?

Да. Она может возникать в любой конкурентной системе, например между процессами, асинхронными задачами или другими конкурентными событиями.

### Что такое Lost Update?

Ситуация, когда одно изменение общего состояния теряется из-за конкурентного выполнения операций.

Например:

```text
A прочитал 0
B прочитал 0
A записал 1
B записал 1

Ожидалось: 2
Получили: 1
```

## 🧠 Формула для собеседования

> **Race Condition = результат зависит от порядка конкурентных операций.**
>
> Частый источник:
>
> **Shared Mutable State → Concurrent Access → неправильный interleaving → Race Condition.**
>
> Решение:
>
> **синхронизация (`Lock`, `RLock`, `Semaphore`, `Queue` и т.д.) или уменьшение shared mutable state.**
>
> И главное:
>
> **Race Condition ≠ Data Race ≠ GIL.**
