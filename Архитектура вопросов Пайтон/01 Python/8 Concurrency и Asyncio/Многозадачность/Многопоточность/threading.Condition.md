# 🧵 threading.Condition — условные переменные в многопоточности Python

## 🎤 Короткий ответ

**`threading.Condition`** — примитив синхронизации потоков, который позволяет одним потокам ожидать изменения общего состояния, а другим — уведомлять их об этом.

Он объединяет блокировку (`Lock` или `RLock`) и механизм ожидания уведомлений.

Основные методы:

- `wait()` — временно освобождает блокировку и переводит поток в ожидание.
- `notify()` — пробуждает один ожидающий поток по умолчанию.
- `notify_all()` — пробуждает все ожидающие потоки.
- `wait_for()` — ожидает выполнения заданного условия.

`Condition` используется, когда поток должен продолжить работу только после изменения определённого состояния.

## 🗣️ Ответ на собеседовании

`threading.Condition` — это механизм синхронизации потоков, который позволяет ожидать выполнения определённого условия без постоянной проверки состояния.

Например, есть поток-производитель, который добавляет данные в общий буфер, и поток-потребитель, который должен дождаться появления данных.

Потребитель захватывает блокировку и проверяет буфер. Если данных нет, вызывает `condition.wait()`. Этот метод освобождает блокировку и блокирует текущий поток до уведомления.

Производитель захватывает ту же блокировку, добавляет данные и вызывает `notify()`.

После уведомления потребитель снова захватывает блокировку, проверяет состояние и продолжает работу.

Важный нюанс: `notify()` не освобождает блокировку автоматически. Поэтому пробуждённый поток сможет продолжить работу только после её освобождения производителем.

Обычно `Condition` используется с циклом `while` или методом `wait_for()`, поскольку уведомление не гарантирует, что нужное условие действительно выполнено.

## 📚 Разбор поглубже

### 1. Зачем нужен Condition

Представим два потока:

- **Producer** — производитель, который добавляет данные.
- **Consumer** — потребитель, который обрабатывает данные.

Потребитель должен дождаться, пока производитель добавит элемент в общий список.

Без `Condition` можно использовать постоянную проверку:

```python
import threading
import time


data = []


def consumer():
    while not data:
        time.sleep(0.1)

    print("Получено:", data.pop())


def producer():
    time.sleep(2)
    data.append("Сообщение")


thread1 = threading.Thread(target=consumer)
thread2 = threading.Thread(target=producer)

thread1.start()
thread2.start()

thread1.join()
thread2.join()
```

Такой подход называется **polling** — периодическая проверка состояния.

Проблемы:

- Поток регулярно просыпается для проверки.
- Между появлением данных и обработкой возникает задержка.
- Нет полноценной синхронизации доступа к общему списку.
- При большом количестве потоков увеличивается количество лишних проверок.

`Condition` решает эту задачу через ожидание уведомления.

### 2. Простой пример threading.Condition

```python
import threading
import time


condition = threading.Condition()
data = []


def consumer():
    with condition:
        condition.wait_for(lambda: bool(data))

        item = data.pop()
        print(f"Получено: {item}")


def producer():
    time.sleep(2)

    with condition:
        data.append("Сообщение")

        print("Данные добавлены")

        condition.notify()


thread1 = threading.Thread(target=consumer)
thread2 = threading.Thread(target=producer)

thread1.start()
thread2.start()

thread1.join()
thread2.join()
```

Результат:

```text
Данные добавлены
Получено: Сообщение
```

**Разбор логики:**

1. Создаём общий объект `Condition`.
2. Потребитель захватывает блокировку через `with condition`.
3. `wait_for()` проверяет, есть ли данные.
4. Если список пустой, поток освобождает блокировку и переходит в ожидание.
5. Производитель захватывает блокировку.
6. Добавляет сообщение в список.
7. Вызывает `notify()`.
8. Освобождает блокировку при выходе из `with`.
9. Потребитель снова захватывает блокировку.
10. Проверяет условие и забирает элемент.

**Главная идея:** поток не должен постоянно проверять данные. Он может ожидать уведомления об изменении состояния.

### 3. Что происходит под капотом

Упрощённая схема:

```text

                    |

             condition.wait()
                    |

                    |

              Блокируется
                    |

                    |                  |

                    |           Захватывает Lock
                    |                  |
                    |                  v
                    |           Добавляет данные
                    |                  |
                    |                  v
                    |              notify()

             Продолжает работу
```

Важный момент:

**`wait()` атомарно освобождает связанную блокировку и переходит к ожиданию уведомления.**

При использовании стандартного `RLock` механизм `Condition` корректно освобождает его даже при рекурсивном захвате и затем восстанавливает состояние блокировки.

### 4. Основные методы Condition

| Метод | Назначение |
|---|---|
| `acquire()` | Захватить блокировку |
| `release()` | Освободить блокировку |
| `wait(timeout=None)` | Ожидать уведомления |
| `wait_for(predicate, timeout=None)` | Ожидать выполнения условия |
| `notify(n=1)` | Уведомить до `n` ожидающих потоков |
| `notify_all()` | Уведомить все ожидающие потоки |

Для операций `wait()`, `notify()` и `notify_all()` необходимо владеть связанной блокировкой.

Поэтому используется:

```python
with condition:
    ...
```

### 5. wait() — ожидание уведомления

Пример:

```python
with condition:
    condition.wait()
```

Когда поток вызывает `wait()`:

1. Освобождает блокировку.
2. Блокируется в ожидании уведомления или таймаута.
3. Перед возвращением снова захватывает блокировку.

Однако `wait()` не проверяет бизнес-условие самостоятельно.

Поэтому правильно использовать цикл:

```python
with condition:
    while not data:
        condition.wait()

    item = data.pop()
```

Почему именно `while`, а не `if`?

Потому что после уведомления:

- Другой поток мог первым забрать данные.
- Состояние могло снова измениться.
- Возможно пробуждение без выполнения нужного условия.

Поэтому после каждого пробуждения необходимо повторно проверять состояние.

### 6. wait_for() — ожидание условия

Метод `wait_for()` упрощает код.

Вместо:

```python
with condition:
    while not data:
        condition.wait()
```

Можно написать:

```python
with condition:
    condition.wait_for(lambda: bool(data))
```

`lambda: bool(data)` — предикат, то есть функция, возвращающая `True` или `False`.

Если условие ложно, поток ожидает уведомления.

После пробуждения условие проверяется повторно.

Можно ожидать более сложное состояние:

```python
with condition:
    condition.wait_for(
        lambda: len(data) >= 5
    )
```

Здесь поток продолжит работу, когда в списке окажется минимум пять элементов.

### 7. notify() vs notify_all()

**`notify()`** пробуждает один ожидающий поток по умолчанию:

```python
with condition:
    data.append("Новый элемент")
    condition.notify()
```

**`notify_all()`** пробуждает все ожидающие потоки:

```python
with condition:
    state["ready"] = True
    condition.notify_all()
```

Разница:

| Метод | Поведение |
|---|---|
| `notify()` | Уведомить один ожидающий поток |
| `notify(3)` | Уведомить до трёх ожидающих потоков |
| `notify_all()` | Уведомить все ожидающие потоки |

**Важно:** `notify()` не освобождает блокировку.

Пробуждённый поток должен дождаться, пока текущий владелец освободит блокировку.

Кроме того, уведомления не накапливаются. Если вызвать `notify()` до того, как поток начал ожидание, уведомление не сохранится для будущего вызова `wait()`.

Поэтому состояние всегда проверяется отдельно.

### 8. Condition vs Lock vs RLock

**Lock** обеспечивает взаимное исключение — только один поток может владеть блокировкой.

```python
lock = threading.Lock()

with lock:
    shared_counter += 1
```

**RLock** — реентерабельная блокировка. Один и тот же поток может захватить её несколько раз, но должен освободить столько же раз.

**Condition** использует блокировку и дополнительно позволяет потокам ожидать изменения состояния.

```python
condition = threading.Condition()
```

По умолчанию `threading.Condition()` создаёт внутренний `RLock`.

Можно передать собственную блокировку:

```python
lock = threading.Lock()

condition = threading.Condition(lock)
```

Это полезно, если несколько компонентов должны синхронизировать доступ к одному общему состоянию через одну и ту же блокировку.

### 9. Condition vs Event vs Semaphore vs Queue

| Примитив | Для чего нужен |
|---|---|
| `threading.Lock` | Защита общего ресурса |
| `threading.RLock` | Повторный захват блокировки тем же потоком |
| `threading.Event` | Сигнал о наступлении события |
| `threading.Condition` | Ожидание изменения общего состояния |
| `threading.Semaphore` | Ограничение количества потоков в защищённом участке |
| `queue.Queue` | Потокобезопасная передача элементов |

**Condition vs Event**

`Event` хранит внутренний флаг.

```python
event = threading.Event()

event.set()
event.wait()
```

Если флаг уже установлен, `wait()` сразу вернётся.

`Condition` не хранит отдельный флаг готовности, а позволяет проверять произвольное общее состояние под блокировкой.

**Condition vs Queue**

Если требуется просто передавать элементы между потоками, обычно лучше использовать `queue.Queue`.

```python
from queue import Queue

queue = Queue()

queue.put("Сообщение")

item = queue.get()
```

`Queue` уже реализует необходимую синхронизацию, в том числе с использованием условных переменных.

### 10. Producer–Consumer с несколькими потоками

Рассмотрим пример с двумя потребителями.

```python
import threading
import time
from collections import deque


condition = threading.Condition()
buffer = deque()
finished = False


def producer():
    global finished

    for number in range(5):
        time.sleep(0.5)

        with condition:
            buffer.append(number)
            print(f"Добавлено: {number}")

            condition.notify()

    with condition:
        finished = True
        condition.notify_all()


def consumer(name):
    while True:
        with condition:
            condition.wait_for(
                lambda: bool(buffer) or finished
            )

            if not buffer:
                return

            item = buffer.popleft()

        print(f"{name} обработал {item}")


threads = [
    threading.Thread(target=consumer, args=("A",)),
    threading.Thread(target=consumer, args=("B",)),
    threading.Thread(target=producer),
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()
```

Здесь:

- Производитель добавляет пять чисел.
- Два потребителя ожидают появления элементов.
- `notify()` пробуждает ожидающего потребителя.
- После завершения производства устанавливается `finished = True`.
- `notify_all()` позволяет всем оставшимся потребителям завершить работу.

Почему условие выглядит так?

```python
lambda: bool(buffer) or finished
```

Потому что потребитель должен проснуться не только при появлении данных, но и при окончании производства.

Иначе после обработки последнего элемента он может навсегда остаться в ожидании.

### 11. Таймауты

`threading.Condition` поддерживает таймаут непосредственно в методах `wait()` и `wait_for()`.

```python
import threading


condition = threading.Condition()
ready = False


with condition:
    success = condition.wait_for(
        lambda: ready,
        timeout=3,
    )

    if success:
        print("Условие выполнено")
    else:
        print("Время ожидания истекло")
```

Если за три секунды `ready` не станет `True`, `wait_for()` вернёт ложное значение.

При этом блокировка будет захвачена на момент возврата из `wait_for()` и освободится при выходе из `with`.

### 12. Condition и GIL

Частый вопрос: зачем нужен `Condition`, если в CPython есть GIL?

**GIL (Global Interpreter Lock)** в обычных сборках CPython ограничивает одновременное выполнение Python-байткода несколькими потоками.

Но GIL не заменяет синхронизацию общего состояния.

Например:

```python
if not data:
    condition.wait()
```

Между логическими операциями состояние может измениться из-за переключения потоков.

`Condition` обеспечивает согласованную проверку состояния и ожидание уведомлений с использованием блокировки.

Кроме того, во время многих блокирующих I/O-операций GIL освобождается.

В современных версиях Python существуют также free-threaded сборки CPython, где GIL может быть отключён. Правильная синхронизация остаётся необходимой независимо от наличия GIL.

### 13. threading.Condition vs asyncio.Condition

Это два похожих инструмента, но они предназначены для разных моделей конкурентности.

| Характеристика | threading.Condition | asyncio.Condition |
|---|---|---|
| Используется для | Потоков ОС | Асинхронных задач |
| Ожидание | `condition.wait()` | `await condition.wait()` |
| Контекстный менеджер | `with` | `async with` |
| Блокирует поток | Да | Нет, приостанавливает задачу |
| Потокобезопасность | Предназначен для потоков | Не потокобезопасен |
| Типичный сценарий | Многопоточная программа | Async Backend |

**threading:**

```python
with condition:
    condition.wait()
```

**asyncio:**

```python
async with condition:
    await condition.wait()
```

Главное отличие — способ ожидания.

В `threading` ожидающий поток блокируется.

В `asyncio` приостанавливается корутина, а Event Loop может выполнять другие задачи.

### 14. Где применяется в Backend

`threading.Condition` может использоваться:

- Для координации рабочих потоков.
- Для ожидания появления данных в общем буфере.
- Для управления состоянием потокобезопасного кэша.
- Для реализации собственных пулов ресурсов.
- Для построения низкоуровневых механизмов синхронизации.

Но в обычной Backend-разработке чаще достаточно готовых примитивов:

- `queue.Queue` — передача задач между потоками.
- `ThreadPoolExecutor` — управление пулом потоков.
- `threading.Event` — простой сигнал готовности.
- `asyncio.Condition` — координация асинхронных задач.

`threading.Condition` полезно понимать, даже если в реальном проекте ты редко используешь его напрямую.

### 15. Типичные ошибки

**Ошибка 1. Вызывать wait() без блокировки.**

```python
condition.wait()  # RuntimeError
```

Правильно:

```python
with condition:
    condition.wait()
```

**Ошибка 2. Вызывать notify() без блокировки.**

```python
condition.notify()  # RuntimeError
```

Правильно:

```python
with condition:
    condition.notify()
```

**Ошибка 3. Использовать if вместо while.**

```python
with condition:
    if not data:
        condition.wait()
```

После пробуждения данные могут отсутствовать.

Надёжнее:

```python
with condition:
    while not data:
        condition.wait()
```

**Ошибка 4. Считать notify() немедленной передачей управления другому потоку.**

Пробуждённый поток не сможет продолжить выполнение защищённого участка, пока не получит блокировку.

**Ошибка 5. Считать уведомления сохраняемыми событиями.**

`Condition` не хранит историю вызовов `notify()`.

**Ошибка 6. Забывать о завершении потребителей.**

Если производитель больше не создаёт данные, ожидающие потоки могут зависнуть без сигнала завершения.

**Ошибка 7. Держать блокировку во время долгой обработки.**

Это препятствует другим потокам получать доступ к общему состоянию.

Лучше забрать элемент под блокировкой, освободить её и затем выполнить длительную обработку.

## 🎤 Вопросы на собеседовании

**1. Что такое threading.Condition?**

Примитив синхронизации, который объединяет блокировку и механизм ожидания уведомлений об изменении общего состояния.

**2. Чем Condition отличается от Lock?**

`Lock` обеспечивает взаимное исключение, а `Condition` дополнительно позволяет ожидать изменения состояния и уведомлять потоки.

**3. Что делает condition.wait()?**

Освобождает блокировку, блокирует текущий поток до уведомления или таймаута, а перед возвращением снова захватывает блокировку.

**4. Что делает condition.notify()?**

Пробуждает один ожидающий поток по умолчанию, но не освобождает блокировку.

**5. Чем notify_all() отличается от notify()?**

`notify_all()` пробуждает всех ожидающих потоков, а `notify()` — заданное количество, по умолчанию один.

**6. Почему wait() вызывают в цикле while?**

Потому что после пробуждения условие может оставаться ложным, поэтому его необходимо повторно проверить.

**7. Что делает wait_for()?**

Повторно проверяет предикат и ожидает уведомлений, пока условие не выполнится или не истечёт таймаут.

**8. Какую блокировку Condition использует по умолчанию?**

`threading.RLock`.

**9. Чем threading.Condition отличается от asyncio.Condition?**

Первый синхронизирует потоки и блокирует ожидающий поток, второй координирует асинхронные задачи без блокировки Event Loop.

**10. Зачем Condition, если есть GIL?**

GIL не гарантирует корректность последовательностей операций с общим состоянием и не заменяет явную синхронизацию.

**11. Когда лучше использовать queue.Queue?**

Когда нужно передавать элементы между потоками без ручной реализации буфера и механизма уведомлений.

**12. Можно ли использовать Condition между процессами?**

`threading.Condition` предназначен для потоков одного процесса. Для межпроцессной синхронизации используют соответствующие примитивы `multiprocessing` или внешние механизмы.

## 🧪 Мини-задание

Реализуй два потока с помощью `threading.Condition`.

**Производитель:** добавляет числа от 1 до 10 в общий список с интервалом 0,5 секунды.

**Потребитель:** ожидает, пока в списке накопится минимум три элемента, затем забирает их и выводит на экран. После завершения производителя должен обработать оставшиеся элементы и корректно завершиться.

Вопросы для самопроверки:

1. Почему `wait()` освобождает блокировку?
2. Почему `notify()` не освобождает блокировку самостоятельно?
3. Что произойдёт, если производитель завершится, а потребитель не получит сигнал об окончании работы?

**Главное, что нужно запомнить:** `threading.Condition` = блокировка + ожидание изменения состояния + уведомления между потоками. Это механизм координации, а не передачи данных.
