# 🧠 Shared Memory

## 🎤 Короткий ответ

**Shared Memory (общая память)** — это область памяти, к которой могут обращаться несколько потоков или процессов.

В случае **потоков одного процесса** общая память является естественным свойством модели: потоки видят объекты и данные процесса. Именно поэтому они могут напрямую обмениваться данными, но одновременно возникает риск **[[Race Condition]]** и **[[Data Race]]**.

У процессов память обычно изолирована. Если процессам нужно работать с одной областью памяти, используются специальные механизмы **[[Shared Memory]]**, например `multiprocessing.shared_memory`.

---

## 🗣️ Ответ на собеседовании

> Shared Memory — это память, доступная нескольким конкурентным участникам выполнения.
>
> Для потоков одного процесса общая память является естественной частью модели: потоки разделяют адресное пространство процесса, поэтому один поток может работать с объектом, созданным другим потоком.
>
> Это удобно для обмена данными, но создаёт проблему синхронизации: если несколько потоков одновременно изменяют общий объект, могут возникнуть [[Race Condition]] и [[Data Race]].
>
> У процессов память обычно изолирована, поэтому они не могут просто взять и обратиться к переменной другого процесса. Если нужно эффективно обмениваться большими объёмами данных, можно использовать специальные механизмы shared memory, например `multiprocessing.shared_memory`.
>
> Главный компромисс такой: Shared Memory обеспечивает быстрый обмен данными, но требует аккуратного управления конкурентным доступом.

# 📚 Разбор поглубже

## 1. Что такое память процесса

Когда запускается программа, операционная система выделяет процессу собственное **виртуальное адресное пространство**.

Упрощённо:

```text
Process
┌──────────────────────────┐
│ Code                     │
│ Heap                     │
│ Stack                    │
│ Global data              │
│ Python objects           │
└──────────────────────────┘
```

Процесс владеет своим адресным пространством.

Другой процесс получает другое:

```text
Process A                 Process B
┌──────────────┐          ┌──────────────┐
│ Memory A     │          │ Memory B     │
│              │          │              │
└──────────────┘          └──────────────┘
```

Поэтому обычная переменная процесса A не становится автоматически доступной процессу B.

---

# 2. Shared Memory у потоков

Главная особенность threading:

```text
Process
│
├── Thread 1
├── Thread 2
└── Thread 3
```

Все эти потоки работают внутри одного адресного пространства процесса:

```text
             Process Memory
          ┌─────────────────┐
          │ Python objects   │
          │ global state     │
          │ heap             │
          └─────────────────┘
             ↑      ↑     ↑
             │      │     │
          Thread 1 Thread 2 Thread 3
```

Поэтому:

```python
counter = 0
```

может быть доступен нескольким потокам.

Это и есть один из фундаментальных механизмов многопоточности.

---

# 3. Что именно разделяют потоки

Важно не говорить:

> «У потоков полностью одинаковая память».

Точнее:

> **Потоки одного процесса разделяют адресное пространство и большую часть ресурсов процесса, но каждый поток имеет собственный стек и состояние выполнения.**

Упрощённо:

```text
Process
│
├── Shared
│   ├── Heap
│   ├── Global data
│   ├── Objects
│   └── Resources
│
├── Thread 1
│   └── own stack / execution state
│
├── Thread 2
│   └── own stack / execution state
│
└── Thread 3
    └── own stack / execution state
```

---

# 4. Почему Shared Memory удобна

Главное преимущество — потоки могут напрямую обмениваться данными.

Например:

```python
result = []

def worker():
    result.append("done")
```

Другой поток может получить доступ к тому же объекту:

```python
print(result)
```

Не требуется специальный IPC-механизм только для того, чтобы передать объект между потоками.

Условно:

```text
Thread 1
   │
   ├── writes data
   │
   ▼
Shared Memory
   │
   ▼
Thread 2
   │
   └── reads data
```

# 5. Главная проблема — Shared Mutable State

Если общий объект можно изменять:

```python
users = []
```

и несколько потоков делают:

```python
users.append(...)
```

появляется конкурентный доступ к общему состоянию.

```text
Thread 1 ──┐
Thread 2 ──┼──> users
Thread 3 ──┘
```

Поэтому:

```text
Shared Memory
      ↓
Shared Mutable State
      ↓
Concurrent Access
      ↓
Race Condition / Data Race
```

Именно поэтому Shared Memory тесно связана с темами:

* Race Condition;
* Data Race;
* Lock;
* thread safety;
* synchronization.

---

# 6. Shared Memory ≠ Shared Mutable State

Эти понятия нужно различать.

### Shared Memory

Факт:

> Несколько участников имеют доступ к одной области памяти.

### Shared Mutable State

Более конкретная ситуация:

> В этой общей памяти находится изменяемое состояние, которое участники могут менять.

Например:

```text
Shared Memory
│
├── immutable configuration
├── constants
└── mutable counter  ← Shared Mutable State
```

Сам факт наличия общей памяти не означает наличие Race Condition.

Проблемы возникают прежде всего при неконтролируемом конкурентном изменении состояния.

---

# 7. Shared Memory и процессы

Теперь важное отличие.

### Потоки

```text
Process
├── Thread 1 ──┐
├── Thread 2 ──┼── Shared Address Space
└── Thread 3 ──┘
```

### Процессы

```text
Process A              Process B
┌───────────┐          ┌───────────┐
│ Memory A  │          │ Memory B  │
└───────────┘          └───────────┘
```

По умолчанию процессы **не разделяют обычную память**.

Например:

```python
counter = 0
```

в Process A и:

```python
counter = 0
```

в Process B — это два разных объекта в разных адресных пространствах.

---

# 8. Почему процессы изолированы

Изоляция памяти — одно из фундаментальных отличий процессов от потоков.

```text
Process A
┌────────────────┐
│ Memory A       │
└────────────────┘

       X

Process B
┌────────────────┐
│ Memory B       │
└────────────────┘
```

Если процесс A изменяет:

```python
counter = 100
```

это не изменяет автоматически:

```python
counter
```

в процессе B.

Для обмена данными нужны специальные механизмы **IPC (Inter-Process Communication)**.

---

# 9. IPC

**IPC — Inter-Process Communication** — механизмы взаимодействия процессов.

Основные варианты:

```text
IPC
│
├── Queue
├── Pipe
├── Shared Memory
├── Socket
└── другие IPC-механизмы
```

Shared Memory отличается тем, что процессы получают доступ к одной области памяти.

```text
Process A ──┐
            │
            ▼
      Shared Memory
            ▲
            │
Process B ──┘
```

# 10. `multiprocessing.shared_memory`

В Python есть специальный модуль:

```python
from multiprocessing import shared_memory
```

Он позволяет нескольким процессам работать с общей областью памяти.

Упрощённый пример:

```python
from multiprocessing import shared_memory


shm = shared_memory.SharedMemory(
    create=True,
    size=10
)

shm.buf[0] = 42

print(shm.buf[0])

shm.close()
shm.unlink()
```

Здесь:

```python
shm.buf
```

представляет буфер общей памяти.

Другой процесс, имеющий имя этого shared memory segment, может подключиться к нему.

---

# 11. Почему Shared Memory может быть быстрее IPC через сериализацию

Представим передачу большого массива данных.

Один подход:

```text
Process A
   ↓
serialize
   ↓
copy
   ↓
IPC
   ↓
deserialize
   ↓
Process B
```

Это может создавать накладные расходы.

Shared Memory позволяет организовать:

```text
Process A ──┐
            ▼
      Shared Memory
            ▲
            └── Process B
```

Данные находятся в общей области, и процессы могут работать с ней напрямую.

Поэтому shared memory особенно интересна для больших объёмов данных, когда копирование и сериализация становятся дорогими.

---

# 12. Но Shared Memory не решает синхронизацию

Это очень важный момент.

Shared Memory решает:

> **Как предоставить нескольким процессам доступ к одним данным?**

Но не решает автоматически:

> **Как сделать конкурентный доступ к этим данным безопасным?**

Например:

```text
Process A ── WRITE ──┐
                     ├── Shared Memory
Process B ── WRITE ──┘
```

Всё ещё может возникнуть конфликт.

Поэтому:

```text
Shared Memory
      +
Concurrent Access
      ↓
нужна синхронизация
```

Можно использовать соответствующие примитивы синхронизации или архитектуру, минимизирующую конкурентные изменения.

---

# 13. Shared Memory vs Queue

Это важное архитектурное различие.

### Shared Memory

```text
Process A ──┐
            ├── Shared Data
Process B ──┘
```

Участники работают непосредственно с общими данными.

### Queue

```text
Process A ──> Queue ──> Process B
```

Данные передаются между участниками.

Получаем два разных подхода:

```text
Shared Memory
→ shared state

Queue
→ message passing
```

Message passing часто проще с точки зрения конкурентности, потому что уменьшает прямой доступ к общему изменяемому состоянию.

# 14. Shared Memory vs обычная память процесса

|               | Обычная память процесса             | Shared Memory                               |
| ------------- | ----------------------------------- | ------------------------------------------- |
| Доступ        | один процесс                        | несколько процессов                         |
| Изоляция      | да                                  | намеренно нарушается для выбранной области  |
| Обмен         | IPC                                 | общая область памяти                        |
| Сериализация  | часто требуется для передачи данных | может быть не нужна для самой общей области |
| Синхронизация | зависит от задачи                   | нужна при конкурентных изменениях           |

---

# 15. Shared Memory vs Threading

|                 | Threading                       | Multiprocessing + Shared Memory                 |
| --------------- | ------------------------------- | ----------------------------------------------- |
| Единый процесс  | да                              | нет                                             |
| Общая память    | естественно                     | создаётся специально                            |
| Изоляция        | низкая                          | выше                                            |
| Передача данных | напрямую                        | через shared memory / IPC                       |
| Синхронизация   | нужна при shared mutable state  | нужна при общей памяти                          |
| CPU parallelism | ограничен GIL в обычном CPython | процессы могут выполнять Python-код параллельно |

# 16. Практический пример

Представим, что несколько worker-процессов обрабатывают изображения.

Есть большой массив:

```text
Image data
    ↓
Shared Memory
```

Вместо:

```text
Process 1
    ↓
copy image

Process 2
    ↓
copy image

Process 3
    ↓
copy image
```

можно организовать:

```text
             Shared Memory
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
    Process 1 Process 2 Process 3
```

Все процессы работают с одной областью данных.

Это может быть полезно, когда копирование больших объёмов данных становится узким местом.

# 17. Главное различие: Thread и Process

Это нужно уметь объяснить на собеседовании:

```text
Thread
│
└── находится внутри Process
    │
    └── автоматически видит
        адресное пространство процесса
```

А:

```text
Process
│
└── имеет собственное
    адресное пространство
```

Поэтому:

```text

→ shared memory по умолчанию

Processes
→ isolated memory по умолчанию
→ shared memory только через специальные механизмы
```

# 🎤 Вопросы на собеседовании

### Что такое Shared Memory?

Область памяти, доступная нескольким конкурентным участникам выполнения.

### Есть ли Shared Memory у потоков?

Да. Потоки одного процесса разделяют адресное пространство процесса.

### Есть ли Shared Memory у процессов?

По умолчанию нет. Процессы имеют изолированные адресные пространства. Общую память нужно создавать специальными механизмами.

### Почему Shared Memory может быть опасна?

Потому что несколько участников могут одновременно изменять одни и те же данные, что приводит к Race Condition и Data Race.

### Shared Memory сама решает проблему синхронизации?

Нет. Она предоставляет общий доступ к данным, но не определяет, как этот доступ синхронизировать.

### Как процессы могут использовать Shared Memory в Python?

Например, через:

```python
multiprocessing.shared_memory
```

### Что такое IPC?

**Inter-Process Communication** — механизмы взаимодействия между процессами: Queue, Pipe, Shared Memory, sockets и другие.

### Чем Shared Memory отличается от Queue?

Shared Memory предоставляет общий state, а Queue организует передачу сообщений/данных между участниками.

### Почему Shared Memory может быть эффективнее передачи через Queue?

Для больших объёмов данных можно избежать части копирования и сериализации, работая непосредственно с общей областью памяти.

### Shared Memory и Shared Mutable State — одно и то же?

Нет.

**Shared Memory** — механизм/факт общего доступа к памяти.

**Shared Mutable State** — изменяемое состояние, которым совместно пользуются несколько конкурентных участников.

---

## 🧠 Формула для собеседования

> **Shared Memory = несколько конкурентных участников имеют доступ к одной области памяти.**
>
> Для потоков:
>
> **один Process → общее адресное пространство → Shared Memory естественна.**
>
> Для процессов:
>
> **разные Process → изолированная память → Shared Memory создаётся специально.**
>
> Главная проблема:
>
> **Shared Memory + Mutable State + Concurrent Access → Race Condition / Data Race.**
>
> Поэтому:
>
> **Shared Memory отвечает за доступ к общим данным, а Synchronization — за безопасный доступ к ним.**
