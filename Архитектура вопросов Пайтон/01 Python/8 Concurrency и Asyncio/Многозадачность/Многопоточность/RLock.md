# 🔒 RLock в Python

## 🎤 Короткий ответ

**RLock (`Reentrant Lock`)** — это повторно захватываемая блокировка. Один и тот же поток может несколько раз захватить один `RLock`, не заблокировав сам себя.

При каждом `acquire()` увеличивается внутренний счётчик захватов, а `release()` уменьшает его. Блокировка становится доступной другим потокам только после соответствующего количества `release()`.

Главное отличие от обычного `Lock`: **`Lock` нельзя повторно захватить тем же потоком, а `RLock` можно.**

---

## 🗣️ Ответ на собеседовании

`RLock` — это reentrant lock, то есть повторно захватываемая блокировка.

Обычный `Lock` может быть захвачен потоком один раз. Если тот же поток попытается захватить его повторно, он заблокируется сам на себе.

`RLock` хранит владельца блокировки и количество её захватов. Поэтому один и тот же поток может вызвать `acquire()` несколько раз. Для полного освобождения нужно вызвать соответствующее количество `release()`.

Это полезно, когда методы одного объекта используют общую блокировку и один защищённый метод вызывает другой защищённый метод. В таком случае с обычным `Lock` можно получить самоблокировку, а `RLock` позволяет безопасно повторно войти в критическую секцию.

## 📚 Разбор поглубже

### 1. Что такое RLock

`RLock` — примитив синхронизации из `threading`:

```python
import threading

lock = threading.RLock()
```

Его основная особенность — **reentrant**, то есть повторный захват той же блокировки владельцем разрешён.

Условно внутри есть:

```text
RLock
├── owner = Thread A
└── count = 2
```

Это означает:

> Thread A захватил блокировку два раза.

---

### 2. Проблема обычного Lock

Рассмотрим:

```python
import threading

lock = threading.Lock()

def outer():
    with lock:
        inner()

def inner():
    with lock:
        print("hello")
```

Происходит:

```text
Thread A
   │
   ├── outer()
   │      │
   │      └── acquire() → Lock захвачен
   │
   └── inner()
          │
          └── acquire() → ждём Lock
```

Но блокировка уже принадлежит **этому же потоку**.

Получается самоблокировка:

```text
Thread A
   ↓
держит Lock
   ↓
пытается получить Lock снова
   ↓
ждёт
   ↓
никто другой не может освободить Lock
   ↓
DEADLOCK
```

---

### 3. RLock решает эту проблему

С `RLock`:

```python
import threading

lock = threading.RLock()

def outer():
    with lock:
        inner()

def inner():
    with lock:
        print("hello")
```

Теперь:

```text
Thread A

outer()
  │
  ├── acquire() → count = 1
  │
  └── inner()
        │
        └── acquire() → count = 2
```

После выхода:

```text
inner()
  └── release() → count = 1

outer()
  └── release() → count = 0
```

Только после `count = 0` блокировка становится доступной другим потокам.

---

### 4. Главное правило

Количество `release()` должно соответствовать количеству `acquire()`.

```python
lock.acquire()  # count = 1
lock.acquire()  # count = 2

lock.release()  # count = 1
lock.release()  # count = 0
```

Поэтому безопаснее использовать контекстный менеджер:

```python
with lock:
    ...
```

Если есть вложенный `with`:

```python
with lock:
    with lock:
        ...
```

каждый `with` корректно управляет своим захватом.

---

### 5. Lock vs RLock

| | `Lock` | `RLock` |
|---|---|---|
| Повторный захват тем же потоком | ❌ | ✅ |
| Запоминает владельца | нет такой семантики | ✅ |
| Счётчик захватов | ❌ | ✅ |
| Защита критической секции | ✅ | ✅ |
| Сложнее и тяжелее обычного Lock | ❌ | немного ✅ |
| Типичное применение | простая синхронизация | вложенные вызовы |

---

### 6. Когда использовать RLock

Хороший сценарий — объект, где несколько методов используют одну блокировку:

```python
class BankAccount:
    def __init__(self):
        self.balance = 0
        self.lock = threading.RLock()

    def deposit(self, amount):
        with self.lock:
            self.balance += amount
            self._log_balance()

    def _log_balance(self):
        with self.lock:
            print(self.balance)
```

`deposit()` уже владеет `RLock`, но `_log_balance()` может безопасно захватить его повторно.

---

### 7. RLock не делает код автоматически безопасным

Важно:

> `RLock` защищает только те операции, которые действительно выполняются под этой блокировкой.

Например:

```python
with lock:
    shared_data += 1
```

защищено.

А это:

```python
shared_data += 1
```

в другом месте программы — уже нет.

Кроме того, `RLock` не решает все проблемы синхронизации и не предотвращает логические ошибки в многопоточном коде.

---

### 8. RLock и deadlock

`RLock` предотвращает **самоблокировку одного потока при повторном захвате**, но не устраняет все deadlock.

Например:

```text
Thread A:
Lock 1 → Lock 2

Thread B:
Lock 2 → Lock 1
```

Может возникнуть:

```text
Thread A держит Lock 1 и ждёт Lock 2
Thread B держит Lock 2 и ждёт Lock 1
```

Это классический deadlock между двумя потоками.

`RLock` сам по себе такую ситуацию не решает.

## 🎤 Вопросы на собеседовании

### Что такое RLock?

`RLock` — повторно захватываемая блокировка. Один поток может захватить её несколько раз, а для полного освобождения должен выполнить соответствующее количество `release()`.

### Чем RLock отличается от Lock?

Главное отличие — **reentrancy**. `Lock` нельзя повторно захватить тем же потоком, а `RLock` можно.

### Зачем нужен RLock?

Например, когда один метод под блокировкой вызывает другой метод, который тоже пытается захватить ту же блокировку.

### RLock полностью защищает от deadlock?

Нет. Он предотвращает самоблокировку при повторном захвате одним потоком, но deadlock между несколькими потоками всё равно возможен.

### Почему лучше использовать `with RLock()`?

Контекстный менеджер автоматически вызывает `acquire()` и соответствующий `release()`, поэтому меньше риск неправильно управлять блокировкой.

### Как RLock понимает, когда можно отдать блокировку другому потоку?

Он учитывает **владельца и глубину захвата**. Пока счётчик захватов не станет равен нулю, блокировка остаётся за текущим потоком.
