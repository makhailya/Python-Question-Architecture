# 🔒 Lock

## 🎤 Короткий ответ

**Lock (блокировка)** — механизм синхронизации конкурентных транзакций, который ограничивает одновременный доступ к данным или объектам базы.

Например, две транзакции одновременно изменяют одну строку:

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

Первая транзакция получает блокировку строки. Вторая транзакция при попытке получить несовместимую блокировку будет ждать.

Главная идея:

```text
Transaction A
    ↓
Lock
    ↓
Row / Table
    ↓
Transaction B
    ↓
wait
```

Locks нужны для предотвращения конфликтов при конкурентном доступе и являются частью механизма обеспечения согласованности данных.

---

## 🗣️ Ответ на собеседовании

Lock — это механизм PostgreSQL, который позволяет координировать конкурентный доступ транзакций к данным и объектам базы.

Например, если одна транзакция хочет изменить строку счёта, а другая одновременно хочет изменить ту же строку, PostgreSQL использует блокировки, чтобы корректно сериализовать конфликтующие операции.

Я бы разделял **row-level locks** и **table-level locks**. Например:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

получает блокировку выбранной строки до конца транзакции.

Если другая транзакция пытается получить несовместимую блокировку, она ждёт освобождения первой.

При этом Lock и [[MVCC]] — не одно и то же. PostgreSQL использует [[MVCC]] для изоляции версий строк, а блокировки — для координации конфликтующих операций. Также существуют deadlock'и, когда транзакции ждут блокировки друг друга; PostgreSQL умеет обнаруживать такие ситуации и прерывает одну из транзакций.

# 📚 Разбор поглубже

## 1. Зачем нужны Lock

Представим счёт:

```text
balance = 1000
```

Две транзакции одновременно хотят снять деньги.

```text
Transaction A → снять 700
Transaction B → снять 500
```

Если обе сначала прочитают:

```text
balance = 1000
```

они могут принять решение независимо друг от друга.

Нужна координация конкурентного доступа.

Один из вариантов:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;
```

После получения блокировки другая транзакция не сможет получить несовместимую блокировку этой строки до освобождения первой.

---

# 2. Lock и транзакция

Блокировки обычно связаны с жизненным циклом транзакции.

Например:

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 700
WHERE id = 1;

COMMIT;
```

Упрощённо:

```text
BEGIN
  ↓
получили Lock
  ↓
работаем с данными
  ↓
COMMIT
  ↓
Lock освобождён
```

При `ROLLBACK` блокировка также освобождается.

---

# 3. Row-level Lock

**Row-level lock** блокирует конкретные строки.

Например:

```sql
SELECT *
FROM users
WHERE id = 42
FOR UPDATE;
```

Условно:

```text
users

id=41  → свободна
id=42  → 🔒
id=43  → свободна
```

Другая транзакция может работать с другими строками.

Это существенно отличается от блокировки всей таблицы.

---

# 4. `SELECT ... FOR UPDATE`

Один из важнейших вариантов блокировки строк:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

Смысл:

> Я собираюсь изменить эти строки, поэтому хочу заблокировать их до завершения транзакции.

Типичный сценарий:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

---

# 5. Что произойдёт со второй транзакцией

Допустим:

### Transaction A

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

Получает lock:

```text
row id=1 🔒 A
```

### Transaction B

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

Она будет ждать:

```text
A → lock
B → waiting
```

После:

```sql
COMMIT;
```

в Transaction A:

```text
A → lock released
B → продолжает выполнение
```

---

# 6. Lock ≠ MVCC

Очень важное различие.

### MVCC

Позволяет транзакциям работать с версиями строк:

```text
row version 1
row version 2
row version 3
```

Это основа конкурентного чтения в PostgreSQL.

### Lock

Координирует операции, которые конфликтуют между транзакциями.

Упрощённо:

```text
MVCC
→ какие версии строк я вижу?

Lock
→ кто сейчас блокирует конфликтующую операцию?
```

Это разные механизмы, хотя они работают вместе.

---

# 7. Row-level lock не означает физическую блокировку всей строки для любого чтения

Это важный нюанс.

Если Transaction A выполнила:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

это не означает:

> никто вообще не может прочитать эту строку.

Обычный `SELECT` в PostgreSQL может продолжать читать данные согласно правилам MVCC и выбранному уровню изоляции.

Конфликтуют конкретные типы операций и lock modes.

Поэтому нельзя упрощать до:

```text
LOCK = строка полностью недоступна
```

---

# 8. Основные row-level lock modes

PostgreSQL имеет несколько режимов блокировок строк.

Основные:

```text
FOR UPDATE
FOR NO KEY UPDATE
FOR SHARE
FOR KEY SHARE
```

Упрощённо:

```text
FOR UPDATE
→ наиболее сильная блокировка для обычного изменения строки

FOR NO KEY UPDATE
→ блокировка изменения без изменения ключевых значений

FOR SHARE
→ хотим читать строку с блокировкой

FOR KEY SHARE
→ защищаем ключевые значения от определённых изменений
```

На собеседовании обычно достаточно понимать идею совместимости этих режимов и знать `FOR UPDATE`.

---

# 9. `FOR SHARE`

Например:

```sql
SELECT *
FROM products
WHERE id = 10
FOR SHARE;
```

Транзакция получает разделяемую блокировку строки.

Несколько транзакций могут одновременно получить совместимые share locks.

Но конфликтующие изменения строки будут ждать.

Упрощённо:

```text
Transaction A → SHARE 🔒
Transaction B → SHARE 🔒
Transaction C → UPDATE → wait
```

---

# 10. Table-level Lock

PostgreSQL также блокирует таблицы.

Например:

```sql
LOCK TABLE users IN ACCESS EXCLUSIVE MODE;
```

Теперь блокировка относится к таблице целиком.

```text
users
┌─────────────────┐
│ 🔒 TABLE LOCK   │
│                 │
│ row 1           │
│ row 2           │
│ row 3           │
└─────────────────┘
```

Table-level locks используются самим PostgreSQL для разных операций, в том числе DDL.

---

# 11. Уровни table lock

В PostgreSQL существует несколько режимов table-level lock.

Например:

```text
ACCESS SHARE
ROW SHARE
ROW EXCLUSIVE
SHARE UPDATE EXCLUSIVE
SHARE
SHARE ROW EXCLUSIVE
EXCLUSIVE
ACCESS EXCLUSIVE
```

Они имеют разные правила совместимости.

На практике важно понимать:

```text
более сильная блокировка
        ↓
может конфликтовать
с большим количеством операций
```

`ACCESS EXCLUSIVE` — самый сильный стандартный режим.

---

# 12. Почему обычный SELECT может работать одновременно с UPDATE

Это хороший вопрос на собеседовании.

PostgreSQL использует MVCC.

Например:

```text
Transaction A
UPDATE users
SET name = 'Bob'
WHERE id = 1;
```

При этом обычный:

```sql
SELECT *
FROM users
WHERE id = 1;
```

не обязательно должен ждать завершения UPDATE.

В зависимости от snapshot и уровня изоляции он может увидеть подходящую версию строки.

Поэтому PostgreSQL не работает по модели:

```text
UPDATE → блокируем таблицу → все SELECT ждут
```

MVCC позволяет значительно повысить concurrency.

---

# 13. Lock Contention

**Lock contention** — ситуация, когда несколько транзакций конкурируют за одну и ту же блокировку.

Например:

```text
Transaction A
      ↓
    🔒 row
      ↑
      │
Transaction B → WAIT
      ↑
      │
Transaction C → WAIT
```

Если такие ожидания происходят часто, это может существенно ухудшить производительность.

Причины:

- длинные транзакции;
- слишком крупные критические секции;
- частая работа с одними и теми же строками;
- неправильный порядок блокировок;
- высокая конкуренция.

---

# 14. Deadlock

**Deadlock** — взаимная блокировка.

Например:

### Transaction A

```text
захватила row 1
ждёт row 2
```

### Transaction B

```text
захватила row 2
ждёт row 1
```

Получаем:

```text
A → 🔒 row 1 → ждёт row 2
                         ↑
                         │
B → 🔒 row 2 → ждёт row 1
```

Никто не может продолжить.

---

# 15. Как PostgreSQL решает Deadlock

PostgreSQL умеет обнаруживать deadlock.

После обнаружения он прерывает одну из транзакций.

Приложение получает ошибку и обычно должно:

1. откатить транзакцию;
2. при необходимости повторить операцию.

Поэтому приложение должно быть готово к transient database errors, включая deadlock.

---

# 16. Как уменьшать вероятность Deadlock

Один из основных методов:

> Брать блокировки в одинаковом порядке.

Плохо:

```text
Transaction A:
row 1 → row 2

Transaction B:
row 2 → row 1
```

Лучше:

```text
Transaction A:
row 1 → row 2

Transaction B:
row 1 → row 2
```

Тогда одна транзакция подождёт первую, после чего продолжит.

Другие практические меры:

- делать транзакции короткими;
- не выполнять долгие внешние операции внутри транзакции;
- блокировать только необходимые строки;
- избегать чрезмерно широких блокировок.

---

# 17. `NOWAIT`

Иногда ждать блокировку не нужно.

Можно сказать PostgreSQL:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE NOWAIT;
```

Если строка уже заблокирована несовместимым lock'ом, PostgreSQL сразу вернёт ошибку вместо ожидания.

```text
Lock свободен
    ↓
получили

Lock занят
    ↓
ошибка сразу
```

Это удобно, когда приложение хочет самостоятельно решить, что делать с занятым ресурсом.

---

# 18. `SKIP LOCKED`

Другой вариант:

```sql
SELECT *
FROM jobs
WHERE status = 'pending'
FOR UPDATE SKIP LOCKED;
```

Если строка уже заблокирована другой транзакцией, PostgreSQL её пропускает.

Типичный сценарий:

```text
Queue:
job 1 🔒 Worker A
job 2 🔒 Worker B
job 3 свободна
job 4 свободна

Worker C
    ↓
SKIP LOCKED
    ↓
берёт job 3
```

Это особенно полезно для реализации очередей задач на PostgreSQL.

---

# 19. Пример очереди задач

Таблица:

```text
jobs
────────────────
id
status
payload
```

Worker:

```sql
BEGIN;

SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

После этого worker может обработать выбранную задачу.

Несколько workers могут работать параллельно:

```text
Worker A → job 1
Worker B → job 2
Worker C → job 3
```

не выбирая одну и ту же заблокированную задачу.

---

# 20. Lock Timeout

Можно ограничить время ожидания блокировки:

```sql
SET lock_timeout = '2s';
```

Если блокировка не освободилась за это время, операция завершается ошибкой.

Это полезно, чтобы приложение не зависало на неопределённо долгое время.

---

# 21. Где посмотреть блокировки

PostgreSQL предоставляет системное представление:

```sql
pg_locks
```

Например:

```sql
SELECT *
FROM pg_locks;
```

Для диагностики обычно также смотрят `pg_stat_activity`.

Упрощённо:

```text
pg_stat_activity
→ кто выполняет запрос?

pg_locks
→ какие locks существуют?
```

Это позволяет искать:

- кто держит lock;
- кто ждёт;
- какие объекты заблокированы.

---

# 22. Lock и длительная транзакция

Представим:

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

А затем приложение:

```text
делает HTTP-запрос
↓
ждёт 10 секунд
↓
обрабатывает данные
↓
COMMIT
```

Lock всё это время может оставаться удерживаемым.

Получаем:

```text
10 секунд
    ↓
row locked
    ↓
другие транзакции ждут
```

Поэтому правило:

> Не держать транзакцию дольше необходимого.

Особенно не стоит без необходимости выполнять внешние сетевые вызовы внутри транзакции с удерживаемыми locks.

---

# 23. Pessimistic Locking

Lock обычно связывают с **pessimistic locking**.

Идея:

> Сначала заблокировать ресурс, потом работать с ним.

Например:

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

Мы заранее предполагаем возможность конфликта и явно захватываем lock.

---

# 24. Optimistic Locking

Другой подход — **optimistic locking**.

Мы не блокируем строку заранее.

Например, используем версию:

```text
id | balance | version
1  | 1000    | 5
```

Обновляем:

```sql
UPDATE accounts
SET balance = 900,
    version = 6
WHERE id = 1
  AND version = 5;
```

Если:

```text
updated rows = 1
```

значит версия была ожидаемой.

Если:

```text
updated rows = 0
```

значит кто-то уже изменил строку.

Сравнение:

```text
Pessimistic:
lock → work → commit

Optimistic:
work → check version → update
```

---

# 25. Lock vs Optimistic Locking

| | Pessimistic Locking | Optimistic Locking |
|---|---|---|
| Блокировка | Да | Обычно нет |
| Конфликт | Предотвращаем заранее | Обнаруживаем при записи |
| Пример | `FOR UPDATE` | `WHERE version = ?` |
| Хорошо при | Частых конфликтах | Редких конфликтах |
| Ожидание | Возможное | Обычно меньше ожидания |
| Сложность | Управление locks | Обработка конфликтов/retry |

---

# 26. Lock и isolation level

Locks и уровни изоляции связаны, но это разные понятия.

Isolation Level определяет:

```text
что транзакция может видеть
```

Lock определяет:

```text
какие конфликтующие операции могут выполняться одновременно
```

Например:

```text
Isolation Level
      +
MVCC
      +
Locks
      ↓
concurrency control
```

---

# 27. Важный нюанс: не каждый UPDATE требует `FOR UPDATE`

Например:

```sql
UPDATE users
SET name = 'Bob'
WHERE id = 1;
```

PostgreSQL сам выполняет необходимые действия для конкурентного изменения строки.

`FOR UPDATE` нужен, когда приложение хочет **сначала прочитать и зафиксировать строку для последующей логики**, например:

```text
прочитать balance
    ↓
проверить условие
    ↓
рассчитать новое значение
    ↓
изменить
```

Пример:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- бизнес-логика

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

# 28. Типичная Backend-ситуация

Есть склад:

```text
product_id = 10
stock = 1
```

Два HTTP-запроса одновременно хотят купить последний товар.

Без корректной синхронизации бизнес-логики можно получить конфликт.

Пессимистический вариант:

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 10
FOR UPDATE;
```

Получили:

```text
stock = 1
```

Проверили:

```text
stock > 0
```

Обновили:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 10;
```

После `COMMIT` следующая транзакция увидит:

```text
stock = 0
```

и не сможет продать тот же последний экземпляр.

# 29. Типичные ошибки

### ❌ «Lock блокирует всю таблицу»

Не обязательно.

Может блокироваться:

- конкретная строка;
- таблица;
- другой объект.

Зависит от типа lock.

### ❌ «Обычный SELECT всегда ждёт UPDATE»

Нет.

MVCC позволяет обычному чтению работать с подходящей версией строки.

### ❌ «`FOR UPDATE` блокирует строку от любого доступа»

Нет.

Он устанавливает определённый row-level lock, совместимость которого зависит от типа другой блокировки.

### ❌ «Deadlock = lock contention»

Нет.

**Lock contention** — конкуренция за lock.

**Deadlock** — циклическое ожидание, из которого транзакции самостоятельно выйти не могут.

### ❌ «PostgreSQL сам всегда повторит транзакцию после deadlock»

Нет.

PostgreSQL прерывает одну транзакцию. Retry должен быть реализован на уровне приложения.

```text
Transaction
    │
    ├── MVCC
    │     └── версии строк / visibility
    │
    ├── Isolation Level
    │     └── правила видимости
    │
    └── Locks
          ├── Row-level
          ├── Table-level
          ├── FOR UPDATE
          ├── FOR SHARE
          ├── NOWAIT
          └── SKIP LOCKED
```

А проблемы concurrency:

```text
Locks
 ├── Lock Contention
 └── Deadlock

Concurrency Control
 ├── MVCC
 ├── Isolation
 ├── Pessimistic Locking
 └── Optimistic Locking
```

## 🎯 Формула для собеседования

```text
Lock
  ↓
защита от конфликтующего конкурентного доступа
  ↓
Row-level / Table-level
  ↓
FOR UPDATE / FOR SHARE
  ↓
конфликт
  ↓
WAIT / NOWAIT / SKIP LOCKED
  ↓
долгие locks → contention
  ↓
циклическое ожидание → deadlock
```

Ключевая фраза:

> **Lock — это механизм PostgreSQL для координации конфликтующих операций между транзакциями. Блокировка может быть на уровне строки или таблицы; при конфликте транзакция может ждать, получить ошибку через `NOWAIT` или пропустить заблокированную строку через `SKIP LOCKED`.**

## 🎤 Вопросы на собеседовании

### Что такое Lock?

Механизм синхронизации конкурентных операций, который не позволяет несовместимым операциям одновременно работать с одним ресурсом.

### Что делает `SELECT ... FOR UPDATE`?

Получает блокировку выбранных строк до конца транзакции, чтобы другие конфликтующие операции не могли изменить их одновременно.

### Чем Lock отличается от MVCC?

```text
MVCC
→ какие версии строк видит транзакция

Lock
→ какие конфликтующие операции могут выполняться одновременно
```

### Что такое Lock Contention?

Ситуация, когда несколько транзакций конкурируют за одну блокировку и часть из них вынуждена ждать.

### Что такое Deadlock?

Циклическое ожидание блокировок:

```text
A → ждёт B
B → ждёт A
```

PostgreSQL обнаруживает deadlock и прерывает одну из транзакций.

### Как уменьшить вероятность Deadlock?

- одинаковый порядок получения locks;
- короткие транзакции;
- минимизация критической секции;
- блокировка только необходимых данных.

### Что делает `NOWAIT`?

Не ждёт освобождения несовместимого lock, а сразу возвращает ошибку.

### Что делает `SKIP LOCKED`?

Пропускает уже заблокированные строки вместо ожидания.

### Где применяется `SKIP LOCKED`?

Один из типичных сценариев — несколько workers, разбирающих очередь задач из PostgreSQL.

### Что такое Pessimistic Locking?

Сначала блокируем ресурс, затем выполняем операцию.

```text
FOR UPDATE
```

### Что такое Optimistic Locking?

Не блокируем ресурс заранее, а проверяем версию или другое условие при обновлении.

### Всегда ли нужно использовать `FOR UPDATE` перед `UPDATE`?

Нет. Сам `UPDATE` уже выполняет необходимые блокировки. `FOR UPDATE` нужен, когда бизнес-логике требуется сначала прочитать и зафиксировать строку перед последующими действиями.

### Почему длинные транзакции опасны?

Они могут долго удерживать locks, из-за чего другие транзакции будут ждать и возникнет lock contention.
