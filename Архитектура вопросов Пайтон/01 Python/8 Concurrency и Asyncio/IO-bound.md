# 🌐 I/O-bound

## 🎤 Короткий ответ

**I/O-bound** — это тип задачи, где основное время программа тратит не на вычисления CPU, а на **ожидание операций ввода-вывода (I/O)**.

Например:

* HTTP-запросы;
* запросы к базе данных;
* чтение/запись файлов;
* работа с сетью;
* ожидание ответа другого сервиса.

Для I/O-bound задач хорошо подходят **asyncio**, многопоточность и другие модели конкурентного выполнения, потому что пока одна операция ждёт I/O, можно выполнять другую работу.

---

## 🗣️ Ответ на собеседовании

I/O-bound — это задачи, ограниченные скоростью ввода-вывода, а не производительностью процессора.

Например, приложение отправляет HTTP-запрос и ждёт 500 миллисекунд ответа сервера. В это время CPU практически не занят вычислением этой задачи — программа в основном ждёт сеть.

Поэтому I/O-bound задачи хорошо масштабируются за счёт конкурентности. Например, `asyncio` может приостановить корутину на `await` и передать управление Event Loop, который продолжит другие задачи.

К типичным I/O-bound операциям относятся сетевые запросы, работа с базой данных, файловой системой и внешними API.

В отличие от I/O-bound, **CPU-bound** задачи ограничены вычислительной мощностью процессора. Для них asyncio обычно не является основным способом ускорения.

# 📚 Разбор поглубже

## 1. Что такое I/O

**I/O = Input/Output**, то есть ввод-вывод.

Это взаимодействие программы с внешним источником данных.

Например:

```text
Программа
   │
   ├── HTTP → Интернет
   ├── SQL → База данных
   ├── read() → Файл
   ├── socket → Сеть
   └── API → Другой сервис
```

Главная особенность — внешняя система может быть значительно медленнее CPU.

---

# 2. Почему задача становится I/O-bound

Рассмотрим HTTP-запрос:

```python
response = requests.get("https://example.com")
```

Упрощённо происходит:

```text
Python
  ↓
формирование запроса
  ↓
отправка через сеть
  ↓
          ⏳ ожидание сервера
          ⏳ ожидание сети
          ⏳ ожидание ответа
  ↓
получение данных
  ↓
обработка ответа
```

Большая часть времени может приходиться именно на ожидание.

Поэтому задача является **I/O-bound**.

---

# 3. I/O-bound vs CPU-bound

Это одна из основных классификаций задач.

| I/O-bound                  | CPU-bound                      |
| -------------------------- | ------------------------------ |
| Ограничена скоростью I/O   | Ограничена CPU                 |
| Много ожидания             | Много вычислений               |
| HTTP                       | Вычисление хеша                |
| База данных                | Обработка изображения          |
| Файлы                      | ML/математические расчёты      |
| Сокеты                     | Сжатие данных                  |
| Внешние API                | Обработка большого массива     |
| `asyncio` часто эффективен | multiprocessing часто подходит |

---

# 4. Пример I/O-bound

Допустим, нужно получить данные из трёх API:

```text
API A → 500 ms
API B → 300 ms
API C → 700 ms
```

Последовательно:

```text
A ───── 500ms
       ↓
B ─── 300ms
       ↓
C ─────── 700ms

≈ 1500ms
```

При конкурентном выполнении:

```text
A ───────────── 500ms
B ─── 300ms
C ───────────────── 700ms

≈ 700ms
```

В идеализированном случае общее время определяется самой долгой операцией:

```text
max(500, 300, 700) = 700 ms
```

Плюс накладные расходы.

Именно здесь появляется преимущество `asyncio`.

---

# 5. Почему asyncio подходит для I/O-bound

Представим три задачи:

```text
Task A → ждёт HTTP
Task B → ждёт БД
Task C → выполняет работу
```

Event Loop может делать:

```text
A
↓
await HTTP
↓
B
↓
await DB
↓
C
↓
A получил ответ
↓
A продолжает работу
```

То есть время ожидания одной задачи используется для выполнения других.

Это и есть основная идея асинхронного I/O.

---

# 6. I/O-bound не означает «CPU вообще не используется»

Это важный нюанс.

I/O-bound задача всё равно выполняет код на CPU:

```text
CPU
 ↓
подготовить запрос
 ↓
I/O
 ↓
CPU
 ↓
обработать ответ
 ↓
I/O
 ↓
CPU
```

Просто **основным ограничивающим фактором является ожидание I/O**.

Поэтому нельзя определять I/O-bound как:

> «CPU не работает».

Точнее:

> **CPU не является главным bottleneck задачи.**

---

# 7. I/O-bound и блокирующие операции

I/O может быть:

### Блокирующим

```python
import requests

response = requests.get(url)
```

Поток ждёт завершения запроса.

### Асинхронным

```python
response = await client.get(url)
```

Корутина приостанавливается на `await`, позволяя Event Loop выполнять другие задачи.

Поэтому:

```text
I/O-bound
    │
    ├── blocking I/O
    │      └── Threading / другие подходы
    │
    └── async I/O
           └── asyncio
```

---

# 8. I/O-bound и многопоточность

Многопоточность также хорошо подходит для I/O-bound задач.

Например:

```text
Thread 1 → HTTP request
Thread 2 → HTTP request
Thread 3 → HTTP request
```

Пока один поток ждёт сеть, другой может выполнять работу.

Поэтому в Python:

```text
I/O-bound
   ├── asyncio
   └── threading
```

оба подхода могут быть эффективны.

Разница в модели выполнения.

---

# 9. I/O-bound и GIL

В обычном CPython с включённым GIL потоки не дают полноценного параллельного выполнения Python bytecode на CPU.

Но для I/O-bound задач это не является основной проблемой.

Когда поток ожидает блокирующий I/O, GIL обычно может быть освобождён, позволяя другим потокам выполнять Python-код.

Поэтому:

```text
CPU-bound + threads
    → GIL может ограничивать масштабирование

I/O-bound + threads
    → обычно работает нормально
```

---

# 10. I/O-bound и multiprocessing

Multiprocessing может использоваться для I/O-bound задач, но обычно это не первый инструмент.

Создание процессов дороже:

```text
Process
├── отдельная память
├── IPC
├── создание процесса
└── serialization
```

Если задача в основном ждёт сеть, часто рациональнее использовать:

```text
asyncio
```

или:

```text
threading
```

---

# 11. Как определить I/O-bound задачу

Задай вопрос:

> **«Где программа проводит большую часть времени?»**

Если:

```text
HTTP → ждём сервер
DB → ждём запрос
File → ждём диск
Socket → ждём данные
API → ждём внешний сервис
```

скорее всего задача **I/O-bound**.

Если:

```text
цикл вычислений
математика
кодирование
сжатие
обработка изображений
ML inference
```

скорее всего задача **CPU-bound**.

---

# 12. Важный нюанс: I/O-bound ≠ всегда asyncio

Нельзя делать вывод:

> «Если I/O-bound, значит обязательно asyncio».

Правильнее:

```text
I/O-bound
   │
   ├── asyncio
   │     └── много конкурентных async I/O операций
   │
   ├── threading
   │     └── блокирующие библиотеки / I/O
   │
   └── обычный синхронный код
         └── когда конкурентность вообще не нужна
```

Выбор зависит от архитектуры приложения и используемых библиотек.

---

# 13. Практический пример для Backend

Допустим, FastAPI-сервис получает запрос:

```text
Client
  ↓
FastAPI
  ↓
PostgreSQL
  ↓
внешний API
  ↓
Redis
  ↓
Response
```

Большая часть времени может уйти на:

```text
PostgreSQL     → ожидание
External API   → ожидание
Redis          → ожидание
```

Это I/O-bound сценарий.

Асинхронный backend может обслуживать другие запросы во время этих ожиданий.

> **I/O-bound — это задача, в которой bottleneck находится на вводе-выводе, а не на CPU. Например, HTTP-запросы, БД, файлы и сеть.
