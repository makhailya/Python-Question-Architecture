# ⚛️ Атомарность операций

## 🎯 Ответ на собеседовании

**Атомарная операция** — операция, которая выполняется **целиком и неделимо с точки зрения других потоков**: другой поток не может увидеть её промежуточное состояние.

Например, простое присваивание:

```python
x = 10
```

в CPython обычно является атомарным на уровне выполнения Python-кода.

Но составные операции могут состоять из нескольких действий и поэтому быть **неатомарными**:

```python
counter += 1
```

Упрощённо:

```text
прочитать counter
       ↓
прибавить 1
       ↓
записать counter
```

Между этими действиями другой поток может вмешаться.

---

## 📌 Пример race condition

```python
counter = 0

def increment():
    global counter

    for _ in range(100_000):
        counter += 1
```

Если несколько потоков одновременно выполняют `increment()`, возникает **race condition**.

Упрощённо:

```text
Поток A: прочитал 10
Поток B: прочитал 10

Поток A: записал 11
Поток B: записал 11
```

Ожидали:

```text
12
```

получили:

```text
11
```

Одно увеличение потерялось.

---

## 🔐 Как обеспечить атомарность

Для составных операций используют синхронизацию:

```python
import threading

lock = threading.Lock()
counter = 0


def increment():
    global counter

    for _ in range(100_000):
        with lock:
            counter += 1
```

Теперь изменение `counter` защищено `Lock`.

```text
Поток A → 🔒 → изменил counter → 🔓
Поток B → 🔒 → изменил counter → 🔓
```

## 🧠 Атомарность ≠ потокобезопасность

Это разные понятия.

**Атомарность** — конкретная операция выполняется неделимо.

**Потокобезопасность** — код корректно работает при одновременном доступе из нескольких потоков.

Например, отдельные операции `dict` в CPython могут быть атомарными на практике, но последовательность:

```python
if key not in d:
    d[key] = value
```

не является атомарной.

Между проверкой и вставкой другой поток может изменить `d`.

---

## ⚠️ GIL не означает атомарность всего Python-кода

Распространённая ошибка:

> «В CPython есть GIL, поэтому race condition невозможны».

❌ Неверно.

GIL ограничивает одновременное выполнение Python-кода несколькими потоками в обычной GIL-enabled сборке CPython, но **не делает произвольную последовательность операций атомарной**.

Например:

```python
counter += 1
```

нельзя считать безопасным способом синхронизации общего счётчика.

Для критических секций используют:

```python
threading.Lock
threading.RLock
threading.Semaphore
```

или другие подходящие механизмы синхронизации.

---

## 📌 Атомарность и `list` / `dict`

Некоторые простые операции встроенных структур в **CPython** атомарны на практике благодаря деталям реализации и GIL, например:

```python
lst.append(x)
d[key] = value
x = d[key]
```

Но при написании многопоточного кода **не стоит строить корректность программы на предположении, что любая операция с `list` или `dict` атомарна**.

Особенно опасны составные последовательности:

```python
if x not in lst:
    lst.append(x)
```

или:

```python
if key not in d:
    d[key] = value
```

Они состоят из нескольких операций.

## 🔥 Атомарность, race condition и Lock

Связь между понятиями:

```text
Несколько потоков
       ↓
общие данные
       ↓
одновременный доступ
       ↓
race condition
       ↓
неатомарная критическая секция
       ↓
Lock / другой механизм синхронизации
```

---

## 🧠 Главное

* **Атомарность** → операция выполняется неделимо.
* **Неатомарная операция** → между её частями может вмешаться другой поток.
* `counter += 1` — классический пример составной операции.
* **GIL ≠ полноценная синхронизация пользовательского кода.**
* Для критических секций используют `Lock` и другие примитивы синхронизации.
* Атомарность конкретных операций встроенных типов может зависеть от реализации Python; особенно осторожно с предположениями о CPython.

### 🎤 Суперкоротко

> **Атомарность — свойство операции выполняться неделимо с точки зрения других потоков. GIL не делает весь Python-код атомарным и не устраняет race condition, поэтому для составных операций над общими данными используют механизмы синхронизации, например `Lock`.**
