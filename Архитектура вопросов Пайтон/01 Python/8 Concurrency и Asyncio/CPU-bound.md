# 🧮 CPU-bound

## 🎤 Короткий ответ

**CPU-bound** — это задача, в которой основным ограничением является производительность процессора. Программа большую часть времени выполняет вычисления, а не ждёт внешние операции.

Примеры:

* сложные математические вычисления;
* обработка изображений;
* сжатие и кодирование данных;
* криптографические вычисления;
* обработка больших объёмов данных;
* некоторые ML-задачи.

Для CPU-bound задач `asyncio` обычно не даёт ускорения, потому что вычисления продолжают занимать CPU. В Python для использования нескольких ядер обычно применяют **multiprocessing** или `ProcessPoolExecutor`.

---

## 🗣️ Ответ на собеседовании

CPU-bound — это тип нагрузки, при котором bottleneck находится на процессоре. Программа практически постоянно выполняет вычисления и редко простаивает в ожидании I/O.

Например, если мы обрабатываем большое изображение, вычисляем хеши для миллионов объектов или выполняем сложные математические операции, CPU будет загружен вычислениями.

`asyncio` здесь обычно не помогает, потому что корутина не может уступить Event Loop управление, пока выполняется длинный CPU-bound участок синхронного кода. Event Loop фактически блокируется.

В обычном CPython с включённым GIL потоки также не дают полноценного параллельного выполнения Python bytecode на нескольких ядрах. Поэтому для CPU-bound Python-кода часто используют **multiprocessing** или `ProcessPoolExecutor`, где разные процессы могут выполнять вычисления параллельно на разных ядрах.

# 📚 Разбор поглубже

## 1. Что такое CPU-bound

**CPU-bound** означает, что скорость выполнения задачи в основном определяется тем, насколько быстро CPU способен выполнять вычисления.

Упрощённо:

```text
CPU-bound
    ↓
много вычислений
    ↓
CPU постоянно занят
    ↓
мало времени на ожидание I/O
```

Например:

```python
def calculate():
    total = 0

    for i in range(100_000_000):
        total += i * i

    return total
```

Здесь программа практически всё время выполняет инструкции на CPU.

---

# 2. CPU-bound vs I/O-bound

Это одна из ключевых классификаций нагрузки.

| CPU-bound             | I/O-bound      |
| --------------------- | -------------- |
| Ограничена CPU        | Ограничена I/O |
| Много вычислений      | Много ожидания |
| Математика            | HTTP           |
| Обработка изображений | База данных    |
| Сжатие                | Файлы          |
| Криптография          | Сокеты         |
| CPU-intensive ML      | Внешние API    |

Упрощённая модель:

```text
CPU-bound:

CPU ████████████████████
I/O ░
```

```text
I/O-bound:

CPU ██░░░░░░██░░░░░░██
I/O   ██████    ██████
```

---

# 3. Почему asyncio плохо подходит для CPU-bound

Рассмотрим:

```python
import asyncio


async def heavy_calculation():
    total = 0

    for i in range(100_000_000):
        total += i * i

    return total
```

На первый взгляд функция `async`.

Но это не делает вычисления асинхронными:

```text
Event Loop
    ↓
heavy_calculation()
    ↓
длинный цикл
    ↓
CPU работает
    ↓
CPU работает
    ↓
CPU работает
    ↓
Event Loop заблокирован
```

Внутри цикла нет:

```python
await ...
```

Поэтому Event Loop не получает возможности переключиться на другие задачи.

---

# 4. Почему `await` сам по себе не решает проблему

Важно понимать:

```python
await something()
```

полезен, когда есть что **ожидать**.

Например:

```python
response = await client.get(url)
```

Здесь:

```text
отправили запрос
      ↓
ждём сеть
      ↓
можно выполнять другие задачи
```

Но если у нас:

```python
for _ in range(100_000_000):
    calculate()
```

нечего ждать.

CPU должен выполнить вычисления.

Поэтому:

> **Asyncio эффективно использует время ожидания, но не создаёт дополнительную вычислительную мощность CPU.**

---

# 5. CPU-bound и GIL

В обычном CPython с включённым GIL несколько потоков не позволяют одновременно выполнять Python bytecode на нескольких ядрах.

Например:

```text
CPU cores:

Core 1 ── Thread A
Core 2 ── Thread B
```

Для CPU-bound Python bytecode GIL ограничивает такое выполнение.

Упрощённо:

```text
Thread A → Python bytecode
Thread B → ждёт GIL

Thread A → освобождает GIL
Thread B → Python bytecode
```

Поэтому простое добавление потоков не означает ускорение CPU-bound Python-кода.

> Важно: существуют free-threaded сборки CPython, появившиеся в Python 3.13+, где GIL может быть отключён. Поэтому корректнее говорить именно про **обычный CPython с включённым GIL**.

---

# 6. Multiprocessing

Для CPU-bound задач один из классических подходов — использовать несколько процессов.

```text
                CPU
        ┌────────┼────────┐
        ↓        ↓        ↓
    Process 1 Process 2 Process 3
        ↓        ↓        ↓
      Core 1   Core 2   Core 3
```

Каждый процесс имеет собственное адресное пространство и собственный Python-интерпретатор.

Поэтому процессы могут действительно выполнять вычисления параллельно на разных ядрах.

---

# 7. Пример с multiprocessing

```python
from multiprocessing import Pool


def calculate(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


if __name__ == "__main__":
    with Pool(4) as pool:
        results = pool.map(calculate, [10_000_000] * 4)
```

Здесь можно распределить работу между несколькими процессами.

Условно:

```text
Task 1 → Process 1 → Core 1
Task 2 → Process 2 → Core 2
Task 3 → Process 3 → Core 3
Task 4 → Process 4 → Core 4
```

---

# 8. ProcessPoolExecutor

В современных приложениях часто используется более высокоуровневый интерфейс:

```python
from concurrent.futures import ProcessPoolExecutor


def calculate(n):
    total = 0

    for i in range(n):
        total += i * i

    return total


if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(
            executor.map(calculate, [10_000_000] * 4)
        )
```

Идея та же:

```text
CPU-bound
    ↓
несколько процессов
    ↓
несколько CPU cores
    ↓
параллельное выполнение
```

---

# 9. CPU-bound и потоки

Для обычного CPython с GIL:

```text
CPU-bound + threading
        ↓
несколько потоков
        ↓
GIL
        ↓
нет полноценного параллельного выполнения Python bytecode
```

Поэтому:

```text
CPU-bound
    ├── threading
    │      └── обычно не ускоряет Python bytecode
    │
    └── multiprocessing
           └── использует несколько процессов
```

Но есть важное исключение.

Некоторые C/C++ расширения могут освобождать GIL во время тяжёлых вычислений.

Поэтому нельзя утверждать:

> «Threads никогда не подходят для CPU-bound».

Точнее:

> Для чистого Python CPU-bound кода в обычном CPython с GIL потоки обычно не дают ожидаемого масштабирования на несколько ядер.

# 10. CPU-bound и количество ядер

Если процессор имеет:

```text
8 CPU cores
```

теоретически можно выполнять несколько CPU-bound задач параллельно.

Например:

```text
Core 1 → Task A
Core 2 → Task B
Core 3 → Task C
Core 4 → Task D
```

Но нельзя автоматически считать:

```text
4 процесса = ровно 4× быстрее
```

Есть накладные расходы:

* создание процессов;
* переключение контекста;
* передача данных;
* сериализация;
* синхронизация;
* конкуренция за память и кэш;
* другие процессы системы.

---

# 11. Почему multiprocessing не всегда выгоден

Допустим, задача занимает:

```text
5 ms
```

а на передачу данных между процессами требуется:

```text
10 ms
```

Тогда multiprocessing может сделать программу **медленнее**.

Поэтому параллелизм имеет смысл, когда вычислительная работа достаточно крупная, чтобы компенсировать overhead.

---

# 12. CPU-bound и Shared Memory

У процессов по умолчанию:

```text
Process A
└── Memory A

Process B
└── Memory B
```

Память не является общей.

Если процессам нужно обмениваться большими объёмами данных, появляется дополнительная стоимость IPC и сериализации.

Можно использовать:

* `Queue`;
* `Pipe`;
* `SharedMemory`;
* другие механизмы IPC.

Это важно учитывать при проектировании CPU-bound pipeline.

# 13. CPU-bound в Backend

Представим FastAPI-сервис:

```text
HTTP request
     ↓
FastAPI
     ↓
сложное вычисление 10 секунд
     ↓
Response
```

Если выполнить вычисление прямо внутри Event Loop:

```text
Request A
    ↓
CPU calculation
    ↓
10 секунд
    ↓
Event Loop заблокирован
```

Другие async-запросы могут начать ждать.

Поэтому тяжёлые CPU-bound операции обычно выносят из Event Loop.

Например:

```text
FastAPI
   │
   ├── I/O → asyncio
   │
   └── CPU-heavy
          ↓
       ProcessPool
```

---

# 14. CPU-bound + asyncio

Asyncio и multiprocessing можно комбинировать.

Например:

```text
                    FastAPI
                       │
              ┌────────┴────────┐
              ↓                 ↓
          HTTP / DB          CPU task
              ↓                 ↓
          asyncio          ProcessPool
```

Это довольно распространённая архитектурная схема:

* `asyncio` — управление большим количеством I/O;
* процессы — тяжёлые CPU-вычисления.

# 15. Пример архитектуры

Предположим, API получает изображение:

```text
Client
  ↓
FastAPI
  ↓
получение файла
  ↓
async I/O
  ↓
передача CPU-задачи
  ↓
ProcessPool
  ↓
обработка изображения
  ↓
результат
  ↓
Response
```

Здесь разные части системы используют разные модели выполнения.

```text
I/O-bound → asyncio
CPU-bound → multiprocessing
```

# 16. Как определить CPU-bound

Главный вопрос:

> **Что является bottleneck?**

Если задача постоянно загружает CPU:

```text
CPU ███████████████████████
I/O ░░░
```

скорее всего она CPU-bound.

Практически можно смотреть на:

* загрузку CPU;
* профилирование;
* время выполнения функций;
* количество операций;
* системные метрики.

Например:

```text
CPU usage ≈ 100%
I/O wait низкий
```

Это сильный признак CPU-bound нагрузки.

---

# 17. Не путать CPU-bound с «сложной задачей»

CPU-bound не означает:

> «Задача сложная».

Например, простой HTTP-запрос может занимать 5 секунд:

```text
CPU → почти ничего
Network → ожидание 5 секунд
```

Это всё ещё **I/O-bound**.

А простая математическая операция, повторённая 100 миллионов раз:

```text
CPU → постоянно занят
```

может быть CPU-bound.

Ключевой критерий — **где находится bottleneck**, а не субъективная сложность задачи.

# 18. Полная картина

```text
                    Нагрузка
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
         I/O-bound           CPU-bound
             │                   │
             │                   │
       много ожидания       много вычислений
             │                   │
       ┌─────┴─────┐       ┌─────┴──────┐
       ↓           ↓       ↓            ↓
   asyncio    threading  processes   ProcessPool
```

Упрощённое правило:

```text
I/O-bound
→ эффективно ждать конкурентно

CPU-bound
→ эффективно использовать CPU параллельно
```

## 🎤 Формула для собеседования

> **CPU-bound — это задача, в которой bottleneck находится на CPU: программа большую часть времени выполняет вычисления, а не ждёт I/O. Для чистого Python-кода в обычном CPython с включённым GIL многопоточность обычно не даёт параллельного выполнения Python bytecode на нескольких ядрах.
