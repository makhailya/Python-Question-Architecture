## ⚡ Быстрый ответ (шпаргалка перед собесом)

- **[[JOIN]]** — объединение строк из двух и более таблиц. В основе всех JOIN лежит
- **[[CROSS JOIN]]** (декартово произведение всех строк, без условия).
- **[[INNER JOIN]]** = [[CROSS JOIN]] + условие, оставляющее только совпадающие строки.
- **[[LEFT JOIN]]** — берёт все строки левой таблицы, если совпадения в правой нет — ставит `NULL`.
- **[[RIGHT JOIN]]** — зеркально (если поменять таблицы местами и написать 
- [[LEFT JOIN]]— получится то же самое, только строки будут в другом порядке).
- **[[SELF JOIN]]** — таблица соединяется сама с собой (типичный пример — иерархия «сотрудник → его руководитель» в одной таблице).

- **[[WHERE]] vs [[HAVING]]**: `WHERE` фильтрует строки **до** группировки ([[GROUP BY]]), [[HAVING]] — фильтрует уже сгруппированные результаты **после** группировки (можно использовать [[Агрегатные функции в SQL]] типа `SUM`, `AVG`).

# - **[[Типы индексов в PostgreSQL]]**:

- **[[B-tree]]** (по умолчанию, универсальный — равенство и диапазоны/сравнения), **[[Hash]]** (только точное равенство),
- **[[GIN]]** (полнотекстовый поиск, инвертированный индекс: связь «слово → документы», а не «документ → слова»),
- **[[GiST]]/[[SP-GiST]]** (геоданные и сложные структуры),
- **[[BRIN]]** (легковесный индекс для физически отсортированных данных, например по дате — хорош для больших таблиц с диапазонными запросами).

- **[[B-tree]]** — сбалансированное дерево (все листья на одном уровне), сложность поиска и вставки $O(\log n)$ за счёт того, что дерево сбалансировано и отсортировано — можно отсекать половину данных на каждом уровне сравнения.

- **[[EXPLAIN]] / [[EXPLAIN ANALYZE]]**:
- [[EXPLAIN]] показывает **план** выполнения запроса (без реального выполнения) — оценочную стоимость, тип сканирования;
- [[EXPLAIN ANALYZE]] реально выполняет запрос и добавляет фактическое время выполнения.

- # **[[Типы сканирования в PostgreSQL]]**:

- **[[Последовательное сканирование - Sequential Scan]]** (последовательное сканирование всей таблицы — индекс не используется),
- **[[Index Scan]]** (идём по индексу, затем при необходимости — в таблицу), 
- **[[Index Only Scan]]** (все нужные данные есть прямо в индексе, в таблицу лезть не нужно — самый быстрый вариант, актуален при покрывающем индексе),
- **[[Bitmap Index Scan]]** (промежуточный вариант между [[Последовательное сканирование - Sequential Scan]] и [[Index Scan]] — собирается битовая карта нужных страниц, читаются пачками).

- **[[Селективность индекса]]** ≠ **[[Cелективность условия (предиката)]]** — частая путаница! Селективность **индекса** — отношение количества **уникальных** значений к общему числу строк, стремится к 1 (100% уникальности = отличный индекс). Селективность **условия/предиката** — какая доля строк удовлетворяет условию [[WHERE]], здесь чем **ближе к 0**, тем эффективнее использовать индекс (мало строк нужно достать).

- **[[Покрывающий индекс (Covering Index)]]** — индекс, включающий все колонки, нужные запросу, так что в саму таблицу лезть не требуется ([[Index Only Scan]]). **[[Композитный индекс - Composite index]]** — индекс по нескольким колонкам сразу, важен **порядок** колонок: индекс по `(a, b)` хорошо работает для условий по `a` и по `a+b`, но не работает эффективно для условия только по `b`.

- **[[MVCC]]** — в PostgreSQL при изменении строки создаётся **новая версия** строки (со своими служебными полями — минимум/максимум id транзакции), старая помечается как устаревшая, но не удаляется сразу. Это позволяет читать данные **без блокировок на чтение** — читающие транзакции видят согласованный снапшот, не мешая пишущим.

- **[[VACUUM]]** — процесс очистки «мёртвых» версий строк (оставшихся после [[MVCC]]), которые больше не нужны ни одной активной транзакции. Обычный [[VACUUM]] освобождает место **внутри** файла таблицы для повторного использования, но не возвращает его операционной системе. [[VACUUM FULL]] полностью перестраивает таблицу и физически возвращает место ОС, но это медленная блокирующая операция. [[ANALYZE]] — обновляет статистику для планировщика запросов.

- **[[ACID]]**: **A**tomicity (транзакция выполняется полностью или полностью откатывается — [[BEGIN]]/[[COMMIT]]/[[ROLLBACK]]), 
- **C**onsistency (после транзакции данные остаются в согласованном состоянии — соблюдены все ограничения/связи),
- **I**solation (параллельные транзакции не мешают друг другу),
- **D**urability (после коммита данные гарантированно сохранены на диск, даже при сбое — реализуется через **[[WAL (журнал предзаписи)]]**, Write-Ahead Log — журнал предзаписи: изменения сначала пишутся в журнал, потом применяются к самим таблицам).

# - **[[Уровни изоляции транзакций]]**: `

- **[[Read Uncommitted]]**` (можно читать незакоммиченные данные других транзакций — «грязное чтение», на практике почти нигде не применяется), `
- **[[Read Committed]]**` (дефолт в PostgreSQL — видим только закоммиченные на момент запроса данные), `
- **[[Repeatable Read]]**` (в рамках всей транзакции видим один и тот же снапшот данных, даже если кто-то параллельно их изменил), `
- **[[Serializable]]**` (самый строгий — полностью защищает от аномалий параллелизма, но сильно нагружает БД: больше блокировок, ретраев, ниже доступность — поэтому не используется «на всё подряд»).

- **[[Масштабирование БД]]**:
- **[[Репликация]]** (полное копирование базы на другие сервера — для отказоустойчивости и распределения нагрузки на чтение),
- **[[Шардинг (Sharding)]]** (разбиение базы на части, размещённые на **разных серверах**),
- **[[Партиционирование]]** (разбиение таблицы на более мелкие части **внутри одной базы/сервера**, например по диапазону дат или по хэшу).

- **[[Репликация]]**: типы по ролям — **[[master-slave]]** (один инстанс пишет, остальные только читают) и **[[multi-master]]** (несколько инстансов и пишут, и читают — сложнее синхронизировать). Типы по подтверждению — **[[Синхронная репликация]]** (ждём подтверждение от всех реплик — надёжнее, но медленнее и ниже доступность), **[[Асинхронная репликация]]** (не ждём подтверждения — быстрее, но данные могут разойтись, на практике используется чаще), **[[Полусинхронная репликация]]** (промежуточный вариант). Читать с мастера при асинхронной репликации можно, если критично получить самые свежие данные (например, сразу после списания с баланса).

- **[[N+1 проблема]]**: при получении списка из N объектов ORM делает 1 запрос за списком + ещё N запросов за связанными данными по каждому объекту. Решается через **[[JOIN Load]]** (JOIN'ит связанные данные в одном запросе — но при связи «один ко многим» даёт декартово произведение) или **[[Selection Load]]** (делает один дополнительный `SELECT ... WHERE id IN (...)` вместо N отдельных запросов).

# 📖 Подробно

## 1. [[JOIN]]

Все виды [[JOIN]] концептуально строятся на **[[CROSS JOIN]]** — декартовом произведении: каждая строка левой таблицы соединяется с каждой строкой правой, без каких-либо условий.

```sql
-- CROSS JOIN: если в orders 100 строк, а в users 50 — получим 5000 строк
SELECT * FROM orders CROSS JOIN users;

-- INNER JOIN = CROSS JOIN + условие совпадения
SELECT * FROM orders
INNER JOIN users ON orders.user_id = users.id;

-- LEFT JOIN: все строки orders, даже если пользователя не нашли (тогда user-поля = NULL)
SELECT * FROM orders
LEFT JOIN users ON orders.user_id = users.id;
```

| [[JOIN]]       | Что возвращает                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| [[INNER JOIN]] | Только строки, где есть совпадение в обеих таблицах                                                                   |
| [[LEFT JOIN]]  | Все строки левой таблицы + совпадения из правой (или `NULL`, если нет совпадения)                                     |
| [[RIGHT JOIN]] | Зеркально `LEFT JOIN` (все строки правой таблицы)                                                                     |
| [[FULL JOIN]]  | Все строки из обеих таблиц, `NULL` там, где нет совпадения                                                            |
| [[SELF JOIN]]  | Таблица соединяется сама с собой — полезно для иерархических данных (например, `employees.manager_id → employees.id`) |

**[[WHERE]] vs [[HAVING]]**: [[WHERE]] применяется к строкам **до**  [[GROUP BY]], [[HAVING]] — к уже сгруппированным строкам **после** [[GROUP BY]], поэтому в [[HAVING]] можно использовать [[Агрегатные функции в SQL]] (`SUM`, `COUNT`, `AVG`), а в `WHERE` — нет.

```sql
SELECT department, AVG(salary)
FROM employees
WHERE hired_at > '2020-01-01'   -- фильтр до группировки
GROUP BY department
HAVING AVG(salary) > 100000;    -- фильтр после группировки
```

## 2. Индексы

[[Индекс]] — объект в базе данных, ускоряющий поиск/выборку данных за счёт хранения отсортированной/структурированной ссылки на строки таблицы (аналогия — алфавитный указатель в конце книги).

| [[Типы индексов в PostgreSQL]] | Для чего                                                                                                                                                          |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **[[B-tree]]** (по умолчанию)  | Универсальный: равенство, диапазоны, сортировка                                                                                                                   |
| **[[Hash]]**                   | Только строгое равенство (`=`), не поддерживает диапазоны                                                                                                         |
| **[[GIN]]**                    | Полнотекстовый поиск, инвертированный индекс (слово → список документов, а не документ → слова)                                                                   |
| **[[GiST]]**                   | Геоданные, сложные типы данных                                                                                                                                    |
| **[[SP-GiST]]**                | Тоже геоданные, но для более специфичных/неравномерных структур                                                                                                   |
| **[[BRIN]]**                   | Легковесный, для физически упорядоченных данных на диске (например, монотонно растущая дата) — отлично подходит для очень больших таблиц с диапазонными запросами |

**[[B-tree]] подробнее**: сбалансированное бинарное дерево (все листья на одном уровне), данные отсортированы. Благодаря сортировке и балансировке поиск идёт со сложностью $O(\log n)$ — на каждом уровне дерева отсекается примерно половина оставшихся данных. Например, для миллиарда значений глубина дерева — порядка 30 уровней.

## 3. [[EXPLAIN]] и [[Типы сканирования в PostgreSQL]]

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
```

- [[EXPLAIN]] — показывает **план** запроса без реального выполнения: оценочную стоимость, ожидаемое число строк, тип сканирования.
- [[EXPLAIN ANALYZE]] — реально **выполняет** запрос и добавляет к плану фактическое время выполнения и точное число обработанных строк.

**[[Типы сканирования в PostgreSQL]] (в плане запроса):**

| Тип                       | Что означает                                                                                                                                                                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **[[Последовательное сканирование - Sequential Scan]]**          | Последовательное сканирование всей таблицы — индекс не используется (или не эффективен для этого запроса)                                                                                                                                             |
| **[[Index Scan]]**        | Поиск идёт по индексу, при необходимости — дополнительное обращение к самой таблице за остальными колонками                                                                                                                                           |
| **[[Index Only Scan]]**   | Все нужные запросу колонки есть прямо в индексе — в таблицу заходить не нужно вообще (самый быстрый вариант, требует **покрывающего индекса**)                                                                                                        |
| **[[Bitmap Index Scan]]** | Промежуточный вариант между Seq Scan и Index Scan: строится битовая карта нужных страниц данных, затем они читаются пачками — используется, когда выборка не настолько маленькая, чтобы был эффективен чистый Index Scan, но и не вся таблица целиком |
|                           |                                                                                                                                                                                                                                                       |

## 4. Селективность: индекса vs условия — не путать!

- **[[Селективность индекса]]** = (количество **уникальных** значений в колонке) / (общее число строк). Стремится к **1** (100%) — чем больше уникальных значений, тем «избирательнее» и полезнее индекс. Пример: колонка `email` — почти всегда уникальна → отличная селективность индекса, стоит индексировать. Колонка `is_active` (булево) — всего 2 уникальных значения на миллион строк → плохая селективность индекса, индекс почти бесполезен.

- **[[Cелективность условия (предиката)]]** = (количество строк, подходящих под [[WHERE]]) / (общее число строк). Здесь чем **ближе к 0**, тем эффективнее использовать индекс — если условию соответствует малая доля строк, есть смысл лезть по индексу за конкретными строками, а не сканировать всю таблицу.

## 5. [[Покрывающий индекс (Covering Index)]] и [[Композитный индекс - Composite index]]

- [[Покрывающий индекс (Covering Index)]]  — включает все колонки, которые нужны запросу (и в [[WHERE]], и в [[SELECT]]), поэтому движку не нужно обращаться к самой таблице — получаем [[Index Only Scan]].

- **[[Композитный индекс - Composite index]]** — индекс сразу по нескольким колонкам, например `(a, b)`. Важен **порядок** колонок: такой индекс эффективно работает для условий `WHERE a = ...` и `WHERE a = ... AND b = ...`, но **не работает эффективно** для условия только `WHERE b = ...` (без `a`). Также композитный индекс хорошо работает **до первого условия неравенства** (`>`, `<`) в списке колонок — после него сортировка индекса дальше не помогает.

## 6. [[MVCC]] и [[VACUUM]]

**[[MVCC]]** — механизм, позволяющий читателям не блокировать писателей и наоборот. При изменении строки PostgreSQL не перезаписывает её «на месте», а создаёт **новую версию** строки. У каждой версии есть служебные поля с id транзакций, которые её создали/удалили (условно: `xmin`/`xmax`). [[Транзакция]] видит только те версии строк, которые актуальны для её снапшота — за счёт этого чтение и запись могут идти параллельно без блокировок на чтение.

**[[VACUUM]]** — процесс, который очищает «мёртвые» версии строк (те, что уже никому не нужны, потому что ни одна активная транзакция их больше не видит):

- **VACUUM** (обычный) — помечает место, занятое мёртвыми строками, как свободное для повторного использования **внутри** файла таблицы, но не возвращает это место операционной системе (файл на диске не уменьшается).

- **[[VACUUM FULL]]** — полностью перестраивает таблицу и физически возвращает освободившееся место ОС — но это тяжёлая блокирующая операция, требует эксклюзивной блокировки таблицы.

- **[[ANALYZE]]** — отдельный процесс, обновляющий статистику по данным (сколько строк, распределение значений), которую использует планировщик запросов для построения оптимального плана.

- В PostgreSQL есть **[[Autovacuum]]** — фоновый процесс, который сам запускает VACUUM/ANALYZE по мере необходимости.

## 7. [[ACID]] и [[Уровни изоляции транзакций]]

| Буква | Свойство                                                                         | Механизм в PostgreSQL                            |
| ----- | -------------------------------------------------------------------------------- | ------------------------------------------------ |
| **A** | Atomicity — всё или ничего                                                       | [[BEGIN]] / [[COMMIT]] / [[ROLLBACK]]            |
| **C** | Consistency — данные после транзакции согласованы (соблюдены constraints, связи) | Проверка ограничений (constraints, foreign keys) |
| **I** | Isolation — параллельные транзакции не мешают друг другу                         | Уровни изоляции + MVCC + блокировки              |
| **D** | Durability — после коммита данные не теряются даже при сбое                      | **WAL (Write-Ahead Log)** — журнал предзаписи    |

**[[WAL (журнал предзаписи)]]** — ключевой механизм надёжности: любое изменение сначала записывается в последовательный журнал на диске, и только потом применяется к самим файлам таблиц. Если случится сбой посреди операции — при восстановлении база «доигрывает» журнал и приходит в консистентное состояние.

**Уровни изоляции (от слабого к строгому):**

| Уровень                                        | Что допускает/защищает                                                                                                                                                                                                                                                                                            |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [[Read Uncommitted]]                           | Можно читать незакоммиченные данные других транзакций («грязное чтение»). Практически нигде не применяется, в PostgreSQL по факту ведёт себя как Read Committed.                                                                                                                                                  |
| [[Read Committed]] (по умолчанию в PostgreSQL) | Видим только те данные, которые были закоммичены на момент **начала каждого запроса** внутри транзакции                                                                                                                                                                                                           |
| [[Repeatable Read]]                            | В рамках **всей** транзакции видим один и тот же снапшот данных — даже если кто-то параллельно их изменил и закоммитил, мы этого не увидим до конца своей транзакции                                                                                                                                              |
| [[Serializable]]                               | Самый строгий — гарантирует, что результат параллельных транзакций эквивалентен какому-то последовательному их выполнению. Защищает от всех аномалий параллелизма, но требует больше блокировок (в т.ч. предикатных), ретраев — снижает доступность и производительность, поэтому не используется «на всё подряд» |

## 8. Масштабирование баз данных

| Подход                                  | Суть                                                                                       | Для чего                                                                                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **[[Репликация]]**                      | Полное копирование базы на другие сервера                                                  | Отказоустойчивость, распределение нагрузки на чтение                                                                                         |
| **Шардирование** [[Шардинг (Sharding)]] | Разбиение базы (по таблицам/диапазонам) на части, размещённые на **разных серверах**       | Горизонтальное масштабирование объёма данных и нагрузки на запись                                                                            |
| **[[Партиционирование]]**               | Разбиение таблицы на более мелкие части **внутри одной базы/сервера** (по list/hash/range) | Ускорение запросов и обслуживания больших таблиц (например, вынести редко используемые JSONB-поля в отдельную таблицу, или разбить по датам) |

**Репликация подробнее:**

- По ролям: **[[master-slave]]** (один инстанс принимает запись, остальные — только на чтение) и **[[multi-master]]** (несколько инстансов пишут и читают одновременно — сложнее синхронизировать, риск конфликтов).

- По подтверждению: **[[Синхронная репликация]]** (мастер ждёт подтверждения от всех/части реплик перед тем, как считать запись завершённой — надёжнее, но ниже доступность и скорость), **[[Асинхронная репликация]]** (мастер не ждёт подтверждения от реплик — быстрее, но данные могут временно разойтись; на практике используется чаще), **[[Полусинхронная репликация]]** (ждём подтверждения хотя бы от одной реплики — компромисс).

- **Можно ли читать с мастера при асинхронной репликации?** Да, и иногда это **нужно** — например, для операции с балансом пользователя, где критично прочитать самое актуальное значение сразу после записи (реплика может ещё не успеть подтянуть последние изменения).

**[[Connection pool]] / [[PgBouncer]]**: при большом числе инстансов приложения и большом числе запросов может «расплодиться» слишком много одновременных соединений с БД. Решение — **пул соединений** ([[Connection pool]]), например через **[[PgBouncer]]** — прослойка, которая переиспользует ограниченное число реальных соединений с БД между множеством клиентских запросов.

## 9. [[N+1 проблема]]

Классическая проблема ORM: при получении списка из N связанных объектов сначала делается 1 запрос за самим списком, а затем **ещё N отдельных запросов** — по одному на каждую связанную сущность.

```python
# Плохо: N+1 — 1 запрос за orders + N запросов за user каждого order
orders = session.query(Order).all()
for order in orders:
    print(order.user.name)  # отдельный SELECT на каждой итерации
```

**Решения (термины из [[SQLAlchemy]], в [[Django ORM]] — аналоги [[select_related]]/[[prefetch_related]]):**

- **[[joinedload]] (join load)** — добавляет `JOIN` к связанной таблице прямо в основной запрос: один запрос вместо N+1. Минус — при связи «один ко многим» получаем декартово произведение строк (для каждой связанной строки — дублируется основная), поэтому подходит лучше для связей «многие к одному» / «один к одному».

- **[[selectinload]] (selection load)** — делает **один дополнительный** запрос вида `SELECT ... WHERE parent_id IN (...)` для всех связанных объектов сразу — вместо JOIN, что не даёт декартова произведения. Хорошо подходит для связей «один ко многим».

```python
from sqlalchemy.orm import selectinload

orders = session.query(Order).options(selectinload(Order.user)).all()
# теперь всего 2 запроса вместо N+1
```
