## ⚡ Быстрый ответ (шпаргалка перед собесом)

- **[[Монолит]]** — единая кодовая база, одно приложение, обычно один репозиторий. Плюсы: просто развернуть, быстро проверить гипотезу/[[MVP]], меньше сетевых издержек. Минусы: сложнее масштабировать точечно, при большой команде — конфликты в репозитории, высокая связанность кода.

- **[[Микросервисы]]** — приложение разбито на независимые сервисы, каждый отвечает за свою бизнес-функцию, обычно в отдельном репозитории. Плюсы: независимое масштабирование и [[Деплой]] каждого сервиса, разные команды работают независимо, меньше git-конфликтов. Минусы: сложнее настраивать взаимодействие между сервисами (сеть, издержки), сложнее деплоить и мониторить (свой [[CI и CD]] и релиз на каждый сервис), сложнее реализовать [[Распределённые транзакции]].

- **[[Распределённые транзакции]]** — бизнес-операция, затрагивающая несколько микросервисов, которую нужно выполнить атомарно (либо целиком, либо полностью откатить).

- **Способы обеспечить [[Атомарность]] в микросервисах**:
- **[[2PC]]** (two-phase commit, классический, но тяжёлый подход),
- **[[Saga]]** (последовательность локальных транзакций ([[Локальные транзакции]])с компенсирующими ([[Компенсирующие операции]]) действиями на случай сбоя), **[[Outbox pattern]]** (гарантия доставки события: запись в БД и запись в outbox-таблицу происходят в одной локальной транзакции ([[Локальные транзакции]]), событие в брокер отправляется только после этого).

- **[[Saga]]**: два вида — **хореография** ([[Хореография Saga]])(сервисы общаются между собой напрямую через события, без единого координатора) и **оркестрация** ([[Оркестрация Saga]])(есть центральный оркестратор — сервис/процесс, который дирижирует всей цепочкой вызовов, например через [[Airflow]] или собственный orchestrator-сервис). [[Хореография Saga vs Оркестрация Saga]]

- **[[Идемпотентность]]** — свойство операции: повторное выполнение с теми же входными данными не меняет результат повторно (важно для [[Retry]], чтобы, например, не списать/не начислить деньги дважды). Реализуется через [[Ключ Идемпотентности]]  / ключ [[Дедупликация]].

- **[[Паттерны GoF]]** делятся на 3 группы:

- **[[Порождающие паттерны GoF]]** (creational — как создавать объекты: Singleton, Factory, Builder), 
- **[[Структурные паттерны GoF]]** (structural — как компоновать объекты: Adapter, Decorator, Facade),
- **[[Поведенческие паттерны GoF]]** (behavioral — как объекты взаимодействуют: Observer, Strategy, Chain of Responsibility).

- **[[Kafka vs RabbitMQ]]**:

- [[Kafka]] работает по **pull-модели** (консьюмер сам читает из журнала событий в своём темпе, событие не удаляется после чтения — хранится по retention policy) и хорошо масштабируется горизонтально через партиции.

- [[RabbitMQ]] работает по **push-модели** (брокер сам «толкает» сообщение консьюмеру через очередь; после подтверждения обработки — сообщение удаляется из очереди), внутри есть exchange (маршрутизация) → queue.

- **[[Kafka]]: топики и партиции** — топик делится на партиции для параллельного чтения несколькими консьюмерами (число консьюмеров ≤ число партиций для полного параллелизма). Каждый консьюмер хранит **offset** — позицию последнего прочитанного сообщения.
- **[[Consumer lag]]** — ключевая метрика [[Kafka]]: разница между `log-end-offset` (сколько всего сообщений в партиции) и `current offset` консьюмера (сколько он уже прочитал) — показывает, насколько консьюмер отстаёт.

# 📖 Подробно

## 1. [[Монолит]] vs [[Микросервисы]]

| | Монолит | Микросервисы |
|---|---|---|
| Кодовая база | Единая, обычно один репозиторий | Разбита по сервисам, обычно разные репозитории |
| Деплой | Единый релиз | Свой релиз на каждый сервис |
| Масштабирование | Всего приложения целиком | Точечное — только нужный сервис |
| Командная работа | Больше git-конфликтов при большой команде | Команды независимы, меньше конфликтов |
| Сложность инфраструктуры | Ниже | Выше (сеть, мониторинг, деплой каждого сервиса) |
| Когда выбирать | Быстрый MVP, проверка гипотезы, небольшая команда | Крупный продукт, нужна независимость команд и масштабирования |

[[Микросервисы]] обычно **не общаются друг с другом напрямую синхронно** (хотя технически могут) — чаще выстраивается событийная ([[event-driven]]) архитектура через брокер сообщений, чтобы снизить связанность.

## 2. [[Распределённые транзакции]] 

Когда бизнес-операция затрагивает несколько микросервисов (например, банковская операция: списание с одного счёта, зачисление на другой, запись в историю, уведомление), а каждый сервис работает со своей базой данных — обычная  [[Реляционная транзакция]] ([[BEGIN]]/[[COMMIT]]/[[ROLLBACK]]`) не подходит, потому что она ограничена одной базой. Нужно обеспечить атомарность **на уровне всей цепочки сервисов**.

**Подходы:**

1. **[[2PC]] (Two-Phase Commit)** — классический протокол: фаза подготовки (все участники подтверждают готовность закоммитить) → фаза коммита (если все готовы — коммитим везде, если хоть один отказал — откатываем везде). Тяжёлый, снижает доступность системы (все участники блокируются на время согласования), в микросервисах используется редко.

2. **[[Saga]]** — последовательность **локальных** транзакций в каждом сервисе, где для каждого шага предусмотрено **компенсирующее действие** на случай сбоя. Если что-то пошло не так на шаге N — Saga последовательно «откатывает назад» через компенсирующие действия шаги N-1, N-2, ... до начала.

   - **[[Хореография Saga]] (choreography)** — сервисы взаимодействуют между собой напрямую через события (публикуют/подписываются), нет единого координатора.
   
   - **[[Оркестрация Saga]] (orchestration)** — есть выделенный оркестратор (сервис или инструмент вроде [[Airflow]]), который явно вызывает шаги по очереди и решает, что делать при сбое.

3. **[[Outbox pattern]]** — решает проблему «как гарантированно доставить событие в брокер, если основная запись в БД и отправка события — это по сути два разных действия, между которыми может произойти сбой». Решение: в рамках **одной** локальной транзакции сервис пишет и в основную таблицу, и в отдельную `outbox`-таблицу («у нас событие готово к отправке»). Отдельный процесс читает `outbox`-таблицу и отправляет события в брокер (например, [[Kafka]]), помечая их как отправленные только после подтверждения. Это гарантирует, что событие не потеряется, даже если сервис упал сразу после коммита в БД.

**[[Идемпотентность]] и [[Retry]]**: при сбое (например, между 3 и 4 шагом [[Saga]]) система может попытаться повторить операцию ([[Retry]]). Чтобы повторный [[Retry]] не привёл к двойному списанию/начислению средств, каждая операция должна быть **идемпотентной** — то есть повторное выполнение с теми же данными не должно повторно менять состояние системы. Практическая реализация — ** [[Ключ Идемпотентности]]** (уникальный ключ операции), по которому сервис проверяет: «эта операция уже была выполнена?» — и если да, просто возвращает предыдущий результат, не выполняя действие повторно.

## 3. Паттерны проектирования (GoF) [[Паттерны GoF]]

Классические паттерны GoF (Gang of Four) делятся на 3 группы:

| Группа                                          | Что решает                                                 | Примеры                                              |
| ----------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| **[[Порождающие паттерны GoF]] (Creational)**   | Как создавать объекты                                      | Singleton, Factory Method, Abstract Factory, Builder |
| **[[Структурные паттерны GoF]] (Structural)**   | Как компоновать объекты и классы в более крупные структуры | Adapter, Decorator, Facade, Proxy                    |
| **[[Поведенческие паттерны GoF]] (Behavioral)** | Как объекты взаимодействуют и распределяют ответственность | Observer, Strategy, Chain of Responsibility, Command |

Самые часто упоминаемые на собесах:

- **[[Singleton]]** — гарантирует, что у класса есть только один экземпляр (например, соединение с конфигурацией/логгером).
- 
- **[[Factory]]** — выносит логику создания объектов в отдельный метод/класс, скрывая конкретную реализацию от клиентского кода.
- 
- **[[Adapter]]** — «переводчик» между двумя несовместимыми интерфейсами.

## 4. Брокеры сообщений: [[Kafka vs RabbitMQ]]

|                    | [[Kafka]]                                                                                                                     | [[RabbitMQ]]                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Модель             | **Pull** — консьюмер сам читает из журнала событий [[Журнал событий в Kafka]]                                                 | **Push** — брокер сам доставляет сообщение подписанному консьюмеру                                               |
| Хранение сообщений | Хранятся в журнале (лог) на диске какое-то время (по retention: по времени или по объёму), не удаляются сразу после прочтения | Сообщение обычно удаляется из очереди после подтверждения обработки (ack)[[ACK и NACK]]                          |
| Маршрутизация      | Топики → партиции [[Partition]]                                                                                               | [[Exchange]] (маршрутизация сообщений) → [[Queue]] (очередь)→[[Consumer в RabbitMQ]]→[[ACK и NACK]]→[[Prefetch]] |
| Масштабирование    | Отлично масштабируется горизонтально за счёт партиционирования топиков по кластеру брокеров                                   | Масштабируется, но обычно хуже подходит для очень высоких объёмов событий                                        |
| Когда использовать | Много событий, нужна история/replay, аналитика в реальном времени, высоконагруженные системы                                  | Классические очереди задач, где важна гибкая маршрутизация и приоритеты                                          |

**[[Kafka]] — устройство подробнее:**

- **Топик (**[[Topic]]) — логический поток событий, делится на **партиции** [[Partition]] для параллельной обработки несколькими консьюмерами  [[Consumer в Kafka]](если партиций 5 — для полного параллелизма нужно 5 консьюмеров в группе; больше консьюмеров, чем партиций — лишние будут простаивать).

- **[[Offset]]**— позиция сообщения в партиции [[Partition]]; каждый консьюмер [[Consumer в Kafka]] хранит, до какого offset он дочитал — это позволяет продолжить чтение с нужного места после падения/перезапуска (аналогия — «закладка в книге»).

- **[[Consumer lag]] ** — ключевая метрика мониторинга [[Kafka]]. Считается как разница между [[Log End Offset (LEO) в Kafka]] (общее число сообщений, накопленных в партиции) и [[Current Offset в Apache Kafka]] (сколько сообщений консьюмер уже прочитал). Большой lag = консьюмер не успевает обрабатывать поток событий.

- **[[Retention]]** — период хранения сообщений в журнале, настраивается по времени и/или по объёму диска.
