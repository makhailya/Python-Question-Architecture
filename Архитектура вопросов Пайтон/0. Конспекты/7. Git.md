# [[Git]]: [[Репозиторий]], [[Коммиты - Commit]], [[Ветки - Branch]], [[Merge]], [[Rebase]], [[GitHub]], [[Конфликты]], [[Stash]]

## ⚡ Быстрый ответ (шпаргалка перед собесом)

* **[[Git]]** — распределённая система контроля версий. Позволяет хранить историю изменений, работать параллельно в [[Ветки - Branch]], откатывать изменения и синхронизировать код между разработчиками.

* **[[Репозиторий]]** — директория проекта, в которой Git хранит историю изменений и служебную информацию в каталоге `.git`.

* Основной цикл Git:

```text
Working Directory
       ↓
git add
       ↓
Staging Area
       ↓
git commit
       ↓
Local Repository
       ↓
git push
       ↓
Remote Repository
```

* **[[Коммиты - Commit]]** — зафиксированное состояние проекта в определённый момент времени. Каждый коммит имеет уникальный [[Hash|хеш]].

* **[[Staging Area]]** — промежуточная область, куда мы помещаем изменения, которые хотим включить в следующий коммит.

* **`git add`** — добавляет изменения в staging area.

* **`git commit`** — создаёт новый коммит из содержимого staging area.

* **`git push`** — отправляет локальные коммиты в удалённый репозиторий.

* **`git pull`** — получает изменения из remote и интегрирует их в текущую ветку. По сути:

```text
git fetch + git merge
```

* **`git fetch`** — получает изменения с remote, но не изменяет текущую рабочую ветку.

* **[[Ветки - Branch]]** — отдельная линия разработки. В Git ветка — это указатель на коммит.

* **[[Merge]]** — объединяет две истории. При наличии расходящихся изменений может создать отдельный [[Merge Commit]].

* **[[Rebase]]** — переносит коммиты текущей ветки поверх другой ветки. История становится линейнее, но хеши перенесённых коммитов изменяются.

* **[[merge vs rebase]]**:

  * [[Merge]] сохраняет историю ветвления;
  * [[Rebase]] переписывает историю коммитов.

* **[[Конфликт слияния]]** возникает, когда Git не может автоматически определить, какую версию изменения оставить.

* **`git stash`** — временно сохраняет незакоммиченные изменения, чтобы можно было переключиться на другую ветку.

* **`git reset`** перемещает указатель `HEAD` и в зависимости от режима может изменять staging area и рабочие файлы:

  * `--soft` — только `HEAD`;
  * `--mixed` — `HEAD` + staging;
  * `--hard` — `HEAD` + staging + рабочие файлы.

* **`git revert`** не удаляет старый коммит, а создаёт новый коммит, отменяющий его изменения. Для общей истории обычно безопаснее, чем `reset`.

* **`HEAD`** — ссылка на текущий коммит/текущее положение ветки.

* **[[Remote Repository]]** — удалённый репозиторий, например на [[GitHub]] или [[GitLab]].

* **`origin`** — стандартное имя удалённого репозитория, которое Git обычно создаёт при `git clone`.

* **`.gitignore`** — файл с правилами, какие файлы Git не должен отслеживать.

# 📖 Подробно

## 1. [[Git]] и [[Система контроля версий]]

[[Git]] — распределённая система контроля версий.

Она позволяет:

* хранить историю изменений;
* видеть, кто и когда изменил код;
* возвращаться к предыдущим версиям;
* создавать отдельные ветки;
* объединять работу нескольких разработчиков;
* работать без постоянного подключения к серверу.

Главное отличие распределённой системы:

> У разработчика есть **полная локальная копия истории репозитория**, а не только рабочая версия файлов.

## 2. [[Репозиторий]]

После:

```bash
git init
```

Git создаёт скрытую директорию:

```text
.git/
```

В ней хранится служебная информация Git:

```text
project/
├── .git/
├── src/
├── tests/
└── README.md
```

**Важно:** удаление `.git` удалит историю Git для этой директории, но сами файлы проекта останутся.

## 3. Три состояния файла

Одна из самых важных концепций Git:

```text
Working Directory
       ↓ git add
Staging Area
       ↓ git commit
Repository
```

### Working Directory

Текущее состояние файлов проекта.

Например:

```python
print("Hello")
```

Ты изменил код — Git видит изменение, но оно ещё не входит в следующий коммит.

---

### [[Staging Area]]

Промежуточная область.

```bash
git add main.py
```

Теперь Git понимает:

> Изменения `main.py` нужно включить в следующий коммит.

---

### Repository

После:

```bash
git commit -m "Add greeting"
```

изменение становится частью истории Git.

---

## 4. [[Коммит]]

Коммит — это зафиксированное состояние проекта.

Пример:

```bash
git commit -m "Add user authentication"
```

Коммит содержит информацию о:

* состоянии файлов;
* родительском коммите;
* авторе;
* времени;
* сообщении;
* собственном идентификаторе.

Git идентифицирует коммит по [[Hash|хешу]].

Например:

```text
a81f9e2...
```

Можно посмотреть историю:

```bash
git log
```

Кратко:

```bash
git log --oneline
```

---

## 5. [[HEAD]]

`HEAD` показывает, где сейчас находится текущая позиция Git.

Например:

```text
A → B → C
        ↑
       HEAD
```

Если текущая ветка указывает на `C`, то `HEAD` находится на `C`.

Проверить состояние:

```bash
git status
```

---

## 6. [[Ветки - Branch]]

В Git ветка — это указатель на коммит.

Например:

```text
A → B → C
        ↑
      main
```

Создаём новую ветку:

```bash
git branch feature/auth
```

Переключаемся:

```bash
git switch feature/auth
```

Или:

```bash
git checkout feature/auth
```

Современный Git предпочтительно использовать через `switch` для переключения веток.

Можно сразу создать и переключиться:

```bash
git switch -c feature/auth
```

---

## 7. [[Merge]]

Предположим:

```text
A → B → C        main
     \
      D → E      feature
```

Мы закончили работу над feature:

```bash
git switch main
git merge feature
```

Git объединяет истории.

При необходимости появляется merge commit:

```text
A → B → C ───── F
     \         /
      D → E ──
```

### Когда использовать merge?

Когда важно сохранить реальную историю ветвления.

---

## 8. [[Rebase]]

При `rebase` Git переносит коммиты одной ветки поверх другой.

Было:

```text
A → B → C       main
     \
      D → E     feature
```

После:

```bash
git switch feature
git rebase main
```

получаем:

```text
A → B → C → D' → E'
```

Обрати внимание:

```text
D ≠ D'
E ≠ E'
```

Хеши изменяются, потому что фактически создаются новые коммиты.

### Главное правило

> Не стоит бездумно делать `rebase` публичной ветки, которую уже используют другие разработчики.

---

## 9. [[merge vs rebase]]

|                                | Merge               | Rebase                  |
| ------------------------------ | ------------------- | ----------------------- |
| История                        | Сохраняет ветвление | Делает историю линейнее |
| Создаёт merge commit           | Может               | Нет                     |
| Переписывает коммиты           | Нет                 | Да                      |
| Меняет hash коммитов           | Нет                 | Да                      |
| Безопасность для общей истории | Выше                | Требует осторожности    |

Формула:

> **Merge сохраняет историю, Rebase переписывает историю.**

Например:

## 11. `git clone`

Клонирование:

```bash
git clone https://github.com/user/project.git
```

Git:

1. скачивает репозиторий;
2. создаёт `.git`;
3. настраивает remote `origin`;
4. создаёт локальную рабочую копию.

## 12. `git fetch`

```bash
git fetch origin
```

Получает изменения с сервера.

Но:

> **не объединяет их автоматически с текущей веткой.**

Можно посмотреть изменения отдельно.

## 13. `git pull`

```bash
git pull
```

В упрощённом виде:

```text
git fetch
+
git merge
```

В зависимости от настроек Git может использовать и другую стратегию интеграции, например rebase.

## 14. `git push`

```bash
git push origin main
```

Отправляет локальные коммиты в remote.

Типичный цикл:

```bash
git add .
git commit -m "Add feature"
git push
```

## 15. [[Конфликт слияния]]

Конфликт возникает, когда Git не может автоматически объединить изменения.

Например, два разработчика изменили одну строку:

```text
<<<<<<< HEAD
print("Hello")
=======
print("Hi")
>>>>>>> feature
```

Разработчик должен вручную выбрать правильный вариант.

После исправления:

```bash
git add file.py
git commit
```

При rebase:

```bash
git add file.py
git rebase --continue
```

Отменить merge:

```bash
git merge --abort
```

Отменить rebase:

```bash
git rebase --abort
```

---

## 16. `git stash`

Допустим, ты работаешь:

```text
feature/payment
```

Есть незакоммиченные изменения, но срочно нужно переключиться на `main`.

Можно временно сохранить изменения:

```bash
git stash
```

Переключиться:

```bash
git switch main
```

Вернуться:

```bash
git switch feature/payment
```

Вернуть изменения:

```bash
git stash pop
```

Посмотреть список:

```bash
git stash list
```

## 17. `reset` vs `revert`

### `git reset`

Перемещает `HEAD`.

```bash
git reset --soft HEAD~1
```

Последний коммит убран из истории ветки, но изменения остаются staged.

---

### `--mixed`

```bash
git reset --mixed HEAD~1
```

Коммит убирается, изменения остаются в рабочей директории.

Это стандартное поведение `reset`.

---

### `--hard`

```bash
git reset --hard HEAD~1
```

Перемещает `HEAD` и удаляет изменения из staging и рабочей директории.

⚠️ Использовать осторожно.

---

### `git revert`

```bash
git revert <commit>
```

Создаёт новый коммит, который отменяет изменения указанного коммита.

Например:

```text
A → B → C
```

После:

```bash
git revert C
```

получаем:

```text
A → B → C → D
```

Где `D` отменяет изменения `C`.

### Формула

> **Reset переписывает историю, revert добавляет новую отмену в историю.**

## 19. Типичный рабочий процесс разработчика

```bash
git clone <url>

git switch -c feature/auth

# пишем код

git status
git add .
git commit -m "Add authentication"

git fetch origin
git rebase origin/main

git push -u origin feature/auth
```

После этого создаётся Pull Request / Merge Request.

```text
Feature branch
      ↓
Commit
      ↓
Push
      ↓
Pull Request / Merge Request
      ↓
Code Review
      ↓
Merge
      ↓
main
```
