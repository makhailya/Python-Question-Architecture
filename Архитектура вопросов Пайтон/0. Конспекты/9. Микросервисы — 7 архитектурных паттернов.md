# Микросервисы — 7 архитектурных паттернов

## Формула для собеседования

**Микросервисные паттерны** решают типичные проблемы распределённых систем: миграцию с монолита, маршрутизацию запросов, независимость данных, надёжную доставку событий, повторную обработку сообщений, распределённые транзакции и отказоустойчивость.

| Паттерн                      | Какую проблему решает                                      |
| ---------------------------- | ---------------------------------------------------------- |
| [[#1. Strangler Fig]]        | Позволяет постепенно заменить монолит микросервисами       |
| [[#2. API Gateway]]          | Создаёт единую точку входа для клиентов                    |
| [[#3. Database per Service]] | Устраняет прямую зависимость сервисов от чужих баз данных  |
| [[#4. Transactional Outbox]] | Предотвращает потерю событий между БД и брокером сообщений |
| [[#5. Idempotent Consumer]]  | Защищает от повторной обработки сообщений                  |
| [[#6. Saga]]                 | Координирует бизнес-операции в нескольких сервисах         |
| [[#7. Circuit Breaker]]      | Ограничивает последствия отказа зависимого сервиса         |

**Главная мысль:** микросервисы упрощают независимую разработку и масштабирование, но добавляют сетевые ошибки, проблемы согласованности данных и необходимость управлять отказами.

---

## Короткий ответ

Микросервисная архитектура предполагает разделение приложения на независимо развиваемые сервисы. Однако само разделение не решает всех проблем.

Для безопасного перехода используют Strangler Fig, для маршрутизации — API Gateway, для изоляции данных — Database per Service. Transactional Outbox помогает надёжно публиковать события, Idempotent Consumer предотвращает повторные бизнес-операции, Saga координирует изменения между сервисами, а Circuit Breaker защищает систему от каскадных отказов.

Выбирать паттерны нужно исходя из реальной проблемы, а не ради усложнения архитектуры.

---

## Ответ на собеседовании

При проектировании микросервисной системы я рассматриваю паттерны в зависимости от возникающих проблем.

- При миграции с монолита использую Strangler Fig, чтобы переносить функциональность постепенно.
- Для единой точки входа и централизованной маршрутизации применяю API Gateway.
- Для независимости сервисов закрепляю данные за их владельцами с помощью Database per Service.
- Для надёжной публикации событий использую Transactional Outbox.
- Для защиты от дублирования бизнес-операций реализую идемпотентную обработку сообщений.
- Для согласования операций между несколькими сервисами использую Saga с компенсирующими действиями.
- Для предотвращения каскадных отказов применяю Circuit Breaker вместе с таймаутами и подходящими механизмами повторных попыток.

При этом каждый паттерн увеличивает сложность системы, поэтому его внедрение должно быть оправдано требованиями проекта.

# 1. Strangler Fig

**Strangler Fig — паттерн постепенной замены монолита микросервисами.**

### Какую проблему решает

Полностью переписывать работающий монолит рискованно: миграция может затянуться, а новая система потребует длительного тестирования.

Strangler Fig позволяет переносить функциональность частями, сохраняя работоспособность старого приложения.

### Как работает

1. Выбираем отдельный функциональный модуль монолита.
2. Реализуем его в новом микросервисе.
3. Настраиваем маршрутизацию запросов в новый сервис.
4. Остальные запросы продолжают обрабатываться монолитом.
5. Постепенно переносим следующие модули.
6. Когда старый функционал больше не нужен, удаляем соответствующую часть монолита.

### Пример

Есть интернет-магазин с монолитным приложением. Сначала из него выносят каталог товаров, затем оплату, после этого уведомления.

```text
                   Клиент
                      |
                Маршрутизатор
                      |
           +----------+----------+
           |                     |
       Монолит              Микросервисы
           |                     |
    Старые функции        Каталог / Оплата
```

Маршрутизацию можно реализовать на уровне reverse proxy, API Gateway или самого приложения.

### Преимущества

- Не нужно переписывать всю систему одновременно.
- Можно постепенно проверять новые сервисы в работе.
- Снижается риск масштабного отказа при миграции.
- Команда может переносить функциональность поэтапно.

### Недостатки

- Некоторое время одновременно существуют монолит и микросервисы.
- Нужно поддерживать маршрутизацию между старой и новой архитектурой.
- Могут возникнуть проблемы с согласованностью данных.
- Миграция требует контроля зависимостей и постепенного переключения трафика.

### Когда применять

Когда монолит уже сложно развивать, но полностью заменить его одним релизом невозможно или слишком рискованно.

### Когда не нужен

Если приложение небольшое, работает стабильно и не испытывает проблем с независимостью команд или масштабированием, миграция на микросервисы может не дать достаточной выгоды.

### Как запомнить

**Strangler Fig = постепенно заменяем монолит, не останавливая развитие системы.**

# 2. API Gateway

**API Gateway — единая точка входа для клиентских запросов к микросервисам.**

### Какую проблему решает

Без Gateway клиентам приходится знать адреса нескольких сервисов. Кроме того, маршрутизация, проверка токенов и ограничение частоты запросов могут дублироваться в каждом сервисе.

API Gateway позволяет централизовать общие задачи на внешнем уровне.

### Как работает

1. Клиент отправляет запрос на единый адрес.
2. Gateway определяет целевой сервис.
3. При необходимости проверяет токен и ограничивает частоту запросов.
4. Перенаправляет запрос нужному сервису.
5. Возвращает клиенту ответ.

### Пример маршрутизации

```text
GET /api/products/15
          |
          v
      API Gateway
          |
          v
   Product Service
          |
          v
       PostgreSQL
```

### Пример на FastAPI

Упрощённый пример проксирования запроса:

```python
import httpx

from fastapi import FastAPI, HTTPException
from fastapi.responses import Response

app = FastAPI()

client = httpx.AsyncClient(timeout=2.0)


@app.get("/products/{product_id}")
async def get_product(product_id: int):
    try:
        reply = await client.get(
            f"http://product-service/products/{product_id}"
        )
    except httpx.RequestError:
        raise HTTPException(
            status_code=503,
            detail="Product service unavailable",
        ) from None

    return Response(
        content=reply.content,
        status_code=reply.status_code,
    )
```

**Что здесь происходит:**

- `AsyncClient` выполняет асинхронные HTTP-запросы.
- `timeout=2.0` ограничивает время ожидания ответа.
- `client.get()` обращается к внутреннему сервису.
- `httpx.RequestError` позволяет обработать ошибки сетевого запроса.
- `HTTPException(503)` сообщает клиенту, что зависимый сервис недоступен.
- `Response` возвращает тело и HTTP-статус полученного ответа.

Это учебный пример. Полноценный Gateway должен учитывать заголовки, передачу ошибок, WebSocket, потоковые ответы, управление соединениями и другие особенности HTTP-проксирования.

### Какие задачи можно вынести в Gateway

- Маршрутизация запросов.
- Проверка аутентификации.
- Rate limiting — ограничение частоты запросов.
- Логирование входящего трафика.
- Некоторые операции преобразования запросов и ответов.

**Важно:** проверка токена не заменяет авторизацию на уровне конкретного сервиса. Сам сервис должен проверять права на выполнение операции.

### Преимущества

- Клиенту достаточно знать один внешний адрес.
- Общая инфраструктурная логика меньше дублируется.
- Удобнее управлять внешним API.
- Можно централизовать некоторые механизмы защиты.

### Недостатки

- Gateway может стать единой точкой отказа.
- Дополнительный сетевой переход увеличивает задержку.
- Сам Gateway требует масштабирования и мониторинга.
- Ошибка в маршрутизации может затронуть сразу несколько сервисов.

### Примеры технологий

- Kong.
- Envoy.
- KrakenD.
- Nginx — для более простых сценариев маршрутизации и проксирования.

### Как запомнить

**API Gateway = единый вход, маршрутизация и общие задачи на границе системы.**

# 3. Database per Service

**Database per Service — паттерн, при котором каждый микросервис владеет собственными данными.**

### Какую проблему решает

Если несколько сервисов напрямую работают с одними таблицами, изменение схемы одним сервисом может сломать остальные.

Формально сервисы разделены, но фактически продолжают зависеть друг от друга через общую базу данных.

### Как работает

Каждый сервис:

- Управляет собственными данными.
- Определяет структуру своих таблиц.
- Выполняет миграции своей схемы.
- Предоставляет другим сервисам доступ к данным через API или события.

```text
Product Service  ---> Product DB

Order Service    ---> Order DB

Payment Service  ---> Payment DB
```

Другой сервис не должен напрямую читать или изменять таблицы владельца.

### Важное уточнение

Database per Service не обязательно означает отдельный физический сервер для каждого сервиса.

Несколько баз данных или схем могут находиться в одном кластере PostgreSQL. Важно, чтобы границы владения данными и доступ к ним были организованы правильно.

### Как получить чужие данные

**Вариант 1. Синхронный запрос**

Order Service обращается к Product Service через HTTP API.

Преимущество: можно получить актуальный ответ непосредственно от владельца данных.

Недостаток: заказ становится зависимым от доступности Product Service.

**Вариант 2. Асинхронные события**

Product Service публикует событие об изменении товара. Другие сервисы получают событие и поддерживают собственные представления нужных данных.

Преимущество: меньше синхронных зависимостей.

Недостаток: данные могут обновляться с задержкой.

### Преимущества

- Независимые миграции.
- Меньшая связанность между командами.
- Возможность выбирать разные технологии хранения.
- Чёткое владение данными.

### Недостатки

- Нельзя без дополнительных механизмов выполнить обычный `JOIN` между таблицами разных сервисов.
- Сложнее собирать данные для отчётов.
- Межсервисные операции требуют дополнительных механизмов согласованности.
- Возникают проблемы временной недоступности сервисов и устаревших данных.

### Когда применять

Когда независимость сервисов важнее простоты централизованного доступа к данным.

### Как запомнить

**Database per Service = данные принадлежат сервису, а не всей системе одновременно.**

# 4. Transactional Outbox

**Transactional Outbox — паттерн надёжной публикации событий после изменения данных в базе.**

### Какую проблему решает

Предположим, сервис сохраняет заказ в PostgreSQL, а затем публикует событие `OrderCreated` в RabbitMQ.

Если процесс упадёт между этими действиями, заказ сохранится, но событие не будет отправлено.

```text
1. Заказ сохранён в PostgreSQL.
2. Приложение падает.
3. Событие не отправлено.
4. Другие сервисы не узнают о заказе.
```

Это проблема двойной записи: нужно согласовать изменение в БД и отправку сообщения в брокер.

### Как работает

Вместо немедленной отправки события приложение записывает его в таблицу `outbox` в той же транзакции, в которой сохраняет бизнес-данные.

```text
             Одна транзакция
                   |
          +--------+--------+
          |                 |
      Сохранение         Запись события
        заказа            в outbox
          |                 |
          +--------+--------+
                   |
                 COMMIT
                   |
                   v
              Outbox Worker
                   |
                   v
              RabbitMQ
                   |
                   v
             Другие сервисы
```

### Пример на Python

```python
async with conn.transaction():
    await conn.execute(
        """
        INSERT INTO orders (id, status)
        VALUES ($1, $2)
        """,
        order_id,
        "created",
    )

    await conn.execute(
        """
        INSERT INTO outbox (event_id, payload)
        VALUES ($1, $2::jsonb)
        """,
        event_id,
        payload,
    )
```

В примере используется интерфейс асинхронной работы с PostgreSQL, поддерживающий транзакционный контекст.

**Логика:**

1. Сохраняем заказ.
2. Сохраняем событие в `outbox`.
3. Фиксируем транзакцию.
4. Фоновый обработчик читает новые события и отправляет их в брокер.

Если транзакция откатится, не сохранится ни заказ, ни событие.

### Что делает Outbox Worker

1. Находит необработанные события.
2. Отправляет их в брокер.
3. Дожидается подтверждения публикации.
4. Отмечает событие отправленным.
5. При ошибке повторяет попытку.

Для конкурентной обработки нескольких событий могут потребоваться блокировки, например `FOR UPDATE SKIP LOCKED`, либо другой механизм координации обработчиков.

### Гарантии доставки

Transactional Outbox обычно обеспечивает возможность повторной публикации события, пока оно не будет успешно отправлено.

Однако **он не гарантирует доставку ровно один раз**.

Возможна ситуация:

1. Worker отправил сообщение.
2. Брокер принял его.
3. Worker упал до отметки об успешной отправке.
4. После восстановления сообщение отправляется повторно.

Поэтому Outbox часто используют совместно с [[#5. Idempotent Consumer]].

### Преимущества

- Снижается риск потери событий при падении приложения.
- Бизнес-изменение и запись события фиксируются атомарно.
- Можно повторять публикацию после восстановления брокера.
- События сохраняются для диагностики и восстановления.

### Недостатки

- Нужна дополнительная таблица и фоновый обработчик.
- Необходимо очищать старые записи.
- Требуются повторные попытки и мониторинг.
- Дубликаты событий всё ещё возможны.

### Альтернатива

CDC (Change Data Capture) — механизм отслеживания изменений базы данных, позволяющий публиковать изменения из журнала транзакций или другого источника изменений.

### Как запомнить

**Transactional Outbox = сначала атомарно сохраняем данные и событие в БД, затем публикуем событие.**

# 5. Idempotent Consumer

**Idempotent Consumer — паттерн, при котором повторная доставка одного события не приводит к повторному выполнению бизнес-операции.**

### Какую проблему решает

Брокеры сообщений могут доставлять одно событие несколько раз.

Например, сервис обработал платёж, но упал до подтверждения сообщения. Брокер решил, что сообщение не обработано, и отправил его повторно.

Если повторная обработка снова спишет деньги, пользователь заплатит дважды.

### Что такое идемпотентность

Операция идемпотентна, если её повторное выполнение не изменяет конечный результат после первого успешного выполнения.

Например:

```python
user.active = True
```

Повторное присваивание `True` не меняет итоговое состояние.

Но операция:

```python
user.balance += 100
```

не идемпотентна: каждый повтор увеличивает баланс.

### Как работает Idempotent Consumer

1. Каждое событие получает уникальный `event_id`.
2. Потребитель получает сообщение.
3. Проверяет, обрабатывалось ли событие раньше.
4. Если да — пропускает повторную обработку.
5. Если нет — выполняет бизнес-операцию и фиксирует идентификатор.

Для хранения идентификаторов можно использовать таблицу `inbox`.

```text
             Получено событие
                    |
                    v
          Проверка event_id в inbox
                    |
             +------+------+
             |             |
         Уже есть       Нет записи
             |             |
         Пропустить     Выполнить
         сообщение      операцию
                           |
                           v
                  Сохранить event_id
```

### Пример структуры таблицы

```sql
CREATE TABLE inbox (
    consumer_name TEXT NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (consumer_name, event_id)
);
```

Составной первичный ключ позволяет одному событию обрабатываться разными потребителями, но не повторно одним и тем же потребителем.

### Важный момент: одна транзакция

Если обработка изменяет данные в PostgreSQL, запись в `inbox` и бизнес-изменение нужно выполнять в одной транзакции.

Упрощённая схема:

```python
async with conn.transaction():
    inserted = await conn.fetchval(
        """
        INSERT INTO inbox (consumer_name, event_id)
        VALUES ($1, $2)
        ON CONFLICT DO NOTHING
        RETURNING event_id
        """,
        "notification-service",
        event_id,
    )

    if inserted is None:
        return

    await process_business_operation(conn, payload)
```

Здесь `process_business_operation()` — условная функция, выполняющая бизнес-операцию в той же транзакции.

Если два обработчика одновременно получат одно сообщение, ограничение уникальности в БД поможет не допустить двойной обработки. При этом обработчик должен корректно учитывать результат конкурентной вставки и завершение транзакции.

### Когда этого недостаточно

Если операция вызывает внешнее действие, например отправляет письмо или обращается к платёжному провайдеру, одной таблицы `inbox` недостаточно для полной защиты от дубликатов.

Нужно отдельно продумать идемпотентность внешнего вызова, например использовать поддерживаемый провайдером ключ идемпотентности.

### Преимущества

- Защищает от повторной обработки сообщений.
- Позволяет безопасно повторять доставку.
- Снижает риск двойных списаний и повторных уведомлений.

### Недостатки

- Нужно хранить идентификаторы обработанных событий.
- Необходимо учитывать параллельную обработку.
- Внешние действия требуют дополнительных механизмов защиты.

### Как запомнить

**Idempotent Consumer = повторная доставка возможна, но повторная бизнес-операция не выполняется.**

# 6. Saga

**Saga — паттерн координации бизнес-транзакции, которая состоит из нескольких локальных транзакций в разных сервисах.**

### Какую проблему решает

В монолите несколько изменений можно выполнить в одной транзакции PostgreSQL.

Но в микросервисной архитектуре сервисы владеют разными базами. Обычная транзакция PostgreSQL не объединяет произвольные операции этих сервисов в один общий `COMMIT` или `ROLLBACK`.

Saga решает задачу на уровне бизнес-процесса.

### Как работает

1. Выполняется первая локальная транзакция.
2. При успехе запускается следующая операция.
3. Процесс продолжается до завершения всех шагов.
4. Если продолжить невозможно, запускаются компенсирующие операции.

Компенсация исправляет бизнес-последствия уже выполненного шага. Она не является буквальным откатом ранее зафиксированной транзакции.

### Пример: оформление подписки

```text
Создать покупку
      |
      v
Списать деньги
      |
      v
Активировать подписку
      |
      +------ Успех ------> Завершить покупку
      |
      +------ Ошибка -----> Вернуть деньги
```

Если деньги списаны, но подписку активировать невозможно, система инициирует возврат средств.

### Пример на Python

```python
payment = await payments.charge(
    purchase_id,
    amount,
)

try:
    await music.activate_subscription(
        user_id,
        purchase_id=purchase_id,
    )
except ActivationFailed:
    await payments.refund(
        payment.id,
        purchase_id=purchase_id,
    )
    raise
```

Это упрощённый пример оркестрации.

В production-системе необходимо учитывать повторные попытки, таймауты, сохранение состояния Saga и возможность ошибки самой компенсации.

### Два способа реализации

**1. Оркестрация**

Отдельный компонент управляет последовательностью шагов.

```text
          Saga Orchestrator
             /         \
            v           v
      Payment Service  Music Service
```

Преимущества:
- Последовательность процесса видна в одном месте.
- Проще отслеживать состояние выполнения.
- Удобнее управлять компенсациями.

Недостатки:
- Оркестратор становится дополнительным компонентом.
- Он содержит логику координации процесса.

**2. Хореография**

Сервисы реагируют на события друг друга и самостоятельно запускают следующие операции.

```text
OrderCreated
     |
     v
PaymentCompleted
     |
     v
SubscriptionActivated
```

Преимущества:
- Нет единого оркестратора для всех шагов.
- Сервисы взаимодействуют через события.

Недостатки:
- Сложнее понять общую последовательность процесса.
- Труднее отслеживать ошибки и зависимости.
- При большом количестве участников процесс может стать запутанным.

### Связь с Transactional Outbox

Saga может использовать Transactional Outbox для надёжной публикации событий между участниками процесса.

Эти паттерны решают разные задачи:

- Saga управляет бизнес-процессом.
- Outbox помогает надёжно публиковать события.

### Преимущества

- Позволяет согласовывать операции между сервисами.
- Не требует одной общей транзакции на все базы.
- Поддерживает бизнес-компенсации при ошибках.

### Недостатки

- Нужно хранить состояние процесса.
- Необходимо продумывать компенсации.
- Повторные запросы должны быть безопасными.
- Возможны ошибки и во время компенсации.
- Согласованность обычно достигается не мгновенно.

### Как запомнить

**Saga = последовательность локальных транзакций плюс компенсации при неудаче.**

# 7. Circuit Breaker

**Circuit Breaker — паттерн, который временно прекращает обращения к проблемному сервису.**

### Какую проблему решает

Представим, что Product Service обычно отвечает за 100 мс, но из-за перегрузки начинает отвечать за 10 секунд.

Другие сервисы продолжают отправлять запросы и ждать ответы. Со временем накапливаются незавершённые запросы, расходуются соединения и рабочие ресурсы.

В итоге проблема одного сервиса может вызвать отказ других.

Circuit Breaker помогает ограничить распространение такого отказа.

### Три состояния

| Состояние | Что происходит |
|---|---|
| `CLOSED` | Запросы проходят в обычном режиме, ошибки отслеживаются |
| `OPEN` | Запросы к проблемному сервису блокируются |
| `HALF_OPEN` | Пропускаются пробные запросы для проверки восстановления |

### Как работает

1. Сервис обращается к зависимому компоненту.
2. Circuit Breaker отслеживает ошибки и другие настроенные показатели.
3. Если порог срабатывания достигнут, переходит в `OPEN`.
4. Запросы временно блокируются или обрабатываются через запасной сценарий.
5. По истечении заданного времени включается `HALF_OPEN`.
6. Если пробные запросы успешны, автомат возвращается в `CLOSED`.
7. Если ошибки продолжаются, он снова переходит в `OPEN`.

```text
             CLOSED
                |
         Порог ошибок достигнут
                |
                v
              OPEN
                |
           Таймер истёк
                |
                v
           HALF_OPEN
             /     \
         Успех     Ошибка
           |         |
           v         v
        CLOSED     OPEN
```

### Пример

Главная страница музыкального сервиса показывает подборку подкастов.

Если сервис подкастов недоступен, Circuit Breaker может временно блокировать обращения к нему, а главная страница продолжит показывать музыку без подборки.

Это пример graceful degradation — сохранения основной функциональности при отказе второстепенного компонента.

### Что важно учитывать

Circuit Breaker не заменяет таймауты.

- **Timeout** ограничивает время ожидания конкретного запроса.
- **Circuit Breaker** ограничивает дальнейшие обращения при устойчивых признаках проблем.

Повторные попытки также нужно настраивать осторожно: агрессивные retries могут дополнительно перегружать зависимый сервис.

Не для каждой операции есть безопасный запасной сценарий. Например, нельзя считать платёж успешным только потому, что сервис платежей временно недоступен.

### Преимущества

- Снижает количество запросов к неработающему сервису.
- Помогает избежать каскадных отказов.
- Освобождает ресурсы вызывающего сервиса.
- Позволяет сохранять второстепенную функциональность системы.

### Недостатки

- Нужны правильные пороги и временные интервалы.
- Неверная конфигурация может блокировать здоровый сервис.
- Требуются мониторинг и тестирование поведения при отказах.

### Как запомнить

**Circuit Breaker = временно прекращаем обращения к проблемному сервису, чтобы защитить остальную систему.**

# Сравнение семи паттернов

| Паттерн | Основная проблема | Ключевой механизм |
|---|---|---|
| Strangler Fig | Рискованная миграция с монолита | Постепенное переключение функциональности |
| API Gateway | Множество внешних точек входа | Централизованная маршрутизация |
| Database per Service | Связанность через общую БД | Владение данными отдельным сервисом |
| Transactional Outbox | Потеря события между БД и брокером | Атомарная запись события в БД |
| Idempotent Consumer | Повторная доставка сообщения | Уникальный идентификатор события |
| Saga | Бизнес-операция между несколькими сервисами | Локальные транзакции и компенсации |
| Circuit Breaker | Каскадные отказы | Временная блокировка обращений |

---

# Как паттерны работают вместе

Рассмотрим систему интернет-магазина.

1. **Strangler Fig** позволяет постепенно выделить каталог и оплату из монолита.
2. **API Gateway** принимает внешние запросы и направляет их нужным сервисам.
3. **Database per Service** закрепляет данные заказов, товаров и платежей за соответствующими сервисами.
4. **Transactional Outbox** обеспечивает надёжную публикацию событий о создании заказа.
5. **Idempotent Consumer** предотвращает повторное выполнение бизнес-операций при повторной доставке событий.
6. **Saga** координирует оформление заказа, оплату и резервирование товара.
7. **Circuit Breaker** ограничивает обращения к временно недоступным сервисам.

У каждого паттерна своя зона ответственности. Они дополняют друг друга, но не заменяют друг друга.

# Типичные вопросы на собеседовании

### 1. Почему нельзя просто переписать монолит на микросервисы?

Можно, но это увеличивает риск и стоимость миграции. Strangler Fig позволяет переносить функциональность поэтапно и проверять результат на каждом шаге.

### 2. Чем API Gateway отличается от reverse proxy?

Reverse proxy перенаправляет запросы к внутренним серверам и может выполнять балансировку. API Gateway обычно дополнительно управляет внешним API: маршрутизацией по правилам приложения, аутентификацией, ограничениями запросов и другими политиками.

Функциональность этих компонентов может пересекаться.

### 3. Обязательно ли каждому микросервису иметь отдельный сервер БД?

Нет. Важно разделение владения данными и прав доступа, а не физическое размещение. Несколько баз могут находиться в одном кластере.

### 4. Гарантирует ли Transactional Outbox доставку ровно один раз?

Нет. Событие может быть опубликовано повторно, если отправитель упал после публикации, но до фиксации результата. Поэтому потребители должны быть готовы к дубликатам.

### 5. Чем идемпотентность отличается от дедупликации?

Дедупликация определяет, что событие уже встречалось, и позволяет пропустить его повторную обработку.

Идемпотентность — более общее свойство операции: повторный вызов не должен менять результат сверх эффекта первого успешного вызова.

### 6. Почему Saga не использует обычный ROLLBACK для всех сервисов?

Потому что локальные транзакции уже могли быть зафиксированы в разных базах. Для исправления бизнес-последствий выполняются отдельные компенсирующие операции.

### 7. Чем Circuit Breaker отличается от Retry?

Retry повторяет неудачный запрос в надежде на успех.

Circuit Breaker временно прекращает обращения, если система считает зависимость проблемной. Без ограничений Retry может усиливать перегрузку.

### 8. Что важнее при проектировании микросервисов?

Чёткие границы владения данными, независимость сервисов, наблюдаемость, обработка ошибок и осознанный выбор компромиссов.

Микросервисы не делают систему автоматически надёжной. Надёжность достигается архитектурой, реализацией и эксплуатацией.

# Что нужно запомнить

- **Strangler Fig** — постепенная миграция.
- **API Gateway** — единая точка входа.
- **Database per Service** — изоляция данных.
- **Transactional Outbox** — надёжная публикация событий.
- **Idempotent Consumer** — защита от повторных бизнес-операций.
- **Saga** — координация распределённого бизнес-процесса.
- **Circuit Breaker** — защита от каскадных отказов.

Главный принцип: выбирай паттерн по проблеме, которую он решает. Каждый дополнительный механизм должен приносить пользу, оправдывающую его сложность.
