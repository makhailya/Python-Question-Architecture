## ⚡ Быстрый ответ (шпаргалка перед собесом)

- **Изменяемые**: [[list]], [[dict]], [[set]], [[bytearray]].
- **Неизменяемые**: [[int]], [[float]], [[complex]], [[bool]], [[str]], [[tuple]], [[frozenset]], [[bytes]], [[NoneType]], [[memoryview]].
- [[Передача объектов в функции Python]]
- В Python в функцию передаётся **ссылка на объект**, а параметр функции становится ещё одним именем, которое ссылается на этот объект.
  Если внутри функции мы **изменяем сам объект**, например через `.append()`, изменения будут видны снаружи.
  Если мы **присваиваем параметру новое значение**, мы просто переназначаем локальное имя — внешняя переменная не изменяется.
  Поэтому важно различать **изменение объекта** и **переназначение имени**Технически это называют **call by sharing** или **передача объекта по ссылке**.

- **[[list vs tuple]]**: список — динамический массив, изменяемый; кортеж — неизменяемый аналог, используется, когда нужна гарантия неизменности данных ([[Константы]], [[Ключи словаря]], [[Hashable-объекты]]).

- **[[Алгоритмическая Сложность операций list]]**: добавление/удаление с конца — $O(1)$; вставка/удаление в середине — $O(n)$; доступ по индексу — $O(1)$; поиск по значению — $O(n)$.

- **[[dict]]** — хэш-таблица; в CPython (с 3.6+) — «компактная упорядоченная хэш-таблица» (compact ordered hash table) из двух структур: [[Таблица индексов]] + [[Таблица entries]]. Вставка/поиск — $O(1)$ в среднем, $O(n)$ в худшем случае ([[Реалокация]] или много коллизий). [[Коллизии в хеш-таблице]] в CPython решаются [[Открытая адресация]] (не [[Цепочки]]).

- **[[Реалокация]] словаря**([[dict]]) — когда таблица заполнена на $\frac{2}{3}$ ([[Load Factor]]), CPython выделяет новую таблицу большего размера (обычно ×2, иногда больше) и переносит туда данные — сложность такой операции $O(n)$.

- **[[Сборщик мусора (GC)]]** = [[Счётчик Ссылок]] (reference counting) + поколенческий сборщик циклических ссылок ([[Generational GC]], 3 поколения). Для борьбы с [[Циклические ссылки]]: [[Cлабые Cсылки (Weakref)]], явный вызов [[Управление GC вручную]], избегание лишних вложенных циклических структур.

- [[GIL — Global Interpreter Lock]] — блокировка, разрешающая исполнять байткод только одному [[Поток]]у одновременно. Нужен для защиты внутренних структур CPython (в первую очередь — [[Счётчик Ссылок]]) от гонок данных между [[Поток]]ами. НЕ защищает от гонок данных и дедлоков в пользовательском коде.

- **[[Виды многозадачности]]**:
- [[Многопроцессность (Multiprocessing)]] (для CPU-bound),
- [[Многопоточность (Multithreading)]] (для IO-bound, из-за GIL бесполезна для CPU-bound),
- [[Асинхронность (Asyncio)]] (тоже для IO-bound, на [[Event Loop — цикл событий]], но без GIL-ограничений на переключение — конкурентность в одном потоке).

# 📖 Подробно

## 1. Типы данных и передача аргументов

| Изменяемые (mutable)                       | Неизменяемые (immutable)                                                                                              |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| [[list]], [[dict]], [[set]], [[bytearray]] | [[int]], [[float]], [[complex]], [[bool]], [[str]], [[tuple]], [[frozenset]], [[bytes]], [[memoryview]], [[NoneType]] |
|                                            |                                                                                                                       |

**Важный нюанс с собеса**: Технически в Python **всё передаётся по ссылке** (на объект) [[Передача объектов в функции Python]]. Разница проявляется в поведении:

```python
def change(x):
    x = 11  # переопределяем локальное имя x — на внешний объект не влияет

a = 10
change(a)
print(a)  # 10, не изменилось

def append_item(lst):
    lst.append(4)  # мутируем сам объект по ссылке

my_list = [1, 2, 3]
append_item(my_list)
print(my_list)  # [1, 2, 3, 4] — изменилось!
```

Живая аналогия: представь, что переменная — это стикер с именем, наклеенный на коробку (объект). Когда мы делаем `x = 11` внутри функции — мы просто клеим стикер `x` на **новую** коробку. Старая коробка (объект `10`), на которую снаружи наклеен стикер `a`, не тронута. А когда мы делаем `lst.append(4)` — мы открываем ту же самую коробку и кладём туда предмет, поэтому все стикеры, наклеенные на эту коробку (включая внешний `my_list`), видят изменение.

## 2. Список и кортеж [[list vs tuple]]

- **[[list]]** — динамический массив (переменной длины), изменяемый, поддерживает разнородные типы.
- **[[tuple]]** — по сути тот же список, но неизменяемый. Используют, когда важно гарантировать, что данные не изменятся: константы, ключи [[dict]] ([[tuple]] кортеж — [[Hashable-объекты]], [[list]] (список) — нет), возврат нескольких значений из функции, передача «замороженного» набора данных.

[[Алгоритмическая Сложность операций list]]:

| Операция | Сложность |
|---|---|
| Добавить/удалить в конец (`append`/`pop`) | $O(1)$ |
| Вставка/удаление в середине (сдвиг индексов) | $O(n)$ |
| Доступ по индексу `lst[i]` | $O(1)$ |
| Обход всего списка | $O(n)$ |
| Удаление по значению (`remove`) | $O(n)$ (сначала поиск индекса — $O(n)$, потом сдвиг) |

## 3. Словарь ([[dict]]) — устройство

[[dict]] — это [[Хеш-Таблица]]. В современном CPython (начиная примерно с 3.6) это **компактная упорядоченная [[Хеш-Таблица]]** (compact ordered hash table), состоящая из двух структур:

1. [[Таблица индексов]] — разреженная таблица, изначально заполнена значениями `-1` («пусто»). По хэшу ключа вычисляется позиция в этой таблице, там хранится **индекс** записи в таблице entries.
2. [[Таблица entries]] — компактная (без «дырок») таблица, где последовательно (в порядке добавления) хранятся тройки ([[Hash]], key, value) [[Key-Value]].

Почему это даёт **сохранение порядка вставки**: элементы в `entries` всегда дописываются последовательно (0, 1, 2, …), а таблица индексов лишь указывает, где их искать. Поэтому обход `entries` по порядку = обход в порядке добавления ключей.

Почему это называется **компактной**: раньше (до этого механизма) под саму таблицу бакетов сразу выделялся большой объём памяти (например, под 8 пар), даже если реально хранилось меньше значений. Сейчас таблица индексов выделяется заранее, а таблица entries растёт по мере необходимости — экономия памяти.

[[Алгоритмическая сложность dict]]:

| Операция | В среднем | В худшем случае |
|---|---|---|
| Вставка / поиск / удаление | $O(1)$ | $O(n)$ |

Худший случай возникает при:

- **[[Коллизии в хеш-таблице]]** — несколько ключей ссылаются на один и тот же индекс. В CPython используется [[Открытая адресация]] ([[Пробирование в хеш-таблицах]]): при коллизии интерпретатор ищет следующую свободную ячейку по определённому алгоритму (не строго последовательно). Это отличается от C++, где чаще используется метод [[Цепочки]] (chaining) — там в ячейке хранится список пар.

- **[[Реалокация]] (rehashing)** — когда таблица заполняется примерно на $\frac{2}{3}$ ([[Load Factor]]), Python создаёт новую, увеличенную таблицу (обычно кратно ×2, но может быть и больше при малом исходном размере) и переносит туда все данные — операция $O(n)$, но происходит она нечасто, поэтому амортизированная сложность вставки всё равно $O(1)$.

## 4. [[Сборщик мусора (GC)]]

Работает по двум механизмам:

1. **[[Счётчик Ссылок]] (reference counting)** — у каждого объекта есть счётчик ссылок; когда он достигает 0, объект сразу удаляется из памяти.

2.  **Поколенческий сборщик [[Циклические ссылки]] (generational GC)** — нужен, потому что подсчёт ссылок не справляется с циклами (объект A ссылается на B, B ссылается на A, но извне на них никто не ссылается — счётчики никогда не станут 0). Работает по принципу **поколений**: новые объекты попадают в «первое поколение»; если объект «пережил» цикл сборки — переходит в следующее поколение (всего 3 поколения). Более старые поколения проверяются реже — это оптимизация, основанная на наблюдении, что большинство объектов «умирают молодыми».

Сборщик мусора **не атомарен** и **не потокобезопасен** сам по себе — именно поэтому ему (и вообще операциям с счётчиком ссылок) нужен [[GIL — Global Interpreter Lock]] для корректной работы в [[Многопоточность (Multithreading)]] окружении.

**Методы борьбы с циклическими ссылками:**

- **[[Cлабые Cсылки (Weakref)]]** — не увеличивают счётчик ссылок объекта. Если на объект остались только слабые ссылки — сборщик мусора удалит его.
- Явный вызов `gc.collect()`[[Управление GC вручную]].
- Архитектурно — избегать ненужных вложенных циклических структур.

## 5. [[GIL — Global Interpreter Lock]]

[[GIL — Global Interpreter Lock]] — это блокировка на уровне интерпретатора CPython, которая разрешает исполнять байт-код **только одному [[Поток]]у в один момент времени**.

**Зачем он нужен:**

- Защищает низкоуровневые операции CPython (в первую очередь — операции с [[Счётчик Ссылок]] объектов) от гонок данных. Инкремент/декремент счётчика ссылок — это не [[Атомарность Операции]] («взять значение → увеличить → положить обратно»), и если бы два [[Поток]]а делали это параллельно — состояние могло бы стать неконсистентным (утечки памяти или преждевременное удаление объекта, который ещё используется).
- Упрощает работу сборщика мусора, который тоже не рассчитан на потокобезопасность.

**Что GIL НЕ делает:**
- Не защищает от гонок данных ([[Архитектура вопросов Пайтон/1. Основы Python/Race Condition]]) и [[Deadlock]] (дедлоков) в **пользовательском** коде.

**Почему [[Многопоточность (Multithreading)]] всё равно полезна для IO-bound задач:** пока [[Поток]] ожидает ответа (сеть, диск, БД), [[GIL — Global Interpreter Lock]] освобождается, и интерпретатор может переключиться на исполнение другого [[Поток]]а. Для [[CPU-bound]] задач это не помогает — [[Поток]] всё равно выполняет вычисления и удерживает [[GIL — Global Interpreter Lock]].

### 6. [[Виды многозадачности]]

| Вид                                         | Что это                                                                                                 | Хорошо для                                                                          | Плохо для                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **[[Многопроцессность (Multiprocessing)]]** | Несколько отдельных процессов, у каждого свой интерпретатор и своя память                               | [[CPU-bound]] задач (математика, рендеринг)                                         | IO-bound — только тратим ресурсы на создание процессов без выигрыша                         |
| [[Многопоточность (Multithreading)]]        | Несколько потоков в рамках одного процесса, управляются ОС                                              | [[IO-bound]] задач (ожидание сети/диска)                                            | CPU-bound — GIL блокирует параллельное исполнение вычислений                                |
| [[Асинхронность (Asyncio)]]                 | Конкурентное выполнение в одном потоке через [[Event Loop — цикл событий]], [[Корутина - (coroutine)]], [[Генератор]] | [[IO-bound]] задач, особенно много одновременных ожиданий (много запросов к API/БД) | CPU-bound — блокирующий синхронный вызов внутри `async` функции заблокирует весь event loop |

**Если внутри асинхронного кода нужно выполнить синхронную ([[Блокирующий код в asyncio]]) функцию** — она заблокирует [[Event Loop — цикл событий]], и все остальные [[Корутина - (coroutine)]] будут ждать. Решение: вынести эту функцию в отдельный [[Поток]] ([[run_in_executor и asyncio.to_thread]]) либо в отдельный [[Процесс]]/[[Worker]] (например, [[Celery]]).
