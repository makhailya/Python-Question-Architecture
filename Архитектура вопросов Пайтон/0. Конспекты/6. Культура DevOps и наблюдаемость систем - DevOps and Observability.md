# DevOps: [[Docker]], [[Kubernetes]], [[Observability]], [[CI и CD]]

---

## ⚡ Быстрый ответ (шпаргалка перед собесом)

- **Виртуализация vs контейнеризация**: 
- [[Виртуальная машина]] — полностью отдельная операционная система со своим выделенным ядром и памятью (тяжеловесно). 
- [[Контейнер]] использует **ядро хост-ОС**, изолируя только процессы/файловую систему приложения — гораздо легче по памяти и месту на диске. Условно контейнеры можно представить как более лёгкую изоляцию «поверх» одной ОС, в отличие от полностью отдельной ОС у виртуалки.

- **[[Docker|Docker]]** — платформа контейнеризации. Контейнер собирается по инструкциям из **Dockerfile**. Взаимодействие — через **порты** (проброс наружу) и **volumes** (постоянное хранилище данных, не теряющееся при пересоздании контейнера).

- **[[Dockerfile]] — слоистость и кэширование**: каждая инструкция (строка) — это отдельный **слой**, который кэшируется. Слои, которые меняются реже (установка зависимостей), стоит писать **раньше** тех, что меняются часто (копирование кода приложения) — так Docker переиспользует кэш и не пересобирает всё с нуля при каждой правке кода.

- **[[Docker Compose]]** — конфигурационный файл для запуска и связывания нескольких контейнеров одной командой (вместо отдельного `docker run` на каждый).

- **[[Healthcheck]]** — механизм проверки, что зависимый сервис (например, БД или Redis) реально готов принимать запросы, а не просто «запущен» (используется, чтобы, например, бэкенд не стартовал раньше, чем поднимется база).

- **[[Kubernetes]] (K8s)** — оркестратор контейнеров. Главные возможности: **[[self-healing]]** (автоматически перезапускает упавшие контейнеры), автоматическое **масштабирование** количества экземпляров исходя из нагрузки.

- **[[Pod]]** — минимальная единица развёртывания в Kubernetes, представляет собой один или несколько тесно связанных Docker-контейнеров, [[Контейнер]] запускаемых вместе.

- **[[Observability]] (наблюдаемость)** — способность понять, что происходит внутри системы, на основе внешних сигналов.
- Три основных «столпа» [[Observability]]: 
- **[[Метрики]]** (числовые показатели — нагрузка CPU, число запросов, коды ответов), 
- **[[Логи]]** (текстовые записи бизнес-событий и ошибок), 
- **[[Трейсинг]]** (отслеживание пути одного запроса через все системы/сервисы). 
- Дополнительно — **[[Профилирование]]** (анализ использования ресурсов — память, CPU конкретного процесса).

- **[[CI и CD]] пайплайн** — типичные шаги: [[Merge Request]] / [[Код-ревью]] → [[Dev-окружение]] → [[Тестовое окружение]] → [[Сборка релиза]] → [[Архитектура вопросов Пайтон/08 Культура DevOps/Деплой|Деплой]].

- **[[MyPy]]** — статический анализатор типов (проверяет соответствие аннотаций типов реальному использованию), это не про форматирование и не про тесты.

- Действия при инциденте (500 ошибки посыпались после недавнего деплоя): проверить метрики/графики → посмотреть, что недавно задеплоено (система контроля версий, последние коммиты) → при необходимости откатиться на предыдущую версию (rollback) или переключиться на другой инстанс, пока разбираетесь.

# 📖 Подробно

## 1. Виртуализация vs контейнеризация

| | Виртуальная машина | Контейнер |
|---|---|---|
| Ядро ОС | Своё, полностью отдельная ОС | Общее с хост-системой |
| Вес | Тяжёлый (гигабайты) | Лёгкий (мегабайты) |
| Изоляция | Полная (на уровне гипервизора) | На уровне процессов/namespaces |
| Скорость запуска | Медленная (загрузка целой ОС) | Быстрая (секунды) |

Можно сказать, что **[[Контейнер]]ы технически можно запускать и внутри виртуальной машины**  [[Виртуальная машина]]— это довольно частая практика в облаках (виртуалка как хост, а внутри неё уже крутится [[Docker|Docker]]/[[Kubernetes]]).

## 2. [[Docker|Docker]]

- **[[Dockerfile]]** — текстовый файл с инструкциями по сборке образа: базовый образ, установка зависимостей, копирование кода, команда запуска.

```dockerfile
FROM python:3.12-slim

WORKDIR /app

# Сначала зависимости — этот слой кэшируется, пока requirements не меняется
COPY pyproject.toml poetry.lock ./
RUN pip install poetry --break-system-packages && poetry install --no-root

# Потом код приложения — меняется часто, но не ломает кэш предыдущих слоёв
COPY . .

CMD ["python", "main.py"]
```

**Слоистость и кэширование**: каждая инструкция [[Dockerfile]] (`FROM`, `RUN`, `COPY` и т.п.) создаёт отдельный **слой**. При пересборке [[Docker|Docker]] проверяет, изменился ли слой (и все, что перед ним) — если нет, использует кэш и не выполняет инструкцию заново. Поэтому важно **сначала** копировать и устанавливать зависимости (меняются редко), и **только потом** копировать сам код приложения (меняется часто) — иначе любое изменение в коде будет заставлять переустанавливать все зависимости заново.

- **Взаимодействие контейнеров**: через **порты** (проброс `-p host:container`) и **[[Volumes]]** (монтирование постоянного хранилища — данные не теряются при пересоздании контейнера, в отличие от файловой системы самого контейнера).

- **[[Docker Compose]]** — YAML-файл, описывающий несколько сервисов (контейнеров) и их связь, поднимаются одной командой `docker compose up` вместо запуска каждого через отдельный `docker run`.

**[[Healthcheck]]**: чтобы гарантировать, что, например, бэкенд запускается только тогда, когда реально готова база данных или [[Redis]] (а не просто когда контейнер стартовал — процесс внутри может ещё не успеть подняться), используют [[Healthcheck]]-проверки:

```yaml
services:
  redis:
    image: redis
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    build: .
    depends_on:
      redis:
        condition: service_healthy
```

## 3. [[Kubernetes]]

**[[Kubernetes]] (K8s)** — оркестратор контейнеров, который управляет их жизненным циклом на кластере серверов.

Главные возможности:

- **[[self-healing]]** — если контейнер упал, [[Kubernetes]] автоматически перезапускает его без ручного вмешательства.

- **Автоматическое масштабирование** — при росте нагрузки [[Kubernetes]] может поднимать дополнительные копии (реплики) [[Репликация]] приложения, при снижении — сокращать их количество.

**[[Pod]]** — минимальная единица развёртывания и управления в [[Kubernetes]]. Представляет собой один или несколько тесно связанных [[Docker|Docker]] (или другого рантайма) контейнеров, которые всегда запускаются и масштабируются вместе (например, основной контейнер приложения + [[Sidecar-контейнер]] для логирования).

Базово стоит понимать, что в кластере есть **[[Worker-ноды]] (где реально исполняются поды) и **master**-компоненты (управляют состоянием кластера), но на джуниорском уровне обычно достаточно знать концепцию [[Pod]] и общее назначение [[Kubernetes]] как оркестратора.

## 4. [[Observability]] (наблюдаемость)

Термин **[[Observability]]** описывает способность понять, что происходит **внутри** системы, опираясь на **внешние сигналы**, которые система предоставляет.

Три основных вида сигналов (три «столпа» observability):

| Сигнал           | Что это                                                                  | Пример                                                                         |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **[[Метрики]]**  | Числовые показатели, обычно во времени                                   | Загрузка CPU, число запросов в секунду, число 500-х ошибок, задержка (latency) |
| **[[Логи]]**     | Текстовые записи событий                                                 | Успешное завершение операции, ошибка, дебаг-информация                         |
| **[[Трейсинг]]** | Отслеживание одного запроса через все системы/сервисы, которые он прошёл | Путь запроса через API-gateway → сервис A → сервис B → БД                      |

Дополнительно упоминается **[[Профилирование]]** — анализ использования ресурсов конкретным процессом (память, CPU) для поиска узких мест производительности.

Инструменты, часто упоминаемые вместе с этой темой: **[[Prometheus]]** (сбор и хранение метрик), **[[Grafana]]** (визуализация метрик — важно: [[Grafana]] — это именно графический интерфейс/дашборд, а не сама метрика или система наблюдаемости).

## 5. Действия при инциденте (пример с собеса)

Сценарий: в системе метрик резко посыпались 500-е ошибки, при этом недавно (около часа назад) кто-то выкатил изменения в прод.

Разумная последовательность действий:

1. Посмотреть на **[[Метрики]]/графики** ([[Grafana]]/[[Prometheus]]) — понять масштаб проблемы, какой сервис/эндпоинт затронут.

2. Если проблема совпадает по времени с недавним деплоем([[Архитектура вопросов Пайтон/08 Культура DevOps/Деплой|Деплой]])— зайти в систему контроля версий (Git), посмотреть, что было закоммичено/задеплоено.

3. Принять решение: **откатиться ([[ROLLBACK]])** на предыдущую рабочую версию, либо, если проблема ясна и решение быстрое — исправить прямо в новом коммите ([[Hotfix]]).

4. Параллельно можно **переключить трафик** на другой стабильный инстанс/регион, если инфраструктура это позволяет, чтобы не держать сервис лежащим, пока разбираетесь.

## 6. [[CI и CD]] и статический анализ

Типичный пайплайн:

```
Merge Request (код-ревью) → Dev-окружение → Test-окружение → Сборка релиза → Deploy
```

На этапе проверки кода перед мержем обычно запускаются:

- **[[Линтеры]]/[[Форматтеры]]** (например, [[Black]], [[Ruff]]) — проверяют стиль кода, форматирование.

- **[[MyPy]]** — **статический анализатор типов**. Проверяет, что аннотации типов (`def foo(x: int) -> str:`) соблюдаются по всему коду, находит потенциальные несоответствия типов **до** запуска программы. Это отдельная категория инструментов — не форматирование и не юнит-тесты.

- **Тесты** ([[pytest]]) — отдельный шаг, проверяющий корректность работы кода.
