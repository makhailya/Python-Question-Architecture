## ⚡ Быстрый ответ (шпаргалка перед собесом)

- [[REST API]] — архитектурный стиль клиент-серверного взаимодействия. Принципы: **[[Client-Server]]**, **[[Stateless]]** (запрос содержит всё необходимое, сервер не хранит состояние клиента между запросами), **Cacheable** (кэшируемость ответов), **[[Layered System]]** (слоистая архитектура), **[[Uniform Interface]]** (единообразие: понятные [[URI]] как ресурсы, стандартные HTTP-методы, единый формат — обычно JSON), опционально **[[Code on Demand]]**.

- [[HTTP-методы]]: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` (как GET, но без тела ответа — только заголовки), `OPTIONS` (какие методы поддерживает ресурс), `TRACE` (диагностика, возврат запроса как есть — считается небезопасным, почти не используется), `CONNECT`.

- **[[HTTP 1.1]] vs [[HTTP 2]]**: [[HTTP 3]] — бинарный протокол (а не текстовый), поддерживает **мультиплексирование** (несколько запросов в рамках одного TCP-соединения одновременно, без ожидания ответа на предыдущий), сжимает заголовки (HPACK), чаще идёт поверх TLS. HTTP/1.1 — по сути один запрос = одно соединение, синхронное ожидание ответа. gRPC — фреймворк от Google, использующий HTTP/2.

- **[[TCP]] vs [[UDP]]**: TCP гарантирует доставку (устанавливает соединение через **three-way handshake** — «тройное рукопожатие»), надёжнее, но медленнее. UDP просто отправляет пакеты без гарантии доставки и без установки соединения — быстрее, используется там, где важна скорость больше надёжности (стриминг, игры).

- **[[TLS]]/[[HTTPS]]** — шифрование поверх [[HTTP]]. Сертификаты выдаются центрами сертификации (CA), которые подтверждают подлинность сервера.

- **[[Идентификация]] → [[Аутентификация]] → [[Авторизация]]**: идентификация — «кто ты» (логин, номер телефона), аутентификация — «докажи, что ты это ты» (пароль, токен), авторизация — «что тебе разрешено делать» (права/роли).

- [[Способы аутентификации]]: Basic Auth (логин/пароль в заголовке), Token-based (в т.ч. [[JWT]]), OAuth2, по SMS-коду, по API-ключам.

- **[[JWT]]** состоит из трёх частей:
- **[[Header]]** (тип токена, алгоритм шифрования), 
- **[[Payload]]** (данные пользователя — id, роль, время выдачи/истечения; **нельзя хранить чувствительные данные**, т.к.  header и payload легко декодируются без секрета), 
- **[[Signature]]** (подпись, вычисляется с использованием **secret key**, который хранится только на бэкенде — без него невозможно подделать подпись). У [[JWT]] ограниченное время жизни (TTL), поэтому рядом обычно хранится **refresh-токен** (просто случайная строка/хэш в БД) для обновления сессии без повторного логина.

- **[[SOLID|SOLID]]**: 
- [[Single Responsibility]] (класс/модуль отвечает только за одну задачу),
- [[Open Closed]] (открыт для расширения, закрыт для изменения),
- [[Liskov Substitution]](наследника можно подставить вместо родителя без поломки поведения),
- [[Interface Segregation]] (много маленьких интерфейсов лучше одного большого),
- [[Dependency Inversion]] (модули верхнего уровня не должны зависеть от модулей нижнего уровня напрямую — оба должны зависеть от абстракции).

- [[Dependency Injection]] (DI)** — паттерн, реализующий принцип Dependency Inversion на практике: объект получает свои зависимости уже готовыми (через конструктор/параметр), а не создаёт их сам внутри. Связанный более широкий термин — [[Inversion of Control (IoC)]] **. Пример в Python-мире — [[Depends]] в FastAPI.

- [[WSGI]] vs [[ASGI]]**: [[WSGI]] — синхронный интерфейс между веб-сервером и приложением (используется [[Django|Django]] «из коробки», сервер — [[Gunicorn]]). [[ASGI]] — асинхронный интерфейс (используется [[FastAPI]], сервер — [[Uvicorn]], часто вместе с [[Gunicorn]] как process manager: `gunicorn -k uvicorn.workers.UvicornWorker`).

- **[[Nginx]]** — веб-сервер, чаще всего используется как **reverse proxy** (принимает запросы и перенаправляет на нужный инстанс приложения) и как **балансировщик нагрузки**.

- [[Алгоритмы балансировки нагрузки]]:
- **[[Round Robin]]** (по кругу),
- **[[Weighted Round Robin]]** (по кругу, но с учётом «веса»/производительности сервера),
- **[[Least Connections]]** (на сервер с наименьшим числом активных соединений), 
- **[[Sticky Session]]** (закрепление клиента за конкретным сервером на время сессии).

# 📖 Подробно

## 1. [[REST API]]

[[REST]] (REpresentational State Transfer) — архитектурный стиль (не протокол и не стандарт) для построения клиент-серверных веб-приложений. Ключевые принципы:

- **[[Client-Server]]** — разделение ответственности: клиент управляет запросами, сервер отдаёт данные.
- **[[Stateless]]** — сервер не хранит состояние клиента между запросами; каждый запрос должен содержать всё необходимое для его обработки (в заголовках или теле).
- **[[Cacheable]]** — ответы должны явно помечаться, можно ли их кэшировать, чтобы снизить нагрузку на сервер при повторных одинаковых запросах.
- **[[Layered System]]** — клиент не обязан знать, взаимодействует ли он напрямую с сервером или через промежуточные слои (балансировщики, прокси).
- **[[Uniform Interface]]** — ресурсы адресуются через понятные URL, взаимодействие идёт через стандартные HTTP-методы, представление данных единообразно (обычно JSON, иногда XML).
- **[[Code on Demand]]** (опционально) — сервер может передавать клиенту исполняемый код (редко используется на практике).

## 2. [[HTTP]] методы и версии протокола

| Метод   | Назначение                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------- |
| GET     | Получить ресурс                                                                                   |
| POST    | Создать ресурс                                                                                    |
| PUT     | Полностью заменить ресурс                                                                         |
| PATCH   | Частично обновить ресурс                                                                          |
| DELETE  | Удалить ресурс                                                                                    |
| HEAD    | Как GET, но без тела ответа — только заголовки (проверить существование/метаданные)               |
| OPTIONS | Узнать, какие методы поддерживает ресурс                                                          |
| TRACE   | Диагностика — сервер возвращает то же, что получил; считается небезопасным, почти не используется |
| CONNECT | Установка туннеля (например, для HTTPS через прокси)                                              |

**[[HTTP 1.1]]**: по сути одно TCP-соединение = один запрос, ответ ожидается синхронно (в базовой модели), текстовый протокол.

**[[HTTP 2]]**: бинарный протокол, поддерживает **мультиплексирование** — несколько запросов и ответов могут «ехать» в рамках одного TCP-соединения одновременно, без блокировки друг друга (в отличие от [[HTTP 1.1]]). Заголовки сжимаются алгоритмом HPACK. Чаще всего работает поверх TLS. **gRPC** (фреймворк от Google) использует [[HTTP 2]] как транспорт — в отличие от классического [[REST]], который обычно работает поверх [[HTTP 1.1]].

## 3. [[TCP]] vs [[UDP]], [[TLS]]

- **[[TCP]]** — протокол с гарантией доставки: перед передачей данных устанавливается соединение через **[[three-way handshake]]** («тройное рукопожатие»: SYN → SYN-ACK → ACK). За счёт этого [[TCP]] надёжнее, но медленнее [[UDP]].

- **[[UDP]]** — просто отправляет пакеты без установки соединения и без гарантии доставки — быстрее, используется там, где скорость важнее надёжности (видеостриминг, онлайн-игры, [[DNS]]).

- **[[TLS]]** — протокол шифрования поверх транспортного уровня; [[HTTP]] + [[TLS]] = [[HTTPS]]. Центры сертификации (CA) выдают сертификаты, подтверждающие подлинность сервера, клиент их проверяет при установке соединения.

## 4. [[Идентификация]], [[Аутентификация]], [[Авторизация]]

| Термин | Вопрос, на который отвечает |
|---|---|
| Идентификация | «Кто ты?» — логин, номер телефона |
| Аутентификация | «Докажи, что ты это ты» — пароль, токен, биометрия |
| Авторизация | «Что тебе разрешено делать?» — права, роли |

**[[Способы аутентификации]]**: Basic Auth (логин/пароль в заголовке `Authorization`), Token-based (в т.ч. JWT), OAuth2 (делегированная авторизация через сторонний провайдер), по одноразовому SMS-коду, по API-ключам.

## 5. [[JWT]] (JSON Web Token)

Структура: `header.payload.signature`

- **[[Header]]** — тип токена ([[JWT]]) и алгоритм подписи (например, `HS256`).

- **[[Payload]]** — данные: id пользователя, роль, время создания (`iat`), время истечения (`exp`) и т.п. **Важно**: [[Header]] и [[Payload]] — это просто **закодированные** (base64), а не зашифрованные данные. Их можно декодировать без секретного ключа, поэтому чувствительные данные (пароли и т.п.) туда класть нельзя.

- **[[Signature]]** — подпись, вычисленная на основе [[Header]]+[[Payload]] и **secret key**, который хранится только на сервере (обычно в переменных окружения, секрет-менеджере или [[Kubernetes Secrets]] в более серьёзных проектах). Без секретного ключа злоумышленник не сможет подделать подпись, даже если перехватит и декодирует токен.

Так как [[JWT]] имеет ограниченное время жизни (**[[TTL]]**, например 10-15 минут), рядом с [[Access Token]]ом обычно выдаётся **[[Refresh Token]]ом** — обычно это просто случайная строка/хэш, хранящаяся в БД, — по нему можно получить новый [[Access Token]] без повторного ввода логина/пароля.

**Что может сделать злоумышленник, перехватив токен**: [[Декодирование JWT Header и Payload]] и получить нечувствительную информацию о пользователе (id, роль). Подделать подпись он не сможет без secret key.

## 6. [[SOLID|SOLID]]

- **S — [[Single Responsibility]] Principle**: класс/модуль/функция должны отвечать только за одну зону ответственности, решать одну задачу.

- **O — [[Open Closed]] Principle**: сущности открыты для **расширения** (например, через наследование), но закрыты для **изменения** существующего кода.

- **L — [[Liskov Substitution]]  Principle**: объект класса-наследника должен быть взаимозаменяем с объектом родительского класса без нарушения корректности программы (наследник должен поддерживать тот же контракт методов и атрибутов).

- **I — [[Interface Segregation]] Principle**: лучше несколько маленьких специализированных интерфейсов, чем один большой «интерфейс на всё».

- **D — [[Dependency Inversion]] Principle**: модули верхнего уровня не должны напрямую зависеть от модулей нижнего уровня — оба должны зависеть от абстракций.

## 7. [[Dependency Injection]] / [[Inversion of Control (IoC)]]

**[[Dependency Injection]] (DI)** — практическая реализация принципа [[Dependency Inversion]]: объект **не создаёт** свои зависимости сам, а **получает их готовыми** извне (через конструктор, параметр функции и т.п.).

**[[Inversion of Control (IoC)]] ** — более широкий термин/паттерн, частью которого является DI: управление созданием и жизненным циклом зависимостей передаётся какому-то внешнему механизму (контейнеру, фреймворку), а не самому объекту.

Пример в Python — [[Depends]] в [[FastAPI]]:

```python
from fastapi import Depends, FastAPI

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users")
def read_users(db=Depends(get_db)):
    return db.query(User).all()
```

Эндпоинт `read_users` не создаёт сессию с БД сам — он получает её «готовой» через [[Depends]]. Под капотом подобные DI-фреймворки в других языках часто построены на классических паттернах — фабрике или адаптере.

## 8. [[WSGI]] vs [[ASGI]], [[Django|Django]] vs [[FastAPI]]

- **[[WSGI]] (Web Server Gateway Interface)** — синхронный интерфейс между веб-сервером (например, [[Nginx]]) и Python-приложением. Веб-сервер приложений — **[[Gunicorn]]**. [[Django|Django]] изначально синхронный и работает через [[WSGI]].

- **[[ASGI]] (Asynchronous Server Gateway Interface)** — асинхронный аналог, поддерживает `async`/`await`. Сервер приложений — **[[Uvicorn]]** (часто запускается под управлением [[Gunicorn]] как воркер: `gunicorn -k uvicorn.workers.UvicornWorker`). [[FastAPI]] построен вокруг [[ASGI]].

- И [[WSGI]]-, и [[ASGI]]-сервер выполняют роль прослойки: принимают «сырой» запрос от веб-сервера, превращают его в понятные Python-объекты и передают в код приложения.

- [[Django|Django]] «из коробки» даёт много готового (ORM, авторизация, админка), поэтому его часто выбирают для monolith-приложений и быстрого [[MVP]]. [[FastAPI]] — легче, асинхронный, сейчас чаще выбирается для новых бэкендов.

## 9. [[Nginx]] и [[Алгоритмы балансировки нагрузки]]

**[[Nginx]]** чаще всего используется как:

- **[[Reverse proxy]]** — принимает запросы от клиента и перенаправляет их на нужный внутренний инстанс приложения.

- **[[Алгоритмы балансировки нагрузки]]** — распределяет запросы между несколькими инстансами приложения.

**[[Алгоритмы балансировки нагрузки]]:**

| Алгоритм                 | Суть                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| [[Round Robin]]          | Запросы распределяются по кругу, по очереди на каждый сервер                                                                                    |
| [[Weighted Round Robin]] | То же самое, но с учётом «веса» сервера (более мощный сервер получает больше запросов)                                                          |
| [[Least Connections]]    | Запрос уходит на сервер с наименьшим числом активных соединений                                                                                 |
| [[Sticky Session]]       | Клиент в рамках одной сессии всегда направляется на один и тот же сервер (важно для приложений, хранящих состояние сессии локально на инстансе) |
| **[[IP Hash]]**          | это алгоритм балансировки нагрузки, при котором сервер для клиента выбирается на основе **хеширования его IP-адреса**.                          |
| **[[Random]]**           | это алгоритм балансировки нагрузки, при котором каждый новый запрос направляется на **случайно выбранный сервер** из доступных.                 |
