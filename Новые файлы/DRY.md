# DRY — конспект для Python Backend

## Формула для собеседования

**DRY (Don't Repeat Yourself)** — принцип проектирования программного обеспечения, согласно которому каждое знание о системе должно иметь одно авторитетное представление. Цель — избежать дублирования бизнес-правил и логики, чтобы изменения можно было вносить в одном месте, не рискуя забыть обновить остальные копии.

## Короткий ответ

DRY означает: не дублируй одну и ту же логику в разных местах программы. Если одно бизнес-правило реализовано в нескольких функциях, его изменение потребует исправлять каждую копию, что повышает риск ошибок. Вынеси общую логику в функцию, класс или модуль, если это действительно одна и та же ответственность.

При этом DRY не означает, что нужно объединять любой похожий код. Иногда две похожие реализации отражают разные бизнес-правила, и искусственное объединение только усложнит систему.

## Ответ на собеседовании

DRY — это принцип, который помогает уменьшать дублирование знаний и бизнес-логики в приложении.

Например, если проверка допустимости скидки реализована в трёх разных местах, при изменении правил придётся обновлять все три реализации. Можно забыть одну из них, и приложение начнёт работать непоследовательно.

Вместо этого я выношу правило в отдельную функцию или сервис и использую его во всех необходимых местах. Тогда бизнес-правило имеет единое авторитетное представление, и его проще тестировать и изменять.

Но я не объединяю код только потому, что он выглядит похожим. Если две функции обслуживают разные бизнес-сценарии и могут изменяться независимо, преждевременное объединение создаст лишнюю связанность. Поэтому DRY относится прежде всего к дублированию знаний, а не к механическому устранению одинаковых строк.

## 1. Пример нарушения DRY

Предположим, в интернет-магазине есть два места, где рассчитывается цена со скидкой.

❌ Дублирование логики:

```python
def calculate_order_price(price: float) -> float:
    if price >= 10_000:
        return price * 0.9
    return price


def calculate_cart_price(price: float) -> float:
    if price >= 10_000:
        return price * 0.9
    return price
```

Обе функции содержат одно и то же бизнес-правило: при сумме от 10 000 применяется скидка 10%.

Если размер скидки изменится, придётся исправлять обе функции.

## 2. Как применить DRY

✅ Вынесем общее правило в одну функцию:

```python
def apply_discount(price: float) -> float:
    if price >= 10_000:
        return price * 0.9
    return price


def calculate_order_price(price: float) -> float:
    return apply_discount(price)


def calculate_cart_price(price: float) -> float:
    return apply_discount(price)
```

Теперь правило скидки определено в одном месте. Изменение порога или размера скидки не требует редактировать каждую функцию-потребитель.

В реальном приложении для денежных сумм обычно следует использовать `Decimal`, а не `float`, чтобы избежать ошибок двоичного представления дробных чисел.

## 3. Где применять DRY в Python Backend

### Функции и модули

Повторяющиеся преобразования, вычисления и проверки можно вынести в общую функцию.

```python
def normalize_email(email: str) -> str:
    return email.strip().lower()
```

Если нормализация должна быть одинаковой в нескольких сценариях, единая реализация помогает сохранить единообразие поведения.

### Валидация данных

Если одно бизнес-правило должно действовать во всех сценариях создания и изменения сущности, не стоит независимо реализовывать его в каждом обработчике.

При этом валидация входных данных на уровне API и проверка бизнес-инвариантов — не всегда одно и то же. Их можно организовать на разных уровнях, не дублируя само правило.

### Работа с базой данных

Повторяющиеся операции доступа к данным можно вынести в репозиторий или отдельные функции, если это улучшает структуру проекта.

Однако не нужно создавать универсальный репозиторий только ради устранения нескольких похожих запросов. Абстракция должна приносить реальную пользу.

### Конфигурация

Повторяющиеся значения, такие как тайм-ауты, имена очередей или настройки подключения, лучше хранить в одном подходящем месте, если они должны изменяться согласованно.

При этом одинаковые числовые значения не обязательно являются одним и тем же знанием: например, тайм-аут HTTP-запроса и интервал периодической задачи могут иметь разные причины и изменяться независимо.

### Обработка ошибок

Общую техническую логику логирования, преобразования ошибок или формирования стандартного ответа можно вынести в общий компонент, если семантика обработки действительно одинакова.

Не следует объединять разные бизнес-ошибки в один обработчик, если для них требуются разные действия.

## 4. DRY и похожий код — не одно и то же

Это важное различие.

Предположим, две функции выглядят одинаково:

```python
def calculate_delivery_fee(distance: float) -> float:
    return distance * 10


def calculate_taxi_fare(distance: float) -> float:
    return distance * 10
```

Математическая формула одинакова, но бизнес-правила могут быть разными. Стоимость доставки и тариф такси способны изменяться независимо.

Если объединить их в одну функцию только ради сокращения кода, изменение одного тарифа может случайно повлиять на другой.

**Практическое правило:** объединяй код, когда он выражает одно и то же знание или правило, а не просто выглядит одинаково.

## 5. Когда не нужно применять DRY

Не стоит устранять дублирование любой ценой.

- **Разные бизнес-правила:** одинаковый код может представлять независимые требования.
- **Преждевременная абстракция:** универсальный компонент усложняет простые сценарии.
- **Сильная связанность:** изменения одной функции неожиданно влияют на несколько несвязанных модулей.
- **Неоправданная универсальность:** вместо двух понятных функций появляется сложный механизм с множеством параметров и условий.

Иногда временное дублирование лучше преждевременного объединения. Если выяснится, что правила действительно совпадают и должны изменяться вместе, рефакторинг можно выполнить позднее.

## 6. DRY, KISS и YAGNI

| Принцип | Основной вопрос | Смысл |
|---|---|---|
| **DRY** | Не дублируем ли мы одно знание? | Устранять повторение бизнес-логики и правил |
| **KISS** | Не усложняем ли мы решение? | Выбирать простую и понятную реализацию |
| **YAGNI** | Действительно ли это нужно сейчас? | Не создавать ненужную функциональность заранее |

Эти принципы дополняют друг друга.

Например, можно слишком буквально применить DRY и создать сложный универсальный класс ради двух небольших функций. Это устранит дублирование, но нарушит KISS. Если класс ещё и поддерживает множество гипотетических сценариев, которых нет в требованиях, возникает нарушение YAGNI.

## 7. Частые вопросы на собеседовании

**Что именно запрещает DRY?**

Не всякое повторение кода, а дублирование знаний и логики, которые должны изменяться согласованно.

**Как DRY помогает тестированию?**

Общее правило можно проверить в одном месте, а затем отдельно проверить, что вызывающие компоненты правильно используют его.

**Нужно ли выносить повторяющийся код в отдельную функцию всегда?**

Нет. Нужно учитывать смысл кода, его ответственность и вероятность независимого изменения. Не каждая похожая конструкция заслуживает абстракции.

**Может ли применение DRY ухудшить код?**

Да. Неудачное объединение независимой логики создаёт связанность и усложняет изменение отдельных частей системы.

**Как DRY связан с рефакторингом?**

При рефакторинге можно обнаружить дублирование и вынести общее правило в единое место, сохранив внешнее поведение приложения.

## 8. Шпаргалка

- **DRY:** Don't Repeat Yourself.
- **Цель:** единое авторитетное представление каждого знания или бизнес-правила.
- **Основной приём:** вынести действительно общую логику в функцию, класс или модуль.
- **Польза:** меньше ошибок при изменениях, проще тестирование и сопровождение.
- **Риск чрезмерного применения:** ненужные абстракции и сильная связанность.
- **Главное отличие:** одинаковый код не обязательно означает одинаковое бизнес-правило.
- **Связанные принципы:** KISS, YAGNI, SOLID.
