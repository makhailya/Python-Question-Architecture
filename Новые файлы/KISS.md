# KISS — конспект для Python Backend

## Формула для собеседования

**KISS (Keep It Simple, Stupid)** — принцип проектирования, согласно которому решение должно быть настолько простым, насколько это возможно без потери необходимых требований. Простота уменьшает количество ошибок, облегчает тестирование, поддержку и развитие кода.

## Короткий ответ

KISS означает: не усложняй код без необходимости. Предпочитай понятное решение сложной абстракции, если оба варианта решают задачу одинаково хорошо. Не добавляй лишние классы, уровни абстракции и универсальные механизмы, пока для них нет реальной потребности.

## Ответ на собеседовании

KISS — это принцип разработки программного обеспечения, который рекомендует выбирать наиболее простое решение, удовлетворяющее требованиям задачи.

Например, если нужно проверить, есть ли пользователь в базе данных, достаточно одного понятного метода репозитория. Необязательно создавать фабрику репозиториев, несколько интерфейсов и универсальную систему плагинов, если проект этого не требует.

Простота здесь не означает отсутствие архитектуры или сокращение количества строк любой ценой. Код должен оставаться понятным, надёжным, тестируемым и удобным для изменения.

Я применяю KISS, когда выбираю между несколькими вариантами реализации: оцениваю необходимую функциональность, сложность сопровождения и реальные требования проекта. При этом не отказываюсь от абстракций, если они действительно уменьшают дублирование или изолируют сложность.

## 1. Как применять KISS на практике

### Пример 1. Избыточная абстракция

❌ Слишком сложно для простой задачи:

```python
from abc import ABC, abstractmethod


class GreetingStrategy(ABC):
    @abstractmethod
    def generate(self, name: str) -> str:
        pass


class DefaultGreetingStrategy(GreetingStrategy):
    def generate(self, name: str) -> str:
        return f"Привет, {name}!"


class GreetingFactory:
    @staticmethod
    def create() -> GreetingStrategy:
        return DefaultGreetingStrategy()


greeting = GreetingFactory.create().generate("Илья")
```

✅ Простое решение:

```python
def greet(name: str) -> str:
    return f"Привет, {name}!"


greeting = greet("Илья")
```

В первом варианте есть несколько уровней абстракции, но нет реальной необходимости выбирать стратегию или создавать разные реализации. Функция решает задачу с меньшими затратами на чтение и поддержку.

**Когда первый вариант оправдан:** если действительно требуется переключать стратегии, внедрять разные реализации или расширять поведение через общий интерфейс.

### Пример 2. Не усложняй проверку

❌ Избыточно:

```python
def is_adult(age: int) -> bool:
    if age >= 18:
        return True
    else:
        return False
```

✅ Проще:

```python
def is_adult(age: int) -> bool:
    return age >= 18
```

Второй вариант напрямую выражает условие и не содержит лишних ветвей.

### Пример 3. Не создавай универсальный механизм заранее

Допустим, API должен получать пользователя по идентификатору.

Если проекту нужен только один запрос, не обязательно создавать универсальный движок фильтрации, динамический конструктор SQL и систему расширяемых обработчиков.

Достаточно понятной функции:

```python
def get_user(user_id: int) -> User | None:
    return repository.get_by_id(user_id)
```

При этом SQL-запрос, права доступа, обработку ошибок и другие необходимые требования нельзя упрощать в ущерб корректности или безопасности.

## 2. KISS и соседние принципы

| Принцип | Основная идея | Как различать |
|---|---|---|
| **KISS** | Делай решение простым | Не добавляй лишнюю сложность |
| **DRY** | Не дублируй знания и логику | Выноси действительно повторяющееся поведение |
| **YAGNI** | You Aren't Gonna Need It | Не реализуй функции, которые пока не нужны |
| **SOLID** | Набор принципов объектного проектирования | Организуй код так, чтобы его было проще изменять и расширять |
| **Separation of Concerns** | Разделяй ответственность | Не смешивай несвязанные задачи в одном компоненте |

KISS, DRY и YAGNI дополняют друг друга, но не означают одно и то же.

Например, ради DRY можно создать универсальный абстрактный компонент, который окажется сложнее двух небольших функций. KISS помогает оценить, оправдывает ли устранение дублирования эту дополнительную сложность.

## 3. KISS в Python Backend

Принцип применим на разных уровнях разработки.

- **Функции:** одна понятная задача и предсказуемый результат.
- **Классы:** не вводить классы там, где достаточно функции или простого объекта.
- **API:** понятные HTTP-методы, URL и форматы ответов.
- **База данных:** обычный запрос вместо ненужного универсального слоя запросов.
- **Архитектура:** не дробить приложение на микросервисы без реальной причины.
- **Обработка ошибок:** использовать подходящие исключения, а не создавать сложную систему ошибок для каждого случая.
- **Тестирование:** проверять конкретное поведение без избыточной инфраструктуры.

Пример API на FastAPI:

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

users = {
    1: {"id": 1, "name": "Илья"},
}


@app.get("/users/{user_id}")
def get_user(user_id: int) -> dict:
    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found",
        )

    return user
```

Это небольшой пример понятного обработчика. В реальном приложении хранилище, валидация, авторизация и зависимости должны соответствовать требованиям проекта. KISS не требует помещать всю бизнес-логику в один файл или игнорировать архитектурные границы.

## 4. Когда простота превращается в проблему

KISS не означает, что нужно выбирать самое короткое решение.

Плохое упрощение может привести к следующим проблемам:

- дублированию бизнес-логики;
- отсутствию валидации и обработки ошибок;
- смешению бизнес-логики и доступа к данным;
- небезопасной работе с SQL или пользовательским вводом;
- отказу от нужных абстракций и тестов;
- созданию монолитной функции, которую трудно изменять.

**Правильный критерий:** минимальная необходимая сложность при соблюдении функциональных, нефункциональных требований и ограничений безопасности.

## 5. Как понять, что решение слишком сложное

Перед добавлением абстракции задай себе несколько вопросов:

1. Решает ли она существующую проблему?
2. Есть ли реальные сценарии, которым нужна такая гибкость?
3. Уменьшает ли она сложность для других разработчиков?
4. Можно ли добиться того же результата меньшим количеством концепций?
5. Не станет ли изменение простого поведения слишком трудоёмким?

Если абстракция не приносит измеримой пользы, её лучше не добавлять.

## 6. Частые вопросы на собеседовании

**Означает ли KISS, что нужно писать меньше строк кода?**

Нет. Цель — уменьшить ненужную сложность. Иногда несколько дополнительных строк делают код значительно понятнее.

**Как KISS связан с YAGNI?**

KISS рекомендует не усложнять решение без необходимости. YAGNI конкретнее запрещает реализовывать функциональность на будущее, пока в ней нет реальной потребности.

**Конфликтует ли KISS с SOLID?**

Не обязательно. SOLID помогает организовать изменяемый код, а KISS напоминает не применять абстракции и шаблоны механически. Следует выбирать те архитектурные решения, которые действительно оправданы задачей.

**Всегда ли нужно устранять дублирование по DRY?**

Нет. Две похожие строки могут представлять разные бизнес-правила. Их объединение в универсальный компонент иногда увеличивает связанность. Сначала нужно понять, повторяется ли одна и та же логика или только похожий код.

**Как применять KISS в большом проекте?**

Разделять систему на понятные компоненты с чёткими границами, использовать подходящие абстракции и не добавлять универсальность без реальной потребности. Простота оценивается на уровне системы, а не только отдельной функции.

## 7. Шпаргалка

- **KISS:** Keep It Simple, Stupid.
- **Цель:** уменьшить ненужную сложность.
- **Основной вопрос:** можно ли решить задачу понятнее?
- **Не означает:** писать минимум строк любой ценой.
- **Не запрещает:** архитектуру, абстракции, паттерны и разделение ответственности.
- **Связанные принципы:** DRY, YAGNI, SOLID.
- **Главный критерий:** код должен быть простым для понимания, тестирования и изменения.
