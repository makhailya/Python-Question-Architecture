# Отказоустойчивость в Backend-разработке

## Формула для собеседования

**Отказоустойчивость (Fault Tolerance)** — способность системы продолжать предоставлять сервис при отказе отдельных компонентов или корректно восстанавливаться после сбоев.

Основные механизмы:
- **Timeout** — ограничивает время ожидания ответа.
- **Retry** — повторяет неудачные запросы.
- **Exponential Backoff** — увеличивает интервалы между повторами.
- **Circuit Breaker** — временно прекращает обращения к проблемному сервису.
- **Fallback** — использует запасной сценарий.
- **Bulkhead** — изолирует ресурсы, чтобы отказ одного компонента не перегружал остальные.
- **Health Check** — проверяет состояние приложения.
- **Redundancy** — обеспечивает резервирование компонентов.
- **Graceful Degradation** — сохраняет основную функциональность при недоступности второстепенных возможностей.

**Главный принцип:** отказоустойчивая система не обязательно предотвращает все сбои. Она ограничивает их последствия, сохраняет критически важные функции и обеспечивает восстановление.

---

## Короткий ответ

В распределённых системах отдельные компоненты могут быть недоступны, отвечать с задержкой или возвращать ошибки. Поэтому при проектировании Backend-приложений нужно учитывать не только успешный сценарий, но и поведение при сбоях.

Я использую таймауты, ограниченные повторные попытки, Circuit Breaker и изоляцию ресурсов. Для фоновых задач предусматриваю безопасную повторную обработку, а для критичных данных — транзакции и механизмы восстановления.

Дополнительно применяю мониторинг, логирование, health checks и резервирование. Конкретный набор механизмов зависит от требований к доступности, допустимой потере данных и времени восстановления.

---

## Ответ на собеседовании

Предположим, мой FastAPI-сервис зависит от PostgreSQL, Redis и нескольких внешних API.

Если внешний сервис начинает отвечать медленно, я не должен позволять запросам бесконечно занимать ресурсы приложения. Поэтому задаю таймауты и ограничиваю количество повторных попыток.

Если зависимость продолжает выдавать ошибки, Circuit Breaker временно прекращает обращения к ней. Если операция допускает запасной сценарий, использую Fallback. При этом изоляция ресурсов помогает не допустить, чтобы перегрузка одного компонента затронула всё приложение.

Для фоновых задач предусматриваю повторные попытки и идемпотентную обработку. Для восстановления после сбоев использую мониторинг, health checks, резервные копии и проверенные процедуры восстановления.

Важно выбирать механизмы исходя из характера операции. Например, повторять запрос на чтение обычно безопаснее, чем повторять списание денег без ключа идемпотентности.

# 1. Основные понятия

## 1.1. Fault Tolerance — отказоустойчивость

Способность системы продолжать работу при отказе отдельных компонентов.

Например, если один экземпляр сервиса перестал отвечать, балансировщик направляет запросы на другие работающие экземпляры.

## 1.2. High Availability — высокая доступность

Способность системы оставаться доступной для пользователей в течение требуемого времени.

Для высокой доступности используют несколько экземпляров приложения, резервирование инфраструктуры, автоматическое переключение и мониторинг.

**Разница:**

- Fault Tolerance — система способна переживать отказы.
- High Availability — система стремится минимизировать время недоступности.

Эти понятия связаны, но не являются полными синонимами.

## 1.3. Resilience — устойчивость к сбоям

Способность системы выдерживать нарушения нормальной работы, ограничивать последствия сбоев и восстанавливаться.

В практической разработке Resilience включает обнаружение проблем, изоляцию отказов, деградацию функциональности и восстановление.

## 1.4. Graceful Degradation — деградация функциональности

Если второстепенный компонент недоступен, система продолжает выполнять основные операции.

**Пример:** интернет-магазин не может загрузить рекомендации, но пользователь всё ещё может открыть каталог и оформить заказ.

## 1.5. Single Point of Failure — единая точка отказа

Компонент, отказ которого способен вывести из строя всю систему или критическую часть её функциональности.

Примеры:
- Единственный экземпляр приложения.
- Единственный сервер базы данных без резервирования.
- Один брокер сообщений без подходящего механизма восстановления.
- Единственный Gateway без резервирования.

Наличие нескольких экземпляров приложения не гарантирует отказоустойчивость, если все они зависят от одной уязвимой инфраструктурной точки.

# 2. Timeout — ограничение времени ожидания

## Проблема

Предположим, FastAPI отправляет запрос другому сервису. Если зависимый сервис не отвечает, обработчик может долго удерживать соединение и другие ресурсы.

При большом количестве таких запросов приложение рискует исчерпать доступные ресурсы.

## Решение

Установить таймаут, после которого операция завершается ошибкой.

### Пример на Python

```python
import httpx

from fastapi import FastAPI, HTTPException

app = FastAPI()


@app.get("/weather")
async def get_weather():
    try:
        async with httpx.AsyncClient(
            timeout=2.0
        ) as client:
            response = await client.get(
                "https://weather.example.com/api"
            )
            response.raise_for_status()
            return response.json()

    except httpx.TimeoutException:
        raise HTTPException(
            status_code=504,
            detail="Weather service timeout",
        ) from None

    except httpx.HTTPError:
        raise HTTPException(
            status_code=502,
            detail="Weather service error",
        ) from None
```

Адрес здесь условный — пример показывает структуру обработки ошибок.

### Разбор

- `timeout=2.0` задаёт таймауты HTTP-клиента.
- `response.raise_for_status()` вызывает исключение при HTTP-ошибке.
- `TimeoutException` позволяет отдельно обработать превышение времени ожидания.
- `HTTPException(504)` сообщает клиенту о таймауте зависимой операции.
- `HTTPException(502)` сообщает об ошибке при взаимодействии с внешним сервисом.

В реальном проекте важно отдельно настраивать таймауты подключения, чтения и другие параметры, если этого требует сценарий.

### Важный нюанс

Таймаут не гарантирует, что удалённая операция не выполнилась.

Например, платёжный сервис мог списать деньги, но ответ не успел дойти до клиента.

Поэтому после таймаута нельзя автоматически считать, что операция не состоялась.

**Запомнить:** Timeout ограничивает ожидание, но не отменяет возможные последствия уже выполненной удалённой операции.

# 3. Retry — повторные попытки

## Проблема

Временные сетевые ошибки, кратковременная перегрузка или переключение узлов могут привести к единичному неудачному запросу.

Иногда повторная попытка позволяет успешно выполнить операцию.

## Как работает

1. Выполняется запрос.
2. Если возникает подходящая временная ошибка, запрос повторяется.
3. Количество повторов ограничивается.
4. Если попытки исчерпаны, ошибка передаётся вызывающему коду.

### Пример на Python

```python
import asyncio
import httpx


async def fetch_data(url: str) -> dict:
    for attempt in range(3):
        try:
            async with httpx.AsyncClient(
                timeout=2.0
            ) as client:
                response = await client.get(url)
                response.raise_for_status()
                return response.json()

        except (
            httpx.TimeoutException,
            httpx.ConnectError,
        ):
            if attempt == 2:
                raise

            await asyncio.sleep(0.5 * (2 ** attempt))

    raise RuntimeError("Unreachable")
```

### Что происходит

- `range(3)` — максимум три попытки.
- `attempt` начинается с нуля.
- `raise` повторно выбрасывает последнюю ошибку, если попытки исчерпаны.
- `asyncio.sleep()` делает паузу, не блокируя весь поток выполнения.
- Интервалы между попытками увеличиваются: 0,5 и 1 секунду.

В этом примере обрабатываются только таймауты и ошибки подключения. В реальном приложении набор повторяемых ошибок определяется отдельно.

### Какие запросы безопасно повторять?

| Операция | Повтор |
|---|---|
| HTTP GET | Обычно безопасен, если сервер соблюдает семантику HTTP |
| Получение данных из PostgreSQL | Обычно безопасно |
| Создание заказа | Только при корректной защите от дубликатов |
| Списание денег | Нужна идемпотентность или ключ идемпотентности |
| Отправка письма | Нужна защита от повторной отправки |

**Запомнить:** Retry помогает при временных ошибках, но бесконтрольные повторы способны усилить перегрузку.

# 4. Exponential Backoff и Jitter

## Exponential Backoff

Это стратегия, при которой пауза между повторными попытками увеличивается экспоненциально.

Например:

| Попытка | Пауза |
|---|---:|
| 1 | 0,5 секунды |
| 2 | 1 секунда |
| 3 | 2 секунды |
| 4 | 4 секунды |

На практике обычно устанавливают максимальную паузу и общий предел времени повторных попыток.

## Jitter

Jitter добавляет случайность к интервалам между повторами.

Это необходимо, чтобы множество клиентов не отправляло повторные запросы одновременно.

Если все клиенты повторяют запрос ровно через секунду, возникает синхронная волна нагрузки.

### Пример

```python
import random


def retry_delay(attempt: int) -> float:
    base = 0.5
    maximum = 10.0

    delay = min(
        base * (2 ** attempt),
        maximum,
    )

    return random.uniform(0, delay)
```

Здесь используется Full Jitter: случайная задержка от нуля до вычисленного максимума.

### Где применять

- Вызовы внешних API.
- Взаимодействие с брокерами сообщений.
- Повторное подключение к временно недоступным сервисам.
- Фоновые задачи.

**Важно:** повторные попытки должны укладываться в общий бюджет времени запроса. Иначе приложение может продолжать повторять запросы даже тогда, когда клиент уже перестал ждать результат.

# 5. Circuit Breaker

**Circuit Breaker защищает систему от постоянных обращений к проблемному компоненту.**

### Три состояния

| Состояние | Поведение |
|---|---|
| `CLOSED` | Запросы выполняются, ошибки отслеживаются |
| `OPEN` | Запросы временно блокируются |
| `HALF_OPEN` | Выполняются пробные запросы для проверки восстановления |

### Пример

Интернет-магазин получает рекомендации от отдельного сервиса.

Если сервис рекомендаций перегружен, система временно прекращает обращения к нему и показывает страницу без рекомендаций.

При этом каталог и оформление заказа продолжают работать.

### Circuit Breaker и Retry

Эти механизмы решают разные задачи:

- Retry повторяет запрос после временной ошибки.
- Circuit Breaker ограничивает обращения при устойчивых проблемах.

Их можно использовать вместе, но количество повторов должно быть ограничено.

**Связанная заметка:** [[Микросервисы — 7 архитектурных паттернов#7. Circuit Breaker]]

# 6. Fallback — запасной сценарий

Fallback позволяет вернуть альтернативный результат, когда основная операция недоступна.

### Примеры

- Не удалось получить рекомендации — вернуть пустой список.
- Не удалось получить погоду — показать последнее сохранённое значение с отметкой времени.
- Не удалось получить аватар из внешнего сервиса — использовать изображение по умолчанию.

### Пример на Python

```python
async def get_recommendations(user_id: int) -> list:
    try:
        return await recommendation_service.get(
            user_id
        )
    except RecommendationServiceUnavailable:
        return []
```

Это упрощённый пример: `RecommendationServiceUnavailable` — условное исключение, которое должен определить проект.

### Важное ограничение

Fallback не должен маскировать критические ошибки.

Если система не может подтвердить проведение платежа, нельзя возвращать сообщение об успешной оплате только для того, чтобы интерфейс выглядел работоспособным.

**Запомнить:** запасной сценарий допустим только тогда, когда его результат соответствует бизнес-правилам.

# 7. Bulkhead — изоляция ресурсов

Название происходит от водонепроницаемых переборок на корабле. Если один отсек затапливает, остальные отсеки остаются защищёнными.

В программном обеспечении идея та же: ограничить ресурсы, доступные отдельным компонентам.

### Пример

В приложении есть:
- Запросы к PostgreSQL.
- Запросы к внешнему API.
- Фоновые задачи.

Если внешнее API работает медленно, его запросы не должны занимать все доступные соединения и блокировать работу с базой.

### Как реализовать

- Отдельные пулы соединений.
- Ограниченные очереди.
- Семафоры и лимиты параллелизма.
- Отдельные worker-процессы для разных типов задач.
- Ограничение количества одновременных запросов к внешнему сервису.

### Пример с asyncio

```python
import asyncio

external_api_limit = asyncio.Semaphore(10)


async def call_external_api():
    async with external_api_limit:
        return await external_api_request()
```

В примере допускается не более десяти одновременных операций внутри данного ограничения.

`external_api_request()` — условная функция обращения к внешнему API.

### Важный нюанс

`asyncio.Semaphore` ограничивает параллелизм внутри одного процесса. Если приложение запущено в нескольких worker-процессах или контейнерах, суммарное количество запросов может быть выше.

Для глобального ограничения потребуется отдельный механизм координации.

**Запомнить:** Bulkhead ограничивает влияние перегрузки одного компонента на остальные.

# 8. Health Check — проверка состояния

Health Check позволяет инфраструктуре понять, находится ли приложение в рабочем состоянии.

Обычно различают два вида проверок.

## Liveness

Показывает, работает ли процесс приложения и не завис ли он критическим образом.

Если Liveness-проверка постоянно проваливается, оркестратор может перезапустить контейнер.

## Readiness

Показывает, готово ли приложение принимать трафик.

Например, приложение может запуститься, но ещё не установить необходимые соединения.

В таком случае оно работает, однако пока не должно получать обычные запросы пользователей.

### Пример на FastAPI

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/health/live")
async def liveness():
    return {"status": "alive"}


@app.get("/health/ready")
async def readiness():
    if not app.state.ready:
        return {
            "status": "not_ready"
        }

    return {
        "status": "ready"
    }
```

Здесь `app.state.ready` — условный флаг, который приложение должно правильно устанавливать при старте и завершении работы.

В production readiness-проверка может учитывать доступность критически важных зависимостей.

### Важный нюанс

Не нужно бездумно проверять все внешние сервисы в Liveness.

Если PostgreSQL временно недоступен, но процесс приложения работает, перезапуск контейнера может не решить проблему и даже увеличить нагрузку на систему.

**Запомнить:**
- Liveness — нужно ли перезапустить приложение?
- Readiness — можно ли направлять в него запросы?

# 9. Redundancy — резервирование

Резервирование означает наличие дополнительных компонентов, которые позволяют продолжить работу при отказе основных.

### Примеры

- Несколько экземпляров FastAPI.
- Реплики базы данных.
- Несколько брокеров сообщений.
- Резервные сетевые соединения.
- Несколько зон доступности.

### Горизонтальное масштабирование

Вместо одного экземпляра приложения запускаются несколько.

```text
                Load Balancer
                 /         \
                v           v
           FastAPI 1    FastAPI 2
                \           /
                 v         v
                  PostgreSQL
```

Если один экземпляр приложения выходит из строя, балансировщик может направлять запросы на оставшийся экземпляр.

Но в приведённой схеме PostgreSQL всё ещё является потенциальной единой точкой отказа.

### Важный нюанс

Репликация сама по себе не гарантирует отказоустойчивость.

Необходимо продумать:
- Обнаружение отказа.
- Переключение на резервный узел.
- Согласованность данных.
- Резервное копирование.
- Восстановление после повреждения данных.
- Размещение компонентов в независимых зонах отказа.

**Запомнить:** резервирование помогает переживать отказы, но требует корректного переключения и проверки восстановления.

# 10. Graceful Shutdown — корректное завершение

Graceful Shutdown позволяет приложению завершиться без потери уже выполняемой работы там, где это возможно.

### Что должно происходить

1. Приложение перестаёт принимать новые запросы.
2. Завершает обработку текущих запросов в пределах заданного времени.
3. Корректно завершает фоновые задачи или возвращает их в очередь.
4. Закрывает соединения с БД и внешними сервисами.
5. Завершает процесс.

### Почему это важно

При обновлении контейнера или остановке сервера приложение может получать сигнал завершения.

Если процесс немедленно завершится, текущие запросы и задачи могут оборваться.

### Особенности фоновых задач

Для надёжной обработки задач обычно нужны:
- Подтверждение сообщения после успешной обработки.
- Ограниченное время выполнения.
- Повторная доставка при сбое.
- Идемпотентность обработчика.
- Возможность корректного завершения worker-процесса.

**Запомнить:** Graceful Shutdown уменьшает вероятность прерывания операций при штатной остановке, но не защищает от внезапного отключения питания или аварийного завершения процесса.

# 11. Защита фоновых задач

Фоновые задачи часто обрабатываются через Celery, RabbitMQ или другие очереди.

Чтобы система переживала сбои, нужно предусмотреть несколько механизмов.

## Повторная доставка

Если обработчик завершился аварийно до подтверждения сообщения, брокер может доставить его повторно.

## Идемпотентность

Повторная доставка не должна приводить к повторному списанию денег, созданию дубликата заказа или повторному выполнению другого критического действия.

## Ограничение повторов

Бесконечные повторные попытки могут перегрузить систему.

Для временных ошибок используют ограниченные retries с задержкой.

## Dead Letter Queue

DLQ — очередь для сообщений, которые не удалось обработать по предусмотренным правилам.

Такие сообщения можно анализировать отдельно и при необходимости повторно обрабатывать после устранения причины ошибки.

## Мониторинг очередей

Следует отслеживать:
- Количество сообщений.
- Возраст самого старого сообщения.
- Скорость поступления и обработки.
- Количество ошибок.
- Количество повторов.
- Число сообщений в DLQ.

**Связанная заметка:** [[RabbitMQ]]

# 12. Резервное копирование и восстановление

Резервные копии защищают данные от потери, повреждения и некоторых ошибок оператора.

Однако наличие резервной копии ещё не гарантирует, что систему удастся быстро восстановить.

Нужно регулярно проверять процесс восстановления.

## RPO — Recovery Point Objective

Максимально допустимая потеря данных, выраженная во времени.

Например, RPO в 15 минут означает, что после аварии допустимо потерять изменения примерно за последние 15 минут.

## RTO — Recovery Time Objective

Целевое время восстановления работоспособности после аварии.

Например, RTO в один час означает, что система должна восстановиться в течение установленного часового интервала.

### Пример

Для сервиса заказов бизнес может установить:
- RPO — не более 5 минут.
- RTO — не более 30 минут.

Эти значения являются примером требований, а не универсальными нормами.

Для достижения таких показателей нужно выбрать подходящие методы резервирования, репликации и восстановления, а затем проверить их на практике.

**Запомнить:**
- RPO — сколько данных можно потерять.
- RTO — сколько времени можно потратить на восстановление.

# 13. Observability — наблюдаемость

Отказоустойчивость невозможно обеспечить без понимания того, что происходит внутри системы.

Основные составляющие наблюдаемости:

## Logs — логи

Записи о событиях приложения.

Полезно фиксировать:
- Ошибки внешних API.
- Таймауты.
- Неудачные попытки подключения.
- Повторные попытки.
- Срабатывания Circuit Breaker.
- Ошибки фоновых задач.

## Metrics — метрики

Числовые показатели состояния системы.

Примеры:
- Количество запросов в секунду.
- Доля ошибок.
- Время ответа.
- Количество активных соединений.
- Длина очереди.
- Количество повторных попыток.
- Доступность зависимых сервисов.

## Traces — распределённые трассировки

Позволяют проследить путь одного запроса через несколько сервисов.

Например:

```text
API Gateway
    |
    v
Order Service
    |
    v
Payment Service
    |
    v
PostgreSQL
```

Трассировка помогает понять, какой компонент увеличил время ответа или вызвал ошибку.

### Принцип

Недостаточно собирать логи. Нужно определять значимые показатели, устанавливать пороги оповещения и проверять, что команда способна обнаружить и диагностировать реальные сбои.

# 14. Как механизмы сочетаются друг с другом

Рассмотрим вызов внешнего сервиса из FastAPI.

1. **Timeout** ограничивает время ожидания.
2. **Retry** повторяет запрос при подходящей временной ошибке.
3. **Exponential Backoff + Jitter** распределяют повторы во времени.
4. **Circuit Breaker** прекращает обращения при устойчивых проблемах.
5. **Bulkhead** ограничивает ресурсы, выделенные для зависимости.
6. **Fallback** позволяет продолжить работу по безопасному запасному сценарию.
7. **Metrics и Logs** позволяют обнаружить проблему и оценить эффективность механизмов.

Не обязательно внедрять все механизмы одновременно.

Например, для простого сервиса получения погоды может быть достаточно таймаута и безопасного fallback. Для платёжной системы потребуются более строгие требования к идемпотентности, обработке неопределённого результата операции, мониторингу и восстановлению.

# 15. Типичные ошибки

### Ошибка 1. Повторять любой запрос

**Проблема:** повторная операция может создать дубликат заказа или повторно списать деньги.

**Решение:** определять безопасные для повторов операции и использовать идемпотентность.

### Ошибка 2. Установить Retry без Timeout

**Проблема:** каждая попытка может ждать слишком долго.

**Решение:** задавать таймауты и общий бюджет времени операции.

### Ошибка 3. Бесконечно повторять запросы

**Проблема:** приложение усиливает перегрузку зависимого сервиса.

**Решение:** ограничивать количество повторов, использовать задержки и учитывать `Retry-After`, если это применимо.

### Ошибка 4. Считать репликацию полноценной заменой резервным копиям

**Проблема:** ошибочное удаление или повреждение данных может распространиться на реплики.

**Решение:** сочетать подходящие механизмы репликации с резервным копированием и проверкой восстановления.

### Ошибка 5. Перезапускать приложение при любой проблеме

**Проблема:** если зависимость недоступна, постоянные перезапуски могут не помочь.

**Решение:** различать проблемы процесса, готовности приложения и внешних зависимостей.

### Ошибка 6. Возвращать успешный ответ при неизвестном результате операции

**Проблема:** клиент считает платёж или заказ успешно выполненным, хотя это не подтверждено.

**Решение:** использовать состояния операции, безопасную проверку результата и механизмы идемпотентности.

# 16. Вопросы для собеседования

## Чем отличаются Retry и Circuit Breaker?

Retry повторяет отдельную операцию после подходящей ошибки.

Circuit Breaker временно блокирует обращения к зависимости при устойчивых проблемах.

## Зачем нужен Timeout?

Чтобы ограничить время ожидания и не позволить медленным зависимостям бесконтрольно занимать ресурсы приложения.

## Почему Retry может ухудшить ситуацию?

Повторные запросы увеличивают нагрузку на уже перегруженный сервис. Если много клиентов повторяют запросы одновременно, возникает дополнительный всплеск трафика.

## Что такое Bulkhead?

Изоляция ресурсов, которая ограничивает влияние отказа или перегрузки одного компонента на другие.

## Чем Liveness отличается от Readiness?

Liveness показывает, нужно ли перезапустить процесс. Readiness показывает, готов ли экземпляр приложения принимать трафик.

## Что такое RPO и RTO?

RPO задаёт допустимую потерю данных во времени. RTO задаёт целевое время восстановления.

## Почему резервная копия не гарантирует восстановление?

Копия может оказаться неполной, повреждённой или несовместимой с процедурой восстановления. Поэтому восстановление необходимо регулярно проверять.

## Можно ли гарантировать полное отсутствие отказов?

Нет. Можно уменьшать вероятность отказов и их последствия, но распределённые системы должны быть рассчитаны на ошибки оборудования, сети, приложений и операторские ошибки.
