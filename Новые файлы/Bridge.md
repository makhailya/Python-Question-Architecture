# Bridge — конспект для Python Backend

## Формула для собеседования

**Bridge (Мост)** — структурный паттерн проектирования, который разделяет абстракцию и её реализацию, позволяя развивать их независимо друг от друга.

**Формула:**

`Абстракция → Реализация`

Они связаны через композицию: абстракция содержит ссылку на объект-реализацию и делегирует ему выполнение конкретных операций.

Главная идея: вместо одной иерархии классов с множеством комбинаций создать две независимые иерархии, которые можно расширять отдельно.

## Короткий ответ

Bridge нужен, когда у системы есть два независимых измерения изменчивости.

Например, приложение поддерживает разные типы уведомлений — обычные и срочные — и разные каналы доставки: Email, SMS и Telegram.

Без Bridge можно создать отдельный класс для каждой комбинации: `EmailNotification`, `UrgentEmailNotification`, `SmsNotification`, `UrgentSmsNotification` и так далее.

Bridge позволяет отделить тип уведомления от способа доставки. Новые типы уведомлений и новые каналы добавляются независимо.

## Ответ на собеседовании

Bridge — это структурный паттерн проектирования, который разделяет абстракцию и реализацию, чтобы они могли изменяться независимо друг от друга.

Вместо наследования для каждой комбинации используется композиция: объект абстракции хранит ссылку на объект реализации и делегирует ему часть работы.

Например, в Python Backend можно отделить бизнес-логику уведомлений от каналов доставки. Тип уведомления определяет содержание и правила обработки, а реализация канала отвечает за отправку через Email, SMS или Telegram.

Главное преимущество Bridge — уменьшение количества классов-комбинаций и независимое расширение обеих сторон. Недостаток — дополнительные интерфейсы и объекты, которые могут быть избыточны для простой системы.

## 1. Какую проблему решает Bridge

Представим Backend-приложение, которое отправляет уведомления.

Есть два измерения:

- **Тип уведомления:** обычное, срочное.
- **Канал доставки:** Email, SMS, Telegram.

Если реализовывать каждую комбинацию отдельным классом, количество классов будет расти вместе с числом вариантов.

Например:

```python
class EmailNotification:
    pass


class UrgentEmailNotification:
    pass


class SmsNotification:
    pass


class UrgentSmsNotification:
    pass
```

При добавлении Telegram и ещё нескольких типов уведомлений количество комбинаций продолжит увеличиваться.

Это проблема комбинаторного роста наследования.

Bridge разделяет систему на две части:

1. Абстракция — тип уведомления и его бизнес-поведение.
2. Реализация — конкретный механизм доставки.

Теперь эти части можно расширять независимо.

## 2. Структура паттерна

| Компонент | Назначение |
|---|---|
| Abstraction | Определяет высокоуровневый интерфейс |
| Refined Abstraction | Расширяет поведение абстракции |
| Implementor | Определяет интерфейс реализации |
| Concrete Implementor | Реализует конкретный механизм |

В примере с уведомлениями:

- `Notification` — Abstraction;
- `UrgentNotification` — Refined Abstraction;
- `NotificationSender` — Implementor;
- `EmailSender`, `SmsSender` — Concrete Implementor.

**Важно:** абстракция в Bridge — это не обязательно Python-класс с `ABC`. Это роль в архитектуре: высокоуровневый объект, который использует отдельную реализацию.

## 3. Реализация Bridge на Python

### Шаг 1. Определяем интерфейс реализации

```python
from abc import ABC, abstractmethod


class NotificationSender(ABC):
    @abstractmethod
    def send(self, recipient: str, message: str) -> None:
        pass
```

Этот интерфейс описывает способ отправки уведомления, не определяя бизнес-правила уведомлений.

### Шаг 2. Реализуем каналы доставки

```python
class EmailSender(NotificationSender):
    def send(self, recipient: str, message: str) -> None:
        print(f"Email для {recipient}: {message}")


class SmsSender(NotificationSender):
    def send(self, recipient: str, message: str) -> None:
        print(f"SMS для {recipient}: {message}")


class TelegramSender(NotificationSender):
    def send(self, recipient: str, message: str) -> None:
        print(f"Telegram для {recipient}: {message}")
```

Каждый класс отвечает только за свой способ доставки. В реальном приложении здесь находились бы вызовы SMTP-сервера или API провайдера.

### Шаг 3. Создаём абстракцию

```python
class Notification:
    def __init__(self, sender: NotificationSender):
        self._sender = sender

    def notify(self, recipient: str, message: str) -> None:
        self._sender.send(recipient, message)
```

Класс `Notification` не знает, как именно отправляется сообщение. Он делегирует отправку объекту `sender`.

### Шаг 4. Добавляем расширенную абстракцию

```python
class UrgentNotification(Notification):
    def notify(self, recipient: str, message: str) -> None:
        urgent_message = f"[СРОЧНО] {message}"
        self._sender.send(recipient, urgent_message)
```

Срочное уведомление добавляет бизнес-поведение, но не зависит от конкретного канала доставки.

### Шаг 5. Используем разные комбинации

```python
email = EmailSender()
sms = SmsSender()
telegram = TelegramSender()

regular = Notification(email)
urgent = UrgentNotification(sms)

regular.notify("user@example.com", "Заказ оформлен")
urgent.notify("+79990000000", "Оплата не прошла")

telegram_notification = UrgentNotification(telegram)
telegram_notification.notify("123456", "Сервис недоступен")
```

Результат: любой поддерживаемый тип уведомления можно сочетать с любой подходящей реализацией отправки.

Чтобы добавить новый канал, например Push, достаточно реализовать `NotificationSender`. Чтобы добавить новый тип уведомления, достаточно расширить `Notification`.

Это и есть независимое развитие двух сторон Bridge.

## 4. Почему Bridge использует композицию

Ключевой принцип — **предпочитать композицию наследованию**, когда поведение можно делегировать отдельному объекту.

При наследовании приходится создавать классы под комбинации двух характеристик:

```text
EmailNotification
UrgentEmailNotification
SmsNotification
UrgentSmsNotification
TelegramNotification
UrgentTelegramNotification
```

При Bridge используются две независимые группы:

```text
Абстракция:
Notification
└── UrgentNotification

Реализация:
NotificationSender
├── EmailSender
├── SmsSender
└── TelegramSender
```

Количество классов становится примерно пропорциональным сумме вариантов двух групп, а не количеству их комбинаций.

Если есть \(m\) типов уведомлений и \(n\) каналов:

- при отдельных классах для комбинаций может потребоваться до \(m \times n\) классов;
- при Bridge достаточно примерно \(m + n\) классов, не считая общих интерфейсов.

Это оценка для сравнения архитектур, а не обязательное число классов в любой реализации.

## 5. Когда применять Bridge

Bridge подходит, когда:

- у системы есть два или более независимых измерения изменчивости;
- обе стороны нужно расширять независимо;
- наследование приводит к большому количеству классов-комбинаций;
- высокоуровневая логика должна быть отделена от технических деталей;
- требуется подменять реализацию во время выполнения.

### Примеры в Python Backend

**Уведомления.** Тип сообщения отделён от канала доставки.

**Платёжная система.** Высокоуровневые сценарии платежей отделены от интеграций с провайдерами, если эти измерения действительно развиваются независимо.

**Хранилища файлов.** Бизнес-операции над файлами отделены от механизмов хранения: локальная файловая система, S3-совместимое хранилище или другое хранилище.

**Экспорт отчётов.** Логика формирования отчёта отделена от механизма вывода, если оба направления требуют независимого расширения.

## 6. Когда Bridge не нужен

Не стоит применять паттерн, если:

- есть только одна реализация;
- второй аспект системы не планируется расширять;
- достаточно обычного полиморфизма;
- дополнительные интерфейсы делают код сложнее без ощутимой пользы.

Например, если приложение отправляет только Email и не имеет нескольких типов уведомлений, отдельная архитектура Bridge может быть избыточной.

Паттерн должен решать реальную проблему расширяемости, а не просто увеличивать количество классов.

## 7. Bridge vs Adapter

Bridge и Adapter внешне похожи: оба часто используют композицию и делегирование. Однако назначение у них разное.

| Критерий | Bridge | Adapter |
|---|---|---|
| Основная задача | Разделить абстракцию и реализацию | Согласовать несовместимые интерфейсы |
| Когда применяется | При проектировании расширяемой системы | При интеграции с существующим компонентом |
| Направление работы | Позволяет развивать обе стороны независимо | Преобразует один интерфейс в другой |
| Типичный пример | Тип уведомления + канал доставки | Адаптер стороннего SMS API к интерфейсу приложения |

**Запомнить:**

- Bridge проектирует независимые стороны системы.
- Adapter помогает совместить уже существующие несовместимые интерфейсы.

## 8. Bridge vs Strategy

Bridge также можно спутать со Strategy, поскольку оба паттерна используют композицию и делегирование.

| Критерий | Bridge | Strategy |
|---|---|---|
| Основная задача | Разделить две независимые иерархии | Инкапсулировать взаимозаменяемые алгоритмы |
| Фокус | Архитектурное разделение двух измерений | Выбор алгоритма поведения |
| Пример | Тип уведомления + канал доставки | Выбор алгоритма расчёта скидки |

Граница не всегда однозначна: одна и та же реализация может напоминать оба паттерна. Определяющим является не синтаксис кода, а архитектурная задача.

## 9. Связь с SOLID и Dependency Injection

### Dependency Inversion Principle (DIP)

Высокоуровневая логика уведомлений зависит от интерфейса `NotificationSender`, а не от конкретного `EmailSender` или `SmsSender`.

Это снижает связанность и облегчает тестирование.

### Open-Closed Principle (OCP)

Можно добавить новый канал доставки, реализовав `NotificationSender`, не изменяя существующую бизнес-логику уведомлений.

### Dependency Injection (DI)

Реализация передаётся в конструктор:

```python
notification = Notification(EmailSender())
```

В реальном Backend-приложении выбор реализации может происходить в конфигурации приложения или контейнере зависимостей.

Bridge не является DI-контейнером: он задаёт архитектурное разделение, а DI помогает передавать нужные зависимости.

## 10. Типичные ошибки

1. **Путать Bridge с Adapter.** Bridge разделяет независимые части архитектуры, Adapter согласует интерфейсы.
2. **Путать Bridge со Strategy.** Нужно смотреть на цель разделения, а не только на композицию.
3. **Создавать классы для каждой комбинации.** Это возвращает исходную проблему комбинаторного роста.
4. **Привязывать абстракцию к конкретному классу.** Например, хранить внутри `Notification` именно `EmailSender`, а не абстракцию реализации.
5. **Вводить Bridge без необходимости.** Если система проста и не предполагает независимого расширения двух сторон, паттерн может быть избыточен.

## 11. Вопросы для собеседования

### Что такое Bridge?

Это структурный паттерн, разделяющий абстракцию и её реализацию, чтобы они могли изменяться независимо.

### Какую проблему он решает?

Уменьшает количество классов-комбинаций при наличии нескольких независимых измерений изменчивости.

### Почему используется композиция?

Абстракция хранит ссылку на реализацию и делегирует ей работу, вместо того чтобы создавать отдельный подкласс для каждой комбинации.

### Чем Bridge отличается от Adapter?

Bridge проектирует независимое взаимодействие двух сторон системы. Adapter преобразует интерфейс существующего компонента в интерфейс, ожидаемый клиентом.

### Чем Bridge отличается от Strategy?

Bridge разделяет абстракцию и реализацию как два независимых направления расширения. Strategy заменяет один алгоритм другим.

### Как реализовать Bridge в Python?

Определить интерфейс реализации, создать его конкретные реализации, затем реализовать абстракцию, которая принимает объект реализации через конструктор и делегирует ему работу.
