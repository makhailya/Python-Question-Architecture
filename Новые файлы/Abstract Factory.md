# Abstract Factory — конспект для Python Backend

## Формула для собеседования

**Abstract Factory (абстрактная фабрика)** — порождающий паттерн проектирования, который предоставляет интерфейс для создания **семейств связанных объектов**, не привязывая код к конкретным классам этих объектов.

Ключевая идея: клиент работает с абстрактной фабрикой и абстрактными продуктами, а конкретная фабрика определяет, какие именно объекты будут созданы.

**Формула:**

`Клиент → Абстрактная фабрика → Конкретная фабрика → Семейство совместимых объектов`

## Короткий ответ

Abstract Factory нужен, когда приложение должно создавать несколько связанных объектов, которые должны работать совместно.

Например, приложение поддерживает PostgreSQL и MongoDB. Для каждой базы нужны собственные реализации репозитория и клиента. Фабрика PostgreSQL создаёт совместимые с PostgreSQL компоненты, а фабрика MongoDB — компоненты для MongoDB.

Это позволяет переключать семейства объектов без изменения бизнес-логики.

## Ответ на собеседовании

Abstract Factory — это порождающий паттерн, который инкапсулирует создание семейств взаимосвязанных объектов. Он определяет общий интерфейс фабрики, а конкретные фабрики реализуют создание продуктов определённого семейства.

Например, в Python Backend-приложении могут быть разные способы работы с хранилищем. Фабрика PostgreSQL создаёт PostgreSQL-репозиторий и соответствующий клиент, а фабрика MongoDB — MongoDB-репозиторий и клиент. Код приложения зависит от абстракций, а не от конкретных реализаций.

Главное преимущество — согласованное создание совместимых объектов и возможность заменять семейства реализаций. Недостаток — усложнение архитектуры: для каждого нового семейства обычно приходится добавлять новую фабрику и реализации продуктов.

## 1. Какую проблему решает Abstract Factory

Представим, что приложение работает с двумя системами хранения данных:

- PostgreSQL;
- MongoDB.

Для каждой системы необходимы два компонента:

- репозиторий для работы с данными;
- клиент для взаимодействия с хранилищем.

Без фабрики клиентский код может содержать условия:

```python
if database_type == "postgres":
    repository = PostgresRepository()
    client = PostgresClient()
elif database_type == "mongo":
    repository = MongoRepository()
    client = MongoClient()
```

Проблемы такого подхода:

- бизнес-логика знает о конкретных классах;
- условия выбора реализации могут дублироваться;
- легко случайно смешать несовместимые компоненты;
- добавление нового семейства требует изменения клиентского кода.

Abstract Factory переносит создание объектов в отдельные фабрики.

## 2. Структура паттерна

В классическом варианте участвуют четыре основных элемента.

| Элемент | Назначение |
|---|---|
| Abstract Factory | Определяет методы создания продуктов |
| Concrete Factory | Создаёт конкретное семейство продуктов |
| Abstract Product | Определяет интерфейс продукта |
| Concrete Product | Реализует конкретный продукт |

**Клиент** использует интерфейсы фабрики и продуктов, не зная конкретных классов.

## 3. Реализация на Python

### Шаг 1. Определяем интерфейсы продуктов

В примере у каждого семейства есть репозиторий и клиент базы данных.

```python
from abc import ABC, abstractmethod


class Repository(ABC):
    @abstractmethod
    def get_user(self, user_id: int) -> dict:
        pass


class DatabaseClient(ABC):
    @abstractmethod
    def connect(self) -> None:
        pass
```

Абстрактные классы задают контракт, которому должны соответствовать реализации.

### Шаг 2. Создаём продукты PostgreSQL

```python
class PostgresRepository(Repository):
    def get_user(self, user_id: int) -> dict:
        return {"id": user_id, "database": "PostgreSQL"}


class PostgresClient(DatabaseClient):
    def connect(self) -> None:
        print("Подключение к PostgreSQL")
```

### Шаг 3. Создаём продукты MongoDB

```python
class MongoRepository(Repository):
    def get_user(self, user_id: int) -> dict:
        return {"id": user_id, "database": "MongoDB"}


class MongoClient(DatabaseClient):
    def connect(self) -> None:
        print("Подключение к MongoDB")
```

### Шаг 4. Определяем абстрактную фабрику

```python
class DatabaseFactory(ABC):
    @abstractmethod
    def create_repository(self) -> Repository:
        pass

    @abstractmethod
    def create_client(self) -> DatabaseClient:
        pass
```

Фабрика объявляет методы создания всех продуктов, входящих в семейство.

### Шаг 5. Реализуем конкретные фабрики

```python
class PostgresFactory(DatabaseFactory):
    def create_repository(self) -> Repository:
        return PostgresRepository()

    def create_client(self) -> DatabaseClient:
        return PostgresClient()


class MongoFactory(DatabaseFactory):
    def create_repository(self) -> Repository:
        return MongoRepository()

    def create_client(self) -> DatabaseClient:
        return MongoClient()
```

Каждая фабрика создаёт согласованное семейство объектов.

### Шаг 6. Клиент работает через абстракции

```python
def run_application(factory: DatabaseFactory) -> None:
    client = factory.create_client()
    repository = factory.create_repository()

    client.connect()
    user = repository.get_user(1)
    print(user)


factory = PostgresFactory()
run_application(factory)
```

Чтобы переключиться на MongoDB, достаточно передать `MongoFactory()` вместо `PostgresFactory()`.

Функция `run_application()` не изменяется и не зависит от конкретных классов продуктов.

> Пример демонстрирует структуру паттерна. В реальном приложении клиент базы данных обычно передаётся репозиторию через конструктор, а подключение, конфигурация и управление ресурсами организуются отдельно.

## 4. Как выбирать конкретную фабрику

Abstract Factory сам по себе не определяет, какая реализация нужна. Выбор обычно выполняется на уровне конфигурации приложения — например, в точке входа или composition root.

```python
import os


def get_database_factory() -> DatabaseFactory:
    database = os.getenv("DATABASE", "postgres")

    factories = {
        "postgres": PostgresFactory,
        "mongo": MongoFactory,
    }

    try:
        return factories[database]()
    except KeyError:
        raise ValueError(
            f"Неизвестная база данных: {database}"
        ) from None
```

Использование:

```python
factory = get_database_factory()
run_application(factory)
```

Переменная окружения `DATABASE` определяет семейство продуктов.

**Практический принцип:** инфраструктурные зависимости выбираются на границе приложения, а бизнес-логика получает уже готовые абстракции.

## 5. Abstract Factory vs Factory Method

Эти паттерны часто путают, потому что оба связаны с созданием объектов.

| Критерий | Factory Method | Abstract Factory |
|---|---|---|
| Основная задача | Делегировать создание конкретного продукта | Создавать семейство связанных продуктов |
| Масштаб | Обычно один тип продукта | Несколько типов продуктов |
| Интерфейс | Метод создания продукта | Несколько методов создания продуктов |
| Пример | Создать конкретный парсер | Создать парсер и совместимый валидатор |
| Главный акцент | Какой объект создать | Какие совместимые объекты создать вместе |

**Запомнить:**

- Factory Method — выбор реализации одного продукта.
- Abstract Factory — создание семейства совместимых продуктов.

Паттерны могут сочетаться: методы конкретной Abstract Factory нередко реализованы как фабричные методы.

## 6. Abstract Factory vs простой фабричный метод или функция

Для Python важно не применять паттерн автоматически.

Простая функция-фабрика часто достаточна:

```python
def create_repository(database: str) -> Repository:
    if database == "postgres":
        return PostgresRepository()
    if database == "mongo":
        return MongoRepository()

    raise ValueError("Неизвестная база данных")
```

Используй простую функцию, если нужно создать один объект и семейства связанных компонентов нет.

Abstract Factory оправдан, когда:

- создаются несколько типов взаимосвязанных объектов;
- у каждого семейства есть свои совместимые реализации;
- клиентский код должен оставаться независимым от конкретных классов;
- семейств достаточно много, чтобы централизовать их создание.

## 7. Преимущества и недостатки

### Преимущества

- **Согласованность:** фабрика создаёт совместимые продукты одного семейства.
- **Слабая связанность:** клиент зависит от интерфейсов, а не от конкретных классов.
- **Удобная замена реализаций:** можно переключить семейство через конфигурацию.
- **Централизация создания:** логика построения объектов не размазана по приложению.
- **Удобство тестирования:** фабрики можно подменять тестовыми реализациями.

### Недостатки

- **Больше классов и интерфейсов:** простое решение может стать чрезмерно сложным.
- **Сложно добавлять новый вид продукта:** интерфейс фабрики и все конкретные фабрики приходится расширять.
- **Не решает все вопросы зависимостей:** создание объектов не заменяет полноценное управление жизненным циклом соединений и ресурсов.
- **Может дублировать DI-контейнер:** если контейнер зависимостей уже решает ту же задачу, отдельные фабрики могут быть лишними.

## 8. Где применяется в Python Backend

### Работа с разными хранилищами

Фабрика создаёт набор совместимых адаптеров для разных СУБД или внешних хранилищ.

### Интеграции с внешними API

Например, разные провайдеры платежей могут требовать создания клиента, адаптера проверки статуса и обработчика ответов.

### Несколько инфраструктурных окружений

Разные реализации компонентов для production, тестового окружения и локальной разработки.

### Экспорт документов

Семейства объектов для PDF, CSV или XLSX: генератор документа, форматтер и валидатор. Однако если создаётся только один объект экспорта, отдельная Abstract Factory обычно не нужна.

## 9. Связь с Dependency Injection

Abstract Factory и Dependency Injection (DI) решают связанные, но разные задачи.

- **Abstract Factory** определяет, как создавать семейства объектов.
- **Dependency Injection** обеспечивает передачу зависимостей потребителям вместо их самостоятельного создания.
- **DI-контейнер** может выбирать и собирать реализации, фактически выполняя часть работы фабрики.

В FastAPI зависимости часто передаются через `Depends()`. Если приложение имеет несколько сложных семейств инфраструктурных компонентов, Abstract Factory может быть частью конфигурации зависимостей. Но для обычного `get_db()` отдельная иерархия фабрик чаще всего избыточна.

## 10. Типичные ошибки

1. **Создавать фабрику ради одного простого объекта.** Сначала проверь, достаточно ли функции.
2. **Смешивать продукты разных семейств.** Это нарушает основную гарантию паттерна.
3. **Выбирать реализацию внутри бизнес-логики.** Клиент должен получать фабрику снаружи.
4. **Путать Abstract Factory с Factory Method.** Первый ориентирован на семейства продуктов.
5. **Считать фабрику менеджером ресурсов.** Она создаёт объекты, но не обязательно управляет соединениями, закрытием и временем жизни.
6. **Добавлять интерфейсы без практической необходимости.** В Python иногда достаточно протоколов `typing.Protocol` или простой функции.

## 11. Вопросы для собеседования

### Зачем нужен Abstract Factory?

Для создания семейств взаимосвязанных объектов через общий интерфейс без привязки клиента к конкретным классам.

### Какую проблему он решает?

Снижает связанность и помогает гарантировать, что используемые компоненты принадлежат одному совместимому семейству.

### Чем отличается от Factory Method?

Factory Method обычно делегирует создание одного продукта, а Abstract Factory предоставляет набор методов для создания семейства продуктов.

### Можно ли реализовать его без `ABC`?

Да. В Python можно использовать `typing.Protocol`, обычные классы или функции. `ABC` — один из способов явно задать интерфейс, а не обязательное требование паттерна.

### Как добавить новое семейство?

Создать новые реализации продуктов и конкретную фабрику, реализующую интерфейс абстрактной фабрики. Клиентский код при этом, как правило, не меняется, но конфигурацию выбора фабрики потребуется обновить.

### Какой главный недостаток?

Добавление нового типа продукта усложняет расширение системы: придётся расширить интерфейс фабрики и реализовать новый метод во всех конкретных фабриках.

### Когда не стоит использовать Abstract Factory?

Когда приложение создаёт один объект, семейства продуктов не связаны между собой или задача уже просто решается функцией-фабрикой либо DI-контейнером.
